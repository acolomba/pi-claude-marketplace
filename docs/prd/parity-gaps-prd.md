# Product Requirements Document: Claude Code parity gaps

**Document version:** 1.2

**Date:** 2026-11-11

**Status:** Input for milestone planning. No requirement here is approved or scheduled.

**Audience:** The maintainer, and the agents that will plan design and implementation work from this document.

______________________________________________________________________

## 1. Purpose

`pi-claude-marketplace` installs real Claude Code plugins on the Pi coding agent. It translates each plugin component into a Pi-native artifact. This document lists the gaps that the 2026-11-11 analysis found between what Claude Code does with a plugin and what this project does, for the six component kinds the project supports: commands, skills, hooks, MCP servers, workflows, and subagents. It also covers the plugin container features that those six kinds depend on.

Each gap that can be closed is written as a requirement. Section 7 defines the two forms a requirement can take.

The analysis had two objectives:

1. Use more of what the latest Pi and its companion extensions offer, so that more Claude Code plugin behavior works. Parts of the current code and documentation were written against older versions. For example, the hook event audit in `docs/research/claude-hooks-vs-pi-events.md` dates from Pi 0.73.
2. Align behavior with Claude Code where Pi allows it, and keep the core design of Pi and of this project. The project is not a Claude Code emulator. A requirement that would rebuild a Claude Code subsystem is out of scope.

**A proposed measure of success.** The official plugins that the analysis found affected must work end to end on Pi: `security-guidance`, `hookify`, `ralph-loop`, `code-modernization`, `claude-security`, and the five plugins of the `anthropics/skills` marketplace. This set is the test for the priorities in section 6: a gap that breaks one of these plugins ranks above a gap that no plugin in the sample shows.

### 1.1 What a new reader needs to know

**The system.** The existing product PRD, [`pi-claude-marketplace-prd.md`](pi-claude-marketplace-prd.md), describes the system, and its section 3 is the glossary. Its "Component" entry predates hooks and workflows support. `.planning/codebase/ARCHITECTURE.md` describes the code layers.

**The companion extensions.** Four packages besides Pi appear throughout this document:

- **Pi's built-in MCP:** part of Pi since 1.5.0. It connects MCP servers with no extension.
- **pi-mcp-adapter:** an extension that connects MCP servers with more features than the built-in. When it is loaded, the project uses it in place of the built-in.
- **pi-subagents:** an extension that runs subagents from agent files. The project writes one agent file for each plugin agent.
- **pi-dynamic-workflows** (`@quintinshaw/pi-dynamic-workflows`): an extension that runs saved workflow scripts. This document calls it "the workflow engine".

**Terms this document uses.**

- **Upstream:** Claude Code, and only Claude Code. Pi and the companion extensions are named.
- **Bridge:** the part of this project that translates one component kind. "The hooks bridge" translates hooks; "a bridged agent" is an agent file the agents bridge wrote.
- **Stage:** to write the translated copy of a component into the Pi-side location at install time. "The staged skill" is that copy.
- **Partially available:** the resolver's verdict for a plugin that declares something Pi cannot run. A normal install refuses such a plugin. `install --partial` installs the parts that work.
- **Install note** and **warning:** a line that an install or the `info` command prints about one component. Neither refuses the install.
- **Profile:** one of the two test configurations of the cucumber suite, `adapter` (pi-mcp-adapter loaded) and `builtin` (Pi's built-in MCP).
- **Scripted model:** the test stand-in for a language model. A scenario gives it the replies and tool calls to play.
- **The `run_plugin_command` tool:** the tool this project registers so that the model can run a plugin command.
- **The skill-read fill:** the step that fills `${CLAUDE_*}` variables when the model reads a staged `SKILL.md`.

**Where the records are.** This document cites recorded decisions and open items by ID.

- Decision IDs that start with `D-`, and the requirement IDs `NFR-n`, `SC-n`, `SUB-n`, `AG-n`, `SK-n`, and `MATCH-V2-n`, are in `.planning/PROJECT.md`. Some are also in the product PRD.
- Milestone requirement IDs such as `ANAME-n` and `WNAM-n` are in the `*-REQUIREMENTS.md` files under `.planning/milestones/`.
- Open items written as "BACKLOG `<ID>`" are in `.planning/BACKLOG.md`.
- `grep -rn '<ID>' .planning docs/prd` finds any of them.

The rule that section 5 applies, "a divergence from Claude Code needs a recorded decision or a Pi capability gap", is the "Upstream parity" constraint in `AGENTS.md`.

## 2. Summary

The analysis found 85 requirements, listed in section 6, and about 70 Claude Code behaviors that this project cannot deliver today. It also found about 70 statements in the project's own documentation, code comments, and planning records that are wrong or out of date.

**Read this first: nothing below was observed in a run, except where a spike in section 9 says so.** The findings come from reading source and documentation. "Does nothing" and "fails" mean "the code path leads there".

The P0 findings. Each is a defect in behavior the project says it supports, and each affects a plugin in the sample or every plugin of a kind.

01. **A plugin cannot start its own workflow by name (WF-01).** The reference rewriter adds a leading slash to the workflow name inside `Workflow({ name: "plugin:wf" })`. The workflow engine's tool refuses a name with a slash. Both official plugins that ship workflows start them this way. Fixing this is necessary and not sufficient: two engine behaviors in section 8 also affect those plugins.
02. **Hooks on file tools get Pi's field names (HOOK-01).** A hook on `Read`, `Edit`, or `Write` receives `path` and `edits`, not `file_path`, `old_string`, and `new_string`. The official `security-guidance` and `hookify` plugins read the Claude names.
03. **Hook matchers are too strict (HOOK-03).** A comma list or a regular expression drops the hook group. A matcher on `UserPromptSubmit` or `Stop` also drops the group, where Claude Code ignores the matcher and runs the hook.
04. **The `Stop` loop limit is one too low and misses two rules (HOOK-13).** A loop plugin such as `ralph-loop` is cut after seven continuations.
05. **Subagents are forced to the foreground, against Claude Code's default (AGENT-01, HOOK-07a).** Decision D-CF4-05 records that Claude Code runs subagents in the foreground by default. Spike S12 found that the probes behind that decision ran headless and asked for the foreground in each call; none tested the default. The documentation, the 2.1.322 binary, and an interactive 2.1.322 session all show the background as the default.
06. **Two dependency floors are behind (AGENT-02 with AGENT-07 b, MCP-02).** pi-subagents 0.87.0 fixed both bugs that kept a background subagent from a plugin's MCP tools; the floor is 0.84.0. pi-mcp-adapter 7.0.1 shortens tool names longer than 64 characters, and the project does not model that.
07. **A plugin MCP tool call that is silent for 60 seconds fails (MCP-01).** This holds when the plugin declares no timeout and the tool reports no progress. Claude Code allows 30 minutes for a stdio server and 5 minutes for a remote server. No plugin in the sample declares a timeout.
08. **A marketplace entry that lists its skills installs every skill (CORE-01).** For an entry whose source is the marketplace root, Claude Code loads only the listed skill folders. All five plugins of the `anthropics/skills` marketplace have this shape.
09. **A relative link from one skill to a sibling skill points at nothing (SKILL-04).** Two official plugins have such links.
10. **A workflow does not keep an agent's tool restriction (SEC-01).** A plugin agent that Claude Code restricts to read-only tools holds `bash`, `edit`, and `write` when a workflow uses it as an agent type. Spike S4 confirmed this with a run of the workflow engine's own code.

Other findings worth knowing before planning:

- **Pi has an event for `Stop` hooks that the project does not use (HOOK-02, P1).** The project's documentation calls the `Stop` timing difference "irreducible". Pi 0.87.0, which is older than the 1.5.0 floor, added the `agent_before_settle` event. The repository has no reference to it.
- **`userConfig` blocks a normal install (CORE-03, P1).** The project treats it as an unsupported component kind. In Claude Code it is an input to hooks and MCP servers.
- **A project-scope plugin's `bin` directory reaches `PATH` without the project trust check (CORE-06, P1).** The fix is cheap, but it does not close the wider gap behind it (SEC-02): Pi reports a project as trusted when it holds only this extension's files, so every trust gate of this project is weaker than it looks.

Section 5 lists the decisions for the maintainer. The five that gate the P0 work were answered on 2026-11-11.

## 3. Scope

In scope:

- The six supported component kinds, and the plugin container features they depend on: manifest fields, path variables, `userConfig` as an input, the plugin `bin` directory, the plugin `settings.json`, and plugin naming.
- Pi 1.5.2, pi-mcp-adapter 7.0.1, pi-subagents 0.88.0, and pi-dynamic-workflows 3.15.1, compared against Claude Code 2.1.322.

Out of scope:

- Marketplace add, remove, and update mechanics, install scopes, and version resolution.
- The component kinds the project does not bridge: `lspServers`, `monitors`, `themes`, `outputStyles`, `channels`, `syntaxHighlighting`, the hooks module (`mod`), and `binaries`.
- Any requirement that needs a rebuild of a Claude Code subsystem: the permission system, agent teams, task tools, the session-as-agent mode, and channels.
- Architecture. This document states behavior. Component layout and data flow are deferred to the design of each milestone.

## 4. Method and evidence

Six research passes ran in parallel, one for each area. Each pass built three inventories from primary sources: the Claude Code contract, the capability of the latest Pi or extension, and the current behavior of this project. Each pass then compared them.

| Pi and extensions | The unpacked npm packages of Pi 1.5.2, `@earendil-works/pi-mcp` 1.5.2, pi-mcp-adapter 7.0.1, pi-subagents 0.88.0, and pi-dynamic-workflows 3.15.1: documentation, type definitions, source, and changelogs |

**Requirement IDs.** An ID in this document is the ID in its report, with these exceptions. Where two reports found the same gap, this document keeps one ID: `MCP-07` is `AGENT-02`; `SKILL-02` and `CMD-02` are `CORE-05`; `PI-03` is `HOOK-10`; `MCP-11` is part of `CORE-03`. `HOOK-07` is split into `HOOK-07a` and `HOOK-07b`. `DOC-01` and `SEC-01` to `SEC-03` are new here. Where a report and this document disagree, this document is right.

**Sample sets.** Statements about how often plugins use a feature come from three sets on the analysis machine:

- **The local sample:** the clone of the official marketplace, `claude-plugins-official`. It holds 17 plugin folders with local content: 40 skills, 33 commands, 40 agents, 7 workflow scripts, 7 hook files, and 14 `.mcp.json` files, each of which declares one server. The catalog lists 317 plugins, and most come from remote sources that were not fetched. "0 uses" in this document means "0 uses in the local sample".
- **The cached plugins:** 21 plugins in the Claude Code plugin cache of that machine.
- **"76 plugins":** the 55 `plugin.json` files in the clone plus the 21 cached plugins.

The `anthropics/skills` marketplace is a separate marketplace. Only its `marketplace.json` was fetched.

Limits of the evidence. Read these before you trust a requirement.

- **No live session ran in the analysis.** No Pi session, no Claude Code session, and no `npm` script ran. Statements about run-time behavior come from source, documentation, or a pure function run in isolation. Section 9 lists the checks that need a live run. Five have run since (S1, S2 in part, S3, S4, and S12), and section 9 records their results.
- **The claims were re-checked twice, and both checks found errors.** A first check re-read the main claims in the source and corrected two errors in the reports: `WebFetch` and `WebSearch` have no session tool to map to (HOOK-16), and a `SKILL.md` at the plugin root is discovered only when the manifest declares it (SKILL-06). A document review on 2026-11-11 then found one error made in this document: the hook matcher rule in HOOK-03 left out the space character. All P0 entries were then compared with their reports. The P1 and P2 entries were not compared in that way. Planning for a milestone should re-read each requirement against its report.
- **Confidence is stated for each full-form requirement** as High, Medium, or Low. High means all three sides were read in primary sources. Medium means one side is inferred. Low means the requirement needs a spike or a decision before it is real.

A divergence from Claude Code is legitimate only when a recorded decision covers it or when Pi cannot do it. The analysis found recorded decisions whose stated reason is no longer true, and divergences that no decision covers. Each row ends with the question to answer.

## 6. Requirement list by priority

The priorities rank value. They do not depend on whether a requirement waits for a decision or a spike; those are separate columns.

- **P0:** A defect in behavior the project says it supports, which affects a plugin in the sample today or every plugin of a kind. Also an open security question.
- **P1:** A defect in supported behavior that no plugin in the sample shows, or a parity gain that a plugin in the sample uses. The capability exists, and the size is small or medium.
- **P2:** A parity gain that no plugin in the sample uses. Not scheduled. Promote one when a plugin that needs it is found. A wider count over the 317 catalog entries would test these rows cheaply.
- **P3:** Possible, but of low value or close to rebuilding a Claude Code subsystem. Recorded so that nobody investigates it again. Not recommended.

Each row is one requirement, and the four tables hold 85 rows. A requirement that has parts with different priorities has one row for each part. Four rows are not translation gaps: `DOC-01` is a documentation page, and `SEC-01` to `SEC-03` are security questions. The "Decision" and "Spike" columns point to sections 5 and 9.

## 7. Requirements by area

**Two forms.** Every P0 requirement and most P1 requirements have the full form. The other requirements are rows in a table; a P1 row states its acceptance.

The full form has these fields:

- **Upstream:** what Claude Code does.
- **Today:** what this project does.
- **Enabler:** the Pi or extension capability that makes the change possible, with the minimum version when it is above the declared floor. "None needed" means that the change is inside this project.
- **Requirement:** the behavior to build, as a user or a plugin sees it. It does not choose a design. Where a requirement names a function or a file, that is evidence of where the behavior lives today, not an instruction.
- **Acceptance:** the user-visible proof, written so that it can become a cucumber scenario.
- **Notes:** risks, dependencies, open questions (marked "Open:"), and how often plugins in the sample use the feature (marked "Use:").

**Paths.** A path that starts with `domain/`, `bridges/`, `orchestrators/`, `edge/`, `platform/`, `persistence/`, or `shared/` is under `extensions/pi-claude-marketplace/`. Other paths are relative to the repository root. A path inside another package names the package.

**Sizes.** S is one day or less. M is two to five days. L is more than a week.

**Existing installs.** A requirement that changes what an install writes takes effect for an installed plugin at its next `update` or `reinstall`. These requirements rename or remove an artifact of an installed plugin, and their design must say how: CORE-01, CORE-02, AGENT-01, AGENT-05, MCP-01, MCP-06, WF-06.

**What the test harness can run.** The cucumber harness can run a stand-in subagent child: a Pi process that carries the marker pi-subagents sets, with the scripted model and recording hooks (`features/plugin/subagent-child.feature`). It cannot run a real detached child that pi-subagents starts (BACKLOG AGTASYNC-01). Where an acceptance needs a real child, it says so.

**Two tool-name tables.** The project has two tables that map Claude tool names to Pi tool names. The hook table (`domain/components/hook-tool-names.ts`) decides which tool a hook matcher names. The agent table (`TOOL_MAP` in `bridges/agents/convert.ts`) decides which tools an agent is granted. They already differ. Each requirement that adds a tool name says which table it means. Whether to merge the tables is a design question.

### 7.1 Skills and commands

**State of parity.** A typed plugin command or skill no longer runs as a static prompt template. The extension handles it in Pi's `input` event. There it fills arguments by Claude Code's rules, fills the `${CLAUDE_*}` variables, and runs `` !`command` `` injection. The model can run a command through the `run_plugin_command` tool, and the skill-read fill covers a model read of a staged `SKILL.md`. Pi 1.5.1 and 1.5.2 add nothing new for skills, templates, or commands. Two planning records still describe the earlier state: D-CF3-02 and BACKLOG SKILLMODEL-01. This area has one P0 requirement and four P1 requirements.

#### SKILL-04 -- A relative link to a sibling skill points at nothing

Priority P0. Size S. Confidence High.

- **Upstream:** A plugin skill stays inside the plugin tree, so `../other-skill/references/x.md` resolves.
- **Today:** Each skill is staged alone under its generated name `<plugin>-<folder>`. The sibling is staged beside it under its own generated name, so `../build-mcp-server/...` is a dead path. The reference rewriter covers `plugin:skill` tokens only. Pi tells the model that references are relative to the staged folder, so the model follows the dead path.
- **Enabler:** None needed. The pass that rewrites `plugin:skill` tokens in staged Markdown (`rewriteSupportingMarkdown`) already knows the installed names.
- **Requirement:** In a staged `SKILL.md` and its supporting Markdown, a relative link to a sibling skill of the same plugin resolves to that sibling's staged folder.
- **Acceptance:** Skill `a` says `See ../b/ref.md`. After install, the text the model receives names a path that exists and holds `b`'s file.
- **Notes:** Open: a path that climbs to the plugin root (`../../docs/x.md`) also breaks, and this requirement does not cover it. If that case matters later, an option is to stage a plugin's skills under one folder that keeps the original folder names; whether Pi's skill discovery accepts that was not checked. Use: 2 of 40 skills, in the official `mcp-server-dev` and `plugin-dev` plugins.

#### SKILL-01 / CMD-01 -- `@file` references are not attached

Priority P1. Size S to M. Confidence Medium.

- **Upstream:** A `@path` reference in the body of a local skill or command attaches the named file to the prompt. The binary also parses `@"path with spaces"` and a `#L10-20` line range.
- **Today:** Nothing handles it. The model receives the literal `@path` text. No decision, backlog entry, or scenario mentions it.
- **Enabler:** The extension already builds the final text in its `input` transform. Pi's own form for an attached file is `<file name="<abs>">`, the content, and `</file>` (Pi `dist/cli/file-processor.js:60`).
- **Requirement:** A typed bridged command or skill attaches each `@path` reference that its author wrote and that names an existing regular text file. A `@path` that arrives through an argument, including an argument the model passes to the `run_plugin_command` tool, or through the output of an injected `!` command, is not attached. References inside fenced code and code spans are not attached.
- **Acceptance:** A command body `Review @${CLAUDE_PLUGIN_ROOT}/templates/x.md` reaches the scripted model with the template text in a `<file>` block. A second scenario: the user types `/demo:review @/etc/hostname`, and the model receives the argument as text with no `<file>` block.
- **Notes:** The second rule exists because an attached file does not pass through a `PreToolUse` hook on `Read`. Open: what text Claude Code attaches, and whether it attaches a path that arrives through an argument (spike S8); a size limit and symbolic links, for design; what a directory reference does. Use: 1 of 40 skills (`claude-security`); the `plugin-dev` plugin teaches the pattern in more than 20 places.

#### CMD-09 -- A command loses its Claude Code name when its file name starts with the plugin name

Priority P1. Size S. Confidence High.

- **Upstream:** `asana/commands/asana-setup.md` is `/asana:asana-setup`.
- **Today:** Pi lists `/asana:setup` (D-141-01). `/asana:asana-setup` is not an alias, because command aliases come only from the frontmatter `name`. A skill in the same case does keep its Claude Code name as an alias.
- **Enabler:** None needed.
- **Requirement:** A bridged command also answers to Claude Code's own name for it, `/<plugin>:<path>:<file>`, whenever that name differs from its Pi name.
- **Acceptance:** With `demo/commands/demo-lint.md`, the typed text `/demo:demo-lint x` sends the body.
- **Notes:** Needs decision 13. Use: 1 of 33 commands.

#### SKILL-11 / CMD-10 -- Alias suggestions show no description and no argument hint

Priority P1. Size S. Confidence High.

- **Upstream:** The `/` menu lists `/plugin:skill` with its description and argument hint.

### 7.2 Hooks

**State of parity.** The bridge admits 10 of the 33 Claude Code hook events: `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Stop`, `StopFailure`, `PreCompact`, and `PostCompact`. It runs only the `command` handler type. It subscribes to 11 of Pi's 41 extension events. The largest gaps are not missing events. They are in the data that hooks receive and in the matcher parser, and they affect hooks that the project reports as supported.

"The three tool events" below are `PreToolUse`, `PostToolUse`, and `PostToolUseFailure`.

#### HOOK-01 -- Tool payloads use Pi's field names

Priority P0. Size M. Confidence High.

- **Upstream:** For `Read`, `Edit`, and `Write`, `tool_input` carries an absolute `file_path`. `Edit` carries `old_string` and `new_string`. The `Bash` timeout is in milliseconds. A hook's `updatedInput` and `updatedToolOutput` use the same shapes.
- **Today:** The bridge sends Pi's own input object under the Claude tool name (`bridges/hooks/payloads/pre-tool-use.ts:38`). A `Read` hook receives `{"path": ...}`, and `features/hook/tool-failure.feature:54` asserts exactly that. A hook's `updatedInput` is written back key by key, so a Claude-shaped rewrite of an `Edit` deletes Pi's `path` and `edits` and breaks the call. The header of `features/hook/tool-use.feature` says hooks get "the tool call in Claude's shape", which is true only for `bash`. No decision covers this.
- **Enabler:** None needed. Pi's tool schemas are typed and stable, and a `tool_call` handler may change the input.
- **Requirement:** For the tools in the hook table, a hook receives a Claude-shaped `tool_input`, and a Claude-shaped `updatedInput` from a hook changes the call as the hook intended. Pi's `edit` tool can carry several replacement pairs in one call, where Claude's `Edit` carries one. No pair of a multi-pair edit escapes a hook that matches `Edit`. For MCP tools, `updatedMCPToolOutput` is honored as `updatedToolOutput` is.
- **Acceptance:** A scripted `edit` call with one pair makes a recording hook receive `{"file_path":"{project dir}/a.txt","old_string":"x","new_string":"y"}`. A hook that blocks on the text of the second pair of a two-pair `edit` blocks the call. A hook returns a Claude-shaped `updatedInput` for `Write`, and the file on disk has the rewritten content.
- **Notes:** Open, for design: how a multi-pair edit is presented (one hook run for each pair, or one run with all pairs); how `updatedInput` maps back for a multi-pair edit; how far to translate `tool_response`; `Glob` and `Grep` options differ in meaning from Pi's `find` and `grep`. The `if` condition evaluator reads Pi's fields today and must keep working. Use: 14 files in the 7 official hook plugins read `file_path`.

#### HOOK-03 -- Matchers: lists, regular expressions, and events that ignore the matcher

Priority P0. Size S to M. Confidence High.

- **Upstream:** A matcher that holds only letters, digits, `_`, `-`, spaces, `,`, and `|` is an exact list: Claude Code splits it on `|` and `,` and trims each name. Any other matcher is an unanchored regular expression. `UserPromptSubmit` and `Stop` ignore the matcher and run the hook every time.
- **Today:** Any character outside `[A-Za-z0-9_|-]` makes a tool matcher `regex` and drops the hook group (`domain/components/hooks/matcher.ts:4`). So `Edit, Write`, `^Bash$`, and `mcp__.*__write.*` all make the plugin partially available. A matcher on `UserPromptSubmit` or `Stop` also drops the group.
- **Enabler:** None needed.
- **Requirement:** Three parts. (a) An exact-list matcher with commas or spaces matches each listed tool. (b) A matcher on `UserPromptSubmit` or `Stop` is ignored, and the group runs. (c) Any other matcher is a regular expression tested against the Claude-form tool name; a pattern that does not compile drops the group.
- **Acceptance:** (a) `Edit, Write` runs on a scripted `write` call. (b) A `Stop` hook with a matcher runs, and the plugin installs without `--partial`. (c) A `PreToolUse` hook with the matcher `^Ba.*` runs on a scripted `bash` call and not on `read`.
- **Notes:** Parts (a) and (b) are defects and need no decision. For part (c), decisions 6 and 24 were answered on 2026-11-11: regular expressions are allowed, and `info` reports such a group as supported. Use: 1 regular expression matcher in the 7 official hook plugins (`claude-security`).

#### HOOK-13 -- The `Stop` loop limit is one too low and never resets on a tool call

Priority P0. Size S. Confidence Medium.

- **Upstream:** Eight consecutive blocks continue; the ninth is overridden. The count resets when the model calls a tool. `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` changes the limit.
- **Today:** The count is compared with `>=` against a limit of 8, so the eighth block is overridden and seven continuations run (`bridges/hooks/runtime.ts:275-277`). The count resets only on user input or on a settle that does not block. `docs/hooks-compatibility.md:78` says the limit is "identical".
- **Enabler:** None needed.
- **Requirement:** A `Stop` hook can block eight times in a row before the limit applies. A run that called a tool starts the count again.
- **Acceptance:** No cucumber scenario covers the limit today. A `Stop` hook that always blocks makes eight re-entries, and then the limit notice appears. A `Stop` hook that blocks ten times, with a tool call in each iteration, is never overridden.
- **Notes:** Confidence is Medium because the reset rule is from the documentation; the binary was read for the count and for the variable name only. Reading `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` is a separate small addition and is not part of this requirement. Use: the official `ralph-loop` plugin relies on many consecutive blocks.

#### HOOK-07a -- A background subagent runs the plugin's hooks as if it were a main session

Priority P0. Size M. Confidence Medium.

- **Upstream:** Inside a subagent, plugin hooks on tool events fire with `agent_id` and `agent_type`. The session events of the main conversation do not fire there; `SubagentStart` and `SubagentStop` take their place.
- **Today:** A pi-subagents background child loads this extension. The hooks bridge has no child check, so it fires `SessionStart(startup)`, `UserPromptSubmit` on the task text, `Stop` at the child's settle, and `SessionEnd`. A check for a child exists (`platform/subagent-child.ts`), but only the reconcile and the agent grants step use it.
- **Enabler:** pi-subagents sets `PI_SUBAGENT_CHILD=1` in the child's environment.
- **Requirement:** In a pi-subagents child, the plugin's `SessionStart`, `UserPromptSubmit`, `Stop`, and `SessionEnd` hooks do not run. Tool hook payloads carry `agent_type`, and `agent_id` when the child can know it.
- **Acceptance:** With the stand-in child of `features/plugin/subagent-child.feature`: a plugin with recording `SessionStart` and `Stop` hooks records no run of either, and its `PreToolUse` hook still runs.
- **Notes:** This is one item with AGENT-01: once agents run in the background by default, the bridge runs in every child, and a `Stop` hook that blocks there would keep the child running. Design should treat the child case as a mapping from main-session events to subagent events, not as a list of events to skip, so that HOOK-07b can later run `SubagentStart` and `SubagentStop` in the child, where a block is possible. Spike S2 ran this with the stand-in child: the plugin's `UserPromptSubmit` and `Stop` hooks ran there. Confidence stays Medium because a real detached child was not run.

#### HOOK-02 -- Run `Stop` on `agent_before_settle`, so that a block continues the same run

Priority P1. Size M. Confidence High.

- **Upstream:** A blocking `Stop` hook prevents the stop and continues the conversation. `Stop` does not run after a user interrupt.
- **Today:** `Stop` runs at `agent_settled`, after Pi has settled, and re-enters with a follow-up message that starts a new run. Every listener of `agent_settled` sees a false "finished" between blocks, `before_agent_start` fires again, and in print mode the process may exit before the re-entry. `docs/hooks-compatibility.md:76-80` calls this "one irreducible divergence".
- **Enabler:** `agent_before_settle`, in Pi since 0.87.0, which is older than the 1.5.0 floor. Pi's documentation says it "is the final actionable boundary: it can append session entries and request one continuation", and that an aborted run skips it.
- **Requirement:** A `Stop` hook that blocks continues the same run. Listeners of `agent_settled` see one event for a run, however many times a `Stop` hook blocked.
- **Acceptance:** A run that a `Stop` hook blocks twice raises one `agent_settled` event, and shows no second run start.
- **Notes:** Spike S1 ran this on Pi 1.5.2 in print mode. The event fired again after each continuation it granted: nine continuations in one run, one `agent_settled` at the end, and `before_agent_start` once. So the boundary can carry the eight continuations of HOOK-13. Each continuation is one model request. Pi waited for a handler that took 20 seconds; the 600-second case was not run. Not run: the terminal and RPC modes, and Pi 1.5.0. Use: 4 of the 7 official hook plugins have a `Stop` hook.

#### HOOK-04 -- Missing stdin fields

#### MCP-01 -- A server without `timeout` fails after 60 seconds of silence

Priority P0. Size S. Confidence Medium.

- **Upstream:** With no `timeout`, only the idle timer stops a call: "The idle window defaults to five minutes for HTTP, SSE, WebSocket ... servers, and to 30 minutes for stdio servers". `MCP_TOOL_TIMEOUT` sets a limit on the whole call, and `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` sets the idle window. A remote server also has a 60-second timer to its first response byte.
- **Today:** The project writes a timeout only when the plugin declares one. Otherwise both implementations use their own default of 60 seconds. `docs/mcp-compatibility.md:588` records this as "a Pi capability gap". Neither environment variable is read.
- **Enabler:** Both timeouts already restart when the tool reports progress, which is the meaning of the Claude Code idle timer. Pi `timeout` in seconds; adapter `requestTimeoutMs`. No floor change.
- **Requirement:** A tool call of a plugin server that declares no `timeout` may be silent for as long as Claude Code allows: 30 minutes for a stdio server and 5 minutes for a remote server. Under the adapter, a timeout the user wrote on the entry still wins.
- **Acceptance:** Under both profiles, the registered configuration of a stdio plugin server with no declared timeout shows a 30-minute timeout. A scenario with a tool that is silent for more than 60 seconds is the full proof and is slow; design decides whether to keep it.
- **Notes:** Decision 4 was answered yes on 2026-11-11, with 5 minutes for remote servers. Risk: a stdio server that hangs now blocks a call for 30 minutes, where today it blocks for 1 minute. That is the Claude Code behavior. Confidence is Medium because of the remote case: Claude Code's 60-second first-byte timer means that a remote server that does not stream also fails there. Reading `MCP_TOOL_TIMEOUT` and `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` is a separate small addition and is not part of this requirement. Use: all 14 servers in the sample declare no `timeout`.

#### MCP-02 -- The adapter 7.0.1 shortens names over 64 characters, and the project does not model it

Priority P0. Size M. Adapter only. Confidence Medium.

- **Upstream:** Tool names are not shortened up to 128 characters.
- **Today:** The adapter profile returns the full name (`domain/mcp-implementation.ts:72-80`). The hooks bridge passes an adapter tool name through unchanged. The agents bridge writes the full name into `excludeTools`. `docs/mcp-compatibility.md:126` says "the names of plugin tools are not shortened". Only the built-in path models a shortened name.
- **Enabler:** In pi-mcp-adapter 7.0.1, "A name longer than 64 characters is now shortened to 64 and ends in a short hash". The hash is the first 8 hexadecimal digits of the SHA-256 of the full joined name (pi-mcp-adapter `types.ts:968-991`), so the project can compute it. 7.0.1 is inside the declared range.
- **Requirement:** Under the adapter, a plugin tool whose Claude Code name is longer than 64 characters still works everywhere the project names it: a hook matcher written with the Claude Code name matches it, the hook receives the Claude Code name, and an agent's disallowed-tool entry for it removes it.
- **Acceptance:** The adapter twin of the long-name scenario in `features/mcp-server/listing.feature`; a hook scenario whose matcher is the full Claude Code name of a long tool; an agent scenario where a long tool named in `disallowedTools` is not offered to the child.
- **Notes:** Decision 3 was answered on 2026-11-11: the floor rises to 7.0.1, so the project models one behavior. Risk: the hash rule is in the adapter's source, not in a published contract, so a later adapter release can change it; a test against the installed adapter should hold the rule. A mismatch in the agent case leaves a disallowed tool available. The name budget is `12 + plugin + 1 + server + 2 + tool` characters: a plugin `chrome-devtools-mcp` with the server `chrome-devtools` leaves 15 characters for the tool name. Spike S3 ran the adapter's naming code and confirmed the shortened name; the hook effect in a session was not run, so confidence stays Medium.

### 7.4 Workflows

**State of parity.** A Claude workflow script loads in the workflow engine, and its statements run. The behavior differs in the eight ways that the last table of this section lists. Recorded decisions D-CF7-01 to D-CF7-04, which cover approval before a run, slash arguments, and script admission, still hold against engine 3.15.1 and Pi 1.5.2. Engine 3.15.0 to 3.15.1 changes nothing relevant. pi-subagents 0.88.0 also runs workflow scripts, but with a different API and no saved registry, so it is not a better target.

How the engine finds a plugin's agents: the agents bridge writes each agent file with the name `<plugin>:<agent>`, and the engine reads the same agent files and keys its agent types on that name. So `agent("...", { agentType: "<plugin>:<agent>" })` in a script binds the bridged agent.

One planning record is out of date. BACKLOG WOUT-01 says that workflow subagents get no tools. Since engine 3.13.1 the engine creates subagents through Pi's `createAgentSession`, and they get `read`, `bash`, `edit`, and `write`.

What a workflow subagent does not get: no MCP tools, no plugin hooks, and no plugin skills, because the engine loads no extension in a subagent. It also does not run on the session model unless the engine setting `inheritMainModel` is on.

#### WF-01 -- A workflow name inside `Workflow({ name: ... })` gets a leading slash

Priority P0. Size S. Confidence High.

- **Upstream:** A plugin's commands and skills start its workflows through the `Workflow` tool, by registered name: `Workflow({ name: "code-modernization:modernize-harden-scan", args: {...} })`.
- **Today:** The reference rewriter turns every `<plugin>:<source>` token that names a staged workflow into `/<workflow name>` (`domain/skill-tokens.ts:113-115`). The token pattern accepts a quote before the token, so the string inside the tool call is rewritten too. The engine's `workflow` tool refuses any name that contains `/`: `no saved or built-in workflow named "/code-modernization:..."`.
- **Enabler:** None needed. The same name without the slash loads the saved workflow this bridge wrote.
- **Requirement:** A reference to a plugin workflow that the source wrote with no leading slash names the installed workflow with no leading slash. A reference that the source wrote with a leading slash keeps it.
- **Acceptance:** A fixture plugin has a workflow `scan` and a command whose body says `Workflow({ name: "demo:scan" })`. The scripted model runs the command, calls `workflow` with the name copied from the prompt it received, and the run completes. Today the prompt holds `/demo:scan` and the call fails.
- **Notes:** This requirement is necessary for the two official workflow plugins and not sufficient. Two engine behaviors in section 8 remain: the engine's tool text tells the model to call `workflow` only when the user opted in, so a model may decline a plugin command's instruction; and `parallel()` rejects where six of seven official scripts expect a `null` slot. The scripted model always calls, so the acceptance does not show the first. Risk: a model given the failed call today may retry without the slash, so the present effect is not certain. Open: does any existing fixture rely on a bare `plugin:workflow` mention becoming a slash command? The rewrite was confirmed by running the pure function on the real plugin files; a full install was not run. Use: 9 call sites in 7 files, in both official plugins that ship workflows.

#### SEC-01 -- A workflow agent type does not keep its tool restriction

Priority P0. Size S. Confidence High.

- **Upstream:** An agent's `tools` list restricts it, also when a workflow uses the agent as an `agentType`.
- **Today:** The engine filters its own custom tools by the agent type's tool list. It passes no tool list to Pi when it creates the child session, and Pi keeps its own `read`, `bash`, `edit`, and `write` active. Spike S4 ran the engine's child-session code (engine 3.15.1, Pi 1.5.2): a child whose agent type allows only `read` held `read`, `bash`, `edit`, and `write`, and a child whose agent type denies `bash` still held `bash`. A user can start a saved plugin workflow by its typed command today, so this does not depend on WF-01.
- **Enabler:** None in this project: the engine creates the child, and the agents bridge cannot change that call. The engine removes the denied tools only when its codemode option is on.
- **Requirement:** Until the engine enforces the restriction: the compatibility page says that a workflow does not keep an agent's tool restriction, and the install of a plugin whose workflow script names an agent with a `tools` or `disallowedTools` field prints a note. The engine request in section 8.4 is filed.
- **Acceptance:** A plugin with an agent `reader` (`tools: Read`) and a workflow that uses `agentType: "demo:reader"` installs with the note, and `info` shows it.
- **Notes:** The spike stopped before a model request, so it shows which tools the child session offers, not a tool call. Use: `agentType` is in 7 of 7 official scripts; the agents they name declare `tools: Read, Glob, Grep, Bash`, so for those agents the practical loss is `edit` and `write`.

#### WF-02 -- `agentType` names plugin agents, nothing proves the binding, and a missing agent fails without a message

Priority P1. Size S for the scenario and the documentation, M for the install note. Confidence High.

- **Upstream:** `agentType` is resolved from the agent registry. An unknown type throws `agent type '<x>' not found`.
- **Today:** The binding rests on two source reads and no scenario. When the agent is not installed, the engine logs one line and runs a default agent with default tools. `docs/workflows-compatibility.md:126` says an unresolved `agentType` "is not an error on either side", which is wrong for Claude Code.
- **Enabler:** None needed for the note. The project already parses workflow scripts into a syntax tree (`domain/workflow-script.ts`).
- **Requirement:** (a) A workflow's `agent("...", {agentType: "demo:helper"})` runs the plugin's agent `helper`. (b) The install of a plugin whose script names an `agentType` that the plugin does not install prints one note for each such name. A note never refuses the install. ### 7.5 Subagents

**State of parity.** The agents bridge writes one agent file for pi-subagents for each plugin agent. Naming matches Claude Code: the declared name is `<plugin>:<name>`. Skill preloading, the `effort` to `thinking` mapping, and the warnings for fields that Claude Code ignores on plugin agents are in place. The gaps are in the launch mode, the tool mapping, the model mapping, and the frontmatter parser.

How pi-subagents runs a child decides what a bridged agent can reach. A **background** child loads the parent's extensions, so plugin MCP tools and plugin hooks can work in it. A **foreground** child is created with no extensions, so neither can. Both facts are from pi-subagents 0.88.0 source. The agent table today maps seven Claude tool names: `Read`, `Bash`, `Edit`, `Write`, `Grep`, `Glob`, and `LS`.

#### AGENT-01 -- Bridged agents are forced to the foreground

Priority P0. Size S, or M with HOOK-07a. Confidence High.

- **Upstream:** The documentation says: "With nothing configured, a subagent that Claude spawns from your main conversation starts in the background." The CHANGELOG entry for 2.1.198 says "Subagents now run in the background by default". `background: true` only means "keep it in the background even when Claude asks to wait".
- **Today:** Every agent without `background: true` gets `async: false` (`bridges/agents/convert.ts:1035`). D-CF4-05 records the reason as "Upstream runs agents in the foreground by default". An agent that has plugin MCP tools already gets `async: true` (D-CF6-10), so plugin MCP tools are reachable today for those agents.
- **Enabler:** pi-subagents defaults to the background. Leaving out the `async` line hands the choice to pi-subagents and to the user's `asyncByDefault` setting. No floor change.
- **Requirement:** A bridged agent runs in the launch mode that pi-subagents chooses, unless the source sets `background: true` or the agent has plugin MCP tools; those two run in the background. The warning for agents with MCP tools no longer says that Claude Code runs them in the foreground.
- **Acceptance:** `subagent get` shows no `async false` line for a plain agent. The scenario "A call that leaves the launch mode open runs a bridged agent in the foreground" in `features/agent/frontmatter.feature` is replaced. A full background run needs a real child.
- **Notes:** Decision 1 was answered yes on 2026-11-11. Spike S12 settled the premise. The probes behind D-CF4-05 ran under `claude -p` with `run_in_background: false` in each call, so they did not test the default. In an interactive 2.1.322 session, 13 of 13 subagents started in the background with no parameter, and the binary's tool text says "Agents run in the background by default". The documentation adds that in an interactive session Claude cannot wait for a subagent unless the user turns fork mode off; in `claude -p`, Claude can wait on its own judgment. What this requirement gains, beyond the agents with MCP tools: the same launch mode as Claude Code, and plugin tool hooks inside the child. What it costs: the parent gets an acknowledgement and not the child's reply, so a plugin command that delegates and then uses the result in the same turn behaves differently; headless `pi -p` runs wait for background work only up to a timeout. A user who wants the foreground sets `asyncByDefault: false` in pi-subagents; this project adds no setting. This is one item with HOOK-07a. The stored text of the MCP warning is matched byte for byte when agent files are rewritten, so the old and the new text must both be recognized. Agent files of installed plugins keep `async: false` until `update` or `reinstall`. Use: all 40 agents in the sample; none sets `background`.

#### CORE-03 -- `userConfig` is treated as an unsupported kind

Priority P1 for step 1, P2 for steps 2 and 3. Size S, S, M. Confidence High for step 1.

- **Upstream:** A plugin declares options in `userConfig`. Each value is exported to hooks as `CLAUDE_PLUGIN_OPTION_<KEY>` and fills `${user_config.KEY}` in hook commands, in MCP configurations, and in skill and agent content. A sensitive value is kept out of skill content.
- **Today:** `userConfig` is in the closed set of unsupported kinds, so the plugin is refused without `--partial`. With `--partial`, hooks get no option variable and `${user_config.KEY}` stays literal everywhere.
- **Enabler:** For step 3, `ctx.ui.select`, `ctx.ui.input`, and `ctx.ui.confirm`. Steps 1 and 2 need none.
- **Requirement, in three steps:**
  1. *Defaults and export.* Each option resolves to its `default`. Hooks receive `CLAUDE_PLUGIN_OPTION_<KEY>`. `${user_config.KEY}` is filled in exec-form hook commands and arguments, in the five MCP fields that take variables (`command`, `args`, and `env` of a stdio server; `url` and `headers` of a remote server), and in skill and agent content for values that are not sensitive. A plugin whose options all have a default installs without `--partial`. A plugin with a required option that has no default stays partially available.
  2. *Values without a dialog.* The user can set an option's value at install and afterwards, validated against the schema.
  3. *Dialog.* In terminal and RPC modes, an install asks for options that are not set.
- **Acceptance:** For step 1: a plugin with `userConfig: {"mode": {"type": "string", "default": "fast"}}` and a hook that prints `$CLAUDE_PLUGIN_OPTION_MODE` prints `fast`, and the plugin installs without `--partial`. A plugin with a required option and no default is refused without `--partial`.
- **Notes:** Needs decision 17 for step 1 and decision 30 for the later steps. For MCP, a value should not be written into `mcp-adapter.json`; the entry can reference a process variable, as it does for `CLAUDE_PROJECT_DIR`. Step 2 puts a value on a typed command line; whether a secret typed that way lands in the session history must be answered before step 2. Pi has no masked input field in RPC mode. Use: 1 plugin in the sample (`code-modernization`, 7 options, all with defaults); the four channel plugins rely on it in Claude Code.
