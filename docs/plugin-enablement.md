# Plugin enablement

What decides whether a plugin is enabled, and when that decision is made. Enablement is settled once, at install time, from three declarations whose precedence is fixed; every later lifecycle verb either preserves that answer or replaces it on an explicit user command (DFEN-01 through DFEN-08, OUT-01 through OUT-05, DOC-02). Claims here are transcribed from the shipped sources named at each claim, not from intent -- the Claude Code ground truth was verified against [the upstream plugins reference](https://code.claude.com/docs/en/plugins-reference) on 2026-08-15. The byte forms of the rows described here are pinned in [`docs/output-catalog.md`](output-catalog.md); the row grammar they follow is [`docs/messaging-style-guide.md`](messaging-style-guide.md).

## The three inputs

Three declarations can speak to a plugin's enablement. Every rule below is stated in terms of them, so the precedence table needs no vocabulary of its own.

1. **The marketplace entry's `defaultEnabled`** -- the plugin's entry in the marketplace's `marketplace.json`, read from the cached manifest (`domain/components/plugin.ts`, `domain/manifest-cache.ts`). It is readable for every declared plugin whatever its clone state, which is what lets a read surface answer with no materialized tree and no network call (NFR-5). A literal `false`, and nothing else, is a declaration: an absent field is silent, and so is a non-boolean that reached the entry past validation (`entryDeclaresInstallDisabled`, `domain/resolver.ts`).

2. **The plugin's own `plugin.json` `defaultEnabled`** -- accepted by the same schema field group, and outranked by the marketplace entry wherever both are present, in both directions; absent at both sites resolves to `true` (DFEN-02, `resolveDefaultEnabled` in `domain/resolver.ts`). The install path evaluates the pair once and every consumer reads the resolved boolean rather than re-deriving it (DFEN-03). A read surface deliberately never consults this site at all -- see "The pre-install claim is read from the marketplace entry alone" below, which is where that rule is argued.

3. **The user's `enabled` value in the scope's `claude-plugins.json`** -- our analog of Claude Code's per-scope `enabledPlugins` setting. Its "absent means enabled" default lives in exactly one function, `isDeclaredEnabled` (`persistence/config-io.ts`): a literal `false` excludes, while a literal `true` or an absent field includes (D-04). A value the user has stated outranks the manifest side in EITHER direction -- an `enabled: true` over an entry declaring `defaultEnabled: false` installs the plugin enabled, just as an `enabled: false` over a silent entry installs it disabled (DFEN-05).

## Precedence by surface

Each row names the inputs the surface consults and the rule it applies to them. "The user is silent" means no `enabled` value for the `<plugin>@<marketplace>` key in either of the scope's two physical configuration files, since a local entry replaces the base entry wholesale. "The resolved declaration" means the value input 2's precedence rule produced from the two manifest-side sites.

| Install (`orchestrators/plugin/install.ts`)                                                  | all three                                                | The install lands disabled only where a three-term conjunction holds: the caller passed the install-time opt-in (`applyDefaultEnabled` -- passed by the `/claude:plugin install` handler and by the reconcile apply pass, and deliberately NOT by the import cascade; see the import row below), the user is silent, and the resolved declaration is `false` (DFEN-04 / DFEN-05). The disabled state is written THROUGH to the configuration entry rather than resolved at consume time. That matters because the reload convergence loop reads desired enablement only from the configuration: a disabled record left over a bare entry the loop reads as enabled would be re-enabled on the next `/reload`.                                                                                                                                                                                                                                                                                                                                                                        |
| Import cascade (`orchestrators/import/execute.ts`)                                           | the user's Claude Code `enabledPlugins` value only       | The install-time opt-in is deliberately NOT passed (D-102-03), so the resolved declaration never applies here and a plugin whose entry declares `defaultEnabled: false` imports ENABLED. That follows the precedence rule rather than escaping it: a ref reaches the cascade only because the source settings said `true` for it -- `extractEnabledPluginRefs` (`orchestrators/import/refs.ts`) drops every `false` entry outright and warns on a non-boolean one -- so the user has stated an opinion, and a stated opinion outranks the manifest side in either direction (DFEN-05). Opting in here would land a DISABLED record under that stated opinion, and because the batched post-pass writes the configuration entry only after the install returns, the next reload would read the entry as enabled, find the record disabled, and plan a re-enable. The entry that post-pass writes is bare, and a bare entry over an already-recorded plugin takes the reconcile planner's no-action path rather than its install path, so the declaration is not applied later either. |
| Update and reinstall (`orchestrators/plugin/update.ts`, `orchestrators/plugin/reinstall.ts`) | the user's configuration value only                      | Neither verb re-consults a manifest-side declaration for an already-installed plugin, so a later plugin release that changes `defaultEnabled` cannot flip an existing user (DFEN-07). The guarantee is gated two ways: a source-level guard forbids both orchestrators from NAMING `defaultEnabled` or `applyDefaultEnabled` at all (`tests/architecture/no-lifecycle-default-enabled-read.test.ts`), and behavioral cases in each verb's suite prove that flipping the declaration between install and the verb moves the version and not the enablement. The write-back both verbs share carries no per-operation field (`maybeWritePluginConfigBack`, `orchestrators/plugin/shared.ts`).                                                                                                                                                                                                                                                                                                                                                                                          |

The install's own gate still answers only the absent key, so an entry that already carries `enabled` is untouched in either direction, and the stamp writes into the physical file the declaration lives in. The user's own value wins in either direction, and the consequence is deliberate in both: a configuration-chosen `enabled: false` ALSO renders the row bare, because the token names the AUTHOR-declared cause only. ## Where the state lives

Enablement has two homes and they are not redundant. The configuration entry's `enabled` key in `claude-plugins.json` (or `claude-plugins.local.json`) is the DESIRED state -- the authoritative record the reload convergence loop reads, and the only side a user edits by hand. The installation record's `enabled` flag in `state.json` is what actually materialized, and is what the surfaces that read no source build a disabled row from. Writing the install-time answer through to the configuration is what keeps the two in agreement across a reload.

No state schema migration was needed for any of this. Both `enabled` fields already existed: the resolved declaration lands in the installation record's existing flag and in the configuration entry's existing key, so no persisted field was added on either side.

## Divergences and documented absences

The behaviors below are deliberate divergences from Claude Code or documented absences. Each is the single citable home for a caveat that the sections above mark with a pointer -- the caveat text is not duplicated elsewhere.

### A plugin required by another active plugin is not enabled on its behalf

Claude Code's second override, quoted verbatim from [the upstream plugins reference](https://code.claude.com/docs/en/plugins-reference), retrieved 2026-08-15: "when a plugin is required by another one that is active, Claude Code writes `true` for it at install or enable time. That gives it an explicit setting, so its own default no longer applies." This extension has no counterpart, and the reason is mechanical rather than a policy call: nothing here resolves a plugin's own dependency declarations. The `dependencies` field a plugin declares -- on its marketplace entry and in its `plugin.json` alike -- is schema-accepted opaquely as an unknown value (`domain/components/plugin.ts`; MM-2 / PI-13), and its single consumer is the `info` surface, which filters the declared dependency array to its string-shaped elements, sorts them, and renders them on a `dependencies:` line (`normalizeDependencies`, `orchestrators/plugin/info.ts`). So a plugin's own dependency declarations are parsed and surfaced, but never resolved, never auto-installed, and never consulted for enablement; object-shaped, version-pinned elements do not even reach the renderer. With no resolution mechanism, nothing can know that a plugin is required by an active one, so no code path can write the explicit value upstream writes -- the only writer of an explicit enablement value at install time is the write-back described above, and it writes `false`, never `true`. Note that this is a plugin author's own dependency declarations, an unrelated concept from the soft-dependency companion extensions the notification rows name with the same word. Closing the gap is tracked as PDEP-01 in the backlog and as DFEN-V2-01 in the requirements register, blocked on it (DOC-02).

### The pre-install claim is read from the marketplace entry alone

`list` and `info` answer the manifest side of the pre-install `{installs disabled}` claim from the MARKETPLACE ENTRY and nothing else -- never from the plugin's own `plugin.json`, not even where a warm clone makes it readable with no network at all (`entryDeclaresInstallDisabled`, `domain/resolver.ts`). The whole rule has three inputs, and the user's configuration value outranks the entry in either direction (`rowClaimsInstallDisabled`, same file). Reading the plugin's own manifest would need a materialized clone, and fetching to obtain one would turn a documented network-free read path into a network operation (NFR-5). The asymmetry this accepts is that the same plugin renders identically warm and cold, at the cost of declining to claim where only the unread manifest declares -- and where the entry is silent, declining IS the answer rather than a gap: a row claiming on a value it could not read would state a falsehood on the one surface built to inform the install decision (OUT-02 / OUT-05).

## Not delivered (out of scope)

The following are recognized but not delivered. They are listed here so a reader finds a recorded decision rather than silence.

- **A user-facing option to override the install-time default at install time** -- not in the upstream contract; editing `claude-plugins.json` or running `/claude:plugin enable` already covers it.
- **Any state schema migration** -- the resolved value lands in fields that already existed on both sides, so nothing persisted had to change shape.
- **Teaching `isDeclaredEnabled` the manifest value** -- rejected design: the reconcile planner has no manifest access, a manifest edit would flip a user's plugin off underneath them on reload, and it contradicts the upstream install-time-only timing.

Two absences are recorded affirmatively rather than by silence:

- **This document is not byte-gated.** [`docs/output-catalog.md`](output-catalog.md) is the only document in this repository bound to an automated byte-equality runner. This contract is prose, checked by reading; nothing fails if a claim here drifts from the code it describes. Read it as a record, not as an enforced guarantee.
- **The central row renderer's drop of the pre-install token is not covered by the byte-equality runner.** The two documented list-surface states that carry `{installs disabled}` are driven through the list surface's own render context rather than through the central row renderer, whose arms deliberately drop the reason field. What covers that drop is the live-field guard `tests/shared/notify-not-installed-reasons.test.ts`, not the catalog: if a producer ever renders a declaring row through the central arm, the catalog will not catch it.
