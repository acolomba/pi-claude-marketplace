### U8. Namespacing shared by all kinds

Skills and commands `/<plugin>:<name>`; agents `<plugin>:<name>` with subfolders as segments; workflows `/<plugin>:<meta.name>`; MCP server `plugin:<plugin>:<server>` and tools `mcp__plugin_<plugin>_<server>__<tool>`; output styles `<plugin>:<name>` (`PC`, V). `<plugin>` is the **manifest** name (U7.7).

### U9. Trust

"A project-scope plugin ... loads only after the same trust check that applies to project allow rules" (`PL` "Trust check and component limits for repository plugins", V).

### U10. Debug and validation surfaces

`claude plugin validate <path> [--strict] [--json]` and `/plugin validate <path>` (exit 0, 1, 2); the `/plugin` **Errors** tab with per-component messages (`<component> path not found: <path>`, `path escapes plugin directory`, `Invalid MCP server config for`, `Failed to load hooks from`); `claude --debug` log lines; `/plugin configure`; `claude plugin details`; `claude plugin list --json` (`CLI`, `TS`, V). `/doctor` is not named on any plugin page I read (V for absence on those pages only).

## Gaps that can be closed

Ordered by value.

### CORE-01: a root-source marketplace entry with a `skills` list loads the whole `skills/` folder

- **Upstream (V):** U7.6. `MR`: "only those subdirectories load, and the plugin's default `skills/` directory isn't scanned." `BIN@298182075` shows the rule: it applies when the entry `source` is a string whose segments are all `""` or `"."`, and it also replaces the manifest's own `skills` paths.
- **Current (V):** `conventionalFolderApplies` returns `true` for `skills` unconditionally (`X/domain/component-paths.ts:474-480`), and `collectStrictComponentKind` adds the `skills` folder whenever it exists (`:517-523`). No code looks at whether the source is the marketplace root (`grep -rn -i "marketplace root" X/domain` finds one unrelated escape note).
- **Pi capability:** none needed. This is resolver logic.
- **Proposed change:** when the entry `source` is a path source that resolves to the marketplace root and the entry declares a non-empty `skills` list, read only the listed directories; keep `skills/` only when a listed path is `skills/` itself or the root. Touch: `X/domain/component-paths.ts` (`collectStrictComponentKind`, needs the parsed source), `X/domain/plugin-resolver.ts` (pass it in).
- **Size / risk:** S. Risk: an installed plugin loses skills it should never have had; `update` and `reinstall` must drop them cleanly.
- **User-visible effect:** installing the `document-skills` plugin of `anthropics/skills` installs its 4 listed skills, not every skill in the shared `skills/` folder. Scenario: a marketplace whose entry has `source: "./"` and `skills: ["./skills/a"]`, with `skills/a` and `skills/b` on disk; `info` lists `a` only; it fails today with `a, b`.
- **How common:** the flagship `anthropics/skills` marketplace is built on it. Fetched 2026-11-11: 5 entries, all `source: "./"`, `strict: false`, with `skills` lists of 4, 12, 1, 1 and 1 paths over one shared `skills/` folder. Today each of the five plugins installs every skill in that folder, under five different plugin prefixes (I: follows from the code; not run). In `OM`, `box` and two others list entry `skills` but use non-root sources.
- **Confidence:** high. Binary and docs agree; the project code has no branch for it.
- **Open questions:** does the skills bridge de-duplicate a skill that two plugins claim (not checked)? The skills report may also raise this.

### CORE-02: components are named under the marketplace entry name, not the manifest `name`

- **Upstream (V):** U7.7. `PL`: "The `name` in the manifest: what the plugin's components are namespaced under". `BIN@298137297`: `Ae={name:ne.name,manifest:ne,...}`; the entry name is only the fallback when there is no manifest.
- **Current (V):** the manifest schema makes `name` optional and the comment says "the entry name from marketplace.json wins" (`X/domain/components/plugin.ts:93-98`). No resolver code reads `manifest.name`.
- **Pi capability:** none needed.
- **Proposed change:** keep the entry name as the install key (as upstream), and derive the component namespace from `manifest.name` when the plugin has a manifest: skill and command prefix, agent name, workflow prefix, MCP server name `plugin_<plugin>_<server>`, and the hook matcher names for the plugin's own MCP tools. Touch: `X/domain/plugin-resolver.ts` (resolved metadata), `X/domain/name.ts`, each bridge's name generation, and a migration through `update`/`reinstall`.
- **Size / risk:** M. Risk: renames generated artifacts of installed plugins; name collisions between two entries that share a manifest name (upstream has rules for that in `PL` "Name conflicts").
- **User-visible effect:** `/api-security-testing:<skill>` works as the plugin's own docs say. Scenario: entry name `acme-tools`, manifest name `tools`; the session offers `/tools:hello`; today it offers the `acme-tools` form.
- **How common:** 1 of 21 cached plugins (`42crunch-api-security-testing`, manifest name `api-security-testing`); 0 of 54 path-source entries in `OM`. Unknown for the 262 remote entries.
- **Confidence:** high on the contract; medium on the size.
- **Open questions:** no decision ID covers the current rule (searched `PROJECT.md` and `BACKLOG.md` for "manifest name"). Skill and prompt names on Pi may not be allowed to hold `:`; the per-kind reports own the exact name forms.

### CORE-03: `userConfig` is treated as an unsupported kind; plugin options do not exist

- **Upstream (V):** U4.9-U4.15.
- **Current (V):** `userConfig` is in `UNSUPPORTED_COMPONENT_KINDS` (`X/domain/unsupported-components.ts:44`), so a declaring plugin is refused without `--partial`. With `--partial`, hooks get no `CLAUDE_PLUGIN_OPTION_*`, and `${user_config.KEY}` stays literal in skills, exec-form hook `args` and MCP config. BACKLOG `USRCFG-01` records it as open.
- **Pi capability (V):** `ctx.ui.select` (for `options`), `ctx.ui.input`, `ctx.ui.confirm` (for `boolean`), `ctx.ui.custom` for a masked field (`T:85-89`, `T:132`); the extension's own config files; `getAgentDir()`. All at Pi 1.5.0.
- **Proposed change, in three steps that each stand alone:**
  1. *Defaults and export (S).* Parse the `userConfig` schema. Resolve each option to its stored value or its `default`. Export `CLAUDE_PLUGIN_OPTION_<KEY>` on both hook lanes. Fill `${user_config.KEY}` in exec-form hook `command` and `args`, in the five MCP fields, and in skill and agent content (non-sensitive only; a sensitive one becomes upstream's placeholder text). Refuse a shell-form hook that names `${user_config.*}`, as upstream does. Stop counting `userConfig` as an unsupported kind.
  2. *Non-interactive values (S).* `install --config KEY=VALUE` and `/claude:plugin configure <plugin> [KEY=VALUE ...]`, validated against the schema; print upstream's `N userConfig options not yet set` line. Store non-sensitive values in the user scope, as upstream reads `pluginConfigs` from user or managed settings only.
  3. *Dialog (M).* In `tui` and `rpc`, `configure` and an interactive install prompt for unset options.
- **Sensitive values:** upstream stores them in `~/.claude/.credentials.json` where there is no keychain (`SR`, V). A user-scope file with mode `0600` gives the same custody as upstream on Linux. BACKLOG `USRCFG-01` scopes sensitive values out for lack of a keychain; that reason is stricter than upstream.
- **Touch:** `X/domain/unsupported-components.ts`, `X/domain/components/plugin.ts`, a new `X/domain/user-config.ts`, `X/shared/vars.ts`, `X/bridges/hooks/hook-env.ts` and `spawn-helpers.ts`, `X/domain/claude-mcp-variables.ts`, `X/domain/argument-substitution.ts`, a new handler under `X/edge/handlers/plugin/`.
- **Size / risk:** step 1 S, step 2 S, step 3 M. Risk: a secret written into a staged skill or into `mcp-adapter.json`; upstream keeps sensitive values out of skill content, and the MCP report must say where a sensitive value may be written.
- **User-visible effect:** `code-modernization` installs without `--partial`, and its hooks read `CLAUDE_PLUGIN_OPTION_TELEMETRY`. Scenario for step 1: a plugin with `userConfig: {"mode": {"type": "string", "title": "Mode", "description": "m", "default": "fast"}}` and a hook that prints `$CLAUDE_PLUGIN_OPTION_MODE`; the hook output is `fast`.
- **How common:** 1 of 55 local manifests in `OM` (`code-modernization`: 7 options, all with defaults; its `scripts/telemetry.sh` reads `CLAUDE_PLUGIN_OPTION_TELEMETRY`). No `OM` plugin uses `${user_config.*}` in a config file. Common in third-party MCP plugins that need a token (I, from the docs' own examples; not counted).
- **Confidence:** high for step 1; medium for step 3 (dialog flow in `rpc` was not tried).
- **Open questions:** where a project-scope install keeps its values (upstream excludes project settings; D-LOC-01 keeps project effects in the project). Whether step 1 alone should leave a plugin with a `required` option and no default as `partially-available`.

- **Open questions:** none.

### CORE-05: `${CLAUDE_PROJECT_DIR}` stays literal in user-scope skill and command content

- **Upstream (V):** U4.4: the three path variables resolve "Anywhere in the Markdown body" of skill, command and agent content, in every scope.
- **Current (V):** install-time fill is project-scope only (SUB-02). The invocation-time port has the session `cwd` in hand and still withholds it for user scope: `...(skill.projectScope ? { CLAUDE_PROJECT_DIR: request.cwd } : {})` (`X/orchestrators/skill-invocation.ts:151`), and `if (command.scope === "project")` (`X/orchestrators/command-invocation.ts:164`). `docs/env-vars.md` gives the reason "Pi writes skill, command and agent content once at install time, when the project root of a future session is not known". - **Proposed change:** supply `CLAUDE_PROJECT_DIR = ctx.cwd` for user-scope skills and commands at invocation, in the model-read fill, and in the `run_plugin_command` tool. Agent bodies stay literal at user scope, because pi-subagents reads the agent file itself.
- **Size / risk:** S. Risk: none found; the value equals what hooks and MCP servers already get.
- **User-visible effect:** a user-scope skill that says `Read ${CLAUDE_PROJECT_DIR}/README.md` names the real project. Scenario: user-scope plugin, skill body with the token, invoke it, the model receives the session's working directory.
- **How common:** low in `OM`: 4 `.md` files name `CLAUDE_PROJECT_DIR`, all in `plugin-dev` documentation skills.
- **Confidence:** high on behavior; SUB-02 is a recorded requirement, so this needs a decision to amend it.
- **Open questions:** none.

### CORE-06: a project-scope plugin's `bin` reaches `PATH` in a project Pi does not trust

- **Upstream (V):** U9; a project-scope plugin does not load before the trust check, so its `bin/` is not on `PATH`.
- **Current (V):** `recomputePluginPath(event.cwd)` takes no trust input and reads the project scope's `state.json` always (`X/orchestrators/plugin-path.ts:87-106`; call at `X/index.ts:199`). The same handler computes `projectTrusted` four lines earlier for hooks. `collectBinDirs` takes `rec.resolvedSource` from the project's own `state.json` and checks only that it is absolute. So a repository can commit a `.pi/pi-claude-marketplace/state.json` whose record points at a folder in the repository, and that folder's `bin` is appended to the `PATH` of the model's bash, of hooks and of MCP servers.
- **Recorded decision:** D-LOC-01 lists what is trust-gated: "Project skills, commands, aliases, the model command tool, skill-read fill, and hooks", plus autoapply and the background update. `PATH` is not in the list, and nothing says it is exempt.
- **Proposed change:** pass `ctx.isProjectTrusted()` into `recomputePluginPath` and skip the project scope when it is false.
- **Size / risk:** S; low. `PATH` entries are appended, so no existing command can be shadowed; the exposure is a command name that exists nowhere else on `PATH`.
- **User-visible effect / scenario:** an untrusted project with an enabled project-scope plugin that ships `bin/hello`; `hello` is not found by the bash tool. No cucumber scenario covers the `bin`-on-`PATH` behavior today (`grep -rln "PI_CLAUDE_MARKETPLACE_PATH" features` finds none; the only `bin/` text in `features/` is a hook argument in `features/hook/process.feature:15`), so this would be the first.
- **Confidence:** high on the code path. Low practical reach: Pi answers "trusted" for a project that holds only this extension's files (see "cannot be closed").
- **Open questions:** whether project-scope MCP registrations have the same hole (MCP report).

### CORE-08: a path-source plugin runs from the live marketplace clone

- **How common:** every path-source plugin of every git marketplace: 54 of 317 `OM` entries, and most small marketplaces.
- **Confidence:** medium. I found no decision ID for the in-place rule; `docs/dependency-resolution.md:338` states it as a fact.
- **Open questions:** is the in-place rule a recorded decision I missed? Does `marketplace update` with autoupdate **on** always re-stage every plugin whose files changed but whose version string did not?

### PI-01: activate a change without a typed `/reload`

- **Upstream (V):** U6.7.
- **Current (V):** every mutating command reports `needs reload: true` and the README says "After you install, uninstall, update, or reinstall plugins, run `/reload`."
- **Pi capability (V):** `ctx.reload()` on `ExtensionCommandContext` (`T:342`; in 1.5.0 at `:341`). `D:1513-1532`: it "emits `session_shutdown` for the current extension runtime", then `session_start` and `resources_discover` with `reason: "reload"`; "Code after `await ctx.reload()` still runs from the pre-reload version". Pi refuses a reload while a response streams (`interactive-mode.js:5502-5505`).
- **Proposed change:** after a `/claude:plugin` command that changed installation state and succeeded, call `ctx.reload()` as the last step, in `tui` and `rpc`. The chat rebuild at the start of the reload erases the command's own transient notification, so the result must be re-shown after the reload: stash it on `globalThis` or in a file and print it at the next `session_start` with `reason: "reload"`, or write it as a rendered session entry (`pi.appendEntry` plus `pi.registerEntryRenderer`). Messages printed during the reload itself now stay visible (`CL:1895`). Offer an opt-out setting next to `autoapply`.
- **Touch:** `X/edge/register.ts` (the one command handler), `X/shared/notification-dispatch.ts`, README.
- **Size / risk:** M. Risk: a reload drops the extension runtime while a background update step runs (the background gate exists for this); other extensions see an extra reload; a plugin MCP server reconnects.
- **User-visible effect:** `install` ends with the plugin active. Scenario: run `install`, then, with no `/reload`, the session offers the plugin's skill.
- **Confidence:** medium. `ctx.reload()` from a handler was read, not run.
- **Open questions:** does NFR-2 ("`/claude:plugin apply`, then `/reload`, must suffice") leave room for doing the second step for the user? I think so; it is the user's call.

### PI-02: plugin `settings.json` `agent`

- **Upstream (V):** U1.10; `SR` "agent": "Run the main thread as a named subagent, so Claude Code applies that subagent's system prompt, tool restrictions, and model to your session." User settings override the plugin default.
- **Pi capability (I, appendix):** `before_agent_start` result `systemPrompt` or the mutable `systemPromptOptions`; `pi.setActiveTools()`; `pi.setModel()`.
- **Proposed change:** when exactly one enabled plugin sets `agent` to one of its own agents, apply that agent's body as the session system prompt and its tool list and model, from the converted agent file. Size M. Risk: it changes every session silently; it needs an off switch and a visible status line.
- **How common:** 0 of 76 plugins looked at in `OM`. Low priority; listed because the capability now exists and CORE-04 otherwise leaves `agent` as the only reason a `settings.json` blocks an install.
- **Confidence:** low to medium; the tool-restriction mapping was not designed.

### PI-03: run the `CLAUDE_ENV_FILE` preamble before each bash command

- **Upstream (V):** `CLAUDE_ENV_FILE` is a "shell script whose contents Claude Code runs before each Bash command" (<https://code.claude.com/docs/en/env-vars.md>).
- **Current (V):** "exposed but not sourced" (`docs/env-vars.md`).
- **Pi capability (I, appendix):** a `tool_call` handler may rewrite `event.input.command` of `bash`; the Pi docs show exactly a `source` prefix.
- **Proposed change:** when the session's env file is not empty, prefix `. "<file>"` to the bash command, after PreToolUse hooks have seen the original command. Size S to M. This belongs to the hooks report; it is listed here only because the enabling capability is the cross-cutting "environment of the model's bash" one. Do not count it twice.

### PI-04: `--plugin-dir` for one session

- **Upstream (V):** `claude --plugin-dir <path>` loads a plugin for one session without installing it (`CLI` "Flags that load a plugin for one session").
- **Pi capability (I, appendix):** `pi.registerFlag("plugin-dir", { type: "string" })` and `pi.getFlag()`.
- **Proposed change:** stage the folder as a session-only install in a temporary scope. Size L; it adds a third install origin, which SC-1 (two scopes) was written to avoid. Low priority; a plugin author's tool. Confidence low.
