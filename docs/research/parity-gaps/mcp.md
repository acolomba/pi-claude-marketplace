## Answers to the assignment's questions

1. **Did Pi's built-in MCP gain features from 1.5.0 to 1.5.2?** No. `PI/docs/mcp.md` is byte-identical to the 1.5.0 copy in `REPO/node_modules` (V, `diff` empty). The 1.5.1 MCP entries are bug fixes plus a refactor that moved `createMcpToolName`, `validateMcpServerConfig` and the OAuth sign-in into `@earendil-works/pi-mcp` (V, `PIMCP/CHANGELOG.md:7-13`). The built-in verdict table is still right. The project's source citations to `dist/extensions/mcp/tools.js` and `dist/extensions/mcp/oauth.js` are stale on 1.5.2.
2. **Did the adapter change from 7.0.0 to 7.0.1?** One change matters: a direct or search-mode tool name longer than 64 characters is now cut to 64 with a hash (V, `AD/CHANGELOG.md:21`, `AD/types.ts:963-1004`). The project's adapter profile and docs assume no cut (MCP-02).
3. **Which verdict rows are too pessimistic?** `headersHelper` under the adapter (closable with `requestHeadersCommand`, MCP-04). Tool permission rules are "installed with a warning" although both implementations can hide a blocked tool (MCP-03). No row is too optimistic. `ws`, `oauth.xaa`, the host-only types, a leading `~`, `sse` under built-in, and `bareElicitationCapability` under the adapter are still correctly blocked.
4. **Are tool names the same as upstream?** Yes up to 64 characters, with two known exceptions under built-in (`-` folded to `_`, hash on collision). Over 64 characters both implementations now cut the name; the project handles the cut only for built-in.
5. **Reachability:** see the table in [Latest Pi / extension capability](#latest-pi--extension-capability). Prompts, elicitation and sampling exist only under the adapter. Resources work under both with no project code. `ws` and `${user_config.*}` work under neither.
6. **Is the choice of the active implementation still right?** Yes for the normal case: an installed adapter registers `/mcp` and Pi then leaves its built-in out (V, `PI/docs/mcp.md:266-268`). One edge case is wrong: an adapter embedded with `createMcpAdapter({ config })` leaves the built-in running, and the project still picks the adapter (MCP-10).
7. **The adapter's own Claude plugin loader:** off by default, reads only `.mcp.json` of directories the user lists, keeps the bare server names, expands only `${CLAUDE_PLUGIN_ROOT}`. The project should keep ignoring it. Details in [The adapter's Claude plugin loader](#the-adapters-claude-plugin-loader).

### The adapter's Claude plugin loader

(V) `AD/claude-plugin-loader.ts:15-82`, `:285-292`; `AD/docs/extension-api.md:34-51`.

- It runs only for directories the user lists in `claudePlugins`, with `mcp: true`.
- It reads only the root `.mcp.json`. "Manifest path overrides are intentionally not followed", so `plugin.json` `mcpServers` is ignored.
- "Claude plugin MCP server names are used as written", so tools are not named `mcp__plugin_<plugin>_<server>__<tool>`.
- It replaces only `${CLAUDE_PLUGIN_ROOT}` and sets it in a stdio `env`. No `${CLAUDE_PLUGIN_DATA}`, no `${CLAUDE_PROJECT_DIR}`, no credential deny-list.
- It "does not discover, download, install, or update plugins".

Conclusion: it does not overlap unless a user lists a plugin this project installed; the server then runs twice under two names. The project should not use it or defer to it, because it gives non-upstream names and a smaller variable set. `REPO/docs/mcp-compatibility.md:179` already says this accurately. No change is needed.

## Gaps that can be closed

### MCP-01: a server without `timeout` fails after 60 seconds of silence

- **Upstream.** With no `timeout`, a call may run for about 28 hours, and only the idle timer stops it: "The idle window defaults to five minutes for HTTP, SSE, WebSocket ... servers, and to 30 minutes for stdio servers" (V, `UP/mcp.md:466`). `MCP_TOOL_TIMEOUT` and `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` change the limits (V, `UP/env-vars.md:334`, `:497`). A remote server also has a 60-second timer to its first response byte (V, `UP/env-vars.md:497`).
- **Current.** The project writes a timeout only when the plugin declares one (`EXT/domain/mcp-server-features.ts:139-161`). Otherwise both implementations use 60 s (V, `PI/docs/mcp.md:68`; `AD/docs/servers.md:51`). `REPO/docs/mcp-compatibility.md:588` records it as "a Pi capability gap", and neither environment variable is read (V, no hit for `MCP_TOOL_TIMEOUT` under `EXT/`).
- **Enabling capability.** Both timeouts restart on progress, which is exactly the meaning of the upstream idle timer. Pi `timeout` in seconds (Pi 1.5.0); adapter `requestTimeoutMs` (7.0.0). No new floor.
- **Proposed change.** When the plugin declares no usable `timeout`, write the upstream idle window as the default: 1800 s for stdio, 300 s for a remote server. Under built-in, read `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` from the session environment at registration (the project already resolves the environment there, D-MB-14). Under the adapter, write `requestTimeoutMs` only when neither the plugin nor the user set it, so the user's carried value still wins. Touch points: `EXT/domain/mcp-server-features.ts` (`timeoutField`, `remoteTimeoutField`), `EXT/domain/mcp-builtin-translation.ts`, `EXT/bridges/mcp/adapter-entry.ts` (carried-field rule), `REPO/docs/mcp-compatibility.md`.
- **Size and risk.** S. Risk: a hung stdio server now blocks a call for 30 minutes instead of 1; that is the upstream behavior.
- **User-visible effect and proof.** A plugin tool that works for 90 seconds with no progress (a build, a browser action, a long query) succeeds. Scenario: a stub server whose tool answers after 65 s, under both profiles; today the call fails with a timeout. A cheaper proof is a `builtin-values.feature` row that shows `timeout: 1800` in the registered config.
- **How common.** All 14 local `.mcp.json` files in `MKT/` declare no `timeout` (0 files match `"timeout"`). 9 of them are stdio servers. So the 60 s limit applies to every real plugin server found.
- **Confidence.** High for stdio. Medium for remote: upstream's 60-second first-byte timer means a non-streaming remote server also fails upstream.
- **Open questions.** Should the remote default stay 60 s to match the first-byte timer? Does ANAME-07 ("writes only the values that the plugin declares") need an amendment ID?

### MCP-02: the adapter 7.0.1 cut of names over 64 characters is not modeled

- **Upstream.** Names are not shortened up to 128 characters (V, `UP/mcp.md:1606-1608`).
- **Current.** `adapterToolName` returns the full name (`EXT/domain/mcp-implementation.ts:72-80`). The hooks view passes an adapter tool's Pi name through unchanged (`EXT/bridges/hooks/mcp-tool-view.ts:42-54`). `REPO/docs/mcp-compatibility.md:126` says "the names of plugin tools are not shortened". The agent conversion writes the full name into `excludeTools` (`EXT/bridges/agents/convert.ts:128`).
- **Latest adapter.** "A name longer than 64 characters is now shortened to 64 and ends in a short hash ... A Pi tool allowlist that lists one of these tools by its old full name needs the new, shorter name" (V, `AD/CHANGELOG.md:21`). The hash is the first 8 hex digits of sha256 over the full joined name (V, `AD/types.ts:968-991`), so the project can compute it. 7.0.1 is inside the declared range `>=7.0.0 <8`.
- **Proposed change.** Give the adapter profile the cut rule: `toolName` returns the cut name, and the hooks view maps a cut adapter name back to the Claude name, as `EXT/domain/components/hooks/builtin-mcp-tool-names.ts` does for built-in. Because 7.0.0 does not cut, either raise the floor to 7.0.1 or accept both forms. Fix the doc.
- **Size and risk.** M. Risk: two adapter versions in range behave differently.
- **User-visible effect and proof.** A plugin hook with the matcher `mcp__plugin_<p>_<s>__<long tool>` fires again, and its payload carries the Claude name. Scenario: the adapter twin of the long-name scenario in `listing.feature`, plus a hook scenario that matches the full name.
- **How common.** Not measurable from `MKT/` (tool names come from live servers). The length is `12 + plugin + 1 + server + 2 + tool`; for example a plugin `chrome-devtools-mcp` with server `chrome-devtools` leaves 15 characters for the tool name. Likely for plugins with long names.
- **Confidence.** High that the cut exists (source and changelog). Medium on the hook effect: not run.
- **Open questions.** Does the nested call that the `mcp` proxy makes also use the cut name? (I) yes, from "The full name still works anywhere you write it for the adapter".

### MCP-03: tool permission rules could be enforced

- **Upstream.** `toolPermissions: {tool: "blocked"}` and `tools[].permission_policy` are schema fields of a remote server (V). A blocked tool is treated as switched off (I, `BIN@292732477`: `Object.entries(o).some(([r,s])=>s==="blocked"&&bn(r)===n)`).
- **Current.** Installed, not enforced, warning `MCP server tool rules not enforced.` The doc says "It is not known whether Claude Code enforces these rules for the servers of a plugin" (`REPO/docs/mcp-compatibility.md:340`).
- **Enabling capability.** Built-in: `toolExposure: {"<tool>": "hidden"}` (V, `PI/dist/core/mcp-servers.js:75-85`, Pi 1.5.0). Adapter: `excludeTools` for blocked tools and `approveTools` for ask tools (V, `AD/docs/servers.md:57-58`, 7.0.0).
- **Proposed change.** Map `blocked` and `always_deny` to a hidden or excluded tool. Map `ask` and `always_ask` to `approveTools` under the adapter; under built-in keep the warning for ask rules, or add a `tool_call` confirm later. Narrow the warning to the rules that stay unenforced. Touch points: both translation tables, `EXT/bridges/mcp/adapter-entry.ts` (merge with the user's carried `excludeTools` and `approveTools`), the warning text and its catalog entry.
- **Size and risk.** S for blocked, M with ask. Risk: the merge with user-owned fields under the adapter.
- **User-visible effect and proof.** The model no longer sees a tool the plugin blocks. Scenario: a stub server with two tools, one `blocked`; the search finds only the other.
- **How common.** 0 of 14 local files. These fields look aimed at connectors.
- **Confidence.** Medium: enforcement for a plugin server upstream is inferred from the binary, not observed.
- **Open questions.** Confirm with a sandboxed `claude mcp list` run that a plugin server's `blocked` tool is hidden.

### MCP-04: `headersHelper` can run under the adapter

- **Upstream.** U9.
- **Current.** Blocked under both; "`requestHeadersCommand` of pi-mcp-adapter has a different contract" (`REPO/docs/mcp-compatibility.md:327`).
- **Enabling capability.** `requestHeadersCommand` prints the same output shape upstream requires, a JSON object of string values, has the same 10 s default, and applies its headers last (V, `AD/request-headers-command.ts:7`, `:264-293`). Differences: no shell, no `cwd`, runs per request, inherits the full environment.

Keep the built-in verdict blocked. Apply the `Authorization` rule of D-08-04 to the helper case (upstream: a helper that returns `Authorization` turns OAuth off, which the install cannot know).
- **Size and risk.** M. Risks: the helper runs once per HTTP request, not once per connection, so a slow helper slows every call; upstream strips credential-looking variables from a plugin helper's environment and the adapter does not, which gives the plugin more than upstream does; Windows needs the shell the hooks bridge already finds.
- **User-visible effect and proof.** A plugin whose remote server needs a generated header installs without `--partial` under the adapter and connects. Scenario: the loopback HTTP server of `configuration.feature` with a helper that prints `{"X-Team": "core"}`; assert the header arrives.
- **How common.** 0 of 14 local files. Typical for enterprise plugins, not for the public marketplace.
- **Confidence.** Medium: the mapping is read from source, not run.
- **Open questions.** Is the credential-stripping difference acceptable, or must a small wrapper script scrub the environment? Is a per-request helper acceptable without a cache?

### MCP-05: a plugin server that duplicates a user's server still runs

- **Upstream.** U30: the plugin server is suppressed when a local, project or user server has the same URL or command.
- **Current.** Built-in suppresses by name only (`EXT/bridges/mcp/builtin-overrides.ts`, D-MB-24). The adapter path refuses only an equal key. - **Proposed change.** Before staging (adapter) or registering (built-in), skip a plugin server whose endpoint equals an enabled server in the user's own MCP files, with upstream's URL rule ("differ only in the letter case of the scheme or host, the scheme's default port ... or a trailing slash"). Show it in `info` as overridden.
- **Size and risk.** M. Risk: the adapter reads many config sources; comparing commands needs a rule for `args`.
- **User-visible effect and proof.** One connection, one tool set. Scenario: a user `mcp.json` entry with the stub server's command, then install; `info` shows the plugin server as overridden and the stub logs one start.
- **How common.** Plausible for the popular remote servers in `MKT/` (github, linear, context7, gitlab).
- **Confidence.** Medium. The upstream rule is documented; the exact command comparison is not.
- **Open questions.** How does upstream compare stdio commands (with `args`, after expansion)?

### MCP-06: a stdio plugin server stops after 10 idle minutes under the adapter

- **Upstream.** Stdio plugin servers connect at session start and stay. Only a remote server used before is `cached` and connects on first use (V, `UP/mcp.md:704`).

- **Size and risk.** S. Risk: more memory for users with many plugin servers; the user's carried `lifecycle` still wins.
- **User-visible effect and proof.** A stateful server (a browser, an index) keeps its state between calls more than 10 minutes apart. Scenario: assert the written entry; a timing scenario is too slow.
- **How common.** 9 of 14 local servers are stdio; playwright and serena hold state.
- **Confidence.** High on the mechanism. The decision ANAME-05 must be reopened by the user.
- **Open questions.** `lazy-keep-alive` or `keep-alive` (true upstream parity, but it starts every server at session start)?

- **Upstream.** U20.
- **Current.** `userConfig` is an unsupported kind, so the plugin is partially available. With `--partial`, the server is written with the literal text `${user_config.KEY}`, with no MCP warning (I, from the absence of any `user_config` handling under `EXT/bridges/mcp` and `EXT/domain/claude-mcp-variables.ts`).
- **Enabling capability.** None in Pi or the adapter; the project owns the substitution. Backlog USRCFG-01 (`REPO/.planning/BACKLOG.md:1387`) already proposes it.
- **Proposed change.** Belongs to a `userConfig` feature. For MCP, the value should travel as a process variable that the entry references (as `CLAUDE_PROJECT_DIR` does), so no secret is written to `mcp-adapter.json`. Until then, name the server in the `MCP server variables not set.` warning.
- **Size and risk.** L as a feature, S for the warning.
- **How common.** 1 `plugin.json` in `MKT/` declares `userConfig`; the four channel plugins rely on it upstream.
- **Confidence.** High on the gap, low on a design.

## Divergences with no recorded reason

1. **More than upstream under the adapter: sampling and MCP UI windows.** The adapter declares `sampling` and the MCP Apps UI extension to every server by default (V, `AD/server-manager.ts:1514-1517`). Claude Code documents neither sampling nor rendering of UI resources ("pages for a host application to render rather than content for Claude to read", `UP/mcp.md:1734`). The project writes neither `openUi: false` nor anything else, so a plugin server can open a browser window and ask the model for a completion on Pi. The project's own rule is that "a plugin cannot give itself a pi-mcp-adapter power that Claude Code does not give a plugin" (`REPO/docs/mcp-compatibility.md:317`). No decision ID covers this.
2. **Resources become tools.** Under the adapter each resource is a model-visible tool `mcp__plugin_<p>_<s>__read_<name>`; under built-in, three generic tools appear. Not documented.
3. **No endpoint dedupe under the adapter** (MCP-05). The doc states the upstream rule only in the built-in section.
4. **`callbackPort` upper bound.** The project rejects a port above 65535 as malformed (`EXT/domain/mcp-server-features.ts:249`), which makes an inline-source plugin `(unavailable)`. The 2.1.322 schema is `v().int().positive()` with no upper bound (V, `BIN@283750300`). (I) that a later runtime check does not reject it upstream.
5. **`alwaysLoad: false`** is treated like an absent value. Upstream gives it a meaning of its own (U13). It has no effect today only because per-tool `_meta` is not honored at all (N7).
6. **Session-only disable under built-in.** Upstream keeps the `/mcp` toggle per project. Documented as a fact (`REPO/docs/mcp-compatibility.md:232`), but not listed under "User choices" with a reason.
