### `meta` keys (closed set, VERIFIED at BIN@308025592, functions `M` and `K`)

| Key                                     | Rule                                                                                                                 |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `name`                                  | required, string, `length > 0`                                                                                       |
| `description`                           | required, string, `length > 0` (whitespace-only passes)                                                              |
| `title`                                 | optional non-empty string                                                                                            |
| `whenToUse`                             | optional string. Put in the command prompt the model reads                                                           |
| `phases`                                | optional array; entries without a string `title` are dropped, not an error. Each entry: `title`, `detail?`, `model?` |
| any other key                           | ignored                                                                                                              |
| `__proto__`, `constructor`, `prototype` | refused: `reserved key name not allowed in meta`                                                                     |

There is no top-level `meta.model` upstream. Values must be pure literals: `template interpolation not allowed in meta`, `spread not allowed in meta`, `computed keys not allowed in meta`, `methods/accessors not allowed in meta`, `only negative-number unary allowed in meta`, `sparse arrays not allowed`.

### Other runtime functions (VERIFIED, tool prose and runtime chunk)

- `parallel(thunks)`: a barrier. "A thunk that throws (or whose agent errors) resolves to `null` -- the call itself never rejects." Implemented with `Promise.allSettled`.
- `pipeline(items, ...stages)`: each stage gets `(prev, originalItem, index)`. "A stage that throws drops that item to `null` and skips its remaining stages." A `null` stage result also skips the rest (`if(be.v===null)break`).
- At most 4,096 items per `parallel()`/`pipeline()` call (`QS=4096`), 1,000 agents per run, concurrency `min(16, CPUs-2)` or `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` (1 to 256).
- `workflow(nameOrRef, args?)`: `name` or `{scriptPath}`; one nesting level.
- `phase(title)`, `log(message)`.
- Default subagent: `tools:["*"]` minus three orchestration tools. "Workflow agents can reach all session-connected MCP tools via ToolSearch." Subagents get the same CLAUDE.md files. Permission rules and hooks apply to their tool calls (workflows.md "The subagents the workflow spawns use your permission rules").
- Model: "When nothing else assigns one, the agent runs on your session's model" (workflows.md, Cost).

I do not have a 2.1.267 binary, so this compares 2.1.322 with what `docs/workflows-compatibility.md` records for 2.1.267 and 2.1.316.

### pi-subagents 0.88.0 workflow scripts: complementary, and a worse target

VERIFIED from `docs/workflows.md`:

- A different API: `runs.run(key, {agent, task})`, `runs.all`, `runs.lanes`, `runs.steer`, `emit`, `console`, mission `state`. There is no `agent()`, `parallel()`, `pipeline()`, `phase()` (line 92).
- "nested async functions, async arrows, and async methods are rejected" (lines 82, 209). The idiom every upstream script uses, `parallel(items.map(x => async () => …))` and async pipeline stages, cannot run.
- No saved registry and no command per workflow: a script is a reply block, a file path (`subagent({ workflow: "./x.js", args })`), or one of three packaged named resources, "not a user/project resource registry" (line 146).
- What it does better: children are full pi-subagents agents (their own tools, MCP through `mcp:` entries, extensions for background children), `outputSchema`, `worktree: true` with patch handoff, a permission-restricted script process, and a `subagent_launch` tool call per child that permission extensions can block.

Verdict: a Claude script is not source-compatible with it, so using it needs a script compiler plus an emulation of the three core globals. That is the Claude emulator the brief rules out. The engine stays the right target. pi-subagents is the right target for *agents*, and it shows what the engine's children lack (N4).

### How a user or the model starts a translated workflow

- User: `/<plugin>:<name>` in a new session, same spelling as upstream unless the name starts with `<plugin>-`. It starts at once, with no model turn and no approval.
- Model: `workflow({ name: "<plugin>:<name>", args: {…} })`. This is the path both official plugins use, from a command or a skill. It is broken today by WF-01.
- Scripts are stored per scope as in the table above. Project scope is supported and pinned by `features/workflow/storage.feature`.

## Gaps that can be closed

### WF-01 -- A workflow name inside `Workflow({ name: … })` gets a leading slash, so the model's call fails

- **Upstream.** A plugin's own commands and skills start its workflows through the tool, by registered name. VERIFIED: `code-modernization/commands/modernize-harden.md:38-45`: "Call it by name (the plugin registers it)… `Workflow({ name: "code-modernization:modernize-harden-scan", args: { system: "$system" } })`". `claude-security/skills/claude-security/jobs/scan-codebase.md:74`: `Workflow({ name: "claude-security:scan", args: {…} })`.
- **Current.** `EXT/domain/skill-tokens.ts:83-121` rewrites every `<plugin>:<source>` token that names a staged workflow to `` `/${workflowName}` `` (line 115). The token regex accepts a quote before the token, so the string inside the tool call is rewritten too. VERIFIED by running `rewriteMarkdownReferences` on the real files with the names the generators produce: all 7 call sites in 5 code-modernization commands become `name: "/code-modernization:modernize-…"`, both claude-security job files become `Workflow({ name: "/claude-security:scan",`, and the skill's `allowed-tools` entry becomes `Workflow(/claude-security:scan)`. The call sites are wired with the workflow names for skills, commands and agents: `EXT/orchestrators/plugin/install-outcome.ts:1261`, `:1309-1311`, `EXT/bridges/commands/staged-command.ts:270`, `EXT/bridges/skills/stage.ts:189`, `:361`, `EXT/bridges/agents/convert.ts:1014`. INFERRED for the full install path: I did not run an install.
- **Engine.** `workflow({name})` resolves through `storage.load(name)`, which returns `null` for any name containing `/` (`workflow-saved.ts:84-94`, `:280-287`), then built-ins by exact name. Result: `workflow: no saved or built-in workflow named "/code-modernization:…"` (`workflow-tool.ts:254-258`). The same name without the slash loads the envelope this bridge wrote (E17). Minimum engine version: the declared floor, 3.15.0.
- **Proposed change.** A reference to a workflow in a tool-call position keeps the bare installed name. Keep `/name` only where the source already wrote a slash (a user-facing slash reference). Concretely: when the matched token has no leading `/` in the source and resolves to a workflow, emit `workflowName` with no slash. Touch points: `EXT/domain/skill-tokens.ts:113-115`, `test/domain/skill-tokens.test.ts:271-285`.
- **Size / risk.** S. Low: one branch in one pure function. Check the three callers' expectations for bare `plugin:workflow` prose.
- **User-visible effect and proof.** A plugin command that tells the model to run its workflow by name starts the run. Scenario: a fixture plugin with a workflow `scan` and a command whose body says `Workflow({ name: "demo:scan" })`; with the scripted model, run the command, have the model call `workflow` with the `name` copied from the prompt it received, and expect a completed run. Today the staged prompt holds `/demo:scan` and the tool call errors.
- **Frequency.** 9 call sites in 7 files; every plugin in the official marketplace that ships a workflow (2 of 2) starts it this way.
- **Confidence.** High for the rewrite (executed) and for the engine lookup (read). Medium for "the model does not recover": a model may retry without the slash.
- **Open questions.** Does any existing fixture rely on a bare `plugin:workflow` mention becoming `/plugin:workflow`?

### WF-02 -- Scripts name plugin agents in `agentType`; nothing proves the binding, and a missing agent fails silently

- **Upstream.** `agentType` is resolved from the Agent tool's registry, and an unknown type throws `agent({agentType}): agent type '<x>' not found` (VERIFIED, runtime chunk).
- **Current.** The binding rests on two source reads: the agents bridge writes frontmatter `name: <plugin>:<agent>` (`convert.ts:931-937`), and the engine keys its registry on that field (E6). No scenario under `features/workflow/` or `features/agent/` runs `agent({agentType})`. When the agent is not installed (conversion returned "empty-tools", a duplicate-name skip, an agent of another plugin), the engine logs one line into the run and runs a default agent with default tools (E7). `docs/workflows-compatibility.md:126` says an unresolved `agentType` "is not an error on either side", which is wrong for upstream.
- **Engine capability.** E6, at 3.15.0.
- **Proposed change.** (a) A cucumber scenario: a plugin with an agent and a workflow that calls `agent("…", {agentType:"demo:helper"})`; the run's agent row shows the agent's instructions or its thinking level were bound. (b) At install, compare the string-literal `agentType` values of each admitted script with the agent names the plugin stages, and add one note per unknown name ("workflow script X names agent type Y, which this plugin does not install; the engine runs a default agent"). The AST is already in hand (`workflow-script.ts`), and the note mechanism exists (WGATE-01). A note never refuses. (c) Correct the doc line.
- **Size / risk.** S for (a) and (c), M for (b). Low. A literal in a variable is missed, which is a missing note, never a false one, as long as only `agentType:` property values are read.
- **Effect and proof.** An author or a user sees at install that a script will run an ungoverned default agent. Scenario for (b): a script with `agentType:"demo:ghost"` and no such agent; the install diagnostic lists the note.
- **Frequency.** `agentType` appears in 7 of 7 official scripts, about 20 call sites, every one a `<plugin>:<agent>` name of the same plugin.
- **Confidence.** High on both sides' behavior; medium on (b)'s value, since official scripts name agents that exist.
- **Open questions.** With `--map-model`, the generated agent carries `model: anthropic/…`; the engine treats an agent type's model as explicit and throws `MODEL_NOT_FOUND` when the user has no such model (E12). Should the note cover that?

### WF-03 -- Options and globals the engine silently drops get no install-time note

- **Upstream.** `effort`, `stallMs`, `disallowedTools`, `bashCommandClamp` are honored; a malformed `disallowedTools` refuses the spawn "rather than running it un-narrowed". `setTimeout`, `clearTimeout`, `console.debug` exist (VERIFIED).
- **Current.** The bridge reads `meta` only. `docs/workflows-compatibility.md:124` lists the runtime functions as "the runtime surface belongs to whichever engine runs the script". The six existing gate notes cover `meta` shape only.
- **Engine.** None of the four options exists (E5); none of the three globals exists (E4). No error and no log.
- **Proposed change.** Extend the install note set with a static read of the script body: `agent()` call options named `disallowedTools` or `bashCommandClamp` (note: "the engine ignores this option; the agent runs with its full tool set"), `effort` and `stallMs` (note: ignored), and unguarded references to `setTimeout`, `clearTimeout`, `console.debug`. A note never refuses (WGATE-03). Also add the option-by-option table from this report to the compatibility doc.
- **Size / risk.** M. Low: additive notes. Keep the tool-narrowing note separate from the two cosmetic ones so it is not lost.
- **Effect and proof.** `info` and install name what a script loses on Pi. Scenario: a script with `agent("x",{disallowedTools:["Bash"]})` installs with the note.
- **Frequency.** `effort`: 1 of 7 scripts. `stallMs`: 1. `setTimeout`: 1, guarded. `disallowedTools`, `bashCommandClamp`, `console.debug`: 0.
- **Confidence.** High on the facts. Medium on priority: the security-relevant options are unused in the official marketplace today.
- **Open questions.** Would the engine author take a patch that maps `effort` to `thinking` and merges `opts.disallowedTools` into the existing `disallowedToolNames` plumbing (`workflow.ts:1372-1373`)? Both are a few lines; see N3.

### WF-04 -- The docs do not say how to give workflow subagents the session model or MCP tools

- **Upstream.** Subagents run on the session model and reach session MCP tools (VERIFIED, workflows.md Cost; tool prose).
- **Current.** Not mentioned in `docs/workflows-compatibility.md`, `docs/mcp-compatibility.md`, `docs/hooks-compatibility.md`, or the README (`grep -i 'providerMiddleware\|inheritMainModel'` over `docs/`, `README.md`, `.planning/BACKLOG.md` returns nothing).

- **Size / risk.** S, docs only. The adapter opt-in is a source read; mark it unmeasured until someone runs it.
- **Effect and proof.** A user can restore two upstream behaviors with two settings. Proof would be a live run, not a scenario; the doc should carry the grade it earns.
- **Frequency.** Model choice affects every run. MCP in a workflow subagent: unknown in the official scripts (the agents they name declare `tools: Read, Glob, Grep, Bash` and no MCP).
- **Confidence.** High for `inheritMainModel`. Medium for the adapter opt-in: the allowlist and the adapter's child behavior were read, not run.
- **Open questions.** Does pi-mcp-adapter 7.0.1 start cleanly in an in-process child session that shares the parent's process?

### WF-05 -- `Workflow` in an agent's `tools:` is dropped, so a plugin agent cannot start its plugin's workflow

- **Upstream.** `claude-security/agents/claude-security.md:7`: `tools: …, Workflow, Workflow(claude-security:scan), …`. The agent is the one that runs the scan workflow.

- **Effect and proof.** The claude-security lead agent can start `claude-security:scan`. Proof needs a live pi-subagents child.
- **Frequency.** 1 agent in the official marketplace, in the plugin whose whole purpose is its workflow.
- **Confidence.** Low to medium. I did not read the pi-subagents child launch path or check that the engine tolerates being loaded in a detached child.

### WF-06 -- Workflow names: drop the `<plugin>-` elision, or accept the upstream spelling at the tool

- **Upstream.** `${plugin}:${meta.name}` verbatim (U7).

- **Size / risk.** S to M, with a migration for installed envelopes (rename on update or reinstall, as the D-LOC-01 cleanup does). The user-visible name changes for affected plugins.
- **Frequency.** 0 of 7 official scripts have a name that starts with their plugin's name.
- **Confidence.** High on facts, low on urgency. This is a recorded decision; it is a question for the user.
