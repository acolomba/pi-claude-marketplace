Versions read: Claude Code docs (code.claude.com, fetched 2026-11-11 as raw markdown), Claude Code binary 2.1.322, Pi 1.5.2, pi-subagents 0.88.0, this repository at `fed88184` (`features/gaps`).

## Headline

The brief's table ("commands become Pi prompt templates") undersells what the project does today. Since the `component-features` milestone, a typed plugin command or skill does not use Pi's own expansion. The extension intercepts Pi's `input` event and fills the body itself with a port of Claude Code's argument rules, the `${CLAUDE_*}` variables, and `` !`cmd` `` injection (D-CF1-01, D-CF1-02, D-CF2-06, D-CF3-06). The model gets a `run_plugin_command` tool for commands (D-CF3-01 as amended), and a model read of a staged `SKILL.md` is filled through `tool_result` (D-CF1-03 as amended). Most of the questions in my assignment are therefore already closed, and I refuted them as gaps. What is left falls in three groups:

1. Body and layout features that nobody recorded: `@file` references, sibling-relative paths, boolean spellings, the plugin-root `SKILL.md`, symlinked skill folders.
2. Frontmatter fields that D-CF1-05 drops on the ground "Pi reads only four fields". That ground is true of Pi's loaders but not of Pi's extension API, which the project's own invocation path can call: `effort`, `model`, `disallowed-tools`, `context: fork` with `agent` and `background`.
3. Recorded decisions whose stated reason no longer holds (`${CLAUDE_PROJECT_DIR}` at user scope, `user-invocable: false` on commands).

Pi 1.5.1 and 1.5.2 add nothing for skills, templates, or commands that the project does not already use (VERIFIED, `PI/CHANGELOG.md:3-133`; the only related entry is the prompt-template quoting fix, line 60, which does not affect the project because it never uses Pi's substitution for bridged commands).

### SKILL-01 / CMD-01: `@file` references are not attached

- **Upstream** (VERIFIED docs, binary function seen): a local skill's or command's `@path` references attach the named files to the prompt. `DOCS/skills.md:314`: for a synced skill Claude Code "doesn't attach the files that `@` references name the way it does for a local skill". `BIN` `G3r`/`mGn` extract `@path` and `@"path with spaces"`, and `q3r` parses `#L10-20`.
- **Current** (VERIFIED): nothing. The body reaches the model with the literal `@path`. No decision, backlog entry, or scenario mentions it. The model may read the file on its own (Pi's read tool drops a leading `@`), but nothing makes it.
- **Enabling capability** (VERIFIED, Pi >= 1.5.0, no floor change): the project already builds the final text in its `input` transform, so it can append file content there. Pi's own CLI `@path` form is `<file name="<abs>">\n<content>\n</file>` (`PI/dist/cli/file-processor.js:60`).
- **Proposed change**: after argument and variable substitution and `!` injection, a typed bridged command or skill attaches each `@path` token of the filled body that names an existing regular text file, in Pi's `<file name=...>` form, with a size cap. Paths resolve against the session directory; absolute paths (the common `@${CLAUDE_PLUGIN_ROOT}/...` case, already absolute after install) are used as they are. Tokens in fenced code and code spans are skipped, as upstream's markdown walk does for imports. Touch points: a new pure `EXT/domain/` core, `EXT/orchestrators/command-invocation.ts`, `EXT/orchestrators/skill-invocation.ts`.
- **Size / risk**: S to M. Risk: over-matching (`@scope/package` npm names, e-mail handles); require an existing file. A typed argument can name any readable file, which is also true upstream.
- **User-visible effect and scenario**: `Review @${CLAUDE_PLUGIN_ROOT}/templates/x.md` reaches the scripted model with the template text in a `<file>` block. A scenario fails today because the model call holds only the path.
- **Frequency**: 1 of 40 skills uses it for real (`plugins/claude-security/skills/claude-security/SKILL.md:69`, `@${CLAUDE_SKILL_DIR}/role.md`); plugin-dev's command-authoring guidance teaches the pattern in 20+ places, so third-party commands are likely to use it.
- **Confidence**: medium-high. The contract is stated by the docs only by contrast, and I did not trace the exact attachment format upstream produces.
- **Open questions**: does upstream also attach on the model's Skill-tool path? Should `run_plugin_command` and the skill-read fill attach too? Directory references (`@src/`) list the directory upstream; skip or mirror?

## Assumptions I could not verify

- **Command versus skill precedence inside a plugin.** The docs table says the skill wins over a `.claude/commands/` file; the project's probe of 2.1.316 found the command wins for plugins (D-CF2-03). I did not re-probe 2.1.322, because that needs a running session.
- **`paths` on plugin skills.** The docs say plugin skills accept every field. In `BIN`, the builder that plugin skills and commands share (`B6`, offset ~295098741) returns no `paths` member; I scanned that region and found no `paths` read. INFERRED: 2.1.322 may ignore `paths` on plugin skills.
- **`@file` on the model's Skill-tool path**, and the exact attachment text upstream sends. I verified that the docs promise attachment for local skills and that the extraction functions exist, not the wire format.
- **Root skill with `"skills": "."`** in this project: read from the code, not run.
- **Skill-read fill under a hidden read tool or codemode.** The fill requires `event.toolName === "read"` (`edge/skill-read.ts:36`). Pi tells the model to load skills with bash when the read tool is hidden (`skills.js:283-290`); a `cat` of the file is then not filled. I did not test whether a codemode-nested read fires `tool_result` with that name.
- **Windows command alias** (`/foo:bar` for `/foo.bar`): inferred from the alias source, not run.
- **pi-subagents built-in agent mapping** for `Explore` / `Plan` / `general-purpose`: no upstream or project record defines one; SKILL-10 needs a decision.
