# MCP compatibility

This document compares how Claude Code and this extension run the MCP servers of a Claude plugin. This extension runs them through pi-mcp-adapter or through Pi's built-in MCP, so most tables have a column for each. The document covers names, tool search, the length of tool names, the connection lifecycle, the translation of each server field, and the places where the products differ.

Legend: `✓` supported, `✗` not supported, `⚠` partial (see notes), `--` no equivalent on that side.

The Claude Code column reflects the MCP reference at [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp) and the server schemas in the Claude Code 2.1.291 binary. The row for `_meta["anthropic/alwaysLoad"]` was checked later, on the 2.1.294 binary. The rows on [server sources](#server-sources) and [invalid server configs](#invalid-server-configs) were checked on the Claude Code 2.1.316 binary, with `claude plugin validate`, `claude plugin install`, and `claude mcp list` in a sandbox.

The pi-mcp-adapter column reflects pi-mcp-adapter 7.0.0 on Pi 1.5.0 and the sources under `extensions/pi-claude-marketplace/bridges/mcp/` and `extensions/pi-claude-marketplace/domain/`. Statements about run-time behavior come from the cucumber scenarios under `features/mcp-server/`. Each scenario runs a real Pi 1.5.0 with pi-mcp-adapter 7.0.0 in a sandbox, with a local stub MCP server, a loopback HTTP MCP server, and a scripted model that logs each request. Some statements rest on a run of Pi 1.4.0 and pi-mcp-adapter 7.0.0 outside the cucumber harness, on 2026-11-01, and they say so. Among them are the `MCP_DIRECT_TOOLS` setting and the `--no-extensions` flag. A statement that no run covers says that it was checked in the pi-mcp-adapter 7.0.0 source. Two statements still rest on earlier runs, and they say so: the name lengths, measured on 2026-10-06 with Pi 1.0.0 and pi-mcp-adapter 5.0.0, and the extra `/reload` after an upgrade, measured on 2026-10-09 by the live canary `test/live-uat/mcp-adapter-canary.mjs` on Pi 1.0.0. See [Further reading](#further-reading) for the canary.

The Pi built-in column reflects the built-in MCP of Pi 1.5.0 and the sources under `extensions/pi-claude-marketplace/bridges/mcp/` and `extensions/pi-claude-marketplace/orchestrators/mcp/`. Each statement in that column, and each statement about Pi's built-in MCP in the text, cites its proof. The proof is a cucumber scenario under `features/mcp-server/` that runs under the builtin profile, or a Pi 1.5.0 source file. The builtin profile starts a real Pi 1.5.0 without pi-mcp-adapter, so Pi's built-in MCP runs the servers. A Pi source file is cited by its path under `node_modules/@earendil-works/pi-coding-agent/`, for example `dist/extensions/mcp/index.js`.

This extension does not run MCP servers itself. Each install writes one entry for each plugin server into the `mcp-adapter.json` file of the install scope: `~/.pi/agent/mcp-adapter.json` for the user scope, `<project>/.pi/mcp-adapter.json` for the project scope. When Pi loads pi-mcp-adapter, pi-mcp-adapter reads that file and runs the servers. When Pi does not load pi-mcp-adapter but runs its built-in MCP, this extension registers each plugin server with Pi's built-in MCP at each session start, and Pi runs the servers. See [Pi's built-in MCP](#pis-built-in-mcp). Earlier releases of this extension wrote the entries into the `mcp.json` file of the scope. `/reload` moves them into `mcp-adapter.json`. See [Upgrading](#upgrading).

With pi-mcp-adapter, this extension needs pi-mcp-adapter 7.0.0 or a later 7.x release. pi-mcp-adapter 5.2.0 moves the MCP SDK from 2.0.0 to 2.3.1, which fixes the security advisory GHSA-6qxp-vccf-f47h. With the SDK 2.0.0, a malicious or compromised MCP server could point a sign-in at its own authorization server. It then received the refresh token and the client secret that an earlier sign-in saved. Since 5.2.0, pi-mcp-adapter does not follow a server URL that redirects to another host, so a plugin server with such a URL does not connect. A redirect from `http` to `https` on the same host still works. pi-mcp-adapter 7.0.0 still ships the MCP SDK client 2.3.1.

## Choosing an implementation

This extension picks the implementation from what Pi loads. When Pi loads pi-mcp-adapter, pi-mcp-adapter runs the plugin servers. When Pi does not load pi-mcp-adapter and runs its built-in MCP, Pi's built-in MCP runs them. When Pi runs neither, no plugin server runs. The same installed plugin works under each, with no plugin command in between (`features/mcp-server/implementation-switch.feature`).

Each install writes the `mcp-adapter.json` entries and records the servers of the plugin, whatever implementation runs at that time. So you can switch at any time (MSEL-02, MSEL-04):

- To move from pi-mcp-adapter to Pi's built-in MCP, remove pi-mcp-adapter from the packages that Pi loads. Also remove the `-builtin:mcp` entry that pi-mcp-adapter added to the `extensions` of your user Pi settings, `~/.pi/agent/settings.json`. Then start Pi again. Pi's built-in MCP runs the plugin servers (`features/mcp-server/implementation-switch.feature`).
- To move back, add pi-mcp-adapter again, then start Pi again. pi-mcp-adapter runs the entries that the install wrote, also for a plugin that you installed while Pi's built-in MCP ran (`features/mcp-server/implementation-switch.feature`).

This extension never edits your Pi settings (D-MB-01). If you remove pi-mcp-adapter but keep its `-builtin:mcp` entry, Pi runs no MCP. No plugin server runs, and this extension registers nothing, so Pi reports no error (MSEL-03, `features/mcp-server/implementation-switch.feature`). While pi-mcp-adapter runs, this extension also registers nothing with Pi's built-in MCP (MSEL-03, `features/mcp-server/listing.feature`).

A plugin that an earlier release of this extension installed runs under Pi's built-in MCP too, with no reinstall. Its record holds no copy of its servers, so this extension reads them from the plugin source that the record names (MREC-02, `features/mcp-server/implementation-switch.feature`). `/claude:plugin info` shows the state of each of those servers (`features/mcp-server/builtin-status.feature`).

## Server and tool names

Claude Code registers a plugin server under the name `plugin:<plugin>:<server>`. The model sees each tool of that server as `mcp__plugin_<plugin>_<server>__<tool>`. To make a name, Claude Code replaces every character outside `A-Z`, `a-z`, `0-9`, `_` and `-` with `_` (ANAME-01).

This extension gives the tools the same names. It applies the same rule to `plugin:<plugin>:<server>` and adds a `_` at the end. The result is the key of the server entry in `mcp-adapter.json`. Every entry also gets `toolPrefix: "mcp"`. With this key and this prefix, pi-mcp-adapter names each tool `mcp__plugin_<plugin>_<server>__<tool>`, the name that Claude Code uses. The `_` at the end of the key gives the `__` between the server name and the tool name. On pi-mcp-adapter 7.0.0, the `mcp` tool lists the server `stub` of the plugin `demo` under the key `plugin_demo_stub_`, and a search activates its tool as `mcp__plugin_demo_stub__echo` (`features/mcp-server/listing.feature`).

| Plugin | `mcpServers` key | Key in `mcp-adapter.json` | Tool names                      | Pi built-in server name and tool names                                                      | Name shown by `info` |
| ------ | ---------------- | ------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------- | -------------------- |
| `foo`  | `api`            | `plugin_foo_api_`         | `mcp__plugin_foo_api__<tool>`   | `plugin_foo_api`, `mcp__plugin_foo_api__<tool>` (`features/mcp-server/listing.feature`)     | `plugin:foo:api`     |
| `foo`  | `my.db`          | `plugin_foo_my_db_`       | `mcp__plugin_foo_my_db__<tool>` | `plugin_foo_my_db`, `mcp__plugin_foo_my_db__<tool>` (`features/mcp-server/listing.feature`) | `plugin:foo:my.db`   |
| `bar`  | `api`            | `plugin_bar_api_`         | `mcp__plugin_bar_api__<tool>`   | `plugin_bar_api`, `mcp__plugin_bar_api__<tool>` (`features/mcp-server/listing.feature`)     | `plugin:bar:api`     |

Under Pi's built-in MCP, this extension registers each server under the key without its `_` at the end, `plugin_<plugin>_<server>`, and Pi names each tool `mcp__plugin_<plugin>_<server>__<tool>` (D-MB-13). Pi lists the server `stub` of the plugin `demo` as `plugin_demo_stub`, and a search through `tool_search` loads its tool as `mcp__plugin_demo_stub__echo` (`features/mcp-server/listing.feature`). In a tool name, Pi replaces every character outside `A-Z`, `a-z`, `0-9` and `_` with `_`, `-` included, and it cuts a name longer than 64 characters (`dist/extensions/mcp/tools.js`). The registered server name keeps each `-`. See [Name length](#name-length) and [Divergences and documented absences](#divergences-and-documented-absences).

`/claude:plugin info` shows each server by its Claude Code name, `plugin:<plugin>:<server>`, with the server name exactly as the plugin declares it. The pi-mcp-adapter panel and commands, such as `/mcp-adapter disable`, show and accept the key, with its `_` at the end. pi-subagents `mcp:` entries also use the key. Under Pi's built-in MCP, they use the built-in server name instead, `plugin_<plugin>_<server>`, with no `_` at the end. Pi's `/mcp` command shows the name registered with Pi's built-in MCP (`features/mcp-server/builtin-status.feature`).

Two plugins can declare servers with the same name. Their keys usually differ, because each key holds the plugin name. A pair of servers whose names give the same key is refused like any other collision. For example, `plugin:a_b:c` and `plugin:a:b_c` both give the key `plugin_a_b_c_`.

An install, update, or reinstall fails if the new key is equal to the key of another server, and it leaves nothing behind: the command rolls back every component that it already wrote. The other server can belong to the same plugin, to another plugin, or to any MCP configuration that pi-mcp-adapter reads. pi-mcp-adapter 7.0.0 groups the tools of a server under a namespace in which every `-` of the key becomes `_` (checked in the 7.0.0 source, `formatServerNamespace`). So the install also fails if the two keys are equal after every `-` becomes `_`, for example `plugin_foo_my-db_` and `plugin_foo_my_db_`. Claude Code runs these two servers side by side. This refusal applies only to Pi (ANAME-03). See [Divergences and documented absences](#divergences-and-documented-absences).

## Server sources

A plugin can declare its MCP servers in more than one place. This extension reads them in the order of Claude Code 2.1.316 (D-CF6-01):

1. The `.mcp.json` file at the plugin root.
2. The `mcpServers` field of the plugin's `plugin.json`. Its value is a map of servers, a path to a file that starts with `./`, or an array of maps and paths. The elements of an array are read in their order.

A server that a later source declares replaces the server with the same name from an earlier source. The server keeps the position of the first declaration. The plugin's servers are all the servers that remain.

The marketplace entry of the plugin can also declare `mcpServers`. Claude Code reads it only when the plugin has no `plugin.json`. The entry then takes the place of `plugin.json`, whatever its `strict` value is. When the plugin has a `plugin.json`, the entry's `mcpServers` is ignored, and it causes no `strict: false` conflict.

A file that a path names can hold the server map in an `mcpServers` member, or the server map alone. The same applies to `.mcp.json`.

A `.mcp.json` that is a symbolic link is read through the link, wherever the link points. Claude Code 2.1.316 reads it the same way, for a plugin of a local directory marketplace and for a git plugin. A path that `mcpServers` names is read through a symbolic link too, when the real target of the link is inside the plugin root. Claude Code reads it the same way. If the real target is outside the plugin root, the plugin is refused. See [Invalid server configs](#invalid-server-configs) and [Divergences and documented absences](#divergences-and-documented-absences).

For example, a plugin declares the servers `a` and `c` in `.mcp.json`, and the servers `a` and `b` in `plugin.json`:

| Server | In `.mcp.json` | In `plugin.json` | Installed from |
| ------ | -------------- | ---------------- | -------------- |
| `a`    | ✓              | ✓                | `plugin.json`  |
| `c`    | ✓              | --               | `.mcp.json`    |
| `b`    | --             | ✓                | `plugin.json`  |

pi-mcp-adapter 7.0.0 lists the three servers in the order `a`, `c`, `b`, and a call to `a` reaches the server from `plugin.json` (`features/mcp-server/sources.feature`).

A path that ends in `.mcpb` or `.dxt` names an MCP bundle. Claude Code unpacks and runs a bundle, but pi-mcp-adapter cannot. See [Partially available plugins](#partially-available-plugins). A path without `./`, such as `servers.json`, still loads here, although Claude Code refuses such a `plugin.json`. See [Divergences and documented absences](#divergences-and-documented-absences). For a source that is missing or not valid, see [Invalid server configs](#invalid-server-configs).

## Tool search

| --------------------------------------------- | ----------- | -------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tools load on demand through a search         | ✓           | ✓              | ✓ (`features/mcp-server/listing.feature`)        | pi-mcp-adapter: through its `mcp` tool. Pi built-in: through Pi's `tool_search` tool                                                                                                                                        |
| `alwaysLoad: true` keeps tools in context     | ✓           | ✓              | ✓ (`features/mcp-server/builtin-direct.feature`) | pi-mcp-adapter: written as `directTools: true`. Pi built-in: written as `exposure: "direct"`                                                                                                                                |
| `_meta["anthropic/alwaysLoad"]` on a tool     | ✓           | ✗              | ✗ (`dist/core/mcp-servers.js`)                   | each tool follows the setting of its server                                                                                                                                                                                 |
| Pi's own `tool_search` tool                   | --          | ⚠              | ✓ (`dist/extensions/mcp/index.js`)               | pi-mcp-adapter: off by default. Turn it on with `"defaultTools": ["+tool_search"]` in Pi settings. Pi built-in: on as soon as a server with deferred tools is configured. Both find plugin tools by their Claude Code names |
| Pi's own `codemode` tool                      | --          | ⚠              | ⚠ (`dist/extensions/mcp/index.js`)               | off by default. Its scripts call plugin tools by their Claude Code names. Pi's built-in MCP turns on `tool_search`, not `codemode`, for the deferred tools of plugin servers                                                |
| Plugin tools reachable with `tool_search` off | --          | ✓              | ✗ (`dist/extensions/mcp/index.js`)               | Pi built-in: a deferred tool is offered only through `tool_search`. Claude Code keeps MCP tools out of the prompt by default and finds them through its tool search. A server with `alwaysLoad: true` keeps all its tools in the prompt.

This extension writes `directTools: "search"` on every entry, so pi-mcp-adapter keeps the tools out of the first request to the model. A server with `alwaysLoad: true` gets `directTools: true`, so its tools are in every request (ANAME-04). On pi-mcp-adapter 7.0.0, the first request offers the `mcp` tool and no plugin tool (`features/mcp-server/listing.feature`). The mapping of `alwaysLoad` was checked in the 7.0.0 source, where `directTools` takes `true` or `"search"`.

Claude Code 2.1.294 also reads `_meta["anthropic/alwaysLoad"]` on each tool that a server reports. A tool with the value `true` stays in the prompt, even when its server is deferred. Under a server with `alwaysLoad: true`, a tool with the value `false` stays deferred. pi-mcp-adapter ignores the `_meta` of a tool, and this extension writes the entry before any tool list is known. So each tool follows the setting of its server: a tool that asks to stay in the prompt loads on demand like the other tools of its server. The pi-mcp-adapter 7.0.0 source does not read `alwaysLoad` anywhere.

The model finds a tool through the `mcp` tool of pi-mcp-adapter. A call such as `mcp({ search: "query a database" })` searches the tools of all servers and activates each tool that matches. From the next request on, the model sees each activated tool by its full name, such as `mcp__plugin_foo_api__query`, and calls it directly. On pi-mcp-adapter 7.0.0, the search result starts with `Activated as direct tools: mcp__plugin_demo_stub__echo.`, and the next request offers that tool (`features/mcp-server/listing.feature`). A direct call to it reaches the server (`features/mcp-server/invocation.feature`).

Since pi-mcp-adapter 6.0, on Pi 0.99 and later, each plugin tool is also a Pi deferred tool. Pi registers a deferred tool but leaves it out of the requests to the model until a search turns it on. So Pi's own `tool_search` and `codemode` tools can find and call the plugin tools, under their Claude Code names. On Pi 1.5.0, Pi registers `mcp__plugin_demo_stub__echo` before any search, and turns it on only after the search (`features/mcp-server/listing.feature`).

Pi also has its own `tool_search` tool. It is off by default, and pi-mcp-adapter does not turn it on. On Pi 1.4.0 with pi-mcp-adapter 7.0.0, Pi registers `tool_search` and `codemode`, and neither is on. A run on 2026-11-01 measured this. If you want the model to use it, add this setting to your Pi settings file, `~/.pi/agent/settings.json` or `<project>/.pi/settings.json`:

```json
{
  "defaultTools": ["+tool_search"]
}
```

This extension never edits Pi settings files. The choice to add this setting is yours.

If you start Pi with `--no-extensions`, Pi also leaves out its built-in `tool_search` and `codemode`, even with this setting. To keep `tool_search`, also pass `-e builtin:tool-search`. A run of Pi 1.4.0 on 2026-11-01 measured both cases. With `--no-extensions`, Pi registered no `tool_search`, with or without the setting. With `--no-extensions -e builtin:tool-search`, Pi registered `tool_search`, and the setting turned it on.

## Name length

Claude Code does not shorten MCP tool names and does not check their length when it installs a plugin. This extension does the same: no install-time length check exists (ANAME-03).

The measurement of 2026-10-06 showed that Pi and pi-mcp-adapter do not limit the length of these names either. Pi 1.0.0 with pi-mcp-adapter 5.0.0 registered tools with names of 64, 65, 80 and 136 characters. It sent all of them to the model provider, and it ran the 136-character tool when the model called it. No run measured long names on pi-mcp-adapter 7.0.0. Its source builds the name of a direct or search-mode tool with no length limit, so the names of plugin tools are not shortened. Only its deferred names, which `MCP_DIRECT_TOOLS` can give a server, are cut to 64 characters with a hash.

Pi's built-in MCP shortens a tool name that is longer than 64 characters. It keeps the first 55 characters and adds `_` and an 8-character hash (`dist/extensions/mcp/tools.js`). For example, the tool `echo` of the server `a-server-whose-name-runs-well-past-the-limit` of the plugin `demo` would be `mcp__plugin_demo_a_server_whose_name_runs_well_past_the_limit__echo`, 67 characters. Pi names it `mcp__plugin_demo_a_server_whose_name_runs_well_past_the_ca340f16` (`features/mcp-server/listing.feature`). So under Pi's built-in MCP, the model and plugin hooks see such a tool under a name that is not the Claude Code name. See [Divergences and documented absences](#divergences-and-documented-absences).

pi-mcp-adapter turns Pi's built-in MCP off, so this cut does not apply while pi-mcp-adapter runs the servers. At a session start, once for each of its versions, pi-mcp-adapter 7.0.0 adds `-builtin:mcp` to the `extensions` of your user Pi settings and reports it, unless those settings already name `builtin:mcp`. It skips that step in a session started with `--mcp-config`. In such a session, Pi still does not run its built-in MCP support, because pi-mcp-adapter owns the `/mcp` command. Both facts were checked in the 7.0.0 source. To run plugin servers through Pi's built-in MCP later, you remove pi-mcp-adapter and that settings entry yourself. See [Choosing an implementation](#choosing-an-implementation).

The limit is in the model provider:

- OpenAI accepts function names of at most 64 characters.
- Anthropic accepts tool names that match `^[a-zA-Z0-9_-]{1,128}$`, so at most 128 characters.

A long plugin name and a long server name can make a tool name that a provider refuses. The provider then rejects the request. The measurement did not send an over-long name to a real provider, so this document does not record the exact error. To find the length of a tool name, add the lengths of `mcp__plugin_`, the plugin name, `_`, the server name, `__`, and the tool name.

## Connection lifecycle

Claude Code connects to the MCP servers of plugins in the background when a session starts. It keeps the connections for the whole session.

This extension never writes `lifecycle` on an entry, so pi-mcp-adapter uses its default, `lazy` (ANAME-05). In this mode, when Pi starts, the adapter starts only a server for which it holds no valid cached list of tools. It reads the list, saves it, and stops the server. The adapter starts the server again when the model uses one of its tools, and stops it again after a period with no use. A server with a valid cached list does not start until the model first uses one of its tools. Until that first use, `/claude:plugin info` can show `status unknown`. See [Server status in info](#server-status-in-info).

On pi-mcp-adapter 7.0.0, the stub server logs one start for the listing at a session start that has no cached list. A tool call then logs a second start, which lists the tools again before the call (`features/mcp-server/listing.feature`, `features/mcp-server/invocation.feature`). The default `lazy` was checked in the 7.0.0 source.

Thus the first call to a tool of a stopped server waits while the server starts. A server that keeps data in memory loses that data when the adapter stops it. You can change the mode of one server: set `lifecycle` on its entry yourself. pi-mcp-adapter 7.0.0 accepts `lazy`, `lazy-keep-alive`, `keep-alive`, and `eager`. With `lazy-keep-alive`, the server starts on its first use, as with `lazy`, and then stays running for the session. This extension keeps that field when it updates or reinstalls the plugin.

Pi's built-in MCP has no lazy mode for plugin servers. It connects every registered server when the session starts and keeps the connection, as Claude Code does. See [When the servers register](#when-the-servers-register).

## Project-scope servers

This section describes pi-mcp-adapter. Pi's built-in MCP asks for no approval. See [Project trust under Pi's built-in MCP](#project-trust-under-pis-built-in-mcp).

A project-scope plugin writes its servers into `<project>/.pi/mcp-adapter.json`. pi-mcp-adapter treats every server from a project file as a project server, and it owns the trust rules for these servers:

- In a project that Pi does not trust, pi-mcp-adapter blocks the server.
- In a trusted project, an interactive session asks whether to allow the server when the adapter loads it, first at the `/reload` after the install. The first choice, `Don't allow`, is the default. pi-mcp-adapter does not remember `Don't allow`, so it asks again at each load until you allow the server.
- pi-mcp-adapter keeps each approval for the exact entry, so it asks again after an update that changes the entry. An update of a plugin from its own git source changes the entry of each stdio server when the commit changes, because the plugin moves to a new clone directory.
- A headless session, such as a print, JSON or RPC session, skips a server that is not approved. There is one exception: when the user-global configuration of pi-mcp-adapter sets `settings.projectServers` to `allow`, a headless session in a trusted project runs the server without an approval. pi-mcp-adapter ignores this setting in a project file.
- Since pi-mcp-adapter 5.4.0, `pi --mcp-project-servers allow` runs the servers of a trusted project without an approval, in an interactive session too, for that Pi process only. A server of a project that Pi does not trust stays blocked.

The cucumber scenarios in `features/mcp-server/project-scope.feature` measured the headless rules on pi-mcp-adapter 7.0.0. In a trusted project with `settings.projectServers` set to `allow`, the server starts and answers a call. In a trusted project without that setting, and in a project that Pi does not trust even with the setting, the server never starts. A call through the `mcp` tool then returns `Tool "mcp__plugin_demo_stub__echo" not found. Use mcp({ search: "..." }) to search.` A status call, `mcp({})`, lists the server as blocked. The reason holds `project server approval required` in the trusted project, and `blocked by project trust` in the project that Pi does not trust. The interactive dialog and the `--mcp-project-servers` flag were checked in the 7.0.0 source.

While a server waits, `/claude:plugin info` shows `pending approval` for it. pi-mcp-adapter 7.0.0 keeps each approval in `<agent dir>/mcp-project-approvals.json`, and it offers no way for another extension to approve a server. This extension never writes the approval files of pi-mcp-adapter (D-CF6-03, NFR-10). For the full rules, see [Project server trust](https://github.com/nicobailon/pi-mcp-adapter/blob/main/docs/configuration.md#project-server-trust) in the pi-mcp-adapter docs.

Claude Code never asks for approval of a plugin server. It asks only for the servers of a project `.mcp.json` file.

## pi-mcp-adapter settings that change plugin servers

Three settings of pi-mcp-adapter change which plugin servers load, or how their tools reach the model:

- `PI_MCP_CONFIG_MODE=exclusive`: pi-mcp-adapter reads only its user file, `~/.pi/agent/mcp-adapter.json` or the file of `--mcp-config`. Project-scope plugin servers do not load. The adapter also skips the other sources that it reads by default, such as Pi's `mcp.json` files, imported configurations, and the files of parent directories.
- `--mcp-config <file>`: pi-mcp-adapter reads this file in place of `~/.pi/agent/mcp-adapter.json`. User-scope plugin servers do not load. The adapter still reads the project files, so project-scope plugin servers still load.
- `MCP_DIRECT_TOOLS=<server>[/<tool>],...`: pi-mcp-adapter reads this variable once, when Pi loads pi-mcp-adapter. The variable replaces the `directTools` value of every entry. The tools of a server that it names are in every request, under their Claude Code names. A server that it does not name gets no tool in the request, and a search through the `mcp` tool lists its tools but activates none. pi-mcp-adapter then adds one tool for the whole server to every request, `mcp__plugin_<plugin>_<server>_`. It also registers each tool of the server as a Pi deferred tool, a tool that `tool_search` and `codemode` can reach, under the name `mcp__plugin_<plugin>_<server>___<tool>`, with three `_` in front of the tool name. That is not the Claude Code name. `__none__` names no server. Each server then gets the same tool for the whole server, and pi-mcp-adapter registers no deferred tool. With any value, the model still calls each tool of each configured server through the `mcp` tool, under its Claude Code name. Under `__none__`, such a call stays inside the `mcp` tool, so Pi and hooks see only a call to `mcp`. A run of Pi 1.4.0 with pi-mcp-adapter 7.0.0 measured these cases on 2026-11-01.

The first two settings were checked in the pi-mcp-adapter 7.0.0 source. This extension does not read these settings and does not warn about them.

pi-mcp-adapter 7.0.0 also has its own loader for Claude plugins, the `claudePlugins` setting. The loader is off by default. It reads only the plugin folders that you list in `claudePlugins`, and only the `.mcp.json` of a folder whose entry sets `mcp: true`. It names each server by the name in that file, not by the key of this extension. So the servers of a plugin that this extension installed run once, unless you list that plugin there too. Then they run a second time, under the names that the plugin declares. This extension does not read or check `claudePlugins` (MC-4). This was checked in the 7.0.0 source.

For the file layout and the settings of pi-mcp-adapter, see its [configuration docs](https://github.com/nicobailon/pi-mcp-adapter/blob/main/docs/configuration.md).

## Pi's built-in MCP

When Pi does not load pi-mcp-adapter, Pi's built-in MCP runs the plugin servers. This extension registers each server of each enabled plugin with it, under the name `plugin_<plugin>_<server>` (`features/mcp-server/listing.feature`). The entries in `mcp-adapter.json` stay in place for pi-mcp-adapter, and Pi's built-in MCP does not read them.

### When the servers register

This extension registers the servers at each session start and at each `/reload`. It registers them again after the load applies changes to the installed plugins, for example when `autoapply` installs a plugin (D-MB-10, `features/mcp-server/lifecycle.feature`). A plugin command does not register or remove a server at once. So an install, an enable, or an update takes effect at the next `/reload`. A plugin that you disable or uninstall keeps its server until the next `/reload` or session (BLT-06, `features/mcp-server/lifecycle.feature`). A published change to a server reaches Pi only after the plugin updates (`features/mcp-server/lifecycle.feature`).

The registrations live only in the Pi session. Pi starts each session with no registration, and this extension writes no file for Pi's built-in MCP (`dist/core/extensions/loader.js`). Pi connects every registered server when the session starts, and keeps the connection for the session, as Claude Code does. A stub server logs one `initialize` for the whole session (`dist/extensions/mcp/index.js`, `features/mcp-server/lifecycle.feature`).

If Pi refuses a registration, for example a `url` that is not an `http` or `https` URL, this extension writes the refusal to its debug log and registers the other servers. `/claude:plugin info` shows `not loaded` for the refused server (`dist/core/mcp-servers.js`, `features/mcp-server/builtin-status.feature`).

### Variables under Pi's built-in MCP

Pi's built-in MCP has its own variable rules. In `env` and `headers` values, it expands `$NAME` and `${NAME}`, and it runs a value that starts with `!` as a shell command. It has no `${NAME:-default}`, and it does not connect a server whose variable is not set (`dist/core/resolve-config-value.js`). These are not the rules of Claude Code. So this extension resolves every variable itself when it registers the server, with the rule of Claude Code, from the environment of the Pi session (D-MB-14, `features/mcp-server/configuration.feature`). A variable that you set before Pi starts reaches the server with no reinstall (`features/mcp-server/invocation.feature`). `${CLAUDE_PROJECT_DIR}` becomes the working directory of the session, in both scopes (D-MB-15).

In `env` and `headers` values, the fields that Pi expands, this extension writes each `$` as `$$` and a leading `!` as `$!`. Pi turns them back into `$` and `!`, so the server gets the value byte for byte, and no command runs (`dist/core/resolve-config-value.js`, `features/mcp-server/configuration.feature`). A variable that is not set and has no default keeps the literal `${NAME}` text, as in Claude Code (AVAR-02, `features/mcp-server/configuration.feature`). In a `url`, such a literal is not a valid URL, so Pi refuses the server, and info shows `not loaded` (`features/mcp-server/builtin-status.feature`). The [withheld credentials](#withheld-credentials) apply as they do for pi-mcp-adapter. A conformance test runs each expansion case through the resolver of Pi 1.5.0 and compares the result with the value of Claude Code (`test/integration/mcp-builtin-encoding-conformance.test.ts`).

The resolved values are not private to the server. Pi gives the config of every registered server, resolved values and secrets included, to every extension in the same Pi process (D-MB-14, D-MB-04, `dist/core/extensions/loader.js`). The probe extension of `features/mcp-server/builtin-values.feature` reads them this way. These extensions can already read the same values from the environment of the Pi process. This extension writes none of the resolved values to a file.

### Project trust under Pi's built-in MCP

Pi's built-in MCP has no approval step. A project-scope plugin server registers only while Pi trusts the project. It then runs with no approval and no allow setting (BLT-03, D-MB-09, `features/mcp-server/project-scope.feature`). In a project that Pi does not trust, this extension registers no project-scope server, and info shows `project not trusted` for it (`features/mcp-server/project-scope.feature`, `features/mcp-server/builtin-status.feature`). Claude Code also asks for no approval of a plugin server.

For a plugin installed in both scopes, while Pi trusts the project, each project-scope server replaces the user-scope server with the same name. While Pi does not trust the project, the user-scope servers run (D-MB-18, D-MB-23, `features/mcp-server/builtin-trust.feature`).

### Servers in mcp.json

Pi's built-in MCP also reads your `~/.pi/agent/mcp.json` and, in a trusted project, `<project>/.pi/mcp.json` (`dist/extensions/mcp/config.js`). A server in these files wins over a registered server when the two names are equal after every `-` becomes `_` (`dist/extensions/mcp/index.js`). For a plugin server, `/claude:plugin info` then shows `overridden by mcp.json`, and Pi's `/mcp` lists the override (D-MB-19, `features/mcp-server/builtin-status.feature`). Info counts an `mcp.json` entry when it has a `command` or a `url`, so an entry that Pi refuses for another reason also shows as an override (D-MB-24).

Claude Code also lets a server that you configured win over a plugin server. It matches the two servers by their command or URL, not by their names, and `/plugin` reports the skipped plugin server (D-MB-24). This extension shows no notice at load for an overridden server. Info and Pi's `/mcp` report it (D-MB-19).

### A name that another extension registered

Another extension can register a server under the name `plugin_<plugin>_<server>` before this extension does. Pi then still refuses the registration of this extension, because each name has one owner (`dist/core/extensions/loader.js`). This extension notes the refusal for the session, and `/claude:plugin info` shows `not loaded` for the plugin server. Pi's `/mcp` lists the other extension's server under the name (D-MB-29, `features/mcp-server/builtin-status.feature`). Pi 1.5.0 gives an extension no reliable way to learn the path that Pi records for its own registrations, so the refusal is the only signal that the server under the name is not the plugin's.

### Tool search and /mcp

Pi's built-in MCP registers each plugin tool as a deferred tool and turns on Pi's `tool_search` tool. The model searches with `tool_search`, then calls the tool directly by its Claude Code name. No `mcp` proxy tool exists (`features/mcp-server/invocation.feature`, `dist/extensions/tool-search/tool.js`). A search that matches no plugin tool loads none, and the server gets no call (`features/mcp-server/listing.feature`). A server with `alwaysLoad: true` offers its tools from the first request, and the model calls them with no search (`features/mcp-server/builtin-direct.feature`).

Pi's `/mcp` manager can turn a plugin server off, but only for the current session. Pi saves no choice for a server that an extension registered (`dist/extensions/mcp/index.js`). Info then shows `disabled` (`features/mcp-server/builtin-status.feature`). Info reads `disabled` from Pi's tool list, because Pi hides every tool of a server that it turns off. Pi also hides the tools in two other cases. When this extension registers a server again with a changed config, for example after `autoapply` updates the plugin during a load, Pi hides the old tools until the new connection lists its tools. This extension notes such a server, and info shows `not connected` for it while its tools are hidden, also if you then turn it off in `/mcp` (D-MB-20, `test/platform/mcp-builtin-status.test.ts`). When a connected server stops offering every tool, Pi hides the tools that it dropped, and info shows `disabled`. The [user overrides](#user-overrides) in `mcp-adapter.json` apply only to pi-mcp-adapter.

### Legacy mcp.json entries

Releases before AMIG-01 wrote plugin servers into `mcp.json` under the server name that the plugin declares. Pi's built-in MCP reads `mcp.json` at its own session start, before the load of this extension moves those entries out (`dist/extensions/mcp/index.js`). So in the first session after such an upgrade, Pi runs each legacy entry once more under its old name, beside the registered server. In that session, Pi reads the values of the entry with its own `$` and `!` rules, which the entry was not written for (`dist/core/resolve-config-value.js`). The same load moves the entries out of `mcp.json`, so the next session runs only the registered servers (D-MB-21). See [Upgrading](#upgrading).

### Other gaps

- Pi starts a stdio server in the working directory of the session (`dist/extensions/mcp/runtime.js`). Claude Code 2.1.318 starts it in the project root that it resolves, which can differ from the launch directory. This extension writes no `cwd`, because a plugin cannot set one in Claude Code either, and it drops a `cwd` that the plugin sets (D-MB-16, D-MB-26, `features/mcp-server/builtin-values.feature`).
- Pi changes a `command` or an `args` element that is `~`, or that starts with `~/`, into a path in your home directory when it starts the server (`dist/extensions/mcp/runtime.js`). Claude Code passes the `~` as written. The install refuses a server whose own text starts with such a `~`. A variable can still resolve to one, such as `${CONFIG}` with `CONFIG=~/conf`, or `${X:-}~/a` with `X` not set. This extension does not register such a server, because Pi would run another command than Claude Code. It writes the reason to its debug log, and info shows `not loaded` for the server (`features/mcp-server/builtin-status.feature`).
- The `timeout` of Pi starts again on progress, and it is 60 seconds when the plugin sets none. See [Translated fields](#translated-fields) (D-MB-17).
- Pi receives the `description` of the plugin, as pi-mcp-adapter does (D-MB-28, `features/mcp-server/builtin-values.feature`).
- The withheld credentials follow the deny-lists of Claude Code 2.1.291, as for pi-mcp-adapter. Claude Code 2.1.318 can withhold more (D-MB-27).

This extension never writes `oauth.clientSecret`, `oauth.clientName`, or `oauth.clientRegistration` for Pi's built-in MCP (D-MB-11, `features/mcp-server/builtin-values.feature`). Without `callbackPort`, it writes no `callbackUrl`, and Pi then signs in with `http://127.0.0.1:<free port>/callback`, not with the `localhost` address that Claude Code uses (D-MB-25, `dist/extensions/mcp/oauth.js`).

For a `type: "http"` server, pi-mcp-adapter 7.0.0 uses Streamable HTTP. Because `httpTransport` stays unset, the adapter tries the older SSE transport when the server answers a `POST` request with the status 404, 405, 406, or 415 while it connects. This fallback was checked in the 7.0.0 source. After the `notifications/initialized` message, the MCP SDK client also opens an optional event stream with a `GET` request, and a server can answer it with 405. The scenarios in `features/mcp-server/configuration.feature` measured this on a loopback server. They also measured that each request carries the plugin's headers, with each `${NAME}` expanded when the server connects.

The two timeouts do not mean the same thing. In Claude Code, `timeout` is a hard limit on one tool call, in milliseconds. Progress messages from the server do not extend it. If a server sets no `timeout`, Claude Code uses the `MCP_TOOL_TIMEOUT` environment variable, or a default of about 28 hours. In pi-mcp-adapter, `requestTimeoutMs` starts again each time the server reports progress. If an entry has no `requestTimeoutMs`, the default of the MCP SDK applies, which is 60 seconds. This extension does not write a default. So a plugin tool that runs for more than 60 seconds with no progress messages fails under Pi but not under Claude Code. To prevent this, the plugin can set `timeout`, or you can set `requestTimeoutMs` on the entry yourself.

Pi's built-in MCP has the same gap. Its `timeout` is in seconds, so this extension writes the milliseconds of the plugin divided by 1000, with no rounding: a `timeout` of 2500 becomes `2.5` (D-MB-17, `features/mcp-server/builtin-values.feature`). Pi also starts the timeout again on progress, and with no `timeout` it waits 60 seconds (`dist/extensions/mcp/runtime.js`, `dist/extensions/mcp/tools.js`). You cannot change the timeout of a registered server yourself, because Pi reads no user value for it.

### OAuth beside headers

Claude Code signs in to a remote server with OAuth unless its `headers` hold an `Authorization` key, in any case. Other headers do not turn OAuth off. pi-mcp-adapter turns OAuth off for every server with headers, unless the entry sets `auth: "oauth"`. So this extension writes `auth: "oauth"` for a remote server whose headers hold no `Authorization` key (D-08-04). A server with an `Authorization` header gets no `auth`, so OAuth stays off, as in Claude Code. A server with no headers, or with empty `headers`, gets no `auth` either. pi-mcp-adapter then uses OAuth when the server asks for it, as Claude Code does. On pi-mcp-adapter 7.0.0, a server with the one header `X-Team: core` gets `auth: "oauth"`. It connects, receives the header on each request, and starts no sign-in while the server asks for none (`features/mcp-server/configuration.feature`).

In OAuth mode, pi-mcp-adapter refuses a header that references a variable that is not set or is empty, and a header whose value is empty. So this extension writes `auth: "oauth"` only when every written header value is clean. A clean value references only variables that have a non-empty value at install time, and it is not empty after the spaces at its ends are removed. The split token counts as not clean, because it references a variable with an empty value. For this check, a `${NAME:-default}` reference counts as `${NAME}` if `NAME` is set at install time, and as its default text if `NAME` is not set (D-CF1-13). The table shows what the install writes for each kind of header value:

| Header value of the plugin                          | Environment at install | Written value                                                     | `auth: "oauth"` written |
| --------------------------------------------------- | ---------------------- | ----------------------------------------------------------------- | ----------------------- |
| `core`                                              | any                    | `core`                                                            | yes                     |
| `${TEAM}`                                           | `TEAM` set             | `${TEAM}`                                                         | yes                     |
| `${TEAM}`                                           | `TEAM` not set         | `${TEAM}`, with the `MCP server variables not set.` warning       | no                      |
| `${TEAM:-acme}`                                     | `TEAM` not set         | `${TEAM:-acme}`                                                   | yes                     |
| `${TEAM:-acme}`                                     | `TEAM` set, empty      | `${TEAM:-acme}`                                                   | no                      |
| `${TEAM:-}`                                         | `TEAM` not set         | `${TEAM:-}`                                                       | no                      |
| `${ANTHROPIC_API_KEY}`                              | set                    | an empty value, because the credential is withheld                | no                      |
| `Bearer ${ANTHROPIC_API_KEY}`                       | set                    | `Bearer` and a space, which pi-mcp-adapter trims to `Bearer`      | yes                     |
| `${TEAM}_eu`                                        | `TEAM` set             | `${TEAM}{env:PI_CLAUDE_MARKETPLACE_EMPTY}_eu`, with a split token | no                      |

A server without `auth` connects without OAuth, as before. The OAuth item under Variables in [Divergences and documented absences](#divergences-and-documented-absences) records this gap.

## Dropped fields

This extension drops every other field of a plugin server, with no warning, as Claude Code does. The dropped fields include:

- The Claude Code fields `cwd`, `role`, and `discoveryCache`.
- Every field that only pi-mcp-adapter knows, for example `auth`, `approveTools`, `requestHeadersCommand`, `inheritEnv`, `bearerTokenEnv`, `lifecycle`, and `protocolVersion`. So a plugin cannot choose the MCP protocol version that pi-mcp-adapter 7.0.0 negotiates, and the server gets the adapter's default, `legacy`. For `auth`, only the plugin's own value is dropped. This extension writes `auth: "oauth"` itself under the rule in [OAuth beside headers](#oauth-beside-headers).
- Every `oauth` field outside the four in the table, for example `clientSecret`.
- Every unknown field.

A plugin that declares `description`, `directTools`, or `toolPrefix` gets the value of this extension instead.

So a plugin cannot give itself a pi-mcp-adapter power that Claude Code does not give a plugin. For example, a plugin cannot send your Pi provider token to its server with `auth`, and it cannot approve its own tools with `approveTools`.

## Tool permission rules

The schema of Claude Code lets a remote server declare `tools[].permission_policy` and `toolPermissions`. These fields allow, ask about, or block single tools of the server. pi-mcp-adapter has no rule for each tool. Its `approveTools` field belongs to the user.

So this extension installs such a server, and the server works, but the rules are not enforced. The written entry has neither field, and the tools of the server run without these rules. Install, update, reinstall, enable, import, reconcile, and the move on `/reload` show the warning `MCP server tool rules not enforced.` The warning names the server and the fields. It does not name the tools or the values (ANAME-07). An empty `toolPermissions` holds no rule and gets no warning. It is not known whether Claude Code enforces these rules for the servers of a plugin. For the exact notice, see [MCP server tool rules not enforced](output-catalog.md#mcp-server-tool-rules-not-enforced-aname-07).

## Invalid server configs

A server config that the schema of Claude Code rejects is malformed. Examples are an unknown `type`, a `url` with no `type`, a `timeout` that is not a positive integer, and a `callbackPort` outside 1 to 65535. What a malformed server does depends on where the plugin declares it. This extension follows Claude Code 2.1.316 (D-CF6-02):

- A file source is `.mcp.json`, or a file that `mcpServers` names. A malformed server in a file source is skipped with no message. The other servers and the other components of the plugin install. A skipped server does not replace a server with the same name from an earlier source, so that earlier server stays. A file source that is missing, does not parse, cannot be read, or holds no server map is skipped the same way, and the other sources still load. A file that cannot be read includes every file-system error, also a short-lived one such as too many open files (`EMFILE`). The loader of Claude Code also skips these with no message. Only `claude plugin validate` reports them.
- An inline source is a server map written in `plugin.json` or in the marketplace entry, also as an element of an array. A malformed server in an inline source makes the whole plugin `(unavailable)` with the reason `{malformed mcp}`, and no part of it installs. Claude Code refuses to install such a plugin, because its `plugin.json` or its marketplace entry is not valid.
- An `mcpServers` path that is absolute or that leaves the plugin root also makes the whole plugin `(unavailable)` with `{malformed mcp}`. Claude Code refuses such a `plugin.json` too.
- An `mcpServers` path that passes through a symbolic link is read at the real target of the link when that target is inside the plugin root, as Claude Code reads it. If the real target is outside the plugin root, the whole plugin is `(unavailable)` with `{malformed mcp}`. Claude Code reads that file through the link. See [Divergences and documented absences](#divergences-and-documented-absences). A link whose target does not exist names a missing file, which is skipped with no message.

## User overrides

You can change a plugin server's entry in `mcp-adapter.json` yourself. Only pi-mcp-adapter reads these values. Pi's built-in MCP does not. This extension keeps your values of these fields: `disabled`, `approveTools`, `includeTools`, `excludeTools`, `lifecycle`, `idleTimeout`, `requestTimeoutMs`, `debug`, `searchKeywords`, `openUi`, `trace`, `appendStructuredContent`, and `roots`. pi-mcp-adapter 5.4.0 added the last two: `appendStructuredContent: false` shows the model only the `content` of a tool result, and `roots: false` stops the adapter from sending the session folder to the server (D-CF1-14). Your values survive an update, a reinstall, a plugin disable then enable, and an uninstall then reinstall (D-08-01, D-08-02).

The scenarios in `features/mcp-server/lifecycle.feature` measured this for `disabled: true` on pi-mcp-adapter 7.0.0. After an update, after a disable then enable, and after an uninstall then install, the server does not start, and `mcp({})` returns `MCP: 0/0 servers, 0 tools (1 disabled)`, with the line `⊘ plugin_demo_stub_ (disabled)`.

While the server is not installed, this extension keeps your values in the same `mcp-adapter.json`, under the top-level member `_piClaudeMarketplace.serverChoices`. This happens when you disable or uninstall the plugin, and when an update drops the server. pi-mcp-adapter ignores this member. Each stored choice records the server key, the plugin name, and the marketplace name. When the same plugin from the same marketplace writes the server again, your values go back into its entry and leave the store. A stored choice never applies to a server of another plugin, even one with the same key. It also never applies to a plugin with the same name from another marketplace.

`/mcp-adapter disable` writes its choice into the project file, `<project>/.pi/mcp-adapter.json`, whatever the scope of the server. So for a user-scope plugin, that choice already lives outside the plugin's entry, and it applies only in that project. For a project-scope plugin, the choice lands in the plugin's entry, and the store above keeps it. The store also keeps the values that you write into an entry yourself, in either scope.

One exception exists. If the plugin's own entry sets one of these fields, the plugin owns that field. Today this applies only to `requestTimeoutMs`, which comes from the server's `timeout`. An update or a reinstall then writes the plugin's value, not yours. This matches Claude Code, where a user cannot change the timeout of a plugin server.

You can also write an override before the install: an entry under the server's key with no `command` and no `url`. The install keeps that override inside the plugin's entry. If the plugin sets a field of the override, that field stops applying, and the install shows a warning that names the field. If a later version of the plugin stops setting the field, your value applies again. When you uninstall or disable the plugin, this extension writes your override back, with your own value of each field that the plugin set. For the exact notice and the full list of commands that write the override back, see [MCP server override kept](output-catalog.md#mcp-server-override-kept-afile-06).

## Hooks and agents

Plugin hooks see MCP tools by their Claude Code names (ANAME-02). The matcher `mcp__plugin_foo_api__query` fires for that tool, and `mcp__plugin_foo_api__.*` fires for every tool of the server. `if` predicates work the same way. See [Tool name mapping](hooks-compatibility.md#tool-name-mapping).

Since pi-mcp-adapter 6.0, a call that the model makes through the `mcp` tool, such as `mcp({ tool: "mcp__plugin_foo_api__query" })`, runs the real tool as a nested Pi tool call under its Claude Code name. So Pi reports two tool calls: the call to `mcp`, and inside it the call to `mcp__plugin_foo_api__query`. A run of pi-mcp-adapter 7.0.0 on Pi 1.4.0 measured both calls on 2026-11-01. Under `MCP_DIRECT_TOOLS=__none__`, the call stays inside the `mcp` tool, and Pi reports only the call to `mcp`. A direct call to an activated tool is one call under its Claude Code name. For the hooks that each of these calls fires, see [Tool name mapping](hooks-compatibility.md#tool-name-mapping).

### Customizing generated agents

This extension converts each plugin agent into a pi-subagents agent file named `pi-claude-marketplace-<plugin>-<agent>`. Do not edit these files: install, update, and reinstall regenerate them.

Three conversion rules to know:

- If the source agent does not declare `tools:`, the generated agent has no tool allowlist. pi-subagents then grants its default builtin tools, like Claude Code grants every tool available to subagents. pi-subagents documents that background children also receive ambient extension tools, such as MCP tools from pi-mcp-adapter. A foreground child gets none: with pi-subagents 0.84.0 and pi-mcp-adapter 7.0.0, it is offered `read`, `bash`, `edit`, `write`, `bg_wait`, and `contact_supervisor`, with no `mcp` tool and no plugin tool (`features/mcp-server/agent-grants.feature`). If the source agent sets `disallowedTools`, those names become `excludeTools`.
- Agent-level `allowed-tools`, `mcpServers`, `permissionMode`, and `hooks` fields are dropped, with a warning that explains why. Claude Code ignores all four on plugin agents (`allowed-tools` is a slash-command field). The plugin's own MCP servers and its hooks.json still install.
- A `tools:` entry that names one of the plugin's own MCP tools in Claude Code form, `mcp__plugin_<plugin>_<server>__<tool>`, becomes the pi-subagents entry `mcp:plugin_<plugin>_<server>_/<tool>`. An entry that names a whole server, `mcp__plugin_<plugin>_<server>` or `mcp__plugin_<plugin>_<server>__*`, becomes `mcp:plugin_<plugin>_<server>_`. Under Pi's built-in MCP, these entries are `mcp:plugin_<plugin>_<server>/<tool>` and `mcp:plugin_<plugin>_<server>`. The grant names the server of the MCP implementation that is active when the agent is written. A per-tool `disallowedTools` entry of an agent without `tools:` becomes, in `excludeTools`, the tool name that Pi's built-in MCP gives the tool: `mcp__plugin_<plugin>_<server>__<tool>` with each character other than a letter, a digit, or `_` replaced by `_`. Pi shortens a name longer than 64 characters and adds a hash. Under pi-mcp-adapter the entry keeps the Claude Code name. A grant of a server that Pi's built-in MCP cannot run, such as an `sse` server, is dropped with a warning under built-in and kept under pi-mcp-adapter. A per-tool entry must match a tool name that the server reports exactly. If the server renamed or removed the tool, the name is misspelled, or the tool name holds a character that Claude Code replaces, such as `.` or a space, the whole agent launch fails. To avoid this, grant the whole server, `mcp:plugin_<plugin>_<server>_`, with an agent override (see below). The MCP tool names of other servers, including servers that the install leaves out, are dropped with a warning.

pi-subagents 0.84.0 gives MCP tools only to background children, so this extension writes `async: true` into a generated agent that runs plugin MCP tools. On pi-subagents 0.84.0 a background child can still miss the plugin's tools: pi-subagents rejects the `directTools: "search"` value this extension writes for every server without `alwaysLoad: true`, and it computes a different cache key for a server that uses `${VAR:-default}`. Both are pi-subagents bugs, and fixes are drafted for upstream. The extension writes `async: true` for an agent whose `tools:` grants a plugin MCP tool, and for one without `tools:` in a plugin that installs MCP servers. It does so even when the source agent sets `background: false`, and install warns about it. A call that still asks for a foreground launch (`"async": false`) fails before the child runs, also after pi-mcp-adapter has cached the server's tools. With pi-mcp-adapter 7.0.0, such a launch of an agent granted `mcp__plugin_demo_stub__echo` returns this tool result (`features/mcp-server/agent-grants.feature`):

```text
Unresolved MCP direct-tool selectors: plugin_demo_stub_/echo. Direct MCP tools require a matching configured server and fresh metadata cache; runtime-registered servers require a host/pi-mcp-adapter handoff before child launch.
```

Under Pi's built-in MCP the install warning ends `a launch before Pi's built-in MCP has listed the server's tools still fails`. pi-subagents 0.84.0 refuses a foreground launch of such an agent because an extension registered the server. For the stub server of `demo`, it returns this tool result (`features/mcp-server/agent-grants.feature`):

```text
Agent 'demo:runner' selects MCP tools from servers that extensions registered (plugin_demo_stub). Only background children (async: true) load those extensions; run the agent in the background or add the server to the global mcp.json or a trusted project's .pi/mcp.json.
```

In Claude Code, a subagent granted a plugin MCP tool calls it in the foreground. Running it in the background instead is a deliberate divergence for a companion gap (D-CF6-10, which amends D-CF4-05). See [Divergences and documented absences](#divergences-and-documented-absences). A launch before pi-mcp-adapter has cached the server's tools, or before Pi's built-in MCP has listed them, fails too.

To change a generated agent's settings so the change survives plugin updates, use pi-subagents agent overrides in your Pi settings file (`~/.pi/agent/settings.json` for the user scope, `<project>/.pi/settings.json` for the project scope):

```json
{
  "subagents": {
    "agentOverrides": {
      "pi-claude-marketplace-foo-reviewer": {
        "tools": "read,bash,mcp:plugin_foo_github_"
      }
    }
  }
}
```

Under Pi's built-in MCP, write `mcp:plugin_foo_github` instead.

An override replaces the same field in the generated frontmatter. An `mcp:<key>` entry grants the direct MCP tools of the pi-mcp-adapter server stored under `<key>`, such as `plugin_foo_github_` for the `github` server of plugin `foo`. Under Pi's built-in MCP, an `mcp:<name>` entry grants the tools of the built-in server `<name>`, such as `plugin_foo_github`. pi-subagents loads MCP tools only for background (`async: true`) children.

When you switch between pi-mcp-adapter and Pi's built-in MCP, the next start or `/reload` rewrites each generated agent file whose MCP grant differs for the new implementation. It rewrites only those files, one at a time, and reports nothing (D-MB-03, MGRT-01). With no MCP implementation active, the files stay as they are. A file that you edited stays as it is. An agent that an earlier release installed is translated to the built-in form at the first built-in session, with two known gaps: an agent with a per-tool `disallowedTools` name longer than 64 characters stays in the pi-mcp-adapter form, and the grant of a server that Pi's built-in MCP cannot run is translated, not dropped, so the launch still fails. Run `/claude:plugin reinstall` for such a plugin to write the exact form. A pi-subagents background child that loads this extension changes nothing: it rewrites no agent file, runs no autoapply, and moves no MCP server (MGRT-02).

## Variables

A plugin server can reference environment variables as `${NAME}` or `${NAME:-default}`. Claude Code expands them when it loads the server. pi-mcp-adapter expands variables too, but with different rules. This extension rewrites each value at install time, so that pi-mcp-adapter gives the server the value that Claude Code gives it (AVAR-01, AVAR-02, AVAR-03). The install writes no environment value into `mcp-adapter.json`. This section describes pi-mcp-adapter. For Pi's built-in MCP, this extension resolves the values itself at each registration. See [Variables under Pi's built-in MCP](#variables-under-pis-built-in-mcp).

### Where variables expand

Claude Code expands variables in five fields only: the `command`, `args` and `env` values of a stdio server, and the `url` and `headers` values of a remote server. This extension uses the same five fields. It keeps every other field as literal text, for example the `oauth` fields, the `description`, and the keys of `env` and `headers`. The `env` values under the keys `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` also stay literal, as in Claude Code.

Three variables expand at install time:

- `${CLAUDE_PLUGIN_ROOT}` becomes the directory of the plugin.
- `${CLAUDE_PLUGIN_DATA}` becomes the data directory of the plugin in the install scope.
- `${CLAUDE_PROJECT_DIR}` becomes the project directory, at project scope only. For the user scope, see [The project directory at user scope](#the-project-directory-at-user-scope).

Each stdio server also gets `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` in its `env`, as in Claude Code. If the plugin declares a value under one of these keys, the plugin's value wins.

### Other variables

For every other variable, this extension writes the entry so that pi-mcp-adapter applies the rule of Claude Code when it starts the server:

- `${NAME}` stays `${NAME}`. pi-mcp-adapter expands it from the environment of Pi when it starts the server.
- `${NAME:-default}` stays `${NAME:-default}`. When pi-mcp-adapter starts the server, it uses the value of `NAME` if `NAME` is set, also when the value is empty. If `NAME` is not set, it uses the default. Claude Code uses the same rule when it loads the server (D-CF1-13). So a variable that you set after the install takes effect the next time the server starts. You do not have to install the plugin again.

Some defaults resolve at install time instead (D-CF1-13):

- A default that holds the text `$env:` or `{env:`. pi-mcp-adapter would expand that text again after it puts the default in the value. Claude Code does not.
- A withheld credential. See [Withheld credentials](#withheld-credentials).
- A provider base URL, such as `ANTHROPIC_BASE_URL`, in `url` or `headers`. Its value decides whether Claude Code withholds it, and this extension reads that value only at install time.

For a default with `$env:` or `{env:` text, and for a provider base URL, the install writes `${NAME}` if `NAME` is set at install time, also when its value is empty. If `NAME` is not set, the install writes the default as literal text. For a withheld credential, see the rules in its section.

Thus a value from your environment reaches the server only through pi-mcp-adapter, when it starts the server.

If a referenced variable is not set at install time and has no default, the install shows the warning `MCP server variables not set.`. The warning names the server and the variables. The install still writes the server.

### Syntax that only pi-mcp-adapter knows

pi-mcp-adapter also expands `$env:NAME` and `{env:NAME}`. It runs a value that starts with `!` as a shell command. It replaces a leading `~` in `command` and `args` with your home directory. Claude Code does none of these things. This extension writes each value so that pi-mcp-adapter outputs the literal text of Claude Code:

- Text such as `$env:NAME`, `{env:NAME}`, or a `${...}` form that Claude Code does not expand, such as `${1X}`, gets a split token. The split token is a reference to the empty variable `PI_CLAUDE_MARKETPLACE_EMPTY`. For example, `{env:NAME}` is written as `{env:{env:PI_CLAUDE_MARKETPLACE_EMPTY}NAME}`. pi-mcp-adapter replaces the inner reference with an empty string, so it outputs `{env:NAME}`.
- A kept `${NAME}` or `${NAME:-default}` also gets a split token where the text beside it could join with its value or its default into `$env:NAME` or `{env:NAME}`. The token goes in front of the reference if the text before it ends in `$`, `{`, or the start of `$env` or `{env`, such as `$en`. The token goes after the reference if the text after it starts with an ASCII letter, a digit, `_` or `}`, or with a `:` before an ASCII letter, a digit or `_`. For example, `${PREFIX}env:ANTHROPIC_API_KEY` is written as `${PREFIX}{env:PI_CLAUDE_MARKETPLACE_EMPTY}env:ANTHROPIC_API_KEY`. Without the token, a value of `PREFIX` that ends in `$` would make pi-mcp-adapter send the value of `ANTHROPIC_API_KEY` to the server, although Claude Code withholds it. A reference that comes right after another reference gets the token in front if its default could complete such text, as in `${PREFIX}${NAME:-v:KEY}`. Common values such as `${HOST}:8080` and `${NAME}_suffix` also get the token. Values such as `Bearer ${TOKEN}`, `https://${HOST}/mcp`, and `${USER}:${PASSWORD}` do not.
- A leading `!` in an `env` or `headers` value is written as `!!`. pi-mcp-adapter removes one `!`, and it runs no command.
- A leading `~` in `command` or `args` cannot stay literal. Such a server makes the plugin partially available. See [Partially available plugins](#partially-available-plugins).

This extension reserves the variable `PI_CLAUDE_MARKETPLACE_EMPTY`. It sets the variable to the empty string in the process of Pi when it loads and at each session start. The variable must stay set, because pi-mcp-adapter refuses a server whose `url` references a variable that is not set.

### The project directory at user scope

A user-scope entry keeps `${CLAUDE_PROJECT_DIR}`. This extension sets `CLAUDE_PROJECT_DIR` in the process of Pi to the working directory of the session, when it loads and at each session start. pi-mcp-adapter then expands the reference to the current project when it starts the server. Claude Code also uses the current project, at every scope. The install does not report this variable as not set.

If the directory name holds `$env:` or `{env:`, this extension does not set the variable, because pi-mcp-adapter would expand that text again. The same applies if the directory name ends in `$`, `{`, or the start of `$env` or `{env`, such as `$en`. The plugin text after `${CLAUDE_PROJECT_DIR}` can complete such an ending into `$env:NAME` or `{env:NAME}`, and pi-mcp-adapter would then send the value of `NAME` to the server, even a withheld credential. The install now writes a split token after a kept reference wherever the text after it could do this, so this second check protects entries written before the install did so: legacy `mcp.json` entries that the move on `/reload` has not yet rewritten. In both cases this extension also removes any earlier value of the variable from the process of Pi, so a server does not get the wrong project. pi-mcp-adapter then refuses a `url` that references the variable, and it expands the reference to an empty value in the other fields. A debug-log line records the skip.

### Withheld credentials

Claude Code never gives some credentials to a plugin server. This extension applies the deny-list of Claude Code 2.1.291 (AVAR-05). It compares names without regard to case.

- The plain list applies in all five fields. It holds the tokens and session secrets of Claude Code, the `OTEL_*` variables, and the `INPUT_` forms of some of these names.
- The remote list applies only to `url` and `headers`, the fields that go to a remote server. It adds cloud, CI, package registry, proxy and webhook credentials, for example `ANTHROPIC_API_KEY`. It also covers the name patterns `GIT_CONFIG_*` and `CARGO_REGISTRIES_*_TOKEN`. A provider base URL such as `ANTHROPIC_BASE_URL` is withheld only when its value holds a credential, for example a password in the URL. This extension checks that value at install time.

`GITHUB_TOKEN` and `GH_TOKEN` are on neither list, so a server receives them, as in Claude Code. `ANTHROPIC_API_KEY` is withheld only from `url` and `headers`. A stdio server gets it through `command`, `args` or `env`, as in Claude Code.

The install never leaves a withheld reference for pi-mcp-adapter. So a value that you set later cannot reach the server:

- In `url` and `headers`, a withheld reference is written as an empty value. A `:-` default does not apply.
- In the other fields, a withheld reference is written as an empty value if the variable is set at install time. If it is not set, the install writes the default as literal text, and pi-mcp-adapter never sees the reference (D-CF1-13). With no default, it writes the literal text `${NAME}` and shows the `MCP server variables not set.` warning.

If a withheld variable in `url` or `headers` is set at install time, the install shows the warning `MCP server credentials withheld.`. The warning names the server and the variables. It never shows their values.

### Warnings and info

Each command that writes the entries of a plugin shows the two warnings after its own rows (AVAR-04). These commands are `install`, `update`, `reinstall`, `enable`, `import`, and the install that `/reload` runs for a plugin that a layer declares. For the exact text, see [MCP server variables not set](output-catalog.md#mcp-server-variables-not-set-avar-04) and [MCP server credentials withheld](output-catalog.md#mcp-server-credentials-withheld-avar-05).

`/claude:plugin info` shows the same facts for the current environment. Its `mcp:` line lists, for each server, the variables that are not set and have no default, and the credentials that it withholds. An example is `plugin:analytics:api (unset ANALYTICS_TOKEN; withheld ANTHROPIC_API_KEY)`. The line shows names only.

### Proof against pi-mcp-adapter

The rewrite depends on how pi-mcp-adapter expands values. A conformance test runs each expansion case through the functions of pi-mcp-adapter 7.0.0 and compares the output with the value of Claude Code. CI installs that exact version and runs the test with no skipped cases. The peer range of this extension for pi-mcp-adapter is `>=7.0.0 <8`.

The scenarios in `features/mcp-server/configuration.feature` also run real servers under pi-mcp-adapter 7.0.0. A stdio server receives `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, a `${NAME}` set when Pi starts, and a `${NAME:-default}` with `NAME` not set, each as Claude Code expands it. A remote server receives a header whose variable is not set as an empty value.

## Upgrading

Earlier releases of this extension wrote each plugin server into the `mcp.json` file of the install scope, under the name that the plugin declares. On the first start or `/reload` after the upgrade, this extension moves the servers of each installed plugin from `mcp.json` into the `mcp-adapter.json` file of the same scope. It shows one notice that starts with `Plugin MCP servers moved from mcp.json to mcp-adapter.json.` The notice has one row for each moved server, for example `github -> plugin_acme_github_ (acme) [user]`. For the full notice, see [Plugin MCP servers moved out of mcp.json](output-catalog.md#plugin-mcp-servers-moved-out-of-mcpjson-amig-01-amig-03).

On that first start, pi-mcp-adapter can also warn that `mcp.json` holds an ignored `_piClaudeMarketplace` setting. The adapter read the old entries before the move. The warning does no harm.

Under Pi's built-in MCP, the first session after the upgrade also runs the old entries once, under their old names. See [Legacy mcp.json entries](#legacy-mcpjson-entries).

A moved server keeps its declared name in `/claude:plugin info`, for example `plugin:acme:github`. Its key becomes `plugin_<plugin>_<server>_`, and its tools become `mcp__plugin_<plugin>_<server>__<tool>`. See [Server and tool names](#server-and-tool-names).

### What the new names cost

pi-mcp-adapter and pi-subagents keep some data under the old server names. The move does not carry that data to the new names:

- Sign in again to each server that uses OAuth. pi-mcp-adapter keeps each sign-in under the server name.
- Approve each project-scope server again. pi-mcp-adapter keeps each approval under the server name. See [Project-scope servers](#project-scope-servers).
- Run `/reload` one more time. pi-mcp-adapter reads its configuration when the session starts, before the move. Until the next `/reload`, it still shows the old names, and `/claude:plugin info` shows `not loaded` for each moved server. The live canary needed exactly one more `/reload`.
- Edit the pi-subagents `mcp:` overrides and the agent files that name an old server or tool. Edit them by hand, because the move does not rewrite them. `mcp:<old-name>` becomes `mcp:plugin_<plugin>_<server>_`. A tool that pi-mcp-adapter named `<old-name>_<tool>` with its default prefix becomes `mcp__plugin_<plugin>_<server>__<tool>`.
- Make your own changes again under the new name. The move writes each server as a fresh install writes it, so it does not carry an edit that you made to an old `mcp.json` entry (AMIG-01). For example, run `/mcp-adapter disable` again for a server that you turned off. The move removes the old-name settings that pi-mcp-adapter wrote for such a change. See [Old MCP server settings removed](output-catalog.md#old-mcp-server-settings-removed-amig-01).

### Entries that stay in mcp.json

Some entries cannot move. They stay in `mcp.json` and keep working under their old names. The notice lists them on every `/reload` until you remove the cause (AMIG-01, AMIG-04):

| Cause                                                                                                         | What to do                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No installed plugin in the scope owns the entry.                                                              | Install the plugin, or remove the entry from `mcp.json`.                                                                                                                           |
| The plugin comes from a git source, and its clone is not available offline.                                   | Run `/claude:plugin reinstall <plugin>@<marketplace>`. A reinstall clones the plugin's repository when the cache holds no copy of it, then installs the revision its mirror holds. |
| The plugin comes from a git source, and its cached source has no plugin at the path the marketplace declares. | Run `/claude:plugin update <plugin>@<marketplace>`.                                                                                                                                |
| Another MCP configuration already defines the new key. No server of that plugin moves.                        | Remove or rename that server, then run `/reload`.                                                                                                                                  |
| The `mcp.json` file of the scope is not a valid MCP configuration.                                            | Fix the file, then run `/reload`. No server of that scope moves.                                                                                                                   |
| The `mcp-adapter.json` file of the scope is not a valid MCP configuration.                                    | Fix the file, then run `/reload`. No server of that scope moves.                                                                                                                   |
| The marketplace copy cannot give the plugin source, or it declares a path outside the plugin repository.      | Uninstall the plugin to remove its old entries, or run `/claude:plugin marketplace update <marketplace>` when the copy is out of date.                                             |
| The marketplace no longer lists the plugin, or lists it in a form that is not valid.                          | Run `/claude:plugin marketplace update <marketplace>`, or uninstall the plugin to remove its old entries.                                                                          |

| Another Pi process holds the lock on `state.json`.                                                            | Run `/reload` again later.                                                                                                                                                         |
| The move wrote the new entries, but it could not update `mcp.json`.                                           | Run `/reload` again. The next reload finishes the move.                                                                                                                            |

For the exact rows, see [Plugin MCP servers left in mcp.json](output-catalog.md#plugin-mcp-servers-left-in-mcpjson-amig-01-amig-04) and [Plugin MCP server move stopped](output-catalog.md#plugin-mcp-server-move-stopped-amig-03).

### Entries that the move removes

The move removes an old entry and writes no new one in these cases:

- The plugin no longer declares the server.
- The server needs a feature that pi-mcp-adapter cannot run. The other servers of the plugin move, and the plugin becomes `(partially-installed)`. See [Partially available plugins](#partially-available-plugins).
- An inline MCP configuration of the plugin is not valid, or an `mcpServers` path is absolute or leaves the plugin root. The move removes every server of that plugin, as a fresh install installs none of them. A malformed server in a file source does not stop the move: the move treats that server as one that the plugin no longer declares, and it moves the other servers. See [Invalid server configs](#invalid-server-configs).
- The plugin is disabled.

The notice lists each removed entry with its reason. See [Plugin MCP servers removed from mcp.json](output-catalog.md#plugin-mcp-servers-removed-from-mcpjson-amig-01-amig-03).

## Server status in info

On an installed plugin, `/claude:plugin info` shows the state of each server that this extension wrote. Under pi-mcp-adapter, the state is the one that pi-mcp-adapter last reported on its status channel, the `pi-mcp-adapter/status/v1` event. Under Pi's built-in MCP, info reads the state from the servers and tools that Pi lists when info runs, because Pi gives an extension no connection state (D-MB-20, `features/mcp-server/builtin-status.feature`). Info does not connect a server to get it (ASTAT-01). The state comes first inside the parentheses after the server name, for example `plugin:deploy-tools:deploys (pending approval)`.

| Shown text                      | Meaning under pi-mcp-adapter                                                                                                                                                                                                                                                                                  | Meaning under Pi's built-in MCP                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `connected`                     | The server is connected.                                                                                                                                                                                                                                                                                      | A tool of the server is offered. Pi registers the tools of a server when it connects (`features/mcp-server/builtin-status.feature`).                                                                                                                                                                                                                                                                        |
| `cached, connects on first use` | pi-mcp-adapter holds a cached list of the tools of the server. It starts the server when the model first uses one of them. This is the normal state of a lazy server, not a failure.                                                                                                                          | --                                                                                                                                                                                                                                                                                                                                                                                                          |
| `needs authentication`          | The server needs a sign-in.                                                                                                                                                                                                                                                                                   | --                                                                                                                                                                                                                                                                                                                                                                                                          |
| `pending approval`              | pi-mcp-adapter blocks this project server. The project is not trusted, the server needs approval, or you denied the approval. The panel of pi-mcp-adapter shows which. See [Project-scope servers](#project-scope-servers).                                                                                   | --                                                                                                                                                                                                                                                                                                                                                                                                          |

The project-scope server can come from the same plugin of another marketplace. In some sessions, pi-mcp-adapter sends no report until the first MCP use. This happens when every server is lazy, no server comes from a project file, and the adapter holds a valid cached list of tools for each server. The adapter then sends only its empty report at the session start. So `status unknown` is the normal reading in such a session until the first tool call, `/mcp` or `/mcp-adapter` (ASTAT-02).

pi-mcp-adapter 7.0.0 still sends its states on `pi-mcp-adapter/status/v1`, with the same state values (checked in the 7.0.0 source). The cucumber scenarios measured `cached, connects on first use` after the startup listing (`features/mcp-server/companion-missing.feature`) and `pending approval` for a blocked project server (`features/mcp-server/project-scope.feature`). Right after pi-mcp-adapter lists the tools of a server for the first time, `info` can show `status unknown` for a moment, until the adapter sends its report.

## Divergences and documented absences

The behaviors below differ from Claude Code. Each item names its reason: a recorded project decision or a Pi capability gap.

### Naming

- Keys that differ only by `-` versus `_` are refused. Reason: a Pi capability gap. Pi and pi-mcp-adapter group the tools of both servers under one name.
- pi-mcp-adapter shows the server key with a `_` at the end, for example `plugin_foo_api_`, and Claude Code shows `plugin:foo:api`. Reason: a Pi capability gap. The `_` makes pi-mcp-adapter build the tool names that Claude Code uses.
- Some tool names differ. Claude Code replaces every character outside `A-Z`, `a-z`, `0-9`, `_` and `-` in a tool name, and pi-mcp-adapter replaces only `.`. A tool name with another such character, such as a space, reaches the model with that character, and a provider can refuse it. Reason: a Pi capability gap. This extension does not control the tool names that a server reports.
- When `MCP_DIRECT_TOOLS` does not name a plugin server, `tool_search` and `codemode` reach its tools as `mcp__plugin_<plugin>_<server>___<tool>`, not by their Claude Code names. Reason: a Pi capability gap. pi-mcp-adapter builds these deferred names from the server key, and the key ends in `_`. The variable is your own pi-mcp-adapter setting. See [pi-mcp-adapter settings that change plugin servers](#pi-mcp-adapter-settings-that-change-plugin-servers).

### Loading

- Under pi-mcp-adapter, servers start lazily. pi-mcp-adapter stops a server when it is not in use, and Claude Code keeps it connected for the session. Reason: a project decision (ANAME-05). This extension leaves `lifecycle` to you, so you can change it for each server. Pi's built-in MCP keeps each server connected, as Claude Code does.
- Under pi-mcp-adapter, Pi's `tool_search` is off by default. The model finds plugin tools through the `mcp` tool of pi-mcp-adapter. Reason: a Pi capability gap. Pi turns `tool_search` on only from your settings, and this extension does not write outside its own files. Pi's built-in MCP turns `tool_search` on itself.
- The timeouts differ. The timeout of pi-mcp-adapter starts again on progress, and its default is 60 seconds instead of about 28 hours. Reason: a Pi capability gap. This extension writes only the values that the plugin declares (ANAME-07), so it writes no default.
- Under pi-mcp-adapter, project-scope plugin servers wait for the approval of pi-mcp-adapter. Claude Code never asks for approval of a plugin server. Reason: a Pi capability gap and a project decision (D-CF6-03, NFR-10). pi-mcp-adapter owns project trust and offers no way for another extension to approve a server, and this extension never writes its approval files. See [Project-scope servers](#project-scope-servers).
- An `mcpServers` path without `./`, such as `servers.json`, still loads. Claude Code refuses a `plugin.json` with such a path. Reason: a project decision (D-CF6-01). Plugins that install today keep installing. See [Server sources](#server-sources).
- An `mcpServers` path that passes through a symbolic link whose real target is outside the plugin root makes the plugin `(unavailable)` with `{malformed mcp}`. Claude Code 2.1.316 reads the file through the link, wherever the link points. Reason: a project decision (MCPR-04, which applies the D-14 refusal of symbolic links to these paths, amended on 2026-11-02 so that a link whose real target is inside the plugin root is read, and NFR-10). The `.mcp.json` at the plugin root is not held to this rule. It is read through a link, as Claude Code reads it. See [Server sources](#server-sources).
- An agent that runs plugin MCP tools launches in the background (`async: true`), even with `background: false`, because it cannot call them in a foreground launch. pi-subagents 0.84.0 refuses a foreground launch with `Unresolved MCP direct-tool selectors: ...`, and a foreground child without `tools:` gets no MCP tool. Claude Code runs such a subagent in the foreground with the tool. Reason: a Pi capability gap in the pi-subagents companion (D-CF6-10, MCP-07). pi-subagents gives MCP tools only to background children, and in pi-subagents 0.84.0 two bugs can keep a background child from getting them too (`directTools: "search"` rejected; `${VAR:-default}` cache keys). See [Customizing generated agents](#customizing-generated-agents).
- A tool that its server reports with `_meta["anthropic/alwaysLoad"]: true` still loads on demand. Claude Code keeps such a tool in the prompt. Reason: a Pi capability gap. pi-mcp-adapter ignores the `_meta` of a tool, and this extension writes the entry before the tool list is known.
- A server with tool permission rules installs and runs without them, with the warning `MCP server tool rules not enforced.` The schema of Claude Code accepts these rules for a remote server. Reason: a project decision (ANAME-07). pi-mcp-adapter has no rule for each tool, so the warning tells you that the rules do not apply. See [Tool permission rules](#tool-permission-rules).
- Some pi-mcp-adapter settings change or drop plugin servers, and this extension gives no warning about them. Reason: a project decision (ADOC-01). These settings are your own pi-mcp-adapter configuration. See [pi-mcp-adapter settings that change plugin servers](#pi-mcp-adapter-settings-that-change-plugin-servers).

### User choices

- Claude Code keeps the `/mcp` choice for a plugin server per project, in `~/.claude.json`, keyed by `plugin:<plugin>:<server>`. This extension keeps your choices for a server per scope file, in the `mcp-adapter.json` of the install scope, keyed by the server key and the plugin name. So a value that you write into a user-scope entry applies in every project. Reason: a Pi capability gap (D-08-02). pi-mcp-adapter has no per-project store for the fields of a user-scope entry. The one exception is the `disabled` choice, which `/mcp-adapter disable` writes into the project file. See [User overrides](#user-overrides).

### Variables

- Bash and every MCP server inherit `CLAUDE_PROJECT_DIR` from the process of Pi. Claude Code does not set it for Bash. Reason: a project decision (AVAR-01). This is how a user-scope server gets the current project.
- The `MCP server credentials withheld.` warning shows to the user. Claude Code writes the same fact only to its debug log. Reason: a project decision (AVAR-04). A user learns each time that a credential was withheld from a remote server.
- The deny-lists of Claude Code that depend on its mode are not used. These are the lists for a provider that a host manages, for a bridge child process, for the HIPAA tier, and for the scrub of subprocess variables. Reason: a project decision (AVAR-05). These lists depend on the state of a Claude Code process, and Pi does not run in these modes.
- A provider base URL that holds no credential at install time is written as `${NAME}`. If its value holds a credential later, pi-mcp-adapter sends that credential to the server. Claude Code checks the value each time it loads the server. Reason: a project decision (AVAR-05). This extension writes no environment value, so it checks the value only at install time.
- A kept `${NAME}` that is not set when pi-mcp-adapter starts the server becomes an empty value. pi-mcp-adapter refuses a `url` that holds such a reference. Claude Code keeps the literal `${NAME}` and shows a warning. Reason: a Pi capability gap. pi-mcp-adapter replaces every variable that is not set with an empty string.
- If the value of a variable at run time holds `$env:NAME` or `{env:NAME}`, pi-mcp-adapter expands that text again. The same applies if the values of two references join into such text, such as `${A}:${B}` when the value of `A` ends in `$env`. Reason: a Pi capability gap. pi-mcp-adapter has no literal mode that a configuration file can turn on. The values come from your own environment.
- In `command` and `args`, a leading reference that becomes empty before a literal `~` makes the value a path in your home directory, and Claude Code keeps the `~`. Three forms do this: an empty default with the variable not set at install, such as `${X:-}~/a`; a variable that is not set when pi-mcp-adapter starts the server, such as `${MISSING}~/a`; and a withheld credential that is set at install, such as `${OTEL_X}~/a`, which the install writes as an empty value. A value at run time that starts with `~/` does the same. Reason: a Pi capability gap. pi-mcp-adapter replaces a leading `~` after it expands variables. The install check for a leading `~` reads only the text of the plugin, so it cannot know which reference becomes empty.
- pi-mcp-adapter can load before this extension. If a user override then makes a user-scope server `eager` or `keep-alive`, a `url` with a split token can fail one time, before this extension sets `PI_CLAUDE_MARKETPLACE_EMPTY`. This includes a common `url` such as `https://${HOST}:8080/mcp`, which gets a split token after the reference. The session start of pi-mcp-adapter connects the server again in the same session. Reason: a Pi capability gap. An extension cannot set the order in which Pi loads extensions.
- A default that resolves at install time does not follow a variable that you set later. These are a default that holds `$env:` or `{env:` text, the default of a withheld credential, and the default of a provider base URL in `url` or `headers`. For example, `${NAME:-$env:HOME}` is written as the literal text `$env:HOME` while `NAME` is not set, and as `${NAME}` after you set `NAME` and install again. pi-mcp-adapter then sees a new server definition, so it can ask you again to approve a project server. Claude Code reads the variable each time it loads the server. Reason: a Pi capability gap (D-CF1-13). pi-mcp-adapter expands `$env:` and `{env:` again in a default that it puts in a value, and this extension reads the value of a provider base URL only at install time.
- This extension does not set `literalEnv` on an entry. `literalEnv: true` turns off the expansion of `${NAME}` in `env` when pi-mcp-adapter starts the server, and the rule of Claude Code needs that expansion. Reason: a project decision (AVAR-03).
- A remote server whose headers hold no `Authorization` key keeps OAuth in Claude Code, whatever its header values are. In OAuth mode, pi-mcp-adapter refuses a header that references a variable that is not set, a header that is empty, such as a withheld credential, and a header that holds the split token. So this extension writes no `auth: "oauth"` for such a server, and the server keeps connecting without OAuth. Claude Code keeps the text of the header, shows a warning, and keeps OAuth. Also, if a header of a server with `auth: "oauth"` references a variable that is set at install but not when pi-mcp-adapter starts the server, the adapter refuses the header, and the server does not connect. Reason: a Pi capability gap (D-08-04). pi-mcp-adapter has no OAuth mode that accepts such headers. See [OAuth beside headers](#oauth-beside-headers).

### Migration

- The renamed servers appear only after one more `/reload`. In Claude Code, a plugin server keeps one name, so nothing moves. Reason: a Pi capability gap. pi-mcp-adapter reads its configuration when the session starts, before this extension moves the entries. See [Upgrading](#upgrading).
- The move removes every server of a plugin whose inline MCP configuration is not valid, or whose `mcpServers` path is absolute or leaves the plugin root. Claude Code refuses to install such a plugin, so it runs none of its servers, but it has no old entries to remove. Reason: a project decision (AMIG-01, D-CF6-02). A fresh install of that plugin installs no MCP server either.
- The move carries nothing from an old `mcp.json` entry, so an edit that you made to that entry does not survive. Reason: a project decision (AMIG-01). The old entries are cleanup, not input: the move writes each server as a fresh install writes it.

### Status

- `/claude:plugin info` shows `failed` for a server in the failure backoff of pi-mcp-adapter. The status text of Claude Code says `not connected` for a failed server. Reason: a project decision (ASTAT-01). pi-mcp-adapter keeps a failure apart from a server that it never discovered, and `failed` is the word of the `/mcp` panel of Claude Code. See [Server status in info](#server-status-in-info).

### Pi's built-in MCP

- Under Pi's built-in MCP, a `-` in a server name or a tool name becomes `_` in the tool name, for example `mcp__plugin_demo_my_db__echo` for the server `my-db`. Claude Code keeps the `-`. Reason: a Pi capability gap. Pi builds every MCP tool name from `A-Z`, `a-z`, `0-9` and `_` only (`dist/extensions/mcp/tools.js`, `features/mcp-server/listing.feature`).
- Under Pi's built-in MCP, a tool name longer than 64 characters is cut to 55 characters, with `_` and a hash added. Claude Code does not shorten tool names. Reason: a Pi capability gap. Pi keeps every tool name within the 64 characters that some providers accept (`dist/extensions/mcp/tools.js`, `features/mcp-server/listing.feature`). See [Name length](#name-length).
- Under Pi's built-in MCP, the first session after an upgrade from a release before AMIG-01 runs each old `mcp.json` entry once more, under its old name, with Pi's `$` and `!` rules. Reason: a Pi capability gap (D-MB-21). Pi's built-in MCP reads `mcp.json` at its own session start, which no extension can precede (`dist/extensions/mcp/index.js`). See [Legacy mcp.json entries](#legacy-mcpjson-entries).
- Under Pi's built-in MCP, a stdio server starts in the working directory of the session, and Claude Code starts it in the project root that it resolves. Reason: a Pi capability gap and a project decision (D-MB-16, D-MB-26). A plugin cannot set `cwd` in Claude Code, so this extension writes none (`dist/extensions/mcp/runtime.js`, `features/mcp-server/builtin-values.feature`).
- Under Pi's built-in MCP, the timeout of a call starts again on progress, and it is 60 seconds when the plugin sets none. In Claude Code it is a hard limit, about 28 hours by default. Reason: a Pi capability gap (D-MB-17). Pi has no hard limit for a call (`dist/extensions/mcp/runtime.js`, `dist/extensions/mcp/tools.js`).
- Under Pi's built-in MCP, a server in your `mcp.json` wins over a plugin server with the same name after every `-` becomes `_`. Claude Code skips a plugin server that has the command or URL of a server you configured. Reason: a Pi capability gap, because Pi gives `mcp.json` the precedence by name (`dist/extensions/mcp/index.js`), and a project decision for the report: info shows `overridden by mcp.json`, and no notice shows at load (D-MB-19, `features/mcp-server/builtin-status.feature`).
- Under Pi's built-in MCP, a server that another extension registered first under the name `plugin_<plugin>_<server>` keeps that name. Pi refuses the registration of this extension, and info shows `not loaded` for the plugin server. Reason: a Pi capability gap (D-MB-29). Pi gives each name one owner (`dist/core/extensions/loader.js`), and Pi 1.5.0 gives an extension no reliable way to learn the path that it records for its own registrations.
- Under Pi's built-in MCP, a stdio server whose `command` or `args` element resolves to `~` or to a value that starts with `~/` does not run, and info shows `not loaded`. Claude Code runs it with the `~` as written. Reason: a Pi capability gap. Pi changes such a value into a path in your home directory when it starts the server, and has no way to keep it (`dist/extensions/mcp/runtime.js`, `features/mcp-server/builtin-status.feature`). See [Other gaps](#other-gaps).
- Under Pi's built-in MCP, the plugin tools cannot be reached when you turn `tool_search` off. Reason: a Pi capability gap. Pi offers a deferred tool only through `tool_search` (`dist/extensions/mcp/index.js`).
- Under Pi's built-in MCP, info shows `not connected` for a server that is connecting, failed, waits for a sign-in, or offers no tool. Reason: a Pi capability gap (D-MB-20). Pi gives an extension no connection state (`features/mcp-server/builtin-status.feature`).
- Under Pi's built-in MCP, the resolved values of each server, secrets included, are in the Pi session, where every extension of the same Pi process can read them. Reason: a project decision (D-MB-14, which amends D-MB-04). Pi expands variables with rules that are not the rules of Claude Code, so this extension resolves them itself (`dist/core/extensions/loader.js`, `dist/core/resolve-config-value.js`). See [Variables under Pi's built-in MCP](#variables-under-pis-built-in-mcp).
- Under Pi's built-in MCP, a remote server with an `oauth.clientId` and no `oauth.callbackPort` signs in with the redirect address `http://127.0.0.1:<port>/callback`. Claude Code uses `localhost`. Reason: a project decision (D-MB-25). This extension writes `callbackUrl` only for a port that the plugin names (`dist/extensions/mcp/oauth.js`).
- Under pi-mcp-adapter and Pi's built-in MCP, the withheld credentials follow the deny-lists of Claude Code 2.1.291, not 2.1.318. Reason: a project decision (D-MB-27). The lists are pinned until a later release checks them again (`test/integration/mcp-builtin-encoding-conformance.test.ts`).
