# Hook compatibility

Feature-by-feature comparison of Claude Code's hooks system against the Pi-Claude bridge, with the design rationale for which features were implemented, which were deferred, and which the bridge declares unsupportable.

Legend: `✓` supported, `✗` not supported, `⚠` partial (see notes).

The upstream column reflects Claude Code 2.1.316 and its published hooks reference at [code.claude.com/docs/en/hooks](https://code.claude.com/docs/en/hooks). The Pi column reflects the bridge sources under `extensions/pi-claude-marketplace/bridges/hooks/` and `extensions/pi-claude-marketplace/domain/components/`, and the behavior that the cucumber scenarios under `features/hook/` prove (D-CF5-21). A note names its decision ID, such as `D-CF5-01`. A note that describes a difference from Claude Code also names its reason: a Pi gap (Pi has no matching capability) or a project decision.

An Edit runs one hook invocation per pair before one native execution. Equal or adjacent pairs stay separate, so command-hook side effects may repeat. The bridge completes all preflight checks first; later denial, stop or rejected ask blocks the whole batch. All accepted targets, including unchanged pairs, must agree; conflicting targets block even alongside an unsupported candidate. Otherwise one unsupported candidate discards every proposal and runs the original batch. Successful or failed result hooks also run per pair with the same actual batch result or error; an earlier output rewrite does not change later hook stdin. Folding follows pair index and routing order, independent of completion order (D-PG2-01..04/09; [dispatcher owner](../test/bridges/hooks/dispatch.test.ts), [pair scenarios](../features/hook/tool-use.feature), [failure scenarios](../features/hook/tool-failure.feature), [background scenario](../features/hook/async.feature)).

A valid successful `updatedToolOutput` renders text/images back to Pi, including intentional empties, and clears stale `details` and `structuredContent`. The model and a downstream Pi handler see the replacement. Invalid or echoed values preserve the original. A failed result stays failed and ignores output replacement. MCP selects the modern `updatedToolOutput` when *present*, even when empty; only its absence permits the legacy `updatedMCPToolOutput`, and only for a recognized MCP tool. The inspected upstream legacy path is ambiguous. Pi adapter and built-in MCP may expose different rendered envelopes, including structured content rendered as text (D-PG2-05/06; [output adapter](../extensions/pi-claude-marketplace/bridges/hooks/event-adapters.ts), [file output tests](../test/bridges/hooks/tool-output-files.test.ts), [search/shell output tests](../test/bridges/hooks/tool-output-search-shell.test.ts), [Pi boundary test](../test/integration/hooks-result-boundary.test.ts), [MCP scenarios](../features/hook/tool-use.feature)).

Each tool event's stdin also holds the call's `tool_use_id`. The result events hold `duration_ms`, a call to a plugin's MCP server holds `mcp_server`, and every tool event holds `effort` when Pi's thinking level is one of Claude's levels. See the rows of these fields under [stdin, stdout, exit codes](#stdin-stdout-exit-codes) (D-PG6-04).

The projection omits facts Pi does not provide: Read original content, Edit `userModified`, Write create/update type and original content, distinct shell streams, search totals, and counts hidden by ambiguous displays. The bridge measures the execution time itself; see the `duration_ms` row. It never follows an output path to invent these facts. [HOOKRESULT-01](../.planning/BACKLOG.md#hookresult-01-investigate-and-implement-execution-wrappers-for-full-claude-shaped-hook-results) tracks complete execution capture or an upstream seam (D-PG2-07; [file projection tests](../test/bridges/hooks/tool-result-files.test.ts), [search/shell projection tests](../test/bridges/hooks/tool-result-search-shell.test.ts)).

Tool exact lists split on comma or pipe and trim surrounding ASCII spaces; an internal space is not a separator. Empty members and duplicates do not add invocations. Other whole strings compile as unanchored, case-sensitive JavaScript regex against Claude-form names. Invalid regex drops only its group. `UserPromptSubmit` and `Stop` ignore even invalid matcher text. Stop permits eight consecutive blocking continuations; the ninth is overridden once with a cap notice. Any native model tool call resets the budget, even without a matching hook, and `/reload` starts a fresh budget. Stop runs on `agent_before_settle`, and the bridge does not read the cap environment variable (D-PG2-10/11, D-PG5-01, D-PG5-04; [matcher owner](../test/domain/components/hooks/matcher.test.ts), [matcher scenarios](../features/hook/matchers.feature), [Stop runtime owner](../test/bridges/hooks/runtime.test.ts), [Stop scenarios](../features/hook/prompt-and-stop.feature)).

## Hooks in pi-subagents children

A pi-subagents child is a Pi session that pi-subagents starts with its child marker, `PI_SUBAGENT_CHILD=1`, in the environment. The child loads this extension and the hooks of the installed plugins. In a child, only the three tool events run hooks. The other events belong to the main session, so a child does not run them (D-PG3-04). Claude Code also runs plugin tool hooks for the tool calls of a subagent, and runs `Stop` only for the main agent.

| Event                 | Main session | pi-subagents child                                        |
| --------------------- | ------------ | --------------------------------------------------------- |
| `SessionStart`        | runs         | does not run; it stands for `SubagentStart` (unsupported) |
| `UserPromptSubmit`    | runs         | does not run                                              |
| `PreToolUse`          | runs         | runs, with the child identity                             |
| `PostToolUse`         | runs         | runs, with the child identity                             |
| `PostToolUseFailure`  | runs         | runs, with the child identity                             |
| `PreCompact`          | runs         | does not run                                              |
| `PostCompact`         | runs         | does not run                                              |
| `SessionEnd`          | runs         | does not run                                              |
| `Stop`                | runs         | does not run; it stands for `SubagentStop` (unsupported)  |
| `StopFailure`         | runs         | does not run                                              |
| `UserPromptExpansion` | runs         | does not run                                              |

The bridge supports no `SubagentStart` or `SubagentStop` hook yet (PG-HOOK-07b). A compaction in a child runs no hook: not `PreCompact`, not the `SessionStart` with source `compact`, and not `PostCompact`. A `Stop` hook that would continue the main session's run does not keep a child running ([event policy tests](../test/bridges/hooks/event-router.test.ts), [child scenarios](../features/plugin/subagent-child.feature): "A child runs tool hooks without main-session hooks", "A child ignores a Stop hook that would continue the main session", "Child compaction runs no main-session hooks").

A child still does the setup that its tool hooks need. It reads the hooks of every installed plugin. It reads the hooks of a project-scope plugin only when Pi trusts the project. It ignores the outcome of a hook that an earlier load started, and it gives the model the `additionalContext` of its tool hooks. An event that does not run in a child never skips this setup (D-PG3-05).

### Child identity

In a child, the stdin of `PreToolUse`, `PostToolUse`, and `PostToolUseFailure` holds `agent_type` and `agent_id`, as Claude Code sends them for a subagent (D-PG3-06). The bridge reads both at the start of each agent run:

- `agent_type` is the agent name that pi-subagents writes at the start of the child's system prompt, as `<active_agent name="<agent>"/>` and a blank line. pi-subagents puts this tag in front of the custom or the appended prompt section. The bridge reads the tag from Pi's structured prompt options, never from the task text. It decodes `&amp;`, `&quot;`, `&lt;`, and `&gt;` once, so `a&amp;amp;b` becomes `a&amp;b`.
- `agent_id` is the id of the child's current Pi session.

Each load of the bridge keeps its own identity, and the identity applies only to the session that read it. So a new session, a reload, or another child session in the same pi-subagents runner process never reuses it. The stdin of a main-session tool hook holds neither property, not even as an empty value.

In a child whose identity the bridge read, a tool hook's `session_id`, `transcript_path`, `CLAUDE_CODE_SESSION_ID`, and `CLAUDE_SESSION_ID` name the session that launched the child, as Claude Code names the main session in a subagent's hooks. `agent_id` stays the id of the child's own session (D-PG6-01). The bridge reads the launching session once, at the first run of the child session, from two sources that pi-subagents gives a background child (D-PG6-02):

- The `PI_SUBAGENT_PARENT_SESSION` variable gives the id. A value that holds `/` or `\` is a path, so it gives no id.
- The `parentSession` field of the child session's header gives the file. The bridge reads the first line of that file, at most 65,536 bytes, and takes the id from the file's header.

When the file's header and the variable give two different ids, the bridge uses neither. When only the variable gives an id, `transcript_path` is the file that the header names, or `""` when it names none. When neither source names a session, or the bridge could not read the child's identity, the child's tool hooks keep its own session in all four fields. So an input that names the launching session always holds `agent_id`. With the debug log on, a child that has no source writes `Child hook root session unavailable: neither the companion's launch variable nor the child's session header names its launching session`.

The bridge reads one hop, and it sets no variable for the children of a child. So a child of a child names the child that launched it, where Claude Code names the main session. Reason: project decision; the bridge keeps no child state in the process environment (D-PG3-06). The keys that the bridge keeps for itself stay on the child's own session: the name of the `CLAUDE_ENV_FILE`, the journal of the child's background hooks, and the identity check (D-PG6-03). A Bash command in a child still sees the child's own id in `CLAUDE_CODE_SESSION_ID`, so a hook and a Bash command in one child see two different ids. This difference is open for a maintainer decision.

If the tag is missing or malformed, or the two prompt sections name different agents, the child's tool hooks run without `agent_type` and `agent_id`. With the debug log on (`PI_CLAUDE_MARKETPLACE_DEBUG=1`), the bridge writes `Child hook identity unavailable: companion launch metadata is missing or malformed`. It never makes up an agent name. A supported pi-subagents launch always writes the tag, so this path only guards against another extension that changes the system prompt.

Evidence: the [identity tests](../test/bridges/hooks/runtime.test.ts), the [payload tests](../test/bridges/hooks/payloads/post-tool-use.test.ts), and the [child scenarios](../features/plugin/subagent-child.feature): "A child tool hook identifies its own agent and session", "A main tool hook has no child identity", "A child keeps its own identity after another session runs", and "Missing child metadata clears the previous identity". Real children of the installed pi-subagents 0.88.1 run in "A real background child runs its plugin tool hooks and completes" and "Concurrent companion children keep separate hook identities", and in the [real-child tests](../test/integration/pi-subagents-child-identity.test.ts). The first scenario shows a background child's tool hook that names the main session in `session_id`, `transcript_path`, and `CLAUDE_CODE_SESSION_ID`. The second shows children whose runner gives neither source, so they keep their own session. The [launching-session tests](../test/bridges/hooks/child-root-session.test.ts) and the [dispatch context tests](../test/bridges/hooks/translation-context.test.ts) cover each source, a nested child, and a child with no identity. Those tests launch an explicit background agent, an agent granted a plugin MCP tool, an ordinary agent with an empty body under pi-subagents' default launch mode, and two child sessions at once in one runner process. The tag format was also read in the pi-subagents 0.87.0 source, the declared floor; no test runs 0.87.0.

A foreground child runs inside the main Pi's turn and loads no ambient extension, this one included. So no plugin hook runs for its tool calls, where Claude Code runs them. Reason: a Pi capability gap in pi-subagents. The real-child tests show this for an ordinary agent under a foreground default.

### Background hook processes of a child

A child records its `async` and `asyncRewake` hook processes in a journal of its own, under `_shared/async-rewake-children/` in the data root of the scope. The journal name comes from the child's process id, its session id, and a random token. A child never writes or reaps the main session's process table, and it reaps no journal. When a child stops or reloads, it stops its own hook processes.

A later load of a main session reaps a child's journal only when the child's process is gone. It removes the row of a hook process that has already exited, on every system, and sends no signal. It stops a recorded hook process that still runs only when that process has the hook's own dispatch marker in its environment, which it reads on Linux only. Every other case keeps the row: the child's process still runs or cannot be probed, the recorded process id now belongs to another process, or the system is not Linux. A load reads at most 1024 journals ([registry tests](../test/bridges/hooks/async-rewake/registry.test.ts), [ownership tests](../test/integration/subagent-hook-ownership.test.ts), scenario "Loading and stopping a child leaves parent and sibling hooks running").

Pi reports reason `startup` for every launch, so the bridge reads the session at `session_start` to tell the launches apart (D-PG6-17). Otherwise a session that already holds a message is a saved session, and it sends `resume`. A new session holds no message, and it sends `startup`. The bridge reads no file and does not parse Pi's command line. If the read fails, `source` stays `startup` and the hooks still run. These facts were measured on Pi 1.5.0 and Pi 1.5.2. The scenarios "A continued session starts with source resume", "A session opened from its file starts with source resume", "A forked session starts with source fork", "A continued fork starts with source resume", and "Continuing with no saved session starts with source startup" in [`features/hook/session.feature`](../features/hook/session.feature) prove each row. ### Compaction

Each compaction runs three events in order, as upstream does (D-CF5-04, D-CF5-05):

1. `PreCompact`, with `trigger` and `custom_instructions`.
2. `SessionStart`, with `source` `compact`. It runs to the end before the next event starts.
3. `PostCompact`, with `trigger` and `compact_summary`. `compact_summary` is the summary that Pi wrote for the compaction.

Pi reports a compaction as `manual`, `threshold`, or `overflow`. The bridge sends `manual` as `manual`, and `threshold` and `overflow` as `auto`. A `PreCompact` or `PostCompact` matcher of `manual` or `auto` compares with that value. A second compaction in the same session runs the three events again.

A `PreCompact` block cancels the compaction, as upstream does, so `SessionStart` and `PostCompact` do not run. A block is an exit 2, a `decision` of `block`, or a failure under `onFailure: "block"`. A block from any `PreCompact` hook cancels the compaction, whatever the other hooks return: a `continue: false` from another hook does not hide it. The bridge shows `Compaction blocked by PreCompact hook: <message>`, with one `[<command>]: <stderr>` message for each blocking hook, one per line. Upstream shows that notice as a warning. The bridge shows it at `info` severity, as every hook notice (D-CF5-18, D-CF5-24). Pi then answers the compaction with `Compaction cancelled`.

After `/compact`, the bridge shows one `hook-notice` at `info` that lists how each `PostCompact` hook ended, one line per hook in routing order, as upstream does (D-BG-501). A hook that exits 0 shows as `PostCompact [<command>] completed successfully: <text>`, and any other end shows as `PostCompact [<command>] failed: <text>`. When the text is empty, the line ends before the colon. The text is the trimmed stdout after an exit 0 and the trimmed stderr otherwise. A JSON `decision` of `block` gives its `reason` instead. Stdout shows as it is, so a JSON `systemMessage` shows in the line and not as a `says:` notice. A hook that its timeout stops shows `Hook cancelled`. A hook that cannot start shows its start error, with each absolute path cut to its last segment. Under `onFailure: "block"`, a failure shows `failed; blocking because onFailure is "block"` (`timed out; ...` after a timeout), then the stderr on a new line, except after a timeout (D-BG-503). `<command>` is the declared `command` with its placeholders, followed by an exec-form hook's `args` joined by spaces; the block messages of other events leave the `args` out (D-BG-504).

After an automatic compaction (`threshold` or `overflow`), the `PostCompact` hooks still run with their payload, and nothing shows, as upstream (D-BG-502). A `PostCompact` hook cannot change the compaction. Its `systemMessage` and `continue` are dropped, and no output reaches the model.

### Stop continuation

`Stop` runs on Pi's `agent_before_settle` event, which Pi raises when a run is about to end. A block or an added context continues the same run, as upstream (D-PG5-01). The bridge appends one hidden message to the run. The message has one `Stop hook feedback:\n<text>` part for each block reason and for each `additionalContext` value, in routing order. A hook that blocks and adds context gives its reason first (D-CF5-25). The bridge then asks Pi for one more model call in the same run.

A run raises one `agent_settled` event however many times a `Stop` hook blocked. No second `before_agent_start` happens. Pi still raises `agent_start` and `agent_end` for each continuation. The terminal, print, JSON, and RPC modes behave the same on Pi 1.5.0 and 1.5.2, so no mode keeps the earlier path that started a new run for each block (D-PG5-02). `StopFailure` stays on `agent_settled` (D-PG5-03). The scenario "A run that a stop hook blocks twice settles once after one run start" in [`features/hook/prompt-and-stop.feature`](../features/hook/prompt-and-stop.feature) proves the one settlement and the one run start. The scenario "Eight consecutive Stop blocks continue before the ninth is overridden" proves the limit on the same path.

These behaviors stay different from Claude Code (D-PG5-07):

- An `async` hook's answer reaches the model at the next run start, so a continuation does not read it. It arrives with your next prompt.
- While a `Stop` hook runs, the session is busy. Pi queues the input that you type, and the continuation reads it. Escape lets the hook finish, keeps its hidden feedback for your next prompt, and drops the continuation. Pi sets no time limit of its own there, so the hook's `timeout` is the bound.
- Another extension's handler on the same Pi event can replace the bridge's entries or refuse the continuation. Then the run ends though a `Stop` hook blocked (D-PG5-05). When Pi continues a run that a `Stop` hook stopped, for another extension or for input that you typed, the bridge shows no `Stop hook stopped continuation` line, because the run did not stop (D-PG5-13).
- Pi reads a queued follow-up before the event, so `Stop` does not run between a reply and a queued prompt.
- In one measurement on Pi 1.5.0, the terminal showed no working indicator while a `Stop` hook ran.

Two more statements come from a read of Pi's source and were not measured:

- A follow-up that you type while a `Stop` hook runs can lose its `UserPromptSubmit` context when the hooks do not continue the run.
- A `SessionStart` context that a compaction adds just before a block reaches the model at your next prompt.

`Stop` and `StopFailure` are marked `✓` (full support). [`docs/research/issue-103-stop-stopfailure-promotion.md`](research/issue-103-stop-stopfailure-promotion.md) holds the earlier design analysis, and D-PG5-01 amends its fire point.

### UserPromptExpansion

`UserPromptExpansion` hooks run when you type a line that names a prompt template or a skill, before the line expands (D-PG6-18). These lines run them:

- a prompt template, such as `/demo:deploy staging` for a plugin's command or `/notes` for a template of your own
- `/skill:<name>`
- a skill alias of a plugin, such as `/demo:status`

As upstream, the hooks also run for your own templates and skills. They do not run for input that an extension sends, such as a skill that the model starts through a tool. They do not run for a built-in Pi command or an extension's command, and they do not run in a pi-subagents child. Each typed line runs the hooks once, after the `UserPromptSubmit` hooks, as upstream. When a `UserPromptSubmit` hook blocks the line, no `UserPromptExpansion` hook runs. The hooks see the line before an alias expands.

The stdin holds `session_id`, `transcript_path`, `cwd`, `hook_event_name`, and these fields (D-PG6-19):

| Field            | Value                                                                                                                                                                             |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `expansion_type` | always `slash_command`. Pi has no slash command for an MCP prompt, so `mcp_prompt` is never sent (D-PG6-22, Pi gap)                                                               |
| `command_name`   | `<plugin>:<skill>` for a plugin's skill, the Pi name for a plugin's command, and the bare name for an item of no plugin. An alias reports the skill or the command that it names  |
| `command_args`   | the rest of the line, trimmed; `""` when there is none                                                                                                                            |
| `command_source` | `plugin` for a plugin's item, `userSettings` for a template or skill of Pi's user scope, and `projectSettings` for one of Pi's project scope. It is left out for a temporary item |
| `prompt`         | `/` and `command_name`, then a space and `command_args` when there are arguments                                                                                                  |

The stdin holds no `effort`, `permission_mode`, `session_title`, or `model`, as upstream.

The matcher selects on `command_name` by the rules of a tool matcher, with no tool name map (D-PG6-19). An empty matcher or `*` selects every command. A matcher made only of letters, digits, `_`, `-`, spaces, `,`, and `|` is a list of exact, case-sensitive names. Any other matcher is an unanchored regular expression, so `demo:deploy` also selects `demo:deploy-all`, and `^demo:deploy$` selects only `demo:deploy`. A regular expression that does not compile drops its group at install. A hook with an `if` field does not run, as on every event with no tool (D-CF5-23). A synchronous hook's default timeout is 600 seconds, as upstream.

The hooks answer as upstream, with these texts (D-PG6-20):

- A block (`decision: "block"` or exit 2) stops the command, so the model gets no call. You see `UserPromptExpansion operation blocked by hook:` and the reason on the next line. An exit 2 gives the reason `[<command>]: <stderr>`. The first block in routing order gives the notice. Upstream adds `Original prompt: <prompt>`, and the bridge leaves it out, as on `UserPromptSubmit` (D-CF5-24).
- A `continue: false` also stops the command, and you see `Operation stopped by hook: <stopReason>`, or `Operation stopped by hook` with no reason.
- An `additionalContext`, and plain stdout on exit 0, reach the model as `UserPromptExpansion hook additional context: <text>`, after the `UserPromptSubmit` context of the same line.
- A `systemMessage` shows as `UserPromptExpansion says: <text>`. A hook that fails without blocking shows `UserPromptExpansion hook error: Failed with non-blocking status code: <line>`.
- An exit 2 of a missing script blocks, as upstream: the missing-script rule covers only `Stop` and `UserPromptSubmit`.

These behaviors stay different from Claude Code:

- A plugin's command keeps its Pi name in `command_name`. Where Pi's name differs from Claude Code's name, for a command file whose name starts with `<plugin>-` (PG-CMD-09), and on Windows, where Pi joins the names with `.`, a matcher with Claude Code's name does not select it. Reason: project decision.
- The bridge builds `prompt` from `command_name`, so `/skill:demo-status a` gives `/demo:status a`. `UserPromptSubmit` still gets the line as you typed it.
- When the bridge cannot read the names of the installed plugins, a typed template or skill reports Pi's name and no `command_source`, and an alias runs no hook.
- The context of a line that you send as a follow-up while the agent runs never reaches the model. Pi queues the expanded text, not the line you typed, so the bridge cannot find the follow-up in Pi's queue, and the next prompt that you send while the agent is idle drops the context (see [Additional context](#additional-context)). Reason: Pi gap.

The scenarios in [`features/hook/prompt-expansion.feature`](../features/hook/prompt-expansion.feature) prove the block, the fields for a typed command, skill, and alias, the order after `UserPromptSubmit`, the stop, the context, and a template of your own. The [resolver tests](../test/orchestrators/typed-expansion.test.ts) cover each kind of line, and the [dispatcher tests](../test/bridges/hooks/dispatch.test.ts) cover the matcher and each answer.

### Event status classification

The unsupported events fall into three buckets, each with a different forward path:

**Deferred for engineering reasons** -- a faithful Pi-side translation is possible but not yet built. A future milestone may lift these:

- `FileChanged` -- the bridge could watch the filesystem itself but the implementation is deferred.
- `CwdChanged` -- Pi exposes the working directory but does not emit an event when it changes.
- `PostToolBatch` -- Pi's per-turn boundary differs from Claude's parallel-batch boundary; a faithful translation is deferred.
- `SubagentStart` and `SubagentStop` -- a pi-subagents child runs its tool hooks, but the bridge does not yet run these two events (PG-HOOK-07b).
- `PreModelSwitch` and `PostModelSwitch` -- Claude Code 2.1.251 added them, and the bridge does not translate them yet (HKMS-01).

**Blocked on upstream Pi support** -- the bridge cannot expose these until Pi exposes the underlying primitive:

- `Notification` -- the Pi runtime does not expose a subscriber bus for user notifications.
- `PermissionRequest` -- Pi has no event for the permission dialog.
- `PermissionDenied` -- Pi has no auto-mode classifier corresponding to Claude's deny path.
- `MessageDisplay` -- Pi does not expose a render-time hook on assistant messages.
- `DirectoryAdded` -- Pi has no event for a directory that the user adds to the session.
- `TeammateIdle` -- Pi has no agent-team primitive yet.
- `Elicitation` and `ElicitationResult` -- blocked on `pi-mcp-adapter` or Pi's built-in MCP exposing the relevant MCP request. Pi 1.5.0 has no elicitation.
- `WorktreeCreate` and `WorktreeRemove` -- blocked on `pi-worktrees` publishing lifecycle events.

**Permanently inapplicable to Pi** -- the runtime semantics these events name do not exist under Pi and will not appear in any future milestone:

- `ConfigChange` -- the matcher values name Claude-specific settings paths that have no equivalent under Pi.
- `Setup` -- Pi has no init-only command-line mode.
- `InstructionsLoaded` -- Pi reads a different context-file set; the matcher values are Claude-shaped and would not apply.
- `TaskCreated` and `TaskCompleted` -- Pi has no canonical task primitive.

### Tool name mapping

The `matcher` field on tool events (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`) names a tool. Claude plugins use the Claude-side spellings; the bridge translates them to the Pi-side spellings used by the Pi event payload. The two columns below are equivalent: a matcher value of `Edit` matches the Pi `edit` tool, and vice versa.

| Pi tool name | Claude tool name |
| ------------ | ---------------- |
| `bash`       | `Bash`           |
| `powershell` | `PowerShell`     |
| `read`       | `Read`           |
| `edit`       | `Edit`           |
| `write`      | `Write`          |
| `grep`       | `Grep`           |
| `find`       | `Glob`           |
| `ls`         | `LS`             |

Unmapped Claude tools: `MultiEdit`, `NotebookEdit`, `WebFetch`, `WebSearch`, `Task`, `TodoWrite`, `KillShell`, `BashOutput`. Pi has no equivalent for these names, so it cannot translate a `matcher` value that names one. A plain `mcp__<server>__<tool>` matcher uses the exact MCP tool identity. Under Pi's built-in MCP, its server segment is the registered server name, with `-` kept.

A matcher with regex syntax, such as `mcp__<server>__.*`, is an unanchored JavaScript regular expression against the hook-visible tool name. It can also match a longer server name that contains `__`. Add `^` to match from the start, and escape regex characters in a server name. Add `$` when the complete tool name must match.

Plugin MCP tools normally reach hooks under their Claude Code names, `mcp__plugin_<plugin>_<server>__<tool>`, so a plugin's matchers and `if` predicates for its own tools fire as they do in Claude Code. For a name pi-mcp-adapter shortened from over 64 characters, a full-name matcher or `if` field still matches, and every hook of that event receives the full name. With no full-name hook, `PreToolUse` and `PostToolUseFailure` receive the shortened name, while a successful `PostToolUse` recovers the full name from the result. A server prefix longer than the first 55 characters does not match on those two events. This Pi gap comes from pi-mcp-adapter: Pi's tool list and a failed result omit the original name (D-PG1-08, `features/hook/mcp-tool-names.feature`). See [Name length](mcp-compatibility.md#name-length).

Under Pi's built-in MCP, a hook sees a tool as `mcp__<server>__<tool>`, with the server as Pi registered it and `-` kept (D-MB-08): `plugin_<plugin>_<server>` for a plugin server, or the key in Pi's `mcp.json` for a server that you configure yourself. The tool segment keeps Pi's change of `-`, and of every other character outside `[A-Za-z0-9_]`, to `_`, because Pi does not report the original tool name (Pi gap, D-MB-08). For example, the tool `echo-text` of the `mcp.json` server `echo-server` reaches hooks as `mcp__echo-server__echo_text`. Pi ends a tool's name with a hash in two cases: the name is longer than 64 characters, or another tool of the same server already has the name after the change to `_`. For example, of the tools `a-b` and `a_b` of one server, the tool that Pi registers second gets the hash. For a name longer than 64 characters, Pi keeps the first 55 characters, then `_`, then the first 8 hex digits of the sha256 of `<server>`, a NUL character, and `<tool>` (`dist/extensions/mcp/tools.js`, D-MB-13). Pi computes the hash from the original tool name. So for a name with a hash, only a matcher with Claude Code's full name fires, and a matcher with `-` changed to `_` in the tool segment does not. The tool segment keeps Pi's cut and hash, and when the cut falls inside the server part, the hook sees Pi's whole name (Pi gap). `features/hook/mcp-tool-names.feature` shows these names.

A call made through pi-mcp-adapter's `mcp` proxy tool (`mcp({ tool })`) runs a nested Pi call of the real tool. The outer proxy call runs no hook. The nested call runs each matching hook once, under the real tool name, with `tool_input` set to the tool's arguments (D-CF5-12). The same rule applies to a namespace proxy tool `mcp__<server>`. A proxy call that searches, describes, or reports status still reaches hooks as the proxy tool, because Claude Code has no proxy tool (Pi gap). A tool whose 64-character pi-mcp-adapter name looks like a namespace proxy is a direct tool, not a proxy call; its matching hooks run (D-PG1-08, `features/hook/tool-use.feature`). A call that the adapter runs inside the proxy with no nested Pi call does not reach hooks (Pi gap). This proxy rule applies only while pi-mcp-adapter is the active MCP implementation. The bridge checks the active MCP implementation once, at the first proxy-shaped call after a load, and keeps that answer until `/reload`. If that check cannot read Pi's tool or command list, the bridge treats pi-mcp-adapter as not active until `/reload`, so a proxy call then runs each matching hook on the outer call and again on the nested call. Under Pi's built-in MCP, or with no MCP implementation, no call is a proxy call (MHK-02). So each matching hook runs on every call, and a `*` hook also runs on Pi's `tool_search`. `features/hook/tool-use.feature` shows the proxy rule under each MCP implementation.

A tool that Pi does not have drops out of its `matcher` list, and the other alternatives keep working. For example, `Edit|Write|MultiEdit` still runs on `Edit` and `Write`. Pi drops the whole group only when no supported alternative is left. The plugin then reports `(partially-available)` with the reason `{unsupported hooks}`, the same as a matcher of `MultiEdit` alone.

Pi cannot tell a misspelled tool name from a deliberately foreign one. A matcher such as `Wriet|Edit` installs with no warning, because `Edit` alone keeps the hook firing. The plugin still reports that it is fully supported, and nothing flags the dropped `Wriet` alternative. Make sure that you spell every tool name in a `matcher` correctly. A typo in one alternative does not appear in the status that the plugin reports.

A matcher that fires on a Pi tool does not change the data the hook receives. The hook gets the Claude-form payload of the Pi tool that fired. For example, `Write|Edit|apply_patch` runs on Pi `write` and `edit`, and the script gets the `Write` or `Edit` payload. A script written for the similarly-named tool of another agent must handle that input itself.

### Placeholders in `command` and `args`

An exec-form hook (a hook with `args`) gets these placeholders filled in, anywhere in `command` and in each `args` string, as upstream does (D-CF5-15):

- `${CLAUDE_PROJECT_DIR}`
- `${CLAUDE_PLUGIN_ROOT}`
- `${CLAUDE_PLUGIN_DATA}`

The values are the same values that the hook's environment variables get. Both hook lanes (synchronous and `asyncRewake`) fill them in. After them, each `${user_config.KEY}` is filled with the default of the plugin option `KEY`, in `command` and in each `args` string, on both lanes (D-PG10-10). Any other `${...}` text stays as written.

A hook run that names an option with no value does not start. It fails as a hook error with Claude Code's message, `Plugin option "<key>" isn't set. Open /plugin manage to configure it, or check that the plugin's userConfig schema declares "<key>".` (D-PG10-08). On `UserPromptSubmit`, you see `UserPromptSubmit hook error: Failed to run: <message>`, cut to 200 characters (`features/hook/failures.feature`). With `onFailure: "block"`, the failure blocks, as any other failure does. The `asyncRewake` lane starts nothing and writes a debug line. Claude Code 2.1.323 probably shows `Failed with non-blocking status code: <message>` for this failure. That was read in its binary and not run (BACKLOG HOOKOPTFAIL-01).

A shell-form hook (a hook with no `args`) gets no text substitution. The shell expands the environment variables of the same names, as upstream. A shell-form command that names `${user_config.` does not run, whether or not the option has a value, because the shell would parse the value again. It fails as a hook error with Claude Code's message, which starts with `Hook from plugin <plugin> references ${user_config.*} in a shell-form command.` and gives two remedies: use exec form, or read `$CLAUDE_PLUGIN_OPTION_<KEY>` from the hook's environment (D-PG10-10, D-PG10-21, `features/hook/failures.feature`).

Both rules apply also to a plugin that declares no `userConfig`, as in Claude Code (D-PG10-21).

The environment of each hook holds `CLAUDE_PLUGIN_OPTION_<KEY>` for each option with a default (D-PG10-10). Claude Code 2.1.323 gives a hook saved values only, so with nothing saved a hook gets no option variable (read in its binary and not run). This extension has no saved values and treats each declared default as saved. So the default that a hook gets is more than Claude Code does, licensed by a project decision (D-PG10-19, pending maintainer review). It is not parity. See [Plugin options](env-vars.md#plugin-options).

### `onFailure`

With `onFailure: "block"`, a command hook that fails acts as an exit 2 on its event (D-CF5-18). These outcomes are failures:

- The hook cannot start.
- The hook exits with a code other than 0 and 2.
- The hook timeout stops it.
- Its trimmed stdout starts with `{`, ends with `}`, and does not parse as JSON. Stdout that starts with `{` and ends with anything else is plain text, which is a success. Several lines that each parse as JSON are not a failure either.
- On `UserPromptSubmit`, the hook exits 2 for a missing script, as the row `Missing script on exit 2` describes (D-PG5-09).

A failed hook that prints a JSON `deny` (or a `decision` of `block`) on stdout is not blocked by `onFailure`. Its own deny applies with its own reason, as upstream, and any other JSON it prints is dropped. A timeout still blocks with the `timed out` reason.

The block reason is `[<command>]: failed; blocking because onFailure is "block"`, then a new line and the hook's stderr. After a timeout, the reason says `timed out` in place of `failed`. When the hook prints no stderr, the reason ends after `"block"`. `<command>` is the declared `command` text, with its placeholders. For a missing script, the block also keeps the stderr as its detail. Claude Code 2.1.323 writes the missing-script sentence there instead.

The default, `continue`, lets the failure pass. The bridge ignores `onFailure` on `Stop` hooks, a missing script included, and on `async` and `asyncRewake` hooks, as upstream, and writes a debug line. On `SessionStart` and `SessionEnd`, which cannot block, the block shows as the event's hook error (D-CF5-24). On `PostCompact`, the failure shows in the hook's line after `/compact` (D-BG-501).

Each hook's `additionalContext` reaches the model. When several hooks of one event give context, the bridge keeps every value, in routing order (D-CF5-09, D-CF5-13).

| Event                                                    | How the model gets the context                                                                                                                                                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SessionStart`                                           | as `SessionStart hook additional context: <text>` in a hidden message before the first prompt of the session. The message stays in the session history for later turns                                              |
| `UserPromptSubmit`                                       | as `UserPromptSubmit hook additional context: <text>` after your prompt, which reaches the model unchanged. Upstream adds the text to the same request. Pi adds a separate hidden message after the prompt (Pi gap) |
| `UserPromptExpansion`                                    | as `UserPromptExpansion hook additional context: <text>`, after the `UserPromptSubmit` context of the same line (D-PG6-20)                                                                                          |
| `PreToolUse`, `PostToolUse`, `PostToolUseFailure`        | as `<Event>:<Tool> hook additional context: <text>` in a hidden message after the tool result. A call that the hook denies also sends its context                                                                   |
| `Stop`                                                   | as a `Stop hook feedback:\n<text>` part of the hidden message that continues the run; see [Stop continuation](#stop-continuation) (D-CF5-25, D-PG5-01)                                                              |
| `SessionEnd`, `PreCompact`, `PostCompact`, `StopFailure` | not sent, as upstream                                                                                                                                                                                               |

When `SessionStart`, `UserPromptSubmit`, and `UserPromptExpansion` give context for one prompt, one message carries the parts in that order. A value that is empty or only white space adds nothing. Each bridge load, `/reload` included, empties the context that waits for the next prompt.

A `UserPromptSubmit` context belongs to its own prompt. When a prompt starts no turn, for example because another extension handled it, the next prompt drops its context. A prompt that you send while the agent runs (a steer or a follow-up) starts no turn of its own, so its context goes in a hidden message on the model call that reads the prompt. Pi reads a steer on the next model call, so the bridge sends a steer's context at once. Pi reads a follow-up only when the agent would otherwise stop, so the bridge holds a follow-up's context until the turn after which Pi reads that follow-up. It finds the follow-up in Pi's queue by its text, as Pi does. A follow-up whose text Pi changes before it queues it, such as a skill command, is not found, and the next prompt that you send while the agent is idle drops its context. Pi changes the text of every line that runs `UserPromptExpansion` hooks, because it expands the template or skill first. So a follow-up always loses its `UserPromptExpansion` context, and its `UserPromptSubmit` context too. Pi queues the prompt only after the hooks finish, so the message comes just before the prompt, where upstream puts the text after it (Pi gap) (D-CF5-13).

A context string has a limit of 10,000 characters, as upstream (D-PG5-14). The bridge measures each string alone, before it joins strings, in JavaScript string length. The limit applies to these strings:

- A hook's `additionalContext`, on every event, in the synchronous and the background lane.
- Plain stdout that counts as context, on `SessionStart`, `UserPromptSubmit`, and `UserPromptExpansion`.
- The `systemMessage` of a plain `async` hook's answer, which goes to the model.

The limit does not apply to a block reason, an exit-2 stderr, a rewake text, or a replaced tool output. A synchronous hook's `systemMessage` goes only to you, and the notice bound of 2,000 characters cuts it.

The bridge saves a string over the limit whole to a file. In place of the string, the model receives this text, after the bridge's label (D-PG5-15):

```text
<persisted-output>
Output too large (<size>). Full output saved to: <path>

Preview (first 2KB):
<preview>
...
</persisted-output>
```

`<size>` is the length in KB, such as `11.7KB` for 12,000 characters. The preview is the head of the string. It ends at the last line break in the first 2,000 characters when that break comes after character 1,000, else at character 2,000.

The file is `hook-<id>-<source>.txt` in the folder `pi-claude-marketplace/data/_shared/hook-output/` under the root of the hook's plugin scope. `<source>` is `additionalContext`, `systemMessage`, or `stdout`. For a user plugin, the folder is `~/.pi/agent/pi-claude-marketplace/data/_shared/hook-output/`. For a project plugin, the folder is `<project>/.pi/pi-claude-marketplace/data/_shared/hook-output/`, inside the project directory. If you keep the project in version control, add this folder to the ignore list. Claude Code writes the file to its session directory, which is outside the folders that this extension writes. Each bridge load removes the files in the folder that are older than 30 days. This retention is a project choice, because upstream ties the file to its session. The sweep has these limits:

- It removes only regular files named `hook-<id>-<source>.txt`. It keeps a link, a sub-folder, and every other file, and it follows no link.
- It skips the folder of a project that Pi does not trust.
- A file that it cannot read or remove, for example one that another Pi removed first, does not stop the sweep. The sweep goes on with the next file, and with the debug log on it writes one line for that file. A file that it could not remove stays until a later load.

If the bridge cannot write the file, the model receives the head of the string, then `[Hook <source> truncated at 10000 chars`, a space, an em dash, a space, and `persist-to-disk failed: <error>]`. The whole text stays within 10,000 characters, and the event goes on. The scenario "A prompt hook's context over 10,000 characters reaches the model as a saved file and a preview" in [`features/hook/additional-context.feature`](../features/hook/additional-context.feature) proves the saved file.

### Messages to the user

A hook's `systemMessage` is shown to you and never sent to the model (D-CF5-14). The bridge shows it through the extension's notifications, at `info` severity, as `<label> says: <text>`. In JSON and RPC mode, each notice is a `hook-notice` entry. `<label>` names the event and the value that the hook matched, as upstream names the hook:

- `PreToolUse:<Tool>`, `PostToolUse:<Tool>`, `PostToolUseFailure:<Tool>`
- `UserPromptSubmit`
- `UserPromptExpansion`
- `Stop`
- `SessionStart:<source>`, for example `SessionStart:clear`

`SessionEnd`, `PreCompact`, `PostCompact`, and `StopFailure` drop a `systemMessage` with a debug line, as upstream. An empty `systemMessage` shows nothing. When several hooks give a message, the messages show in routing order.

The same notice kind carries twelve more notices (D-CF5-24, D-BG-501, D-PG5-11, D-PG5-13, D-PG6-20):

- A blocked prompt shows `UserPromptSubmit operation blocked by hook:` and the reason on the next line. The prompt does not reach the model. Upstream adds a third line, `Original prompt: <prompt>`. The bridge leaves it out.
- A blocked typed command shows `UserPromptExpansion operation blocked by hook:` and the reason, or `[<command>]: <stderr>` for an exit 2, on the next line. The command does not expand, and the model gets no call. The bridge leaves out upstream's `Original prompt:` line here too.
- A block on `SessionStart` or `SessionEnd`, which cannot block, shows as `<label> hook error: <message>`. An exit 2 gives the message `[<command>]: <stderr>`.
- After `/compact`, one notice lists how each `PostCompact` hook ended, one line per hook (see [Compaction](#compaction)). An automatic compaction shows none (D-BG-501, D-BG-502).
- A `PreCompact` block shows `Compaction blocked by PreCompact hook: <message>` (see [Compaction](#compaction)).
- A hook that fails without blocking shows `<label> hook error: Failed with non-blocking status code: <line>` (see the row `Other exit -> non-blocking, stderr to user`).
- A hook that cannot start shows `<label> hook error: Failed with non-blocking status code: Error occurred while executing hook command: <error>`.
- A hook that fails inside the bridge after its start shows `<label> hook error: Failed to run: <error>`.
- A missing script on `Stop` or `UserPromptSubmit` shows `<label> hook error: Hook script appears to be missing`, an em dash, and the rest of the text (see the row `Missing script on exit 2`).
- A `continue: false` on `UserPromptSubmit` or `UserPromptExpansion` shows `Operation stopped by hook: <stopReason>`, or `Operation stopped by hook` with no reason.
- A `continue: false` on `PreToolUse` shows `PreToolUse:<Tool> hook stopped continuation: <stopReason>`, or `Execution stopped by hook` in place of an empty reason. The model still reads `Operation stopped by hook` as the reason of the stop, where upstream sends `Execution stopped by PreToolUse hook`.
- A `continue: false` on `Stop` shows `Stop hook stopped continuation: <stopReason>`. With no reason, it shows nothing. Pi decides whether the run goes on only after every extension's handler of that event, so the bridge shows the line when the run stops, after the hooks' other notices. When Pi continues the run anyway, the bridge shows nothing, because the run did not stop. That happens when another extension continues the run, or when you typed input while the hook ran. When another extension ends the run, or you press Escape, the line shows.

A notice can echo data that a hook read, such as a tool input or a file. So every notice loses its terminal escape sequences, every other control character except a line break or a tab becomes a space, and a notice longer than 2,000 characters is cut and ends with `… (+N chars)`.

Upstream merges the hooks of a `plugin.json` `hooks` field with `hooks/hooks.json`, and a marketplace entry's `hooks` replaces events of the plugin's own configuration. The bridge does not merge them yet. So it reports such a plugin as `(partially-available)`, and you install it with `--partial`. The hooks of `hooks/hooks.json` then run, and the hooks of the field do not.

A project-scope plugin's hooks run only when Pi trusts the project (`ctx.isProjectTrusted()`), as Claude Code loads no project-scope plugin before you trust the workspace. The session start and each load read Pi's answer, and an install, update, reinstall, or enable during the session uses the answer of the last of them. In a project that Pi does not trust, the hooks of its plugins do not run, and the skip is silent. A project install writes nothing outside the project, so no record of it is kept in your home directory (D-LOC-01). Pi 1.5.0 trusts, without asking, a project that holds none of Pi's own settings files. A repository that holds only this extension's files is such a project, so its hooks run. Pi 1.5.0 honors a saved "Do not trust" answer for such a project too, and then its hooks do not run.

## Install-time disposition

The bridge picks one of four responses when a plugin declares a feature outside the supported set:

**Partial-partition drop** -- when a `hooks.json` parses and validates cleanly but declares an unsupportable event, matcher group, or handler type, the bridge drops only the offending entries and installs the rest. The plugin resolves `(partially-available)` and, once installed, derives `(partially-installed)`. Every dropped entry rides a SINGLE aggregate `{unsupported hooks}` brace (D-71-04); the per-handler `event(matcher) (unsupported)` breakdown is shown on the `plugin info` surface (D-71-05). The bridge favors partial support over a whole-plugin failure so that a plugin's supported hooks still run. Applies to:

- any unsupportable event in `hooks.json`, including `DirectoryAdded`, `PreModelSwitch`, and `PostModelSwitch` (it drops per-entry; supported events declared alongside it still install, D-CF5-19)
- tool-event regex matchers with invalid syntax
- tool-name matchers naming a Claude tool with no Pi analog
- non-tool matchers outside the per-event closed set (for example, `logon` on `SessionEnd`)
- any handler `type` other than `"command"`
- a `plugin.json` `hooks` field other than `hooks/hooks.json`, and any marketplace entry `hooks` field (D-CF5-20)

**Structural unavailable** -- a structurally malformed `hooks.json` (invalid JSON, or a schema failure such as a `type: "command"` handler missing its `command`) resolves `(unavailable)` and none of the plugin's hooks install. This is a distinct arm from the partial-partition drop above: its reason brace is sourced through `narrowResolverNotes`, not the `narrowUnsupportedKinds` path the partial drop uses.

**Silent fall-open** -- the hook fires on every matcher hit and a `hookDebugLog` warning records the cause. This matches Claude Code's documented best-effort contract for the `if` field. Applies to:

- every `if`-field shape outside the supported prefix set (`Grep(...)`, `LS(...)`, `Cd(...)`, parameter matching, tool-name wildcards, unknown prefixes)
- malformed `if` syntax (`Bash(` with no close, broken globs)
- runtime Bash commands containing `$(...)`, backticks, or `$VAR`
- runtime PowerShell commands containing `$(...)`, `$VAR`, or `${VAR}` -- a PowerShell backtick is an escape rather than command substitution, so it does not make a command uncertain

**Silent drop** -- the bridge accepts the field at parse time but never acts on it. Applies to:

- `terminalSequence` -- no Pi surface to render it
- `initialUserMessage`, `sessionTitle`, `watchPaths`, `reloadSkills` on `SessionStart`
- `once` on a plugin hook, as upstream (D-CF5-17)
