# The world and stand-ins

Part of the `cucumber` skill: `.agents/skills/cucumber/SKILL.md`.

## The world

- `features/support/world.ts` declares the world class and registers it. Every scenario gets a fresh world.
- A hook lives in the support module of the thing it sets up and is registered as a step is: a `Before()` or `After()` hook that uses the world is a `function` expression with a typed `this`, and one that does not is an arrow. `BeforeAll()` and `AfterAll()` run once per worker, outside any scenario, so they get no world and are always arrows.
- Keep scenario state on the world as initialized fields; no module-level mutable state anywhere under `features/`. Module state outlives the scenario that set it and leaks into the next one.
- One exception: a process under test that is too slow to start per scenario. The support module named after that process may hold it as the run's only module-level state, with `BeforeAll()` starting it and `AfterAll()` stopping it. A `Before()` hook then resets it before every scenario: it empties everything the process reads, and asserts that nothing from an earlier scenario is left. A process left busy or gone by a failed scenario is replaced. Each parallel worker loads its own copy of that module, so each worker gets its own process.
- A scenario that needs a session in another project starts a second Pi of its own through the world's `startSessionInAnotherProject()`. The world stops that Pi and removes its project directory. The second Pi is scenario state, not module state, so only the scenarios that need it pay its start-up time.
- A scenario that needs Pi to run with another GitHub base address, such as one Pi refuses (GHB-03), starts a Pi of its own in the run's sandbox through the world's `usePiWithGitHubBaseUrl()`, behind the step `pi runs with the github base address "<value>"`. That Pi takes the place of the run's Pi for the rest of the scenario, and the world stops it. Its startup load reads the configs, so the step comes before the steps that write them.
- A scenario that proves an RPC session does not run the background update starts a Pi of its own in the same way through the world's `usePiWithBackgroundUpdateDelay()`, behind the step `pi runs with the background update delay "<value>"`, because a Pi's environment is fixed when it starts, and the run's Pi never sets `PI_CLAUDE_MARKETPLACE_AUTOUPDATE_DELAY_MS`. With no delay, a pass that wrongly armed would append its notice inside the driver's window.
- A stand-in whose address or trust that process fixes when it starts shares the same run state. For example, Pi reads the run's certificate and the git host's port once, at start, so the https git host lives in the same `PiRun` as Pi. The same `BeforeAll()` starts the stand-in before the process, and `AfterAll()` stops it after the process. `Before()` resets the stand-in together with the process: it empties the repositories, the arming, the request log, the connections, and the CGI children, and asserts that nothing is left. A replaced process gets the same environment, so it trusts the same certificate and reaches the same address.
- The git host serves bare repositories under any owner: `acme` for the fixtures, and `anthropics` for the official marketplace, which Pi reaches through the GitHub base override. A step names a repository through the `{git repository}` parameter type, by the marketplace or the plugin it serves, such as `marketplace "tools"` or `plugin "ghp"`. The plugin form names the one git plugin repository of the scenario that holds that plugin now. A step that arms a repository registers a release that disarms it. `the git host serves the <repository> again` removes that arm as a precondition before the scenario's `When`, so an arm never outlives its scenario.
- The git host also serves the static catalog files of hosted marketplaces, from memory, at `/<owner>/<directory>/<file>`. An arm of a hosted marketplace applies to its catalog as it applies to a repository. `Before()` resets the files with the repositories, and its check asserts that the host serves none.
- Keep `order: random` in `cucumber.json`, so a reset that leaks fails.
- The world owns the lifetime of everything else a scenario creates (temporary directories, fakes, child processes). The step or hook that creates a thing registers its release with `this.onRelease()`; the `After()` hook in `world.ts` runs the releases in reverse order, so teardown happens in one place and in the reverse of setup even when a scenario fails halfway. Every release runs even when an earlier one fails; the failures surface together as one `AggregateError`. No other hook releases scenario resources.
- A step timeout above the default is a named constant with a comment that says why. A run-wide default goes in `world.ts`, beside the world it governs.

## Fakes and drivers

- A fake listens on loopback only, records what it receives, and can be armed to fail, so scenarios cover error paths. A fixture reaches its error paths through bad input that scenarios write.
- A driver that runs the code under test validates what it returns against the published contract, such as a JSON schema, before a step reads it.
- The command driver returns every payload a command emits, in the order the command emits them. It validates each payload against the published payload schema (DRV-01).
- The session driver reads the payloads of a new session, such as its reconcile report, through Pi's RPC `get_entries` request. It validates each one (DRV-01) and returns every one in session order. Pi binds the extension twice in an RPC `new_session`, so a lasting reconcile failure appears twice. The driver keeps both, and a scenario states both.
- A plain message's background result is read from the entries that follow the message. Pi refuses the message for want of a model, but only after its input handlers ran, so the driver asserts the refusal and that the refusal carries no payload, which proves no update ran before Pi answered. It then reads the entries until at least one payload follows the message and no new payload has arrived for a quiet window, or until its window ends, and returns the payloads it read, which can be none. Only a tui session arms the background update, and the suite drives Pi over RPC, so the driver's purpose is the RPC negative: `Then the session reports no results` proves that nothing followed the message. The quiet window still lets a later, extra payload reach the step when one arrives. `When the user sends the message` keeps those payloads as session results.
- A tui session's Pi reads its environment when the first message arrives, so `Given the tui session starts with the environment variable {string} set to {string}` (the world's `setTuiVariable`) adds a variable to that session alone, before the session starts. `Then the tui session reports no notice` first waits for Pi's refusal of the message, which follows its input handlers, so its quiet window starts after the background pass was armed or declined.
- A terminal turn with the scripted model is one `When`, as in `features/step_definitions/skill/aliases.steps.ts`. The step starts the terminal Pi through the world's `startTuiSession("scripted")`. That call loads and selects the scripted model (`--provider faux --model faux-1`), waits for the `readyText` `[Extensions]`, and registers `this.onRelease(() => tui.stop())` at once. A terminal-only action before the turn runs in the same `When`, such as `/reload` through `PiTuiSession.reload()` in `the user reloads pi in the terminal and then prompts {string}`. `sendTerminalTurn()` in `features/lib/scripted-model/terminal-turn.ts` sends the turn and keeps its log lines. The step waits only on render events, such as the completion menu marker, the redrawn input, Pi's reload status, and the reply, and it records the turn for the `Then` steps.
- `When the user starts a new pi session` keeps the session's payloads as the last results, as `When the user runs` does for a command. So the rules below for uncompared rows and notices cover sessions too. A command is always followed by a field step, but a session is not, so the world also fails a scenario when a session reported a result whose fields no step stated. The steps that state the fields of every result, such as `the result has these fields:` and `the session reports these results:`, record the comparison through the world's `markResultsCompared()`. A session that reports nothing leaves nothing to compare.
- A step that expects one result asserts that there is exactly one payload. It never picks one payload out of several.
- A command with several payloads is compared in two steps (D-02). The first step, `the command reports these results:`, lists one row per payload. The second step, `the results list these marketplaces and plugins:`, lists the rows across all the payloads. When no payload carries rows, the first table alone is the whole value. An info fan-out, whose payloads are a marketplace-info and a plugin-info, is an example. A new session's payloads are compared the same way, with `the session reports these results:` as the first step. Each of the two first steps refuses the results of the other source: `the command reports these results:` fails after a new session, and `the session reports these results:` fails after a command.
- The steps that state a result's fields hide its row arrays, `marketplaces`, `blocks`, and the `plugins` of a `background-update`. A row step records that it compared them through the world's `markRowsCompared()`. A scenario that otherwise passes fails when the last command left a non-empty row array that no row step compared, and a second `When` fails when the first one's rows went uncompared. `the result lists these plugins:` reads the plugin rows of a `cascade` and of a `reconcile-applied-cascade`, the blocks of a `plugin-info-cascade`, whose columns have the names the fields of a single `plugin-info` result have, and the `plugins` of a `background-update`, whose columns are `name`, `marketplace`, `scope`, `from version`, and `to version`. `the result lists these marketplaces:` reads the marketplace blocks of a `cascade` and of a `reconcile-applied-cascade`, and the blocks of a `marketplace-info-cascade`. The field steps compare a kind without a row array whole, such as `prune-empty`, `reconcile-pending-empty`, `usage-info`, `reconcile-aborted`, `internal-error`, and `prune-committed-warning`; `the results list these marketplaces and plugins:` skips such a result, since it has no row to miss. A new kind with a `marketplaces` or `blocks` row array fails until a row step learns its rows.
- An MCP config notice result has no rows: its notices are fields, and only `the command reports these results:` states them. That step records it through the world's `markNoticesCompared()`. A scenario that otherwise passes fails when the last command emitted a notice that step did not compare, and a second `When` fails when the first one's notices went uncompared.
- Local marketplace fixtures live under the sandbox home directory.
- The world records the source kind of each published marketplace, and the library code dispatches on it. A new source kind changes library code only, not the steps.
- The official marketplace is recorded like any published marketplace: a github source on the git host. So every marketplace step works on it.
- A driver may reuse a process harness from `test/` rather than copy it.

## Profile Pis and the scripted model

### The profile Pi and project trust

- The run's shared Pi has no model, and its MCP implementation follows the profile, as "MCP implementations" below says. A scenario that needs the scripted model or a companion starts a profile Pi through a `Given`, which calls the world's `usePiWithProfile()`. The profile Pi runs in the run's sandbox and becomes the Pi that the steps talk to. The scenario's release stops it together with its process group (D-CF1-15). One scenario starts at most one profile Pi through a `Given`. Only the restart steps of "MCP implementations" replace it with another.
- A profile Pi loads, in this order, the real extension, the scripted model, the registry probe, the companions that the step names (always in the order pi-subagents, pi-mcp-adapter, pi-dynamic-workflows), and then the profile's `extraExtensions`. A phase adds its own Pi extension under `features/lib/` through `extraExtensions`, not by editing the world. The world finds each companion through the `pi.extensions` entry of its `package.json` in the optional peer cache, and checks its version against the declared floor. It never hard-codes an entry path. After the start, the world selects the scripted model (`faux`/`faux-1`) and turns auto retry off, so a call past the script fails at once.
- The profile Pi runs with `TMPDIR` set to `{home}/tmp`. Its environment is the run's allowlist plus the git keys plus `TMPDIR`, and nothing else. Pi compiles each TypeScript extension through jiti, which caches under `$TMPDIR/jiti`, and a cold cache costs ten seconds or more per start. So `{home}/tmp/jiti` is a symlink to `<run root>/jiti-cache`, which lasts the worker's run and holds only compiled sources.
- A step that starts a profile Pi uses `PROFILE_PI_START_TIMEOUT_MS` (90 seconds) from `world.ts`, because each worker's first profile Pi compiles through a cold cache. The untrusted-profile `Given` uses its own 60-second timeout in `companion.steps.ts`, because Pi loads every extension twice in a project that needs a trust decision.
- The launch-environment extension, `features/lib/pi-launch-environment.ts`, gives a profile Pi a variable that the user's shell would set. A step writes the variables to `{home}/pi-launch-environment.json` before the start and loads the extension through `extraExtensions`. The extension copies them into Pi's `process.env` and logs them to `pi-launch-environment.jsonl` in the harness directory. Everything that Pi starts later, such as an MCP server, inherits them. The worker's own `process.env` is never touched.
- The profile Pi trusts the sandbox project through a persisted entry in `<agent dir>/trust.json`, the record that Pi saves when a user answers its trust prompt. It never uses `--approve` or `defaultProjectTrust` (D-CF1-07). An untrusted scenario starts a profile Pi with no entry, through `pi runs with the scripted model and these companions in an untrusted project:`.
- Pi trusts a project that holds no trust-requiring resource, whatever `trust.json` says. So an untrusted scenario also writes `<project>/.pi/settings.json` with `the project holds a pi settings file`, before the profile `Given`, and the trusted scenario beside it holds the same file. Then only the trust entry differs between the two.
- An agent scenario observes trust through a run with `agentScope: "project"`. pi-subagents 0.84.0 lists the agents of an untrusted project, but its runs refuse them, so the `list` action shows no difference.
- An agent feature starts the profile Pi with pi-subagents before its install. Without the companion, the install warns (`requires pi-subagents`), and `Given the user has run` accepts only info results.
- A hook scenario that needs a Pi in the terminal starts a profile Pi first and installs through it. A plugin installed through the run's shared Pi keeps its SessionEnd hook routed there until the next scenario's reset starts a new session (D-CF5-26).
- `pi-subagents hides its builtin agents` merges one key into `{agent dir}/settings.json` and restores the old bytes on release, so an agent scenario's expected list can hold only bridged agents (D-CF4-13). Where builtins stay visible, the agent-list projection folds them into one `pi-subagents' own agents` line.
- Approval of project MCP servers is a separate `Given`, `pi-mcp-adapter allows project mcp servers for the user`, that writes the user-level `projectServers` setting of pi-mcp-adapter to `<agent dir>/mcp-adapter.json`. It is never part of the default profile.

### MCP implementations

Which scenarios run under which profile is in `.agents/skills/cucumber/rules/features.md` ("MCP implementations"). This section says how each Pi gets its implementation.

- The profile reaches the harness as the world parameter `mcpImplementation`, `adapter` or `builtin` (DUAL-01). The shared Pi's `BeforeAll()` stays an arrow: it reads the profile through cucumber's `context.parameters`, and fails at once on any other value.
- The run's shared Pi follows the profile (P1-DC-03). Under the adapter profile it loads pi-mcp-adapter. The run's start and every reset then write `{agent dir}/mcp-onboarding.json`, with `piBuiltinMcpHandledVersion` set to the version of the cached adapter, before a session starts (P1-DC-13). Without that file, the adapter adds `-builtin:mcp` to the sandbox settings at every session start. Under the builtin profile the shared Pi loads no companion and keeps Pi's built-in MCP.
- Every RPC Pi that the run or a scenario starts is checked against the implementation that its launch configuration implies (DUAL-02, P1-DC-14). That covers the shared Pi at the start of the run and after each reset, every profile Pi, and every restarted Pi. If pi-mcp-adapter is among its extensions, the expected implementation is the adapter. Else, if Pi starts with `--no-mcp`, or the `extensions` of `{agent dir}/settings.json` or `{project dir}/.pi/settings.json` hold `-builtin:mcp`, it is none. Else it is built-in.
- The check reads Pi's command list through `get_commands` and applies the extension's own detection rule (MSEL-01): the adapter when `/mcp-adapter` is loaded, else built-in when `/mcp` comes from `builtin:mcp`, else none. `classifyMcpImplementation()` in `features/lib/mcp-implementation.ts` passes the command list to the extension's `softDepStatus()`, so the harness and the extension cannot apply two rules. A mismatch fails the step that started the Pi, and the failure names both implementations. A terminal (TUI) Pi is not checked.
- The completion steps classify plugins for the profile's implementation (D-P6-22). `the user requests plugin completions for {string}` passes the world's `mcpProfile` to `pluginCompletions()` in `features/lib/plugin-completions.ts`, as the registered command passes the active implementation. So a completion scenario expects the set that its profile offers.

The MCP implementation steps are frozen (frozen interface 9). A scenario uses them with this exact text:

- `Given pi runs with the scripted model and the mcp implementation` starts a profile Pi with the scripted model and the profile's implementation: pi-mcp-adapter under the adapter profile, and no companion plus the built-in stand-in under the builtin profile. A step that needs more companions composes `mcpImplementationLaunch(profile)` from `features/lib/mcp-implementation.ts` with its own list.
- `Given the mcp implementation has listed the tools of the stub mcp server {string} of the plugin {string}` waits for the adapter's listing under the adapter profile, and for Pi's built-in connection and listing under the builtin profile.
- `Given a stand-in registers the stub mcp server {string} of the plugin {string} with pi's built-in mcp` names a stub server for the built-in stand-in. It comes before the step that starts the profile Pi. Under the adapter profile no stand-in loads, so the step has no effect there.
- `Given the user's pi settings turn off pi's built-in mcp` adds `-builtin:mcp` to the `extensions` of `{agent dir}/settings.json`, as pi-mcp-adapter or a user does. It comes before any profile Pi starts.
- `When the user restarts pi without pi-mcp-adapter` removes pi-mcp-adapter from the companions. A `-builtin:mcp` entry that the adapter wrote stays on disk, as after a real removal.
- `When the user restarts pi with pi-mcp-adapter` adds pi-mcp-adapter to the companions.
- `When the user restarts pi with pi's built-in mcp turned on` removes the `-builtin:mcp` entry from `{agent dir}/settings.json`, as a user does, and keeps the companions. D-MB-01 forbids the extension to edit Pi settings. It does not forbid the harness, which acts as the user (P1-DC-08).
- `When the user restarts pi with no mcp` removes pi-mcp-adapter from the companions and starts Pi with `--no-mcp`.
- `Then pi lists these registered mcp servers:` compares the whole list of MCP servers that extensions registered with Pi, by name, as the registry probe reports them.

A restart needs a profile Pi that the scenario started. When that Pi loaded pi-mcp-adapter, each restart first waits until the adapter's onboarding file records the adapter's version, so the adapter's `-builtin:mcp` write is on disk before anything changes. Each restart stops that Pi and asserts that its stand-ins stopped. The check waits up to 10 seconds (`STAND_IN_EXIT_TIMEOUT_MS` in `features/lib/turn-records.ts`), because a stand-in that Pi lost track of exits only when its stdin closes. A stand-in that still runs after that time fails the step. It keeps the sandbox, the trust entry, the script, and the installed plugins. Then it starts a new profile Pi with the scripted model, and records the new session's report as the last session results, so `the session offers these skills:` and `the session reports no results` read it.

In an `@own-implementation` scenario, the world removes the harness onboarding seed before a profile Pi that loads pi-mcp-adapter starts. So the adapter's real first-run write happens.

The built-in stand-in is a harness Pi extension under `features/lib/builtin-mcp-stand-in/` (P1-DC-05):

- Only `pi runs with the scripted model and the mcp implementation` loads it, through `extraExtensions`, and only under the builtin profile.
- It registers in its `session_start` handler, never when Pi loads it. It loads after the real extension, so its handler runs after the extension's.
- For each stub server that the stand-in step named, it registers `builtinMcpServerName(plugin, server)` with the stub's command and `exposure: "deferred"` (D-MB-02).
- It skips a name when Pi already has a registration or an `mcp.json` server of that name. It compares names with `-` and `_` folded. So it serves built-in scenarios before the extension registers servers itself, and steps aside once the extension does.
- It never throws. The scenarios that prove the extension's own registration (BLT-01 to BLT-06) never name it.

### The scripted model

- The scripted model is Pi's faux provider, loaded as a Pi extension from `features/lib/scripted-model/` (D-CF1-17). It reads the scenario's script from `model-script.json` in the harness directory, `{home}/harness`. It counts the lines of its own call log, `model-calls.jsonl`, to find the next step, so the Pi of a child agent reads the same script. The script, the call log, and the count reset with the sandbox.
- The scripted model registers through `pi.registerProvider()` with the literal key `scripted-model`. Pi counts a provider with a literal key as configured at once, so a new session never starts without a model. The key reaches no service, because the faux stream makes no request.
- `the scripted model plays these steps:` writes the script. Each row is a reply (column `reply`), or a tool call (columns `tool` and `arguments`, whose arguments are a JSON object).
- The scripted model records every call whole: the messages, the tools, and the system prompt.
- The scripted model has no fallback reply. A call past the end of the script fails the turn, and a step that no call used fails the scenario.
- A feature file writes the whole script as literals. The shared `@mcp` hook scenarios are the one exception. Their step `the scripted model calls the tool {string} of the hooks' stub mcp server {string} of the plugin {string} through the mcp implementation with {string}, then replies {string}` (in `hook/tool-use.steps.ts`, through `features/lib/hook-mcp-calls.ts`) builds the script from `profileFor(...).toolName`, because no literal names the tool under both implementations (P5-DC-14).
- A `Then` reads the call log, never the script, because a step that reads the script back proves nothing. `the model receives these calls:` lists one row per message of every call of the last turn, with the columns `call`, `role`, and `text`, and leaves out system messages. A tool call reads `tool call <name> <json>`, and a tool result has the role `tool result` and reads `<tool> returned: <text>` or `<tool> failed: <text>`. Text that Pi or a companion writes itself (a pi-subagents agent list or run wrapper, a pi-mcp-adapter `mcp` result, Pi's read notices) reaches the row through `features/lib/upstream/`, which reduces it to the facts this extension owns in a fixed form of our own, so the row never states upstream wording. Pi's `tool_search` result has its own step, `the model receives these calls, with each tool search reduced to the tools it loads:`, which projects it through `upstream/tool-search.ts`.

### Upstream text

- A scenario pins what this extension does, never wording, layout, defaults, or order that Pi or a companion owns. An upstream release that rewords its own output must break no scenario. This covers Pi, pi-subagents, pi-mcp-adapter, and the workflow engine.
- A step reduces upstream text to our facts through a projection in `features/lib/upstream/` (or the step's own parser), then compares the whole projection. A projection parses tolerantly, anchored on our values, and throws when it cannot read the text, so a real format break fails loudly instead of passing.
- `features/lib/upstream/tool-search.ts` reduces Pi's `tool_search` result to the tools that the search loads. It writes one `found <tool>: <description>` line per tool, sorted by tool name, or `found no tools`. That is the form `upstream/mcp.ts` gives a search through pi-mcp-adapter's `mcp` tool, so a built-in scenario and its adapter twin can state the same rows.
- Where upstream composes our part into a larger whole (a child system prompt, Pi's offered tool list), the step checks only our part, and its name says so. It never states the upstream remainder.
- A text this extension writes itself stays exact, even when it copies an upstream format, such as the skill block it builds as Pi does.

### The model turn

- The model-turn `When`, `the user prompts {string}`, sends the prompt. If Pi reports the `handled` disposition, no turn runs. Otherwise the step waits for `agent_settled` with `aborted: false` until a named deadline. It never sleeps for a fixed time.
- The step keeps every record that the turn produced: RPC events, tool events, custom entries, notifies, and extension errors. It also keeps every line that the stand-ins logged during the turn. It fails on a dialog or an extension error in the turn. The Pi process cancels every dialog, also one that arrives outside a request, so Pi never waits on one.
- A `Then` that compares the whole of what a turn reports marks it compared through the world's `markTurnCompared()`. The world fails a scenario that otherwise passes when no step compared its last turn, and a second turn fails when the first one went uncompared.
- Pi queues a prompt sent during a turn as a follow-up. So a step never sends a second prompt before the first turn settles.
- A workflow run does not use the model-turn `When`. `the user runs the workflow command {string}` waits for the terminal `pi-dynamic-workflows:progress` entry in Pi's session, because workflow results do not come back over RPC. It fails when the scripted model is called during the run. A command the engine refuses before a run writes no progress entry: `the user runs the workflow command {string}, which starts no run` reads Pi's records up to its answer and fails on any progress entry, and `the workflow engine shows these notices:` compares the engine's notices, with U+2014 read as `--`.

### Stand-ins of the profile Pi

- A stand-in appends one JSON line per event to `{home}/harness/<name>.jsonl`. A stand-in process writes its pid to `{home}/harness/<name>-<pid>.pid` and removes the file when it exits. A turn keeps, for each log, the lines it gained during the turn.
- The registry probe is a Pi extension under `features/lib/pi-registry-probe/`. Its command, `pi-registry-probe`, appends one `pi-registry-probe` custom entry with Pi's tools, all of them and the active ones, and Pi's commands, each with its source and path, in Pi's order. `When the user lists the slash commands pi offers` runs it and keeps the validated report as the world's `registrySnapshot`. `pi offers these slash commands from prompt templates:` compares the commands whose source is `prompt`. The probe's own command is in every profile Pi's command list, so a step that compares all extension commands expects it.
- The built-in config probe is a Pi extension under `features/lib/mcp-builtin-config-probe/` (P2-DC-24). A built-in values scenario loads it through `extraExtensions`, with `pi runs with the scripted model and a probe of the mcp servers registered with pi's built-in mcp`. Its command appends one custom entry with the name and the whole config of every MCP server registered with Pi, in Pi's order. `the user asks pi for the configs of the mcp servers registered with it` runs the command and reads that entry.
- The hook recorder, `features/lib/hook-recorder.ts`, runs as a hook command. Each run appends one line to `hook-runs.jsonl` in one write, with the event, the stdin, the arguments, and the `CLAUDE_*` and `CLAUDECODE` environment. Each hook passes its own name as the argument, so a row says which hook ran. The recorder writes no pid file, because it exits when its stdin ends.
- The MCP stub, `features/lib/mcp-stub-server.ts`, is a stdio JSON-RPC server with no dependencies. It logs every message it receives, requests and notifications, with its plugin and server names, to `mcp-stub-requests.jsonl`. It keeps `mcp-stub-<pid>.pid`, and exits when its stdin closes. It finds the harness directory through `HOME`, which pi-mcp-adapter passes on from Pi.
- `features/lib/hook-mcp-tool-server.ts` is a stdio JSON-RPC server with no dependencies, no request log, and no pid file. It lists one tool named by its argument, answers `tools/call` with `<tool>:<text>`, and exits when its stdin ends. `pi's mcp.json configures the server {string} with the hooks' stub mcp tool {string}` writes `{agent dir}/mcp.json` with that server under `direct` exposure. Write it after the install and before `pi runs with the scripted model and the mcp implementation`. The step refuses a started profile Pi, and the file is removed when the scenario ends.
- A new RPC session binds the extension twice, and each binding starts pi-mcp-adapter's startup listing of a server. So an MCP scenario installs through the run's shared Pi before the profile Pi starts, and waits for the startup listing to end before the turn. An `@mcp` scenario waits with `the mcp implementation has listed the tools of the stub mcp server {string} of the plugin {string}`. An `@adapter-only` scenario can also wait with `pi-mcp-adapter has listed the tools of the stub mcp server {string} of the plugin {string}`.
- These stand-ins are `.ts` files under `features/lib/`, never under `features/support/`, because cucumber imports `features/support/` into every worker (D-CF1-17). A Pi extension under `features/lib/` carries `// fallow-ignore-next-line unused-export -- Pi's --extension loader reads this default.` above its default export.
- The `fix-unicode-dashes` and `fix-smartquotes` pre-commit hooks rewrite feature files. So a feature file cannot pin a companion text that holds an em dash or a smart quote literally, such as pi-subagents' `Available agents:` lines. Only a step that projects such a character to a token, or reduces the text to facts that hold none, can compare that text.
- No step filters or deduplicates records. Since pi-mcp-adapter 6.0, a call through the `mcp` proxy runs the real tool as a nested Pi tool call. So a step lists both the `mcp` event and the event of the real tool, and the nested call's id is the `mcp` call's id followed by `/1`.

### Reset and CI

- The reset asserts a clean baseline. After the profile Pi stops, every pid that a stand-in recorded is dead within the same 10-second wait as a restart, and the script has no unused step. The `Before()` of the next scenario empties the sandbox.
- Under the builtin profile the shared Pi can start real stub processes. The reset asserts that no stand-in or stub process that the shared Pi started outlives its scenario.
- `npm run test:cucumber` installs the companions, then runs the adapter profile, then the builtin profile. `npm run test:cucumber:profile -- --profile <profile> <paths>` runs one profile on the paths given. Give paths to `test:cucumber:profile` only, because npm adds the arguments after `--` to the last command of a chain.
- The behavioral CI job runs as a matrix with a profile axis and `fail-fast: false` (D-CF1-16, DUAL-03). Each matrix item has a `profile`, a `shard`, and `paths`, and the job's name shows the profile and the shard. It has three legs: adapter lifecycle (`features/marketplace` and `features/plugin`), adapter components (the six function directories), and builtin all (`features`). Each leg receives its profile and paths through the `PROFILE` and `SHARD_PATHS` variables of `env:` and calls `npm run test:cucumber:profile -- --profile "$PROFILE" $SHARD_PATHS`. Each leg's timeout is at least 1.5 times its measured run and never below 15 minutes. `npm run check:features` dry-runs every scenario, so a leg hides no unused step. A new function directory joins the paths of the adapter components leg in `.github/workflows/ci.yml`. `test/architecture/behavioral-shard-coverage.test.ts` fails when a profile of `cucumber.json` other than `default` has no shard, and when a feature file is in no shard of a profile or in two shards of one profile.

### Arguments that start with `!`

- In a skill or a command, an argument word that starts with `!` reaches the model as `\!`, as in Claude Code (`xM`, D-CF1-01). A scenario that types such an argument states the backslash in its expected value. This is upstream parity, not a defect.
