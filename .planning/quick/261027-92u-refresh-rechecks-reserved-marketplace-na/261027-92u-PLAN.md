<plan_decisions>
These are settled for this plan. Task 3 records them in 05-CONTEXT.md as D-PL5-27.

- **Scope, all source kinds.** The refreshed manifest's `name` goes through `reservedMarketplaceNameRefusal(name, recordedSource)`, exactly as the add does (D-PL5-01). The only exemption is a github source owned by anthropics. Hosted, path, and url sources are never exempt.
- **Row shape.** The update keeps its existing failed row. That row is the failed marketplace block with one failed child row: `marketplaceSubject: true`, so the JSON id is the bare name; reason `invalid manifest`; and a cause chain that starts with the update's own frame and ends with Claude Code's sentence. Upstream reports the same failure as `Failed to refresh marketplace '<name>': <sentence>`. The frame is `Failed to update marketplace "<name>".` for path and hosted sources, and `Marketplace "<name>" clone advanced but manifest could not be persisted.` for github and url sources. Do not strip the frame. Do not add a reason token.
- **Hosted.** The refusal runs inside `refreshHostedCatalog`: after the staged download validates, before the rename. The stored catalog and the record stay byte-identical, and the staging directory is removed. Upstream also discards its temp download.
- **Path.** The manifest is read in place. The refusal runs after the read and before the record is stamped, so the record keeps its baseline and timestamp.
- **Git (github and url): the state record stays untouched, and the checkout is not restored.** The refusal throws after the read and before the stamp: no `lastSuccessfulManifest` or `lastUpdatedAt` write, no state save, no autoupdate cascade, no completion-cache drop. The checkout stays at the fetched commit. Reasons:
  1. Upstream refreshes a registered github clone in place (its `<owner>-<repo>` folder) and neither deletes nor restores it on this refusal.
  2. The in-place D-14 refresh already leaves the checkout advanced when a refreshed manifest is invalid. That is the MU-5 `clone advanced` path, and the refusal takes it unchanged.
  3. A restore would need a HEAD read before every git refresh, plus a path for a failed restore. And `plugin update`'s PUP-2 sync advances the same checkout with no name check, so a restore could not keep the refused commit out anyway.
  - Known divergence: upstream refreshes a `git` source into a `temp_git_*` clone and discards that clone on this refusal, so its old cache stays. Our `url` kind keeps the advanced checkout instead. Flag this choice for user review in the SUMMARY.
- **Error class.** `ReservedMarketplaceNameError` moves to `shared/errors.ts`, so add, the hosted refresh, and update throw one typed class. That matches the convention that every domain error lives in `shared/errors.ts`. It cannot live in add.ts: hosted-catalog.ts importing add.ts would close a cycle.
- **`refreshHostedCatalog` signature.** It takes `source: HostedManifestSource` in place of `url`, so the refresh knows the source kind the refusal sentence depends on.
- **Out of scope:**
  - `plugin update`'s PUP-2 marketplace sync (`orchestrators/plugin/update-flow.ts`), which belongs to Phase 7 per ROADMAP. It still re-reads a refreshed github or url catalog without the check. Upstream's plugin-update refresh warns and continues with cached data.
  - The shared `refreshGitHubClone` and `refreshUrlClone`.
  - The other MKTNAME-01 rules: look-alike names, other spellings, package-manager names, the `claudeai-` prefix, the `<owner>-<repo>` folder rule, and the load-time refusal.
  - Edits to CHANGELOG.md, BACKLOG.md, PROJECT.md, and AGENTS.md. Their proposals go in the SUMMARY.
  - Merging and pushing.
