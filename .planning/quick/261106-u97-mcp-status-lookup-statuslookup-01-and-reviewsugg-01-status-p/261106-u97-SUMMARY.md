## Questionable choices

| Choice | Alternatives | Why questionable | Severity |
| --- | --- | --- | --- |
| `status unknown` (`no-snapshot`) for a failed read of Pi's registry or tool list | `not loaded`; `not connected` | `status unknown` is less specific. But `not loaded` claims that Pi lists no registration, and the docs pair it with "Run `/reload`", which does not help a read failure. `not connected` claims that Pi lists the registration. | low |
| The guard sits in the platform reader (`createBuiltinMcpStatusReader`) | A catch around `reader.lookup` in `builtinStatus` (`info-mcp-status.ts`) | A catch in the stamp would also cover a future reader that throws. The reader guard keeps the "a lookup never throws" contract at the Pi boundary and mirrors `recordedMcpServers`. | low |
| One debug line per failed lookup | One line per info command | A plugin with many servers writes one line per server. The line is env-gated, and a per-command line would need state that crosses lookups. | low |
| The `none` arm keeps pi-mcp-adapter's reader | A `none` arm with no reader that stamps `status unknown` directly | The reader-less arm states the meaning in the type. Keeping the reader keeps today's output and the unedited MSEL-01 table in `info.test.ts`. | low |
| Three arms (`adapter`, `none`, `builtin`) | Two arms (`adapter \| none` share one shape) | `adapter` and `none` have the same shape. Three arms match the must-have "one arm per `ActiveMcpImplementation`" and let a future `none`-only field land without reshaping. `mcpStatusLookup` groups the two in one `case` (sonarjs rejects identical case bodies). | low |
| Unbranded readers | Brand the readers so that a hand-built literal cannot pair a reader with the wrong implementation | Only tests build literals. Branding would change both reader factories and every test seed. | low |
| `mcpStatusLookup` in `platform/mcp-status.ts` | In `orchestrators/plugin/info-mcp-status.ts` | The builder sits beside `McpStatusLookup` and `McpStatusReaders`, and `info.ts` takes a value import from `platform/`. The orchestrator module would keep the type's builder away from its definition. | low |
| The harness: a hidden tool with a throwing namespace name | No scenario (no harness path makes `getMcpServers()` throw in a live Pi) | The scenario covers the tool-list path end to end. The registry-throw path is covered by unit case G1 only. | low |
| Keep `not loaded` for the resolved leading `~` | `failed`; an `unsupported command ~` or `args ~` entry | `failed` would claim a connection attempt. An unsupported entry would add a closed-set token and change install-time output. `not loaded` matches "Pi lists no registration". | low |
| `mcp-status.test.ts` keeps its cases at the top level although the module now has two entrypoints | One `describe()` per entrypoint (typescript-unit-tests `cases.md`) | Wrapping the existing tracker cases would re-indent the whole file. The sibling `mcp-builtin-status.test.ts` also has several entrypoints at the top level. | low |
| The T1 `@ts-expect-error` directives sit inside each literal, above `projectTrusted` | Above the `void (` statement, as the plan's model `staging-warnings.test.ts:15` does | On a multi-line literal, TypeScript reports the excess property at its own line, so a directive above `void` would go unused. A one-line literal does not fit in 100 columns. | low |
