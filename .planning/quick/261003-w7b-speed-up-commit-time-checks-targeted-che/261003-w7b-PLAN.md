# Speed up commit-time checks

<objective>
Make commit-time checks proportional to the change, serialize the expensive full runs across
worktrees, record every run so later tuning is measured, stop agents from paying for the
same checks twice, and keep passing check output down to failures and warnings so it does not
fill agent context.

Purpose: 36 of today's 73 commits fell through `planChecks()` to the full path because one
input was not a source/test pair (`.planning` data, type-member contract JSON, unpaired tests
and test support, docs, analyzer scripts). Pre-commit runs took a median of 27 minutes; agents
spent 9.5 hours in sleep/grep poll loops and re-ran ESLint and type checks right before
committing. A passing full `npm run check` also prints about 9,700 lines (about 750 KB), and
almost all of that is passing-test and Fallow report noise. Covers W7B-01..W7B-07 below.

Output: rule-based selection, a full-run lock, and a JSONL run log in `scripts/check-changed.mjs`;
controls for all of it in `scripts/check-changed.negative.mjs`; a failure-focused test reporter
with its own control; quiet Fallow gates; updated guidance in AGENTS.md,
skills/local-verification/SKILL.md, and CONTRIBUTING.md.
</objective>

Task 3 choices, each measured during planning (W7B-07):

- The test reporter is a small custom module, because no built-in reporter fits. `spec`, `tap`,
  and `junit` print every test. `dot` prints a dot per test and drops both the count summary
  and the coverage-threshold message, so a threshold failure would exit 1 with no explanation.
  The custom reporter passes failures through Node's own `spec` reporter, so failure output
  stays Node's.
- `test:e2e`, `test:e2e:nightly`, `test:coverage:integration`, and `test:coverage:e2e` keep
  their reporters. They are outside the requested scope and outside `npm run check`.
- `fallow health` gains `--complexity`. That flag only selects report sections: the findings
  and the exit code are identical to a default run (measured with a lowered threshold: 65
  findings and exit 1 in both).
- No `fallow dupes` flag prints the clone report only on failure. `--top 0` withholds the
  clones on failure too, and every other format prints the clones on a pass. So the script runs
  dupes once with stdout discarded and re-runs it, with its report, only when that first run
  fails.
- The npm `> script` header lines that npm prints for each nested `npm run` stay (about 4 lines
  per member). Removing them would change the `check` chain that other gates parse.
