## Findings that shape the plan

- **Import today.** `readPassForImport` (`execute.ts`) builds `claims` from `marketplaceSourceClaims`, drops claims of a name in the scope plan's settings-name list (the WR-01 fix), and reads `marketplaceClaimConflicts` (WR-02). `executeScopedPlan` then renames each claimed marketplace and its plugin refs to the recorded name, rewriting `ref.raw` (6.12). `ensurePlannedMarketplaces` asks the planner's mismatch list first. A conflicted claim, or an own-name mismatch with no plugin (D-PL6-09), fails the block through `recordMarketplaceAddFailure`. An own-name mismatch with plugins gives each plugin a `{source mismatch}` row.
- **Reconcile and a config source change.** `plan.ts::diffMarketplaces` reports a declared name recorded with a different source as `source-mismatch`. The `apply-outcomes.ts` header calls it "planner-only, report-only". `reconcile/notify.ts::applySourceMismatch` renders `(failed) {source mismatch}`. `apply` never re-adds, and reconcile still aliases a config name to a recorded marketplace through a one-to-one source claim. After this plan, import follows Claude Code's startup reconciler for settings, while `pending`, `apply`, and the load keep the config contract. Those two divergences go to the SUMMARY. Neither `apply.ts` nor `notify.ts` changes: the scope fence keeps them out.
- **The `{marketplace not added}` brace cannot ride an import row.** It is one of three structural reasons that `ContentReason` excludes, so neither `MpFailed.reasons` nor a plugin row can carry it. Only the standalone `marketplace-not-added` notification renders it. Install's orchestrated marketplace-absent failure (`install-flow.ts`, the `marketplace-absent` case) returns the cause `Marketplace "<name>" is not added in the <scope> scope.` with no reason. That cause is the existing marketplace-not-found row that import shows.
- **Rows need a header.** `buildImportNotificationMarketplaces` renders a row only under a block that some marketplace outcome created (the WR-04 invariant). A reused marketplace has no outcome, so the not-added failures must create its `(failed)` block. The source-mismatch rows already work this way.
- **The lock-free seam is missing.** `addMarketplaceToState` refuses a name the scope records (MA-8, `newMarketplaceName`). For a git source it also refuses an existing `sources/<name>/` whose origin is another source (`recognizeLeftover` → `{stale clone}`). An in-place re-add must therefore take the record out of the working state and set the old clone aside first. Nothing under `orchestrators/marketplace/` does that today, and `removeMarketplace` would uninstall the plugins. Task 2 adds the seam to `add.ts`, and the re-add goes through `addMarketplace`'s orchestrated outcome, which import already dispatches.
- **Upstream E3, read from the 2.1.310 binary by the planner.** `W7r` sorts a declared name into `missing`, `sourceChanged` (known with another source), or `upToDate`. An entry with `sourceIsFallback` (the official marketplace that an enabled plugin brings) is always `upToDate`. `CRn` maps `sourceChanged` to an `update` action. For a path source (`directory`/`file`) whose path does not exist, it logs "declared path does not exist; keeping materialized entry" and skips the entry. Otherwise it calls `Lle(source)`. `Lle` first returns any known marketplace that already holds the source ("Source already materialized as ..."). Only then does it clone, overwrite the entry under the manifest name ("exists with different source — overwriting"), and delete the old clone unless the old source is a path.
- **The official marketplace.** `marketplaces.ts::planMarketplaceSources` plans `claude-plugins-official` only from an enabled plugin's ref, always with the built-in source, so it is upstream's fallback entry.
- **CR-01 still serves one case.** When the settings name recorded marketplace `Y` directly and the config declares `Y` under alias `X`, the repair would otherwise add `Y` beside `X`. The planner then excludes the declared `Y` as a claim candidate, plans `X` as an add, and every later `pending` shows `will add` for it. `configNamesByRecorded` and `declaredNameFor` stay.

## Planner choices (for review; copy into the SUMMARY's uncertain choices)

1. **D-PL6-17 row.** The reused marketplace gets no row of its own. When the settings enable plugins from it, their failed rows sit under a `(failed)` block for the settings name, because a cascade row needs a block. Alternative: a `(skipped)` block, which would claim that the settings name is added.
2. **D-PL6-17 cause.** Each plugin row carries install's cause `Marketplace "<name>" is not added in the <scope> scope.` and no brace, because `ContentReason` excludes `{marketplace not added}`. Alternative: also name the record that holds the source.
3. **D-PL6-17 skips the install call.** Import records the failure itself. Install's cross-scope fallback (D-MF-04) therefore cannot install `p@<settings name>` from the other scope's marketplace of that name. Claude Code's marketplaces are unscoped, so there a marketplace of that name would answer.
4. **D-PL6-19 row.** The re-added marketplace reads `(added)`. Alternative: `(updated)`. Upstream's reconciler counts it as updated, but `ImportBlockStatus` has no `updated`.
5. **D-PL6-19 when the new manifest names another marketplace.** The re-add fails closed as `invalid manifest` and restores the record and clone. Upstream would write the manifest's name beside the old entry.
6. **D-PL6-19 when the re-add fails.** Its plugins are blocked for this run, as after any failed add. Upstream's plugins would still resolve against the kept entry.
7. **D-PL6-19 keeps the record when the new source is recorded under another name** (`Lle` checks the source before the name). Planner-inferred parity: the user named only the missing-path case.
8. **Kept records and the repair.** A kept record reads `(skipped) {already added}`. When the config lacks the name, the existing repair declares the settings source, and the next `pending` shows `{source mismatch}`. Nothing is torn down.
9. **The official marketplace keeps `{source mismatch}`.** It is unchanged, because the user's decisions cover `extraKnownMarketplaces` entries only. Upstream treats it as up to date (`W7r`: `sourceIsFallback`). Follow-up candidate.
10. **The post-pass writes only the base layer.** A local-layer declaration of the old source still wins the merged view, so the next load reports `{source mismatch}`.
