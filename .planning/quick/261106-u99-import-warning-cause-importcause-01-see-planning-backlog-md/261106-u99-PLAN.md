<objective>
IMPORTCAUSE-01: an import whose plugin is not installable records the warning cause `Plugin "hello" is not installable: \n\ncause: Plugin "hello" is not installable: `. The not-installable message appears twice, and its reason list is empty. `test/orchestrators/import/execute.test.ts:3593` pins this text today (the MREC-06 real-wiring case).

The planner traced the cause at `19f3630`. See "Planner's trace" below. The import does not build the text. `dispatchFailedOutcome` copies install's orchestrated `outcome.cause` into the warning without change. Install builds that string with `formatOrchestratedCause`: the message, a blank line, and then a cause line whose first link is the same message again. The reason list is empty because `requireInstallable` writes the message from the resolver notes. An sse server under Pi's built-in MCP has no note: its signal is only in `unsupportedKinds`, which the warning's `reasons` already narrow to `unsupported mcp`.

The fix follows the backlog's direction: build the cause once from the narrowed reasons, as install does. The import builds each warning's cause from the typed `PluginShapeError`, one time:
- For an uninstallable plugin: install's not-installable wording (`shared/errors.ts` `buildPluginShapeMessage`, about line 1245, PR-6) over the same reasons that `narrowResolverReasons` gives the row (`install.messaging.ts`, about line 371 and lines 613-677).
- For a plugin the marketplace does not list: the error's own message. This is the same repetition in the sibling arm of the same switch.

Purpose: the warning's cause states the refusal once, in install's words, and names the reasons the row shows.

Output: Task 1 (tracer) fixes the uninstallable arm end to end, through the real-wiring MREC-06 path. Task 2 fixes the not-in-manifest arm, removes the import's read of install's formatted string, and corrects the doc comments that describe that read. No cucumber scenario is added, because no user surface shows this field (see Disposition 5).
</objective>
