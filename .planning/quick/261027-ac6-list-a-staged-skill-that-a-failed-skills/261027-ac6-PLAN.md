## Planner findings

- **Where `leaks` comes from.** `shared/notification-resolve.ts::resolveFailure` sets `leaks` from `manualRecoveryLeaks(cause)` of the row's own cause only. It never reads a rollback phase's cause. The resolved `failure.leaks` feeds both the text line (`notification-grammar.ts::composeFailureLines`, `    leaked: <leak>`) and the JSON `leaks` (`notification-json.ts::wireFailure`), which the cucumber `leaks` cell reads.
- **How a leak is named elsewhere.** The only AS-7 leak producer is `ManualRecoveryError` through `errorWithManualRecovery`, used by the mcp bridge's `replacePreparedMcp` with entries such as `failed to restore mcp-adapter.json at <path>: <message>`. The workflows undo names its leftovers in a `WorkflowsUnstageFailureError` message, and the agents bridge in `appendLeaks` text; neither reaches `leaks`. The `leaks` contract (`ResolvedFailure` doc, `docs/json-output.md`: "Paths left behind by failed cleanup, after redaction") is a path. `RunPhasesResult.leaks` (AS-5) is never filled.
- **Why the leak is empty today.** `install-outcome.ts` `skillsPhase.undo` calls `bridges/skills/unstage.ts`, which throws the raw fs error at the first removal it cannot finish. The ledger stores that error as the `skills` RollbackPartial cause. No `ManualRecoveryError` exists anywhere on the row.
- **Why the leak must ride the phase cause.** Import rebuilds its failed row's head from a string (`execute.ts::pushUnexpectedFailure`), so a leak on the row cause would need an `execute.ts` edit. Import and apply both pass every rollback phase cause through `shared/redact-absolute-paths.ts::redactCauseChain` (module-private `redactedRollbackPartials` in `execute.ts` and `reconcile/apply.ts`). `redactCauseChain` rebuilds plain `Error`s, so it drops the class today. If it keeps a `ManualRecoveryError` link with its leaks redacted, the leak reaches both surfaces with no edit to `execute.ts` or `apply.ts`.
- **No second link.** `errorWithManualRecovery` wraps the error, which repeats its message as a second cause link. That would change every `[skills]` phase cause from one link to two (eight scenario cells, three apply.test.ts cases). The undo therefore throws a `ManualRecoveryError` that stands in for the bridge error: same message, no cause. The bridge's removal and lstat errors carry no cause, so the chain the row shows does not change.
- **Who calls the skills unstage.** Only `install-outcome.ts` (this undo) and `orchestrators/marketplace/shared.ts` (uninstall, disable, update, reinstall). Reinstall maps any `ManualRecoveryError` to `{rollback partial}` (`reinstall-record.ts::typedReinstallReason`), so the bridge stays unchanged and only the install ledger's undo changes.
- **Tests that pin a real skills undo failure.** Only the three MIM-03 cases in `test/orchestrators/reconcile/apply.test.ts` (read-only directory through the real ledger) gain a `leaked:` line. `test/orchestrators/import/execute.test.ts`, `install-flow.test.ts` (the retry case replaces the undo), `enable-disable.test.ts`, `prune.test.ts`, and the notification suites use synthetic partials with plain `Error` causes and do not change.
- **Generated skill names.** `demo-skill` and `lib-skill` in the scenarios, `hello-tool` and `bar-tool` in apply.test.ts, `empty-alpha` and `empty-beta` in install-outcome.test.ts (`generatedSkillName` elides a matching plugin prefix; skills discovery sorts by `localeCompare`, so `empty-alpha` is removed before `empty-beta`).
- **Baselines (HEAD `3954e584`, Node v26.12.1, uid 1000).** `npx cucumber-js --name 'rollback cannot finish|cannot finish the rollback'` selects the eight read-only skill scenarios (one install, four import, three apply) and passes 8/8 in about 6 s. Every grep gate below reads 0 at HEAD.

## Planner choices (for review)

1. The leak is the skill directory's path (`<scope root>/pi-claude-marketplace/resources/skills/<name>`), as the `leaks` contract and the `leaked: <path>` line read. It is not mcp's `failed to restore <file> at <path>: <message>` sentence; the error stays on the `[skills]` phase row.
2. `import` and `apply` show the leak cut to its last segment (`demo-skill`), as they cut every other path on the row (D-PL6-12, T-55-02-02). `install` shows the full path.
3. The leak rides the skills phase's cause, not the row cause and not `RunPhasesResult.leaks` (AS-5), so `execute.ts` and `apply.ts` stay unedited. The leak data still passes through their existing `redactedRollbackPartials` at runtime.
4. The stand-in `ManualRecoveryError` keeps the bridge error's message and drops its stack and errno fields. Nothing downstream of the ledger reads them.
5. Only directories that an lstat (`pathExists`) finds after the failed undo are listed. If that check itself throws, its error becomes the phase cause. In practice it is the same error the undo hit on the same directory.
6. `redactCauseChain` keeps every `ManualRecoveryError` link it rebuilds. An import or apply row whose own chain holds one (an mcp restore that leaked while another undo also failed) now lists those leaks too, redacted. No test or scenario has such a row.
7. Only the skills undo produces a leak, because D-PL6-20 names skills. A failed commands, agents, hooks, mcp, or workflows undo still leaves `leaks` empty.
8. Standalone `enable`, `bootstrap`, and an autoapply load render the same ledger rows, so they list the skill too. No scenario or unit case pins a real skills undo failure there.
9. Scenario titles stay unchanged, so the `--name` filter above still selects the eight scenarios.
10. `resolveFailure` lists a path once (first occurrence), as `errorWithManualRecovery` dedupes leaks (F-5).
