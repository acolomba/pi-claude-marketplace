# Quick task 261025-n1z: one `apply` moves a plugin and the newer dependency it needs (APPLY1-01)

## Decision

APPLY1-D1, the user's option C (2026-10-25). An update is an install of a
newer version after removing the old, and a fresh install converges on its
closure in one run, so the catalog moves run as one cascade:

- dependencies move first, in post-order;
- a dependent held for a dependency's version is released when the moves
  planned with it enabled satisfy it, and `pending` previews the same cascade
  through the same function (`settleMoveCascade`);
- a move that waits on a failed move is not made and reports `{dependency failed}`;
- a dependent whose own move fails after its dependency moved keeps the
  dependency moved and is disabled with the marker when its copy's
  declarations reject the moved dependency; a later `apply` enables it only
  once its move lands (no flip-flop);
- no pre-move disable when the cascade satisfies the range; net rows.

The reverted planner release loop (121c6168) is not reintroduced: the release
is judged on moves planned with the released set enabled, the set only
shrinks, and `apply` judges the outcome on moves that landed.
