# Quick Task 260913-n7w

Fix the FIFO state-server reader pairing race.

## Problem

PR #183 is red. Three jobs (`npm run check`, `direct coverage`, `sonarcloud`) fail on one
test, and `sonarcloud` failed again on an explicit rerun, so it reproduces on GitHub
runners. The cause is not the CI-hardening work in that PR. It is
`tests/orchestrators/plugin/state-fifo.ts`, added by commit `147b63f4` on this same branch.

The harness header states an invariant that is false. It claims "Each open pairs exactly one
reader with one writer." A FIFO has no such pairing: the kernel keeps **one** pipe object per
FIFO inode, shared by every open of that inode, and EOF is a property of the inode's writer
count re-evaluated at each `read(2)`. The serve loop's next `open(fifoPath, "w")` revives
that writer count, cancels the EOF the previous reader was about to observe, and appends the
second payload to the first reader's `readFile`. Downstream `JSON.parse` then throws
`Unexpected non-whitespace character after JSON at position 475`.

Measured in RESEARCH.md: **10 failures in 80 runs** under 64-way CPU saturation on a 28-core
box. Unloaded it passed 40/40, and pinned to one core it passed 60/60 — which is why the
original 25/25 proof said nothing.

## The settled design — do not re-open it

Read `260913-n7w-RESEARCH.md` section 6 for the mechanism, the correctness proof, and the
exact server source.

Retire each FIFO inode from the namespace with `rename` **while the server still holds it
open for write, before the payload write, not after the close**. The already-paired reader
keeps its fd and still receives its payload, but nothing can reopen the retired inode by
name, so its EOF is guaranteed. The server's next iteration then opens whatever fresh FIFO
the rename installed at the state path.

Measured 160/160 under the identical saturation that breaks the current design. One extra
syscall per payload. The header's "nothing here polls, sleeps, or retries" property survives.

Two things are already refuted with data. **Do not revive either.**

- **ENXIO polling** is worse than the bug it would replace: 17 failures in 100 under the same
  load, every one `Unexpected end of JSON input`, because the probe is destructive — open
  plus close hands a parked reader an empty payload. A reader blocked inside
  `open(O_RDONLY)` also suppresses ENXIO, so the probe cannot tell "previous reader still
  draining" from "next reader already waiting".
- **Unlink plus mkfifo** is silent rather than loud: the path is briefly absent and
  `loadState` maps `ENOENT` to the default empty state without throwing
  (`persistence/state-io.ts:381-391`), so the test would get a wrong answer that still
  passes. Only `rename`, which is atomic, is admissible.

## Decisions taken at planning time

**The `served:N` invariant is restored by the fix; it needs no separate work.** RESEARCH.md
section 4 found a second, previously unreported defect: under the bug the server reported
`["ready","served:1","served:2"]` and exited 0 with only one reader ever existing, because
`served:N` counts the server's *write-opens*, which the bug decouples from reads. That is why
the consumers' `deepEqual` on `messages` does not catch the failure and only the downstream
`JSON.parse` does. After the fix, a write-open can no longer complete without a distinct
reader pairing on a distinct inode — each inode is retired from the namespace immediately
after it pairs — so `served:N` is once again the exact read count. The new gate's
post-`complete` `messages` assertion is what pins it.

**The over-read hang is a known limitation, not a regression.** An orchestrator that reads
more times than there are payloads blocks in `open` forever (the server has already exited,
so its watchdog is cleared) and the test hangs to its 60 s timeout instead of failing loudly.
This is pre-existing and every candidate design preserves it. Record it as one plain sentence
in the harness header. Do not build a timer to close it.

**Litter is prevented by the rename itself, and proved by the gate.** Each `rename` consumes
one spare name and unlinks the inode it replaces, so N payloads create N spares and consume
N. A clean run leaves exactly `state.json`, still a FIFO, and nothing else. Unconsumed spares
can only survive a watchdog exit or a `kill()`, and on both of those paths each consumer
`rm -rf`s its cwd in `finally` — so add no cleanup code, and prove the claim instead with a
`readdir` assertion in the new gate.

**Spares are named `.state-fifo-spare-N`, as hidden siblings of the state path.** `rename`
needs the same filesystem, and a sibling is one. The leading dot matches the `.state-lock`
precedent at `persistence/locations.ts:47`. Nothing in production enumerates `extensionRoot`
itself — re-confirmed by grep this session, every `readdir`/`opendir` call site targets a
subdirectory (`pluginClonesDir`, `resources/skills`, `resources/prompts`, `hooks/`, `data/`)
— so the transient siblings are invisible to the code under test.

**The gate lives at `tests/architecture/state-fifo-pairing.test.ts`.** A file under
`tests/orchestrators/plugin/` would demand a production module at
`extensions/pi-claude-marketplace/orchestrators/plugin/state-fifo.ts`, which does not exist,
and would fail `npm run test:corresponding` with `unexpected-test`
(`scripts/check-corresponding-tests.mjs:10,166-170`). `architecture` is one of the four
exempt roots and is inside the `npm test` glob, so a regression surfaces in the fast loop
rather than only in `test:integration`.

**The gate's first assertion sits between its two reads, which is a deliberate departure from
arrange/act/assert.** Under a broken server the first read returns both payloads and then the
server exits; the second read would block forever on a path with no writer left, turning a
clean one-second failure into a 60-second timeout. Asserting the first payload before issuing
the second read keeps the failure fast and legible. Say so in a comment so nobody "fixes" it
back.

**The gate is written first and observed failing.** That is the plant-the-violation proof this
repository requires (`CONVENTIONS.md`: a gate wants a test that plants the violation, and
`import-x/no-cycle` is the recorded case of a gate that was configured-but-inert). Writing it
first gets the proof for free, with no `git stash` and no file swapping. Task 1 therefore
commits nothing — the tree is briefly red by design, and Task 3 makes the single commit.
