<objective>
Make the resolver return `unavailable` for a plugin that has at least one unsupported component and nothing Pi can install. Today `decideResolution` in `extensions/pi-claude-marketplace/domain/plugin-resolver.ts` returns `partially-available` whenever `partial.unsupported` is not empty. So `/claude:plugin install --partial` admits such a plugin and installs nothing, and `list` and `info` call it partial. In the official Claude marketplace this covers 14 of 317 plugins: the 13 Anthropic LSP plugins and `theme-examples`.

Purpose: the user decided this rule (locked). Claude Code installs these plugins because it hosts LSP servers and hook modules. Pi hosts none of their components, so the divergence is a Pi capability gap. This plan only moves Pi's own word for it from `partially-available` to `unavailable`.

Output: five tasks, each run in a fresh context and each ending in one commit. The run order is 1, 2, 3, 5, 4: Task 5 runs before Task 4, so that the full gate of Task 4 stays the last step. Task 1 (tracer) ships the resolver change, its unit proof, and two scenarios for an LSP-only plugin. Task 2 makes an unavailable row show each kind's own reason. Task 3 gives the fixtures of 12 other test modules a supported component, so they keep testing the partial paths. Task 5 records the rule as the decision `D-NSC-01` and brings every current spec, doc, and comment in line with it. Task 4 adds the README lines and the CHANGELOG entry and runs the full gate.

User decisions of 2026-11-25 on the first draft of this plan (locked):

1. USER-1, supported MCP server. A server counts as supported when it passes the neutral verdict: it is a key of `declaredMcpServers` that `droppedMcpServers` does not name (D-P3-01). `partial.mcpServers` is not read here, because it is the subset pi-mcp-adapter supports (MSEL-04).
2. USER-2, truthful reasons. A plugin that is unavailable only for its unsupported kinds shows the reason token of each kind, the same closed token the kind has on a partial row today (D-90-05), on `list`, `info`, and `install` rows. It never shows `unsupported source`. `no supported components` is not a token and changes no row.
3. USER-3: the README sentence stays, in both languages.
4. USER-4: the CHANGELOG bullet carries no pull request number.

User request of 2026-11-25 after Task 1 was merged (locked):

5. USER-5, consistency. Every current spec and doc states the rule: the PRD rows it contradicts (PR-3 and its siblings), a new decision row in `.planning/PROJECT.md` with a durable ID, the output catalog, the messaging style guide, the compatibility docs, both READMEs, and the code comments and help text that give a structural defect as the only meaning of `unavailable`. The comment of `decideResolution` and the new unit and scenario titles cite the ID. Historical records are not rewritten: `.planning/milestones/`, `.planning/phases/`, `.planning/reviews/`, `.planning/research/`, `docs/research/`, `docs/plans/`, and archived SUMMARY and CONTEXT files. Task 5 carries this out.

How this plan carries out USER-2:

- The closed `Reason` set has no token named `mod` or `themes`. The tokens a partial row shows today come from `narrowUnsupportedKinds`: `lsp` for `lspServers`, `unsupported hooks` for `hooks`, `unsupported mcp` for `mcpServers`, `options not set` for `userConfig`, and `unsupported component` for every other kind (D-90-05). So a hooks-module-only or themes-only plugin reads `(unavailable) {unsupported component}`.
- An unavailable resolution carries only notes, so the kinds travel in the notes. The new arm names every unsupported kind: a kind whose stage writes no note (a dropped hook, a blocked server, a bundle) gets a `contains <kind>` note. With that, the note `no supported components` is not needed, and this plan does not write it.
- The classifiers give kind tokens only when every note of the plugin names a kind. Beside a structural note, a `contains <kind>` note keeps reading `unsupported source`, as the SURF-01 rider of D-90-05 says.
