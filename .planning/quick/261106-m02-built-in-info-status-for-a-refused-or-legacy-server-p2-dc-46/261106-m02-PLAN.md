<objective>
Two fixes to the state that `/claude:plugin info` shows for a plugin's MCP servers under Pi's built-in MCP.

(a) P2-DC-46 / D-MB-29. When another Pi extension registered `plugin_<plugin>_<server>` first, Pi refuses this extension's registration (`MCP server "<name>" is already registered by extension "<path>"`). Today the step only debug-logs the refusal, so info's built-in row shows the other extension's server state (`connected`, `disabled`, ...). The user decided on 2026-11-06 (P2-DC-46 option 2, D-MB-29 Locked): the registration step remembers refused names for the session in the process-level state it already keeps (name owners and replaced names, D-MB-20, P2-DC-92), and info shows the existing token `not loaded` for them. No new closed-set token, message kind, or catalog change.

(b) W1. `builtinRecordedServers` (`info-mcp-status.ts:149-151`) reads `record.mcpServerConfigs` itself and falls back to `resources.mcpServers` for a record written before that key existed, because the synchronous stamp cannot call the asynchronous legacy reader. The registration step instead reads servers through `recordedMcpServers` and its legacy reader (MREC-01, MREC-02), so for such a record the step registers a server (for example one only pi-mcp-adapter blocks) that info never stamps. Route info through the same read so info lists exactly the servers the step registers.

Purpose: BLT-05 says info shows each built-in server's state; both bugs make it show the wrong state or none. The AGENTS.md behavioral-test rule requires each user-visible change to ship with a cucumber scenario that fails without it.

## Design (decided by the planner; listed as dubious choices in the return)

1. Refused names live in `platform/mcp-builtin-status.ts` as a module Set beside `replacedRegistrations`, with the same lifecycle: `noteRefusedBuiltinRegistration(name)` adds a name; `noteFreshBuiltinRegistration` and `noteReplacedBuiltinRegistration` also delete it (Pi accepted a registration of ours under that name, or the sync removed it). `builtinRegistrationRefused(name)` reads it. `noteBuiltinServerOwners` stays as it is. Every `registerMcpServer` throw counts as a refusal (another extension's name, a `-`/`_` namespace clash, a config Pi rejects); the code never matches Pi's message text.
2. The refusal is applied in `info-mcp-status.ts`, beside the D-MB-23 owner rule, not inside the status reader: order mcp.json override, then `ownedElsewhere`, then refused, then `reader.lookup`.
3. `withMcpServerStatus` becomes async and takes a fifth parameter, a port that reads one record's MCP servers, `(record: PluginInstallRecord) => Promise<RecordedMcpServers>` (`RecordedMcpServers` from `domain/mcp-implementation.ts`). `info-mcp-status.ts` no longer reads `record.mcpServerConfigs` itself. `info.ts` binds the port to the merged three-argument `recordedMcpServers(record, legacySource, createLegacyServersReader)` over the block's own source (marketplace name, marketplace record, plugin name, `locationsFor(scope, cwd)`), the same read the registration step makes. The port is called only under `builtin`, only for a stampable block with a record and an `mcp` list.
4. `recorded` and `re-resolved` answers stamp their servers by name; `unreadable` stamps `record.resources.mcpServers` (the step registers none of them, so they read `not loaded`, matching the record arm's MREC-02 fallback in `info.ts` `stateOnlyMcpEntries`).
5. The cucumber harness gets a load-time mode in the built-in stand-in: an entry of the stand-in's server list marked `first` is registered while Pi loads the stand-in, before any `session_start` handler, so the extension's own registration of that name is refused. Pi's loader applies a load-time `registerMcpServer` when the stand-in's factory commits, and it emits `session_start` only after every extension has loaded (`test/architecture/no-factory-time-probe.test.ts` header). The existing session-start behavior is unchanged for unmarked entries.
