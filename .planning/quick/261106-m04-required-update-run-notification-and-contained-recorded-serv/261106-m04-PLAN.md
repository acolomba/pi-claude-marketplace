## Design (decided by the planner; listed as dubious choices in the return)

1. `recordedMcpServers` takes the record's `LegacyServersSource` and a reader factory, `readerFor(source)`, in place of a built reader. The stored path needs the source for the clone-root check; a factory lets one source feed both the check and the reader, so a caller cannot pair a source with a reader built for another. The factory is called only for a record without `mcpServerConfigs`. No parameter has a default (typescript-unit-tests forbids defaulting a parameter to a live boundary). `isPluginRootContained`, `createLegacyServersReader`, `LegacyServersReader`, and `LegacyServersSource` keep their signatures.
2. Only the stored path gains the check. The legacy path already refuses through the production reader, and `mcp-verdict-read.ts`'s factory keeps its no-trace answer (no servers, no manifest read) as it is.
3. The refusal reuses `LegacyServersUnreadableError` with the reason `uncontained` and the same catch, so the stored refusal logs `recorded MCP servers unreadable: cannot re-resolve the MCP servers of <plugin>@<marketplace>: uncontained`. The message text is unchanged, so the three tests that pin it elsewhere stay as they are.
4. The registration step keeps its own pre-check and its debug line `its plugin root is outside its sources`. For a stored record it now walks the root twice; that is a few `lstat` calls per record per sync.
5. The scenario models the hand edit UF-1 guards against (`06-SECURITY.md` trust boundary "installation records to the legacy MCP reader"): a step copies the installed plugin directory under the sandbox home and points the record's `resolvedSource` at the copy. It carries `@mcp`: the expected row is the same under both implementations. It discriminates under the adapter profile only, because under Pi's built-in MCP the recomputed and the stored verdict agree for this server.
6. The harness's record reader and writer move from `features/lib/mcp-builtin-earlier-record.ts` into a new `features/lib/installation-record.ts`, named for the thing it reads, so the new rewrite does not land in a module named for earlier-release records and nothing is copied (fallow dupes).
