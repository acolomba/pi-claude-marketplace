# Quick Task 260913-f6a

Gate the two SonarQube workflow findings, `githubactions:S6505` and `githubactions:S7637`.

## Problem

SonarQube IDE reports two MAJOR rule violations in `.github/workflows/*.yml` that nothing
in the repository gates:

- `githubactions:S6505` -- package manager scripts run during installation. 8 bare `npm ci`
  calls.
- `githubactions:S7637` -- external actions are not pinned to a commit hash. 3 external
  action references.

The gap has one root cause: `sonar-project.properties` sets
`sonar.sources=extensions/pi-claude-marketplace`, so SonarCloud's CI analysis indexes zero
`.yml` files. Both findings have only ever appeared in the editor, never in a quality gate.

All line numbers below were re-confirmed by live grep at planning time.

- `npm ci`: `ci.yml` 74, 95, 115, 165, 224; `e2e-nightly.yml` 31; `lint.yml` 38;
  `sonarcloud.yml` 59.
- Unpinned external actions: `lint.yml` 41 (`pre-commit/action@v3.0.1`), `lint.yml` 53
  (`fallow-rs/fallow@v3`), `sonarcloud.yml` 65 (`SonarSource/sonarqube-scan-action@v8`).

## Approach

Fix both findings, then gate each so they cannot return. S7637 is gated by zizmor, S6505
by a local script, because no off-the-shelf linter carries S6505.

### Corrections to the handed-down research -- read before starting

Five statements in the task brief were tested during planning and do not hold. The plan
below already accounts for all five; they are recorded so the executor does not chase a
green that is not there.

1. **The stated verification `uvx zizmor --config zizmor.yml --persona=regular
   .github/workflows/` exits 14, not 0.** The brief's config silences nothing but
   `unpinned-uses`. At the `regular` persona, two further audits fire inside
   `.github/workflows/` alone: `artipacked` x10 (`ci.yml` 64, 85, 105, 147, 214;
   `e2e-nightly.yml` 21; `lint.yml` 21, 47; `publish.yml` 39; `sonarcloud.yml` 47) and
   `self-repository` x1 (`publish.yml` 26). The brief's claim that the config "reduces
   findings from 23 to 3" is true only of the `unpinned-uses` audit in isolation, not of
   the run's exit code.
2. **The upstream zizmor hook audits more than the workflows.** Its `files:` pattern also
   matches `.github/dependabot.yml` and `.pre-commit-config.yaml`, which add two audits
   nobody has seen yet: `dependabot-cooldown` x2 and `archived-uses` x1 (the latter because
   `pre-commit/mirrors-prettier` is an archived repository).
3. **The four unwanted audits are filtered by severity, not by an ignore list.**
   `unpinned-uses` is the only **High**-severity audit that fires. The four declined ones
   are below it: `archived-uses` and `dependabot-cooldown` are Medium, `artipacked` and
   `self-repository` are Low. So `--min-severity=high` on the hook leaves exactly the S7637
   findings and nothing else -- no `ignore:` entries at all. This was measured three ways:
   the current tree reports exactly the 3 `unpinned-uses` findings; a simulated post-fix
   tree exits 0; and adding a brand-new workflow file to that tree still exits 0. That last
   case is the reason to prefer it -- a filename `ignore:` list makes every new workflow
   file fail the hook until someone remembers to add it. (`ignore: ["*"]` is not an escape
   hatch either: zizmor's parser rejects it with `invalid workflow filename`.)

4. **Editing `package.json` fires `npm-typecheck`**, contrary to the brief. That hook's
   `files:` pattern includes `package(-lock)?\.json`. `npm-format-check` also fires, since
   its pattern covers `scripts/.*\.mjs`. Budget for four local hooks, not two: `npm-lint`,
   `npm-format-check`, `npm-typecheck`, `npm-fallow`. Only `npm-coverage-direct` stays
   skipped.
5. **The `unused-file` risk from fallow is probably already moot.** `.fallowrc.json` lists
   `scripts/**` in `boundaries.coverage.allowUnmatched`, and
   `scripts/check-phase-06-hub-ledger.mjs` exists today with no `package.json` script and a
   green gate. Wire the script into `package.json` anyway, for the house convention, and
   still verify by running `npm run fallow`.

### What was proven to work

A simulated post-fix tree -- the 3 references pinned, the corrected `zizmor.yml` in place --
was audited over workflows plus `dependabot.yml` plus `.pre-commit-config.yaml` and exited
**0**. The three `actions/*` references stayed at `@v7` and passed, which confirms the
`ref-pin` policy and the instruction not to pin them. `yamlfmt` was run against the
corrected config and passed without stripping the quotes from the `"*"` key, so the
formatter will not corrupt it.

### Why a severity floor rather than an ignore list or dropping zizmor

The operator already reviewed zizmor's output and declined `artipacked` and
`self-repository`. A `--min-severity=high` floor honors that decision without encoding it
as a list of filenames that goes stale: a new workflow file, or a renamed one, passes
cleanly instead of failing until someone edits the config.

The tradeoff is that the floor is scoped by severity, not by audit identity -- if a future
zizmor release adds another High-severity audit, it will fire. That is a loud, reviewable
failure on a real supply-chain finding, which is preferable to the ignore list's failure
mode (silent drift plus a trap for every new file). The remaining alternative, a second
local script mirroring the S6505 one, drops the Python dependency but also drops every
other audit zizmor would ever catch; it is recorded here and not chosen.

## Tasks

1. **Fix both findings and add the zizmor config.**
   - Add `--ignore-scripts` to all 8 `npm ci` calls at the lines listed above. The repo has
     no install script of its own, and the one dependency that has one (`unrs-resolver`)
     runs a fallback that is not required when optional dependencies resolve normally.
   - Pin the 3 external actions, each with a trailing version comment, matching the form
     Dependabot's already-configured `github-actions` ecosystem maintains:
     - `lint.yml:41` -> `pre-commit/action@2c7b3805fd2a0fd8c1884dcaebf91fc102a13ecd # v3.0.1`
     - `lint.yml:53` -> `fallow-rs/fallow@30167b42257ded3bef683f6c91b4aa4017a1ff59 # v3.25.0`
     - `sonarcloud.yml:65` -> `SonarSource/sonarqube-scan-action@22918119ff8e1ca75a623e15c8296b6ea4fbe28f # v8.2.1`
   - Do **not** pin any `actions/*` reference. S7637 covers external actions only, which is
     why Sonar reports 3 and not 23.
   - Create `zizmor.yml` at the repository root with exactly this content, plus a comment
     block citing `githubactions:S7637` for the policy block and recording that the hook
     carries a `--min-severity=high` floor (see Task 3) so the declined Low/Medium audits
     never reach the gate:

     ```yaml
     rules:
       unpinned-uses:
         config:
           policies:
             "actions/*": ref-pin
             "*": hash-pin
     ```

     No `ignore:` entries. `yamlfmt` was verified not to strip the quotes from the `"*"`
     key, so the formatter will not corrupt this file.

   - verify: `uvx zizmor --config zizmor.yml --persona=regular --min-severity=high
     .github/workflows/ .github/dependabot.yml .pre-commit-config.yaml` exits 0. Separately
     confirm the S7637 scope held: `grep -c 'actions/[a-z-]*@[0-9a-f]\{40\}' .github/workflows/*.yml` reports
     0 for every file.

2. **Add the S6505 gate and prove it fires.**
   - Create `scripts/check-workflow-install-scripts.mjs`, following
     `scripts/check-corresponding-tests.mjs` exactly: a named export
     `checkWorkflowInstallScripts(projectRoot)` returning a violation array, a `main()` that
     parses an optional `--root <path>`, writes a pass line to `process.stdout` or one line
     per violation to `process.stderr` and sets `process.exitCode = 1`, and an
     `import.meta.url` guard so the module can be imported without running. Scan
     `<root>/.github/workflows/` for `.yml` and `.yaml` files. Flag any line matching
     `/(^|[^-])\bnpm\s+(ci|install|i)\b/` that does not contain the ignore-scripts flag.
     Comment the module with the rule key `githubactions:S6505`.
   - Conform to the `files: ["scripts/**/*.mjs"]` block in `eslint.config.js` (line 379):
     type-aware linting is disabled there and Node globals are declared, but
     `no-console` is a warning, so use `process.stdout.write` and `process.stderr.write` as
     the sibling scripts do.
   - Create `scripts/check-workflow-install-scripts.negative.mjs`, following
     `scripts/check-corresponding-tests.negative.mjs`: build a `mkdtemp` fixture holding a
     planted workflow whose run line installs without the flag, assert the gate reports
     exactly one violation, rewrite the same line with the flag, and assert it reports
     none. This is the planted-violation proof the repository's conventions require of a
     new gate; a check that only reads configuration does not count.
   - Wire both into `package.json` as `lint:workflows` and `lint:workflows:negative`, and
     append both to the `check` chain after `npm run lint`, matching how the two existing
     negative controls are wired.
   - Add a local hook to the existing `- repo: local` block in `.pre-commit-config.yaml`:
     id `workflow-install-scripts`, `entry: npm run lint:workflows`, `language: system`,
     `pass_filenames: false`, `files: '^\.github/workflows/.*\.ya?ml$'`.
   - verify: `npm run lint:workflows` exits 0 against the real tree, and
     `npm run lint:workflows:negative` exits 0, which is the proof the gate flags a planted
     violation. Then `npm run lint`, `npm run format`, `npm run format:check` and
     `npm run fallow` all clean -- `fallow` is the one that would report the new file as
     `unused-file`, so run it rather than assume.

3. **Wire the zizmor hook, extend the Sonar sources, and run the full gate.**
   - Add a new repo block to `.pre-commit-config.yaml` before the `- repo: local` block:
     `repo: https://github.com/zizmorcore/zizmor-pre-commit`, `rev: v1.30.1` (confirmed the
     latest tag), hook id `zizmor`, and
     `args: ["--no-progress", "--config", "zizmor.yml", "--min-severity", "high"]`.
     Override nothing else. The upstream definition already supplies `language: python`,
     `types: [yaml]`, `require_serial: true` and the `files:` pattern; `--no-progress` has
     to be repeated because overriding `args` replaces the upstream list rather than
     extending it.
   - In `sonar-project.properties`, change `sonar.sources` to
     `extensions/pi-claude-marketplace,.github` so SonarCloud indexes the workflows and the
     PR quality gate can see both rules.
   - verify: `pre-commit run --all-files` is clean. Expect `yamlfmt`, `yamllint`, `prettier`
     and the four local hooks to run; accept any `yamlfmt` rewrite, restage, and re-run
     until clean. Do not run `npm run check` -- nothing here touches `extensions/` or
     `tests/`, and Task 2 already ran every gate the changed files reach.

4. **Commit.**
   - Re-run `pre-commit run --all-files` immediately before committing, per the project
     rule that a failed hook means the commit did not happen. Note that the `prettier` and
     `yamlfmt` hooks write, so check `git status` after the commit and fix with a follow-up
     commit rather than amending.
   - verify: clean hook run, then a conventional-commit message under 72 characters with no
     milestone or phase reference.

## Watch item, not a gate

Adding `.github` to `sonar.sources` may surface `githubactions:*` findings beyond these two
rules on the next pull request. That cannot be measured locally -- it needs a SonarCloud
run. If the quality gate reports new rules, triage them separately rather than widening
this task.
