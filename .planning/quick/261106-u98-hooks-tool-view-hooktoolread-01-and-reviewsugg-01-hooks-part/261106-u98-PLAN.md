## Design (decided by the planner; the SUMMARY lists each under "Questionable choices")

1. A failed probe is one in which either read threw: `getCommands()` as well as `getAllTools()`. The backlog title names the tool-list read; a failed command read keeps the same possibly wrong answer for the generation, and the watched inventory treats both reads alike at no cost.
2. One debug line per generation, shared by `identify` and the probe, naming the first failure's message. Later failures of that generation, even with another message, write nothing. A retrying probe would otherwise write a line at every proxy-shaped event.
3. The view detects a failed read by handing `openNotificationSnapshot` a watched inventory that records each throw and throws it again, so `softDepStatus` handles it exactly as it handles Pi's own throw and the read order and counts stay the same. `SoftDepStatus` gets no failure field: every soft-dependency consumer shares it, and 261106-u9b edits it.
4. A failed probe returns its own answer for that one call, not a fixed `false`: the snapshot still uses the reads that succeeded (for example the adapter's `mcp-adapter` command when only the tool read threw).
5. The extending interface is removed; `identify` returns `McpToolIdentity`, and `claudeFormToolName(tool)` derives the name in `dispatch.ts` from the server segment as Pi's `createMcpToolName` folds it. Keeping the field and computing it in the view would leave a value that can disagree with `builtinServer`. Reading Pi's namespace `name` would add a second Pi field that Pi 1.5.0 builds from the same server name, while the matcher (`toolLiteralNames`) already models Pi's naming through the fold. The function keeps its name: "Claude's form" already describes what it returns, Pi's name included for a tool that no built-in server serves (D-P5-05).
6. `BUILTIN_MCP_SOURCE_PATH` lives in `platform/pi-api.ts`. The domain module cannot hold it, because `platform` may import only `shared` (`.fallowrc.json`), so `pi-api.ts` could not read it there. `shared/` could hold it, but the value names Pi's own loader path, which the Pi chokepoint module owns.
7. The single-line unit case compares the captured lines that start with `[mcp] mcp-tool-view:`, not every captured line, so a line that 261106-u9b may add inside `softDepStatus` for the same failed read does not break it on the combined tree. The two-generation case reads no snapshot and compares every captured line.
8. No new cucumber scenario. Nothing user-visible changes: the debug line goes to stderr only with `PI_CLAUDE_MARKETPLACE_DEBUG=1`, and in Pi 1.5.0 neither read can throw at tool-event time (Pi facts above; a stale generation's handlers return before any read), so no scenario can reach the retry. The name derivation and the constant keep the bytes the existing scenarios pin; the plan re-runs `features/hook/mcp-tool-names.feature` and `features/hook/tool-use.feature` under both profiles.
