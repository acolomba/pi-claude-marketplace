## Design (decided by the planner; the SUMMARY reports each under `## Questionable choices`)

1. One constructor, `legacyServersSourceFor(locations, marketplace, pluginName)`. "The scope" is the caller's `ScopedLocations`: the scope whose state file the caller read. Every caller already holds one, and the constructor cannot rebuild it, because a project location needs the cwd. A module-private `unique symbol` brand, as `persistence/locations.ts` brands `ScopedLocations`, makes the constructor the only way to build a source.
2. The source carries the plugin record the marketplace record lists under the plugin name, and every reader takes the source alone. A record passed beside the source was the pairing LEGACYSRC-01 names; a run-time identity check would keep the two arguments and only refuse a mismatch.
3. The constructor throws a plain `Error` when the marketplace record lists no such plugin (`the marketplace record <name> lists no plugin <plugin>`, no path). No production caller reaches it: each iterates `marketplace.plugins` or looks the record up first. Returning `undefined` instead would put a branch no input reaches at every iterating caller, and direct coverage requires 100% of branches. A plain `Error` suits an invariant that only a programming mistake breaks; no caller narrows it.
4. Scope agreement is part of the containment check. `owningRoot` refuses first when `source.marketplace.scope` is not `source.locations.scope`, so the source reads as `uncontained`. The constructor does not throw on it. A hand-edited state must not make `list` or `info` throw, and in the registration step a throw counts as a read failure, which keeps live registrations, and UF-1 forbids that.
5. The marketplace name is the marketplace record's `name`. Callers passed the `state.marketplaces` key, and two passed `mp.name`; the two are equal for every state this extension writes.
6. Two ports keep their shape. The degrade-baseline port `(record, marketplace, plugin)` stays: `recordDegradeBaselineReader` builds its source with the constructor from the port's marketplace record and plugin name, and passes the port's `record` to `degradeBaselineOf` for its basis only. The port is not a `LegacyServersSource`, and its only caller passes the same record object. The `readServers` port of `info-mcp-status.ts` stays `(record) => Promise<RecordedMcpServers>`: info's reader builds the source lazily from the block's own scope record and ignores the argument, which is the same record. Its test "MREC-02: under builtin the servers are read from the row's own record" keeps its meaning.
7. `ComposeInstalledListRowOptions` carries `marketplace` (the marketplace record from the plugin scope's state file) in place of `marketplaceRoot`, `marketplaceName`, `marketplaceSource`, `manifestPath`, and `record`. The row builds one source and takes its record from it. `list-flow.ts` and `edge-deps.ts` pass the record they iterate.
8. The type keeps the name `LegacyServersSource`, as the backlog entry names it; only the error gets a neutral name, as the item asks. Alternative: `RecordedServersSource`. Not taken, to keep to the stated scope.
9. The refusal error becomes `RecordedServersUnreadableError`, after the module and `RecordedMcpServers`. Its message says `cannot read`, because a stored record is not re-resolved.
10. The unreadable arm carries `reason: UnreadableMcpServersReason`, a union `domain/mcp-implementation.ts` owns (the domain cannot import the orchestrator). The members are `uncontained`, `not-in-manifest`, `unavailable`, `root-mismatch`, and `version-mismatch` (the refusals), plus `read-failed` (any other error). The registration step reads it. Every other consumer treats every reason alike, and the doc comment names them.
11. The readable arm keeps `kind: "recorded" | "re-resolved"`: both carry the same servers and bundle, every consumer reads them alike, and the kind tells a test or a reader which read answered (MREC-01 or MREC-02).
12. `mcp-verdict-read.ts`'s no-trace reader still answers no servers without the containment check, unchanged from today. Moving the check ahead of it would change the degrade baseline of an uncontained legacy record, which this item does not ask for.
