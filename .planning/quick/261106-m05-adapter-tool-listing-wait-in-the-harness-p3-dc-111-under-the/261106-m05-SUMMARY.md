# Quick 261106-m05: the tool listing waits for pi-mcp-adapter's tools (P3-DC-111)

## What changed

Commit d3e5e85, `test(mcp-server): wait for pi-mcp-adapter's tools when listing them`, changes two
harness files: `features/lib/mcp-implementation.ts` and
`features/step_definitions/mcp-server/listing.steps.ts`. The When `the user lists the mcp tools pi
offers` now calls `registryAfterListing()`. When Pi runs pi-mcp-adapter, that function reads the
registry probe every 50 ms (`POLL_MS`), for at most 10 s (`ADAPTER_TOOLS_WAIT_MS`), until Pi has a
tool of every stub server whose tools/list a stub logged. Then it returns `settledRegistry()`. The
built-in-only predicate became `isStubTool(implementation, ...)`. No step text changed, and no file
under `extensions/` changed.

## Root cause

- **The CI failure.** Run 41967152313, attempt 1, job 127046695523 ("behavioral tests, adapter
  components (Node 24)"), seed 944382, 434 of 435 scenarios passed. The failing scenario was
  `features/mcp-server/lifecycle.feature:392`, "A new session offers the plugin's tool again
  (BLT-01)". The failing step was `Then pi offers these plugin mcp tools:`
  (`listing.steps.ts:218`, assertion at `:230`). The actual rows were `[['tool','active']]`. The
  expected rows were `[['tool','active'],['mcp__plugin_demo_stub__echo','no']]`.
- **Which read failed.** The registry probe report, which the When stored through
  `settledRegistry()`. The scenario has no model turn, so the scripted model's tool list was not
  read. Nothing calls the adapter's `mcp` tool, so the adapter's `mcp` listing was not read either.
- **The mechanism.** Pi 1.5.0 `newSession()` stops the session, builds a new runtime with a new
  tool registry, and rebinds the extensions. pi-mcp-adapter 7.0.0's `session_start` registers
  tools before it returns only when it has a valid saved listing (`mcp-cache.json`). Without one,
  it connects to the server, lists, closes, saves, and only then registers the tools. All of that
  happens after the RPC answer. The adapter calls `owner.throwIfInactive()` before
  `saveMetadataCache()`. So a `session_shutdown` that arrives after the stub exited, but before
  the save, aborts the first session's initialization, and the listing is never saved. This
  aborted-save step is inferred from pi-mcp-adapter's code; the CI log shows only its effect.
- **Why no step waited.** The second `the mcp implementation has listed the tools ...` step comes
  after the new session. Its adapter branch is satisfied at once by the first session's tools/list
  line, while no stub runs yet. `settledRegistry()` returns once two reports 250 ms apart agree.
  Two reports without the tool agree while the adapter is still listing the stub again.

## Dubious Choices

| Choice | Alternatives | Why dubious | Severity |
| --- | --- | --- | --- |
| The wait lives in the When `the user lists the mcp tools pi offers`, not in the post-session listing Given | Make the adapter branch of `listingDone()` also require a tool in the registry | The Given still says the listing is done when the adapter has not registered the tools yet. A future step that reads the tools a different way after a new session would need its own wait | low |
| `adapterToolMissing()` checks every tools/list line in the whole scenario log, not only the lines since the new session | Count the lines after the session started | A scenario that lists a stub and then removes its plugin (no tool expected) under the adapter would wait the full 10 s before its Then passes. No current scenario does that; every listing use measured 253 to 516 ms | low |
| The forced race uses a 1 s stub delay and a deleted `mcp-cache.json`, not the natural shutdown-before-save timing | Reproduce on a loaded machine without edits | It forces the effect (no saved listing, slow relisting), not the inferred aborted save itself | low |
| `isStubTool("adapter", ...)` relies on the adapter profile's `toolNamePrefix` from the extension's domain module | Hard-code the `mcp__plugin_<plugin>_<server>__` prefix in the harness | The harness then shares the extension's naming. A naming bug in the extension would match itself, though the Then compares the exact tool name | low |
