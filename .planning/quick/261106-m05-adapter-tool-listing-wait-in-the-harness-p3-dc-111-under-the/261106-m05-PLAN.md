## Root cause (confirmed during planning)

**The read that fails.** The log of CI run 41967152313 attempt 1 is saved at
`$S/m05-job-log.txt`, lines 200 to 237. It comes from job 127046695523, "behavioral tests, adapter
components (Node 24)", and was fetched from the public Actions API. Every step passed up to
`Then pi offers these plugin mcp tools:` (`features/step_definitions/mcp-server/listing.steps.ts:218`).
Its assertion at line 230 found the actual rows `[['tool','active']]`, without the expected
`mcp__plugin_demo_stub__echo | no` row. So the read that missed the tool is the registry probe
report. `When the user lists the mcp tools pi offers` stored that report through `settledRegistry()`
in `features/lib/mcp-implementation.ts`. It is not the scripted model's tool list, because the
scenario has no model turn. It is not the adapter's `mcp` listing, because nothing calls `mcp`.

**Why the tool was missing.** These facts come from reading Pi 1.5.0 and pi-mcp-adapter 7.0.0:

- `node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session-runtime.js` `newSession()`
  stops the session (`session_shutdown`), builds a new runtime with a new tool registry, and rebinds
  the extensions (`session_start`). The RPC `new_session` handler in `dist/modes/rpc/rpc-mode.js`
  rebinds a second time.
- `node_modules/.cache/optional-peers/node_modules/pi-mcp-adapter/index.ts` `session_start` has two
  paths. With a valid saved listing (`<agent dir>/mcp-cache.json`), `getDeferredSessionSnapshot()`
  registers the tools before the handler returns. Without one, `startInitialization()` connects to
  the server, lists, closes, saves (`init.ts`, `saveMetadataCache`), and only then registers the
  tools. All of that happens after the handler returned, so after the RPC answer.
- `init.ts` calls `owner.throwIfInactive()` before `saveMetadataCache()`. So a `session_shutdown`
  that arrives after the stub exited, but before the save, aborts the first session's
  initialization, and the listing is never saved. The first listing step returns as soon as the
  stub logged a tools/list and its pid file is gone. That is the moment of this race. This step is
  inferred from code; the CI log shows only its effect.

**Why no step waited.**

- The second `the mcp implementation has listed the tools ...` step comes after the new session.
  Its adapter branch (`listingDone()`) is satisfied at once by the first session's tools/list line,
  while no stub runs yet.
- `settledRegistry()` returns once two reports taken 250 ms apart agree. Two reports without the
  tool agree while the adapter is still listing the stub again.
