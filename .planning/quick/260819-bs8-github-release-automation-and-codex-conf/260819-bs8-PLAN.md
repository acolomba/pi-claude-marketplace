# Quick Task 260819-bs8: GitHub release automation and Codex config tracking

## Task 1 - Create GitHub releases from the changelog on tag push

**Files:** `.github/workflows/publish.yml`

**Action:**

1. Tighten the tag trigger from `- "v*"` to `- "v*.*.*"`.
2. Append a `release` job after the existing `publish` job that runs
   `taiki-e/create-gh-release-action@v1` with `changelog: CHANGELOG.md`.

**Rationale:**

- The repository has 34 `v*` tags but zero GitHub releases. Every release since
  `v0.1.0` was tagged and published to npm without a releases-page entry.
- `v*` also matches GSD milestone tags. `v1.7` is already on the remote and
  `v1.8` exists locally; pushing one starts a full CI plus npm publish run that
  fails at the npm step. `v*.*.*` excludes both while matching all 32 release
  tags.
- `taiki-e/create-gh-release-action@v1` does changelog extraction and release
  creation in one step, so no hand-written extraction script is needed. Its
  parser, `taiki-e/parse-changelog`, was verified locally against this
  repository's `CHANGELOG.md`: it parsed all 32 version sections, matching the
  32 `v*.*.*` tags, with output byte-identical to a hand-rolled awk extractor.
- Relied-on defaults: `title` defaults to `$tag`; `token` falls back to
  `github.token`; `allow-missing-changelog` defaults to `false`, so a tag with
  no `CHANGELOG.md` section fails the job instead of publishing an empty
  release.
- `needs: [publish]` is deliberate. A release page must not announce a version
  that is not yet on npm.
- `permissions: contents: write` is scoped to the new job only. The
  workflow-level `permissions: contents: read` stays unchanged.
- `actions/checkout@v7` is required because the action reads `CHANGELOG.md`,
  and matches the version used elsewhere in the repository.

**Verify:** `yamllint .github/workflows/publish.yml` passes; the workflow-level
`permissions: contents: read` is unchanged; the `release` job declares
`needs: [publish]`.

**Done:** `publish.yml` triggers on `v*.*.*` only and carries a `release` job.

## Task 2 - Exclude the Codex harness directory from the hooks

**Files:** `.pre-commit-config.yaml`

**Action:** Add `\.codex/` to the top-level `exclude` regex on line 1.

**Rationale:** That top-level key applies to every hook, and it already
excludes `\.claude/`. `.codex/` holds the same class of content: generated
harness configuration and skill mirrors, not project source. Without this it
would be the only harness directory the hooks lint. This also removes `.codex/`
from the trufflehog scan, matching the existing treatment of `.claude/`.

**Verify:** `pre-commit run markdownlint-cli2 --files .codex/config.toml`
reports no files to check.

**Done:** `.codex/` is excluded from every pre-commit hook.

## Task 3 - Track the Codex harness configuration

**Files:** `.gitignore`, `.codex/config.toml`

**Action:** Commit the already-modified `.gitignore`, which drops the blanket
`/.codex` ignore and replaces it with granular `/.codex/gsd-*` rules mirroring
the existing `/.claude/` block, plus the files it un-ignores.

**Scope change from the original plan.** The plan opened expecting 85 files:
`config.toml` plus an 84-file `.codex/skills/spike-findings-pi-claude-marketplace`
mirror. That mirror was removed from disk in a separate session while this task
was in flight, so only `config.toml` remained to track. The skills mirror is
regenerated by `spike-wrap-up` from `.planning/spikes/`, which is intact, so
nothing is lost.

**Scope limits.** Do not stage: `.claude/settings.json`,
`.claude/commands/upstream-releases.md`, `.claude/jobs/`, `.sonarlint/`,
`.vscode/`.

**Verify:** `git status --short` shows the excluded paths still dirty or
untracked after the commit; `.codex/skills/gsd-*` stays ignored.

**Done:** `.gitignore` and `.codex/config.toml` are committed.
