## Upstream finding (claude-code-compat-research evidence record)

- **Question.** When Claude Code reads a plugin's `.claude-plugin/plugin.json` through a link, what
  boundary must the resolved target stay inside, and what happens when it leaves it?
- **Evidence.** Binary 2.1.310
  (`/home/linuxbrew/.linuxbrew/Caskroom/claude-code@latest/2.1.310/claude`), grepped 2026-10-27.
  `VJ` (read manifest) first calls `ows(containedIn, pluginDir, name, <manifest path>)`. Its
  helper `g9n` lstats each segment of the manifest path below the plugin directory and returns with
  no check when none is a link. When one is a link, `DHe(boundary, manifestPath)` realpaths the
  manifest:
  - ENOENT or ENOTDIR, then `stat` also missing: absent (a dangling link is no manifest);
  - any other realpath failure: escapes ("it could not be resolved");
  - a real path outside every boundary root: escapes ("it resolves to …, outside the <boundary>");
  - inside: `ngo` checks that the spelled and the resolved path are one file (dev and inode).

  An escape makes `ows` throw `Bz` ("plugin manifest not confirmed inside the plugin"), a
  containment error that fails the plugin's load. It does not read as a missing manifest. The
  read itself then opens the spelled path (`fNe`).
- **Boundary** (`q9n`; `k0` realpaths each root):
  - a cached copy: `[pluginDir]` ("plugin directory");
  - a plugin loaded in place from a directory marketplace, or after a failed cache copy
    (`containmentAnchorDir`): `[pluginDir, marketplaceDir]` ("plugin directory and its
    marketplace directory");
  - a link-farm producer: `[producerDir, pluginDir]`.
- **Confidence.** High for the walk, the realpath check and the load failure (code read directly).
  Medium for the in-place trigger (`eje`/`Am`, read by name only).
- **Boundary this plan uses.** The record's owning root (`installedCopyOwnerRoot`), as the user
  decided. For a path-source record (the marketplace clone) it equals Claude Code's in-place
  boundary. For a git record (all of `plugin-clones/`) it is wider than Claude Code's
  plugin-directory boundary: a link from one copy into another part of `plugin-clones/` is followed
  here and refused upstream. License: the recorded user decision (D-PL2-13 reversal, 2026-10-27).
- **Hardening compared.** Upstream reads the spelled path after its identity check. This plan reads
  the resolved path after the containment walk, so it is no weaker against a swap of the original
  link.

## Caller trace: what each caller does with `unusable` (D-PL2-17)

`readInstalledCopyDeclaration` has three production call sites. A copy-root refusal (D-PL2-12)
still answers `absent` everywhere: decision 2 names the manifest only.

1. **`readInstalledCopy`** (dependency-index.ts). Reached from `readCatalogDeclarations` for a
   delisted record, which serves both `readRecordDeclarations` (catalog-first, D-05-06) and the
   catalog fallback of `readInstalledRecordDeclarations`.
   - Before: an escaping link answered `absent`. The read became the failure arm
     `not in manifest`, with the cause "cannot read the dependencies of <key>: not declared by its
     marketplace, and its installed copy cannot be read".
   - Now: `unusable` goes to `unusableDeclaration`, the failure arm `unreadable manifest`, with the
     cause "cannot read the dependencies of <key>: its own manifest is present but cannot be read".
     It is the same arm type, so every consumer still ends the scope walk (D-PL2-05): the uninstall
     dependents guard, prune, `marketplace remove`, `readEnabledDependents`, the load verdict (the
     REC-05 stale-declarer row now names `{unreadable manifest}`), the convergence and `pending`
     plan, `judgeFinalScope`, `withPlannedInstalls` and `localLayerCoverage`.
   - An inside link that used to fail closed as `not in manifest` now reads.
2. **`readInstalledRecordDeclarations`** (dependency-index.ts, D-PL2-06, records with
   `resolvedSha`).
   - Before: `absent` fell back to `readCatalogDeclarations`.
   - Now: `unusable` goes to `unusableDeclaration` and fails closed, with no catalog read. Its two
     consumers:
     - the enable closure: `enableCascadeLookup` throws `EnableRefusedError("unreadable", …)` and
       enable fails `{unreadable}`. The delisted-root exemption `isDelistedRead` matches only
       `not in manifest`, so a delisted root is refused the same way a corrupt installed manifest
       already is;
     - the update preflight: `buildInstalledScopeDeclarationDetail` →
       `evaluateCatalogConstraint` throws `DependencyDeclarationsUnreadableError`, and the update
       fails closed (D-18-17).
   - An inside link now answers with the copy's declarations instead of the catalog's.
3. **`installedCopyDeclarations`** (reconcile/convergence.ts). Reached from `recordMoveIsolated`
   (D-12a, where the copy's declarations join the catalog's) and from `installedCopyReader`
   (APPLY1-01: `apply`'s final judgement and `judgePlannedScope`).
   - It folds every answer other than `found` to `undefined`, so `unusable` behaves as `absent`
     did: the catalog declarations stand alone. This is the existing rule for a corrupt copy
     manifest. No code change, so APPLY1-D1 is unchanged.
   - An inside link now adds the copy's declarations.
