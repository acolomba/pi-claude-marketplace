<objective>
The error-handling part of BACKLOG REVIEWSUGG-01 (PR #303 review suggestions) for the built-in MCP registration path and the two reads it relies on. Do not edit `.planning/BACKLOG.md`; report each disposition in the SUMMARY.

(a) Two plugin servers whose registered names collide. Measured on the base tree (19f3630):
- Equal registered names. D-MB-13 replaces every character outside `[A-Za-z0-9_-]` with `_`, so `my.api` and `my_api` of one plugin, `a_b`/`c` and `a`/`b_c`, or one plugin name in two marketplaces of one scope give one name. `syncSession` builds `new Map(...)` from the registrations, so the later one wins with no trace, and so does the owner map. Info's owner check compares scope, marketplace, and plugin only, so a left-out server of the same record reads the registered server's state (a misreport).
- Names that differ only by `-` and `_` (the case the item names). They are two keys, so both reach Pi. At a fresh session Pi's `registerMcpServer` clash check refuses the later one (logged, noted refused, `not loaded`). At the resync after a load whose autoapply installed a plugin, the result depends on what the session already registered: the server declared later keeps the namespace until the next `/reload`. So "keep one deterministically" is not met.
- Reachable: install refuses folded keys only among the servers it writes for pi-mcp-adapter (`keyedServers` in `bridges/mcp/stage.ts`, AFILE-05). A server that pi-mcp-adapter blocks but Pi's built-in MCP runs, such as one with `bareElicitationCapability: true` (P2-DC-06), is recorded in `mcpServerConfigs` and registered, so both collisions reach the load.
Fix: decide one registration per Pi namespace in the step, exactly as a fresh session decides (Design 1), log each left-out registration, and make info read each left-out server as `not loaded` with existing tokens only.

(b) A failed unregister only debug-logs. Expected disposition: confirmed, no production change. The load must stay silent (RECON-05, NFR-2; BACKLOG BLTNOTICE-01 carries the deferred load notice for refused built-in registrations), and the next sync retries because it lists Pi's registry again. Pin the retry with a unit test and say it in the bridge's doc comment.

(c) Name owners are noted before the sync. When `retainedOwners` has no failures it does not list the registry, so a `getMcpServers` throw inside `syncBuiltinRegistrations` comes after `noteBuiltinServerOwners` already wrote the new owners while Pi still runs the old registrations; info then misreads them (for example a user row reads `overridden by project scope` while the user server runs). In Pi 1.5.0 the list throws only through `assertActive()` (a stale or failed runtime), but the owner map must describe only a sync that reached Pi. Fix: note the owners after the sync returns.

(d) `bridges/mcp/builtin-overrides.ts` and `bridges/mcp/builtin-description.ts` swallow read and parse failures with no trace. Add one `mcp`-channel debug line per swallowed failure, keeping the no-throw contract (T-02-18) and leaking no file text (Design 6).

Purpose: REVIEWSUGG-01 rated these as suggestions; (a) and (c) can make `info` misreport a built-in server (BLT-05), and (d) leaves a failure invisible even with the debug channel on. AGENTS.md requires a cucumber scenario that fails without each user-visible change.

Output: Task 1 (tracer) ships the equal-name rule end to end (step, owner map, info, scenario). Task 2 expands it to the `-`/`_` namespace rule, moves the owner note after the sync, pins the unregister retry, adds the second scenario and the docs. Task 3 adds the debug lines to the two readers.

## Design (decided by the planner; each is listed under Questionable choices in the SUMMARY)

1. **One registration per Pi namespace, decided as a fresh session decides.** After `desiredRegistrations`, the step walks the registrations in declaration order (user records, then the trusted project's; each scope in its state order; each record in its server order) with a map from Pi namespace to the registration that holds it. The key is `foldedMcpServerKey(name)` from `domain/name.ts`, the only fold of a server key (Task 1 keys by the exact name; Task 2 switches to the namespace). A registration whose namespace nothing holds takes it. A registration with the holder's exact name replaces the holder in place: Map position kept, as D-MB-23 / P2-DC-14 already do across scopes, as Pi does when an extension registers its own name again, and as Claude Code does when two plugin servers share a name (Design 7). Any other registration in a held namespace is left out, as Pi's clash check refuses a different name in a taken namespace. The result equals what the sync gives an empty registry, so it never depends on what an earlier pass registered. In Task 2, a listed server that a server declared before it now holds the namespace of is unregistered by the sync, as any `plugin_` name the desired set lacks is, and the holder registers.
2. **Owners name the declared server.** `BuiltinServerOwner` (`platform/mcp-builtin-status.ts`) gains `readonly server: string`, the server's name as the plugin declares it (`RecordedMcpServer.name`), because two servers of one record can give one registered name (D-MB-13). `isOwnedByFailure` keeps comparing the record only (scope, marketplace, plugin). Info's `ownedElsewhere` treats a name as the row's own only when scope, marketplace, plugin, and the row's server all match; otherwise it keeps today's answer (`overridden by project scope` for a user row owned by a project record, else `not loaded`, D-MB-23 / P2-DC-93). In Task 2, each left-out name whose spelling differs from its holder's name gets the holder's owner in the owner map, so info reads that row as owned elsewhere (`not loaded`) even when another extension lists that spelling. The owner map precedence, lowest first: left-out spellings, then retained names (`retainedOwners`), then the registrations the step asked Pi for.
3. **One debug line per left-out or replaced registration**, written after the walk against the final holder, through the step's existing `debugLog` (the `mcp` channel, absolute paths cut). Exact text: `MCP server <name> for <server> of <plugin>@<marketplace> (<scope> scope) not registered: <holder name> for <holder server> of <holder plugin>@<holder marketplace> (<holder scope> scope) holds its Pi namespace`, where `<server>` is the declared server name. Example: `MCP server plugin_demo_my_api for my.api of demo@mp (user scope) not registered: plugin_demo_my_api for my_api of demo@mp (user scope) holds its Pi namespace`. A D-MB-23 replacement of a user server by the project's writes this line too.
4. **Owners after the sync.** `syncSession` calls `noteBuiltinServerOwners` after `syncBuiltinRegistrations` returns, both calls staying in `syncSession`. `syncBuiltinRegistrations` throws only when its first `getMcpServers` throws, before it changes anything, so the owners of the last sync then still describe what Pi runs. `retainedOwners` still reads the previous owners before the note.
5. **(b) is confirmed, not changed.** The step reaches the user through no notify function (`hookDebugLog` only), RECON-05 keeps a load silent, and BLTNOTICE-01 holds the load notice idea. Each sync lists Pi's registry again and unregisters every listed `plugin_` name the desired set lacks, so a removal that threw is tried again; the throw notes nothing, so the status notes stay as they were. In Pi 1.5.0 `unregisterMcpServer` throws only through `assertActive()` (`dist/core/extensions/loader.js` around line 399), and a new runtime starts with an empty registry. The doc comment of `syncBuiltinRegistrations` says so (it contains "tries the removal again").
6. **(d) trace rules, both readers.** A missing file (`isAbsenceError` from `domain/manifest-containment.ts`: ENOENT, ENOTDIR) leaves no line, as Pi's own `mcp.json` reader skips a missing file (`existsSync`, `dist/extensions/mcp/config.js` line 47) and as the description reader already treats a missing manifest candidate as none. Any other read error leaves one line with `errorMessage(error)`. A parse failure leaves one line with a fixed phrase and never the parser's message: V8's `JSON.parse` message quotes the start of the text (measured on Node 24: `Unexpected token 's', "{"a": secret-tok"... is not valid JSON`), and `mcp.json` holds header and env credentials. Each line goes through `redactAbsolutePaths`, then `hookDebugLog(line, "mcp")`, inside the existing catch paths, so neither reader can throw (T-02-18). Shape mismatches (a top level or `mcpServers` that is not an object, a manifest without a usable `description`) stay silent: they are not read or parse failures, and Pi reports `mcp.json` shape errors itself.
   - `builtin-overrides.ts` line: `mcp.json servers not read: <reason>`, reason `the file is not valid JSON` for a `SyntaxError`, else the error message.
   - `builtin-description.ts` line: `MCP server description of <plugin> not read from <source>: <reason>`. For the marketplace manifest (`declaredEntry`), `<source>` is `the marketplace manifest` and the reason is `it is not a valid marketplace manifest` for an `InvalidMarketplaceManifestError` (its message embeds the parser's text), else the error message. For a plugin manifest candidate, `<source>` is its `MANIFEST_CANDIDATES` entry (`.claude-plugin/plugin.json` or `plugin.json`) and the reason is the error message of an `unresolvable` location or a read error other than "no manifest", or `the file is not valid JSON` for a parse failure. Only the candidate that decides the walk (the first one there, D-01-07) writes its failure; the candidates are read in parallel, and a failure after the deciding one changes nothing. A link that leaves the boundary (`escapes`, D-PL2-24) is a refusal, not a failure, and stays silent.
7. **Upstream parity record.** Claude Code 2.1.319 (`/opt/claude-code/bin/claude`, observed 2026-11-06) builds each enabled plugin's servers into a map keyed `plugin:<plugin>:<server>` (`grep -c 'function bQo(e,n,r,s,h=!1){let y={},S=E\$(n,r);for(let\[w,H\]of Object.entries(e)){let z=.plugin:\${S}:\${w}.' /opt/claude-code/bin/claude` prints 1; each `.` stands for a backtick) and merges the plugins in order with `Object.assign` (`grep -c 'for(let kn of pt)if(kn)Object.assign(ne,kn)' /opt/claude-code/bin/claude` prints 1), so the later plugin's same-named server wins. Confidence medium (minified code, one version). Claude Code keeps `-` and `.` in server names, so `my-api`/`my_api` and `my.api`/`my_api` both run there; dropping one is a Pi capability gap (Pi's name rule `^[A-Za-z0-9_-]+$` and its `-`-to-`_` namespace fold, ANAME-03, D-MB-13). Re-run the two greps in Task 1 and record the output, version, and date in the SUMMARY. If they no longer match, record "no upstream position known" and keep the rule: D-MB-23 already requires the later same-named server across scopes.
