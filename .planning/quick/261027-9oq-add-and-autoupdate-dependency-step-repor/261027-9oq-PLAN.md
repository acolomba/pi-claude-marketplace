## Interfaces (current source, for orientation)

- `ScopeDependencyInstallFn = (request: ScopeDependencyInstallRequest) => Promise<ScopeDependencyInstallResult>`. The result is `{ rows: readonly ScopeDependencyInstallRow[]; mcpConfigNotices: readonly McpConfigNotice[] }`, and `ScopeDependencyInstallRow = PluginInstalledMessage | PluginFailedMessage` (`orchestrators/types.ts`).
- `runScopeIsolated(scope, outcomes: PerEntryOutcome[], op: () => Promise<void>)` (`orchestrators/reconcile/read-pass.ts`, already imported by `apply.ts`) turns a throw out of `op` into the outcome `{ kind: "invalid-block", scope, basename: "state.json", reason: classifyReadPassThrow(err), cause: new Error(redactAbsolutePaths(errorMessage(err))) }`.
  - `apply` uses it after its moves, in the private `readPlainPlan`, around this same `readPlainPlanForScope`.
  - `classifyReadPassThrow` returns `lock held` for a `StateLockHeldError`, `unparseable` for a `SyntaxError` cause, and otherwise `narrowProbeError`. A plain `Error` becomes `unreadable`.
- `applyMarketplaceOutcomeToBlock` (`notify.ts`) renders an `invalid-block` outcome as a failed `state.json` block header. When the outcome carries a cause, it also adds one synthetic child row: `{ status: "failed", name: basename, reasons: [reason], cause, severity: "error", needsReload: false }`. That child row is "the row `apply` uses" for the add-time step.
- `cascadeAutoupdates(snapshot, args)` (`update.ts`) returns `{ outcomes, installs }`. It runs the plugin-update loop, which already rethrows GHB-03 from a plugin update, then `installAutoupdateDependencies`. `refreshOneMarketplace` renders the result after the cascade returns.
- `notifyAdded` (`add.ts`) is the model for (B): it runs the step in a `try` and sends the `(added)` notification and the MCP notices from the `finally`.

## Why (A) has no cucumber scenario (carry into the SUMMARY under `## Proof scope`)

The step's read (`readPlainPlanForScope`) can throw at three points:
- taking the scope's state lock;
- loading `state.json`;
- the MIG-01 save of the base config.

The same command passed all three moments earlier, under the same lock and on the same files. The add, or the update's plugin updates, loaded and saved `state.json` and wrote the layer config into the same scope directory.

A scenario can change the sandbox only in `Given` steps, before its single `When` starts. No `Given` may follow a `When` (`.agents/skills/cucumber/rules/features.md`). Nothing in the world can run between two lock acquisitions inside one command.

The only lock stand-in, `another process holds the state lock of the <scope> scope` (`features/lib/state-lock-holder.ts`), takes the lock before the command starts. So the add itself fails as `lock held`, and the step never runs. `features/marketplace/state-lock.feature` shows this in "Adding a marketplace while another process holds the state lock of the scope fails as lock held and leaves no marketplace".

A corrupt installation record would fail the add in the same way. No step may name the extension-owned `pi-claude-marketplace/state.json`, because steps name user-visible things only.

The MIG-01 save writes only when the base config is absent and the state records something that no layer declares. That is a legacy, pre-config record, and no step can create one.

02-REVIEW-FIX.md (WR-02, WR-05) reached the same limit. The unit cases of Task 2 carry the proof.
