## Planner findings

- **The shared-dependency (IN-02) apply scenario does not move under a pair sort as written.** Its rows read `app`, `lib`, `kit`. `app` already sorts before `lib`, and `kit`'s lone `{dependency failed}` row comes from a later install (the IN-02 dedupe drops its copy of the `lib` row). Import sorts only the pair, so "as import does" leaves those rows where they are, and the scenario would pass without the change. Task 1 renames the two requested plugins so the shared dependency sorts first (`app` becomes `server`, `kit` becomes `web`). The rows then read `lib`, `server`, `web`, and the scenario fails on the unchanged source (`server`, `lib`, `web`).
- **The single-dependency apply scenario stays as is.** It lists `app` before `lib`. That is name order, so after the change it guards against an order that always puts the dependency first (IN-03's suggested fix). With the renamed IN-02 scenario, which guards against requested-first, the two scenarios pin name order.
- **"Strictly again" means the behavior before 78e79e6e, not exact-only.** Before that commit every error token projected from its exact message and from its cut form (D-PL6-14). The cut form must stay: on Node 26 (local Node is v26.12.1) `readFile` on a directory reports `EISDIR: illegal operation on a directory, read '<path>'`, and import and apply show that cause with the path cut, so `{mcp-adapter.json read error}` cells in import and apply match only through the cut form. Every scenario that uses an error token other than the read-only one predates 78e79e6e and passed then.
- **The 13 scenarios that use an error token** match `--name 'rollback cannot finish|cannot finish the rollback|second dependency move fails|fails in its mcp phase'` (dry-run count 13; they pass at HEAD in about 6 s).
- **Probe baseline:** the Task 2 probe fails at HEAD on its last assertion only: today `{mcp-adapter.json read error}` still projects from the message at `/elsewhere/mcp-adapter.json`.

## Planner choices (for review)

1. Pair sort only, as import does (D-PL6-15's wording), so the plan renames the IN-02 scenario's requested plugins instead of sorting every row of a block.
2. The sort lives in `apply.ts::installFailedOutcomes`, not `notify.ts`: the pair is built there, as import builds and sorts its pair, and `buildReconcileAppliedCascade` keeps its documented insertion order within a block.
3. No same-block condition: rows in two blocks render the same in either order, so the sort runs on every pair and adds no branch.
4. The token text gets one source: an exported `READ_ONLY_SKILL_REMOVAL_ERROR_TOKEN` in `features/lib/run-tokens.ts`, used by `projectTokens` and by the step that records it. It cannot live in `published-marketplace.ts`, because that module imports `cutQuotedPaths` from `run-tokens.ts` (an import cycle).
5. The two MIM-03 unit cases keep their titles; only the expected text moves.
6. The decision IDs are recorded in the code comments, the skill rule, and this task's SUMMARY. `06-CONTEXT.md`'s decision list is left to the orchestrator, because quick executors commit code only.
