<objective>
Introduce the provenance field end to end — declared on the persisted install record, written by every install path, carried across clone and reinstall, and back-filled for every document written before it existed.

This is step 1 of D-04-04's three-step contract. After this plan the field exists and is written; nobody reads it yet. The cascade dependency stays protected by Phase 3's config write, which is untouched here and retired in wave 5.

Purpose: `--prune` (Phase 5) and reconcile's dependency exemption (wave 4) both read this field. Nothing downstream can be built until it is true of every record.
Output: `provenance: "explicit" | "dependency"` required at schemaVersion 3, a silent `ensurePluginProvenance` fill, and one end-to-end test proving a cascade root records `"explicit"` while its dependency records `"dependency"`.
</objective>

<assumption_delta_decision>
**Noun that is now primary:** the install record's `provenance` — a record now states
*how the plugin got here*, of which "the user asked for it by name" is one variant
rather than the only shape.

**Decision: promote.**

Before this phase an install record was implicitly one kind of thing: every record
was a direct install, and the desired-state config (`claude-plugins.json`) was the
carrier of "the user wants this". This phase generalizes that into two kinds. The
correct move is to promote the general representation to primary and demote the old
specific one to a variant — which is exactly what D-04-01 and D-04-03 do: a single
REQUIRED field on the single `PLUGIN_INSTALL_RECORD_SCHEMA`, not an optional
side-field and not a second record type. There is no second record shape left
alongside the first.

The add-alongside trap in this phase is concrete and named: keeping Phase 3's config
write (the OLD carrier of "the user wants this") next to the new provenance field.
That would leave two sources of the same fact, free to disagree, and it is precisely
what D-04-02 and D-04-04's step 3 remove. Retiring the old carrier in wave 5 is what
makes this a promote rather than an add-alongside.

**Invariant test that encodes the generalized intent** (suggested, not required):
the COMPAT-01 key-set pin in `tests/architecture/compat-01-no-expansion.test.ts`
already fails if the field is dropped; pair it with a migrate case asserting that a
record with no provenance is REJECTED by `STATE_VALIDATOR.Check` when the fill is
bypassed. Together they make a future phase that re-optionalizes the field go red
rather than silently reintroducing the singular assumption.
</assumption_delta_decision>
