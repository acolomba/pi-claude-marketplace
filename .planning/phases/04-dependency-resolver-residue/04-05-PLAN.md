<objective>
RSV-01 (UPDDEP-01 b1), second half, per D-PL4-01: every plugin the plan previews and
then installs installs the commit its preview resolved, with one network resolve.

- One helper, `memberLedgerPin`, gives a member's ledger pin. A release tag's commit
  and semver win (RESV-03, GV-01); otherwise `previewedCommit` becomes
  `sourcePinOverride` alone, with no `resolvedVersion`, so `deriveInstallVersion` takes
  its third tier and records what an unpinned install of the same commit records. Both
  builders use it.
- `planInstallMoves` passes the root preview's commit as `rootCommit`.
- `dependencyInstallsFollow`'s doc states D-PL4-02.
- A WR-C case pins D-PL4-04's side effect on a plain update (Uncertain choice 5).

Mechanism (verified in 04-RESEARCH.md, RSV-01 (b)): with `sourcePinOverride` set,
`probeInstallClone` takes its pinned arm, `resolvePluginPin` answers with no network,
and `materializePluginClone` finds the per-commit copy the preview created under the
same `pluginCloneKey(canonicalCloneUrl(source), sha)`. No clone sweep runs between
the preview and the install.

Output: install-flow.ts (the planning and missing-dependency functions only; Phase 11
splits the file later, so move nothing) and its owner test. Two commits.
</objective>
