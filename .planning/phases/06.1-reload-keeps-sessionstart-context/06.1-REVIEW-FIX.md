### WR-01: A compaction steered between turns forces an extra model call when a queued follow-up or polled steer takes the next turn

**Files modified:** `extensions/pi-claude-marketplace/bridges/hooks/event-router.ts`, `test/bridges/hooks/event-router.test.ts`, `features/hook/additional-context.feature`, `docs/hooks-compatibility.md`, `.planning/REQUIREMENTS.md`, `.planning/PROJECT.md`
**Commits:** `977d77c` (fix, scenario, unit row, docs, HKRL-03), `4365eac` (D-CF5-13 amendment)
**Status:** fixed: requires human verification (logic change)
**Applied fix:** The `turn_end` callback now sets `runPhase = event.context.pendingMessages.length === 0 ? "between" : "turn"`. I checked this against Pi 1.5.1:

- `agent-session.js` `_dispatchTurnEndBoundary` runs inside `finishTurn`, before the steering poll that `agent-loop.js` `runLoop` makes after `turn_end`.
- `_buildBoundaryContext` sets `pendingMessages` to `[...agent.peekQueuedMessages(), ..._pendingCustomMessages]`. `peekQueuedMessages()` returns the steering queue when it is not empty and the follow-up queue otherwise.
- So a queued steer or follow-up shows at the turn end. That message takes the next turn, and the poll after `prepareNextTurn` runs only when `pendingMessages` is empty.

The phase then stays `turn`, and the compaction's context is sent with `{ triggerTurn: false }`, held to that turn's end. The check counts held custom messages too. So when the bridge holds context of its own, the compaction context also waits a turn. That is the safe direction, because it adds no model call.

Other changes:

- The `RunPhase` JSDoc and the step-6 registration comment say this.
- The router delivery table gained the row `holds the SessionStart context of a compaction before a queued message's turn to that turn's end (HKRL-03)`. It uses a `turn_end` whose `pendingMessages` holds a user message, and the loop now looks up handlers by `RUN_EVENTS[...].type`.
- The scenario `A compaction before a queued follow-up's turn keeps the compact context without another model call` (`additional-context.feature:524`) queues a follow-up while a tool runs. The reply after the tool reports 120000 context tokens, so Pi compacts before the follow-up's turn. The scenario checks call 4, the follow-up's call: the summary, `Done.`, and `also say hi`. A second prompt then shows the context at call 5, after `Hi.`. So the context is kept, and no call is added.
- `docs/hooks-compatibility.md` (HKRL-03 paragraph), HKRL-03 in `.planning/REQUIREMENTS.md`, and D-CF5-13 in `.planning/PROJECT.md` now name the queued-message case. The steer case is marked as read from Pi's source, and the follow-up case as measured.

Upstream gap that remains, and is documented: Claude Code puts the context in the compacted conversation, so the queued message's own call reads it. Pi gives an extension no way to add a message to a call that a queued message already takes, short of steering, which adds the call.

### IN-01: An aborted overflow retry leaves the steered context in Pi's steering queue

**Files modified:** `docs/hooks-compatibility.md`
**Commit:** `1320d2b`
**Applied fix:** Documented, not handled. In Pi 1.5.1, `AgentSession.abort()` calls `agent.abort()`, which does not empty `agent.steeringQueue`. Interactive mode's Escape and the extension `abort` handler call `restoreQueuedMessagesToEditor`, which calls `clearQueue()` and `agent.clearAllQueues()`, and that drops a queued custom message. The bridge cannot take one message back out of Pi's queue, and a resend could duplicate the context, so no small, safe handling exists. The HKRL-03 paragraph now says, as read from Pi's source: the next run reads the context after the next prompt; when Pi empties the queue first, as the terminal does, the context is lost; neither case starts a model call.

**Applied fix:** I added the scenario `A resumed session carries nothing from the session the user left` (`:358`):

- Session A is a new session (`clear`), and its hook gives `a-ctx`. The user prompts `a prompt`.

Two new setup steps support it: `the user has started pi again in a new session` and `the user has resumed the session of the prompt {string}`. `sessionFileWithPrompt` in `features/lib/saved-sessions.ts` finds the session file.
