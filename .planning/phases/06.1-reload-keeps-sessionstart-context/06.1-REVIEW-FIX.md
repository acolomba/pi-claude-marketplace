**Commit:** `34d4e27`
**Status:** fixed: requires human verification (logic change)

**What Pi 1.5.1 does.** I read `pi-agent-core/dist/agent-loop.js` (`runLoop`), `agent.js` (`PendingMessageQueue`, `peekQueuedMessages`), and `pi-coding-agent/dist/core/agent-session.js` (`_dispatchTurnEndBoundary`, `_buildBoundaryContext`, `_installAgentNextTurnRefresh`, `_compactBeforeNextAssistantResponse`, `sendCustomMessage`, `_flushPendingCustomMessages`, `pendingMessageCount`, `_queueUserInput`, `prompt`, `_handlePostAgentRun`, `_checkCompaction`):

- After a turn, `runLoop` reads one steer (`one-at-a-time`). It then calls `prepareNextTurn`, where Pi compacts. It reads the steering queue again only when the first read found nothing. The retry after an overflow starts with a read of the steering queue.
- A follow-up is read only when the turn has no more tool calls and no steer was read.
- `pendingMessages` at `turn_end` is `[...peekQueuedMessages(), ..._pendingCustomMessages]`. The peek is the steering queue when it has items, else the follow-up queue. Nothing in a message tells the two queues apart.
- Pi appends `_pendingCustomMessages` to the session at that same turn end. They take no model call.
- `ctx.hasPendingMessages()` is `pendingMessageCount > 0`, which counts only the session's user steers and follow-ups. An item stays counted until its `message_start`, so the count stays above 0 while a read steer waits for its call.
- Every queued user input, from the terminal, RPC, or `sendUserMessage`, passes the `input` handlers with `streamingBehavior` set, before Pi expands it and queues it.

**Which check, and why.** I filter `pendingMessages`. I do not use `ctx.hasPendingMessages()`.

- At the turn end, `hasPendingMessages()` cannot tell a steer from a follow-up either, so it cannot fix P2. It also misses an extension's custom steer or follow-up, which takes the next call, so steering there would add a call.
- At send time, `hasPendingMessages()` is true while a follow-up waits behind the tool results (P2), so it would hold the context in exactly the case P2 needs it steered.

**The fix.** A per-registration tracker, `createRunPhaseTracker`, replaces the `runPhase` variable. `turn_start`, `turn_end`, `agent_end`, and the last `input` subscription (the STOP-07 reset) move it.

- At `turn_end`, the tracker drops the bridge's own held messages (`claude-hook-tool-context` and `claude-hook-additional-context`). A queued message is a follow-up only when a follow-up input of the same run gave its text, counted with repeats. Any other queued message means a steer waits.
- Queued messages take the next call when the turn ends the work (`endsTheWork`), which also uses up those follow-ups. After a tool call, the call for the tool results comes first.
- A steer input sets "a steer waits" until the next turn end. A follow-up input records its text until the run reads that follow-up or `agent_end`.
- The SessionStart event now carries `nextCallReadsSteer: () => boolean`, in place of the boolean `nextCallInRun`. The adapter calls it when the hooks finish, so the decision uses the queue state at send time (WR-02). The context is steered when no steer waits and either the compaction is an overflow retry or the run is between two turns.
- So the overflow retry is now held too when a steer waits ahead of it. Iteration 2 steered it unconditionally, and a queued user steer then took the retried call, so the context forced one more call.
