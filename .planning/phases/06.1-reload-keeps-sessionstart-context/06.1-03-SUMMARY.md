# Phase 06.1 Plan 03: A Compaction's SessionStart Context Reaches the Next Model Call Summary

When Pi retries a model call after an overflow compaction, or compacts between two turns of a run, the bridge now steers the compaction's SessionStart context into the running agent (`deliverAs: "steer"`), so the very next model call reads it after the summary, as Claude Code 2.1.330 puts it. Every other case keeps `{ triggerTurn: false }`, so a compaction after the run ended starts no model call. A run phase that `turn_start`, `turn_end`, and `agent_end` keep decides the case. Four scenarios, the router's five compaction delivery rows, the adapter's steer and hold cases, and four breaks prove it.

## Product fix

- **Defect per path (review WR-02):** the compaction leg ran SessionStart with `{ source: "compact" }`, and the adapter sent `{ triggerTurn: false }`, which Pi holds to the turn end while a run is active. (d) A threshold compaction in the middle of a run happens between the loop's `turn_end` and its next `turn_start`; the held message sits in `_pendingCustomMessages`, which the rebuilt projection leaves out, so call 3 missed it. (e) An overflow compaction with `willRetry: true` follows the error turn's `agent_end`; the retry is built from the session projection, so call 5 missed it. - **Delivery hint (`payloads/session-start.ts`):** `ClaudeSessionStartEvent` gains `readonly nextCallInRun?: boolean;` with a JSDoc citing HKRL-03. Dispatch never matches on it, and `translateSessionStart` never writes it to stdin (a new unit case proves the envelope).

Text, `details`, and the prompt context messages are unchanged.
- **Compaction leg (`event-router.ts`):** `runCompactionSessionStart` takes `nextCallInRun` and runs `sessionStartHandler({ source: "compact", nextCallInRun }, ctx)`. `sessionCompactCallback` takes `betweenTurns: () => boolean` and passes exactly `event.willRetry || betweenTurns()`.
- **Run phase and its three events:** module-private `type RunPhase = "idle" | "turn" | "between"`; `let runPhase: RunPhase = "idle"` before the `session_compact` registration, whose callback reads `() => runPhase === "between"`. A new `pi.on("turn_start", bindWithMode(...))` right before `turn_end` sets `turn`; the `turn_end` callback sets `between` before `sendDueFollowUpContext`; the `agent_end` callback sets `idle`, then calls `agentEndCacheHandler(runtime, generation)`. All three go through `bindWithMode`, so a stale generation's callback never runs. The step 6 comment counts 15 call sites and 13 Pi event names, and both `index.ts` comments count 15.
- **Why `turn_start`:** Pi also compacts inside `prepareRequest` for a virtual model, after the turn's steering poll. Without the reset, the phase would stay `between` through later turns, and a steer there would be read at the turn end and force an extra turn. With it, that path keeps `{ triggerTurn: false }`, and the context waits for the turn end (router row R5).
- **Harness:** the tool variant of `ScriptStep` and its validator take `contextTokens`; `REPLY_ONLY_COLUMNS` keeps `stop reason`, and the new `RESPONSE_ONLY_COLUMNS` holds `context tokens`, which only an error row refuses; `replyContextTokens` is now `stepContextTokens`, and `toolStep` spreads it; the refusal reads `model script row <n> sets <columns>, which a <kind> row does not take`. `playNextStep` wraps the tool message with `withContextTokens` when the step has tokens.
