## Summary

I re-reviewed all three plans of the phase since `90e38915`:

- HKRL-01: the SessionStart context is sent at once.
- HKRL-02 (plan 06.1-02): a resume or fork removes duplicate values one by one, and each SessionStart message carries `details`.
- HKRL-03 (plan 06.1-03): a compaction's context is steered into the run, and a new `turn_start` registration tracks the run phase.

I traced each path through Pi 1.5.1:

- `agent-session.js`: `sendCustomMessage`, `_runAutoCompaction`, `_checkCompaction`, `_handlePostAgentRun`, `_prepareRun`, `_compactBeforeNextAssistantResponse`, and `abort`.
- `pi-agent-core`: `agent.js` `continue` and `createLoopConfig`, and `agent-loop.js` `runLoop`.
- `session-manager.js`: `projectContextEntry` and `buildSessionProjection`.

**Iteration-1 findings:**

- **CR-01 (a fork copied the parent's context): closed.** The user chose upstream parity (ROADMAP criterion 4). A fork and a resume now drop each value that the projection already holds. The scenario at `additional-context.feature:255` proves one copy after a fork at the first prompt.
- **WR-01 (no-leak scenarios): mostly closed.** `:334` covers a new session. `:279`, `:305`, and `:358` cover a continued session. `:255` covers a fork. No scenario resumes a *different* saved session (IN-03).
- **WR-02 (compaction placement): closed.** `:381`, `:409`, `:436`, and `:462` cover a manual compaction, a compaction after the run, one between turns, and the overflow retry. The docs table row now names the placement for each source.
- **IN-01 to IN-04: closed.** The failure line is attributed. The attribution test was dropped. The stale router case now resolves a context. The JSDoc names synchronous throws only. The barrel comment and the U34 row were updated. IN-04 below lists the stale lines that remain.

**What holds:**

- **Duplicate removal matches the evidence record.** It applies to `resume` and `fork` only. It compares one value at a time, by `details.values` or, for an older message, by the labeled text part. It normalizes the `saved to:` path. When nothing is new, it sends nothing.
- **No extra call after the run ends.** A compaction after `agent_end` is never steered (`runPhase` is `idle`), so Pi's `hasQueuedMessages()` return from `_runAutoCompaction` stays false.
- **A run that errors resets the phase.** `handleRunFailure` emits `turn_end`, then `agent_end`.
- **NFR-2.** The new `turn_start` callback cannot throw, and `bindWithMode` wraps it. The projection read is in a try/catch.
- **IL-2.** No change adds an output channel.
- **Count.** There are 15 `pi.on` call sites on 13 event names. The code, the `index.ts` comments, and `ARCHITECTURE.md:112` agree.
- **Coverage.** Direct coverage, run with `--base 90e38915`, is 100% for all ten changed source pairs.

**Defects:**

- WR-01: a compaction steer can still force an extra model call inside a run. This happens when a queued follow-up or a polled steer takes the next turn. The docs leave the follow-up case out and understate the steer case.
- WR-02: the duplicate removal trusts `details` over the text that the model sees.
- WR-03: no test proves the projection-over-branch property that the summaries claim.

## Warnings

### WR-01: A compaction steered between turns forces an extra model call when a queued follow-up or polled steer takes the next turn

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-router.ts:1633-1641` (the `turn_end` callback sets `runPhase = "between"` unconditionally), and `:1312` (`event.willRetry || betweenTurns()`). The docs claim is at `docs/hooks-compatibility.md:161`, and the requirement at `.planning/REQUIREMENTS.md:45`.

**Issue:**

I traced this in `pi-agent-core/dist/agent-loop.js` `runLoop`:

1. A turn ends with no tool call. Its `turn_end` sets `between`.
2. The steering poll at line 191 finds nothing, so the inner loop exits.
3. `getFollowUpMessages()` returns a queued follow-up, so `pendingMessages = [followUp]` and the outer loop runs again.
4. `prepareNextTurn`, which is `_compactBeforeNextAssistantResponse`, runs a threshold compaction. The bridge steers the context, because `runPhase === "between"`. The message goes into `agent.steeringQueue`.
5. The poll after preparation runs only `if (pendingMessages.length === 0)`. The follow-up is pending, so the poll does not run. The follow-up's model call does not see the context.
6. That call ends with no tool call. The poll at line 191 now returns the context message, so `pendingMessages.length > 0`, and the loop makes one more model call. Its input ends with the hidden context message, and the model answers it.

Claude Code places the compact context in the compacted conversation itself, so the follow-up's call reads it and no call is added.

Other paths hit the same mechanism:

- A user steer that the line-191 poll already took. The SUMMARY admits it "causes one extra call". `docs/hooks-compatibility.md:161` says only "the context can wait one more turn".
- Any extension follow-up, such as `sendMessage(..., { deliverAs: "followUp" })`.

So the docs understate the steer case, and the follow-up case is not documented at all. HKRL-03 says the context "reaches the very next model call in every compaction path". That is not true for either case. No scenario covers a compaction before a follow-up turn.

**Fix:** Steer only when no queued message will be polled ahead of the context. Otherwise hold the context to the turn end with `triggerTurn: false`, which never starts a call. The `turn_end` event already carries what Pi will read next:

```ts
pi.on(
  "turn_end",
  bindWithMode(() => (event: FollowUpTurnEnd) => {
    // HKRL-03: a queued steer or follow-up takes the next turn before a
    // steered context would, so hold the context to that turn's end.
    runPhase = event.context.pendingMessages.length === 0 ? "between" : "turn";
    sendDueFollowUpContext(event, runtime, pi);
    return Promise.resolve(undefined);
  }),
);
```

Then:

- Add a router row: `turn_end` with a non-empty `pendingMessages`, then `session_compact` with `threshold`. The send should use `{ triggerTurn: false }`.
- Add a scenario: a tool step with `context tokens`, a follow-up queued while the tool runs, and a script that would fail on one call too many.
- Reword `docs/hooks-compatibility.md:161` and HKRL-03 to name the queued-message case.

### WR-02: Duplicate removal trusts `details` over the text the model sees, so a context edit drops values and an unrecognized `details` resends them

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-adapters.ts:822-842` (`messageKeys`)

**Issue:** The comment at `:844-847` and D-CF5-13 say the removal compares against "the conversation the model sees". `messageKeys` reads `details` first and uses the text only when `details` is `undefined`. Two kinds of drift break the claim:

1. **A context edit.** Pi 1.5.1 lets an extension write `context_edit` drafts at `turn_end` and `agent_before_settle` (`ContextEditEntryDraft`, `extensions/types.d.ts:785`). `projectContextEntry` (`session-manager.js:236-254`) replaces only `content` and keeps `details` (`{ ...message, content }`). Suppose a context-trimming extension rewrites the SessionStart message. On the next resume or fork, the bridge still treats the old values as held and drops them. The model never sees them again.
2. **A `details` that the guard rejects.** This covers a later release's shape, a `null`, or any malformed value. The message then gives no keys at all, and the labeled text part that the model sees is ignored. On resume, the value is sent a second time. The unit row `ignores null details ...` (`event-adapters.test.ts:2364`) pins this duplicate as intended behavior. So the stored shape is not forward compatible: a future `details` version makes this release resend the context on every resume.

**Fix:** Take the keys from what the model sees, and use `details` only to split that text into its values when the two agree:

```ts
function messageKeys(message: AgentMessage): readonly string[] {
  if (message.role !== "custom" || message.customType !== HOOK_CONTEXT_MESSAGE_TYPE) {
    return [];
  }
  if (typeof message.content === "string") {
    return [];
  }
  return message.content.flatMap((part) => {
    if (part.type !== "text" || !part.text.startsWith(SESSION_START_CONTEXT_LABEL)) {
      return [];
    }
    const text = part.text.slice(SESSION_START_CONTEXT_LABEL.length);
    return isSessionStartContextDetails(message.details) &&
      message.details.values.join("\n") === text
      ? message.details.values.map((value) => contextKey(value))
      : [contextKey(text)];
  });
}
```

Add rows for a message whose content a context edit replaced, and for a message with unrecognized `details` whose text holds the value. The second row should send nothing.

### WR-03: No test fails if the removal reads the whole branch instead of the projection after the latest compaction

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-adapters.ts:848-850`; `test/bridges/hooks/event-adapters.test.ts:2223-2310`; `features/hook/additional-context.feature`

**Issue:** Both summaries and D-CF5-13 state one property: the held context is read from `buildSessionProjection().messages`, never the branch, "so a compaction's summarized entries do not count". The prompt asked to verify this too. No case appends a compaction:

- `grep appendCompaction test/bridges/hooks/event-adapters.test.ts` finds nothing.
- No scenario resumes or forks after a `/compact`.

Two mutations would pass every test: one that maps `getBranch()` entries, and one that reads `buildSessionContext()` without the compaction cut. Under either, a value that a compaction summarized away would never be sent again on resume. The model would lose the context, and no test would show it. AGENTS.md "Behavioral tests" requires a test that fails without the change.

**Fix:** Add a row to the held-session table. Use `SessionManager.inMemory`, append a SessionStart message with `details: ["held context"]`, append a user and an assistant message, then `appendCompaction(summary, <id after the held message>, ...)`. A `resume` with `["held context"]` must then send `["held context"]`. Optionally, add a scenario: prompt, `/compact` without a `compact` matcher hook, continue the session, prompt. The model call should hold the startup context once, after the summary.

## Info

### IN-01: An aborted overflow retry leaves the steered context in Pi's steering queue

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-adapters.ts:627`; `event-router.ts:1312`

**Issue:** With `willRetry`, the context goes to `agent.steer()` while the SessionStart hook runs inside Pi's awaited `session_compact` emit. Suppose the user aborts during that hook. `_handlePostAgentRun` returns `false` and the loop breaks. `agent.abort()` does not clear the steering queue (`agent.js:221`). The message then stays in memory and is never persisted. Two outcomes follow:

- **The next run reads it.** The run's first steering poll adds it after the next prompt.
- **The queue is cleared.** Then the message is lost. A `clearQueue()` is one way to clear it.

This is not an extra call and not a crash, but it is not documented.

**Fix:** Add one line to the HKRL-03 paragraph of `docs/hooks-compatibility.md`, saying that an aborted retry delivers the context after the next prompt. Mark the line as read from Pi's source.

### IN-02: Nothing pins that a re-registration starts the run phase at `idle`

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-router.ts:1560`

**Issue:** `runPhase` resets on `/reload` and on a new session only because it is a `let` inside `registerHooksBridgeWith`. No router case registers twice and checks the result. The check would be: `turn_end` in generation 1, then register again, then `session_compact` sends `{ triggerTurn: false }`. Without that case, moving the cell into `createHooksRuntime` would let a reload during a run steer a stale `between` phase, and every test would still pass.

**Fix:** Add a row to the HKRL-03 delivery loop that registers the bridge a second time between `before` and the compaction.

### IN-03: The iteration-1 "resume of another session" no-leak scenario was not added

**File:** `features/hook/additional-context.feature`

**Issue:** WR-01 of iteration 1 asked for a scenario that resumes a different saved session and checks that no row comes from the session the user left. The new scenarios cover `/new`, a continue of the same session, and a fork. Isolation for a switch to another session still rests on Pi's runtime replacement alone.

**Fix:** Add a scenario. Save session A with a SessionStart hook that gives `a-ctx`. Start session B. Resume A, then prompt. The call should hold `a-ctx` once and nothing from B.
