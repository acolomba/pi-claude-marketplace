# Phase 06.1: Code Review Report

**Reviewed:** 2026-11-23
**Depth:** standard
**Files Reviewed:** 16
**Status:** issues_found

## Summary

I reviewed the HKRL-01 change since `90e38915`. A SessionStart `additionalContext` is now sent at once through `sendHookContextMessage` (`pi.sendMessage(..., { triggerTurn: false })`, `display: false`), and the SessionStart buffer is gone from the runtime, the routing state, and `before_agent_start`.

I traced the send through Pi 1.5.1 (`agent-session.js` `sendCustomMessage`, `_flushPendingCustomMessages`, `reload`, and `agent-session-runtime.js` `fork`). These parts hold up:

- **NFR-2:** a synchronous throw, including Pi's stale-context error after a session replacement or reload, is caught and debug-logged. The `session_start` and `session_compact` callbacks keep their outer try/catch.
- **Stale runs:** a run whose generation goes stale folds to noop before the adapter runs (`runHooks`, dispatch.ts:280-290). A new session's runtime is a new factory with a new `pi`, so a late fold of the old session hits Pi's stale check and is not sent.
- **Repeats and reloads:** SSDEDUP-01 still drops a repeated `session_start`. `reason: "reload"` still returns before dispatch, so a reload sends nothing twice.
- **Subagent children:** a child never dispatches SessionStart (`CHILD_EVENT_POLICY`).
- **Streaming:** while a run streams, Pi holds the message in `_pendingCustomMessages` and never steers. While idle, it appends a `custom_message` entry, which `/reload` keeps (the session manager survives `reload()`).
- **Output and display:** IL-2 is respected (model channel, not `ui.notify`), and the message is hidden.
- **Coverage:** direct coverage is 100% for all five changed sources (checked with a focused `test-coverage-direct.mjs` run).

The defects are in what the phase claims about session changes:

- **Fork:** a fork now copies the parent's SessionStart context. I checked this with Pi's `SessionManager`. This contradicts HKRL-01, ROADMAP success criterion 2, the D-CF5-13 amendment, the docs, and the adapter comment.
- **No-leak tests:** no test proves the no-leak claims at all.
- **Compaction:** the change also moves where a compaction SessionStart context lands, and no scenario covers that.

## Critical Issues

### CR-01: A fork now copies the parent session's SessionStart context, against HKRL-01 and every doc that states the rule

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-adapters.ts:769-770` (claim). The same claim is in `docs/hooks-compatibility.md:449`, `.planning/PROJECT.md:2273` (D-CF5-13 amendment), `.planning/REQUIREMENTS.md:42`, and `.planning/ROADMAP.md:328`.

**Issue:**
- **What the docs claim:** each place says a forked session "does not get" the SessionStart context, or "starts without the context of the session before it". The adapter comment says "A new, resumed, or forked session is a new Pi session, so the message stays with the session that sent it."
- **Why that is wrong:** the context is now a `custom_message` entry *before* the first user message. Pi's fork (`agent-session-runtime.js:180-225`) sets `targetLeafId = selectedEntry.parentId` and calls `createBranchedSession(targetLeafId)`, which copies the branch up to that leaf.
- **Probe result:** a fork at the first prompt now copies the parent's context entry into the new session. I checked this against Pi 1.5.1's `SessionManager`:
  - The fork target's parent entry is `custom_message`.
  - The branched session holds `custom_message:claude-hook-additional-context`.
  - `buildSessionProjection()` gives `[["custom","claude-hook-additional-context"]]`.
- **What the user sees:** the fork's own `session_start` (`reason: "fork"`) then runs SessionStart with `source: "fork"` and sends the context again. So the forked session's first model call reads the hook context twice: once from the parent and once of its own.
- **Regression:** before this change the entry sat after the first prompt, so a fork at the first prompt carried nothing. The phase made the documented no-leak rule false for that case.

Upstream behavior for a fork is not in `06.1-UPSTREAM-EVIDENCE.md`. Copying the head rows may be Claude Code's behavior too, but that is unverified. Under AGENTS.md "Upstream parity", the gap between the requirement and the code must go to the user, not ship silently.

**Fix:** Choose one, and record the choice in D-CF5-13:
1. **If upstream copies the head rows on a fork** (check with `claude-code-compat-research`): amend HKRL-01, ROADMAP criterion 2, D-CF5-13, `docs/hooks-compatibility.md:449`, and the comment at `event-adapters.ts:769-770`. They should say that a fork copies the earlier history, the SessionStart context included, and that the fork's own `source: "fork"` run adds its own context. Add a scenario that pins that.
2. **If the no-leak rule must hold:** the context cannot sit in the copied branch before the first prompt. For example, keep it out of the fork's projection with a `context` handler that drops `claude-hook-additional-context` SessionStart entries that came before the fork point. Then add a scenario that forks at the first prompt and asserts one copy.

## Warnings

### WR-01: No test proves the new/resume/fork no-leak claim that success criterion 2 rests on

**File:** `features/hook/additional-context.feature` (missing scenario); `.planning/ROADMAP.md:328`

**Issue:** Criterion 2 says "the existing no-leak scenarios still pass". `06.1-RESEARCH.md:212` says no such scenario exists: "No scenario today asserts that context does not cross new/resume/fork." The `session.feature` scenarios assert hook runs, not model calls. So the isolation claim in the docs, the PROJECT.md amendment, and the adapter comment has no proof, and CR-01 shows it is already false for fork. The design rests entirely on Pi's session replacement. A later Pi change to `newSession` or `switchSession` that keeps the in-memory branch would leak with every test still green.

**Fix:** Add scenarios to `features/hook/additional-context.feature`, each with a SessionStart hook that gives context:
- `/new` then a prompt: the model call holds exactly one `SessionStart hook additional context` row, from the new session's `clear` run.
- A resume of another session: no row from the session you left.
- A fork at the first prompt: whichever count CR-01 settles on.

### WR-02: Compaction SessionStart context moved, with no scenario, and the docs row describes only the startup case

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-adapters.ts:796-809`; `docs/hooks-compatibility.md:178`, `:442`

**Issue:** The same adapter serves the compaction SessionStart (`sessionCompactCallback`, event-router.ts:1267-1310). This change moves that context, which the model sees, in three ways:
- **Manual `/compact` while idle:** before, the context sat after the next prompt. Now it is appended at once, after the compaction summary.
- **Auto-compaction before a prompt** (`_prepareRun`, run active): the context is held, then flushed *before* the prompt (`_startRun`, agent-session.js:1501-1504). Before, it came after the prompt.
- **Overflow recovery with `willRetry: true`** (agent-session.js:2705-2706): `agent.continue()` runs the retry model call before any flush. The next flush is at that turn's `turn_end` (agent-session.js:854-856), so the retry call does not see the context.

No scenario or router-level test asserts where a `source: "compact"` context lands. The router tests at event-router.test.ts:4626-4790 check only hook runs and stale guards. AGENTS.md "Behavioral tests" requires a scenario that fails without the change. The docs table row at `:442` says the message goes "before your first prompt", which is wrong for `compact`, and for `resume` and `clear`, where earlier prompts exist. The `:178` note covers only the streaming case and is marked unmeasured.

**Fix:**
- Add a scenario (in `features/hook/compaction.feature` or `additional-context.feature`): a SessionStart hook with `matcher: compact` gives context, the user runs `/compact`, then prompts. Assert the model call holds `SessionStart hook additional context: ...` after the compaction summary and before the prompt.
- Reword the `:442` row to name the placement for each source: startup before the first prompt, compaction after the summary, resume and clear at the point the session was opened.
- Either measure the `:178` note or keep it marked unmeasured, and add that a retry after an overflow compaction does not see the context.

## Info

### IN-01: The SessionStart failure log lost the plugin provenance that OBS-01 used

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-adapters.ts:803-808`

**Issue:** The removed buffer kept `scope`, `marketplace`, and `pluginId` "so OBS-01 debug telemetry can attribute leaks back to the contributing plugin". The new failure line `adaptObservation: session start context failed: <error>` names no plugin, though `context.attributedTo` is still there.

**Fix:** Build `failureLog` with the attribution, for example `adaptObservation: session start context failed for ${attributedTo?.pluginId ?? "<unattributed>"}@${attributedTo?.marketplace ?? ""}`.

### IN-02: Two SessionStart tests can no longer fail on the behavior their titles name

**File:** `test/bridges/hooks/event-adapters.test.ts:1970-1984`; `test/bridges/hooks/event-router.test.ts:2941-2988`

**Issue:**
- **Attribution test:** SessionStart no longer reads `attributedTo`, so "sends the SessionStart context of a fold that no entry is attributed to" gives the same result as the attributed case. It can never tell the two apart.
- **Stale-dispatch test:** "stale SessionStart stops after an injected dispatch await" asserts `messages` is `[]`, but its executor always resolves `{ kind: "noop" }` with no context. A stale run that wrongly called `sendMessage` would still pass. Stale dropping is covered elsewhere (dispatch.test.ts:1065-1102), so this assertion is vacuous.

**Fix:** Drop the attribution test, or fold it into the first one. In the router test, resolve the deferred run with `{ kind: "mutate", additionalContext: "stale context" }`, so `messages` being `[]` proves the stale send is dropped.

### IN-03: The "never thrown" comment covers only synchronous failures

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-adapters.ts:571-578`

**Issue:** `pi.sendMessage` is fire-and-forget over the async `sendCustomMessage` (agent-session.js:2860-2868). A rejection is reported by Pi through `runner.emitError`, as a user-visible extension error, not through `hookDebugLog`. One example is `appendFileSync` failing in `_persist` on a resumed session that is already saved. NFR-2 still holds, but "a send that throws is debug-logged" overstates what the try/catch covers. The prompt-context path has the same gap.

**Fix:** Say that only a synchronous throw, such as Pi's stale-context error, is debug-logged, and that Pi reports a failed write itself.

### IN-04: Comments edited in this phase name the wrong owner, and a research doc keeps the old design

**File:** `extensions/pi-claude-marketplace/bridges/hooks/index.ts:3-8`; `docs/research/parity-gaps/hooks.md:192`

**Issue:** The edited barrel comment says the "pending prompt context buffers" are "owned by routing-state.ts". They live in `createHooksRuntime` (`runtime.ts:317-330`), and `routing-state.ts` now holds only their types. The parity-gaps table still says SessionStart "context via buffer".

**Fix:** Name `runtime.ts` as the owner of the buffers in the barrel comment, and update the U34 row to "context sent as a hidden session message (HKRL-01)".
