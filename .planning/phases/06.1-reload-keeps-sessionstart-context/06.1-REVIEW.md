## Warnings

### WR-01: The `turn_end` check counts messages that never take a model call, so a mid-run compaction context misses the next call. This is a regression from iteration 2.

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-router.ts:1645`, with the JSDoc at `:626-633` and the comment at `:1636-1641`. Also `docs/hooks-compatibility.md:161`, `.planning/REQUIREMENTS.md:45` (HKRL-03), and the D-CF5-13 amendment in `.planning/PROJECT.md`.

**Issue:** `runPhase = event.context.pendingMessages.length === 0 ? "between" : "turn"` treats every pending message as one that "takes the next model call". Pi 1.5.1 builds that list as `[...agent.peekQueuedMessages(), ...this._pendingCustomMessages]` (`agent-session.js:668`). Two kinds of entries take no model call ahead of a steered context:

1. **Held custom messages (`_pendingCustomMessages`).** Every `sendMessage(..., { triggerTurn: false })` sent while the run streams goes there (`agent-session.js:1975-1980`). That includes the bridge's own PostToolUse, PreToolUse, and PostToolUseFailure context (`dispatch.ts:900-908`) and its queued-prompt context. Pi flushes them into the session at this same `turn_end` (`agent-session.js:854-856`), before `prepareNextTurn`. They never take a call. But they force `runPhase = "turn"`, so a threshold compaction in `_compactBeforeNextAssistantResponse` sends the compact context with `{ triggerTurn: false }`, and the very next call does not read it. If that call ends the run, the context waits for the user's next prompt. The model then runs the rest of the turn without its compaction context. Probe P1 shows this: call 3 holds the summary and `PostToolUse:Bash hook additional context: checked by hook`, but no `compact-ctx`. Iteration 2's code steered here. The post-preparation poll runs because the loop's `pendingMessages` is empty, so the context reached call 3 with no extra call.
2. **A follow-up after a turn with a tool call.** `peekQueuedMessages()` returns the follow-up queue when no steer is queued (`agent.js:212-215`). After a turn with a tool call, `hasMoreToolCalls` keeps the inner loop going, and the line-191 poll returns nothing. The tool-result turn takes the next call, not the follow-up, and the post-preparation poll would read a steer. The bridge cannot tell a follow-up from a steer in the peek. So holding is the safe choice there, but it misses one call. Probe P2 shows call 3, the tool-result call after the compaction, without `compact-ctx`.

The docs say "When a steer or a follow-up is queued as the turn before the compaction ends, that message takes the next model call". The JSDoc says "Pi gives that message the next model call". Both are false for case 2. Case 1 appears nowhere in the docs, and it contradicts HKRL-03 ("reaches the very next model call in every compaction path", with only the queued-message exception). The fixer's report admits case 1 ("The check counts held custom messages too ... the safe direction"), but this costs the model its context for the rest of the run. It is not just one turn late. No router row and no scenario cover either case. The `:524` scenario puts `context tokens` on the turn with no tool call, so it cannot see case 2.

**Fix:** Count only messages that Pi polls ahead of a steer. The bridge knows its own held carriers. They are custom messages of `claude-hook-tool-context`, and `claude-hook-additional-context` messages sent with `triggerTurn: false`. Pi flushes them at this turn end:

```ts
// HKRL-03: Pi flushes the custom messages held with `triggerTurn: false` at
// this turn end, so they take no model call; a queued steer or follow-up does.
function queuedAheadOfSteer(event: FollowUpTurnEnd): boolean {
  return event.context.pendingMessages.some(
    (message) =>
      message.role !== "custom" ||
      (message.customType !== TOOL_CONTEXT_CUSTOM_TYPE &&
        message.customType !== HOOK_CONTEXT_MESSAGE_TYPE),
  );
}
// ...
runPhase = queuedAheadOfSteer(event) ? "turn" : "between";
```

Another approach is `ctx.hasPendingMessages()`. It counts only the session's queued steers and follow-ups (`pendingMessageCount`, `agent-session.js:2056`). But it misses an extension's `deliverAs: "steer"` message, so it can add a call in that case. Whichever approach is chosen:

- Add a router row: a `turn_end` whose `pendingMessages` holds only a `claude-hook-tool-context` message, then a threshold `session_compact`. It should expect `{ deliverAs: "steer" }`.
- Promote probe P1 to `additional-context.feature`.
- Correct the JSDoc, the comment, the docs paragraph, and HKRL-03. They should say that a follow-up after a turn with a tool call also holds the context for one call, because Pi's peek cannot be told apart from a steer, and that held messages of another extension do the same.

### WR-02: A steer typed while Pi compacts still forces an extra model call, and the docs sentence that named it was deleted

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-router.ts:1312-1319` (`event.willRetry || betweenTurns()` decides the steer when the hook finishes); `docs/hooks-compatibility.md:161`; `.planning/REQUIREMENTS.md:45`.

**Issue:** `runPhase` is fixed at `turn_end`. But the context is steered later, at `session_compact`, after Pi's summary call or calls and after the SessionStart hook process has run. That is a window of seconds. Pi's steering queue is `one-at-a-time` by default (`agent.js:141`, `PendingMessageQueue.drain`). Suppose the user types a steer in that window:

1. The steer is queued before the bridge's context.
2. The post-preparation poll (`agent-loop.js:115-117`) drains only the user's steer.
3. The next call reads the user's steer without the context.
4. If that call has no tool call, the line-191 poll returns the context, `pendingMessages.length > 0`, and Pi makes one more model call for the hidden context alone.

Iteration 2's docs had a softened form of this: "When you steer the run at the same moment, the context can wait one more turn." The fix deleted that sentence. HKRL-03 now says "the bridge never adds a model call". That is not true for this path. I found this by reading Pi's source and did not measure it.

**Fix:** Decide at send time, when the queue state is known. Steer only when nothing is queued now:

```ts
event.willRetry || (betweenTurns() && !ctx.hasPendingMessages()),
```

`ctx` is already in scope in `sessionCompactCallback`. A held context then joins the session at the end of the steer's turn, and no call is added. Add a router row with `ctx.hasPendingMessages()` returning true after a `between` `turn_end`, which should expect `{ triggerTurn: false }`. If the check is not adopted, put the residual back in the docs and the requirement as a case that adds a call.

### WR-03: A context edit that writes string content still causes a duplicate value on resume or fork

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-adapters.ts:830-832` (`if (typeof message.content === "string") return [];`); `test/bridges/hooks/event-adapters.test.ts:2396-2398` (the row `ignores text content without details ...`).

**Issue:** The WR-02 fix rests on the claim that keys come from "the text the model sees", because a context edit replaces `content` and keeps `details`. Pi's `ContextEditEntry.replacement.content` is `ContextEditableContent`, which includes `CustomMessage["content"]`, that is `string | (TextContent | ImageContent)[]` (`session-manager.d.ts:117-125`). `projectContextEntry` passes a string replacement through unchanged for a custom message (`session-manager.js:248-251`). It wraps a string only for `assistant` and `toolResult`. Suppose a context-trimming extension rewrites the SessionStart message as `"SessionStart hook additional context: ss-ctx"`. `messageKeys` then returns no keys for a message whose text the model sees. The next resume or fork sends `ss-ctx` a second time. Before `c777ac5`, the `details` branch covered this case, so this one shape got worse while the array shape was fixed. The unit row `ignores text content without details` pins the resend as intended.

**Fix:** Read a string content as one text part:

```ts
const parts =
  typeof message.content === "string"
    ? [{ type: "text" as const, text: message.content }]
    : message.content;
return parts.flatMap((part) => { /* unchanged */ });
```

Change the `text content without details` row to expect `[]`. Add a `heldEdited` variant whose replacement is a string.
