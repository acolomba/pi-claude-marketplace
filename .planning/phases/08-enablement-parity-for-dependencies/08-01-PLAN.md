<objective>
Teach `/claude:plugin enable` about plugin dependencies. Enabling a plugin resolves
its declared dependency closure transitively in the same scope, re-materializes
every member whose record is installed-and-disabled through that record, and
reports the FULL closure -- one row per member, already-enabled ones included --
in the single terminal notification the verb already emits.

Purpose: EDEP-01 and the enable-side half of EDEP-03. It also lands the
`dependency enabled` closed-set token (D-08-02) that plan 08-03's install-side
arm reuses, because a closed-set amendment must arrive with the first row that
renders it.

Output: a dependency-aware enable orchestrator, a multi-row enable message
composer, the 60th closed reason, and one new catalog state documenting the
cascade block.
</objective>

**Closure resolution (`resolveEnableCascade`, new helper in `enable-disable.ts`).**
Inside the existing locked transaction closure, before the enable branch runs:

1. Call `buildScopeDeclarationDetail({ state, locations })` to get the scope's
   whole declaration map, keyed by `<name>@<marketplace>`. It is offline,
   fail-closed (D-05-07) and already covered by the network-free gate. On its
   `ok: false` arm, throw `EnableRefusedError("unreadable", result.cause.message)`
   -- the same carrier shape `uninstall.ts::UninstallRefusedError` uses, so the
   existing transaction catch renders a `(failed)` row with the declarer named on
   the cause line and nothing is saved.
2. Call `resolveDependencyClosure` with `rootKey` = `${plugin}@${marketplace}`
   and these three arguments, each of which is load-bearing:
   - `installedKeys: new Set()` -- EMPTY. `walkDependencyEdge` returns WITHOUT
     recursing on an `installedKeys` hit, so any non-empty set truncates the walk
     at the first installed dependency and EDEP-01's word "transitively" would be
     false. For `enable`, being already installed is the PRECONDITION for being
     enabled, not a reason to stop walking.
   - `lookup` -- a reader over the map from step 1. A key the map holds answers
     `{ kind: "found", dependencies }` with that record's declarations. A key the
     map does NOT hold answers `{ kind: "found", dependencies: [] }`, NOT
     `{ kind: "absent" }`: the enable cascade's question is "is there a record
     here to turn on", and answering absent would reach the walk's `not-found`
     arm and refuse an enable over a missing dependency that LOAD-01's load-time
     check already owns reporting.
   - `knownMarketplaces` -- the union of `Object.keys(state.marketplaces)` and
     every marketplace named by a declaration in the map. D-03-08's guard exists
     to refuse an INSTALL into a marketplace the scope has not added; this cascade
     installs nothing, so seeding the guard so it cannot fire is the truthful
     reading, and membership is decided by the record in step 3 instead.
   The only failure arm this configuration can still reach is `cycle`; carry it
   through as `EnableRefusedError("dependency cycle", ...)` with the chain on the
   cause line, matching `install-cascade.messaging.ts::closureFailureFacts`'s
   cycle arm.
3. Classify every non-root closure member against the LIVE locked snapshot by
   exact-key lookup (`state.marketplaces[member.marketplace]?.plugins[member.name]`,
   no case folding, no normalization) into an `EnableCascadeDisposition`. This
   task implements the `"re-enabled"` arm only (record present and
   `isRecordedButDisabled` true); leave the other two arms as explicit
   compile-checked cases Task 3 fills.

**Per-member materialization (`runEnableCascadeMembers`, new helper).** Drive the
members in the walk's post-order (dependencies before dependents, root last)
through `runPhases` from `transaction/phase-ledger.ts`, one `Phase` per member,
so a member failure unwinds every member this command already turned on --
the same all-or-nothing stance D-03-07 gives the install cascade, and the reason
a half-enabled graph never reaches disk (NFR-3). Each phase's `do` calls
`transaction.runInstallLedger` on the OUTER transaction's state snapshot with
`pinVersionOverride` set to the member record's own `version`,
`allowExistingRecord: true`, `partial` derived from the member record's own
`compatibility.installable`, and `removalOps: createRemovalOps()` -- the exact
argument set `runEnableBranch` already passes, now per member. Each phase's
`undo` puts the member BACK to disabled via `cascadeUnstagePlugin` +
`toDisabledRecord`, the pair `runDisableBranch` already composes; it must NOT
delete the record, because the record is what owns those artifacts. Clear the
Phase 6 `dependencyDisabled` marker on each record this write turns on, in the
same write. Never call `installPlugin` -- it opens a second `withStateGuard` on
the same `stateLockFile` and `proper-lockfile` (`retries: 0`) is not re-entrant.
The root keeps going through the existing `runEnableBranch`, unchanged.
