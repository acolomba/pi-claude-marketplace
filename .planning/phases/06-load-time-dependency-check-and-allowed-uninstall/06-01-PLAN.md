<objective>
Land the load-time dependency check end to end for its thinnest real case: an
installed, declared-enabled plugin whose declared dependency is not installed in
the same scope is disabled at `/reload` and reported with the upstream remedy.

Purpose: LOAD-01 is the whole of this phase's new machinery, and every later
plan (the disabled arm, the out-of-range arm, the LOAD-02 lift, LOAD-03's
allowed uninstall) hangs off the seams this plan proves. Proving the full
persistence to planner to apply to renderer path on one arm first means an
architectural dead end costs one plan, not five.

Output: a persisted `dependencyDisabled` marker, a constraint-preserving
declaration walk, a new reconcile verdict module with the propagation fixpoint,
a new plan bucket, a new apply step that owns its own lock, a new outcome arm,
a new closed-set reason token, and a widened cause trailer gate.
</objective>

**R1 — where the interpolated remedy legally renders.** Resolved: widen
`PluginDisabledMessage` with `cause?: Error` and widen the trailer gate in
`shared/notification-grammar.ts` to admit `status === "disabled"`. RESEARCH.md
called this an unprecedented shape; it is not. The line immediately above that
gate already pushes a 4-space-indented trailer onto a `(disabled)` row when
`p.enableHint === true` (the frozen `ENABLE_HINT_TRAILER`). A trailer on a
`(disabled)` row therefore has precedent; only the interpolating trailer is new,
and the `cause:` chain is the one channel in this grammar that legally
interpolates an identifier.

Three concrete hazards were found by reading the three gate tests RESEARCH.md
and PATTERNS.md both flagged as unread. Task 3 must handle all three:

1. `tests/architecture/notify-grammar-invariant.test.ts` declares
   `DISABLED_TOKEN_RE`, which admits no `{reasons}` brace and no trailing cause
   line. It is applied only to `DISABLED_VARIANT_FIXTURES`, a hand-written
   array. Leaving both untouched keeps the suite green while the new row is not
   covered at all — the project's own "green runs that checked nothing" failure
   mode. The regex must be widened to admit an optional reasons brace and a
   LOAD-01 fixture must join the array.
2. The `RECON-04` subject-first test in the same file builds
   `ROW_ICONS_AT_START` from `●`, `○`, `⊘` only — it omits the `◍` glyph the
   `(disabled)` row uses — and it strips a leading two spaces from every line
   before testing, which turns the 4-space cause line into a 2-space line and
   defeats its own `line.startsWith("    ")` escape. Adding a LOAD-01 fixture to
   `RECONCILE_APPLIED_FIXTURES` requires fixing both.
3. `tests/architecture/notify-stamp-coverage.test.ts` `deepEqual`s the stamp
   list built from `appliedOutcomes()`. `disabled` is already in its
   `transitionStatusList`, so the new outcome is picked up by the filter and the
   expected array must gain its row — at `severity: "warning"`, which is a
   severity no transition row in that array carries today.

RESEARCH.md's Example 4 target block proposes the summary line
`A plugin operation completed with warnings.` That sentence is wrong and must
not be copied into the catalog: `SUMMARY_GRAMMAR` in
`notify-grammar-invariant.test.ts` and the builder in
`shared/notification-summary.ts` both fix the warning verb as
`needs attention` / `need attention`. The correct summary for a single
warning-severity row is `A plugin operation needs attention.`

**R2 — who writes the marker.** Resolved: a new `applyDependencyDisables` step
in `apply.ts`, called from `applyPlan` after the two `applyPluginToggles` calls,
taking its own per-scope lock. `applyPluginToggles` delegates the whole record
write to `setPluginEnabled` and never touches a record, and `enable-disable.ts`
is out of this phase's boundary. The step is modelled on
`orchestrators/reconcile/backfill.ts`, not on `applyPluginToggles`.

**R3 — sibling versus reuse of `buildScopeDeclarationIndex`.** Resolved:
sibling, in `dependency-index.ts` itself. Two independent blockers confirmed:
the existing walk flattens every declaration to a bare `name@marketplace` key
and discards `dep.version`, and its `exclude` parameter models a "key under
decision" that the whole-scope load-time question does not have. Keeping the
sibling in `dependency-index.ts` inherits that file's existing network-free gate
entry rather than requiring a new `NETWORK_FREE_TARGETS` member.

**R4 — retire or repurpose the old refusal token.** CONTEXT.md D-06-07 is a
locked decision: retire. Plan 06-03 executes it. Not re-opened here.

**R5 — does the reconcile-driven uninstall also name dependents?** Resolved:
**no, not in this phase**, and the reason is structural rather than budgetary.
On the reconcile surface the same fact is already reported, and reported better:
the load-time check disables each dependent and gives it its own row with the
full remedy naming both parties, where a dependents brace on the uninstalled row
would only list names. Carrying both would report one fact twice inside a single
emission, which RECON-04's single-emit discipline treats as a defect. LOAD-03's
"the row names the dependents" is therefore satisfied on the standalone command
surface only — the one surface where the user typed `uninstall` and gets no
immediate load-time follow-up. One consequence to state plainly: because the
verdict is computed in the read pass and `applyPluginUninstalls` is the first
apply step, a reconcile pass that uninstalls X reports X's dependents as
unsatisfied on the NEXT reload, which is exactly what LOAD-03's "each becomes
unsatisfied at the next load" says.
