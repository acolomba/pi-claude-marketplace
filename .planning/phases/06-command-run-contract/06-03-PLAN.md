<state_contract>
State belongs to the command run, never a process singleton or formatter. Introduce only fields read in this plan: hasOutcome, needsReload, settled, and delivery ("open", "recovering", or "closed"). Non-command origins have no command completion state. Allocate the command state before inventory reads and carry the same object into the completed NotificationRun; setup-error delivery uses this same state without fabricating softDeps. Test seeds return fresh state.

Before each attempted command emission, OR its resolved needsReload into run state; a later false cannot clear true. Count a command outcome only after successful machine append. Classification is exhaustive over the presentation union. Outcomes: cascade, marketplace-info, plugin-info, marketplace-info-cascade, plugin-info-cascade, marketplace-not-added, reconcile-pending-empty, prune-empty, prune-committed-warning, usage-error, usage-info, internal-error. Non-outcomes: diagnostic, device-flow-prompt, reconcile-applied-cascade, reconcile-aborted, plugin-path-skipped, async-rewake-summary, stop-override-cap. Count only command-origin entries; load/hook runs never satisfy completion. Empty diagnostics and empty rewake summaries keep their existing no-op behavior.

Keep one low-level append site in the dispatcher, retaining the original receiver. On an ordinary append exception set recovering BEFORE reporting, resolve an internal-error from that failure using the same identity and accumulated reload, and attempt append once directly through the low-level helper. No recursive call through normal emission. If recovery succeeds, count the delivered internal-error as an outcome and return delivery to open. Later command emissions before settlement proceed normally, use live mode, and contribute their outcomes and reload truth. If recovery also fails, set delivery to closed, invoke hookDebugLog with an already safe message, and contain a throwing logger. Swallow the original transport exception inside dispatch so existing operation catches cannot classify it as a business failure or trigger rollback. Never use a second sink.

A failed ordinary append of an internal-error itself still allows one direct recovery attempt; a failure of that recovery append closes delivery and never restarts the root error reporter. The one-attempt bound applies to recovery of each failed ordinary append, not to all later emissions of the run. A separate later append failure after successful recovery receives its own single direct error attempt. Suppress later emissions for delivery failure only when that recovery also failed and delivery is closed. Successful recovery satisfies the outcome check but does not suppress later business results or a later unexpected-throw error. The settled guard remains separately required by D-10. Do not retry/abort/replay business work merely because output failed. Existing operations finish their current flow. D-08 is a delivery contract, not a new transaction policy.
</state_contract>
