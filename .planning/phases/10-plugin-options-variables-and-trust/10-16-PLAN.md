<objective>
Give a plugin's hooks their option variables in the session that installed, enabled, updated,
or reinstalled the plugin.

Purpose: PG-CORE-03 under D-PG10-10 and D-PG10-15. A command that stages a plugin's hooks
also puts them in the running session's routing table, so the hooks run at once, with no
`/reload`. Plan 10-08 gave a hook its options at every load, from the record. The entry that
a command caches still holds no options, so in the session that ran the command a hook runs
without its `CLAUDE_PLUGIN_OPTION_<KEY>` variables until the next load. This plan gives the
install-time producer the options as a required input and feeds it at its four call sites.

Output: the producer's input, the options on the values that carry a member to the hooks
hydrate, the four call sites, and three scenarios.
</objective>

## Planner decisions

- **The producer's input is the resolved options, required.** `ReadAndCachePluginHooksOptions`
  takes a `ResolvedOptions` member, as the carriers do. A caller with no options passes
  `resolveOptions(undefined)` explicitly.
- **Every call site holds a resolution.** Each computes `resolveOptions` of the
  `declaredUserConfig` of the resolution it takes the plugin root from. No call site reads
  the record's field, so `recordedOptionsOf` stays the one reader of the record.
- **Tracer on the install path.** The input is required, so the two enable call sites and
  the update call site state `resolveOptions(undefined)` in Task 1. Task 2 gives each its
  options, with its own red scenarios.
- **The scenarios prompt in the session that ran the command.** They are in
  `features/hook/process.feature`, beside the scenario of plan 10-08 that starts a new
  session; they differ from it by having no new session.
