<objective>
Keep each plugin's option schema on its install record, and export every option that has a
default to the plugin's hooks as `CLAUDE_PLUGIN_OPTION_<KEY>`.

Purpose: PG-CORE-03 under D-PG10-10, D-PG10-14, D-PG10-15, and D-PG10-23. Three readers of
options never open a manifest: the hooks hydrate at load, the built-in MCP registration, and
the process-variable pass. A manifest read at load would cost a parse per plugin, would miss a
plugin whose options live in the marketplace entry, and for a path-source plugin could be
newer than the staged content. So the declared schema rides the record, as `mcpServerConfigs`
does, and every reader goes through one function that validates it again, because a project
record is a file a repository can commit. Hooks are the first consumer: both spawn lanes build
their environment in one function. Under D-PG10-19 (pending maintainer review), a declared
default counts as a saved value here, which is more than Claude Code 2.1.323 does for hooks.

Output: the record field at all its write sites with one reader, the options on the hooks
routing carriers, the hook environment, and two scenarios.
</objective>

## Planner decisions

- **The field is present only when the plugin declares `userConfig`.** A declared empty
  schema is stored as an empty object; an undeclared plugin's record has no field. So no
  record text that a test or a scenario pins today changes, and the difference that
  D-PG10-21 needs between "declares none" and "declares options" survives a load.
- **The reader lives in `persistence/state-io.ts`.** `recordedOptionsOf(record)` returns
  `ResolvedOptions`. `bridges/hooks` and `orchestrators` both reach it, and `domain` stays
  pure.
- **The carriers take the resolved options as a required member.** A fixture or a producer
  that has no options passes `resolveOptions(undefined)` explicitly.
