<objective>
Fill `${user_config.KEY}` in the five MCP fields that take variables, under both MCP
implementations, without writing an option value into `mcp-adapter.json`.

Purpose: PG-CORE-03 under D-PG10-11, D-PG10-12, D-PG10-21, and D-PG10-23. Claude Code
2.1.323 fills options in `command`, `args`, `env`, `url`, and `headers` after the path
variables. Both encodings of this extension go through one walk, `expandClaudeValue`, which
today leaves `${user_config.KEY}` as text because the key holds a dot. Under pi-mcp-adapter
the entry gets a reference to the process variable that plan 10-10 sets and the adapter
expands at connect; under Pi's built-in MCP the value is filled in memory at each
registration, where no file is written. Plan 10-11 already leaves out a server that names an
option with no value, so every reference this plan writes has a value.

Output: the option pass of the walk in both forms, the adapter stage's references and
environment overlay, the home-path reason of the `option-blocked` notice, the built-in fill,
conformance cases against pi-mcp-adapter and Pi, and the scenarios of
`features/mcp-server/options.feature`.
</objective>

## Planner decisions

- **One walk, two forms.** The option pass of `expandClaudeValue` emits a `ref` segment with
  the owned name for the adapter encoding and a `text` segment with the value for the
  built-in encoding. It never goes through `segmentFor`.
- **The home-path case reuses the `option-blocked` notice.** Its closed reason set gains one
  member at its tail, for an option value that would be home-expanded at the start of
  `command` or of an `args` element. The stage decides it with the adapter's own home rule,
  read from the adapter's source and pinned by the conformance case of plan 10-02.
- **Scenario tags.** A scenario whose result is the same under both implementations is
  `@mcp`. The reference-only entry is `@adapter-only (PG-CORE-03, D-PG10-11)`, and the
  registry value is `@builtin-only (PG-CORE-03, D-PG10-12)`.
