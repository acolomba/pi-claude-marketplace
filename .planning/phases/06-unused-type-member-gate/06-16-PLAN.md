<the_governing_risk>
Read this before the first task. It is the reason the plan is shaped and ordered the way it is.

**An engine change can clear rows by becoming sloppy, and a new category is new permissive surface by construction.** Four of 06-15's six corrections widened a proof that already existed; three of this plan's four changes create a class of accepted exception that did not exist at all. A manufactured observation is worse than a deleted field, because the field comes back in one revert while a permissive prover silently absolves every future member of the same shape.

06-03 wrote the rule this plan is governed by: *an exemption category earns its keep by naming what it refuses, so every new proof ships with the counterexample that fails it.* A category that accepts its two target rows and refuses nothing has not earned its keep and must not be written.

Seven obligations follow. They are task requirements, not advice, and each task's `done` restates the ones that bind it.

**1. Every new proof ships the counterexamples that fail it, in the same commit.** For each change the neighbouring shapes that must still be refused are named in the task. Write them as controls beside the acceptance.

**2. Prove each new refusal discriminates by writing the permissive variant of its own prover.** This is 06-15's strongest result and it is mandatory here. A refusal control on a prover that did not exist before cannot fail RED -- there was nothing to refuse it with -- so RED alone measures nothing. Instead, after the prover works, mutate it into the sloppy version the refusal is meant to forbid (accept any member of the constrained literal; accept a pin that mentions only one side; accept an upstream that does not declare the key; follow a destructured binding key-blind), run the whole repository's gate suites against the mutant, and record which controls break. A refusal no mutant can break is not yet a refusal: re-derive it until one does.

**3. The delta must be EXACTLY the predicted rows.** After each change take `node scripts/check-unused-type-members.mjs --json`, diff it against the snapshot taken immediately before by `(path, owner, key)` set difference, and require that the rows which left `unread` are precisely the ones the change was predicted to clear, named below by coordinate. A change that clears an unrelated row has become permissive: narrow it or revert it. Do not rationalise it after the fact.

**4. Take the engine-alone zero-delta measurement on every task, including the last one.** A contract entry is opt-in, so widening a prover cannot move a row until somebody writes an entry. That makes the engine-alone measurement free and exact, and 06-15 took it four times with a zero result every time. It applies to all four changes in this plan, including the arrival correction -- **measured fact to confirm before relying on it: the recorded transfer list is consumed by the contract engine and by nothing else**, so an arrival widening cannot credit a member with no entry. Confirm that by reading the consumers before the first measurement, and if it is no longer true, say so and fall back to the stricter whole-tree control.

**5. Nine named rows must not move.** Four belong to source plan 06-17: `domain/components/hooks.ts:77:3` and `:79:3`; `orchestrators/edge-deps.ts:58:3` and `:64:5`. Naming any of them in a contract entry is forbidden, and any of them changing status is a permissiveness finding to investigate before continuing. D-32-05 in particular is a recorded decision that this plan has no authority to revoke.

**6. 06-07's negative controls must still pass, and must still REJECT an always-passing gate.** Seven defective gates the harness must refuse, including an always-clean mutant rejected on report *content* rather than exit status. Run once at the end on the final snapshot; budget roughly seven minutes at about 2.1 GiB. Treat any change in which control fires as a finding rather than noise.

**7. Performance is a real constraint and has been blown twice in this phase.** 06-02 aborted at 4 GB and 06-04 exhausted 4M and then a raised 40M transfer steps in three and a half minutes. The live analysis today runs 83.85 seconds at 2.049 GiB peak resident size and 3,030,520 transfer steps against an adopted cap of 12,000,000. **This plan's budget: wall time at most 100 seconds, peak resident size at most 2.40 GiB, transfer steps at most 6,000,000.** Every change in this plan is predicted to run inside the contract evaluator, which executes once per entry, so the **predicted transfer-step count is unchanged at 3,030,520**; a step count that moves has a named cause or the change is narrowed. Measure with `/usr/bin/time -v` on the real tree after every change and record the three numbers per task. Exceeding the budget means narrowing or reverting. It never means raising the adopted cap: a cut-off run must stay a refusal rather than a partial answer.

<standing_obligations>
These apply to every task and are part of each task's `done`.

**No product source is touched.** This plan edits nothing under `extensions/`. That is not a convenience: it means no contract coordinate anywhere can shift, which removes the whole class of drift 06-12 hit twice and 06-15 had to re-derive. If a task appears to need a source edit to make a proof work, that is the proof asking to be narrowed, not the source asking to be reshaped. No task may convert a method to an arrow property, restructure a declaration to give a prover an exact type, widen a declared type to manufacture a read, or add a test whose only effect is to make a declaration look used (D-02).

**One definition, never a copy.** 06-15 MOVED `propertySymbolOf` to the shared model leaf rather than pasting a second copy into the contract engine, and that rule holds here. Where a correction needs a helper another module already owns -- binding-source resolution, callee-body resolution, return collection -- export it from its current home or move it to the shared leaf both modules import. If a helper moves, every existing control that exercises it stays in place and stays green; a relocation that quietly drops an ordering, call-count or fault-injection assertion is a regression even when the suite is green.

**Category schema keys are scoped to their own category.** 06-15's `conditional-clause` established this and it is what stops an allowance borrowed from one category reading as valid evidence in another. Each new category declares only the keys its own proof consumes, and an entry naming a key from a different category must be refused as an unknown key. Do not add a key to `commonKeys` to make two categories share it.

**A new category must be disjoint from the ones it sits beside.** If a member's evidence satisfies a stronger existing category, the new category must refuse it and say which category applies instead. A soft substitute for a strict proof is the failure mode these categories exist to prevent.

**The three-way exit contract is load-bearing.** Exit 1 is a member verdict. Exit 2 is a setup failure -- a stale, contradictory or unprovable entry, or an exhausted budget -- and is never a quiet allowance. After every change require the analyzer to exit 1 with member findings. Exit 2 means a coordinate is wrong or a proof refused, and it is a blocking failure to read and fix, never to work around.

**Every contract entry is submitted to the real engine before it is written.** Draft one entry at a time, derive every coordinate from the compiler's own view of the syntax, run the analyzer, and keep the entry only if the engine accepted it. Record every refusal with the engine's verbatim message. Never write an entry the engine refused.

**Fixtures are reduced by hand from the real shape.** Never paste an expected observation out of the analyzer's own enumeration. The contracts fixtures compile under `exactOptionalPropertyTypes`, matching the analysed tree; keep them there, because a fixture compiled under a weaker option proves the engine under a configuration the live entries are not validated under.

**Comments cite durable IDs only.** Any comment this plan writes cites requirement and decision IDs. Planning identifiers -- phase, plan, wave, pitfall or pattern numbers -- are forbidden in source per `CLAUDE.md` and `.claude/rules/typescript-comments.md`. The analyzer modules carry their design rationale in file and function headers; when a correction changes what a header claims, rewrite the header rather than leaving it stale.

**Commit discipline.** One commit per task, or the RED-then-GREEN pair where the task is TDD, Conventional Commits, no milestone or phase identifiers in subject or body. Run `SKIP=trufflehog pre-commit run --files <the task's files>` before each commit and re-run until clean; a failed hook means the commit did not happen, so never recover with `--amend`. Never pass `--no-verify`.

**Test-run hygiene.** Run suites under a hermetic `HOME`. A shared `PI_CODING_AGENT_DIR` is not a valid substitute -- it collapses every suite's user scope into one directory and manufactures a failure that looks exactly like a regression.

**Fallow and the corresponding-test gate react to module surface.** Exporting a helper, moving one between modules, or adding a module all move what `fallow dead-code` and the corresponding-test gate see, and fallow's cognitive ceiling of 15 is computed independently of ESLint's, so a green lint is not proof. Split a function rather than adding a threshold override; the analyzer files still carry none. Clean up only the orphans the change itself created.
