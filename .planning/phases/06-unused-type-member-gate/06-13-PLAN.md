<disposition_ladder>
Every row in this plan is settled by the same four-way ladder, applied in order, and the outcome is written into the row's ledger disposition before the task ends. No row may be left `pending`.

1. **Load-bearing external pin.** The member states a shape this project does not own -- a peer-dependency declaration, a written file's schema, a value handed to a consumer outside the tree. Do NOT remove it. Make the compiler check it where it is not already checked, then earn a validated contract entry for it if one of the five categories fits. If no category fits, record it outstanding with the exact refusal reason.
2. **Load-bearing local proof.** The member exists so an assertion, a `satisfies` constraint or a conditional filter can do type-system work. Prove it load-bearing by deleting it and observing `npm run typecheck` fail, then restore it and record that measurement as the evidence. Do NOT keep the deletion.
3. **Analyzer artifact.** A real read exists but the analysis deliberately under-credits it -- a same-spelled key on two or more union arms, a filter form the engine does not prove, a deliberate cross-layer duplicate whose reads land on its twin. Touch no source. Record the exact witness site that proves the read is real and name the engine or cross-owner work that would credit it.
3a. Under-crediting is the designed direction (06-06). An analyzer artifact is a finding about the analyzer, never a defect in the product, and never a reason to edit `extensions/`.
4. **Genuinely dead local surface.** No production read, no test read, and removal provably changes no type and no behaviour. Remove it, and record the measurement that proved both.

A row may only leave the unread set by 1 (as a validated contract), by 4 (the declaration is gone), or by a real read appearing. It may NEVER leave by widening a proof, by adding a test written only to make a declaration look used (D-02), or by deleting a member whose absence the compiler does not notice but a reader would.
