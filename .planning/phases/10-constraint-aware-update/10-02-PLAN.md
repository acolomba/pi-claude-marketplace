<objective>
Make the gate actually select a version. Stage one probes the plugin's release
tags -- the source repository's for a git-backed source, the marketplace clone's
own for a relative-path source -- picks the highest tag satisfying the
intersected range, and threads that pin into the candidate resolution so the
swap writes the right commit AND the right version string.

This is the expansion that turns plan 10-01's held row into UPDT-01's positive
behaviour. It also closes a defect the phase would otherwise ship: as written
today `deriveUpdateToVersion` returns a `sha-`-prefixed pseudo-version for ANY
git-backed source with a resolved sha, so a tag-pinned update would record the
wrong version even though it fetched the right commit.

Purpose: UPDT-01 for both source kinds, with the record telling the truth about
what landed, and with one tag listing per repository per run.

Output: the gate's stage-one arms and its run-scoped memos, `resolveUpdateCandidate`'s
pin plumbing on both resolver callbacks, the corrected `toVersion` derivation,
and the memo pair threaded from the update run.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote git repository -> tag listing -> pin selection | An untrusted remote advertises the tag names and oids the gate selects a checkout from. |
| local marketplace clone -> tag listing -> pin selection | The marketplace repository's own refs decide which tree a path-source plugin is materialized at. |
| host credential bundle -> tag listing call | A credential composed for the clone path is reused for the listing call. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-06 | Tampering | tag selection | high | mitigate | A crafted tag name cannot select an arbitrary ref: `selectHighestSatisfyingTag`'s `readPinCandidate` rejects any candidate whose name does not start with `${pluginName}--v`, and this plan reaches that selector only through the two existing probes -- an acceptance criterion pins that the gate names the selector zero times and the git surface zero times. |
| T-10-07 | Tampering | pin materialization | high | mitigate | The pin travels as an oid through the resolver's own callbacks into the already-pinned arms of `materializePluginClone` / `materializeMarketplaceTagClone`; `entry.source` is never rewritten, and an acceptance criterion greps for the mutation. |
| T-10-08 | Information disclosure | credential handling on the listing | high | mitigate | AUTH-09: `preparePluginUpdate` composes ONE host bundle and hands the same object to the clone probe and the gate; the gate reads no field of it and places no credential value on any returned arm. The failure arm carries the transport classification and the rendered range only. |
| T-10-09 | Spoofing | recorded version | medium | mitigate | The recorded `toVersion` for a pinned update is the tag's own `version` string from the probe result, not a value derived from the sha, so the record cannot claim a version the tag did not name. A dedicated case asserts it. |
| T-10-10 | Denial of service | bulk tag traffic | medium | mitigate | One memo pair per run bounds listings to one per repository URL and one per marketplace root; memos are written on success only, so a failure is still retried rather than cached. Three cases assert the counts. |
| T-10-SC | Tampering | npm/pip/cargo installs | low | accept | No runtime or dev dependency is added; the Package Legitimacy Gate is recorded as not applicable in RESEARCH.md. |
