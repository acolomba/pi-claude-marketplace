Add performs, in order after its state commit: marketplace-names file invalidation for the resolved scope, then plugin-index memory-and-file drop for the recorded marketplace. Remove performs those same two cache operations after its locked state transaction and before data/clone hygiene. Update drops the refreshed marketplace's plugin index after the refreshed state/manifest is durable and before any plugin cascade. Each operation preserves its established catch boundary and user-visible result.

## Edge assumptions

- Plan 05-06 completed and its summary identifies one production-used transition cache shared by completion reads and existing invalidator adapters. This plan must extend that exact identity instead of creating a peer instance.
- Plan 05-06 removed the dead marketplace-name memory reader but retained schema-version-2 file invalidation. Add and remove therefore invalidate the names file through the cache contract without introducing a replacement names map.
- The transition cache binding is an explicit phase sequencing contract. Plan 05-09 owns moving the already-working graph to one extension-lifecycle instance, and Plan 05-10 owns terminal transition/reset removal.
- `addMarketplace` still has genuine production callers in bootstrap, import, and reconcile composition. `removeMarketplace` still has a reconcile caller. Cache-bound production bindings must preserve those public compositions without optional cache selection or a test-only factory.
- Marketplace update has named and all-target entry points. A successful no-change refresh still invalidates because authoritative manifest content was read and persisted before change classification.
- Add/remove cache hygiene failures remain swallowed after the primary mutation. Update cache hygiene failures remain swallowed after refresh persistence. These failures cannot roll back state or emit a second notification.
- Ordinary invalidation behavior is reproducible with schema-valid files and directories in a case-owned temporary tree. Per D-05-01, tests must use the real 05-06 cache adapter and filesystem behavior rather than a fabricated cache callback.
- Separately constructed test caches retain independent memory. A case that warms one cache and mutates through another must expose the wrong-instance defect by returning the stale row from the first cache.
- Plugin mutation invalidators belong to Plan 05-08. Extension composition and joined add/bootstrap/reconcile proof belong to Plan 05-09. This plan must keep both file families outside its diff.

## Trust Boundaries

| Boundary                                           | Description                                                                                                                                                   |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Command composition -> marketplace handlers        | The cache instance captured for completion reads crosses into add/remove/update command execution and must retain one identity.                               |
| Durable marketplace mutation -> cache invalidation | Cache effects occur only after authoritative state/manifest persistence and cannot corrupt or reverse the primary operation.                                  |
| Scoped cache path -> real filesystem adapter       | Names and plugin cache paths derived from `ScopedLocations` cross into targeted unlink behavior; unrelated scope and marketplace files must remain untouched. |
| Cache invalidation -> later completion read        | The next read must observe authoritative rows through the same instance; a second cache or interaction-only double can hide stale data.                       |
| Update refresh -> plugin cascade                   | Plugin-index invalidation must complete before a cascade can resolve or expose the refreshed marketplace contents.                                            |
