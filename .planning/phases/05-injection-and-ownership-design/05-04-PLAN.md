<interfaces>
Create `HooksRuntime` and `createHooksRuntime()` in `bridges/hooks/runtime.ts`. The runtime is one cohesive object with private routing, settle, and async-rewake substate. It exposes behavior-oriented operations only: registration-generation transition/checks; parsed-config and routing-bucket reads/mutations; pending SessionStart context append/drain; settle message and bounded-reentry transitions; async child registration/removal/enumeration; and per-location PID-table operation serialization. Do not expose Maps, arrays with write authority, counters, child-entry mutation, or a whole-runtime reset.

Preserve `RoutingEntry`, `CacheEntry`, and `PendingSessionStartContext` as production types in `routing-state.ts`, but move their mutable storage into the runtime. Preserve the required hooks hydration reader produced by 05-02 and pass it independently of the runtime; the reader is an I/O capability, while the runtime owns in-memory lifecycle state.

`registerHooksBridge`, hydration/rebuild helpers, dispatch factories, event adapters, settle factories, `dispatchHookExec`, and async-rewake registry operations receive the runtime explicitly or are returned as closures already bound to it. A caller may not select a hidden default runtime.
</interfaces>
</context>

## Edge assumptions

- Pi does not provide a verified unregister/dispose contract for extension callbacks. This plan must prove invalidation by registering twice against one runtime and driving the old captured callbacks; it must not add or require a disposal method.
- Re-entry into `registerHooksBridge` on the same runtime is the production reload boundary already evidenced by the code. A separate invocation of the extension factory constructs a separate runtime and therefore cannot see another lifecycle's memory.
- `shutdownInMemoryChildren` remains a genuine registration/reload operation because production calls it. Tests may drive that public lifecycle behavior, but the runtime itself has no test cleanup operation (D-05-06, D-05-07).
- Persisted PID files intentionally outlive in-memory child handles. Moving the registry and per-path promise chains changes memory ownership only; orphan probing, marker verification, unlinking, and the persisted schema remain unchanged.
- Plan 05-02's hydration reader contract is available and required. Runtime ownership must not absorb it into a dependency bag or recreate a filesystem default inside a consumer.
- Command/reconcile mutation-path propagation is the separate 05-05 outline row. This plan leaves every hooks API explicitly runtime-capable and proves the registration-to-callback path without assuming that Pi disposes old registrations.

## Trust Boundaries

| Boundary                                          | Description                                                                                                                                |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Extension lifecycle -> registered callback        | A callback can outlive the registration generation that created it and must not act on the next lifecycle's state.                         |
| Persisted hooks state -> runtime routing          | Stored marketplace/plugin records become executable routing entries only after hydration, validation, and rebuild into the owning runtime. |
| Hook result -> pending/settle state -> Pi message | Plugin-controlled results can append system context or trigger bounded follow-up turns and must retain scope/plugin attribution.           |
| Spawned child -> terminal callback -> Pi session  | Untrusted subprocess output and timing cross an asynchronous boundary after reload may have occurred.                                      |
| Persisted PID table -> OS process signal          | A recorded PID may belong to another process; marker verification and conservative skips protect unrelated processes.                      |
