## Edge assumptions

- Plan 05-01 completed first and established the required production-adapter pattern; its summary governs any discretionary naming changes that execution recorded.
- Plans 05-02 and 05-03 execute in the same wave. This plan has zero file overlap with them and must not pull marketplace/plugin invalidator call-site migrations into their files.
- The transition adapter is a bounded Phase 5 sequencing device, not the final owner. It preserves one cache identity across current production read/invalidation exports until 05-07/05-08 route callers, 05-09 composes the lifecycle instance, and 05-10 removes the adapter and reset.
- Current research found no production call to the marketplace-name memory reader. The executor must repeat that census immediately before deletion. If a production consumer now exists, migrate it to the factory contract and preserve its behavior instead of deleting a genuine contract.
- The marketplace-names file remains a live cross-process cache/invalidation artifact even when its unused memory reader disappears. Its schema version, path, and ENOENT behavior are not dead code.
- Plugin-index cache files are shared across processes, while memory is per completion-cache instance. Schema validation and TTL remain the defenses against stale or incompatible disk state.
- Existing `GetPluginIndexOptions.now` behavior is an authorized deterministic TTL control. This plan may bind it at the cache operation or factory boundary, but must preserve every current boundary case and must not turn it into a general dependency bag.
- The existing terminal reset export is removed by 05-10 after all downstream owner fixtures migrate. This plan migrates shared/data/provider/register/flag-catalog owners to fresh instances and adds no replacement reset or clear-all operation.

## Trust Boundaries

| Boundary                                                | Description                                                                                                                                      |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Extension command registration -> completion provider   | The registered callback must use the cache instance chosen by production composition, not a hidden or per-keystroke lifetime.                    |
| Persisted cache file -> validated in-memory rows        | Stale, malformed, poisoned, or schema-incompatible JSON crosses TypeBox validation and TTL checks before it can influence completion candidates. |
| Authoritative state/manifest -> cache rebuild           | State-read failures must propagate, while manifest failures alone become persisted poison and empty completion rows.                             |
| Cache instance -> completion consumers and invalidators | A wrong or second instance can leak state across lifecycles or leave stale rows visible after mutation.                                          |
| Scoped cache path -> file invalidation                  | Only derived cache files may be unlinked; missing files are idempotent while other failures retain their established handling.                   |
