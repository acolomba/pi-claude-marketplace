# Phase 3.1: Local Declaration Leak Fix - Context

**Gathered:** 2026-10-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Stop new leaks of `--local` declarations into the shared `claude-plugins.json` (FIX-02).

**The defect.** Phase 3 found it while discussing the code, and its research confirmed it on a real Pi.
- `migrateFirstRunConfig` (`persistence/migrate-config.ts`, MIG-01) runs from `orchestrators/reconcile/apply.ts::readPassForScope` on every load. When the scope has no base file, it writes `claude-plugins.json` from every `state.json` record and never looks at `claude-plugins.local.json`.
- Suppose a scope's first add is `marketplace add <src> --local`. The next session or `/reload` then copies that marketplace into the shared file.
- After that, `remove --local` does not survive a reload, because the base file still declares the marketplace.
- Plugins installed with `--local` leak the same way.

In scope:
- the fix;
- unit tests at 100% direct coverage;
- cucumber regression scenarios;
- one CHANGELOG bullet.

Out of scope: any repair of entries that already leaked (D-03).

**Upstream parity** (claude-code-compat-research evidence record):
- **Question:** may a per-machine declaration reach the shared file?
- **Claude Code:** `.claude/settings.local.json` is personal. It stays out of git, and Claude Code applies it over the committed `.claude/settings.json`, so "personal exceptions don't need a commit".
- **Evidence:** https://code.claude.com/docs/en/settings, read 2026-10-16. Confidence: high.
- **Verdict:** the fix brings the extension in line with upstream. The first-run migration itself is this extension's own mechanism (MIG-01), and Claude Code has no counterpart to it. No divergence.

</domain>

<decisions>
## Implementation Decisions

### Fix mechanism
- **D-01:** When the first-run migration builds the base file from `state.json`, it leaves out everything the scope's local file declares. The local file stays the only record of what is personal, and the `state.json` schema does not change.
  - If nothing non-local is left, no base file is written, which is the existing UAT-01 rule against empty files.
  - The read-only planning mirror in `orchestrators/reconcile/pending.ts` (`mergedViewForPlanning`) must apply the same exclusion, so `pending` and the load agree.
  - `state.json` provenance was considered and not chosen.
- **D-02 (user note):** base and local entries are merged per entry; a local entry replaces the base entry with the same key (`persistence/config-merge.ts::mergeScopeConfigs`, CFG-02). There are also rules that refuse to put a plugin in the shared file when its marketplace is declared only in the local file. The fix must respect that model:
  - the migration leaves out the marketplaces the local file declares;
  - it leaves out the plugin keys `plugin@marketplace` the local file declares;
  - it also leaves out the plugins of a marketplace that only the local file declares, since the shared file may not hold a plugin whose marketplace it does not declare.

  Research locates the existing refusal rule and confirms the migration matches it.

### Coverage
- **D-04:** the whole leak class is fixed, marketplaces and plugins installed with `--local` alike. The marketplace path gets cucumber scenarios. The plugin path is proven by unit tests, because the milestone keeps plugin flows out of `features/`.

### Existing leaks
- **D-03:** no automatic repair and no warning. A marketplace or plugin can legitimately be declared in both files: shared for the team and local for oneself. A leaked entry therefore cannot be told apart from a deliberate one, so any repair or warning would hit legitimate setups (the user's ruling). The CHANGELOG bullet tells affected users to remove the leaked entry from `claude-plugins.json` and reload. No README entry.

### Tests
- **D-05:** regression scenarios start from an empty scope with no base file. One adds with `--local`, starts a new session, and shows the shared file still does not declare the marketplace while the local file still does. Another runs `remove --local` across a new session and shows the marketplace stays removed. Each scenario must fail on today's code first, test-first as in C-10/Phase 6. Unit tests in `tests/persistence/migrate-config.test.ts` (and the pending owner test) prove that non-local records still migrate (Phase 3.1 SC3).

### Claude's Discretion
- How the "no base file" outcome is observed in a scenario. After a load, a missing base file is a real observable, because the migration declined to write. Possible forms are a new read-only config step such as "the X file of the Y scope does not exist", or another observable that research finds.
- Where the scenarios live: `add.feature`, `remove.feature`, or both.
- The exact function signature change in `migrate-config.ts` and how `apply.ts` passes the local config to it.

</decisions>

<code_context>
## Existing Code Insights

- `migrateFirstRunConfig(loc, state)` checks only `loc.configJsonPath`. Its `entryCount === 0` early return (UAT-01) already skips writing an empty file.
- `readPassForScope` treats a scope as used if either config file exists, then calls the migration under the scope lock.
- `features/step_definitions/config.steps.ts` only reads files, and a missing file fails its step. A "file does not exist" assertion would be a new read-only step.
- The Before() hook empties the sandbox, so a scenario starts with no base file. That is exactly the trigger condition.

</code_context>
