<assumption_delta_decision>
The assumption-delta scan flagged the word "alongside" (weak pluralization
signal) in "receives CLAUDECODE=1 and CLAUDE_CODE_SESSION_ID **alongside** the
existing CLAUDE_PROJECT_DIR/... set". This is a literal add-alongside, not a
promote/replace: the locked CONTEXT decision is that "the existing env set stays
byte-for-byte unchanged". Decision = **ADD-ALONGSIDE** — the three new keys are
appended inside the same object literal, after the `...process.env` spread and
after the existing CLAUDE_* keys; no existing key (including the async-only
MARKER_ENV) is renamed, revalued, or removed. There is no competing architecture
to reconcile.
</assumption_delta_decision>

<single_source_of_truth_decision>
CONTEXT lists (Claude's Discretion) whether to import the key names / `"1"` from
`shared/session-env.ts` or duplicate them locally, leaning "prefer a single
source of truth if the import direction is legal". The import direction IS legal
(bridges -> shared, RESEARCH Pitfall 4). Decision = **local literals with
mirrored comments (option b)**, because:
- The single-source route would require refactoring Phase 90's `applySessionEnv`
  (which today uses dotted `process.env.CLAUDECODE = "1"` assignments and exports
  no name/value constants) — a change that does NOT trace to HENV-01/02 and
  violates the CLAUDE.md surgical / "no abstractions for single-use code" rule.
- The genuine anti-drift mechanism is the behavioral drift guard (D-91-01), not a
  shared constant; a shared constant would only couple KEY NAMES, which is not
  where drift bites.
- The two env builders already self-document as deliberate hand-mirrors, so local
  literals with mirrored `HENV-01`/`HENV-02`/`D-91-02` comments fit the existing
  posture.
Trade-off surfaced for the operator: flipping to option (a) means adding exported
`CLAUDECODE_VALUE`/key-name constants to `session-env.ts`, threading them through
`applySessionEnv` and both lanes in one atomic change. Reversible; not chosen here.
</single_source_of_truth_decision>
