<objective>
Make a dependency declared in a plugin's own manifest visible to the cascade, not
just one declared in the marketplace entry.

Purpose: this is the whole reason the roadmap makes this phase depend on the
manifest-read-fidelity work. A plugin whose real metadata lives in its own bare
manifest is exactly the plugin that phase rescued, and a cascade that reads only
the marketplace entry would silently miss its dependencies. Plan 03-01 wired the
lookup as an injected parameter precisely so this plan can fill it.

Output: `orchestrators/plugin/dependency-declaration-read.ts` implementing the
plugin-manifest-first read order under a filesystem-only contract, and the
`install-flow.ts` swap that makes the cascade use it.
</objective>

  <action>
Create `orchestrators/plugin/dependency-declaration-read.ts`. Its header states
that it answers one question -- what dependencies does this plugin declare -- in
the plugin-manifest-first order the manifest-read-fidelity work established, and
that it does so with no network call of any kind.

Declare a `DependencyDeclarationReader` interface for the filesystem operations
it needs, so a test can drive every branch without a real tree, with a frozen
module-scope real implementation named at module scope rather than written as an
inline parameter default. Mirror the reader seam `info.ts` already uses for the
same operations rather than inventing a different shape.

Export `readDependencyDeclaration(options): Promise<ClosureLookupResult>`, taking
the plugin key's name and marketplace, the marketplace root, the parsed source,
the scope locations, an optional reader seam, and the already-loaded marketplace
manifest entry.

Behavior, in order:
1. Resolve a plugin root WITHOUT any network call. A locally resolvable source
   derives its root through the existing derivation, whose containment re-check
   is the containment guarantee for the read; that derivation throws on a
   refusal, so catch totally and read a throw as no-root. The catch must be
   total, not narrowed to the containment error type, because the derivation also
   inspects each path component and a source string the operating system rejects
   outright throws from the syscall layer instead. A git source goes through the
   filesystem-only presence probe and yields a root only from its materialized
   arm; a not-cached, escaping or missing-subdirectory result means there is no
   local tree to read. Never reach the materializing probe, not from any flag.
2. With a plugin root, walk the shared manifest candidate ordering. Fall through
   on ABSENCE only: the first candidate that exists is this plugin's manifest,
   and a candidate that exists but cannot be used ends the walk as not-readable
   rather than handing off to its sibling. Stat before reading so a device or
   pipe cannot supply bytes or block. A parse throw, or a payload that is not a
   JSON object, is a present-but-unusable manifest and reads as not-readable.
3. A readable manifest's dependency value -- INCLUDING an absent key -- is the
   answer. An absent key means the plugin declares no dependencies; the
   marketplace entry's list must not reappear behind it.
4. Only where no manifest was readable does the marketplace entry's dependency
   value answer.
5. Feed whichever value won through `parseDeclaredDependencies` and map its
   result onto the closure lookup contract: a successful parse becomes the found
   arm carrying the parsed dependencies, a rejection becomes the unusable arm
   carrying the parser's reason, and a plugin with no entry and no readable
   manifest becomes the absent arm.

State in the header the deliberate consequence: a git-source dependency with no
materialized clone has no readable manifest at closure time, so its marketplace
entry answers for it. That is the price of keeping the read offline, and it is
the same shape the read-only surfaces already accept.

Write `tests/orchestrators/plugin/dependency-declaration-read.test.ts` against a
faulted reader seam and real temporary trees where a tree is simpler. Cover: a
plugin manifest declaring dependencies while the entry declares none; a plugin
manifest declaring an empty array while the entry declares dependencies, proving
the entry's list does not reappear; a plugin manifest with no dependency key,
same proof; a present-but-unparseable first candidate ending the walk and falling
back to the entry rather than to the second candidate; an absent first candidate
falling through to a second that answers; a git source with no materialized clone
yielding the entry's answer with no fetch attempted; a containment refusal during
root derivation being caught and read as no-root; a syscall-layer throw during
root derivation likewise; and a parser rejection becoming the unusable arm with
the parser's reason preserved.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin tree on disk -> manifest read | Untrusted third-party files are opened by path during install planning |
| derived plugin root -> filesystem read | A manifest-declared source string decides which directory is opened |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-29 | Tampering | plugin root derivation | high | mitigate | The read goes through the existing root derivation whose containment re-check is the project's path-containment chokepoint, so a source string cannot address a file outside its owning clone root. A refusal is caught and read as no-root, so a refused read falls back to the marketplace entry rather than propagating or silently succeeding |
| T-03-30 | Denial of Service | manifest candidate read | medium | mitigate | Each candidate is stat-checked before it is read, so a device node or a pipe planted at a candidate path cannot supply unbounded bytes or block the install. A parse throw is caught and read as an unusable manifest |
| T-03-31 | Spoofing | declaration precedence | medium | mitigate | A present-but-unusable manifest reads as not-readable and falls back to the entry; it is never read as a plugin declaring nothing. That distinction is what stops a truncated or corrupted manifest from silently suppressing a dependency the plugin really declares |
| T-03-32 | Elevation of Privilege | network boundary | high | mitigate | The read has no materializing path at all: a git source yields a root only from the filesystem-only presence probe's materialized arm. `install-flow.ts` stays in the network-free target list and the architecture gate is run in this plan's verification |
</threat_model>
