it: `install foo@mp`, where `foo`'s marketplace entry declares one
unconstrained dependency `bar`, installs `bar` first and `foo` second, under one

Implement the walk with TWO separate structures, per D-03-11. A `path: string[]`
array is pushed before recursing into a member's children and popped only on the
success return; `path.includes(key)` is the ONLY cycle test and the reported
chain is `[...path, key]`. A `visited: Set<string>` is added on first entry and
never removed; a hit is a SUCCESS short-circuit that returns without re-walking.
Conflating the two misreports a legal diamond as a cycle, so keep them distinct
and say so in the module header.

Guard order inside the recursive step is load-bearing and must be exactly:
(1) record the declared range for this key into the per-key accumulator, so a
diamond's second edge still contributes its constraint even though the memo will
short-circuit; (2) if the key is not the root and is present in `installedKeys`,
push it onto `alreadyInstalled` with its accumulated ranges and return without
walking its children (RESV-05); (3) if the key's marketplace is absent from
`knownMarketplaces`, fail `marketplace-not-added` (D-03-08); (4) cycle test;
(5) memo test; (6) add to memo, look up, push to `path`, recurse over each
declared dependency, pop `path`, push the key onto the post-order accumulator.
The post-order accumulator IS the install order -- no separate sort pass.

RESV-02's marketplace fill-in: for each `DeclaredDependency`, the resolved
marketplace is `dependency.marketplace ?? marketplaceOf(declaringKey)`, and the
filled-in value is re-checked with `isRenderableDependencyToken` from
`domain/dependencies.ts` before it becomes part of a key. D-03-10: the range
accumulator is seeded empty and fed ONLY by declarations encountered during THIS
walk -- never by scanning unrelated installed plugins.
