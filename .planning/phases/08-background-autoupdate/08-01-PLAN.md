in-process foreground gate that every `/claude:plugin` command runs through,
the env policy, the first-input scheduler with its shutdown handling, and the

refreshed and its plugins updated in the background, without a command ever
meeting this process's own state lock. The pass is silent until 08-03 adds
the `background-update` notice.

Output: three new `orchestrators/marketplace/background-*.ts` modules with
paired tests, the `runForeground` option on `registerClaudePluginCommand`,
and the `index.ts` wiring.

`includeEntryExports`, so every new export must land in the same commit as a
production importer. The gate is therefore wired through `index.ts` in the
first task, and the pass and the scheduler land together with their

Semantics: `stepSettled()` returns a promise the next `endStep()` resolves when a step is in flight, else an already-resolved promise. `runForeground(command)` increments the count synchronously, awaits `stepSettled()`, awaits `command()`, and in `finally` decrements and wakes the background waiters when the count reaches zero; a rejected command reaches the caller unchanged. `beginStep()` loops while the count is above zero, awaiting a promise the zero-count wake resolves, with `// eslint-disable-next-line no-await-in-loop -- ` and the reason that a command can start before the background resumes, so each wake re-checks; it then sets the flag synchronously (single-threaded JS makes the check-and-set atomic). `endStep()` clears the flag and wakes the step waiters; with no step in flight it changes nothing. There is no timeout (the CONTEXT known limit). Commands are not serialized among themselves.
