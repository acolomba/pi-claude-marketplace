## Decisions honored, and measured corrections

- **Decision 2 mechanism (corrected by M1).** The stated premise ("no `exports`
  field, so `.../package.json` resolves") is false. The resolver still resolves
  the package's `package.json` from the repo root. It does so by Node's own
  package lookup order: `<dir>/node_modules/<pkg>/package.json` for the checkout,
  then each parent directory. It reads the file directly instead of calling
  `require.resolve`. It never consults PATH, NODE_PATH, the global folders or the
  bin shim. In a worktree nested inside the main checkout it finds the parent
  checkout's install, as every other import in the suite does.
- **Decision 2 floor check.** Only `stop-canary.mjs` has the `>= 0.86.1` check;
  it stays, fed by the resolver's version. `manifest-absence-canary.mjs` never had
  one, and none is added.
- **Decision 4 peer-dependency risk (resolved by M5).** Use `--legacy-peer-deps`.
  It also enforces Decision 1 ("no second pi install"). The verify blocks
  re-prove it.
- **Decision 5 optional note (does not hold, M6).** README says the pi.sh prefix
  CANNOT serve as PI_WORKFLOW_ENGINE_ROOT, and why.
