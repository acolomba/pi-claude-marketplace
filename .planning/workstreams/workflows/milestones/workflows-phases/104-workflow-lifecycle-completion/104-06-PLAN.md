<objective>
Pi exposes no way to unregister a command. Registration converges on reload, which satisfies
the recovery model — but deregistration cannot happen mid-session at all. So after any
operation that removes a workflow, the command stays registered and runnable for the rest of
the session. That asymmetry is a host limitation to report, not a defect to hide, and this
plan gives it somewhere to live.

Two obstacles the mechanics have to respect. The uninstalled row is one of the deliberately
reasons-less render variants, so carrying anything on it means widening the message type and
changing two render arms that both hard-code an absent reasons list. And a `warning`-severity
row makes the notifier prepend a summary line, which is a byte change — so this is a NEW
catalog state, never an edit of the existing success block.

**Coordination hazard, recorded here so the next phase can read it:** the following phase
adds its own token to the same tuple tail, the same topic-group header, the same order-pinned
expected array and the same length pin. This plan lands whole in one commit; the next phase
starts from a tuple of 39 members.
