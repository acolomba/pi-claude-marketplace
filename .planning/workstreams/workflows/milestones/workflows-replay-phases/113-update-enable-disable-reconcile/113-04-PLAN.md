<objective>
Tell the user that a workflow command they just retired is still live, from all four verbs that can retire
one — and settle the reinstall requirement with evidence rather than inference.

Purpose: the host exposes no way to unregister a command. Removing a workflow's envelope therefore leaves
its command registered and runnable for the rest of the session, and nothing in the product says so. The
existing reload trailer does not cover it: that trailer is about picking up NEW things, and this is a
REMOVED command that still runs. Three of the four verbs that can produce this state shipped their
workflow removal without any signal at all, so scoping the fix to the two verbs this phase otherwise
touches would ship the same fact reported by half the surface.

Output: one closed-set amendment landed with all four of its gates, four stamp sites plus a fifth on the
module-private enable sentinel, a catalog state per stamping verb, and a verified traceability correction.
</objective>

  <action>
Compute the gate BESIDE each verb's existing reason accumulation, never inside a renderer. The gate is the
recorded names minus the newly staged names, so a rename retires a command exactly as a deletion does.

**Disable.** Read what the cascade REPORTED removing — never the length of the record's workflow inventory.
The record deliberately keeps that array populated across a disable, and it can name envelopes the cascade
failed to remove, so its length answers a different question than "does a command linger". Stamp on BOTH
disable arms: the clean arm and the arm whose partial cascade removed some envelopes before failing. A
cascade that removed two and then failed on a third leaves three commands registered, and reporting none of
them tells the operator that nothing changed, which is the opposite of what happened.

**Enable.** Compute the retired set as the pre-enable record's workflow inventory minus the staged names on
the ledger projection the previous plan added. This is that member's consumer; without it the field is
added and every reader discards it.

**Where the fact lives on the enable/disable path.** On the MODULE-PRIVATE outcome sentinel, on its fresh
arm and on its disable-failed arm — not on the exported projection the reconcile caller consumes. Keeping
it off that union is what structurally guarantees the load-time path cannot stamp it, and a comment at the
projection site must say so, because the omission looks like an oversight otherwise.

**Uninstall and reinstall.** Both compose their rows in file. Uninstall's gate is what its removal took;
reinstall's is its pre-reinstall record inventory minus the names its replace step reported placing, which
is already threaded out of that step.

**Update.** The row is composed by the shared leaf composer both update cascades call, so the fact must
travel on the outcome. Add an optional boolean axis to the update updated-outcome in the shared
orchestrator types, populate it in the success-outcome composition from the recorded inventory minus the
staged names, and read it in the leaf composer as a FOURTH independent axis. Place its token inside the
brace at a fixed position in the composer's established emit order; do not append it wherever it happens to
be computed, and do not let it change the order of the three existing axes.

**Severity.** The token raises the row to warning on every stamping verb. The project's severity model is
three-way — the desired state reached is info, carried out but short of the desired state is warning, and
not carried out is error — and a retired command that still runs is squarely the middle band. The update
composer currently documents that only one of its axes moves the severity channel; extend that sentence
rather than contradicting it, because this axis moves it for a different reason: it is a shortfall in what
the operation achieved, not a configuration defect the row merely names.

**Bytes.** Spread the key only when the retired set is non-empty, so an unaffected row's bytes are
unchanged. Add ONE catalog state per stamping verb — four in total — each showing the row carrying the new
token, and each showing the existing reload trailer alongside it so a reader sees the two coexist and state
different things. Pair each with a fixture keyed by the same section and state. Fixtures are pure
notification data.

Cover every behavior in the block above with owner cases in the five verb suites plus the leaf composer's
own suite. The three that matter most are the empty case on each verb (bytes unchanged), the both-sets case
(no retirement), and the reconcile projection case (token absent regardless).
  </action>
