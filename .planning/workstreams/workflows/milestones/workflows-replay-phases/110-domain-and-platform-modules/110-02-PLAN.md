<objective>
Land the two additive edits the ported script module imports — the workflow name generator and the
collision error — and close the measured WNAM-06 gap in the same change that introduces the function
carrying it.

Purpose: WNAM-06 requires that every generated name pass the engine's `isSafeSavedWorkflowName`. As
ported it does not: a `meta.name` carrying an interior space, a format character or a bidi control
yields a name the engine rejects. In Phase 111 that becomes an envelope written to a path the engine
refuses to register — a silent install with no command. Completing the wrapper is not the rewrite
the ROADMAP forbids; `assertSafeSavedWorkflowName` is new code the port itself introduces, and
completing it makes us match the engine exactly rather than exceed it.

Output: two extended production files, two extended owner tests, one green commit.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted `meta.name` -> generated command name | a plugin-declared string becomes a command name AND a file basename under the engine's storage root |
| generated name -> host engine registration | the engine independently re-validates the name and silently refuses to register one it rejects |
| collision set -> user-facing install message | the offenders are rendered to the user through the notify surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-110-06 | Spoofing | `generatedWorkflowName` emitting an engine-unsafe name | high | mitigate | Add the `/[\s/\\\0]/u` and `/[\p{Cc}\p{Cf}]/u` clauses to `assertSafeSavedWorkflowName` so the wrapper replicates all six engine clauses. Four measured cases — an interior space, a leading space in the source, a format character and a bidi control — are pinned as throws. Without this the install succeeds and the command never registers, with no signal to the author. |
| T-110-07 | Tampering | a bidi or zero-width control in `meta.name` reversing or hiding the displayed command name | high | mitigate | The `\p{Cf}` half of the same screen. A name that renders as one command and registers as another is a spoofing surface, not a cosmetic issue. |
| T-110-08 | Tampering | path traversal through a generated name used as a file basename | high | mitigate | `assertSafeName` already refuses both path separators and both dot forms; the added `/[\s/\\\0]/u` clause re-screens the separators and NUL so the wrapper is complete on its own terms rather than relying on call ordering. |
| T-110-09 | Spoofing | one script silently claiming a name another declared | high | mitigate | `WorkflowNameCollisionError` is a hard throw carrying every claimant as structured data. Keeping the first silently is the misnaming WNAM-05 exists to prevent. Phase 111's consumer reads `collisions`, never the message. |
| T-110-10 | Information Disclosure | the error message echoing the offending name and file names | low | accept | Both are plugin-supplied values the user is already installing and can already list. Redacting them would make the message unactionable. |
| T-110-11 | Denial of Service | a pathological `meta.name` making name validation expensive | low | accept | Both added patterns are flat character classes with no quantifier nesting, evaluated once over a string already capped at 128 code units by the preceding clause. |
| T-110-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package. The one new runtime dependency lands in 110-03 with a verdict of `OK` and no `[ASSUMED]`/`[SUS]` entry. |
</threat_model>
