*WNAM-01, the generated name.* A plain declared name yields `named` with both `metaName` and
`generatedName`, and the generated name carries the plugin prefix elision. Assert both fields in one

*WNAM-03, the three skip causes, each distinct.*
  - no `meta` declarator at all — a script that is only a top-level `return` — expect `skipped` /
    `no-meta`
  - `meta` initialized from a call expression — expect `skipped` / `meta-not-object-literal`
  - a bare `let meta;` with no initializer, which reaches the same cause through the optional-chain
    arm rather than the type check — expect `skipped` / `meta-not-object-literal`
  - `meta` carrying a spread AFTER its last literal `name` — expect `skipped` / `meta-spread`
  - `meta` carrying a spread BEFORE a literal `name` — expect `named`, because the read is last-wins
    and the literal overwrites whatever the spread contributed. This pair is what makes the spread
    rule a rule rather than a coincidence.

*WNAM-01 edge, the empty source.* A zero-length source parses cleanly as an empty Program. Expect
`skipped` / `no-meta`. It must NOT be `refused` / `unparseable`. Title the case so the distinction
is explicit.

*WNAM-04, the parse refusal, and its empty-file counterpart.* Assert BOTH halves in the same
neighbourhood so they can never collapse into one another:
  - genuinely invalid syntax — an unterminated object literal — expects `refused` / `unparseable`
  - the empty source case above expects `skipped` / `no-meta`
  - a source that is BOTH unparseable AND carries a determinism blocklist token expects `refused` /
    `unparseable`, because the parse is settled first. That ordering deliberately differs from the
    engine's, which screens the blocklist before parsing, and the module's header explains why ours
    is the truthful one.
  - a source with no readable `meta` that ALSO carries a blocklist token expects `skipped` /
    `no-meta`, because the meta lookup is settled before the determinism scan.

*WNAM-02, the two stem-fallback arms.*
  - `meta` with a description but no `name` key at all — expect `stem-fallback` with the generated
    name derived from the file stem
  - a `name` that is a template literal — expect `stem-fallback`, and assert the generated name is
    the stem, which is what proves the template was never evaluated
  - a `name` that is a string concatenation — same
  - a `name` that is a numeric literal — same; a numeric `Literal` is a `Literal` node whose value
    is not a string, so it takes the same arm as an identifier
  - a `name` that is a bare identifier — same

*WNAM-02 edge, the empty string literal.* `meta` whose `name` is an empty string literal. This is
NOT a stem fallback: the empty string IS a readable literal, so it is admitted as a name and then
fails the safe-name check. Expect `refused` / `unsafe-name`. Assert it in the same case group as the
stem-fallback rows, with a title saying it is distinct from both, so a later reader cannot fold the
three outcomes together.

*The remaining refusal cause.* A `name` carrying a path separator — expect `refused` /
`unsafe-name`. And a `name` carrying an interior space — expect `refused` / `unsafe-name` too, which
is the 110-02 engine-parity completion observed from this side of the seam. Both prove that a throw
from the name generator becomes this file's own refusal rather than escaping to block the plugin's
other scripts.

*The plugin-name throw.* An unsafe PLUGIN name throws out of `admitWorkflowScript` rather than
producing a verdict, because it is a defect of the whole set and no single file is at fault. Assert
with `assert.throws` and the class-plus-message callback shape.

*The four determinism causes.* Each is separated by WHERE the blocklist match sits, and each needs
its own source:
  - `determinism-code` — a real call in executable code
  - `determinism-comment` — the token named only inside a line comment, with a valid `meta` present
  - `determinism-string` — the token named only inside a string literal
  - `determinism-split` — a match that straddles a comment boundary, produced by a line comment
    ending in the first word of a multi-word blocklist alternative and the rest of that alternative
    on the following line. The pattern's whitespace class matches the newline, so the match is not
