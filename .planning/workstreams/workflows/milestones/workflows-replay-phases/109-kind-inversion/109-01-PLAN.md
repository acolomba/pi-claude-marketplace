<tracer_note>
**Why the leading task is a tracer even though it is deliberately RED.**

Tracer-first decomposition asks for the thinnest path that touches every layer the phase will
modify, wired end to end, carrying a real runnable verify. In this phase that path is the
published contract -> byte gate pair: `docs/output-catalog.md` states what a workflow-bearing
plugin renders, and `tests/architecture/catalog-uat.test.ts` pairs each annotation with live
`notify()` output byte for byte. Task 1 wires exactly that one path, end to end, and its
`<verify>` is a real runnable command.

The divergence from a conventional tracer is the DIRECTION of the verify. A conventional tracer
proves the architecture works; this tracer proves the gates BIND — that the contract the phase is
about to change is genuinely enforced, before a single production byte moves. A working
end-to-end tracer here would require applying the production change first, which is precisely
what Success Criterion 4 forbids: with production edited first the renderer prints whatever the
fixture hands it, both halves still agree, and the observed red never happens. The red slice is
the informative slice, so the red slice is the tracer.
</tracer_note>
