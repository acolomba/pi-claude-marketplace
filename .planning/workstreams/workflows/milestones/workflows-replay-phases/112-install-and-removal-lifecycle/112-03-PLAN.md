<objective>
Make reinstall re-materialize workflow envelopes from the plugin source and record the names it actually
wrote.

Purpose: reinstall is the only one of the four removal-and-materialization verbs that is bespoke. It has
no ledger and no cascade -- a hand-rolled prepare / replace / rollback trio where the rollback ledger is
an array of replacement handles the workflows bridge does not produce. That gap is the single most
intricate piece of this phase and the most likely place for the rollback defect class the preceding
phase's review found twice. It is also what makes the released repair path actually repair a plugin
whose workflows were installed while the kind was unsupported.

Output: a fifth prepare handle, a commit step at the end of the replace sequence, the placed names
threaded out and consumed by the outer recovery path, the record axis filled from the placed names, and
owner-test cases pinning each.
</objective>

<flagged_planner_assumptions>
One decision in this plan is a genuine judgement call with house precedent pointing both ways. It is
surfaced here rather than buried in a task.

**The recovery path swallows a containment refusal into a leak string.** The workflows unstage
primitive RAISES a path-containment refusal rather than reporting it, and the two ledger sites re-throw
it by class because state corruption is meant to be loud. In the install ledger that is exactly right:
the refusal escapes and the renderer's bypass handles it.

Reinstall's outer recovery path is different. It runs inside a `catch` that is already unwinding a
DIFFERENT error and composing a manual-recovery hint out of rollback leak strings. If the removal helper
were allowed to throw there, it would replace the original error and discard every leak string already
collected -- the same shape the preceding phase's review flagged as an Info carry-forward for a throwing
callback.

**The assumption this plan is written under:** in the recovery path the refusal is recorded as a
manual-recovery leak line -- user-visible and loud -- rather than being allowed to destroy the primary
error. The bridge's own contract is unchanged: it still raises, and the ledger still lets it propagate.
Only this one recovery composer converts it, for the same reason the replacement rollback walk collects
leaks and never throws.

If a reviewer reads the containment doctrine as absolute even inside a recovery composer, the alternative
is to let it propagate and accept losing the original error and the leak list. Record whichever reading
holds in the SUMMARY.
</flagged_planner_assumptions>
