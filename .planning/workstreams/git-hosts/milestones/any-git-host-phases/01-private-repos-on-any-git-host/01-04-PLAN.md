<objective>
Close UAT gap G-01-4: a credential bound to one host crosses to another host when the server
redirects.

UAT ran a live HTTPS git server that logged the `Authorization` header of every request. The bound
host `localhost:8444` answered with a 302 to `https://localhost:9443/...`. The `:9443` server then
received the `localhost:8444` credential on `info/refs`, and again on the POST->GET
`git-upload-pack`. The control was a redirect to `127.0.0.1:9443`, another hostname. It sent no
credential and failed clean with `{authentication required}`.

Root cause. `platform/git.ts` passes the stock `isomorphic-git/http/node` client to isomorphic-git.
In that client, `simple-get@4.0.1` follows each 3xx itself. It deletes `authorization` only when
the HOSTNAME changes (`node_modules/simple-get/index.js:55-60`). The host guard in `onAuth` sees only
the original URL, so the check passes. isomorphic-git then sets the `Authorization` header. The
header goes with every redirect that keeps the hostname: to another port, as UAT measured, or to
`http:` on the same hostname. Planning measured the `http:` case through the real transport. That
redirect sends the credential in cleartext.

Operator decision (locked): match git and curl in the extension's own transport. A redirect whose
target origin differs from the original request must not carry `Authorization`. The origin is
scheme, host and port, with the default https port removed, as in 01-02 D2. `<design_decisions>`
records the mechanism chosen and what a cross-origin redirect does, with the reasons.

Purpose: GAUTH-06 promises that a credential resolved for one host is never offered to another.
Today the redirect path breaks that promise.

Output:
- a module-private client in `platform/git.ts` that follows redirects itself;
- tests in `tests/platform/git.test.ts` that reproduce the leak at the wire before the fix and prove
  the fix after it;
- docstrings and requirement text that no longer claim `simple-get` prevents the leak;
- the whole gate, green.

edits shared `.planning/` documents, and its gate needs this checkout's `node_modules`.

<design_decisions>
**DD-1: The mechanism is a wrapping client that follows redirects itself.**

`platform/git.ts` builds a module-private `HttpClient` around `isomorphic-git/http/node`, and all
three isomorphic-git calls use it. The client sends each hop with
`fetchOptions: { followRedirects: false }`. `isomorphic-git/http/node` spreads `fetchOptions` into
the `simple-get` options (`http/node/index.js:207`). `simple-get` then returns each 3xx instead of
following it (`simple-get/index.js:50`). The client follows the redirect itself. It repeats the
redirect step of `simple-get` with one change: it compares the ORIGIN of each hop with the original
request. `simple-get` compares the HOSTNAME with the previous hop.

This is the smallest mechanism that holds. `simple-get` removes headers inside its own redirect
code, and it gives callers no hook. So only the code that follows the redirect can remove the header
for a given hop. The alternatives fail:

- **Refuse any redirect when a credential is present.** This breaks rename redirects that work
  today. Since GAUTH-03, every host has an auth bundle, so this would affect every host.
- **Send the credential through Node's `auth` option.** `simple-get` resets `auth` on every absolute
  redirect (`index.js:22`), including a same-origin rename, and keeps it on a relative one.
- **Remove the header in an `https.Agent` hook.** This depends on the internals of `ClientRequest`.
  It also breaks on an https->http hop, where the agent and the protocol do not match.
- **Patch `simple-get`.** A patch under `node_modules` does not last.
- **Check in `onAuth`.** isomorphic-git passes `onAuth` only the original URL, so `onAuth` never sees
  the redirect target.

**DD-2: A cross-origin redirect is followed without the credential. It is not refused.**

- **Upstream parity (CLAUDE.md Constraints).** Claude Code 2.1.283 clones by running
  `git clone --depth 1`. The binary contains `M=[...exe,...h,"clone","--depth","1"]`. So upstream
  is git over libcurl. libcurl 7.83 and later (CVE-2022-27776) follows the redirect. It sends
  credentials only to the scheme, host and port of the original URL. By default git follows a
  redirect on the initial request (`http.followRedirects=initial`). A refusal would therefore be a
  divergence. A divergence needs a recorded decision or a Pi capability gap, and neither exists
  here.
- **Fail clean (NFR-3, CP-10).** Suppose the target asks for credentials. The auth loop in
  isomorphic-git then ends in the cancel from `onAuthFailure`. That cancel becomes
  `UserCanceledError`, and `classifyGitTransportFailure` turns it into `{authentication required}`.
  UAT's other-hostname control already showed this path failing clean. No raw exception escapes,
  nothing is written to state, and a retry is safe. No new reason token is needed. A refusal would
  need a new token in the closed set, or it would surface an error that nothing classifies.

**DD-3: One parity gap remains. It is recorded, not closed.**

After a redirect on the initial request, git reads the credential for the redirected URL. It asks
the helper for the TARGET host's credential. isomorphic-git calls `onAuth` only with the original
URL. So the extension cannot authenticate a cross-origin redirect target with that target's own
stored credential. Such a target receives nothing and fails clean with `{authentication required}`.
This is a limit of the isomorphic-git transport, not a leak. The SUMMARY reports it to the operator.

**DD-4: All other redirect behavior follows `simple-get`, with one exception.**

- After 10 redirects, the client throws `new Error("too many redirects")`. This is the same class
  and message `simple-get` uses, so every caller classifies it as it does today.
- A 3xx without a `Location` is returned unchanged.
- The body of the redirect response is discarded.
- A POST answered with 301 or 302 becomes a GET. The GET has no body, no `content-type` and no
  `content-length`.
- `cookie` is dropped together with `authorization`, as in `simple-get`. isomorphic-git sets no
  cookie.
- **The exception:** every other 3xx (307, 308) keeps the method and the body. isomorphic-git's
  request bodies are arrays, so the same reference sends the same bytes again. `simple-get` deletes
  the body before the first hop (`index.js:42`) and keeps `content-length`. So it re-sends a POST
  with no body, which no server can answer.
</design_decisions>

<planning_measurements>
All measurements were taken in this checkout on 2026-09-28, with Node 26.10.0, isomorphic-git
1.42.2 and simple-get 4.0.1. The scratch probes are not part of this plan.

1. **The leak reproduces with a socket-level double.** The double replaces the `request` function of
   `node:https`. On the unmodified tree it reproduces the UAT observation exactly for `clone`,
   `fetch` and `resolveRemoteRef`. In the test scenario, the bound host redirects `info/refs` to
   `:8443`, and `:8443` answers every request with 401. The wire log is
   `[bound none, :8443 none, bound Basic, :8443 Basic]`. Each operation rejects with
   `UserCanceledError`. The rejection is the same before and after the fix. Only the credential on
   the fourth request differs, so the wire assertion is the one that fails on the unfixed tree.
2. **The `http:` redirect leaks too.** With the same double, a redirect to
   `http://git.example.invalid/...` carries the credential, in cleartext, through `node:http`. A
   redirect to `https://other.example.invalid/...` carries nothing.
3. **A prototype of DD-1 and DD-4 behaves as specified:**
   - port redirect: no credential reaches `:8443`, and the operation rejects with
     `UserCanceledError`;
   - same-origin redirect: the credential is carried, and the HEAD resolves;
   - POST answered with 302: re-sent as a GET with no body and no `content-*` header;
   - POST answered with 307: re-sent as a POST with the full 83-byte body (47 bytes plus the
     `agent=` packet);
   - redirect loop: `too many redirects` after exactly 11 requests.
4. **The unfixed tree gives the same outcome as the fix in these cases:**
   - a same-origin redirect with a relative `Location` resolves, with the credential carried;
   - a POST answered with 302 is re-sent as a GET with an empty body and no `content-*` header;
   - a 302 without a `Location` rejects with `HttpError`, whose `data` is
     `{"statusCode":302,"statusMessage":"Found","response":""}`;
   - a redirect loop rejects with `too many redirects` after 11 requests.
   The one difference is the POST answered with 307. It is re-sent as a POST with an EMPTY body but
   with `content-length` and `content-type` still set.

   `platform/git.ts`.
6. **Request options and bodies.** isomorphic-git 1.42.2 never sets `fetchOptions`. The only match
