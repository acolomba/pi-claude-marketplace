<objective>
The info surface says the same thing the list surface now says, in the same
words, on the same row — and it costs one function.

The shape work is already done here and was done years of decisions ago: the info
row shape already declares an optional reasons field, and the info renderer
already composes it for every one of its eight statuses. What is missing is a
producer. This plan supplies one, at the single place where all eight
not-installed return sites converge and where the marketplace entry is in scope.

Purpose: `info` is the surface a user opens when they are deciding. A user who
runs `list` may skim; a user who runs `info <plugin>@<marketplace>` is asking a
direct question about one plugin, and "installing this will leave it off" is part
of the answer. Saying it in a new body line instead of the existing brace would
give one fact two grammars on one surface, which is the thing the row grammar
discipline exists to prevent.

Output: one module-private composer, one total status map that turns a future
status addition into a compile error, one call-site wrap, and eight assertions —
four positive, four negative, every one of them also pinning severity.
</objective>

## Settled design calls (do NOT re-litigate at execution time)

- **The info row shape and the info renderer need NO change.** This is the single
  most likely way to overspend on this plan. The info row's base interface already
  declares an optional reasons field, and the info renderer already pipes it
  through the shared brace composer for every info status. Any diff touching the
  info row interfaces or the info render function is out of scope and is a signal
  that the plan was misread.

- **D-104-05 — one composer at the single consumer, not a parameter through five
  builders.** The not-installed path has eight return sites across five builder
  functions, and three of those five never receive the marketplace entry. All
  eight funnel through one `buildBlock` call site where the entry IS in scope.
  The composer applied there cannot miss an arm; the threading approach silently
  misses any arm whose author forgets, and costs five signature edits to not
  achieve that. The house already does exactly this at the same function's
  installed arms with a sibling post-hoc row shape.

- **D-104-05 — the status gate is a TOTAL map, not a set.** A membership set over
  three statuses is a runtime test: a ninth info status added later would inherit
  "does not carry the token" silently. A total map keyed by the closed status
  union and pinned with `as const satisfies` makes that a compile error at this
  site. The sibling composer's reason set is not a counter-example — its members
  are drawn from a 39-entry token tuple where a total map would be absurd, while a
  9-member status union is precisely the case the idiom exists for, and it matches
  the render map's own missing-arm-is-a-compile-error discipline.

- **D-104-04 — the degraded rows carry the token too.** Two info return sites
  produce a `(remote)` row carrying a failure reason, and two more do the same for
  the partially-available arm. The composer stamps these as well, producing a
  two-token brace. This is deliberate: the claim is entry-derived and stays true
  whether or not the clone could be read, and the two facts answer different
  questions. Suppressing the combination would require gating on whether the row
  already has reasons — which would ALSO suppress the token on the clean
  partially-available row, contradicting a locked decision. Do not add that gate.

- **The barrel is not touched.** Add the predicate to the existing multi-line
  resolver import statement.
