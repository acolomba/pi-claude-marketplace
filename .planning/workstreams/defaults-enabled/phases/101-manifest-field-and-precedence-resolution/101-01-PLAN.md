<objective>
Land the whole vertical slice of this phase in one pass: a `defaultEnabled`
declaration on either site is accepted by the schema, the "entry wins, else
manifest, else `true`" rule is evaluated once inside the shared resolution path,
and the resolved boolean is readable off the resolver's materializable output by
the install path.

The slice is indivisible in this codebase. Adding a non-optional field to
`MATERIALIZABLE_FIELDS` breaks 17 construction sites at compile time — one in
production and sixteen in tests — so `npm run typecheck` does not pass again
until the whole path is wired and every fixture supplies the field. The
typecheck IS the end-to-end integration check for this stack, and a task that
edits the field bag without it looks green while the tree does not compile.

Purpose: DFEN-03 exists so that no later consumer re-derives the precedence rule.
This plan buys that guarantee structurally — the field is non-optional and the
value is threaded through explicit parameters, so a forgotten wiring is a
compile error rather than a silent `true`.
Output: the two production edits, the sixteen mechanical fixture updates, one
end-to-end resolver assertion, and the compile-time proof that the field lives on
the two materializable arms and nowhere else.
</objective>

has an answer, and making it optional would push a `?? true` fallback onto every

(3) `domain/resolver.ts` — add the private precedence helper, placed beside the
other private resolution helpers. Suggested name `resolveDefaultEnabled`, signature
`(entry: PluginEntry, manifest: Record<string, unknown> | null): boolean`, with an
explicit return type to match every other private function in the file. Body: if
`typeof entry.defaultEnabled === "boolean"` return it; else if
`typeof manifest?.defaultEnabled === "boolean"` return it; else return `true`.
Three mechanics to get right. First, `entry.defaultEnabled` is a TYPED read — after
edit (1) the property exists on `PluginEntry` as `boolean | undefined`, so do not
reach for a `Record<string, unknown>` cast the way the component-path reads at
`:892` do; those need the cast only because those fields are `Type.Unknown()`.
Second, the manifest side is `unknown`, so the compiler will not accept a bare
`!== undefined` as a boolean narrowing — a `typeof` test is required by the type
system there, and a `typeof` test is a value test, which is what the file header at
`plugin.ts:10-11` prescribes in place of a key-presence test. A key-presence test
would report a declaration for an explicitly-`undefined` property, which the
validator accepts, and would then return `undefined` where the rule requires
falling through to the manifest. Third, a non-boolean value cannot actually arrive
here — both validators have already run — so the `typeof` narrows are
defense-in-depth and must NOT grow an error path. Say that in the doc comment,
citing DFEN-02 and DFEN-03 and stating that the entry wins over the manifest in
BOTH directions. Every guard gets braces and a following blank line, matching
`sourceUnsupportedReason` and `detectOrphanRewake` in the same file.
