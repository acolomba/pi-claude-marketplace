# HOOKLATESS-01: SessionStart for a plugin that loads after the session starts (upstream evidence)

**Researched:** 2026-11-23 (read-only; evidence for the maintainer's decision, not a decision)
**Upstream read:** `/opt/claude-code/bin/claude`, `claude --version` = `2.1.330 (Claude Code)`, the same binary as `06.1-UPSTREAM-EVIDENCE.md`. Offsets are byte offsets into that binary (`grep -boa` / `dd`). Names are minified. They are valid for 2.1.330 only.
**Pi read:** `node_modules/@earendil-works/pi-coding-agent` `"version": "1.5.1"`.
**Docs/CHANGELOG:** `code.claude.com/docs/en/hooks.md` and `raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md`, both fetched 2026-11-23.
**Upstream contract touched?** Yes. The question is about hook lifecycle that a Claude Code user sees.

## Answer in brief

1. Upstream runs a late SessionStart only in the **headless runner** (`-p`, stream-json, SDK). It runs only when a plugin load that the **host started on its own at launch** finishes after SessionStart: the claude.ai/host plugins sync, or the synchronous settings install (`CLAUDE_CODE_SYNC_PLUGIN_INSTALL`). The run covers only the "owed" plugins, which are plugins with a SessionStart hook that no earlier non-compact SessionStart dispatch in the session matched. It uses the session's original `startSource`. It drops `initialUserMessage` and `sessionTitle`. These paths never run it: a user-initiated reload (`/reload-plugins`, the SDK `reload_plugins` request, including `add_plugins`), a late forwarded install, the default background settings install, and every interactive path.
2. Pi side: the closest analogue is the load's **autoapply** (AAP-01). It installs or enables config-declared plugins in `resources_discover`, which Pi emits *after* the awaited `session_start`. So these plugins miss SessionStart in every mode. In `print`/`json`/`rpc`, Pi has no built-in `/reload`. A mid-session `/claude:plugin install`/`enable` makes hooks live at once (WR-03), and that is the analogue of upstream's `reload_plugins` + `add_plugins`, where upstream runs **no** SessionStart.
3. Smallest design with parity: after a `resources_discover` with reason `startup` (Pi's `startup`/`new`/`resume`/`fork` all emit it), in `print`/`json`/`rpc` only, run SessionStart for the plugins the load's autoapply activated that hold an unrun SessionStart route. Use the source the session's `session_start` dispatch sent. Do not run it on a reload or after a command-time install.
4. Under that design D-CF5-03 needs no amendment. No scenario pins the late-run gap. The reload scenarios all install before Pi starts, so the plugin is already covered and they stay valid under every option.

## 1. Upstream (Claude Code 2.1.330)

**The late run, `ib` (headless chunk, @351776028).** `ib` calls `xqa()` and returns if the result is `undefined`. It then dispatches `MIe(session,{kind:"session-start",source:y,newPluginsOnly:k,...})` and appends the rows through `_U`. A turn waits `S5()` = `1e4` ms for it (`me(K,S5())`), then logs `turn_went_ahead`. Telemetry key: `plugin_late_session_start_hooks`. `ib` lives in the chunk that exports `_runHeadlessStreamingForTesting` (export list @352268244). A single `// Version: 2.1.330` header (@351227821) covers that chunk, and the span holds no second header. [VERIFIED: binary grep]

**Who is owed, `xqa`/`Abt` (@323940328).** `xqa` reads `e.startSource` and returns if it is undefined. It takes `jP("SessionStart").filter((r)=>("pluginRoot"in r))`, returns `{source:e.startSource,newPluginsOnly:{owed:(r)=>Abt(e,r).owed,envFileIndexBase:e.hooksDispatched}}`, and drops plugins whose id is already in `pluginsCovered`. `tAe` fills `pluginsCovered` from `onMatched` on every SessionStart dispatch except `compact` (`if(...,o==="compact")return;`). It sets `startSource` only on the first dispatch: `if(o==="startup"||o==="resume"||o==="fork")Ke.startSource=o`. A late run therefore carries `startup`/`resume`/`fork`, never `clear` or `compact`. [VERIFIED: binary grep]

**Only the owed plugins' hooks run.** The executor `$$i` (@~326979000) filters `qe?Lo.filter((sr)=>qe.repoHooks?...:sr.pluginName!==void 0&&vo.some((Ki)=>Ki.pluginId===sr.pluginId)):Lo`. User, project, and other plugins' SessionStart hooks do not re-run. [VERIFIED: binary grep]

**Dropped output fields.** `tAe` logs `"Ignoring initialUserMessage from a SessionStart hook: its plugin loaded after the session started"` when `newPluginsOnly` is set (@~323943700). The docs say: "If your plugin's SessionStart hook supplies `initialUserMessage` or `sessionTitle`, install the plugin before the session starts. Claude Code ignores both fields from a plugin that finishes installing after the SessionStart hooks have run." [CITED: code.claude.com/docs/en/hooks.md, SessionStart decision control] `additionalContext` and stdout still apply.

**Triggers (complete list).** The headless chunk calls `ib(zf)` at exactly two places, both in the factory (@352068705-352068809): `takeNewPluginsSessionStart:()=>{if(!Gy)return;return Gy=!1,ib(zf)}` and `runSessionStartHooksOfNewPlugins:()=>ib(zf)`. Each name has one caller in class `Mk`. [VERIFIED: binary grep; each name occurs 4x in the chunk (field, ctor default, ctor assign, one call) plus once in the string table]
- **T1, at the first command.** After `resolveDeferredPluginStartup` (`Xp`), the code reads `let D=this.takeNewPluginsSessionStart();if(D){...yield D...}` (@351596409). `Gy` is set by `Gy||=sC`, and `sC||=Boolean(aa||Sd)` (@352079871). `aa` is the startup plugins sync, `XRn(e,...)` when `bQt(e)` holds; `bQt` is `ift(e)&&!j8()`, and `ift` reads `CLAUDE_CODE_SYNC_PLUGINS` / relay / `requiredAlone`. `Sd` is the synchronous settings install `jT` → `gMt(...)`, which runs only `if(s.CLAUDE_CODE_SYNC_PLUGIN_INSTALL)`. Without that variable, the install runs in the background as `Xd=N6(jT,...)` and sets no `sC`. [VERIFIED: binary grep]
- **T2, at a later loop top.** `loopTop` (@351599086) reads `let le=(k||g)&&this.runSessionStartHooksOfNewPlugins()`. `k` is `pluginsSyncNeedsRefresh`, set by `notePluginsSyncLanded` when a startup sync that passed its `Xte()` = `CLAUDE_CODE_SYNC_PLUGINS_INSTALL_TIMEOUT_MS??30000` wait lands later. `g` is set when an organization ask that held commands is answered or a marketplace refill lands. The same `loopTop` handles `lateForwardedInstallNeedsRefresh` (set by `noteLateForwardedInstall` from the SDK `reload_plugins` handler, which carries `add_plugins`, @352166900) and `backgroundInstall.needsRefresh` by refreshing only. Neither one is in `(k||g)`. [VERIFIED: binary grep; the meaning of `g` is MEDIUM, inferred from names]
- **Owed is global.** When T1 or T2 fires, every loaded plugin that is not yet covered runs, including one that a `reload_plugins` call or the background install added earlier. [VERIFIED: `Abt` over all `jP("SessionStart")`]

**Interactive.** The only `newPluginsOnly` call site is `ib`. The other occurrences are `tAe`/`xqa` (@323940506-323942137), the executor (@326978693), the `MIe` pass-through (@331960742), and the string table. The interactive startup dispatch (@332117533) passes `source:"startup"` with no `newPluginsOnly`. The 06.1 record shows that `/reload-plugins` → `refreshActivePlugins` dispatches no SessionStart. `/plugin install` in the REPL "activate[s] immediately when safe" (CHANGELOG 2.1.221) through that same refresh. [VERIFIED: binary grep + 06.1 record]

**`--plugin-dir`.** The plugin loads before the launch SessionStart, so the normal run covers it. The headless `plugin-dir watch` (`jAo`, @326015767) re-watches plugin folders. Nothing there reaches `ib`. [VERIFIED: binary grep]

## 2. Pi side (1.5.1) and the bridge today

| Upstream path | Pi counterpart | Pi mode | Late SessionStart today |
|---|---|---|---|
| T1: sync settings install or plugins sync at launch | Load autoapply (AAP-01) in `resources_discover`, after `session_start` | all four | none (installs after the dispatch) |
| T2: late sync landing, org ask, marketplace refill | none (the background autoupdate, D-PL8-01, updates installed plugins under the same id, so nothing is owed) | -- | n/a |
| SDK `reload_plugins` (+`add_plugins`), `claude plugin install` + reload | `/claude:plugin install/enable/apply/import` mid-session: hooks go live at once | json, rpc (print: later prompts of the same run) | none, which matches upstream |
| Interactive `/reload-plugins`, `/plugin install` | `/reload` in tui | tui | none, which matches upstream (D-CF5-03) |

Evidence:
- Pi emits `session_start` and awaits it before `resources_discover`: `await this._extensionRunner.emit(this._sessionStartEvent);` and then `await this.extendResourcesFromExtensions(...)` (`core/agent-session.js:2776-2778`). The bridge awaits the SessionStart dispatch inside that handler (`bridges/hooks/event-router.ts:1633-1642`). The load's autoapply runs later, in `prepareResources` → `loadReconcile` (`extensions/pi-claude-marketplace/index.ts:192-218`). `resources_discover` has `reason: "startup" | "reload"` (`core/extensions/types.d.ts:572-576`). [VERIFIED: Read]
- `/reload` is built in only in tui: `if (text === "/reload")` (`modes/interactive/interactive-mode.js:2762`). The rpc command switch (`modes/rpc/rpc-mode.js:314-562`) has no `reload` case. In print/json/rpc, `prompt()` runs only extension commands for `/...` text (`core/agent-session.js:1704-1711`). There, `ctx.reload()` is reachable only from an extension command (`rpc-mode.js:256-258`, `print-mode.js:81-83`), and this extension calls no `.reload(` (grep of `extensions/`). Print/json runs the prompts it was given in sequence (`print-mode.js:112-116`). [VERIFIED: Read/grep]
- A reload re-emits `session_shutdown` (`reason: "reload"`) and `session_start` (`reason: "reload"`) (`core/agent-session.js:3103,3130`). The bridge hydrates, rebuilds, and prepares data dirs, then returns: `if (event.reason === "reload") { return; }` (`event-router.ts:1626-1631`). It also runs no SessionEnd on reload (`event-router.ts:1341`). [VERIFIED: Read]
- A command-time install makes hooks live with no reload: "a standalone install ... starts dispatching to the new plugin's hooks immediately, without requiring `/reload`" (`orchestrators/plugin/install-flow-ledger.ts:1057-1060`, rebuild at `:400-424`). Enable, update, uninstall, and the reconcile read pass also call `rebuildRoutingTables` (grep). [VERIFIED: Read/grep]
- The bridge has no `initialUserMessage` support (no match in `extensions/`), so upstream's drop has nothing to remove here.

So in a headless Pi mode a plugin can become active mid-session, through autoapply at load or through a command. It cannot become active through a built-in `/reload`, because none exists there.

## 3. Options (for the maintainer)

- **A, strict parity (T1 analogue).** Remember the source the `session_start` dispatch sent (`claudeSessionStartSource(...)`) and which plugins it matched. After `resources_discover` with reason `startup`, and only when `ctx.mode` is `print`, `json`, or `rpc`, dispatch SessionStart for the plugins whose routes the load added and that hold an unrun SessionStart route. Skip it on `reload`, in tui, and in a pi-subagents child (autoapply is skipped there anyway). Deliver the result through the existing SessionStart context path (pending prompt context, HKRL). This matches T1. Pi's autoapply is synchronous and finishes before the first prompt, which is the shape of `Sd`, not of the background `Xd`.
- **B, also after command-time activation in headless modes.** This diverges from upstream, because `reload_plugins`+`add_plugins` runs none. Neither license covers it, so it is a user question, not a parity fix.
- **C, status quo.** A small divergence for the headless autoapply-at-load case only. No recorded decision covers it today.
- **Capability gap?** None for A. Pi has the event order and the mode (`ctx.mode`) it needs. T2 has no Pi counterpart, so nothing is owed there.

## 4. D-CF5-03 and scenarios

- D-CF5-03 ("Pi `/reload` runs neither SessionStart nor SessionEnd", `.planning/PROJECT.md:2288`) matches upstream in every mode: interactive `/reload-plugins` and headless `reload_plugins` both run none. Option A leaves it as is and needs a new decision ID. It should state that A does not fire on a reload's `resources_discover`, even when autoapply installs something there. Option B needs an amendment only if it fires at a reload.
- Scenarios about SessionStart and reload: `features/hook/session.feature:391-409` ("Reloading pi in the terminal runs no session hook"), `features/hook/additional-context.feature:231-252`, and `features/hook/async.feature:413,432,451,519`. Each one installs the plugin before Pi starts, so the plugin is already covered, and they stay valid under A and B. `session.feature:318-349` (the `reload|quit` matcher outline) is unaffected. No scenario combines autoapply or a mid-session install with a SessionStart hook (awk scan of `features/*/*.feature`). A needs a new json or rpc scenario that fails today.

## Confidence and open points

- High: the trigger set, the owed filter, the source, and headless-only, all from the 2.1.330 binary. Medium: what `g` means (org ask, marketplace refill), read from names. Low: that the mechanism started in 2.1.287.
- Open: upstream keys `startSource` and `pluginsCovered` by `tgs.of(N())`. Whether a `/clear` resets them was not settled, and that matters for Pi `new`, whose load also emits `resources_discover` `startup`. Upstream interactive behavior for plugins that a settings install finishes after launch was not probed. No sandbox probe was run.
- Side observation, outside this question: in `rpc`/`json` the install's "needs reload" hint points at `/reload`, which those modes do not offer.
