# Orchestrators — plugin update

**Scope:** `extensions/pi-claude-marketplace/orchestrators/plugin/update.ts` and `tests/orchestrators/plugin/update.test.ts`
**Test files reviewed:** 1 (`tests/orchestrators/plugin/update.test.ts`, 8502 lines, 132 cases)
**Production modules reviewed:** 1 (`extensions/pi-claude-marketplace/orchestrators/plugin/update.ts`, 3157 lines)

## Summary

This is a genuinely rigorous suite: every case is hermetic (`mkdtemp` + `withHermeticHome` + `finally`-block `rm`), assertions are overwhelmingly whole-value (`assert.deepEqual`/full-body `assert.equal` on the rendered notification string, not substring probes), closed-set `reasons[]` arrays are asserted by value rather than by parsing prose, no `describe()`/`it()`/`.only`/`.skip`/process-wide `mock` import appears anywhere, and the git-source (PURL-06) section consistently threads an in-memory `createGitOpsFake`-backed seam through every case that touches a git plugin source — no test reaches a real remote. Several cases go out of their way to prove a negative control (fixture-rot guards, "the row is the same bytes whether the guard held or not, so compare mtime instead," deliberately multi-element lists to catch order-dependence) that a lot of test suites skip entirely. The two themes a fixing pass should attack first: (1) the two rollback helpers that unwind already-prepared bridge handles (`abortHandles`/`abortPartialHandles`) are exercised only for their state-record consequence, never their filesystem consequence — no case proves the staging directories they claim to clean up are actually gone; (2) one test (`dropCache-fail`) asserts nothing that would fail if the feature it names were deleted outright, and its comment describes a `notifyWarning` call that no longer exists in the production file. A third, lower-priority theme is the file's sheer size: production and test are both large single files built from many well-factored small functions, and a split along the module's own natural phase boundaries would make both much easier to review.

## Unit test findings

### `tests/orchestrators/plugin/update.test.ts`

- **[BLOCKER] `dropCache-fail` test asserts nothing that discriminates the behavior it names** — `test('dropCache-fail: cache path is a directory -> notifyWarning emitted after successful update', ...)`, lines 3275–3320
  The test's own comment (lines 3278–3281) says the cache-drop-failure catch "calls notifyWarning," but the current production code (`dropPluginCompletionCache`, `update.ts` lines 2448–2462) has an **empty catch** that swallows the failure per the D-19-01 comment there — no notify call exists on this path at all. The test's actual assertions only check `errs.length === 0` and that a success notification matching `/updated/` exists (lines 3310–3316); it never asserts `notifications.length` is a specific number, and never confirms the cache-drop code path (as opposed to some other, unrelated success path) actually ran. A wrong implementation that deleted the entire `dropPluginCompletionCache` call and its try/catch from `runThreePhaseUpdate` would pass this test unchanged. Rewrite: assert `notifications.length === 1` (proving no second/warning notification appears despite the forced `EISDIR`), rename the test and its comment to state the true current behavior (the failure is swallowed silently), and drop the stale `(lines 690-696)` reference to a `notifyWarning` call that does not exist in the current file. If a warning notification is actually the intended behavior, that is a production bug to raise separately, not something to paper over in the test.
- **[BLOCKER] `abortHandles`/`abortPartialHandles` are proven only by their state-record consequence, never by their filesystem consequence** — `test('prepare-handles-fail: MCP collision in prepareStageMcpServers -> abortPartialHandles fires, outcome=failed', ...)` (line 3116), `test('ST-9: a version that advanced under an in-flight update aborts on the intent-mark', ...)` (line 7963), `test('ST-9: a record uninstalled under an in-flight update aborts instead of resurrecting it', ...)` (line 8023)
  These are the only three cases that reach `abortHandles` (full four-bridge abort when `markUpdateInProgress` throws after every bridge finished preparing) or `abortPartialHandles` (partial abort when one bridge's `prepareStage*` throws mid-way). All three assert only `outcome.partition`/`reasons`/the resulting `state.json` record — none reads back the skills/commands/agents-staging directories (`locations.skillsStagingDir`, `.commandsStagingDir` equivalent, `.agentsStagingDir`) to confirm the corresponding `abortPreparedSkills`/`abortPreparedCommands`/`abortPreparedAgents`/`abortPreparedMcp` calls actually removed the tmp trees the bridges wrote. A wrong `abortHandles`/`abortPartialHandles` that no-ops every call (silently leaking a tmp dir on every intent-mark or prepare failure) would pass all three cases unchanged, since the state-record outcome is identical either way. Add at least one case per helper that lists the relevant staging directory (or asserts it does not exist / is empty) after the abort fires.
- **[WARNING] The warm sha-pinned-cache offline proof checks only `cloneCalls`, not the full call surface** — `test('PURL-06 / D-78-05 pinned unchanged: manifest sha equals recorded -> outcome (unchanged), no swap, clone dirs untouched', ...)`, lines 6449–6499
  This is the case that proves NFR-5's warm-cache-stays-offline amendment, and it correctly asserts `gitState.cloneCalls.length === 0` (line 6483). But the sibling test proving the analogous path-source guarantee (`'NFR-5: path-source marketplace update calls zero gitOps primitives'`, line 1232) checks `fetchCalls`, `forceUpdateRefCalls`, `checkoutCalls`, **and** `resolveRefCalls` are all empty. This test checks only `cloneCalls`, so a change that added a spurious `fetch`/`checkout`/`resolveRemoteRef` call on the warm path (without touching `clone`) would still pass. Add the same multi-array zero-calls assertion here (`fetchCalls`, `checkoutCalls`, `resolveRefCalls`, `resolveRemoteRefCalls`), matching the stricter sibling pattern.
- **[WARNING] Inconsistent AAA phase-comment discipline** — representative: `test('PUP-3: version equality -> outcome.partition=\'unchanged\'; no bridge state mutation', ...)` (line 673), `test('PUP-6 happy: version bump triggers 3-phase swap; ...', ...)` (line 977), `test('PUP-1 @mp form: enumerates all installed plugins ...', ...)` (line 1268)
  Roughly a quarter of the cases (concentrated in the earlier `PUP-*`-numbered section) rely on blank-line separation alone with no `// arrange`/`// act`/`// assert` labels, while later sections (`WB-01`, `S5`, most `D-141-03` cases) label all three phases explicitly. Not a correctness issue — the skill mandates the labeled convention. Add the labels to the unlabeled cases for consistency, or, if the file's size makes that impractical in one pass, note the exception explicitly rather than leaving it as silent drift.
- **[WARNING] `makeCtx()`'s minimal doubles are cast to the full host interfaces via a double `as`** — `tests/orchestrators/plugin/update.test.ts` lines 225–241 (the sole `makeCtx()` helper every one of the 132 cases uses)
  `ctx`/`pi` are built as small object literals (`{ ui: { notify: ... } }`, `{ getAllTools: ... }`) and cast with `as ExtensionContext` / `as ExtensionAPI` rather than being checked against a narrower, consumer-declared port. This is the "broad cast hiding an invalid double" pattern the skill flags. In practice this is confined to one well-isolated helper (not repeated ad hoc through the file), and is very likely a codebase-wide convention forced by `@earendil-works/pi-coding-agent`'s large host interfaces rather than something local to this file — fixing it would mean narrowing `shared/notify.ts`'s accepted `ctx`/`pi` parameter types project-wide, which is out of scope for a single-file pass. Noted for awareness, not urgent.

## Production code findings

### `extensions/pi-claude-marketplace/orchestrators/plugin/update.ts`

- **[WARNING] Seven `as Error` casts on caught `unknown` values with no `instanceof` check or comment** — lines 534, 2096, 2102, 2115, 2122, 2128, 2342
  Every catch in `commitUpdatePhase3a` (the five per-bridge commits) plus the finalize-catch in `runThreePhaseUpdate` and one enumerate-failure site do `cause: err as Error` (or `finalizeErr as Error`) directly on a `catch (err)`-typed `unknown`, with nothing in the file backing the assumption at that call site. The style guide requires `as`/`!` to carry an obvious or commented reason. Contrast with `notifyDirectFailure` in this same file (`const cause = err instanceof Error ? err : new Error(String(err));`), which already does the safe thing. No ESLint rule in this repo enforces "only `Error` is thrown," so this is not toolchain-gated. Either add a one-line comment at each site invoking the project-wide "only `Error` instances are thrown" convention, or switch all seven to the `instanceof`-narrowing pattern already used a few hundred lines away in the same file, for internal consistency.
- **[WARNING] `updateSinglePlugin` reads `process.cwd()` directly instead of taking `cwd` as a parameter** — line 608
  The cascade entrypoint's own comment acknowledges this ("Future wiring may add a dependency-injection seam if needed"). Because of it, 17 cases in the paired test file must call `process.chdir(cwd)` before invoking `updateSinglePlugin` and restore it afterward (all correctly paired via `try/finally` or `t.after()`, so no leak was found, but the discipline burden is real and this is exactly the "hidden dependency" class the testability checklist calls out). `updateSinglePlugin` is typed to the shared `PluginUpdateFn` signature used by other cascade callers, so fixing this here alone would mean changing that shared type across every implementer — flagging as design debt rather than a mechanical one-file fix. The existing `cloneCacheSeam`/`credentialOps` parameter-injection pattern already used on the direct path (`UpdatePluginsOptions`) is the shape a `cwd`-carrying `PluginUpdateFn` would eventually take.
- **[WARNING] Two inline `new Date().toISOString()` calls** — `refreshDisabledRecord` and `finalizeUpdateRecord` (`sRecord.updatedAt = new Date().toISOString();`)
  A hidden-clock dependency per the testability checklist. Low priority: this is a project-wide pattern (every orchestrator stamps `updatedAt` the same way, not something specific to this file), and the paired tests already avoid asserting literal timestamps (they compare mtimes/equality-across-calls instead), so it is not currently causing test pain.
- **[WARNING] `UpdatePluginsOptions` has no top-level doc comment** — line 225
  `UpdateCloneCacheSeam` immediately above it (line 213) carries a full rationale comment; every field of `UpdatePluginsOptions` is individually documented, but the interface itself has no summary line describing what it is for. Add one for consistency with its neighbor.

### Module-size / split recommendation

At 3157 lines, `update.ts` is large enough that its 8502-line paired test file is difficult to navigate even though the individual functions are well-factored (many are already extracted specifically to stay under the sonarjs/fallow cognitive-complexity ceilings, per the file's own comments). The module already has two sibling files for adjacent concerns (`update-row.ts`, `update.messaging.ts`), so extending that same convention is the natural fix rather than a novel restructuring. Four responsibility-aligned pieces are visible in the current file:

1. **`update.ts` (trimmed):** the two public entrypoints (`updatePlugins`, `updateSinglePlugin`), target enumeration (`enumerateTargets`, `enumerateMarketplaceTarget`, `resolveUpdateMarketplaceScope`), and the direct-vs-cascade dispatch glue.
2. **`update-preflight.ts`:** candidate resolution and gating (`preflightUpdate`, `resolveUpdateCandidate`, `triageUpdateMembership`, `staticPreflightRow`, `widensPartialGate`, `makeUpdateCloneProbe`, `deriveUpdateToVersion`) plus the disabled-record refresh path (`refreshDisabledRecord`, `runDisabledRecordRefresh`, `disabledPinProjection`, `nextDisabledPin`, `disabledRefreshWouldWrite`) — "what should happen and is it allowed."
3. **`update-swap.ts`:** the heterogeneous-undo 3-phase engine itself (`prepareUpdateHandles`, `abortHandles`/`abortPartialHandles`, `markUpdateInProgress`, `commitUpdatePhase3a`, `commitUpdateHooks`, `finalizeUpdateRecord`, `applyPerBridgeResources`, `applyAllSuccessRecordFields`, `runThreePhaseUpdate`) — "how the swap is executed," the part the file's own header comment calls out as the hand-rolled, non-`runPhases` design.
4. **`update-cascade.ts`:** outcome-to-message mapping and rendering (`outcomeToCascadePluginMessage`, `projectSkippedOutcome`, `cascadeSkipSeverity`, `renderUpdateCascadeAndNotify`, `notifyDirectFailure`, `narrowDirectFailReason`, `notifyBareFormEnumerateFailure`) — "how the result is reported," naturally paired with the existing `update.messaging.ts`.

Splitting this way would let the paired test file split along the same lines (four files of roughly 2000 lines each instead of one 8502-line file), each independently coverable and reviewable, and would make the rollback-path gap noted above (finding 2) easier to spot in isolation.
