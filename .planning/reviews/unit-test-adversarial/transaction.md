# Transaction — phase ledger, rollback, state guard

**Scope:** `extensions/pi-claude-marketplace/transaction/` (`phase-ledger.ts`, `rollback.ts`, `with-state-guard.ts`) and their paired tests under `tests/transaction/`.
**Test files reviewed:** 3
**Production modules reviewed:** 3

## Summary

This is the strongest area reviewed so far: `phase-ledger.test.ts` and `rollback.test.ts` are model examples of the guidelines — every case records into one shared log or compares one hand-written whole-value literal, forward-failure and undo-failure paths are both fully exercised, `PathContainmentError` bypass is proven by identity, and Error-vs-string undo failures are both covered to prove the `cause` key is omitted (not merely `undefined`) when the undo throw wasn't an `Error`. `with-state-guard.test.ts` is also disciplined about hermeticity (one `mkdtemp` per case, real `proper-lockfile` contention driven by controlled promises instead of sleeps, no second OS process), but it surfaces the one real production gap in this area: `with-state-guard.ts` hardcodes the `proper-lockfile` import with no injectable seam, so seven cases resort to `t.mock.method(lockfile, "lock", ...)` — patching a third-party singleton — to reach the acquisition/release failure paths that `LockedStateTransactionDeps` cannot express. A fixing pass should: (1) add a `null`/non-ELOCKED-code case to close a real branch-coverage gap in `isLockHeldError`, (2) extend `LockedStateTransactionDeps` (or a sibling deps type) with an injectable lock port so the `lockfile` monkey-patching goes away, and (3) group `with-state-guard.test.ts`'s cases into `describe('withStateGuard', ...)` / `describe('withLockedStateTransaction', ...)` blocks to match this module's two exported entrypoints and the majority convention elsewhere in `tests/`.

## Unit test findings

### `tests/transaction/phase-ledger.test.ts`

- **[WARNING] Undocumented compile-time-only fixture** — `lines 109–113` (`SCHEDULE_TYPE_EVIDENCE`). This constant exists purely to prove, at compile time, that a `{ name, do }` object literal (no `undo`) `satisfies Phase<LedgerContext>` — the shape `createSchedule`'s `phasesWithoutUndo` branch relies on. It is legitimate (same spirit as the type-only-module `satisfies` pattern), but it has no comment explaining why it exists or why it's immediately `void`-discarded, so a reader has to reverse-engineer its purpose. Add a one-line comment above it, e.g. `// Compile-time proof that Phase<C>.undo is optional, which phasesWithoutUndo below relies on.`

This file otherwise fully satisfies the order-of-collaborators proof (`context.operations` is the single shared log for every `do`/`undo` call across all phases, compared via `assert.deepStrictEqual` against a hand-written array per case — never per-phase logs), covers every undo-failure combination (own-phase undo failing, reverse-walk undo failing, several reverse failures, `PathContainmentError` short-circuit from both the failing phase's own undo and a later reverse undo), and uses `assert.strictEqual` reference checks everywhere identity (not just structural equality) is the promise — necessary because `assert.deepStrictEqual` compares `Error` objects structurally (name/message/cause), so a wrong implementation that rebuilt an equivalent-looking `Error` instead of preserving the original reference would otherwise slip through.

### `tests/transaction/rollback.test.ts`

No findings. Every case builds its expected `RollbackErrorResult` as an independent hand-written literal (never by calling `formatRollbackError` on itself), asserts the whole value with `deepStrictEqual`, and separately pins reference identity (`assert.strictEqual`/`assert.notStrictEqual` on `.error`, `.error.cause`, and `.rollbackPartials`) exactly where `deepStrictEqual`'s structural `Error` comparison would otherwise let a wrong implementation pass. One clarification for the fixing pass: the brief's check "`formatRollbackError` renders text — compare whole rendered strings" doesn't literally apply to this module — per its own header comment, `formatRollbackError` is presentation-free and returns structured data only (`{ error, rollbackPartials }`); no string is composed here. The equivalent principle (hand-written literal expectations, never round-tripped through the production function) is already satisfied.

### `tests/transaction/with-state-guard.test.ts`

- **[BLOCKER] `isLockHeldError` branch coverage gap** — `extensions/pi-claude-marketplace/transaction/with-state-guard.ts` lines 172–179 (function under test), exercised from this test file. `isLockHeldError` is a 4-clause `&&` chain: `typeof err === "object" && err !== null && "code" in err && err.code === "ELOCKED"`. Every acquisition-failure case in this file rejects with either a real `ELOCKED` error (`"prevents a real contender..."`), a plain `Error` with no `code` property (`"propagates an ordinary acquisition Error..."`, line 593), or a bare string (`"normalizes a non-Error acquisition failure..."`, line 632). No case rejects with a literal `null`, so the `err !== null` clause's false arm is never taken; and no case rejects with an object that has a `code` property set to something other than `"ELOCKED"` (e.g. `"ENOENT"`), so the final `.code === "ELOCKED"` clause's false arm (reached only when `"code" in err` is true) is never taken either. Per this project's direct-coverage rule, an unrun branch is a gap regardless of how narrow it looks. Add two cases mirroring `"propagates an ordinary acquisition Error without loading state or entering the callback"`: one where `t.mock.method(lockfile, "lock", () => Promise.reject(null))` and the thrown error is asserted to be `toError(null)`'s result (a plain `Error`, not `StateLockHeldError`); one where the rejection is an `Error` with a `.code` of something other than `"ELOCKED"` (e.g. `Object.assign(new Error("disk full"), { code: "ENOSPC" })`), asserting the thrown error is likewise the ordinary `Error`, not translated into `StateLockHeldError`. (This was traced statically per the diagnostic-review constraint against running commands; confirm with `npm run test:coverage:direct -- tests/transaction/with-state-guard.test.ts` before or after adding the cases.)

- **[WARNING] No `describe()` grouping by exported entrypoint** — the whole file. `with-state-guard.ts` exports two entrypoints, `withStateGuard` and `withLockedStateTransaction`, but every case in this 830-line file is a flat top-level `test()` with no `describe()` blocks, interleaving cases for both functions. The guideline ("one top-level `describe()` per exported entrypoint when a module has several") and this repo's own majority convention (e.g. `tests/persistence/config-io.test.ts`, `tests/persistence/config-write-back.test.ts`) both call for `describe('withStateGuard', () => { ... })` and `describe('withLockedStateTransaction', () => { ... })` wrapping the respective cases.

- **[WARNING] Hand-rolled call-log stand-ins instead of `t.mock.fn()`** — representative lines: `99–108` (`persistenceLog` in `"saves one explicit transaction..."`), `174–184`, `217–224` (`saveLog`), `334–344`, `379–387` (`saveAttempts` counter), `411–421`, `455–463`. Several cases wrap the injected `loadState`/`saveState` in a hand-written function that pushes a string or a cloned value into a module-scope-shaped array/counter, then asserts that array with `deepStrictEqual`. Since `loadState`/`saveState` are already explicit dependencies (the right design per this project's own DI convention), the idiomatic tool for "real behavior, recorded calls" is the current test context's `t.mock.fn(loadState)` / `t.mock.fn(saveState)` (which delegates to the real implementation and exposes `.mock.calls[i].arguments` and `.mock.callCount()` for free) rather than a manually maintained array. This isn't currently a vacuous check — the state-on-disk assertions in the same cases already independently discriminate the behavior a wrong implementation would break — but replacing the hand-rolled logs with `t.mock.fn()` removes bespoke bookkeeping code and puts the interaction-observation on the sanctioned tool.

- **[WARNING] `t.mock.method(lockfile, "lock", ...)` patches a third-party singleton instead of an injected port** — lines `596`, `632`, `669`, `707`, `744`, `773`, `805`. Seven cases replace `proper-lockfile`'s exported `lock` function directly (via `t.mock.method` on the imported `lockfile` module object) to simulate acquisition and release failures. This uses the sanctioned `t.mock` API and auto-restores after each case, so it isn't a hermeticity break by itself, but it is patching a real third-party module rather than substituting an injected collaborator — see the matching production finding below. Once `with-state-guard.ts` grows an injectable lock port, these seven cases should supply a fake/stub through that port instead of reaching into `proper-lockfile`'s module object.

### `extensions/pi-claude-marketplace/transaction/with-state-guard.ts`

- **[WARNING] Hidden `proper-lockfile` dependency with no injectable port** — `acquireStateLock` (lines 158–166) imports `lockfile` from `"proper-lockfile"` at module scope and calls `lockfile.lock(...)` directly; `withScopeLock` (lines 111–156) calls `acquireStateLock` the same way. Unlike `loadState`/`saveState`, which are already injectable through `LockedStateTransactionDeps` (and that seam is exercised by real production code, `orchestrators/plugin/reinstall.ts`), there is no equivalent seam for lock acquisition/release. This is exactly the "hidden dependency" pattern the testability rubric calls out (fix #3: inject a side-effecting port through a narrow consumer-declared interface) and it's the reason the paired test file resorts to monkey-patching the imported `lockfile` object seven times (see the matching WARNING above). Add a narrow port, e.g. `interface LockProvider { lock(root: string, opts): Promise<() => Promise<void>> }`, default it to the real `acquireStateLock` implementation, and thread it through as an optional field next to `loadState`/`saveState` (either widening `LockedStateTransactionDeps` or adding a sibling deps parameter to `withScopeLock`).

- **[WARNING] Undocumented top-level exports** — `LockedStateTransaction` (lines 40–43) and `LockedStateTransactionDeps` (lines 45–48) have no JSDoc, unlike every other export in this file (`withStateGuard` and `withLockedStateTransaction` both have full doc comments citing ST-7/PRL-10). Add a short `/** ... */` above each interface stating its role (`LockedStateTransaction`: the explicit-save handle passed into a `withLockedStateTransaction` callback; `LockedStateTransactionDeps`: the optional `loadState`/`saveState` override point used by callers such as `reinstall.ts` and by tests).
