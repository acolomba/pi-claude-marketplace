# Architecture — hooks gates

**Scope:** `tests/architecture/{hooks-async-rewake,hooks-lifecycle,hooks-foundation,hooks-translators,hooks-if-field,hooks-dispatch,hooks-cap-notify,no-hooks-strict-additional-properties}.test.ts`, plus the `extensions/pi-claude-marketplace/bridges/hooks/**` and `domain/components/hooks*` production modules these gates assert against.
**Test files reviewed:** 8
**Production modules reviewed:** 10 (full read + style pass); several more consulted only to resolve the pairing question (see "Not covered")

## Summary

The eight files split cleanly into two groups. Five (`hooks-lifecycle`, `hooks-dispatch`, `hooks-if-field` partially, plus the epoch-parity and env-parity cases in `hooks-async-rewake`) are genuine architecture gates: they plant real violations against real source text or drive a real multi-module pipeline, and no single paired unit-test module could express the property they check. The other three (`hooks-foundation`, `hooks-translators`, `no-hooks-strict-additional-properties`) contain material that is either a straight duplicate of stronger, already-existing coverage in the module's real paired test, or the *only* coverage of a single-module behavior that has never made it into that module's paired test file. One gate (`no-hooks-strict-additional-properties`'s "defense-in-depth" block) scans the wrong file entirely and provides zero protection against the regression its own header describes. The production code under `bridges/hooks/**` and `domain/components/hooks*` is uniformly well-documented and typed; the only real findings are two testability-design issues (a test-only reset export, an inline `Date` read) rather than correctness problems. Priorities for a fixing pass: (1) fix the wrong-file defense-in-depth gate, (2) relocate the four single-module behavior tests currently stranded in `tests/architecture/` to their real paired modules, (3) remove the one exact duplicate test and the one exact-duplicate-of-payload-tests assertion.

## Unit test findings

### `tests/architecture/hooks-async-rewake.test.ts`

- **[WARNING] Third test duplicates existing coverage in the paired module** — `test('prevents a pre-reload async child from affecting the advanced routing epoch')` (lines 373–416). This is the same scenario, built from the same primitives (`spawnAndRegister`, `bumpEpoch` before exit/close, assert no `pi.sendMessage`/no notify/empty PID table), as `tests/bridges/hooks/async-rewake/registry.test.ts`'s `test('discards a stale child after the routing epoch advances', ...)` (lines 1595–1637). The paired module's version is strictly more thorough — it also asserts timer cleanup via `observeTimers`. This architecture copy adds no protection a wrong implementation could slip past that the paired test would not already catch. Delete this test from the architecture file; `tests/bridges/hooks/async-rewake/registry.test.ts` already owns the scenario.
- The first two tests (env parity between the sync `dispatchHookExec` lane and the async `spawnAndRegister` lane, for `PreToolUse` and `SessionStart`) are legitimate: no single paired unit-test module can express "these two independently-tested code paths build byte-identical environments except one marker," because that property spans `dispatch-exec.ts` and `async-rewake/registry.ts`. Keep these in architecture.

### `tests/architecture/hooks-lifecycle.test.ts`

- **[WARNING] No `// arrange` / `// act` / `// assert` phase comments anywhere in the file** — all six tests (lines 124–332). Every sibling architecture file in this assignment that runs comparable source-scanning logic (`hooks-dispatch.test.ts`, `no-hooks-strict-additional-properties.test.ts`) uses the three-phase comment convention; this file has none. Add the phase comments (arrange: read the file; act: run the scan/regex; assert: check the result) for consistency, even though the "act" step is thin in a pure source-grep test.
- The grep-based technique itself (strip comments, assert a mutator call site is followed by a rebuild call within a bounded window; Block E's regex-extracted function body) is a legitimate "plants the violation" gate: a real regression (moving the `rebuildRoutingTables()` call out of the per-plugin lock, or removing the `deleteParsedConfig` prefix) would fail it. No behavior finding.

### `tests/architecture/hooks-foundation.test.ts`

It navigates the raw introspected JSON-Schema shape (`anyOf`, `const`) rather than driving the compiled validator. A behaviorally-identical schema built a different way (e.g. `oneOf` instead of `anyOf`, or a differently-shaped-but-equivalent union) would fail this test while validating correctly — it tests shape, not the contract. The actual accept/reject behavior (`schemaVersion` 1 and 2 accepted, 3 rejected) is already exercised through the real validator in `tests/persistence/state-io.test.ts` (the `{ name: "schema version 1/2/3", ... accepted: ... }` data table around lines 213–215). Delete this block; the existing behavior-driven test in the properly-paired module already covers it, more robustly.
- **[WARNING] Block 2 is the same pattern, also duplicated** — `test('HOOK-02 / D-57-01: PLUGIN_INSTALL_RECORD_SCHEMA.resources.hooks is REQUIRED Array(String)')` (lines 63–109). It walks `resourcesSchema.required`, `hooksProp.type`, `itemsSchema.type` on the introspected schema object. The same requirement is already exercised through `Check()`/`loadState` behavior in `tests/persistence/state-io.test.ts`'s `rejects a plugin without hooks at the published validator` and `rejects a plugin with non-array hooks at the published validator` tests (around lines 1071–1108). Delete this block for the same reason as Block 1.
- **[WARNING] Block 3 belongs in the schema module's own paired test, not architecture** — the two `HOOK-03` tests (lines 143–193, `HOOKS_CONFIG_SCHEMA` carries no `additionalProperties: false` / `HOOKS_VALIDATOR.Check` accepts unknown fields). `HOOKS_CONFIG_SCHEMA` and `HOOKS_VALIDATOR` are defined in `extensions/pi-claude-marketplace/domain/components/hooks/schema.ts`, whose paired test is `tests/domain/components/hooks/schema.test.ts` — that file currently has **zero** coverage of the HOOK-03 lenient-stance contract (grepped for `additionalProperties`/`futureField`/`lenient`: no hits). This is a real, unique-to-this-file coverage item, but it belongs in the properly-paired module. Move both tests to `tests/domain/components/hooks/schema.test.ts`.
- Block 4 (`SUPPORTED_COMPONENT_KINDS` / `UNSUPPORTED_COMPONENT_KINDS` closed-tuple pins, lines 199–212) is a legitimate architecture-style closed-set lock, consistent with sibling files elsewhere in the suite (`notify-closed-set-locks.test.ts`, `partial-vocabulary-guard.test.ts`). No finding.
- **[WARNING] Block 5 is single-module behavior of `domain/resolver.ts` with no coverage in its paired test** — the two `resolveStrict`/`resolveLoose` "admits a hook-only plugin" tests (lines 257–285) and the `@ts-expect-error` type-level guard (lines 288–297). `tests/domain/resolver.test.ts` (3,949 lines) has no test exercising a hook-only plugin (`SUPPORTED_COMPONENT_KINDS`/`hookOnly`/`hookplug` all grep to zero hits there). ### `tests/architecture/hooks-translators.test.ts`

- **[WARNING] Second test duplicates coverage that already exists per-module** — `test('keeps shared built-in and custom tool-name mapping across all tool translators')` (lines 110–145). The exact same "bash → Bash" and "mcp__x__y passes through unchanged" mapping is already asserted, with the same input strings, in `tests/bridges/hooks/payloads/pre-tool-use.test.ts`, `post-tool-use.test.ts`, and `post-tool-use-failure.test.ts` (each has a `maps a built-in tool to the complete <Event> envelope` / `preserves a custom tool name and input without mutation` pair). Remove this test from the architecture file — the three payload test modules already gate it. If a genuine cross-file consistency guarantee is still wanted (e.g. "all three translators delegate to the same mapping table"), assert that structurally (same function reference) rather than re-driving each translator with sample inputs.
- **[WARNING] Dynamic import built via string concatenation** — `loadTranslator` (lines 44–49): `"../../extensions/.../payloads/" + kebab + ".ts"`. Use a template literal (`` `.../payloads/${kebab}.ts` ``) for consistency with the rest of the codebase's import-path style; the concatenated form also means the dynamically-imported module's shape is entirely unchecked by the compiler (`as TranslatorModule` at the call site) — acceptable for a test but worth noting as a hand-typed contract that will not fail to compile if a translator's signature changes.
- The first test ("keeps one translator module for every dispatchable event") is a legitimate architecture inventory/completeness check that no single `payloads/<event>.test.ts` file could express. Keep it.

### `tests/architecture/hooks-cap-notify.test.ts`

- **[WARNING] Imports the process-wide `mock` from `node:test` instead of the context's `t.mock`** — `import test, { mock } from "node:test";` (line 20) and `mock.fn()` in `makeCtx()` (line 81). None of the three `test(...)` callbacks take a `t` parameter. Per the unit-testing rules, doubles must come from the current test's context (`t.mock.fn()`), not the module-global `mock` export. ### `tests/architecture/no-hooks-strict-additional-properties.test.ts`

- **[BLOCKER] The "defense-in-depth" gate scans the wrong file and provides no protection** — `test("HOOK-03: hooks.ts source never carries 'additionalProperties: false' (defense-in-depth)")` (lines 43–57), which reads `HOOKS_TS_PATH = ".../domain/components/hooks.ts"`. This test is the only place that property is verified, and it belongs in `tests/persistence/migrate.test.ts`. Move it there.

## Production code findings

### `extensions/pi-claude-marketplace/bridges/hooks/routing-state.ts`

- **[WARNING] `resetEpoch` and `resetRoutingState` are test-only exports** — `resetEpoch` (lines 192–194) and `resetRoutingState` (lines 320–325). Grepping `extensions/` for non-test call sites of either name returns nothing outside this module itself (`resetRoutingState` calls `resetEpoch` internally); every other caller is test setup. The module's own doc comment concedes this ("Its only caller today is test setup, which is what a reset is for"). Per the testability rule, an export that exists only to serve a test is a design finding even when, as here, the module offers a considered rationale (a single lifecycle operation that knows the full cell inventory, rather than four separately-exported clears). No fix is strictly required, but if this stays, label it explicitly as a test-support seam in the doc comment rather than "a public lifecycle operation" — and if a real `/reload`-time full-reset code path is ever added, that will retroactively justify the current framing.

### `extensions/pi-claude-marketplace/bridges/hooks/async-rewake/registry.ts`

- **[WARNING] Inline `Date` read forces global time-faking in tests** — `spawnedAt: new Date().toISOString()` inside `spawnAndRegister` (line 319). This is a hidden dependency on the ambient clock. Its cost is visible in the paired tests: `tests/bridges/hooks/async-rewake/registry.test.ts` and `pid-table.test.ts` both have to assert literal ISO timestamps (e.g. `"2026-08-31T10:05:00.000Z"`) by globally faking `Date` via `t.mock.timers`. Fix: add an injected `now: () => string` to `SpawnDeps` (defaulting to `() => new Date().toISOString()`), the same pattern already used for `spawnImpl`/`dispatchId` in the same interface, so a test can pass a fixed value without touching the global timer.

### `extensions/pi-claude-marketplace/bridges/hooks/event-router.ts`

- **[WARNING] Inline `os.homedir()` reads force a global-env-var workaround in tests** — `homedir()` is called directly inside business logic at three sites: `readAndCachePluginHooks` (line 179), `hydrateCacheFromDisk` (line 446), and `tryHydrateOnePlugin` (line 573), each building the MATCH-03 `ifCtx` anchor triple. This is the same class of hidden dependency as an inline `Date.now()`. The cost shows up in `tests/bridges/hooks/event-router.test.ts`, which has to save, mutate, and restore `process.env.HOME` directly (lines 99–110) to control what `homedir()` returns — a global-state workaround the skill flags as a hermeticity pattern to avoid where an injected value would do. Fix: thread `homedir` through as an explicit parameter (e.g. on the `opts` bag `registerHooksBridge`/`hydrateProjectScopeForCwd` already accept) rather than reading the OS global inline at three separate call sites.
