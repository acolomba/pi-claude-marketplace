# Bridges — hooks `if:` predicate compiler

**Scope:** `extensions/pi-claude-marketplace/bridges/hooks/if-field/{bash,glob,index}.ts` and their paired tests under `tests/bridges/hooks/if-field/`
**Test files reviewed:** 3
**Production modules reviewed:** 3

## Summary

The production code is genuinely clean from a testability standpoint: all three modules are pure, dependency-free (no hidden singletons, no `Date`/`process.env`/`randomUUID` reads), fully typed with discriminated unions and `assertNever` exhaustiveness, and `bash.ts` never shells out — it hand-parses Bash syntax as strings, matching the repo's `no-shell-out` architectural gate. No test in this area spawns a real shell either. Assertions throughout use `assert.deepStrictEqual`/`assert.strictEqual` on whole values; there are no `assert.ok`/`assert.notStrictEqual` vacuous checks and no unawaited async assertions (the whole surface is synchronous). Two real problems stand out. First, `index.test.ts`'s barrel re-export proof only checks type equality, never runtime binding identity, so a future refactor that turns `export { compileBashGlob } from "./glob.ts"` into a wrapper function would sail through undetected. Second, two tests in `index.test.ts` force unreachable catch branches by monkey-patching `String.prototype.endsWith` and `RegExp.prototype.exec` — shared global state during test execution — which is avoidable because `ifFires`/`resolveTarget` only ever read `ctx.cwd` yet are typed to take the entire `ExtensionContext`, forcing every behavioral test into an `as ExtensionContext` cast. The dominant structural theme across all three test files is bundling several independent match/no-match scenarios into one object and one `assert.deepStrictEqual`, rather than one sibling `test()` per scenario; this is pervasive (most of `glob.test.ts`, about half of `index.test.ts` via `.map()` over row arrays) but does not by itself weaken discrimination since every case is still asserted. Finally, all three production files carry stale "lands in a follow-up plan" documentation for functionality (`ifFires`, `compileIfPredicate`, the `ctx.cwd` projectRoot fallback) that is already implemented in this very directory.

## Unit test findings

### `tests/bridges/hooks/if-field/bash.test.ts`

- **[WARNING] Bundled sub-scenarios in `bashSubcommandFires` tests instead of one test per scenario** — `test('applies interpolation fallback only to the promised specific glob')` (lines 419–433) and `test('returns the direct glob decision when interpolation fallback is unavailable')` (lines 435–449). Each test packs two independent match facts (`specific`/`commandName`, `matching`/`different`) into one object and one `assert.deepStrictEqual`. Split each into its own `test()` — e.g. `'fires on the specific pattern when interpolation is present'`, `'does not fire on the command-name-only pattern when interpolation is present'` — so a failure names exactly the scenario that broke.
- **[WARNING] `expectedParse` literals never `satisfies`-checked against `ParseResult`** — e.g. lines 15–28, 41–49, 217, 282 (representative; the pattern repeats across all ~20 cases in `describe('parseBashSubcommands', ...)`). Every `expectedParse` object is a full, direct match for one arm of the exported `ParseResult` union, but none is annotated `satisfies ParseResult`. Add `satisfies ParseResult` to each literal so a future shape change to `ParseResult` fails these tests at compile time instead of only at the (still-correct) runtime `deepStrictEqual`.

### `tests/bridges/hooks/if-field/glob.test.ts`

- **[WARNING] Nearly every test bundles 2–4 independent match scenarios into one object and one assertion instead of one sibling `test()` per scenario** — representative examples: lines 10–49 (`nested`/`missingSegment`/`wrongTail` in one `matches` object), 51–84 (`commandOnly`/`arguments`/`pathArgument`/`longerCommand`), 152–187 (`exact`/`differentSeparator`/`trailingArgument`), 588–625 (`zeroCharacters`/`oneSegment`/`multipleSegments`/`missingTail`), and every row body inside the `compilePathGlob` `for` loop (lines 322–489, e.g. the `zeroSegments`/`multipleSegments`/`wrongRoot` triad per row). These are pure matchers — exactly the case the review brief flags as prime for one-row-one-test structure. Split each bundled `matches`/`paths` object into its own named `test()` (e.g. `'fires when a nested segment satisfies the globstar'`, `'does not fire when the middle segment is missing'`), keeping the compile-time `metadata` assertion (raw/tokens/anchor/absoluteBase) as one separate test per pattern. This does not change any assertion's strength — `deepStrictEqual` on the bundled object already reports every mismatch — but it will make a broken scenario immediately nameable from the test report instead of requiring a diff read, and it stops one scenario's thrown exception (not just a value mismatch) from hiding the pass/fail of its siblings.

### `tests/bridges/hooks/if-field/index.test.ts`

- **[BLOCKER] Barrel re-exports proven equal only by type, never by runtime binding identity** — lines 54–62 (the `Same<...>` `satisfies` checks for `exportedCompileBashGlob`/`exportedCompilePathGlob`/`exportedParseBashSubcommands`/`exportedBashSubcommandFires` against their `defining...` counterparts). `index.ts` re-exports these four functions and two types from `bash.ts`/`glob.ts` (the "Barrels" pattern in the skill). The skill requires "a test asserting each runtime re-export is the same binding as its source with `assert.strictEqual()`" — this file only proves the *types* match. A plausible future edit that turns a re-export into a thin wrapper (e.g. `export function compileBashGlob(raw) { return realCompileBashGlob(raw); }`) keeps every one of these type checks green while silently breaking binding identity, and nothing here would catch it. Add, alongside the existing `Same<>` checks: `assert.strictEqual(exportedCompileBashGlob, definingCompileBashGlob)`, and the same for `exportedCompilePathGlob`/`definingCompilePathGlob`, `exportedParseBashSubcommands`/`definingParseBashSubcommands`, `exportedBashSubcommandFires`/`definingBashSubcommandFires`.
- **[BLOCKER] Global built-in prototypes monkey-patched to force unreachable catch branches** — `test('falls open when Bash predicate compilation throws')` (lines 369–398, patches `String.prototype.endsWith`) and `test('falls open when a prefix match has no captured prefix or inner value')` (lines 417–447, patches `RegExp.prototype.exec`). Both use `t.mock.method` on a shared global prototype rather than on a case-owned collaborator — this is the "shared global state" hermeticity break the skill classifies as a BLOCKER, because during the synchronous body of the test *any* code that calls `.endsWith()` on the exact string `"git *"`, or `.exec()` on a `RegExp` whose `.source` matches `IF_PREFIX_REGEX`, is silently redirected. Both exist only because `compileBashGlob`/`compilePathGlob` are documented as "pure-and-total... MUST never throw" (`glob.ts` lines 25–31), so the surrounding `try`/`catch` in `compileIfPrefixForm` (`index.ts` lines 278–301) is otherwise untestable by honest injection. The third test in this family, `test('falls open when path predicate compilation throws')` (lines 400–415), shows the clean alternative already in the same file: it uses a **locally-scoped throwing getter** on a plain object literal (`get cwd(): string { throw ... }`) with no global mutation at all. Prefer that shape; where the callee truly takes no injectable seam (as `compileBashGlob(inner: string)` does not), do not reach for a global-prototype patch — either accept the branch as compiler/contract-forced-unreachable and drop the test, or give `compileBashGlob`/`compilePathGlob` an injectable failure seam scoped to the test.
- **[BLOCKER] Error assertion matches by message substring instead of the exact message the sibling tests already compute** — `test('rejects a predicate outside the exhaustive dispatch vocabulary')`, lines 682–693: `assert.throws(() => ifFires(...), { name: "Error", message: /unreachable HookExecResult arm/ })`. The identical `assertNever` failure is asserted with the **exact** message elsewhere in this area (`glob.test.ts` lines 271–275 and 715–718: `assert.throws(fn, new Error('unreachable HookExecResult arm: {"kind":"unknown"}'))`). The regex here only proves the prefix string appears, not that the corrupted value (`{"kind":"unknown"}`) is actually embedded — a mutant `assertNever` that drops the serialized value from its message would still pass this test while failing its siblings. Replace with the exact-message form already used in `glob.test.ts`: `assert.throws(() => ifFires(invalidPredicate, ...), new Error('unreachable HookExecResult arm: {"kind":"unknown"}'))`.
- **[WARNING] Row arrays reduced with `.map()` inside one test instead of one sibling `test()` per row** — `test('compiles known Bash and path-tool prefixes in stable row order')` (162–243), `test('partitions empty, non-tool, unknown-prefix, and MCP boundary declarations')` (245–344), `test('compiles MCP literals and both server-prefix forms exactly')` (346–367), `test('evaluates Bash matches, misses, and missing commands independently')` (449–481), `test('evaluates path membership, non-membership, absolute paths, and cwd fallback')` (506–583), `test('evaluates MCP literal equality, server membership, and wrong servers')` (585–616), `test('dispatches all five predicate arms in stable row order')` (618–680). Each builds a `rows`/`declarations` array and reduces it with `.map()` inside a single test, then asserts the whole result array at once. Convert each to a `for (const row of rows) { test(\`...${row.name}\`, () => {...}); }` loop with one `test()` per row, per the skill's data-driven-cases rule, so a thrown exception on one row does not swallow the pass/fail signal of the others and a failing row is nameable from the test report alone.
- **[WARNING] `as ExtensionContext` casts a partial object past the type system, in 7 places** — lines 137, 456, 490, 513, 592, 625, 685 (every behavioral test that calls `ifFires`). Each constructs `{ cwd: ... }` and casts it to the full `ExtensionContext` with `as`, which is the "broad cast hiding an invalid double" pattern the skill flags — the object plainly does not have `ExtensionContext`'s other fields, and `as` forces past that. Line 120 already shows the type-safe version (`{ cwd: compileContext.cwd } satisfies Pick<ExtensionContext, "cwd">`) but still needs `as ExtensionContext` at the call site (line 137) because `ifFires` demands the full type. This is a consequence of a production design gap — see the matching finding on `extensions/pi-claude-marketplace/bridges/hooks/if-field/index.ts` below. Once `ifFires`/`resolveTarget` are narrowed to accept only what they use, delete all 7 casts and construct plain `{ cwd: "..." }` literals (optionally `satisfies Pick<ExtensionContext, "cwd">`).
- **[WARNING] `assert.equal` used once where every other assertion in the file uses `assert.strictEqual`** — line 503 (`test('fails open when Bash command parsing exceeds the recursion limit')`): `assert.equal(fires, true);`. Functionally identical under the `node:assert/strict` import used here, but inconsistent with the rest of the file. Change to `assert.strictEqual(fires, true)`.

### `extensions/pi-claude-marketplace/bridges/hooks/if-field/index.ts`

- **[WARNING] File header claims its own already-implemented functions are future work** — lines 1–8: "Dispatch-time consult (`ifFires`) and parse-time compile (`compileIfPredicate`) land in follow-up plans against this surface." Both functions are fully implemented later in this same file (`compileIfPredicate` at line 230, `ifFires` at line 395). A new reader of this header would wrongly conclude the file is a pure re-export barrel. Rewrite to describe what the file does now (exports `IfPredicate`, `MATCH_ALL_IF`, `compileIfPredicate`, `ifFires`, and re-exports the glob/Bash compile-time primitives).
- **[WARNING] `ifFires`/`resolveTarget` take the full `ExtensionContext` but read only `.cwd`** — `ifFires` signature at lines 395–400, `resolveTarget` at lines 357–363. Neither function touches any `ExtensionContext` field other than `cwd` (confirmed by reading both bodies in full). This is the "hidden dependency on a wider live boundary than the code actually needs" testability finding: every caller — production and test alike — must supply or fake a complete `ExtensionContext`. Contrast with `compileIfPredicate`, which already does this correctly via the narrow, consumer-declared `CompileIfPredicateContext` interface. Apply the same fix here: change both signatures to accept `Pick<ExtensionContext, "cwd">` (or reuse/extend a small named interface), so callers — including every test in `index.test.ts` — can pass a plain `{ cwd: string }` literal with no cast. This removes all 7 `as ExtensionContext` casts flagged in `index.test.ts` above.
- **[WARNING] `toolName as PiToolName` cast has no inline justification** — line 428: `if (!predicate.piEvents.has(toolName as PiToolName)) {`. `toolName` comes from `extractToolName(event)`, which returns a plain `string` (including `""` for malformed events) — casting it to the branded `PiToolName` union is safe only because `Set.has()` performs a structural equality check at runtime regardless of the claimed static type, but that reasoning is not stated anywhere near the cast. Add a one-line comment explaining why the cast cannot fail unsafely (e.g. "`.has()` is a plain runtime equality check; an arbitrary string simply misses the set, so the cast cannot smuggle in a false membership").
- **[WARNING] `try`/`catch` around callees documented as "never throws" is defense-in-depth that cannot be exercised without global mutation** — lines 278–287 (`compileBashGlob` call) and 290–301 (`compilePathGlob` call) in `compileIfPrefixForm`. `glob.ts` (lines 25–31) states both callees are "pure-and-total... MUST never throw." Given that contract holds under normal typed usage (confirmed by reading both implementations — no path in either function can throw with well-typed inputs), these `catch` blocks are reachable in the test suite only via the global-prototype monkey-patches flagged in `index.test.ts` above. Either document explicitly why the `try`/`catch` is kept despite the "never throws" contract (defense against a future regression in `glob.ts`), or drop it if the contract is meant to be relied upon; as written, the only way to cover it is the hermeticity-breaking test technique flagged above.
