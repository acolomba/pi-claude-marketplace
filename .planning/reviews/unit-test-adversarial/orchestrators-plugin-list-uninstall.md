# Orchestrators — plugin list and uninstall

**Scope:** `tests/orchestrators/plugin/list.test.ts`, `tests/orchestrators/plugin/uninstall.test.ts`, paired against `extensions/pi-claude-marketplace/orchestrators/plugin/list.ts` and `.../uninstall.ts`
**Test files reviewed:** 2 (4415 lines, 4402 lines)
**Production modules reviewed:** 2 (1576 lines, 774 lines)

## Summary

The two suites are not at the same level of rigor. `uninstall.test.ts` is excellent: every outcome is a whole-object `assert.deepStrictEqual`, errors are asserted by `instanceof` plus structured fields, and an entire NFR-3 "retry proof" matrix walks every cascade/cleanup failure point (hooks, config-write, state-write, cache-unlink, data-rm, clone-rm) with full on-disk tree snapshots and state re-reads — this is genuinely strong coverage of the unstage/cleanup paths, not "doesn't throw" theater. `list.test.ts` is structurally sound (good `withHermeticHome` hygiene, `strong-mock` used correctly with `verify()`) but roughly half of its ~89 cases assert the rendered row with `assert.match`/`.includes()`/`assert.doesNotMatch()` fragments instead of the whole message, which is exactly the substring-assertion failure mode the row-grammar contract is supposed to guard against. A handful of cases also compute their expected value by calling the same production classifier the code under test calls internally, which is a tautological assertion. On the production side, `uninstall.ts` is a single well-scoped ledger; `list.ts` at 1576 lines mixes at least three distinct concerns (installed-row derivation, not-installed/candidate-row derivation, cross-scope orphan-fold) that already have sibling extraction precedent (`list.messaging.ts`, `plugin-state-classifier.ts`, `git-source-probe.ts`) and would benefit from the same treatment. Neither test file actually gates NFR-5 (no git/network surface) at the source level — that gate lives entirely in the out-of-scope `tests/architecture/no-orchestrator-network.test.ts`.

## Unit test findings

### `tests/orchestrators/plugin/list.test.ts`

- **[BLOCKER] Row/list assertions use substrings and regexes instead of the whole rendered value** — representative: `line 407` (`assert.match(out, /● alpha .../)` + `assert.equal(out.includes(...), false)`), `line 442`, `line 478`, `lines 972-1006` (RSTA-07 `--remote`/`--available` partition), `lines 1143-1148`, `lines 1197-1235` (LIST-01 filter-partition suite), `lines 1497-1500`, `lines 1574-1579`, `lines 1618-1621`, `lines 1879-1880`, `lines 2159-2162`, `lines 2198-2199`, `lines 2990-3007` (PL-4 description placement, `assert.ok(out.includes(...))` x5), `lines 3103-3113`, `lines 3155-3156`, `lines 3221-3222`, `lines 3356-3357`. Roughly 130+ occurrences of `assert.match`/`assert.doesNotMatch`/`.includes()` across the file, versus ~54 places that do it correctly with a hand-built, `"\n"`-joined array compared via `assert.equal`/`assert.deepStrictEqual`. A regex like `/● alpha v1\.0\.0 \(installed\)/` only proves the substring exists *somewhere* in the output — it does not prove there are no extra rows, that ordering matches the promised marketplace-then-plugin sort, or that nothing else in the block is wrong. A plausible wrong implementation (duplicate row, wrong sort position, stray marketplace block, extra blank line) still passes every one of these. Convert every one of these cases to build the full expected string as a literal array joined with `"\n"` (the pattern already used correctly at, e.g., lines 362-370, 3386-3390, 4243-4247) and assert it with a single `assert.equal`/`assert.deepStrictEqual` against `notifications[0]!.message` (or the full `notifications` array). The PL-4 test at lines 2944-3013 is the worst offender: it makes 5 separate `assert.ok(out.includes(...))` calls to pin three rows and two description lines but never asserts the full byte sequence, so a reordering or misplaced description line would not be caught.
- **[BLOCKER] Expected value computed by calling the production classifier under test** — `line 2419` (`assert.match(out, new RegExp('\\{' + narrowUnsupportedKinds(["lspServers"]).join(", ") + '\\}'))`), `lines 2566-2569` (same pattern with `["lspServers", "monitors"]`). `narrowUnsupportedKinds` is imported from `shared/probe-classifiers.ts`, the exact function `list.ts`'s `installedRowMessage` → `partiallyInstalledReasons` calls internally to produce the reason tokens. Computing the expected regex with the same function makes the assertion tautological: if `narrowUnsupportedKinds` regresses, both sides of the comparison move together and the test stays green. Replace both call sites with the hand-written literal token list (e.g. `"{lsp, unsupported source}"`), matching the style already used everywhere else in this file (e.g. line 2569's sibling assertions).
- **[WARNING] Header comment claims an in-file network source-grep that does not exist** — `lines 16-17`. The file header says "Plus the redundant in-test source grep for NFR-5 / PI-2 / PL-3 defense-in-depth (mirror of `tests/architecture/no-orchestrator-network`)", but the only NFR-5-adjacent check in this file is the compile-time `@ts-expect-error` at lines 60-63, which only proves `ListPluginsOptions` has no `gitOps` field — it does not grep `list.ts`'s own imports. **This means `list.test.ts` would NOT catch a regression that added `import { DEFAULT_GIT_OPS } from "../../platform/git.ts"` (or any `gitOps` reference) into `list.ts` and used it internally.** The only thing that gates that is `tests/architecture/no-orchestrator-network.test.ts`, which is outside this review's scope but is the sole real backstop. Either add the grep this comment promises, or fix the comment to stop claiming coverage this file does not have.
- **[WARNING] `DISABLED_BARE_ROW` module-level constant shared across two test cases** — `line 1771`, used at `lines 1843-1844`. It is immutable literal data (not mutable state), so it is not a hermeticity risk, but per the guideline that cross-case data belongs in a seed function returning a fresh value rather than a shared module constant, inline the literal into each of the two call sites (they are the only two, so the abstraction buys little) or turn it into a small function.
- **[WARNING] `outcome.status === "..."` narrow-then-property-check pattern instead of one whole-value comparison** — not present in this file's main body but mirrored in the sibling suite; see uninstall.test.ts finding below. In `list.test.ts` itself the equivalent multi-assertion pattern shows up in the RSTA-07/RSTA-05 blocks (e.g. `lines 967-1007`) where three separate scoped blocks each re-derive `ctx`/`pi`/`notifications` and assert fragments; consider a single whole-value assertion per block once the substring fix above lands.

### `tests/orchestrators/plugin/uninstall.test.ts`

- **[BLOCKER] Hand-rolled `ctx`/`pi` doubles cast with `as`, instead of `strong-mock`** — `lines 77-94` (`makeCtx`), used by every one of the ~56 test cases in the file. `ctx` and `pi` are built as plain object literals (`{ ui: { notify: (m, s) => { notifications.push(...) } } } as ExtensionContext`) rather than `mock<ExtensionContext>({ exactParams: true, ... })` from `strong-mock`. This is precisely the "hand-rolled mock object" anti-pattern the project's own convention forbids (`strong-mock` is the sanctioned interaction-mock library — see `tests/orchestrators/plugin/list.test.ts`'s `makeCtx`, lines 75-98, which does this correctly with `mock()`/`when()`/`verify()` for the identical `ExtensionContext`/`ExtensionAPI` pair). Consequences: (1) the `as ExtensionContext`/`as ExtensionAPI` casts suppress structural checking, so the double can silently drift from the real interface; (2) there is no `verify()` anywhere in the file, so nothing asserts that `ctx.ui` or `pi.getAllTools()` were invoked the expected number of times or with the expected shape — only the *content* pushed into `notifications` is checked, never the interaction contract itself. Port `makeCtx` in this file to the same `mock<ExtensionContext>`/`mock<ExtensionAPI>`/`mock<NotificationUi>` + `when()`/`verify()` shape `list.test.ts` already uses, and add `verify(ctx); verify(pi); verify(ui);` to every case (or centralize it in a shared helper both files import, since `makeCtx` is currently duplicated with materially different quality between the two sibling suites).
- **[WARNING] Prefix/regex-fragment assertions where a whole-value comparison would be stronger** — `lines 520-530` (PU-3 + PU-7: `.startsWith(...)` for the row prefix, then a separate `assert.match(..., /Failed to remove .* agent/i)` for the middle, then a third `.includes()` check for the trailer absence — three partial checks standing in for one whole-string comparison), similarly at `lines 581-585` (PU-5) and `lines 1131-1136` (TR-03 non-AG-5). This is the same failure mode as the list.test.ts BLOCKER above, but it is the exception rather than the rule in this file — the majority of cases (the entire NFR-3 retry-proof matrix, `WB-01`/`CFG-03`/`RECON-03` blocks, etc.) already use a single `assert.deepStrictEqual(notifications, [...])` against the full message. Tighten the ~3-4 remaining prefix/regex cases to the same whole-value form; the exact `AgentsUnstageFailureError` message text is already known at each of these call sites (it is asserted verbatim elsewhere, e.g. `line 3125`), so there is no reason these three cases can't do the same.
- **[WARNING] Property-by-property outcome checks instead of one `assert.deepStrictEqual`** — `lines 1490-1495` (`assert.equal(outcome.status, "uninstalled"); if (outcome.status === "uninstalled") { assert.equal(outcome.name, ...); assert.equal(outcome.version, ...); }`), `lines 1543-1551`, `lines 1752-1757`. Each of these narrows the discriminated union with an `if` and then asserts fields one at a time, when a single `assert.deepStrictEqual(outcome, { status: "uninstalled", name: "hello", version: "0.0.1" })` (the pattern already used at, e.g., `lines 1456-1461`, `2055-2060`, `2990-2999`) says the same thing more strongly and more concisely — a stray extra field on the outcome object would not be caught by the property-by-property form.
- **[WARNING] Misleading test title: "the exported fallback error"** — `test('cascade failure without a cause uses the exported fallback error', ...)`, `line 1343`. The fallback error message (`Cascade unstage failed for plugin "${plugin}".`) is constructed inline inside the private `foldPartialCascadeFailure` helper (`uninstall.ts:325`) and is not exported from anywhere. Retitle to something like `"cascade failure without a cause falls back to a synthesized error"`.
- **[WARNING] Real subprocess + polling + wall-clock timeouts to force a filesystem race** — `lines 1558-1734` (`WR-06 uninstall orchestrated mode -- marketplace removed after resolution converges without mutation`). This case spawns a real child Node process (`spawn(process.execPath, ["--input-type=module", "--eval", monitorSource], ...)`) that watches the state directory and polls every 1ms (`setInterval(..., 1)`) for up to 5-6 seconds (`setTimeout(..., 5_000)` / `6_000`) to win a race against the guard's atomic rename. This is a legitimate way to prove a real concurrent-removal race is handled, but it is exactly the "real sleeps/polling" and subprocess-based hermeticity pattern the review guidelines flag for a unit suite — it is slow, timing-dependent, and the only test in either file that behaves this way. Consider whether this belongs in `tests/integration/` instead (the project already has a dedicated integration tier for this class of scenario), or whether the same guarantee can be proven by injecting a fake at the `withLockedStateTransaction` seam instead of racing real OS process scheduling.
- **[WARNING] No test-file-level NFR-5 gate, matching production's self-declared exemption** — no lines to cite (the file contains zero references to `gitOps`/`platform/git`/`DEFAULT_GIT_OPS`/`no-orchestrator-network`). `uninstall.ts`'s own header (lines 28-30) says it is "implicitly clean by construction" and explicitly "not gated here." That is accurate: nothing in this test file, and no architecture test in scope for this review, would catch a regression that added a git/network import to `uninstall.ts`. This is a real, acknowledged gap rather than a hidden one, so it is recorded here for completeness rather than as a surprise.

### Clean files

- None — both files have findings, but the bulk of `uninstall.test.ts`'s ~56 cases (the entire NFR-3 retry-proof matrix, the LIFE-04 per-bridge-kind suite, the RECON-03 orchestrated-mode suite, and the WB-01/CFG-03 write-back suite) are exemplary: whole-object `assert.deepStrictEqual` on outcomes, `instanceof` + structured-field error assertions (`SymlinkRefusedError.parent/child/linkPath/linkTarget`, `AgentsUnstageFailureError`, `MarketplaceNotFoundError`), full on-disk tree snapshots (`retryTree`) proving both what was removed and what was left alone, and per-resource-kind isolation (D-98-12) so a regression in one bridge's unstage path names itself.

- **[WARNING] `catch {}` returning `undefined` without a comment at the call site's degrade meaning** — `lines 393-397` (`probeUpgradeCandidate`'s `try { return await resolveStrict(...); } catch { return undefined; }`). The surrounding JSDoc block (lines 358-382) does explain the degrade rationale at length, so this is not an *undocumented* empty catch in the sense the style guide flags — the reasoning lives a few lines above the function rather than inside the catch block itself. ### `extensions/pi-claude-marketplace/orchestrators/plugin/uninstall.ts`

- **[WARNING] `err as Error` cast relies on an invariant from another module, undocumented at the cast site** — `line 676` (`const cause = err as Error;` inside `uninstallPlugin`'s outer `catch`). This cast is only safe because `withLockedStateTransaction` (`transaction/with-state-guard.ts:169`, `toError`) normalizes every thrown value to a real `Error` before it can propagate out of the guarded closure — confirmed by tracing `with-state-guard.ts`'s `toError(err)` helper, which every exit path routes through. That invariant is not obvious from `uninstall.ts` alone and is not stated at the cast site. `list.ts`'s equivalent top-level catch (`line 1538`) uses the safer, self-contained form `err instanceof Error ? err : new Error(errorMessage(err))` instead of asserting. Either add a one-line comment at `line 676` naming the invariant it depends on (`withLockedStateTransaction always throws Error instances via toError()`), or switch to the same defensive form `list.ts` uses so the safety does not depend on tracing a different file.

## Answers to the specific checks

**(1) NFR-5 regression coverage.** Neither test file would catch a regression that introduced a network call. `list.test.ts`'s only NFR-5-adjacent check (lines 60-63) is a compile-time `@ts-expect-error` proving `ListPluginsOptions` has no `gitOps` field — it does not inspect `list.ts`'s actual imports, despite the file's header (lines 16-17) claiming an in-file source grep exists. `uninstall.test.ts` has zero NFR-5-related assertions at all, consistent with `uninstall.ts`'s own header comment (lines 28-30) admitting it is "implicitly clean by construction" and "not gated here." The only real backstop for both is `tests/architecture/no-orchestrator-network.test.ts`, which is out of scope for this review and gates `list.ts` but, by the architecture doc's own account, only implicitly covers `uninstall.ts`.

**(2) Output row grammar / whole-value assertions.** `uninstall.test.ts` does this well (whole-message `assert.deepStrictEqual`/`assert.equal` is the dominant pattern, with only ~3-4 exceptions). `list.test.ts` does not: roughly half of its 89 cases assert row content via `assert.match`/`assert.doesNotMatch`/`.includes()` fragments rather than the full rendered string in the promised order. See the BLOCKER finding above. No case in either file was found building its expected string by calling the production renderer itself, except the two `narrowUnsupportedKinds(...)` call sites in `list.test.ts` (lines 2419, 2566-2569), which call a production *classifier* (not the renderer) to build part of the expected value — still a violation of the "build expected values independently" rule.

**(3) `uninstall.ts` unstage-path coverage.** This is the strongest part of either suite. Every bridge's removal (skills, commands/prompts, agents + agents-index, hooks, mcp.json, plus the git-clone-cache GC) has at least one dedicated case verifying both the on-disk artifact is gone *and* the state record reflects it, and the NFR-3 retry-proof matrix (lines 2710-4401) additionally verifies partial-failure shrink-and-retry behavior per resource kind with full directory-tree snapshots. No case was found that asserts only "did not throw" without also checking on-disk/state cleanup. The one soft gap: the PU-1 test's comment (line 279) claims "all four on-disk resources removed" but only asserts three (skill, command, agent — hooks and mcp are not checked in that specific case); this is not a real coverage gap since hooks and mcp removal are each independently verified later (LIFE-04 cases at lines 2604-2628 and 2630-2668), but the comment overstates what that one test itself proves.

**(4) Whole-value outcome/error assertions.** Both files do this well overall. `uninstall.test.ts`'s `UninstallPluginOutcome` assertions are almost all single `assert.deepStrictEqual` calls, and errors are asserted by `instanceof` plus every structured field (see `SymlinkRefusedError` at lines 4239-4245). The exceptions are the narrow-then-check-each-field pattern noted as a WARNING above.

**(5) Test-only exports.** None found. See the "Clean files" note under Production code findings.

**(6) Should either source be split?** `list.ts` (1576 lines): yes — split along the three responsibilities named in the production WARNING above (installed-row derivation, candidate/not-installed-row derivation, cross-scope orphan-fold), leaving `list.ts` itself as a thin entrypoint holding `listPlugins`, `loadPluginListPayload`, the filter predicate, and the final sort. This mirrors the extraction already done for `list.messaging.ts`, `plugin-state-classifier.ts`, and `git-source-probe.ts`, and would let `list.test.ts` be split to match (its size is a direct symptom of one file covering three loosely-related derivation surfaces plus the fold rule). `uninstall.ts` (774 lines): no — it is a single cohesive ledger for one verb, consistent with the architecture's one-file-per-verb convention, and its test file's size (4402 lines) is explained by a genuinely non-redundant NFR-3 retry-proof matrix (one case per resource kind × one case per failure-injection point) rather than by the production file mixing unrelated concerns.
