<the_governing_risk>
Read this before the first task. It is the reason the plan is shaped the way it is.

**An engine change can clear rows by becoming sloppy, and this is the plan most able to cause it.** Every earlier plan in this phase risked deleting live code. This one risks manufacturing observations -- and a manufactured observation is worse than a deleted field, because the field comes back in one revert while a permissive prover silently absolves every future member of the same shape.

06-03 wrote the rule this plan is governed by: *an exemption category earns its keep by naming what it refuses, so every new proof ships with the counterexample that fails it.* A proof that accepts its target and refuses nothing has not earned its keep and must not be written.

Six obligations follow. They are task requirements, not advice, and each task's `done` restates the ones that bind it.

**1. Every new or widened proof ships with the counterexample that fails it.** For each of the five changes, the neighbouring shape that must still be refused is named in the task. Write the refusal control in the same commit as the change. A change whose refusal control passes before the change was written has not measured anything -- re-derive the counterexample until it discriminates.

**2. The delta must be EXACTLY the predicted rows.** After each engine change, take `node scripts/check-unused-type-members.mjs --json`, diff it against the snapshot taken immediately before the change by `(path, owner, key)` set difference, and require that the rows which left `unread` are precisely the ones the change was predicted to clear -- named below, by coordinate. A change that also clears an unrelated row has become permissive: narrow it or revert it. Do not celebrate it, and do not rationalise it after the fact.

**3. Zero rows may gain a witness without a named witness site.** A member moving `unread` to `runtime-observed` or `test-only-observed` must carry a concrete witness coordinate in the report. Open at least one witness per newly credited member and read the source at that coordinate. If a member gains a witness list that is empty, or a witness whose coordinate does not hold what the report claims, that is a permissiveness finding and the change is reverted.

**4. 06-07's negative controls must still pass, and must still REJECT an always-passing gate.** The runner scripts six defective gates the harness must refuse, including an always-clean mutant rejected on report *content* rather than exit status. A permissive engine change could make a genuine defect indistinguishable from a clean tree, and these controls are the guard against exactly that. The run costs roughly seven minutes at about 2.1 GiB, so run it once, at the end, on the final snapshot -- and treat any change in which control fires as a finding rather than noise.

**5. The 90 validated contracts must all still validate, and the refusals must still refuse.** The contracts suite is 48 controls and the live contract file holds 90 accepted entries. Both are the regression surface. Beyond them, this plan carries a specific obligation the earlier plans created: 06-06 refused 7 drafts, 06-11 refused 7, 06-12 refused 3 and 06-13 refused 2. Each task names which of those its change is expected to leave refused, and re-submits them. A widened proof that now accepts a previously refused draft is a finding to investigate and record before anything is written -- it may be the correct answer, but it is never the assumed one.

**6. Performance is a real constraint and has been blown twice in this phase.** 06-02 aborted at 4 GB and 06-04 exhausted 4M and then 40M transfer steps in three and a half minutes before provenance was narrowed to the operand. The live analysis today runs about 80 seconds at about 2.05 GiB peak RSS and 3,002,713 transfer steps against an adopted cap of 12,000,000. **This plan's budget: wall time at most 100 seconds, peak resident size at most 2.40 GiB, transfer steps at most 6,000,000.** Measure with `/usr/bin/time -v` on the real tree after every engine change and record the three numbers per task. Exceeding the budget means narrowing the traversal or reverting the change. It never means raising the adopted cap: a cut-off run must stay a refusal rather than a partial answer, and both budget-exhaustion controls must keep failing rather than reporting clean.

<standing_obligations>
These apply to every task and are part of each task's `done`.

**One definition, never a copy.** 06-03 imported `resolveCandidates` from the model module rather than re-deriving member identity, and that single-definition rule holds here. Where a correction ports a helper another module already owns, export it from its current home or move it to the shared leaf -- do not paste a second copy. If the helper moves, every existing control that exercises it stays in place and stays green; a relocation that quietly drops an ordering, call-count or fault-injection assertion is a regression even when the suite is green.

**The three-way exit contract is load-bearing.** Exit 1 is a member verdict. Exit 2 is a setup failure -- a stale, contradictory or unprovable contract entry, or an exhausted budget -- and is never a quiet allowance. After every change require the analyzer to exit 1 with member findings. Exit 2 means a coordinate is wrong or a proof refused, and it is a blocking failure to be read and fixed, never worked around.

**Contract coordinates are pinned and fragile.** Each entry identifies itself by exact `path:line:column` for both `id` and its evidence site (`filter`, `refines`, `origin`, `boundary`, `upstream`, `necessity`). T2 is the only task that edits `extensions/`, and both files it edits hold contract entries; re-derive every coordinate in those files from the edited source, never by arithmetic on the old value. 06-12 hit this twice for real and both times the drift control caught it.

**No product source is reshaped to satisfy a refused proof.** T2 re-applies two restatements 06-12 built, probed and then reverted, and it re-applies them only because the engine correction lands first and makes the proof available. That is the one permitted `extensions/` edit in this plan. No other task may touch `extensions/`, and no task may convert a method to an arrow property, restructure a handler to give a prover an exact contextual type, widen a declared type to manufacture a read, or add a test whose only effect is to make a declaration look used (D-02).

**Every contract entry is submitted to the real engine before it is written.** Draft one entry at a time, derive every coordinate from the compiler's own view of the syntax, run the analyzer, and keep the entry only if the engine accepted it. Record every refusal with the engine's verbatim message. Never write an entry the engine refused.

**Comments cite durable IDs only.** Any comment this plan writes cites requirement and decision IDs. Planning identifiers -- phase, plan, wave, pitfall or pattern numbers -- are forbidden in source per `CLAUDE.md` and `.claude/rules/typescript-comments.md`. The analyzer modules carry their design rationale in file and function headers; when a correction changes what a header claims, rewrite the header rather than leaving it stale.

**Commit discipline.** One commit per task, Conventional Commits, no milestone or phase identifiers in subject or body. **Test-run hygiene.** Run suites under a hermetic `HOME`. A shared `PI_CODING_AGENT_DIR` is not a valid substitute -- it collapses every suite's user scope into one directory and manufactures a failure that looks exactly like a regression. 06-12 recorded this after it cost real time.
