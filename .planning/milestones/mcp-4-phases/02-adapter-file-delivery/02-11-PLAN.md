<objective>
Close verification gap 1, notice half: install warns once, naming the override fields that stop applying while the plugin owns the name (D-02-21), and the warning stays truthful when the same command writes the override back.

Purpose: plan 02-10 keeps the user's override in the entry's marker and makes only its carried fields active. Every other field silently stops applying until the plugin lets go of the name. D-02-21 asks for one warning that names those fields, as a closed-catalog amendment with passing catalog gates. Plans 02-04 to 02-08 already route `McpConfigNotice` facts from every stage and unstage to the user, standalone and orchestrated, so the new notice is one more kind on that carrier, and no orchestrator changes. Two flows absorb an override and then put it back in the same command: an install that lands disabled, and a dependency cascade that fails after an earlier member installed. An unstage therefore also reports each write-back as a fact the seam uses to drop the matching warning.

Output: the `McpConfigNotice` union (file, override-kept, override-restored), the fold and the line in `notifyMcpConfigNotices`, `inactiveOverrideFields`, `restoredOverrideNames`, the stage and unstage producers, the `mcp-override-kept` catalog block and its byte lock, owner and orchestrator tests, and one commit.
</objective>
