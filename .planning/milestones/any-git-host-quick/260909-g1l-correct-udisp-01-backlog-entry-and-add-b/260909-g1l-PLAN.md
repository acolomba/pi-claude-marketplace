## A. The three UDISP-01 corrections

### A1 -- the `rm()` citation is stale

The entry cites `orchestrators/plugin/uninstall.ts:635` for the unconditional
`rm(dataDir, { recursive: true, force: true })`. The code moved. It is at line
**429**. The stale number appears twice: once in the **Our behavior today**
paragraph, once in the **Code seams** trailer as `call, line 635`.

### A2 -- the cross-scope machinery is wrong and must be dropped

The entry prescribes reusing `otherScope()` + `locationsFor()` + `loadState()`
to run a "last remaining scope" check before deleting the data directory. That
solves upstream's problem, not ours.

Upstream's data directory is **global** -- one `~/.claude/plugins/data/{id}/`
backs every scope -- so upstream has to ask whether another scope still needs
it before deleting. Ours is already **partitioned per scope**: `dataRoot` is
`<scopeRoot>/pi-claude-marketplace/data` (`persistence/locations.ts:165`). A
user-scope uninstall therefore cannot reach project-scope data. The cross-scope
data-loss scenario the entry describes **cannot happen** in our layout.

Two consequences, and the entry must carry both:

1. The prescription is removed, and the reason is recorded in the entry so
   nobody re-adds it from the same upstream doc sentence.
2. The item is **cheaper** than it was filed. The whole fix is the flag.

The same wrong premise also appears as a stated fact, at the end of the **Our
behavior today** paragraph: "The contents of `${CLAUDE_PLUGIN_DATA}` are lost
on uninstall even when the plugin remains installed in the other scope." That
sentence is false under our layout and goes with the prescription.

The **Two call sites** paragraph says both paths "need the same scope-aware
rule". There is no scope-aware rule any more. The paragraph keeps its real
point -- two call sites, one shared behavior -- and drops the scope-awareness.

### A3 -- the "silent" claim is half true, and the resolution is now locked

The entry says upstream deletion is "scope-aware and silent -- no confirmation
prompt for data specifically". That describes the **CLI only**. Upstream's
interactive `/plugin` interface shows the data directory size and prompts
before deleting. The CLI deletes by default with no prompt. Record both.

Then record the resolution, which is **decided and locked**: we ship the
**silent delete with `--keep-data` as the opt-out**, matching the CLI.

The rationale to record, because it is what makes the choice forced rather than
preferred: `orchestrators/reconcile/apply.ts`'s `applyPluginUninstalls()` fires
non-interactively from `resources_discover` / `session_start` when a plugin is
dropped from `claude-plugins.json`, and it has no command line to carry a flag.
A promptless default is the only behavior both call sites can share.
Prompt-with-size would give the same operation two different behaviors
depending on which entry point reached it.

### A4 -- the verified upstream signature to pin

Read off the installed Claude Code CLI **v2.1.236** on 2026-09-09:

`claude plugin uninstall|remove [options] <plugin>`

| Flag | Description |
|---|---|
| `--keep-data` | Preserve the plugin's persistent data directory (`~/.claude/plugins/data/{id}/`) |
| `--prune` | Also remove auto-installed dependencies that are no longer needed (requires `-y` in non-interactive contexts) |
| `-s, --scope <scope>` | `user`, `project`, or `local` |
| `-y, --yes` | Skip the `--prune` confirmation prompt (required when stdin or stdout is not a TTY) |

There is no `--delete-data`. Do not record one. `-y` gates the `--prune`
confirmation **specifically**; it has nothing to do with data deletion. Do not
conflate them.

**The mutex is already handled correctly -- do not delete it.** The
`--keep-data`/`--delete-data` mutex appears three times in the entry and all
three are right as written: the provenance paragraph names it as the
competitor's model the item was first framed against and then moved off; the
**Claude Code's actual behavior** paragraph states upstream has no
`--delete-data`; and **Direction for later** says inventing one would add a
flag Claude Code does not have. None of the three prescribes it. A4 is
**additive** -- pin the flag set to a probed CLI version, replacing a bare
`code.claude.com/docs/en/plugins-reference` citation with a version-anchored
reading.

## B. The new entry

### B0 -- the ID

Read the file's ID scheme before picking: every entry is a topical mnemonic
plus `-01`, and a second entry in a family takes `-02` (only `SRCP-01/02` does
this today). There is no existing family for manifest location. `PSRC-01` is
plugin **source**, `PDEP-01` is plugin **dependencies**; the free adjacent
mnemonic for plugin **manifest** is **`PMAN`**. Verified free: `grep -c 'PMAN'
.planning/BACKLOG.md` returns 0. Use **`PMAN-01`**. Do not invent a numbering
scheme and do not renumber anything.

### B1 -- the gap

Claude Code accepts BOTH `<pluginRoot>/.claude-plugin/plugin.json` and a bare
`<pluginRoot>/plugin.json`. We only ever build the wrapped path, at **two
independent hardcoded call sites**:

- `domain/resolver.ts:627` -- `readManifest()`
- `orchestrators/plugin/shared.ts:921` -- `resolvePluginVersion()` tier 1

On a stat miss `readManifest` returns `{ ok: true, manifest: null }`, so an
absent manifest is deliberately **non-fatal**. Bare-manifest plugins therefore
install fine. We silently ignore a manifest that is there.

### B2 -- who ships it

Four plugins in the official Anthropic marketplace ship the bare form today.
All four were fetched at the shas their `marketplace.json` entries pin.

| Plugin | Repository | Declared skills |
|---|---|---|
| `ui5` | `github.com/UI5/plugins-coding-agents` | `["./skills/"]` |
| `ui5-modernization` | `github.com/UI5/plugins-coding-agents` | `["./skills/"]` |
| `ui5-typescript-conversion` | `github.com/UI5/plugins-coding-agents` | `["./skills/"]` |
| `ui-theme-designer` | `github.com/SAP/ui-theme-designer-plugins-for-coding-agents` | `["./skills/ui-theme-designer-help", "./skills/ui-theme-designer-design-tokens"]` |

The three UI5 plugins ship theirs at `plugins/<name>/plugin.json`. None of the
four declares commands, agents, `mcpServers`, hooks, or any unsupported kind.

### B3 -- severity: no component is dropped today

This is the non-obvious part and the reason the entry is worth reading. Three
independent reasons:

1. `collectStrictComponentKind` (`domain/resolver.ts:1051`) probes
   `<pluginRoot>/skills` and adds it **additively and unconditionally**, so the
   convention path already yields the same set the declarations name. Verified
   against the git trees: `ui5` has 8 skill directories under `skills/`;
   `ui-theme-designer` has exactly the 2 it names.
2. The declared versions do not land either. All four are git-subdir sources
   with a pinned sha, and `deriveInstallVersion`
   (`orchestrators/plugin/install.ts:640`) makes a resolved sha **replace** the
   whole three-tier ladder, so `plugin.json`'s `version` is unreachable for
   them by design.
3. The manifest `description` is not consumed anywhere in `extensions/`.

So it is a parity gap with no in-the-wild victim in the official marketplace
today.

### B4 -- the regression trap in the fix

Resolver dedup is by **raw relative-path string** (`addComponentPath`,
`domain/resolver.ts:1001`), so `"./skills/"` and `"skills"` are distinct keys.
A naive fallback yields `componentPaths.skills = ["./skills/", "skills"]` and
enumerates one directory twice. The skills bridge dedups by generated name,
first wins, so nothing breaks -- but `ui5` would emit 8 spurious "ignoring
duplicate" warnings per install and `ui-theme-designer` 2. That is a net
**output regression** on exactly the plugins that motivate the fix.

### B5 -- the fix shape, decided

Ordered fallback -- `.claude-plugin/plugin.json` first, then bare
`plugin.json` -- applied at BOTH call sites, PLUS a normalized dedup key so
`"./skills/"` and `"skills"` collapse. Keep the miss non-fatal. A malformed
bare `plugin.json` must still route to the existing `malformed plugin.json:
...` reason rather than being silently skipped.

### B6 -- verified and needing no change

An entirely absent `plugin.json` is fine upstream too:
`learn-with-coursera` and `amd-skills` install, and their skills are discovered
by directory convention. Our `manifest: null` behavior already matches, so
absence handling is **explicitly not part of this item**. Record it as a scope
boundary so the next reader does not widen the item.
