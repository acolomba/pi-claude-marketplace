## Design (planner's discretion, recorded)

- **Parse result (UKIND-01).** The success arm of `HookConfigParseResult` gains a required
  `declaresModule: boolean`. It is true exactly when the parsed JSON is a plain object (not null,
  not an array) whose own `modules` property is an array with at least one element. The check does
  not validate the elements: this is detection only. The parser never resolves, reads, or imports
  the module path.
- **Modules-only wrapper (UKIND-01).** When `declaresModule` is true, the object is the plugin
  wrapper even without `hooks`. If the object has an own `hooks` key, the validator candidate is
  that value, so a non-object `hooks` still fails schema validation. Otherwise the candidate is an
  empty record. When `declaresModule` is false, the existing `isPluginWrapper` and bare-shape
  selection run unchanged, so every file without a non-empty `modules` array parses as it does
  today.
- **Hooks resolution fact (UKIND-01).** `HooksResolution` gains an optional
  `declaresHookModule?: boolean`. It is set to `true` only when a hooks file declares a module, and
  it is absent otherwise, like `orphanRewake`. So existing whole-value assertions stay valid. The
  fact adds no note, never makes the result dirty, and never changes `supported`, `unsupported`,
  `hooksConfigPath`, or `droppedHooks`. `PartialResolution` inherits it, and
  `materializableFields` does not copy it onto the resolved plugin.
- **Collection input.** `collectUnsupportedKinds(input, statKind)` takes
  `{ entry, manifest, pluginRoot, declaresHookModule }` (Task 1), and Task 3 adds
  `marketplaceName`. This mirrors the `(input, dependencies)` shape of `collectStrictComponentPaths`,
  `resolveStrictMcp`, and `resolveHooks`. `mod` reads only `declaresHookModule`. No field named
  `mod` on the entry or manifest is ever consulted. Declare the input type inline. Do not add an
  exported interface.
- **Closed-set order.** The final tuple is `lspServers`, `monitors`, `themes`, `outputStyles`,
  `channels`, `userConfig`, `settings`, `syntaxHighlighting`, `mod`, `binaries`. The new kinds are
  appended, so existing order assertions keep their meaning. Notes follow tuple order. The new
  kinds have no filesystem convention.
- **Experimental (UKIND-02).** The nested `experimental.<kind>` form counts for `themes`,
  `monitors`, `outputStyles`, and `syntaxHighlighting`. Use a small set constant in place of the
  two-kind condition, and keep the existing comment's point that current schemas nest these kinds
  while older manifests use top-level fields.
- **Referenced hooks files (UKIND-01, Task 2).** The `resolveHooks` input gains
  `entry: { readonly hooks?: unknown }` and `manifest: { readonly hooks?: unknown } | null`, typed
  like the `resolveStrictMcp` input. The probe runs only when the default file did not declare a
  module, including when the default file is absent:
  1. Collect raw paths from `entry.hooks`, then from `manifest.hooks`. A string contributes
     itself. An array contributes its string elements. Inline records, null, and other values
     contribute nothing, because an inline record is not a hooks file.
  2. Resolve each path with `resolveContainedComponentPath(pluginRoot, raw, "hooks reference")`,
     and skip every `ok: false` result.
  3. Skip the default file's absolute path and any path already probed.
  4. Probe the remaining paths one at a time through the same routine as the default file: stat,
     skip anything that is not a file, read, then `parseHooksConfig` with `skipIfMap: true`.
     Generalize the private `readHooksConfig` to take the file path. Do not write a second reader.
  5. Skip an `{ ok: false }` parse silently. These files carry no other resolver meaning, and a new
     structural failure would make plugins `unavailable` that install today.
  6. Let read and stat errors propagate unchanged, as they do for the default file.
  7. The first success with `declaresModule` sets the flag and stops the probe. The `await` carries
     `// eslint-disable-next-line no-await-in-loop -- the first module-declaring hooks file ends the probe`.
- **Binaries (UKIND-03, Task 3).** `binaries` counts when two things hold. The lowercased
  `marketplaceName` is in `OFFICIAL_MARKETPLACE_NAMES`, a module-private `ReadonlySet<string>`
  that is not exported, per the unit-testing skill. And the entry's or the manifest's `binaries`
  value is a plain object (not null, not an array) with at least one own key. Any other
  marketplace, or an empty or non-object value, adds nothing.
- **Plumbing (UKIND-03, Task 3).** `ResolveContext` gains a required
  `readonly marketplaceName: string`, so `npm run typecheck` proves that every caller supplies it.
  An optional field would let a caller fall back silently to "never official", and then list or
  info would disagree with install.
- **Docs scope.** Update `skills/claude-code-compat-research/SKILL.md`, two lines of
  `docs/prd/pi-claude-marketplace-prd.md`, and `CHANGELOG.md`. Leave the following unchanged, and
  name each in the SUMMARY with its reason:
  - `README.md`: line 164 gives examples, not a list.
  - `docs/output-catalog.md`: it lists no kinds, and it is a build input.
  - `docs/competitive-analysis/pi-plugins.md`: a dated comparison whose rows also state a
    competitor's behavior.
  - `docs/workflows-compatibility.md`: it mentions the schema only.
