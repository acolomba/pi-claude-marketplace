**Tracker assessment.** I checked each tracker transition against the loop:

- In `one-at-a-time` mode the peek holds one message, so `remainingFollowUps` takes only that follow-up's text. With two queued follow-ups, the second text stays recorded for the next turn end. That is correct.
- `readsQueued` uses `endsTheWork`, which is false for `error` and `aborted`. That is correct, because the loop then returns without reading a follow-up.
- `steerWaits` is not reset at `agent_end`. A stale `true` cannot change a decision: every compaction that reads it inside a run comes after a `turn_end`, which recomputes it, and the overflow retry comes after the errored turn's `turn_end`.
- I found no simpler rule that gives the same outcomes. A count of follow-up inputs would treat a waiting steer as a follow-up whenever a follow-up is also queued, because the peek shows only the steer, and then steer into a call that the steer takes. `hasPendingMessages()` cannot tell the two queues apart. So matching by text is the smallest rule that works.

The one defect is the `agent_end` reset of the follow-up texts (WR-01 below).

## Warnings

### WR-01: The tracker forgets the follow-ups that a failed run leaves queued, so the retried run holds the compaction context that it should steer

**File:** `extensions/pi-claude-marketplace/bridges/hooks/event-router.ts:723-726` (`runEnded` clears `followUps`), with the JSDoc at `:695-696` ("A follow-up input keeps its text until the run reads that follow-up or ends"); `test/bridges/hooks/event-router.test.ts:5096` (the row `forgets the follow-up inputs of an ended run ...` pins the outcome); `docs/hooks-compatibility.md:169` and `.planning/REQUIREMENTS.md:45` (HKRL-03), which list the cases that hold the context and omit this one.

**Issue:** The reset assumes that a run drains its follow-ups before `agent_end`. That holds only for a normal exit. When a model call ends in `error` or `aborted`, `runLoop` emits `turn_end` and `agent_end` and returns at once (`agent-loop.js:146-155`), and the follow-up queue keeps its items. Pi then retries:

- An overflow retry runs `_checkCompaction`, then `_omitRecoveryAttempt` and `_runAutoCompaction("overflow", true)`.
- A retryable error such as a 529 runs `_prepareRetry`, which also calls `_omitRecoveryAttempt`.

Both retries call `agent.continue()`. The failed reply is gone from the projection, so `continue()` goes to `runContinuation`, and the follow-up stays queued for the retried run. The extension `agent_end` fires before every retry (`_emitExtensionEvent`, `agent-session.js:962`), so by then `followUps` is `[]`. At the next tool-call turn end in the retried run, `pendingMessages` holds that follow-up, `remainingFollowUps([], [f])` returns `undefined`, and `steerWaits` becomes `true`. A threshold compaction there sends the context with `{ triggerTurn: false }`. But Pi's post-preparation poll would read a steer there, because the follow-up waits behind the tool-results call. This is the P2 case that iteration 3 fixed, and it comes back after any retry. The model then makes the tool-results call without its compaction context.

The docs tell the user that the rule is "a follow-up that you queued in the same run". To the user, a retried run is that same run, so the docs do not cover this case.

**Measured at unit level.** I copied `event-router.test.ts` to `/tmp/claude-0/-home-user-pi-claude-marketplace/ba73c1d1-11d2-59e0-b5d6-895ae262ca9f/scratchpad/probe4/probe.test.ts` with absolute imports. I added one delivery row: `follow_up_input`, `overflow_turn_end_with_queued_follow_up`, `agent_end`, `tool_turn_end_with_queued_follow_up`, then a threshold compaction, expecting `{ deliverAs: "steer" }`. The row fails with `triggerTurn: false`. The existing row at `:5096` describes the same sequence without the errored turn. In Pi, a follow-up can still be queued after `agent_end` without a new `input` only when the run failed, and that is exactly the case where steering is right.

**Fix:** Clear the texts at `agent_end` only when Pi has no queued user input left. `ctx.hasPendingMessages()` counts the session's queued steer and follow-up texts until their `message_start`:

```ts
readonly runEnded: (stillQueued: boolean) => void;
// ...
runEnded: (stillQueued) => {
  phase = "idle";
  if (!stillQueued) {
    followUps = [];
  }
},
// agent_end subscription:
return (event: AgentEndEvent, ctx: ExtensionContext) => {
  runPhase.runEnded(ctx.hasPendingMessages());
  cacheLastAssistant(event);
};
```

You could instead keep the texts when the last assistant message of `event.messages` ended in `error` or `aborted`. Then:

- Keep the `:5096` row with `hasPendingMessages()` returning `false`.
- Add the probe row above with a context whose `hasPendingMessages()` returns `true`. It expects `{ deliverAs: "steer" }`.
- Update the JSDoc at `:695` and the `same run` wording in the docs and HKRL-03.

If you keep the reset, list this case with the other one-call holds: "a follow-up still queued when Pi retries a failed model call".

## Info

### IN-01: The "between two turns" delivery rows set up the phase with a text reply, which in Pi ends the run

**File:** `test/bridges/hooks/event-router.test.ts:5104`, `:5112`, and `:5016`, and the hook-steer case at `:5184` onward. Each uses `RUN_EVENTS.turn_end` or `turn_end_with_hook_context`, which carry `TEXT_REPLY`.

**Issue:** After a turn with no tool call and nothing queued, Pi polls, finds no steer and no follow-up, and emits `agent_end`. No `prepareNextTurn` compaction runs between them, except after another extension's `turn_end` continue. So these rows pin outcomes for an event order that Pi does not produce in the case they name ("between two turns"). The row at `:5112` is the clearest. After a text reply, a follow-up that the run reads takes the next call, so steering there would add a call. Its expectation, `deliverAs: "steer"`, is right only for the tool-call turn it means to model. The rows still pass on the real paths, because the tracker treats both replies the same when nothing is queued. But a later change that tells them apart, for example by setting `phase` from `endsTheWork` alone, would keep these rows green while it breaks the real path.

**Fix:** Add `tool_turn_end: { type: "turn_end", message: TOOL_CALL_REPLY, context: { pendingMessages: [] } }`. Use it for the between-turns rows and for the hook-steer case. Keep `turn_end` only for the rows that end the run (`after the run ended`, `during a model call`).

### IN-02: The add-a-call residuals are worded loosely, and one window is not listed

**File:** `docs/hooks-compatibility.md:171`; `.planning/REQUIREMENTS.md:45` (HKRL-03); the comment at `event-router.ts:657-658`.

**Issue:**

1. "another extension steers the run (`deliverAs: "steer"`)" covers two Pi APIs. `pi.sendUserMessage(..., { deliverAs: "steer" })` goes through `prompt()` and fires `input` with `streamingBehavior: "steer"` (`agent-session.js:2012-2040`), so the bridge sees it and holds the context. Only a custom message (`pi.sendMessage(..., { deliverAs: "steer" })`) is hidden from the bridge.
2. A path not in the list can add a call. The bridge's STOP-07 handler records a steer `input` before Pi queues it, and other extensions' `input` handlers run in that gap (`runner.js:1213-1229`, then `_queueSteer`). If one of them awaits across the end of a tool-call turn, `turnEnded` resets `steerWaits` to `false`, because the steer is not in `pendingMessages` yet. Pi then queues the steer during the compaction, ahead of the steered context, and a call can be added. I found this by reading Pi's source and did not measure it. It needs an extension with a slow `input` handler that is loaded after this one.
3. The comment on `isHeldHookContext` says that each matched message is one "this bridge sends with `triggerTurn: false`". But `claude-hook-additional-context` is also the type of the steered SessionStart context, which waits in the steering queue. In Pi 1.5.1 the next poll always reads that message before any turn end, so this does not change an outcome. Still, the comment states a premise that the code does not check.

**Fix:**

- In the docs and HKRL-03, say "another extension's custom message sent with `deliverAs: "steer"`".
- Add "a steer that another extension's `input` handler is still holding when the turn ends" to the read-from-source cases.
- Reword the comment: "the bridge's tool and prompt context, which waits for the turn end; a steered SessionStart context of the same type is read by the next poll before any turn end."
