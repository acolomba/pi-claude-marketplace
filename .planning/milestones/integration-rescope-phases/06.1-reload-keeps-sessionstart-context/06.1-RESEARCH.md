## Summary

Today the SessionStart adapter stores each folded `additionalContext` in an in-memory buffer of the hooks runtime, and the `before_agent_start` handler drains it into one hidden message after the prompt. A Pi `/reload` keeps the same `AgentSession` but builds a new extension runtime, so the extension factory runs again (`index.ts:116` makes a new `createHooksRuntime()`), and `registerHooksBridgeWith` also empties the buffers (`event-router.ts:1396`). The startup context is lost.

Design A (the CONTEXT default) has no capability gap. At SessionStart the adapter calls `pi.sendMessage({ customType, content, display: false }, { triggerTurn: false })`. While Pi is idle, Pi writes this as a `custom_message` entry in the session and rebuilds the agent's messages from the session. The entry is then part of the conversation, which `/reload` does not touch. A new, resumed, or forked session is a new `AgentSession` with its own session manager, so nothing leaks. Measured in a scratch worktree: the flipped reload scenario passes with design A and fails on the current code at its `Then`. Across all hook features plus `plugin/subagent-child` and `plugin/session-start-hooks` (322 scenarios), only the 5 scenarios that pin the old order or shape change. All new/resume/fork/compaction/session-end scenarios stay green.

Design A changes what the model sees in one way: the SessionStart part now comes **before** the first prompt, as its own message. The UserPromptSubmit and UserPromptExpansion parts stay in one message after the prompt. This is closer to upstream than today. Upstream puts SessionStart context "at the start of the conversation, before the first prompt" and splices the startup rows into the transcript (06.1-UPSTREAM-EVIDENCE.md). The current doc row already says "a hidden message before the first prompt of the session". Design B (persist and restore across reload) is not needed. A third option, `deliverAs: "nextTurn"`, also survives reload, but it puts the context after the prompt (measured), so it keeps the old order and diverges from upstream.

**Primary recommendation:** Use design A. The SessionStart adapter sends the context at once through `pi.sendMessage(..., { triggerTurn: false })`, wrapped in try/catch with `hookDebugLog`. Then remove the SessionStart pending buffer and the SessionStart part of `startRun`. Flip the 5 scenarios. Delete `test/integration/hooks-additionalcontext-end-to-end.test.ts`. Update the docs. One plan.

## Architecture Patterns

### Recommended code shape (scratch-measured core; final names at the executor's discretion)

```typescript
// event-adapters.ts, SessionStart arm of adaptObservationResultForEvent
// Source: measured scratch patch (designA-full.diff), with try/catch from sendQueuedPromptContext
if (claudeEvent === "SessionStart" && result.additionalContext !== undefined && result.additionalContext !== "") {
  sendSessionStartContext(context.pi, result.additionalContext);
}

function sendSessionStartContext(pi: ExtensionAPI | undefined, text: string): void {
  const part = hookContextPart("SessionStart", [text]);
  if (pi === undefined || part === undefined) {
    return;
  }

  try {
    pi.sendMessage(
      { customType: HOOK_CONTEXT_MESSAGE_TYPE, content: [part], display: false },
      { triggerTurn: false },
    );
  } catch (error: unknown) {
    hookDebugLog(`adaptObservation: session start context failed: ${errorMessage(error)}`);
  }
}
```

### Anti-Patterns
- Calling `pi.sendMessage` without try/catch. The unit test double in `dispatch.test.ts:4681` has no `sendMessage`, and the call threw in the scratch run.
- Passing `triggerTurn: true` or leaving it out while streaming. A compaction SessionStart during a run would then steer. Use `{ triggerTurn: false }` explicitly.
- `deliverAs: "nextTurn"`: it survives reload but puts the context after the prompt (B2).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Keeping context across `/reload` | globalThis buffer, session_shutdown persist plus session_start restore | a session entry through `pi.sendMessage` while idle | Pi's session survives reload; new/resume/fork isolation comes for free |
| Placing a message mid-run | your own queue | Pi's `_pendingCustomMessages` behind `triggerTurn: false` | Pi flushes at the safe points (turn end, run start, run end) |

## Common Pitfalls

### Pitfall 1: A send that throws inside a Pi event
**What goes wrong:** `pi.sendMessage` throws (a stale ctx after replacement, or a test double), and the SessionStart handler logs `session_start skipped` and drops later work.
**How to avoid:** use try/catch with `hookDebugLog` inside the helper, and add a unit case for it.

### Pitfall 2: The line number shifts in the verify command
The `:183` table grows a row, so the reload scenario moves from `:230` to `:231` (measured). Derive the line from the edited file.

### Pitfall 3: Leftover doc and comment claims
`docs/hooks-compatibility.md:449`: "one message carries the parts in that order ... Each bridge load, `/reload` included, empties the context that waits for the next prompt" is wrong after the fix. `:442` (SessionStart row) should say that the message goes into the session when the hooks finish, before your first prompt, and that `/reload` keeps it. `:178` ("A `SessionStart` context that a compaction adds just before a block reaches the model at your next prompt", an unmeasured statement) should be reworded or checked against the new path. Also fix the comments listed under Cleanup.

### Pitfall 4: A clone group with `sendQueuedPromptContext`
A second copy of the try/catch send body trips `fallow dupes` (every clone group fails since fallow 3.32). Share the helper.

### Pitfall 5: Reading "no-leak" as a cucumber scenario
No scenario today asserts that context does not cross new/resume/fork. The session.feature new/resume/fork scenarios assert hook runs, and they all stayed green (A1-hook.log). Isolation comes from Pi's new `AgentSession`. If the planner wants a user-visible guard, one optional scenario is: a SessionStart hook with context, `/new`, prompt, and the model call holds the context exactly once (the new session's own). This is not required by the success criteria.

### HKRL-02 design (measured)

**Where to read.** Read `ctx.sessionManager.buildSessionProjection().messages` inside the adapter, at the moment SessionStart(`resume`|`fork`) finishes. Pi emits `session_start` after the new `AgentSession` loaded its session (`agent-session-runtime.js` `createRuntime({ sessionManager, sessionStartEvent })`), so the projection holds the copied or resumed entries. Measured: the fork at the first prompt holds the parent's head entry, and dedup drops it (scenario 1 below). The projection is what the model sees: the messages after the latest compaction, as upstream loads a resumed transcript from its last compact boundary. Do not use `getBranch()`. It includes entries that a compaction summarized away, so it would suppress a value the model no longer sees.

**Matching rules (the scratch code, `fix-src.diff`):**

1. Values are the non-blank (`trim()`) `additionalContext` of every outcome in routing order (the same list `joinedContext` builds). Only source `resume` and `fork` filter. `startup`, `clear`, and `compact` send all values unchanged (HKRL-02).
2. Keys come from projected messages with `role === "custom"` and `customType === "claude-hook-additional-context"`:
   - With `details` of shape `{ event: "SessionStart", values: string[] }`: each value is a key.
   - With `details` present but another shape: no keys. A UserPromptSubmit message has no `details` today, so it falls through to rule 3, and its label does not match.
   - Without `details`, the older message case (CONTEXT [Per-value matching]): for each text part that starts with `SessionStart hook additional context: `, the rest of the text is one key. A message that a released version wrote holds the SessionStart part first and the UserPromptSubmit parts after it (old `startRun` shape), so each part is read on its own.
3. Every key and every value passes `contextKey`: when it starts with `<persisted-output>`, `replace(/(saved to: ).*$/mu, "$1<persisted>")`. This is `gTt` verbatim, with the `u` flag that the lint config wants.
4. Drop every value whose key is held. Also drop everything when the whole new join is a held key. That case is an older message that holds the same joined values. The scratch code makes this check first.
5. Nothing left means nothing sent. `hookContextPart` already returns `undefined` for an empty list, and `sendHookContextMessage` returns early on it.
6. The sent message carries `details: { event: "SessionStart", values: <the values it sends> }`, so a later resume compares per value. Upstream trims a multi-value attachment to its novel strings (`eSe(y,{...R,content:H})`), so `details.values` holds the sent values, not all values.
7. A throwing `buildSessionProjection()` is debug-logged, and every value is sent (NFR-2). The scratch log line is `adaptObservation: session start context read failed: <error>`.

**Placement.** The resume or fork send goes through the same idle `triggerTurn: false` append, so it lands at the end of the loaded conversation. That matches `Vt.push(...)` upstream. Measured on resume: `SS ctx, first prompt, Hello., resume-ctx, second prompt`.

  readonly event: "SessionStart";
  readonly values: readonly string[];

const SESSION_START_LABEL = "SessionStart hook additional context: ";
const PERSISTED_PREFIX = "<persisted-output>";
function contextKey(value: string): string {
  return value.startsWith(PERSISTED_PREFIX)
    ? value.replace(/(saved to: ).*$/mu, "$1<persisted>")

}
function messageKeys(message: AgentMessage): readonly string[] {

**Discriminator.** The scratch code tracks one per-registration cell, `runPhase: "idle" | "turn" | "between"`:
- `turn_start` → `"turn"` (one new `pi.on`)
- the existing `turn_end` → `"between"`
- the existing `agent_end` → `"idle"`

The compaction callback passes `nextCallInRun = event.willRetry || runPhase === "between"` on the Claude event, and the adapter sends `nextCallInRun === true ? { deliverAs: "steer" } : { triggerTurn: false }`.

**Why `turn_start` is needed.** Pi also compacts inside `prepareRequest` for a virtual (routed) model (agent-session.js:536-538). That runs after `turn_start`, so the steering poll for that request has already happened. A steer there would be read at the turn's end and force an extra turn when the response ends the work. With the `turn_start` reset, that path keeps `triggerTurn: false`, and the context waits for the turn end: no extra call, though that one request misses it. The harness has no virtual model, so this case cannot be driven; it needs a router unit test of the phase cell. Without `turn_start`, the phase would stay `"between"` through every later turn.

**Why not other carriers.**
- `deliverAs: "nextTurn"` waits for the next prompt (break Bi fails the manual and (c) scenarios on order).
- `deliverAs: "followUp"` is read only when the agent would stop.
- A `context` event injection is not persisted, so a later turn would lose the context, or it would need a second send that duplicates it.
- `ctx.isIdle()` and `ctx.hasPendingMessages()` cannot tell (c) from (d).

**Plumbing.** Add `readonly nextCallInRun?: boolean;` to `ClaudeSessionStartEvent`. It is router-internal: `translateSessionStart` (payloads/session-start.ts:78-91) copies only `source` to stdin, and the matcher reads only `source` (dispatch.ts:1536-1537). The planner may prefer to pass it through `HookAdapterContext` or a runtime cell instead; the event field is the smallest change.

**Edge cases.**
- In (d), Pi's loop polls steering again only when the earlier poll returned nothing (agent-loop.js:115). If a user steer was already polled at that boundary, the context steer waits one more turn, and when that turn ends the work it causes one extra call. This is rare: a user steer during a tool and a threshold compaction at the same boundary. Note it in the docs and do not code around it.
- In (b), when `willRetry` is true (an unrecovered overflow before a new prompt), `_startRun` drops the retry ("the new prompt replaces it", 1505-1506). The steer then lands right after the prompt, but in the same first call.

**Steer messages show nothing.** The TUI renders only `display: true` custom entries (interactive-mode.js:2893, 3272). `agent.steer(appMessage)` bypasses `_steeringMessages`, the text queue that the UI shows (agent-session.js:1964 vs 1862-1889).

### Pitfalls (gap)

1. **Reading the branch instead of the projection.** `getBranch()` holds entries that a compaction summarized away, so dedup would hide a value the model no longer sees. Use `buildSessionProjection().messages`.
2. **Steering when no call follows (path c).** Measured (Bd): a steer after `agent_end` makes Pi's `_runAutoCompaction` return `hasQueuedMessages()` true, which starts an extra model call. The guard is `willRetry || between turns`, never "run active".
3. **Forgetting the `turn_start` reset.** It cannot be driven in the harness (no virtual model). Cover it with a router unit test.
4. **One hook in the changed-value scenario.** The no-`details` fallback then matches, so Bc passes. Use two unchanged hooks.
5. **Two `When`s in a row.** The world refuses a second turn before the first is compared. Use the new setup `Given`s, or put a `Then the hooks record these runs:` between them.
6. **Line shifts.** New scenarios move later line numbers in `additional-context.feature`. Derive every verify command's `# <file>:<line>` from the edited file, in the failure form `  N) <title> # features/hook/additional-context.feature:<line>`.
7. **Prettier, mdformat.** Run Prettier on `.ts` only. Markdown goes through mdformat in the hook, as the 06.1-01 deviation records.
8. **Untyped `details` on read.** `CustomMessage.details` is `unknown` when read back from the projection. Validate its shape (`isDetails`); never cast.
9. **Direct-coverage environment.** Run with `env -i HOME=$HOME PATH=$PATH LANG=C.UTF-8 TMPDIR=/tmp` plus the prefix, as before. `fd` must be on `PATH` (`fdfind` symlink) for the hook-wide set.
