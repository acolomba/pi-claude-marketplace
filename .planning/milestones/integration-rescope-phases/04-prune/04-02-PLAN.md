**The defect** (RESEARCH "Product finding", measured both ways). `snapshotPath`
(`prune-rollback.ts:103-123`) copies each target with `cp`, which keeps a directory's mode, and
the restore needs that: `sameEntry` (`:125-158`) compares modes. So a member whose skill ships a
`0o555` directory gets a backup that holds a `0o555` directory, and `rm` with `recursive` and
`force` cannot empty it (EACCES on the file inside). The three removals of the backup root are the
same call, `ops.removeBackup(backupRoot, { recursive: true, force: true })`: the prepare failure
path (`:440`, then rethrows), the rollback's final cleanup (`:489`, which pushes a `backup cleanup`
failure), and `discard` (`:499`, which only calls `hookDebugLog`). After F01's prune,
`.pi/pi-claude-marketplace/prune-backup-XXXXXX/0/read-only/data.txt` stays, and a retry does not
remove it.

**The fix.** Two module-private helpers between `artifactTargets` (ends at `:362`) and the JSDoc
of `preparePruneRollback` (`:364`):

- `grantBackupWrites(root)`: `lstat` the path; return unless it is a directory, so a symlink is
  never followed; set its permission bits plus owner read, write, and search (`(mode & 0o7777) |
  0o700`, the mask `restoreArtifact` uses at `:203`; removing a directory's entries needs write
  and search on it, and listing it needs read); list it with `readdir` and recurse into every
  entry through `Promise.all`, because production code may not `await` in a loop
  (`no-await-in-loop`). `chmod`, `lstat`, and `readdir` are already imported.
- `removeBackupRoot(ops, backupRoot)`: when `pathExists(backupRoot)` (already imported from
  `shared/fs-utils.ts`; it reads ENOENT and ENOTDIR as absent), run `grantBackupWrites`; then call
  `ops.removeBackup(backupRoot, { recursive: true, force: true })`, the module's one remaining such
  call. An absent root counts as removed, as `rm` with `force` treats it, so the prepare failure
  path rethrows its own error (the research's caution 1).
- The three call sites become `await removeBackupRoot(ops, backupRoot);`, each inside its existing
  `try`/`catch` or `catch` block. Replace them BEFORE you insert the helpers (caution 2): a
  replacement after the insert also rewrites the helper's own call, and every actual prune then
  recurses forever (the research's 224-second run).

Each helper gets a JSDoc that cites NFR-3 and says why: `snapshotPath` copies modes because
`sameEntry` compares them, so a backup can hold a plugin's read-only directory, and the walk runs
only on a backup that is about to be removed. A rollback with failures keeps its backup for manual
recovery and never reaches the removal, so the walk never changes a kept backup. Comments must not
repeat the removal call's text, which an acceptance gate counts.
