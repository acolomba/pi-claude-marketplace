<objective>
Close both `GGAT-03` gaps by resolving the ESLint configuration that actually applies to a file
instead of reading the configuration's source, and prove the resolution fires by varying the config
source across three offenders built from the real config plus exactly one appended block.

Purpose: `loadZones()` returns the first block that mentions `import-x/no-restricted-paths` and
never resolves the cascade — measured, a later `"off"` leaves it reporting 8 zones while the rule
is disabled. The `hooks-dispatch.test.ts` scrape looks for `files: [...]` arrays that literally
contain the extension path — measured, a blanket `files: ["**/*.ts"]` block flips
`domain/manifest.ts` from severity 2 to 0 while the gate stays green. Both are the same
anti-pattern: reading a config's raw source and matching on it.

Output: one shared effective-config resolver, a `no-console` severity gate sweeping all 229
extension files, a resolved zone-matrix gate, three offender proofs, per-name positive controls
for the joined ledger regexes, and the two superseded gates deleted.
</objective>

**`GGAT-03` / precision — unresolved, flagged.** The probe asks where precision loss, overflow, or
rounding can occur and what the exact contract is. Effective-config resolution has no numeric
contract: ESLint returns severities as the exact integers 0, 1, and 2, already normalized from
`"off"` / `"warn"` / `"error"`, and the zone matrix is a set of strings. There is no arithmetic, no
float, and no tie-break. The honest disposition is that the probe does not apply to this
requirement, not that a precision check was written to satisfy it. Do not fabricate one. If a later
reviewer disagrees, the claim to test would be that a severity comparison uses `===` against the
integer rather than a truthiness check — which the acceptance criteria below already pin by
asserting the exact values 0 and 2.
</edge_coverage_assumptions>
