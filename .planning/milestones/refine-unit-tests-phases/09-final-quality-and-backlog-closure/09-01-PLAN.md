<design_decisions>
Five choices this plan owns under D-09-08 and CONTEXT §"Claude's Discretion". Each is
recorded with what it rejected, because D-09-08 requires the shape to read as deliberate
design and a decision with no recorded alternative does not.

**1. Interface shape — a narrow `HooksFileReader`, with `HooksHydrationReader` extending it.**

```
HooksFileReader      { readHooksJson }                    ← createHooksRouting takes this
HooksHydrationReader { readHooksJson, loadState }          ← createHooksHydration takes this
                     (declared as `extends HooksFileReader`)
```

Chosen because it is the only shape where the read port is exactly one type with exactly one
member, both factories receive that type (hydration receives it as the base of its reader),
and neither factory is handed a member it never calls. `interface X extends Y` is already the
house idiom — `domain/hooks-resolution.ts:10`, `orchestrators/types.ts:23`,
`orchestrators/reconcile/apply-outcomes.ts:42` all use it.

- **Rejected — shape (c), one merged `HooksReader { loadState, readHooksJson }` taken by both
  factories** (09-RESEARCH §2.3's recommendation). It hands `createHooksRouting` a `loadState`
  member routing provably never calls, and forces 139 test call sites to stub an operation the
  unit under test cannot reach. `shared/fs-utils.ts:58-66` states the rule this violates: "Two
  members and no more… Widening this into a general filesystem facade would put every verb in
  this module behind a seam nothing asked for."
- **Rejected — shape (b), a separate `HooksReader` alongside `HooksHydrationReader`,** which
  makes hydration `createHooksHydration(runtime, stateReader, hooksReader)` — three positionals
  and two reader objects for one responsibility.
- **Rejected — shape (a), widening `HooksHydrationReader` and giving routing a different
  one-member reader.** Two ports with different member sets for the same read is the asymmetry
  D-09-06 rejects, relocated rather than removed.

**2. Where the real implementation lives — `bridges/hooks/stage.ts`.**

`readHooksJson` cannot live in `event-router.ts` (D-09-05 forbids the static import there).
`stage.ts` is the hooks bridge's file-primitives module, it already owns a named injected
read-only filesystem port (`HooksTreeInspector`, `stage.ts:30`), its header at `stage.ts:38-40`
already names "(later) … any hydrate-side reader" as a future consumer, it is already exported
through the hooks barrel, and it already has an owner test. Its header line 3 is amended from
"write/remove primitives" to "read/write/remove primitives" so the module says what it holds.

- **Rejected — a new `bridges/hooks/reader.ts`.** `scripts/check-corresponding-tests.mjs:30-36`
  would demand `tests/bridges/hooks/reader.test.ts`, and the module would add a 231st pair to
  the enumeration every downstream plan measures against 230 — churn that buys nothing and
  splits hooks-file I/O across two modules.
- **Rejected — `shared/fs-utils.ts`.** A generic `readUtf8File` there breaks the object-literal
  shorthand at the composition root and contradicts that module's own stated narrowness rule.
- **Rejected — an arrow declared inside `extensions/pi-claude-marketplace/index.ts`.** The entry
  is one of the 230 measured pairs; a factory-local arrow would only be covered by a test that
  drives a real hydration read, which is a coverage risk taken for no design benefit.

**3. How the composition root supplies it — the object-literal shorthand.**

`createHooksRouting(hooksRuntime, { readHooksJson })` and
`createHooksHydration(hooksRuntime, { loadState, readHooksJson })`, with `readHooksJson`
imported by name from the hooks barrel exactly as `loadState` is imported by name from
`persistence/state-io.ts`. Both members are then import shorthands and `index.ts` reads as one
consistent wiring line.

- **Rejected — a `createHooksFileReader()` factory call** (the `createRemovalOps()` style at
  `orchestrators/plugin/install-flow.ts:223`). `index.ts` is under a source-text gate
  (`tests/index.test.ts:787-793`); one literal is easier to pin than a factory whose body lives
  elsewhere, and mixing a factory call into the hydration literal would read
  `{ loadState, ...createHooksFileReader() }`.

**4. How tests supply the double — the production implementation at every existing call site.**

Every call site that exists today reads the real file today. Passing the production
`readHooksJson` preserves that behavior exactly, which is what a mechanical port must do. Only
a case that wants injected behavior writes its own member inline, which is what Task 2 does.

- **Rejected — a shared `tests/bridges/hooks/*-fake.ts`.** `check-corresponding-tests.mjs:44-56`
  carries a `-fake.test.ts` / `-contract.ts` companion rule; paying it for a one-member
  interface is cost with no return (09-PATTERNS §A.8).
- **Rejected — a per-test-file no-op stub constant.** A stub that returns synthetic bytes would
  change behavior at the sites that genuinely read a fixture file.

**5. `tryHydrateOnePlugin` gains a tenth positional parameter rather than an options object.**

The reader is threaded exactly as `routingState` and `generationIsCurrent` already are, which
is the repo's established port-threading style (`ops: RemovalOps` repeated down
`bridges/skills/stage.ts:164, 325, 386, 402, 479, 497, 524`).

- **Rejected — folding the nine parameters into an options object.** CONVENTIONS.md's rule
  names "optional/named fields"; every one of these is required and positional. Folding is a
  separate refactor with its own blast radius that no decision in 09-CONTEXT.md authorizes, and
  the phase boundary bars new work. 09-RESEARCH §2.7 measured the cost of the tenth parameter:
  `max-lines-per-function` is not a configured rule, and `npm run fallow` reports
  `functions_above_threshold: 0` with a 103-line function already present.
</design_decisions>
