<objective>
Report what did not install without failing what did, and record what did install so the next
phase can take it away again.

Purpose: a workflow-bearing plugin routinely carries files that are not commands — shared helper
modules, an unparseable draft, a header comment that trips the engine's raw-text gate. Failing the
whole plugin for any of those would be wrong, and staying silent about them would be worse. The
other half is the install record: the artifacts land outside every scope root, so a record that
does not name them is a record the uninstall path cannot act on.

Output: the per-file warning builders and their routing, the collision hard-fail regression, the
staged-anything disjunction extended to the sixth kind, and the `workflows` member of the install
record with the default-fill that keeps existing state files loadable.
</objective>

<known_limitation>
**The standalone-surface visibility gap is real, is not closed here, and must not be papered over.**

Bridge-side soft warnings are collected on the install context and forwarded to the post-commit
warning list only in orchestrated mode. On a plain, standalone `/claude:plugin install` they are
deliberately dropped, because bridge-side soft warnings have no representation on that row. The
alternative channel — the one that does surface a token on the standalone row — draws from a closed
reason set pinned by the no-expansion architectural gate and by the output catalog's byte-equality
gate, and the new token for this component kind is scheduled with the soft-dependency work of the
following phase.

So: this plan wires the warnings correctly into the channel that exists and proves they arrive
there. It does NOT claim the user sees them on a standalone install, and no acceptance criterion in
this plan is phrased that way. The gap is carried forward explicitly — record it in the summary and
name it in the phase verification so the following phase inherits it as scope rather than
rediscovering it.
</known_limitation>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin-authored script bytes -> warning message text | Untrusted file names and reason strings are rendered into messages the user reads. |
| pre-existing on-disk state file -> the schema validator | A file written by an older build of this extension crosses into a stricter schema. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-103-11 | Spoofing | warning message construction | medium | mitigate | Messages render the decision layer's own reason text and the file name; nothing is paraphrased and nothing is interpolated from script contents. The truthful-attribution rule that distinguishes a match in code from a match in a comment stays in the layer that owns it, so a message cannot claim a rule the script did not violate. |
| T-103-12 | Denial of Service | a plugin full of unreadable or refused scripts | low | mitigate | Every per-file arm is a warning and the walk continues; the plugin still installs. No arm throws, so a single hostile file cannot deny the install of the rest. |
| T-103-13 | Tampering | a name collision resolved silently | high | mitigate | The collision assertion runs over the full verdict array before any dedup, and throws. Keeping the first arbitrarily would install a command under a name its author did not choose. Pinned by a regression case that also asserts the saved directory is empty afterwards. |
| T-103-14 | Denial of Service | a required schema member with no default-fill | high | mitigate | The fill runs inside the migration helper that iterates every record, before the validator is invoked — the same order the most recent additive member established. Pinned by a case that loads a pre-change fixture, which goes red if the fill arm is removed. |
| T-103-15 | Repudiation | artifacts on disk with no record naming them | high | mitigate | The install record gains the generated names the workflows phase staged. Without it, files outside every scope root would exist with nothing tracking them, and the removal path of the following phase would have nothing to act on. |
| T-103-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs no package and runs no package manager. The package-legitimacy audit in `103-RESEARCH.md` records no `[ASSUMED]` and no `[SUS]` entry, so no legitimacy checkpoint is required. |
</threat_model>
