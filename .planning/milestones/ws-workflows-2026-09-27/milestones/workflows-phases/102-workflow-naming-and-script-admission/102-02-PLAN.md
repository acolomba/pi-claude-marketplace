**The vendored constant (WVAL-01).** Declare the determinism blocklist as a module-level `const`,
copied byte-identically from the engine's private constant as quoted in `102-RESEARCH.md` Code
Examples section 3. Declare it with NO flags, so a future reader can diff the literal against
upstream. Its doc comment records: that it is a byte-identical copy of an unexported internal of
`@quintinshaw/pi-dynamic-workflows` at the measured version 3.5.1; that the engine runs it as a raw
text test over the whole script BEFORE acorn parses, which is why it cannot tell code from comment;

Only this one gate is replicated. The engine's `parseWorkflowScript` carries six further structural
rules; they are unexported internals of a 0.x package and are deliberately out of scope, as the
scope note above states.

**Two uses, one pattern text.** The constant answers the verdict with `.test(source)`. Positions come
from a clone built per call — `new RegExp(<constant>.source, "g")` — iterated with `matchAll` to read
each match index. Build that clone inside the function, never at module level: a global regex retains
its match position between calls and silently skips an early match on the second invocation, which
passes when a test runs alone and fails when a sibling runs first. Do not introduce a second regex
literal; two pattern texts drift apart.

**Classification (WVAL-03).** The single `parse()` already collected the comment ranges via
`onComment` and the string and template token ranges by filtering `onToken` on `tokTypes.string` and
`tokTypes.template`. For each match index, test containment against those two range sets. A match
inside no range is executable code. Classify the whole script by its matches: if ANY match is in
code, the script is a real determinism violation; otherwise the script is classified by where its
matches actually sit — comment, or string/template.

Three named private reason builders, one per classification, mirroring `domain/source.ts`'s
reason-builder form rather than inline template literals at the return site. Each names the offending
file and the matched text. The comment classification's message additionally carries the actionable
remedy: the engine's check is raw text, so rewording the comment makes the script load. Keeping the
builders separate is also what keeps the classification function under the cognitive-complexity cap.

All three classifications produce `outcome: "refused"` with three distinct causes. A comment-only
match is still refused — the engine rejects the script wholesale either way, so admitting it would
register a command that cannot run. The distinction changes the message, not the verdict. That is the
whole point of WVAL-03: the engine's own message names a rule the script does not violate, and
reproducing that message would be worse than saying nothing.

Note in a comment that our ordering deliberately differs from the engine's, which runs the blocklist
before parsing: for a script that is both unparseable and carries a token, the engine reports a
determinism error and we report "unparseable". Ours is the truthful one.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin-authored workflow script -> `admitWorkflowScript` | Untrusted third-party JavaScript source text crosses here as a string. It is parsed and classified; it is never executed. |
| plugin-authored `meta.name` -> `generatedWorkflowName` | An attacker-chosen string crosses here and, if admitted, becomes a name a later phase uses as a file basename. |
| a whole plugin's verdict set -> `assertNoWorkflowNameCollisions` | Two scripts in one plugin can claim one name, which without this gate would let a later-written artifact overwrite an earlier one. |
