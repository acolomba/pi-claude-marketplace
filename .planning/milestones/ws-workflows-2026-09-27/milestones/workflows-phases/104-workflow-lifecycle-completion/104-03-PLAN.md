<objective>
`previousWorkflowNames` is accepted by `prepareStageWorkflows`, documented, and supplied by
no production caller, so the entire re-stage branch is unreachable. Meanwhile the commit
rename loop has no already-exists check, so a plugin silently overwrites a user's own
hand-saved workflow of the same name.

**These two land in the same task, not merely the same plan.** With `_previousNames` always
empty, `displacePreviousTargets` short-circuits and every `enable` re-materialization of a
plugin's own envelope would hit an existing target and be refused. Splitting them trades a
silent overwrite for a broken `enable`. Wiring the recorded inventory is what makes the
refusal correct.

Phase 103 already made the commit path safe for their arrival — previous targets are
displaced into staging and restored on failure rather than unlinked — so this is a wiring
change, not a redesign.

Purpose: make the re-stage branch reachable and the shared directory safe at the same
instant.
Output: one supplied parameter, one refusal, and the enable-convergence case that only
works because both landed together.

**Probe edges authored here:** 4 of 22 (all WLIF-05) — three auto-`resolved`
(verification: explicit), plus one additional decided behavior carried as a
`verification: backstop` marker. 0 flagged assumptions, 0 silent drops.
</objective>
