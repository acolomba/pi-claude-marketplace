# Raise the pi-mcp-adapter floor to 5.1.0 and re-check the adapter facts against it

<objective>
Implement D-04-12 before Phase 4 is planned. The optional pi-mcp-adapter peer floor moves from 5.0.0 to 5.1.0. 5.1.0 is the first adapter release whose optional `@earendil-works/pi-ai` peer admits Pi `^1.0.0`. Every live pin of the floor moves with it: the manifest and the lock, the PIFL-03 and AFILE-06 gates, the `scripts/pi.sh` runtime pin, the comments that cite re-verified adapter facts, both READMEs (their upstream peer-gap note goes away), the CHANGELOG, and the live planning records (PIFL-03 is amended). The adapter facts that Phases 2 and 3 rely on, and that Phase 4 builds on, are re-checked against the registry-verified 5.1.0 tarball and recorded in the SUMMARY. The Pi peer floor stays `>=1.0.0` (PIFL-01). The carried-field set (D-02-06) does not change: the new 5.1.0 ServerEntry member `openUi` becomes a visible pin entry and an operator decision, not a silent addition.

Purpose: Phase 4's conformance test pins 5.1.0, and its threat model depends on the adapter's expansion code. A plan built on a 5.0.0 floor, with a README that warns about a peer gap that 5.1.0 closed, would rest on stale facts.

Output: three tasks and three commits.

- Task 1 (tracer): the floor end to end through package.json, the npm-regenerated lock, and both gates, with the ServerEntry pin re-derived from the 5.1.0 tarball after a hash-verified, read-only re-check.
- Task 2: the `scripts/pi.sh` pin, the citations in one source comment and two integration-test comments, and both READMEs.
- Task 3: the CHANGELOG entry, the live planning records, and the final `npm run check`.
</objective>
