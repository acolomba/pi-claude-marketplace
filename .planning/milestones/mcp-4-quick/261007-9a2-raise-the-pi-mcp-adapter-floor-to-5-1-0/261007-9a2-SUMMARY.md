## Operator decision: openUi

5.1.0 adds `openUi?: boolean` to ServerEntry. Its doc comment says: "Set to false to never open MCP
App UIs for this server's tools; results stay inline." The adapter reads it by name in
direct-tools.ts and proxy-modes.ts to skip the MCP App UI session.

Under D-02-06 today, `openUi` is not a carried field. If a user's override stub holds `openUi`, the
bridge keeps the stub in the marker (`_piClaudeMarketplace.keptOverride`). The install warning
names `openUi` as a field that stops applying, and unstage writes it back. If a user sets `openUi`
directly on a marked entry, an update or reinstall drops it, the same as `exposeResources` and
`trace`. The AFILE-06 every-key test and the ANAME-07 hostile-entry test now cover `openUi` and
pass with no change to their expected values.

Carrying it would change these files: `CARRIED_FIELDS` in
`extensions/pi-claude-marketplace/bridges/mcp/adapter-entry.ts`, `CARRIED_KEYS` in
`tests/bridges/mcp/adapter-entry.test.ts` (plus the literal expected JSON of the tests that spread
`CARRIED_KEYS`, at lines 500 and 976, and of the every-key test), `docs/mcp-compatibility.md:137` (the carried-field list),
`docs/output-catalog.md:4224` (the carried-field list), and a new decision that amends D-02-06.
The closed translator never writes `openUi`, so no plugin-set conflict arises, and `openUi` carries
no credential.

Timing: decide before the release that ships Phases 2 to 5. Recommendation: keep the set closed
until the operator decides.
