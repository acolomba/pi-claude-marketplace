<objective>
Settle decision 26: in a pi-subagents child, a tool hook's session fields name the main session, as Claude Code's do, and its `agent_id` names the child.

Purpose: today a child's `session_id`, `transcript_path`, and `CLAUDE_CODE_SESSION_ID` name the child's own Pi session, so `session_id` equals `agent_id`. Claude Code keeps the main session in those fields and puts the subagent in `agent_id`. A hook that keys its state on `session_id` therefore splits one user session into many on Pi. Plan 06-07 resolves the launching session and keeps it with the child's identity; nothing reads it yet.
Output: a translation context with hook-facing session fields and an own session id for every internal key, the env layer and the journal key on the own id, and the real-child scenario that states the main session. Plan 06-13 corrects the compatibility page's "Child identity" passage.
</objective>

## Flagged assumptions

- **A child with no identity keeps its own session fields (planner's rule; pending maintainer review).** D-PG6-01 says a child hook tells itself apart by `agent_id`. When pi-subagents' agent tag is missing, the payload has no `agent_id`, so root session fields would make the run read as a main-session run. The root is therefore applied only with a known identity. This is the plan's one kept prohibition.
- **A nested child names its launcher, not the root (departs from D-PG6-01 for that one case; pending maintainer review).** Plan 06-07 resolves one hop and publishes nothing on `process.env`, so a child of a child reads the child that launched it. The reasons and the alternative are in plan 06-07's flagged assumptions. No real nested child runs in any test.
- **F12: a child's Bash tool keeps the child's own `CLAUDE_CODE_SESSION_ID`.** `applySessionEnv` sets Pi's `process.env` from the own session, so a hook and a Bash command in one child disagree on the variable. D-PG6-01 names the hook's variables only. What Claude Code's Bash tool sees in a subagent was not read (assumption A7). Plan 06-13 records the difference; the maintainer decides whether the root id should also reach the child's `process.env`.
- **An unreadable parent file is passed on as text.** When the root holds a path whose file could not be read, the path is still sent as `transcript_path`. pi-subagents wrote that header for this launch. Claude Code also sends a path before its file exists.
- **Foreground children run no plugin hook**, so the decision concerns background children only (a Pi capability gap already on the compatibility page).
- **The plan runs after plan 06-08.** The two share bridges/hooks/dispatch-exec.ts and async-rewake/registry.ts and their tests, and nothing else: plan 06-08 adds one row to each translator table, and this plan changes the context build beside them. Running this plan second lets it share a wave with plan 06-10, with which it shares no file.
