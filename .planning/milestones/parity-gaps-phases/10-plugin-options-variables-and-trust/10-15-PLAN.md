<objective>
Leave out, and report, a stdio server whose command or argument starts with a plugin option
that holds a home path.

Purpose: D-PG10-11. pi-mcp-adapter expands a leading `~` in `command` and in each `args`
element after it fills variables, and Pi's built-in MCP does the same for its config. Claude
Code 2.1.323 passes an option's value as written. So once plan 10-17 fills option values, a
default such as `~/bin/tool` at the start of a command would start a program under the
user's home that the plugin's author did not name. This plan blocks that server first, in
the verdict of plan 10-12, so the fill never meets the case.

Output: the verdict's second reason, the second member of the `option-blocked` notice's
reason set in its three homes and the catalog, and two scenarios.
</objective>

## Planner decisions

- **The rule is in the verdict.** `mcpOptionBlock` gains its second reason: a `command`, or
  an `args` element, whose text starts with a reference to an option whose MCP value
  pi-mcp-adapter would home-expand. It reads the value from the MCP value map and the rule
  from the adapter's source. The stage, the built-in entry, and the registration step call
  the verdict already, so none of them changes.
- **One rule for both implementations.** The verdict uses the adapter's rule under both, so
  the two cannot disagree. Pi's own home check in `builtin-entry.ts` stays as the second
  line for the built-in fill of plan 10-19.
- **`unset` comes first.** A server that names an unset option and a home-path option gets
  the reason `unset`: with no value for one field the server cannot run, whatever the other
  holds.
- **Tracer on `command`.** Task 1 blocks on `command`; Task 2 adds each `args` element, with
  its own red scenario.
