  <action>
Add the dependents guard to the DISABLE branch only, inside the existing locked
transaction closure, before anything is unstaged.

**Placement.** The guard runs after the write-target selection and after the
`not-recorded` check, and BEFORE the `isRecordedButDisabled(installed) === !enable`
idempotency short-circuit is allowed to return on the disable path -- a target
that is already disabled has nothing to refuse, so let the idempotent arm keep
winning there; but a target that WOULD be disabled must face the guard before
`runDisableBranch` is reached. Keep the whole guard in an extracted helper
(`readEnabledDependents`); `setPluginEnabledWithTransaction` is already near the
cognitive-complexity ceiling of 15 and must not gain an inline branch.

**The read.** Call `buildScopeDeclarationIndex({ state, locations, exclude: key })`
where `key` is `${plugin}@${marketplace}`, then `findDependents(key, result.index)`
-- the exact composition `uninstall.ts::readDeclarers` performs. Its `ok: false`
arm throws the refusal carrier with `"unreadable"` and `result.cause.message`,
preserving D-05-07 fail-closed: a record with no usable answer is never read as
"declares nothing".

**The filter that makes this EDEP-02 and not PRUNE-05.** `buildScopeDeclarationIndex`
indexes DISABLED records too (D-05-04), because holding a declaration does not
depend on being active. EDEP-02 asks about an ENABLED installed plugin, so narrow
`findDependents`'s output to the declarers whose own record is not
`isRecordedButDisabled`. The `candidates` array the index result already carries
gives each key's `record` handle, so no second walk and no key re-lookup is
needed. Write a comment that states this narrowing and cites D-05-04, because a
reader coming from the uninstall guard will expect the unfiltered set.

**The refusal.** Non-empty enabled-dependent set -> throw the refusal carrier with
the brace token Task 1 of plan 08-01 ruled on (the planner's recommendation is
`dependents remain`, re-added at the `REASONS` tail) and the composed cause
sentence as its message. Nothing is unstaged, nothing is saved, no config is
written -- the existing save discipline gives this for free as long as the throw
happens before `runDisableBranch`, so assert the mtime rather than assuming it.
Render through the existing transaction catch, which already produces a `(failed)`
row at `error` severity with no reload hint -- the correct shape for an operation
that was not carried out.

**The sentence (D-08-01).** Upstream's template offers a chained command; this CLI
has no multi-target form, so compose a plain-English instruction instead: name the
target, name the sorted dependents, and state the order -- disable the dependents
first, then the target. Follow `docs/messaging-style-guide.md` for punctuation and
voice. Build it in `enable-disable.messaging.ts` as `composeDisableRefusalCause`,
and route the dependent list through `renderDependentKeys`, a local mirror of
`uninstall.messaging.ts::renderDependents`: when every key passes
`isRenderablePluginKey` the keys are joined, and otherwise the list collapses to a
count. Plugin names admit quote, comma, space and bidi characters under
`domain/name.ts::assertSafeName`, and the cause-chain renderer neither escapes nor
redacts what it prints, so an unchecked name could forge the rest of the sentence.
Chain no nested `cause` behind the message, exactly as `UninstallRefusedError`
does not.

**Closed-set amendment -- all ten surfaces, ONE commit,** if the ruling took the
new-token option. The token appends at the TAIL of `REASONS` (index 60) and its
comment must state why the neighbouring `dependents unsatisfied` cannot carry it:

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| state.json declarer records -> rendered cause sentence | Plugin and marketplace names from other records are interpolated into a line-oriented refusal sentence. |
| marketplace manifest / plugin.json -> declaration index | Author-controlled JSON decides who counts as a declarer, and therefore whether a user's disable is refused. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-06 | Tampering | `composeDisableRefusalCause` dependent list | high | mitigate | Every dependent key passes through `renderDependentKeys`, a mirror of `uninstall.messaging.ts::renderDependents`: the keys are joined only when all of them pass `isRenderablePluginKey`, and otherwise the list collapses to a count. Asserted by the adversarial-name acceptance criterion in Task 1. |
| T-08-07 | Information disclosure | the refusal carrier's message | medium | mitigate | The message is composed from `name@marketplace` keys and fixed phrases only, and the fail-closed arm reuses `dependency-index.ts`'s already path-redacted `cause.message`. No `{ cause }` is chained behind either, so the renderer's cause-chain walk cannot print a raw underlying message. Asserted by the no-absolute-path criterion. |
| T-08-08 | Denial of service | an author-controlled declaration that refuses a user's disable | medium | accept | A plugin the user installed can declare a dependency on another installed plugin and so refuse its disable. This IS the requirement (EDEP-02) and it matches upstream; the remedy is named on the row (disable the dependents first, or uninstall the declarer, which is never refused for this reason under D-06-06). |
| T-08-09 | Tampering | guard bypass through the idempotency short-circuit | medium | mitigate | The guard is placed so that any path reaching `runDisableBranch` has passed it; a target that is already disabled returns through the idempotent arm, which performs no unstage. Asserted by the zero-call `cascadeUnstagePlugin` spy criterion. |
| T-08-SC | Tampering | npm/pip/cargo installs | low | accept | This plan adds no runtime or dev dependency and runs no package-manager install; RESEARCH.md records the legitimacy gate as not applicable for this phase. |
</threat_model>
