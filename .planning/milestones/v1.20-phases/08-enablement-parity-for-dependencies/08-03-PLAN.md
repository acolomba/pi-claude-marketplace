disabled now turns that dependency on through its own record and says so on the
row, and the `{already installed, dependency disabled}` skip that documented the
old refusal is retired from the closed set and from the catalog.

`enable-disable.ts` would leave behind -- plus the two documentation sections
that currently state the reversed rule as this extension's policy.

retired reason token, and the two rewritten doc sections.

**Partition.** In `runInstallCascade`, after `resolveMemberConstraints` succeeds
and before the phase array is built, split `closure.alreadyInstalled` with a new
`partitionAlreadyInstalled` helper into (a) members whose record is
`isRecordedButDisabled` and (b) the rest. The existing `recordedDisabled` helper
already answers (a) by exact-key lookup; reuse it rather than re-deriving the
predicate. Keep the constraint check running over the WHOLE
`alreadyInstalled` set first, unchanged: a member whose recorded version falls
outside the effective constraint must still fail the cascade before anything is
materialized, and that ordering is the contract stated in the module header.

**Phases.** Append one `buildReEnableMemberPhase` phase per member of subset (a)
to the FRONT of the phase array, before the closure's own members, so a dependency
is live before the plugin that needs it materializes. The phase's `do` calls
`seam.runInstallLedger` on the caller's state snapshot with `pinVersionOverride`
set to the member record's own recorded version, `allowExistingRecord: true`,
`partial` derived from the member record's own `compatibility.installable`, and
the caller's `options.capture` -- the same argument set `runEnableBranch` and

`run.members` with `reEnabledFromRecord: true`, so the row composer reads it out
