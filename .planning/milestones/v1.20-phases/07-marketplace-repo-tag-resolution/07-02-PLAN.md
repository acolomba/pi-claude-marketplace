<objective>
Make a version constraint on a path-source dependency usable even when the marketplace repository carries no tag that satisfies it. Today that case is an unconditional cascade failure; after plan 07-01 it is a path-source `no-matching-tag` failure with a local listing behind it. TAGS-02 turns it into a successful install of the marketplace's current copy, reported on the dependency's own row as a quiet info note, with the constraint left for Phase 6's load-time check to enforce.

Purpose: most marketplaces declare plugins with a relative path and most repositories outside Anthropic do not follow the `{name}--v{version}` release-tag convention, so the no-match arm is the arm most users will actually hit. Failing the whole install there would make constraints unusable in practice, which is the opposite of what this phase is for.
Output: a non-failure fallback arm through the cascade's constraint resolution, one new closed-set reason token carried on an `installed` row, and the five closed-set gate amendments plus the catalog state and fixture that a token addition requires in this repository.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| install outcome -> user's reading of the row | The row is the only place the user learns that the copy installed is not the one their constraint asked for; a row that under- or over-states the outcome is the whole failure mode of this plan. |
| new reason token -> catalog consumers | Anything that reads `docs/output-catalog.md` or groups reasons by class (the catalog-UAT fixtures, the parity gates) treats the token's class as load-bearing. |
| unsatisfied constraint -> Phase 6's load-time check | The constraint is deliberately left unenforced at install time; the load-time check is the only thing that will catch a genuinely out-of-range copy. |
