<objective>
Close the gap that makes version constraints unusable on the common case: a marketplace-relative `path` source. Today `install-cascade.ts::resolveMemberTagSource` returns `undefined` for a `path` source, which `probeMemberPin` turns into an unconditional `no-matching-tag` failure for every non-wildcard constraint.

This plan ships the whole happy path end-to-end, as one tracer slice: read the marketplace clone's own tags offline, select the highest satisfying `{name}--v{version}` tag, pin the member on it, materialize the plugin's files from that tag into the existing `plugin-clones/<key>/` cache, and record the tag's own semver plus the tag oid on the install record.

Purpose: make TAGS-01 and TAGS-03 true, and prove the architecture end-to-end before any expansion (TAGS-02's fallback, DIVG-01's docs) is built on it.
Output: a local tag-reading seam in `platform/git.ts`, one shared release-tag selection module in `domain/`, a local marketplace tag probe, a path-source branch in the cascade's constraint resolution, an injectable path-materialization callback on `ResolveContext`, a copy-then-checkout materializer in `clone-cache.ts`, and an integration test that drives a real git repository from install to installed bytes.
</objective>

<assumption_delta_decision>
**Signal:** `pluralization` -- "a stated fallback when no tag matches" and "a second worktree-like checkout". A path-source dependency gains a tag-resolution path alongside its existing git-backed sibling, so `ResolvedCascadeMember.pin` acquires a SECOND producer.

**Decision: `promote`, not `add-alongside`.** Both the git-tag pin and the marketplace-tag pin converge on the identical `{oid, version}` shape, and `ResolvedCascadeMember.pin`'s own docstring states the reason that field exists -- oid and version are folded together "so a producer cannot set one without the other". A second parallel pin field would break exactly that invariant and would fork every downstream consumer (`install-flow.ts::ledgerOptionsFor`, `install-outcome.ts::deriveInstallVersion`). The existing field takes a second producer; no new type is minted.

**Consequence carried into the tasks:** `probeMemberPin`'s path-source branch writes `pin: { oid, version }` through the same literal shape the git-backed branch writes at `install-cascade.ts:497`, which is what makes D-07-02 require zero new code in `install-outcome.ts` or `install-flow.ts`.
</assumption_delta_decision>

  <decision>
    D-07-01 is LOCKED and its four stated intents are honored either way: reuse the `plugin-clones/<key>/` cache and its existing GC sweep, key by the resolved tag oid, invent no second materialization mechanism, and never mutate the marketplace clone's own working tree or HEAD. What is on the table is only HOW the checkout is performed, plus a disk cost the decision did not price.

    Option A -- the decision's literal mechanism: call isomorphic-git `checkout` with `dir` set to the new keyed directory and `gitdir` pointed at the marketplace clone's real `.git`, with `noUpdateHead`. RESEARCH verified against the installed package source that `checkout` reads and writes the index at `${gitdir}/index` regardless of `noUpdateHead`, so this overwrites the marketplace clone's OWN index with the tag's tree state. The clone's working tree and HEAD survive; its index silently desyncs, and the next `marketplace update` runs its analyze/checkout cycle against a stale index. isomorphic-git has no alternates/multi-object-directory support, so there is no variant of Option A that shares the object store safely.

    Option B -- the construction already used in this codebase for the structurally identical problem (`seedOnePluginMirror`): copy the whole marketplace checkout, `.git` included, into a staging directory, then check the tag out using the COPY's own default gitdir, then promote staging into `plugin-clones/<key>/` by atomic rename. Every index read and write lands on the copy. All four D-07-01 intents hold, and the marketplace clone is never opened by any git API at all.

    Option B's price, which D-07-01 did not state: it duplicates the marketplace's whole `.git` history into every distinct `plugin-clones/<key>/` directory it materializes -- one full copy per distinct pinned tag oid across that marketplace's plugins. This is the same cost model SEED-01..06 already accepted for same-repo git-backed plugins, but a marketplace with many independently-tagged path-source plugins multiplies local disk usage per distinct tag.
  </decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| marketplace repository -> tag selection | Tag names and tag objects in a third-party marketplace clone are attacker-influenced input; whoever can push a tag to that repository chooses the strings this phase matches against. |
| marketplace repository tree at a tag -> local filesystem | A historical commit's tree is checked out and its paths are joined to a cache root; the tree's shape (directory names, symlinks) is attacker-influenced. |
| marketplace clone git state <-> this extension | The marketplace clone is state the user owns and other commands (`marketplace update`) depend on; this phase must read it without writing it. |
