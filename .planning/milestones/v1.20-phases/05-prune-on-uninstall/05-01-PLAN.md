<objective>
Give PRUNE-05 a code path on both entry points. Today `uninstall X` removes X whatever
else in the scope declares it, and a `/reload` that drops X from the config does the
same; the plugin that needed X is silently broken.

This plan is the phase's tracer: it wires ONE path — "uninstall X while Y declares X is
refused, naming Y" — through every layer the phase will touch: a pure domain function, a
new offline declaration-index leaf, the uninstall orchestrator's locked transaction, the
closed-set notification vocabulary with its ten pinning surfaces, the catalog, and the
reconcile projection. The `--prune` sweep in the next plan reuses the index this plan
builds and the removal path this plan leaves intact.

Purpose: a plugin that another installed plugin still declares must not be removable by
accident, and the operator must be told which plugin still needs it. Both facts must hold
under `/reload` as firmly as under the typed command (D-05-16).
Output: `findDependents` in `domain/dependency-orphans.ts`, `buildScopeDeclarationIndex`
in `orchestrators/plugin/dependency-index.ts`, the guard inside `uninstall.ts`'s locked
closure, the `dependents remain` member landed in full, two new uninstall catalog states
plus one reconcile-applied state, and the reconcile cause line.
</objective>

<planner_assumptions>
The research's Open Questions are recommendations, not decisions. This plan adopts them
as follows; the operator can override any of them at the plan checkpoint.

- **A-1 (Open Question 1 — the unreadable-declarer row).** The D-05-07 refusal renders on
  the NAMED plugin's own `failed` row, carrying the declarer's read-failure token in the
  brace (`not in manifest` for an entry the marketplace does not list, `invalid manifest`
  for an unusable declaration, or the `narrowProbeError` token for a manifest that fails
  to load) and a cause line `cannot read the dependencies of <declarer-key>: <detail>`.
  No new token. Catalogued as the `refused-declarer-unreadable` state. Because the index
  is built once, before the primary removal, the CONTEXT's "the prune step removes
  nothing and the primary stands" arm is unreachable from either entry point — the guard
  has already refused — so no such arm is written and no test claims it.
- **A-2 (Open Question 2 — two stale records block each other).** Accepted as the cost of
  D-05-07 for this phase: two records in one scope that are BOTH absent from their
  marketplace manifests refuse each other's uninstall until one is repaired
  (`marketplace update`, restoring the manifest) or removed through `marketplace remove`.
  Plan 03 documents the remedy and the phase UAT carries the scenario. D-05-07 is rated
  reversible; this is the scenario that would trigger the reversal.
- **A-3 (Open Question 3).** The D-05-16 reconcile refusal gets its own catalog state under
  `reconcile-applied-cascade` (`reconcile-uninstall-refused-dependents`): it is the one
  surface where a user meets the refusal without having typed the command.
- **A-4 (design).** The refusal is a typed `UninstallRefusedError` thrown INSIDE the lock
  closure and rendered through the existing failure channel (`catch` →
  `emitCascadeFailure`, reason from `narrowCascadeFailure`). This adds zero conditions to
  `uninstallPluginWithTransaction` (fallow 15/14 today against 20/15) and hands the
  reconcile path a typed cause to narrow on with `instanceof`, per the conventions.
- **A-5 (reconcile cause scope).** The reconcile projection surfaces a cause for a
  `plugin-uninstall-failed` outcome ONLY when the orchestrator's error is an
  `UninstallRefusedError`. Every other failed uninstall keeps today's cause-less row: the
  pinned RECON-03 `{permission denied}` bytes stay frozen and no errno path reaches the
  reconcile surface.
- **A-6 (gate pins).** `uninstall.ts` and the new `dependency-index.ts` are added to
  `NETWORK_FREE_TARGETS` now that uninstall composes a manifest read; the gate-targets
  header sentence calling `uninstall.ts` "implicitly clean … not gated" is rewritten.
- **A-7 (sha-pinned declarations).** For the guard, a declaration that names a key HOLDS
  it whatever constraint or `sha` it carries — the fail-closed direction. The closure
  walk's `sha` refusal is an install-time rule and is not copied.
</planner_assumptions>

    - `buildScopeDeclarationIndex({ state, locations, exclude })` walks every record under every marketplace in `state` except the excluded key and returns `{ ok: true, index }` where `index.get("y@mp")` is the set of `name@marketplace` keys `y` declares, each declaration's marketplace defaulting to `y`'s own marketplace; a disabled record is indexed like an enabled one; a record whose entry exists but whose own manifest is unreadable answers from its entry.
    - `buildScopeDeclarationIndex` returns `{ ok: false, declarer, reason: "not in manifest", cause }` when a record's marketplace manifest does not list it; `{ ok: false, reason: "invalid manifest" }` when its declaration parses as unusable; and `{ ok: false, reason: narrowProbeError(err) }` when its marketplace manifest fails to load — in every arm `cause.message` starts with `cannot read the dependencies of <declarer-key>` and contains no absolute path.

    - `uninstall X` when X is the only record: no manifest is read (the index walk finds no other record) and the existing success bytes are unchanged.

<assumption_delta_decision>
**Noun that is now primary:** the uninstall's removal unit. Today the command removes
ONE recorded plugin; with the guard the decision to remove any record depends on every
OTHER record in the scope, and with the next plan's sweep one command removes a SET of
records (the primary plus its orphaned dependencies) under one lock and one save.

**Decision: promote.** The per-plugin removal (cascade → fold-or-commit) becomes the unit
the next plan calls once per member, and the primary is the first member of that set.
This plan prepares it by keeping the guard OUTSIDE the removal body (one index, built
once, consulted for the primary now and for the members next) rather than adding a
second guard inside a second removal path. The report likewise generalizes from one
block to a list of blocks; the primary row stays the first row of the first block, with
no separate "primary" section.

**Accepted debt, named:** the primary and a member differ in failure disposition — the
primary's AG-5 rethrow aborts the save so its row stays intact for retry (TR-03), while a
member's failure becomes a warning row and the save proceeds (D-05-13). That difference
lives in the two callers, not in the body. What would force a further promote: a third
caller (a standalone `prune` verb, backlogged as PRUNE-CMD-01) needing a third
disposition; at that point the disposition becomes a parameter of the body.
</assumption_delta_decision>
