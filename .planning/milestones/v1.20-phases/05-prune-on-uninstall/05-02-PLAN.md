<objective>
Ship `uninstall --prune`. With the guard and the declaration index from Plan 01 in
place, this plan adds the flag on the catalog-owned surface (FLAG-01), the pure fixpoint
that decides which dependency records are orphans (PRUNE-01..03), the whole-scope sweep
inside the same locked transaction that removed the named plugin, and the report that
tells the user what went (PRUNE-04) — with the `dependency pruned` member landed across
all ten pinning surfaces.

Purpose: a dependency the cascade pulled in stays on disk forever unless something
removes it; upstream's answer is `--prune`, and this extension mirrors it with the same
"never a plugin you installed yourself, never one something still needs" rule.
Output: `PRUNE_FLAG` on the catalog, `prune?: boolean` on the option seam,
`pruneOrphans` in `domain/dependency-orphans.ts`, the sweep and its member removal body in
`uninstall.ts`, `composePrunedRow` / `composeRemovalBlocks` in `uninstall.messaging.ts`,
three new catalog states, and the closed set at 56 members.
</objective>

  block are in removal order. Within one fixpoint pass the batch is sorted by key, so the

  config wins, as everywhere else.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user command line → multi-record removal | one typed flag now removes records the user did not name |
| third-party manifest → the orphan decision | a plugin author's `dependencies` array decides which records the sweep keeps |
| primary's committed removal → member removals | members run after the primary's artifacts are off disk and before the only save |
