  <action>
Create `docs/dependency-resolution.md` as a user-facing document, written with
the `simple-english` skill in Plain mode and passed through the `humanizer`
skill. Answer, in this order:

1. What a plugin declares. The two accepted element shapes -- a bare string
   optionally carrying a marketplace and a trailing caret range, and an object
   carrying a name plus an optional marketplace, version and sha. State the
   character limits each field is held to and that one unusable element rejects
   the whole declaration rather than half-rendering it.
2. Which marketplace a dependency resolves from. An element that names one
   resolves there; an element that names none resolves from the marketplace of
   the plugin that declared it.
3. What a version constraint may say. The accepted forms the evaluator handles:
   caret, tilde, comparison operators, a union of alternatives, x-ranges and the
   wildcard. State plainly that matching uses the standard semantic-version
   rules, including prerelease precedence.
4. How several declarations for one dependency combine. They intersect: the
   effective constraint is the one that satisfies every declaration. State that
   only declarations from within the same install's own dependency graph count --
   a constraint declared by an unrelated plugin installed earlier never affects a
   new install. State the two project-owned size limits and that an input past
   either one is refused as too complex rather than computed.
5. How a constrained dependency is resolved. When a constraint applies, the
   dependency's source repository tag list is read over the network, and the
   install pins to the tag that satisfies the constraint. Name the tag form the
   resolver looks for. Say directly that this naming convention comes from the
   plugin-release tooling and is not a general git convention, so a source
   repository that does not follow it will report no matching tag -- and that
   this is the expected answer for most third-party sources today, not a defect.
6. What happens to a dependency that is already installed. It is not reinstalled.
   Its recorded version is still checked against the constraint, and a recorded
   version that does not satisfy it is reported as a conflict.
7. Where a dependency lands. The same scope as the plugin that asked for it, and
   the same config file the asking plugin is declared in.
8. Every way a dependency can fail, as a list: no version satisfies the combined
   constraint, no tag satisfies it, an already-installed copy does not satisfy
   it, the declared constraints are contradictory, the constraints are too
   complex to combine, a constraint is not a valid version range, the dependency
   is not in its marketplace, the dependency's marketplace has not been added, or
   the dependency graph contains a cycle. For the unadded-marketplace case, state
   that nothing is added or cloned to satisfy a dependency and that the fix is to
   add that marketplace first.
9. What a failure does to the install. Any failing dependency fails the whole
   install; nothing is left half-installed, and running the same command again
   starts from the same state as the first attempt.

Add one line to `README.md` linking the new document, in the exact form the two
existing documentation links use.

Do not describe behavior the implementation does not have. Every statement must
be checkable against `domain/dependencies.ts`, `domain/dependency-range.ts`, or
a decision recorded in the phase context.
  </action>
