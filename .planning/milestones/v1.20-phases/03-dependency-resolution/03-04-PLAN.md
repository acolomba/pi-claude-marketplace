<objective>
Give the phase live tag resolution: read a dependency's source repository tag
list over the network and pin the install to the tag that satisfies the
intersected constraint.

the only genuinely new capability in the phase -- a many-tags-per-plugin,
pick-one concept the project's one-entry-one-pinned-ref git model has nowhere
else. It is also the phase's one-way decision, so it gets a confirmation gate
before the code lands.

Output: `listRemoteTags` in `platform/git.ts`, and
`orchestrators/plugin/dependency-tag-probe.ts` as the network-legal leaf that
turns a constraint into a pinned tag or a named failure.
</objective>

Export `probeDependencyTags(options): Promise<DependencyTagProbeResult>` with
arms `{ kind: "pinned"; tag: string; oid: string; version: string }`,
`{ kind: "no-matching-tag"; range: string }` and
`{ kind: "tag-listing-failed"; cause: Error; classification: ... }` using the
existing transport classification.

Behavior:
- Derive the query URL with `canonicalCloneUrl` and the credential bundle with
  `buildCloneAuth`, exactly as the clone probe does.
- Consult the memo first. On a successful listing, store it. On a failure, evict
  the key so a retry re-queries rather than caching a transient error.
- Build the candidate prefix from the dependency's plugin name plus the release
  separator. Consider ONLY tags whose short name starts with that prefix; a tag
  without it is never a candidate. This is what keeps the probe from resolving an
  arbitrary unpinned ref.
- Parse the remainder of each candidate name as a version. A remainder that is
  not a valid version is skipped, not an error.
- Keep the candidates whose version satisfies the range, using the satisfaction
  helper from `domain/dependency-range.ts` rather than a second evaluator, and
  select the HIGHEST such version.
- With no surviving candidate, return the no-match arm carrying the range as
  rendered by the bounded rendering helper from `domain/dependency-range.ts`.
  Return that same arm regardless of which repository the query ran against.
  Per D-03-09 this project does not port upstream's softer arm, so there is no
  branch here on whether the source parsed as a git source, and there is no
  fallback to the repository head. State that in the module header as a recorded
  divergence rather than leaving it as an apparent omission.
- A listing throw is caught and returned as the failure arm; nothing escapes as
  an unhandled rejection.
- No credential value is placed on any returned arm. If this module's credential
  handling warrants it, add it to the credential-leak gate's target list and say
  so in the SUMMARY; if not, record the reasoning.

Write `tests/orchestrators/plugin/dependency-tag-probe.test.ts` against a faulted
seam, never the network. Cover: a single satisfying tag pinning to its object id;

marketplace-repository query; a listing throw returning the failure arm rather
than rejecting; the memo serving a second query for the same URL from one
listing call; and a failed query being evicted so the retry calls the seam again.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote git host -> tag advertisement -> probe | Attacker-controllable ref names and object ids cross into the install pin |
| parsed plugin source -> query URL | A manifest-declared source string becomes a network destination |
| host credential bundle -> tag query | Credentials for a private source are used on a new code path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-13 | Tampering | `dependency-tag-probe.ts` candidate selection | high | mitigate | Only tags whose short name begins with the dependency's own plugin name plus the release separator are candidates, and the remainder must parse as a version that satisfies the range. A crafted tag named to look like a satisfying version for a DIFFERENT plugin is never considered, and there is no head fallback for a no-match, so a repository with no valid release tag can never be installed by this path |
| T-03-14 | Tampering | `platform/git.ts` tag query | medium | mitigate | The query is a structured library call taking a URL and a ref prefix, with no shell and no argument vector, so a crafted URL or prefix cannot inject an additional argument. This is also why a git subprocess is not used: the shell-out allow-list is closed and does not include this module |
| T-03-15 | Denial of Service | `dependency-tag-probe.ts` | medium | mitigate | A remote advertising a very large tag list is filtered by prefix before any version parsing, and the per-URL memo bounds one cascade run to one listing per repository. A transport failure is a typed result, so a hanging or failing host fails the dependency rather than the process |
| T-03-16 | Information Disclosure | `dependency-tag-probe.ts` failure arms | high | mitigate | No credential value is placed on any returned arm; the failure arm carries the classified transport cause and the rendered range only. The credential-leak architecture gate scans named files, so this module's membership in that list is decided and recorded in task 3 rather than assumed |
| T-03-17 | Elevation of Privilege | `install-flow.ts` / `install-outcome.ts` network gate | high | mitigate | The probe stays outside the network-free target list and is reached by injection under a field name the gate does not match, so neither install owner gains a git surface. Enforced by the existing architecture test, run in this plan's verification |
| T-03-18 | Spoofing | pinned tag identity | medium | accept | A tag can be moved on the remote between the probe and the clone. The existing clone-cache pin path is what materializes the source and carries the project's existing pinning guarantees; this plan adds no new guarantee there and none is claimed |
</threat_model>
