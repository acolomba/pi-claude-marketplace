<objective>
Wire the range algebra and the tag probe into the cascade, so a dependency that
carries a real version constraint is resolved against it rather than installed
blind.

Purpose: plan 03-01 proved the cascade on the unconstrained path. Plans 03-02 and
03-04 built the two halves of constraint resolution in isolation. This plan is
where RESV-03 actually fires: a constraint either selects a tag, or fails the
dependency with a reason that names the constraint.

Output: a constraint-resolution step in `install-cascade.ts`, sitting between the
closure walk and ledger phase construction, plus the RESV-05 conflict check for
an already-installed dependency.
</objective>

  <action>
Add a constraint-resolution step to `install-cascade.ts` that runs AFTER
`resolveDependencyClosure` returns and BEFORE any `Phase` is constructed. A
constraint failure must therefore never reach rollback, because nothing has been
materialized yet; state that ordering rationale in the module header.

Export `resolveMemberConstraints`, taking the closure members, an optional
injected tag probe, the shared per-URL tag memo, and the source resolution the
cascade already has for each member. For each member in closure order:

1. Intersect `member.ranges` with `intersectDependencyRanges`. An empty
   accumulator yields the wildcard, which means no constraint.
2. If the intersection failed, return the constraint failure immediately,
   mapping the three intersection reasons onto the cascade's own discriminants:
   contradictory declarations become a range conflict carrying a `why`
   discriminant that distinguishes it from the installed-version case in task 2,
   a cap overflow becomes a too-complex failure, and an unparseable declaration
   becomes an invalid-range failure. Every arm carries the member key and the
   rendered constraint from `renderConstraintRange`. Make no tag query on any of
   these arms.
3. If the intersected range is the wildcard, the member resolves with no pin and
   NO tag query is made. This is the common case and it must stay offline; a
   dependency with no declared constraint must not turn a warm install into a
   network operation.
4. Otherwise call the tag probe for that member's source. A pinned result gives
   the member a pinned ref and object id, which the caller's ledger options
   builder then threads into that member's install so it materializes the
   selected tag rather than the ref the marketplace entry names. A no-match
   result becomes the cascade's no-matching-tag failure carrying the member key
   and the rendered constraint. A listing failure becomes the cascade's
   tag-listing failure carrying the classified cause.

Per D-03-09 the no-match arm is identical whichever repository the query ran
against; there is no branch on source shape and no fallback to a repository head.
The probe already enforces this, so do not re-derive the decision here -- just do
not add a branch.

Inject the probe under a field on `InstallCascadeOptions` named for what it does,
never under the identifier the network architecture gate matches as a bare token.
`install-cascade.ts` is not in the network-free target list, but its callers are,
and the reachable-from-there naming discipline is what keeps the arrangement
legible.

Thread ONE tag memo through the whole cascade run so a graph with several
dependencies from the same repository queries it once, and so a failed query is
evicted and retried rather than cached.

Keep each step a small named helper. Both complexity ceilings apply and there are
no threshold overrides in this project; a single function carrying the
intersection, the three failure mappings, the wildcard short-circuit and the
probe call is the shape most likely to exceed one of them.

Extend `tests/orchestrators/plugin/install-cascade.test.ts` with a faulted tag
probe, never the network. Cover: a wildcard member resolving with the probe never
invoked; two declarations of the same dependency in one graph intersecting before
the query; a contradictory pair failing as a conflict with no query made; a
cap-overflow input failing as too complex with no query made; an unparseable
declaration failing as invalid; a satisfiable range pinning the member and the

constraint named; a listing failure surfacing as its own arm; the memo serving a
second member from one listing call; and D-03-10's negative -- a constraint
recorded for an unrelated installed plugin never entering any member's ranges.
  </action>

  <action>
Extend the constraint-resolution step to also walk the closure's
`alreadyInstalled` members. For each, intersect its accumulated ranges the same
way. A wildcard means there is nothing to check and the member is simply left
alone. A real range is tested against the member's RECORDED version from the
state snapshot using `recordedVersionSatisfies`.

A recorded version that satisfies the range means the dependency is left alone,
exactly as RESV-05 requires: not reinstalled, not re-pinned, not re-declared, and
never turned into a ledger phase. A recorded version that does NOT satisfy the
range fails the whole cascade with a range conflict carrying a `why` discriminant
that distinguishes it from task 1's contradictory-declarations case, plus the
member key, the recorded version and the rendered constraint.

Never query tags for an already-installed member. The question being answered is
whether what is already on disk is acceptable, not what could be fetched.

Per D-03-04 do not special-case a recorded version in this project's content-hash
or git-sha form. It goes through the same normalization ladder as any other
candidate. Record in the module comment that the resulting behavior for those
forms is unpredictable by design and that the risk is accepted rather than
guarded, because a guard the upstream mechanism does not have is a divergence of
its own.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| accumulated manifest constraints -> intersection -> network query | Untrusted range text decides whether and where a network query is made |
| recorded install state -> satisfaction check | A recorded version string of this project's own making crosses into a version evaluator |
| selected tag -> member install pin | A remote-chosen object id becomes the source a plugin is materialized from |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-19 | Denial of Service | `resolveMemberConstraints` | high | mitigate | The intersection runs to a verdict before any query, and every failure arm returns without querying. A graph crafted to force many expensive queries is bounded by the per-URL memo and by the intersection's own two size caps, which fail closed before the work they bound |
| T-03-20 | Elevation of Privilege | member re-pinning | high | mitigate | A re-pin can only select a tag that already carries the dependency's own release prefix on the dependency's own declared source repository; the source itself still comes from the marketplace entry the user's added marketplace declares, and is never rewritten by a dependency declaration |
| T-03-21 | Tampering | already-installed member handling | high | mitigate | An already-installed member is never turned into a ledger phase, so no code path can re-materialize, re-pin or re-declare it. An unsatisfied constraint fails the whole install rather than silently upgrading or downgrading a plugin the user installed earlier |
| T-03-22 | Spoofing | constraint failure detail | medium | mitigate | Failure arms carry the member key and the bounded rendered constraint from `renderConstraintRange`, so a maximally-wide synthesized range cannot flood or forge a row, and no filesystem path is placed on an arm |
| T-03-23 | Denial of Service | graph-scoped accumulator | medium | mitigate | D-03-10 keeps the accumulator fed only by this install's own graph, so an unrelated installed plugin cannot make a new install unsatisfiable. Proved by the negative case in task 1 |
| T-03-24 | Tampering | non-version recorded strings | low | accept | D-03-04 accepts, on the record, that coercing a hexadecimal recorded version can yield a misleading version that unpredictably satisfies or fails a range. A guard is deliberately not added because the mechanism is a parity port; the risk is documented in the module comment |
</threat_model>
