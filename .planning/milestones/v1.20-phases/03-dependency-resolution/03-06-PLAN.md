<objective>
Make the cascade legible: one readable row per member, and a failure that names
the dependency and the reason rather than only the plugin the user typed.

Purpose: RESV-06 is a reporting requirement, and RESV-01's own success criterion
asks for a per-entry outcome the user can read. Plans 03-01 and 03-05 built the
result shapes; this plan renders them, amends the closed reason vocabulary
deliberately, and records the byte forms in the output catalog.

Output: new members in the closed reason vocabulary with their pinned-enumeration
amendment and catalog entries, a new `install-cascade.messaging.ts`, and the
`install-flow.ts` composition that emits the cascade block.
</objective>

Decide the minimum set of new reason members the cascade needs, then add exactly
those. Start from the existing vocabulary and reuse before minting: a member
naming an unadded marketplace already exists, so check whether it can carry the

The distinct outcomes needing a reason, from the failure list
`docs/dependency-resolution.md` already states, are: no tag satisfies the
constraint; the declared constraints contradict each other; an already-installed
copy does not satisfy the constraint; the constraints are too complex to combine;
a declared constraint is not a valid range; the dependency graph contains a

marketplace has not been added; and a dependency that was already installed and
therefore left alone. Map each onto an existing member where one fits and mint a
member only where none does.

Word every new member with the style guide, in the same lowercase noun-phrase

most recently added member set.

Per failure arm, the row must carry:
- a constraint failure: the failing dependency key plus the bounded rendered

complete; the two together are what RESV-06 asks for.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| manifest-declared names and ranges -> rendered notification row | Untrusted text is interpolated into a line-oriented output format |
| cascade failure detail -> user-visible reason | Internal detail could carry a path, a URL or a credential fragment |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-25 | Spoofing | `install-cascade.messaging.ts` | high | mitigate | Every name and marketplace in a row came through the declared-dependency token allowlist, which admits no control, bidi, ANSI, whitespace or quote character; every constraint came through the bounded rendering helper. A crafted manifest therefore cannot forge an extra row or displace an existing one. Proved by the exact-byte cases in task 2 |
| T-03-26 | Information Disclosure | cascade failure rows | high | mitigate | Rows carry plugin keys, versions and closed-set reasons only. Absolute paths go through the existing redaction helper and the basename-only discipline; no cascade arm carries a credential, which the tag probe already guarantees at its own boundary |
| T-03-27 | Repudiation | closed reason vocabulary | medium | mitigate | The pinned enumeration gate is amended by equality in the same commit as the members added, each carrying an inline justification and a catalog entry, so vocabulary growth stays deliberate and auditable rather than incidental |
| T-03-28 | Tampering | notification dispatch | medium | mitigate | All cascade output goes through the project's single sanctioned dispatch surface, which is the one place severity, soft-dependency markers and the reload trailer are computed. Two independent gates forbid a second output path from this tier |
</threat_model>
