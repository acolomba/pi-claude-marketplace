  <action>
Create `domain/dependency-range.ts` with the same module-header shape as
`domain/dependencies.ts`: what it computes, why it lives in `domain/` (pure, no
I/O, no clock, no marketplace knowledge), and the decision IDs it implements
(D-03-01, D-03-02.1, D-03-02.3, D-03-04).

Declare three module-scope frozen constants with doc comments:
`MAX_RANGE_INPUT_CHARS` (total characters across all declared ranges, checked
before any parsing), `MAX_RANGE_CONJUNCTS` (the maximum conjunct count), and
`MAX_RENDERED_RANGE_CHARS` (the bound a range gets when it is rendered into a
reason). The doc comments must name all three as PROJECT-OWNED caps chosen for
this implementation. The research logs the upstream conjunct value as inferred
rather than extracted, so the comment must not claim upstream parity on the
number -- only on the mechanism of guarding before the work.

Export `intersectDependencyRanges(ranges: readonly string[]): DependencyRangeIntersection`
returning `{ ok: true; range: string }` or `{ ok: false; reason: "invalid" | "disjoint" | "too-complex"; detail: string }`.

The algorithm, in this order:
1. An empty input array returns `{ ok: true, range: "*" }`.
2. Sum the input lengths; over `MAX_RANGE_INPUT_CHARS`, return `too-complex`
   naming the measured total and the cap. This runs BEFORE any parse.
3. Validate each input with the semver package's range validator; a rejection
   returns `invalid` with the index of the offending input and never the raw
   text of a sibling input. Split each canonical range on the union operator and
   trim, producing one array of conjunct branches per input.
4. Fold left. Before each fold step, compute the PROJECTED product size as the
   accumulator length times the next input's branch count and compare it to
   `MAX_RANGE_CONJUNCTS`; if it exceeds the cap, return `too-complex` naming the
   projected size and which input index it was reached at. Only then allocate the
   product by joining each accumulator branch and each next branch with a single
   space. Also check the FIRST input's own branch count against the cap before
   the fold begins.
5. Filter the folded conjuncts, keeping only those the range validator accepts
   AND for which the semver minimum-version function returns a value. The
   minimum-version test is the whole disjointness detection: a validator accepts
   a conjunct pair that admits no version, so validation alone would let a
   disjoint intersection through as a range that then matches nothing and
   produces a no-matching-tag failure instead of a truthful conflict.
6. An empty survivor set returns `disjoint`. Otherwise rejoin the survivors with
   the union operator, re-validate, and return the canonical range; a rejection
   at that point is also `disjoint`.

Extract each step into its own small named helper -- a size check, a branch
split, a projected-size check, a product step, a survivor filter, and a rejoin.
Both the ESLint `sonarjs/cognitive-complexity: 15` ceiling and fallow's
independently computed `health.maxCognitive: 15` / `maxCyclomatic: 20` /
`maxUnitSize: 60` apply, they disagree on any given function's score, and
`.fallowrc.json` carries zero threshold overrides. A single function carrying the
size guard, the validate loop, the nested product loops, the filter and the
rejoin is the shape most likely to exceed one of them.

Export `recordedVersionSatisfies(recorded: string, range: string): boolean`. It
normalizes with the semver package's strict validator, falling back to the
coercion function's produced version, then tests satisfaction. Per D-03-04, a
recorded version in this project's content-hash or git-sha fallback form runs
through the SAME ladder as any other candidate. The doc comment must state the
accepted risk plainly: coercion on a hexadecimal string can extract a misleading
digit run and yield a version that unpredictably satisfies or fails a range. Do
not add a guard for those forms; a guard upstream does not have is a parity
divergence of its own.

Export `renderConstraintRange(range: string): string`, which bounds a range to
`MAX_RENDERED_RANGE_CHARS` with an explicit truncation marker naming how many
characters were dropped. A maximally-wide cross-product can produce a range far
longer than any notification row should carry, and an intersected range is
synthesized text rather than declared text, so it does not inherit the declared
allowlist's length bound. State that reasoning in the doc comment rather than
leaving it implicit; the character allowlist itself IS inherited, because every
conjunct is assembled from inputs that already passed the declared-version
allowlist plus single spaces and the union operator.

Write `tests/domain/dependency-range.test.ts` as a table-driven matrix. Title
every case with the requirement or decision ID it serves. Cover: the empty and
single-input identities, an overlapping pair, a disjoint pair proved through the
minimum-version filter rather than through validation, an invalid input, both
size caps (input characters and projected conjuncts) with a fixture that would
be expensive to allocate if the guard ran after the product, a union-bearing
input that multiplies branch count, the satisfaction ladder over a plain version,
a prerelease, a coercible non-semver string and an uncoercible one, both of this
project's hash and sha version forms exercised through the unguarded ladder, and
the rendering bound with and without truncation.
  </action>
