<objective>
Read the dependency list from the source that is actually authoritative.

Upstream treats a plugin's `plugin.json` as the truth and the marketplace entry as a
mirror that can go stale — it says so in its own log line, warning that a catalog entry
listing a dependency `plugin.json` does not carry means the catalog may be stale. Reading
the entry alone means reading the source upstream considers the less trustworthy of the
two.

Purpose: D-01-32 reverses the earlier entry-only rule (D-01-18, retired; D-01-19, moot).
It makes `info` the THIRD reader of the same ordered candidate list, which strengthens
rather than weakens the shared-constant decision.

Output: an fs-only, network-free own-manifest read in `info`, with the marketplace entry
as the fallback when the manifest is not readable, and a cross-reader gate that now covers
all three readers over one planted tree.

**Relationship to plan 01-02.** That plan owns the parse and the render, complete and
permanent. This plan changes only WHERE the raw value comes from. Neither is a first cut
at the other.

**The phase tracer lives in plan 01-01.** This is an expansion plan.
</objective>

Add two module-private helpers to `orchestrators/plugin/info.ts`.

`resolveInfoPluginRootFsOnly` takes the marketplace root, the already-parsed source, and
the block's `locations`, and returns the plugin root or `undefined`. Three arms:

- A path source delegates to the existing `derivePluginRootForInfo`. **Catch
  `PathContainmentError` here and return `undefined`.** This is load-bearing: today that
  function is only reached from inside `buildNonInstallablePathRowFields`, whose ROW-level
  callers wrap it; calling it at block level would introduce a throw path past those
  wrappers. A containment failure means the manifest is not readable, which is exactly the
  condition D-01-32's fallback covers.
- A git source (use the existing `isGitSource` narrowing) goes through
  `makePresenceProbe(locations)`, which is already imported in this file and is the
  fs-only probe. Return the plugin root ONLY on the `materialized` arm; `not-cached`,
  `escapes` and `missing-subdir` all yield `undefined`.
- Any other source kind yields `undefined`.

**Never reach for the materializing probe here, not even when `--fetch` was passed.**
D-01-32 states that readable never means fetching, NFR-5 forbids `info` touching the
network, and `orchestrators/plugin/info.ts` is one of the files
`tests/architecture/no-orchestrator-network.test.ts` pins by name. The consequence is
worth stating in the doc comment: on a cold `--fetch` run the dependency list comes from
the entry even though the row builders materialize a clone moments later.

`readOwnManifestDependencies` takes a plugin root and returns a discriminated result —
readable, carrying the raw `dependencies` value as `unknown`; or not-readable. Walk
`MANIFEST_CANDIDATES` imported from `../../domain/manifest-path.ts`, joined against the
plugin root, following this file's own tolerant-read contract rather than adding a third
stat-first loop: an `ENOENT` or `ENOTDIR` errno means the candidate is absent, so
`continue` to the next one; any other failure — including a `JSON.parse` throw or a
non-object parse result — means the candidate is present and unusable, so STOP and return
not-readable. That is D-01-07's absence-only fall-through expressed through the errno
contract instead of a stat.

State the reasoning in the doc comment, because it deliberately differs from the version
reader's stat gate: on this surface absence and present-but-unusable produce the SAME
user-visible outcome (the entry's list renders either way), so the cheaper errno form
costs nothing here, whereas the version reader must distinguish them and therefore stats.
Copy `readLenientHooksFile`'s doc-comment shape and include its
`NFR-5: reads <path> only, no network` sentence — that sentence is load-bearing
documentation for the architecture gate's reviewer. Read the raw `dependencies` value off
the parsed object through the `as Record<string, unknown>` widening this file already uses.

At the call site inside `buildBlock`, move the `parsedSource` computation ABOVE the
dependency value so it is available, then: derive the fs-only plugin root, read the own
manifest when a root came back, and feed `renderDependencyList` the manifest's
`dependencies` value when the read reported readable, or
`(entry as Record<string, unknown>).dependencies` when it did not. **A readable manifest
is authoritative even when it declares nothing** — do not fall back to the entry on an
absent `dependencies` key, only on a not-readable manifest. Keep the second argument to
`renderDependencyList` as the declaring `marketplace` value already in scope.

Emit NO warning when the entry and the manifest disagree. Upstream logs one; we render
the authoritative source and stay silent (D-01-32).

Document the scoped exception in the same doc comment: warm/cold render symmetry is

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| marketplace clone / plugin tree → `info` | a second untrusted file is opened on a read-only surface that is contractually network-free |
| derived plugin root → filesystem read | the path is composed from a marketplace root and an author-supplied source string |
