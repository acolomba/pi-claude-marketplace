## Scope and limits

This is a code-only audit of the Pi host notification text generated by the
phase. There is no phase UI-SPEC, CSS, component library, or browser surface to
inspect. Visual rendering, color, typography, and spacing are owned by the Pi
host and are therefore **unassessed**, rather than penalized for a capability
this extension does not implement. Pending live `ui5` and `ui-theme-designer`
installation confirmations are UAT work and are not passed by this review.

## Detailed Findings

### Pillar 1: Copywriting (4/4)

**PASS.** The public copy is derived from typed payloads instead of ad-hoc action
labels: `notification-dispatch.ts:29-57` describes the single structured
boundary, and `notification-grammar.ts:892` owns the per-plugin grammar. The
phase’s new `dependencies:` line is parsed by
`orchestrators/plugin/info.ts:420-443`, rendered in a documented address-plus-
constraint form, and catalogued in
`docs/output-catalog.md:1834-1836`. This follows the messaging guide’s rule
that callers construct payloads and the renderer makes wording decisions
(`docs/messaging-style-guide.md:7-11`). No generic browser-style labels apply to
this terminal interface.

### Pillar 2: Visuals (unassessed)

The extension defines semantic glyphs in
`shared/notification-grammar.ts:35-79`, including distinct installed, remote,
disabled, partially available, and unavailable symbols. That establishes a
clear semantic hierarchy in code, but no host-rendered terminal capture was
available to verify legibility, clipping, Unicode fallback, or focal hierarchy.

### Pillar 3: Color (unassessed)

The extension passes only the host severity vocabulary through
`shared/notification-dispatch.ts:34-36` and `platform/pi-api.ts:127`; it has no
CSS, Tailwind tokens, hard-coded RGB/hex values, or theme control. A 60/30/10
color audit therefore has no implementation surface here.

### Pillar 4: Typography (unassessed)

`shared/notification-grammar.ts:101-145` implements text wrapping and a
66-column content width for descriptions, but font family, size, weight, and
line-height are selected by Pi’s terminal host. The missing host capture means
these properties cannot be scored.

### Pillar 5: Spacing (unassessed)

The terminal grammar uses structural indentation and blank-line composition:
the messaging guide specifies marketplace headers at column 0 and plugin rows
at two spaces (`docs/messaging-style-guide.md:79-88`), while
`shared/notification-dispatch.ts:63-72` preserves the blank line between a
usage error and its usage block. This is sound text structure, but screen-space
spacing and wrapping at real host widths remain unverified.

### Pillar 6: Experience Design (4/4 after repairs)

The initial audit scored this pillar 1/4 because CR-03 produced stale dependency
information and CR-04 let a wrong info read pass the agreement gate. Both
findings are now closed at the code level.

`readManifestCandidate` in `orchestrators/plugin/info.ts` checks file kind
before opening bytes. Non-files, ENOENT and ENOTDIR permit the next candidate;
other failures end the walk. The production Node reader supplies the same
regular-file classification used by the other manifest readers.

The refusal fixtures now give the forbidden bare manifest an invalid
dependency declaration. If info incorrectly selects it, the public output
changes to `invalid manifest` with unresolved components. The four-case
negative control in `/tmp/phase1-cr04-negative.log` proves the assertions
observe that change while resolver state and version remain unchanged.

`01-REVIEW-FIX.md` records 177 focused passes after restoration, 100% direct
info coverage and a green full check with 6,124 unit and 32 integration tests.
No temporary production mutation remains. The repaired code preserves the
catalogued notification grammar; there are no remaining code-level UI
findings from this audit. The score assesses that code evidence only, not
live Pi-host rendering or human approval of the logic change.
