<objective>
Stop `info` from throwing away the dependency declarations it can already see.

`normalizeDependencies` filters the array to `typeof d === "string"`, which drops every
object-shaped `{name, version, marketplace}` entry — the shape upstream documents as the
primary use case — and drops a bare string's trailing version range along with it. What
survives renders as a bare address with no constraint at all.

Purpose: DEPS-01 and DEPS-02 are the display half of this phase. A dependency the user
cannot see is one they cannot act on, and a constraint silently discarded is the exact
defect the milestone exists to close.

Output: a pure, reusable dependency-element parser in `domain/`, an `info` render that
lists every usable element with its constraint, and the byte form recorded as a
catalogued output state.

**Relationship to plan 01-04.** This plan owns the PARSE and RENDER of the dependency
list, complete and permanent. Plan 01-04 changes WHERE the raw value is read from
(D-01-32) and changes nothing this plan builds. Neither is a first cut at the other.
</objective>

<planner_derived_extension>
**Constraint fields get the same positive-allowlist treatment as the name.** D-01-25
locks a positive allowlist for `name` and `marketplace` and states the output-forgery
vector closes as a side effect. That claim holds for those two fields only: `version`
and `sha` also render verbatim into a line-oriented notification row, so a newline or
ANSI escape inside either forges a row.

D-01-25 bars `assertSafeName` and bars a control-character DENYLIST. It does not bar
extending its own chosen mechanism, so this plan applies a POSITIVE allowlist to the
constraint fields too, and folds a failure into D-01-05 exactly as D-01-25 folds a bad
name:

- `version` must match `^[A-Za-z0-9.\-+*~^<>=| ]+$` — every semver range form upstream
  accepts (`^1.0.0`, `~1.2`, `>=1.0.0 <2.0.0`, `1.x`, `*`, `1.0.0-beta.1`,
  `1.0.0 || 2.0.0`) passes; no control character, newline, escape, quote, bidi mark or
  `@` does.
- `sha` must match `^[0-9a-fA-F]{7,40}$`, which is also exactly what D-01-30's
  short-form-to-7 rendering assumes.

**One usability rule, stated once:** a field that is ABSENT was not declared and is
simply not rendered. A field that is PRESENT but unrenderable — any non-string value, or
a string failing its allowlist — makes the whole element unusable and the element is
dropped silently. This is what keeps the prohibition intact: nothing is ever
half-rendered with a constraint quietly removed.

Recorded here rather than applied silently. This is carried as threat T-01-03.
RATIFIED as **D-01-33** in `01-CONTEXT.md` after this plan was written; that
decision also corrects D-01-25's original claim that the forgery vector closed
for all fields. Implement to D-01-33 — it and this block agree.
</planner_derived_extension>

<upstream_scope_note>
**D-01-29: the byte form is ours to define, and upstream's failure handling is not copied.**
Upstream renders no dependency list anywhere — no info view lists them, and dependency
names reach the user only inside error and status text. So this line has no upstream
counterpart to match byte-for-byte, which is why D-01-22's catalog state is a closed-set
amendment of OUR contract rather than a parity exercise.

Upstream's failure handling is also asymmetric in a way worth knowing and NOT worth
copying: a bad dependency in `plugin.json` throws and kills the whole plugin load, while a
bad one in a marketplace entry degrades or is dropped with a warn log. This surface is
read-only and takes neither behavior — an unusable element is dropped silently per
D-01-05, and nothing on this path throws.
</upstream_scope_note>
