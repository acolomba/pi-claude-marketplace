  <action>
Record and prove the clear-on-lift contract, which is mostly already true in the
tree and needs to be made deliberate rather than accidental.

The reconcile enable bucket flows through `applyPluginToggles` into
`setPluginEnabled`, whose enable branch reaches the install ledger's state
phase. That phase REBUILDS the plugin record as a fresh object literal naming
every field it means to preserve, rather than spreading the existing record. A
field the literal never names is therefore dropped on every enable, install and
re-materialization. The correct implementation of the clear is deliberate
omission: do NOT add the marker to that literal. Add a comment there recording
that the omission is load-bearing and naming what it implements, so a future
reader who "fixes" the literal by adding the missing field does not silently
break the lift. Do the same at the equivalent literal in
`reinstall-record.ts`.

This is the whole of the clear. Do not add a separate clearing step to the apply
path, and do not clear speculatively: the clear must happen exactly when the
enable is actually applied.

Note the deliberate asymmetry and comment it: `clonePluginRecord` was taught in
plan 06-01 to PRESERVE the marker, and `toDisabledRecord` preserves it by
spreading. That is correct and is not in tension with the omission above. The
clone is a snapshot used to restore a record after a failed operation, so losing
the marker there would let a restore produce a record that reads as a user's own
disable; the disabled-record producer preserves it so an ordinary user disable
over an already-marked record does not erase it. Only the paths that genuinely
re-materialize the plugin drop it, and those are exactly the paths where the
plugin is live again.

In `plan.ts`, confirm the three-term enable gate handles the lift without any
further edit: once the live verdict no longer names the record, the predicate
stops excluding it and the ordinary enable-bucket logic fires because the config
says enabled and the record is recorded-but-disabled. Add a test proving the
lift rather than relying on inspection. If the gate as plan 06-01 left it does
NOT produce the lift, fix it here — but fix it by correcting the predicate's
inputs, never by reading the stored marker in place of the live verdict.

Add the case that keeps the already-held record out of BOTH buckets. A record
already disabled and already marked, whose dependency is still unsatisfied, is
in its terminal state: bucketing it for enable would oscillate, and bucketing it
for dependency-disable again would make the apply step re-perform a no-op write
and would break the silence contract on an unchanged tree. Prove that with an
explicit assertion on both buckets.

Add the case that protects the user's own choice. A record disabled with no
marker must never be lifted by the check even when its dependency is satisfied,
because the check may only lift a transition it performed itself. This is what
D-06-02's stamp-only-at-the-transition rule buys, and it is the assertion that
catches a regression in it.

Do not edit `enable-disable.ts`. It is outside this phase's boundary. A manual
enable on a still-unsatisfied record leaves the marker stale alongside an enabled
record, and the next reconcile pass self-corrects either way — clearing the
marker if the dependency is now satisfied, or re-disabling and re-stamping if it
is not — so no defensive code is needed here. Record that as a boundary note in
the summary, not as a deferred bug.
  </action>
