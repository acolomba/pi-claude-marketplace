  <action>
Rewrite the prose so it describes the behaviour that now exists. Write both
documents in the register they already use: short sentences, active voice, plain
words, addressed to a user rather than to a maintainer. Apply the plain-English
skill in its default mode and the humanizer skill, which the project's own
guidelines name for prose work.

In `docs/dependency-resolution.md`, replace the section on removing a plugin
other plugins need. Its current text tells the user the uninstall is refused,
names the retired row, and tells them to uninstall the dependents first or to
prune. All of that is now wrong. Say instead that the uninstall proceeds, that
the row names the plugins that still declared it, and that each of those is
reported at the next load with a remedy. Keep the worked example of pruning the
dependent, since `--prune` is unchanged, but reframe it as one option among
several rather than as the way to clear a refusal.

Delete the sentence contrasting Claude Code's documented refusal for `disable`
with this extension applying it to `uninstall`. That contrast is exactly what
this phase removed, and it is named directly by the phase's own retirement
decision and by the roadmap's success criterion. Delete the reload paragraph's
claim that a reload refuses the same removal and reports the same row every time
until the configuration is fixed; a reload now removes the plugin and reports the
consequence.

Keep the fail-closed paragraph and correct its subject. An unreadable declarer
still refuses the uninstall, that is still deliberate, and the four cases in
which a declaration cannot be read are unchanged, as is the repair advice. What
changes is only the surrounding claim about what happens when the declarations
CAN be read and a dependent is found.

Add a section for the load-time check. LOAD-01 and LOAD-02 have no prose home
today, and this document is where a user looks for dependency behaviour. Cover:
that every reload re-checks what each installed plugin declares; the three
conditions that make a declaration unsatisfied, which are the dependency not
installed, the dependency disabled, and the dependency's recorded version outside
the declared range; that the dependent is disabled rather than left loading as if
nothing were wrong; that the row says which condition it hit and the cause line
names the remedy with both plugins in it; that the disable is a consequence
rather than a choice the user made, so it is not written into the configuration
file; that a reload does not flip the plugin back and forth; that satisfying the
dependency lifts the disable without the user editing anything; and that a broken
dependency propagates to everything that transitively depended on it in a single
reload. Quote the three remedy shapes exactly as the catalog publishes them,
since the catalog's bytes are gated and this prose is not.

Leave the pruning section alone. `--prune` semantics are unchanged, and the
roadmap says so explicitly.

In `docs/plugin-enablement.md`, correct the two claims this phase falsified. The
precedence table's reconcile row states that the planner never sees the manifest
side and that its only enablement inputs are the configuration value and the
record's own flag. A third input now joins them: the live dependency-satisfaction
verdict, computed before the planner runs and handed to it as data. Say so, and
say that the planner stays free of any read of its own — the verdict arrives
precomputed, which is why the planner's purity gate still holds. The section on
where the state lives states that no persisted field was added on either side.
One was: an optional marker on the installation record recording that the record
is currently held down by the check. Describe it as what it is — a boolean
re-derived on every pass, answering only whether the check is currently holding
the record down, never why — and say that it is deliberately not mirrored into
the configuration, because the configuration carries only what the user asked
for.

Leave the divergence about a plugin required by another active plugin not being
enabled on its behalf exactly as it is. That divergence is about the `enable`
command writing a value on an author's behalf, which belongs to a later phase,
and this phase does not touch the enablement owner.

Do not edit the affirmative note recording that this document is not byte-gated,
except to keep it true. It is the reason these edits need reading rather than a
test run.

Do not touch the documentation item the handoff groups with tag resolution; the
research settled that it belongs to the next phase, not this one.

Format Markdown with the project's Markdown formatter through the pre-commit
pipeline, never with the JavaScript formatter — the format check covers only
JavaScript, JSON and TypeScript, so running the wrong formatter over these files
produces a diff the project does not want.
  </action>
