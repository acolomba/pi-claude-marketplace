# Quick Task 260913-r2h

Make a FIFO state-harness over-read fail loudly instead of hanging.

## Recommendation

**Do it.** The candidate design in the request is not needed — a strictly simpler one-branch
change closes the limitation completely, and I measured it this session rather than reasoning
about it. The whole mechanism is *one* decision inside the existing spare-creation loop: make the
**last** spare a regular file holding a sentinel instead of a FIFO. No probe, no `O_NONBLOCK`, no
ENXIO, no timer in the harness, no polling, no new failure mode. The blast radius is the three
assertions the request named, and each one gets strictly stronger.

## Problem

`tests/orchestrators/plugin/state-fifo.ts:27-29` records its own remaining limitation: an
orchestrator that reads more times than there are payloads parks in `open(O_RDONLY)` until the
test's 60 s timeout, because the server has already exited and nothing is left to report it. A
regression that makes reinstall read three times where two are expected therefore costs a minute
of wall clock and produces no diagnosis.

Confirmed this session against today's harness shape `[VERIFIED: probe, this session]`:

```
current design, over-read after 2002ms: STILL BLOCKED
```

The process could not even exit; the pending `open` held the event loop open until the external
timeout killed it (exit 124).

## The design — one branch, measured, not reasoned

The serve loop pre-creates one spare per payload and, for payload `k`, opens `fifoPath`, renames
`spares[k]` over `fifoPath` (retiring the paired inode while still holding it open for write),
writes, closes. After the last iteration `fifoPath` holds `spares[N-1]`: today a fresh FIFO that no
writer will ever open.

**Change exactly that one object.** Create `spares[0..N-2]` with `mkfifo` as now, and create
`spares[N-1]` as a regular file whose content is the over-read sentinel. Nothing else in the loop
moves.

Why this is sufficient and why the request's Branch B is unreachable: the final `rename` installs
the sentinel at the state path **at the same instant** it retires the last paired inode. There is
no moment after the last payload at which `fifoPath` is a FIFO with no writer coming, so a reader
can never park there in the first place. "Reader already parked when the server finishes" and
"reader arrives after the server finishes" collapse into one case — an `open` on a regular file,
which returns immediately.

Measured `[VERIFIED: probe, this session]`:

### Why the two-branch candidate is refused

- **Branch B (the single non-blocking `O_WRONLY` probe) has nothing left to catch.** Its premise is
  a reader parked on a never-served FIFO; under the change above that object never exists.
- **It reintroduces a refuted hazard for no gain.** `260913-n7w-RESEARCH.md` section 3 measured the
  bare open+close probe as destructive (hands a parked reader an empty payload, `Unexpected end of
  JSON input`, 17/100 under load). Writing the sentinel before closing would probably avoid the
  empty payload, but "probably" is exactly the reasoning that shipped the last bug, and the probe
  buys zero coverage here.
- **It carries a race the one-branch design does not have.** In the proposed ordering a reader that
  opens between the ENXIO probe failing and the sentinel rename landing parks on an inode that the
  rename then makes nameless — unreachable forever. Narrow, but real, and avoidable by not having
  the window.

### The sentinel

```
OVER-READ: the FIFO state harness had no payload left for this read\n
```

It is deliberately not JSON and deliberately front-loads its own name, because V8 quotes only the
first ten characters of the input in its parse error and those ten characters are exactly
`OVER-READ:`. `loadState` (`persistence/state-io.ts:394-399`) does not swallow a parse failure — it
throws `state.json at <path> is not valid JSON: <V8 message>` — so the production reader a real
regression actually hits fails immediately with the token in the message.

## Verified during planning — do not re-derive

- `rename` of a regular file over a FIFO path succeeds while the server still holds that FIFO inode
  open for write, and the paired reader still receives its payload in full. This is the one load-
  bearing mechanic of the change and it is probe-confirmed above.
- A clean run still leaves exactly `['state.json']`. The spare count is unchanged (N spares for N
  payloads, all consumed), so the existing no-litter assertion at
  `state-fifo-pairing.test.ts:64-68` needs no edit.
- `loadState(extensionRoot)` reads `<extensionRoot>/state.json` and throws on non-JSON; only
  `ENOENT` maps to the default empty state (`state-io.ts:381-399`). The sentinel cannot be silently
  absorbed.
- Architecture gates routinely import production modules (`config-state-consistency.test.ts:31-33`,
  `integration-materialization-gate.test.ts:7`), so the new gate may import `loadState` directly.
  `gate-targets.test.ts` polices its own registry, not arbitrary literals in sibling gates.
- `stat` stays in use after the edit in `reinstall-flow.test.ts` and `uninstall.test.ts` (other call
  sites remain), but `state-fifo-pairing.test.ts:63` is its **only** use there, so that import
  member must be dropped or `noUnusedLocals` fails.
- `node --test --test-name-pattern "removed between scope resolution and enumeration"
  tests/orchestrators/plugin/reinstall-flow.test.ts` selects the soak's unit of work
  (`reinstall-flow.test.ts:4932`).
- The harness is already imported by both orchestrator tests (`uninstall.test.ts:44-49`,
  `reinstall-flow.test.ts:~77-82`), so the sentinel joins an existing import block.
