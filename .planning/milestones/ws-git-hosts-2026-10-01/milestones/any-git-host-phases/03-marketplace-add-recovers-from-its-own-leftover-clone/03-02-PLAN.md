## Flagged assumption carried from the edge probe (MA-14, unclassified)

The spec-less probe returned `category: unclassified` for MA-14 with no predicate
(`"unclassified — review manually"`). It is recorded here as an explicit assumption rather than
auto-resolved with a backstop or dropped (see 03-01-PLAN.md § edge_coverage_resolution for the
whole-set accounting).

**Assumption:** MA-14's edge surface is exhausted by the leak-versus-no-leak pair on the pre-rename
`cleanupStaging` call, plus the double-fault case where the leftover removal and the staging removal
both leak on one add. That is what this plan asserts.

**What it does not cover:** a removal that reports success while leaving something behind (a child
mount point, an open file handle on Windows, an immutable-flagged entry). `cleanupStaging` returns
`undefined` for such a case because `fs.rm` did not throw, so the add would proceed to
`mkdir` + `rename` and the rename would fail with its own error, which lands in the existing MA-9
catch rather than in the MA-14 path. No case here covers that shape, and none is added: it is a
platform-specific partial-removal mode with no reproducible fixture on this host. Recorded so a later
reader sees a bounded claim rather than an exhaustive one.
</flagged_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a leftover `.git/config` origin string → the removal decision | Same boundary plan 01 opened. This plan's job is to exercise the refusing side of it, which is where a widened match rule would show up as data loss. |
| a thrown error → the rendered notification | MA-14 routes a leak through `appendLeakToError` into a user-visible message. The message must carry a path and a filesystem error and nothing else. |
| a failed add → the persisted state file | A partially-removed destination must not be recorded. The state file is read by every later command, so an entry naming an unreachable path would mislead `list`, `info`, `update` and `remove`. |
