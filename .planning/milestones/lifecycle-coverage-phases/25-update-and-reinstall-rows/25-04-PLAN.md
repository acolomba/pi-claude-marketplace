Design (recorded so every task builds the same thing):

- The D-12 rule lives in one function, `update-row.ts::revisionVersionSlot`,
  which takes whatever revisions a producer knows (`fromVersion?`,
  `toVersion?`, `fromCommit?`, `toCommit?`) and returns the row's version
  fields: nothing when it knows no version; `version` alone when it knows one
  side, or when both sides are the same revision (same version, and the same
  commit or none on both); `version` (the to side) plus `from` when the
  revision moved, plus `commits` from Plan 03's `revisionCommits` when D-05
  holds. A commit present on one side only counts as a move (the D-16-09
  revision rule the preflight already uses) but shows no commits (D-07). An
  empty-string version never produces a version slot or an arrow.
- The candidate report: `ThreePhaseArgsBase` gains
  `readonly onCandidate?: (move: RevisionMove) => void`. `materializeLatestVersion`
  calls it once, with the preflight's revisions, after the preflight derived a
  candidate and before `swapPluginUpdate` runs; it is never called for a verdict
  the preflight returns. A caller keeps the report in a holder it creates per
  target, so a failure the swap throws can name the revisions without wrapping
  the error: wrapping would add a link to every cause chain the features pin.
  This is how D-12's "after the candidate was derived (swap phase 3, intent
  mark, finalize)" reaches the thrown failures; staging failures before the
  intent mark are after the candidate too, and get the arrow by the same rule.
- `update-swap.ts` exports `preflightMove(preflight): RevisionMove` (fold Plan
  03's file-private commit helper into it), used by the `updated` literal, by
  `composePhase3FailureOutcome`, and by the runner's report, so D-06's two
  shas are read in one place.
