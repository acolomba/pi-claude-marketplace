<objective>
Move `reinstall` onto the shared runner Plan 01 built, so it installs and
reports the latest version the scope knows about (REI-04) through the same code
path as `update` (UPR-01). That is upstream's behavior too: Claude Code has no
reinstall verb, and its install always takes the catalog's current version, so
no divergence is introduced (D-18-01).

Task 1 first makes the shared gate fail closed on an unreadable dependency
walk, for both verbs, with the row naming the true cause (D-18-17), so the
reinstall rewire inherits the final gate. The rewire runs reinstall with
`overwrite: true`, which keeps RINST-01's repair overwrite on the shared path
(D-18-15, through the knob Plan 01 added).

This plan is the expand half of an expand/contract change. The pre-commit hook
gates every commit on fallow, so the old replacement machinery
(`reinstall-replace.ts` and the bridge functions only it calls) cannot be
deleted in the same commit that stops using it without dragging ~30 more files
into one task. Here `createReinstallPlugin` keeps its `ReinstallTransaction`
parameter for one plan, and the rewired flow reads only its
`runPostSuccessMaintenance` member; Plan 04 deletes the rest.

Tests of the deleted behavior and tests whose expectations change are deleted
here and re-added, rewritten to the new semantics, by Plans 05, 06, and 07 (the
re-add lists live there). Only the tests the new code needs for its 100% direct
coverage are rebased in this plan.

Output: the rewired `reinstall-flow.ts`, `reinstallOutcomeFromRun`, the outcome
and messaging shape the shared runner needs, the gate updates, and a green tree.
</objective>

Facts the planning prototype measured (they decide several test edits below):

- The shared runner runs the dependency-constraint gate, whose declaration walk
  reads the manifest entry of EVERY recorded plugin in the scope. The prototype
  measured today's gate holding the operation `{dependents constrain}` at the
  first record it cannot read; after Task 1 it fails the operation
  `(failed) {unreadable}` naming that record (D-18-17). Either way, a fixture
  that records a plugin under a marketplace with no readable manifest, or one
  its manifest no longer declares, stops every reinstall in that scope, and the
  fixture must make that record readable unless the case is about it.
- In direct mode the swap carries only the DISCOVERY half of the staging
  warnings (skills, commands, workflows) on the outcome's `notes`; the agents
  and MCP HYGIENE half is dropped, exactly as for a direct `update`. Reinstall's
  `notes` therefore become discovery + maintenance warnings.
- The swap stages before its intent mark takes the lock, so a reinstall under a
  held lock now leaves the empty `skills-staging/` and `commands-staging/`
  parent directories behind (their per-run contents are aborted), as an update
  does.
- Reinstall's policy sets `overwrite: true`, so the swap's agents commit
  replaces the plugin's own previous agent files a user edited, as RINST-01
  requires (D-18-15); `update` keeps refusing them. A file that no index row

  verbs. The prototype predates the overwrite knob, so it measured the three
  RINST-01 cases failing; with the knob they are expected to pass unedited.
- An invalid GitHub base override now fails a reinstall of a GitHub-source
  plugin even on a warm cache: the shared probe builds the auth bundle before it
  reads the cache (GHB-03, adopted for reinstall by D-18-16).
