## For the orchestrator

- **D-04 interpretation (add row name).** D-04 says "For `add`, the row names the marketplace
  the add would have created." The add takes the scope lock before it reads a manifest or clones
  (`runAddInGuard`), and the duplicate check needs the locked state. So under a held lock the add
  cannot know which marketplace it would have created, or whether it would have created one.
  This plan names the row by the typed source. That is the subject ATTR-07 A2 (`addSubjectName`)
  gives every add failure before the manifest read, the one add.feature calls "named as typed".
  Naming a path source by its manifest `name` instead would need a manifest read outside the
  lock, and a git source cannot be named without a clone. If the user meant the manifest name,
  that is a follow-up change to `handleAddFailure`.
- The add row's JSON id is `<source>@<source>`, the synthetic `<marketplace>@<marketplace>`
  shape that D-04 asks for through `marketplaceFailureRows`. ADD-10 gives a failed add's
  fetched-URL child row the source alone as its id. ROWID-01 in BACKLOG.md already tracks the
  plugin-shaped id of marketplace-level failure rows.
- Orchestrated side effects, both aligned with D-01: reconcile's `mp-add-failed` row for a
  lock-held add now says `lock held` instead of `unparseable`, and an orchestrated lock-held
  remove returns a typed failed outcome that reconcile renders as before.
  `test/integration/marketplace-layer-remove.test.ts` pinned the old rejection and is updated in
  Task 1.
- The CHANGELOG entry for these user-visible results belongs to the milestone PR (AGENTS.md).
