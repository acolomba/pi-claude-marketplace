<objective>
Write the enablement contract down, reconciled against what SHIPPED, and make
it findable.

Two divergences need one citable home. The first is the requirement's own
subject: Claude Code writes an explicit enablement value for a plugin another
active plugin requires, and this extension cannot, because it never resolves a
plugin's dependency declarations. The second arrived a phase ago and has been
living in a decision ID that archives with its phase directory: the pre-install
claim is read from the marketplace entry alone.

The trap here is specific and was caught before it shipped. The phrasing both
the roadmap and the requirement currently use for the dependency gap is FALSE
against the shipped code — the declarations are parsed and surfaced on the info
surface; what is missing is that nothing is ever done with them. Writing the
false version into a contract document would manufacture exactly the class of
requirement-contradicts-implementation drift this phase exists to close, in the
document whose job is to close it.

Purpose: after this plan, a reader who wants to know what decides whether a
plugin is enabled has one document to read, reachable from both READMEs, whose
claims are transcribed from shipped sources, and whose stated limits are legible
as limits rather than as oversights.

Output: one new contract document, two README bullets, two corrected
requirement statements, and one corrected roadmap criterion.
</objective>

  sentence-case titles — not IDs, not questions.

  schema-accepted opaquely on both declaration sites; the single consumer is the
  info surface, which filters the array to its string-shaped elements, sorts
  them and renders them. They are never resolved, never auto-installed, never
  consulted for enablement, and no code path anywhere writes an explicit enabled
  value on behalf of a dependent plugin. That statement supports the divergence
  in full and is true.

  RESEARCH.md carries the two override clauses verbatim from a live fetch of the
  upstream plugins reference, including the detail the in-repo record lacked:
  the write happens at install OR ENABLE time, not install only.

  rows and coverage counts stay exactly as they are.

  must, before any source comment can honestly cite it as the home of the

  sweep accurate rather than a lateral move.
