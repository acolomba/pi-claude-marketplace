<objective>
Close the two named catalog gaps, and nothing else.

The reinstall surface gained a row a phase ago — a plugin whose record is
already disabled is skipped rather than silently re-enabled — and that row has
no documented state. On this project the catalog is not descriptive prose: it
carries a runner that renders every documented state from a fixture and compares
bytes in both directions. A row absent from the catalog is a row nothing guards
at the contract level, which is why the gap is closed in this phase rather than
swept up later.

The second gap is an asymmetry. Both not-installed candidate row families gained
the same optional field in the same change, and only one of the two had its
token-reference cell updated. A reader scanning the table currently sees the
pre-install token documented for one family and not the other.

Purpose: the gate walks forward and backward. A documented state with no fixture
fails; a fixture with no documented state fails. That symmetry is why the block
and its fixture are one task — separating them produces a commit that is red by
construction.

Output: one block-and-fixture pair, and one amended table cell.
</objective>

## Settled design calls (do NOT re-litigate at execution time)

- **Exactly TWO gaps, named by CONTEXT.** The reinstall skip row's missing
  state, and the un-updated token-reference cell. Do not re-audit the catalog;
  it was reconciled one phase ago.

- **Document the BULK form.** The standalone form would render bytes identical
  to the update surface's existing disabled-refresh block, because the tally
  composer returns empty for a single-cardinality message. The bulk form is the
  one that teaches something new.

- **Two rows in the fixture, not three.** One reinstalled row and one skipped
  row are enough to teach both facts — that the skip rides alongside a live row,
  and that the tally counts it as a success. A third row would bury the point.

- **Reuse the section's own register.** The reinstall section's blocks use one
  canonical marketplace name and scope and a small canonical set of plugin
  names. A reader diffing two adjacent blocks should see only the delta that
  matters.

- **The renderer is the contract.** The authored bytes are a prediction; the
  runner is the check. Where they disagree, correct the block — unless the
  render also contradicts the behavioral case that already pins the standalone
  row's bytes, which would make it a renderer finding to surface rather than a
  block to adjust.

- **Cite requirement-level IDs only.** The heading's parenthesized ID list and
  any new prose clause use durable requirement IDs. A later plan in this phase
  is removing the archiving phase-scoped decision IDs from this very file;
  adding a new one here would be self-defeating.

- **UNRESOLVED planner assumption, carried forward deliberately.** The
  edge-shape probe over `DOC-01` returned a single `unclassified` row — no
  boundary, adjacency, ordering, emptiness, idempotency or concurrency question
  fits a requirement whose subject is "a document is amended for a token and its
  emitters". It is recorded here as unresolved rather than dismissed. The
  practical consequence for execution is nil: the requirement's checkable
  content is the block-and-fixture pairing, which the runner gates in both
  directions. If a reviewer can name a shape question this requirement should
  answer, it belongs in the verification record, not invented here.

- **Beware the identifier collision in the tally citation.** The catalog's
  existing tally sentences cite an output requirement ID from an EARLIER
  milestone whose namespace overlaps this milestone's freshly-minted output
  requirement IDs. Reuse the catalog's own existing tally citation verbatim
  where a tally sentence is needed; do not substitute a same-shaped ID from this
  milestone, and do not "harmonize" the existing ones.
