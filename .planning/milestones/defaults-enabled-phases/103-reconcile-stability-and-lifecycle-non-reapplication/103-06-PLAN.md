<objective>
Close the third and last call site of one defect.

Phase 102's review fixed the install's cross-file READ: `readDeclaredEnabled`
(`install.ts:1442`) consults both physical config files, so a user's explicit
value wins wherever it lives. The WRITE half of the same asymmetry survived —
the standalone batched patch at `:1699` still goes to `targetConfigPath`,
derived at `:1553` from `opts.local` alone.

The consequence is not a mis-filed key. A user who hand-writes `"foo@mp": {}`
into `claude-plugins.local.json` and runs `/claude:plugin install foo@mp` with
no flag gets the read right (the merged view says `enabled` absent, so the
plugin lands disabled) and the stamp wrong (it goes to the base file). CFG-02
shadows that stamp wholesale, the merged entry still reads `enabled` absent,
`isDeclaredEnabled` answers true, and `plan.ts:338` pushes an enable on every
reload — forever. That is this phase's success criterion 1, false, through the
standalone-install door.

The fix is one call site, because plan `103-04` already built the helper. What
this plan adds beyond the wiring is the proof that the loop is CLOSED rather
than relocated: the regression asserts through the merged view, and then runs a
reload that must plan nothing.

Purpose: `install`, `enable` and `disable` are the three verbs that author an
ENABLEMENT declaration on the user's behalf. The same conflation — "which file
did the user name" with "which file does the declaration live in" — sits at all
three, so this is one defect and not three coincidences. After this plan the
three agree, and D-103-13's claim that the fix is what makes `install` and
`enable` agree about where a declaration lives becomes true rather than
aspirational.

The sweep is NOT exhaustive, and the plan says so rather than implying
otherwise: `maybeWritePluginConfigBack` (`orchestrators/plugin/shared.ts:815-822`,
on the `update` and `reinstall` post-success paths) still derives its target from
the flag alone. It is deliberately out of scope and benign — its patch carries no
field, so the merged view never moves and no enable is ever planned — and it is
recorded as a backlog candidate in plan `103-05`'s SUMMARY rather than left for
someone to find.
Output: one wiring change, one identity-derived label, one corrected
precedence-table row, and five test cases.

## Settled design calls (do NOT re-litigate at execution time)

- **DS-1 — the helper is CONSUMED, not re-derived.** Plan `103-04` creates
  `selectDeclaringConfigWriteTarget` in `orchestrators/plugin/shared.ts`, which
  `install.ts` already imports from. Call it; do not write a second selection
  with the same rule. The whole point of the three call sites agreeing is that
  they read one decision. `103-04`'s reading of the flag carries over unchanged:
  a typed `--local` targets the local file, no flag follows the declaration,
  neither yields the base file.

- **DS-2 — `targetIsLocal` is derived from the SELECTED path, never from
  `opts.local`.** This is the trap in this change and it is not obvious.
  `readDeclaredEnabled` (`install.ts:1463-1474`) uses `targetIsLocal` to decide
  which of `current` / sibling is the local file, and then picks the ENTRY by
  that identity before reading `enabled`. If the selector flips the target to
  local while `opts.local` is false, passing the caller's flag comparison as the
  label marks the local config as base and the base config as local — inverting
  which physical entry answers the precedence question. Derive it as an
  explicit named const
  comparing the selected path to `locations.configLocalJsonPath`, the same
  accessor the selector returned it from, and comment why the identity
  comparison is the right question. Task 2 carries the case that fails if this
  is got wrong.

- **DS-3 — the CR-02 marketplace adoption rides the same target, deliberately.**
  `writeBatchedConfigEntries` writes the adopted marketplace declaration and the
  plugin entry in ONE atomic save (CR-02, protected as a settled call in plan
  `102-01`). When the target flips to the local file, an adopted marketplace
  declaration follows it there. That arm only fires when the marketplace is
  declared in NEITHER physical file (the membership gate reads base ∪ local), so
  there is no file to contradict; splitting the write to aim the marketplace at
  the base file would break the single-atomic-save property to solve a problem
  that does not arise. Record it in the SUMMARY as a deliberate consequence.

- **DS-4 — the orchestrated (reconcile) path is provably unchanged, and that is
  an argument rather than a hope.** Reconcile passes
  `local: op.configSource === "local"`. When `configSource` is `"local"` the flag
  arm fires and the target is the local file, exactly as today. When it is
  `"base"`, CFG-02 guarantees the key is NOT in the local file — a local entry
  would have made the merged source `"local"` — so the membership probe returns
  the base file, exactly as today. There is no third case. Task 3 pins it with a
  test rather than leaving it to the argument.

- **DS-5 — the common install is untouched.** A plugin key declared in neither
  file (every fresh `/claude:plugin install`) probes local, finds nothing, and
  targets the base file. That is today's behavior and it is the overwhelming
  majority of installs, which is what bounds this change's blast radius.
