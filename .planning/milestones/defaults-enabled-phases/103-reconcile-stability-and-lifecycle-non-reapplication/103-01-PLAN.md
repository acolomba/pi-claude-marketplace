Prove DFEN-06 where the roadmap says it must be proven: against the reconcile
planner's own output, over the bytes a real install wrote, three reloads deep,
for both physical config files.

Phase 102 closed the loop — the install stamps `enabled: false` into the file
the declaration lives in, so the merged view the planner reads no longer says
"absent". This plan asserts the consequence: the planner plans nothing, the
apply path does nothing, and neither changes on the second or the third pass.

Purpose: the hazard this milestone exists to close is an unattended reload
re-enabling a plugin whose author declared it off. `acc.enable.push(...)` at
`orchestrators/reconcile/plan.ts:338` is the one line that would do it. A test
asserting the install boundary cannot see that line at all; only a planner
assertion can, and only a real multi-pass run can prove the apply path agrees.
Output: one planner-level cell plus its counter-case, and two end-to-end
three-pass fixtures — base-declared and local-declared — each ending with a
`planReconcile` call over state and config re-read from disk.

No production file is touched by this plan. If an assertion fails, the
implementation is wrong and the assertion is right.

## Settled design calls (do NOT re-litigate at execution time)

- **The seven buckets are asserted as one whole-plan equality, not seven
  lengths.** `emptyReconcilePlan(scope)` returns exactly the `ReconcilePlan`
  shape with every array empty (`orchestrators/reconcile/types.ts:222-233`), and
  `planReconcile` returns that shape through a fast path when every count is
  zero (`plan.ts:426-436`), so `assert.deepEqual(plan, emptyReconcilePlan(scope))`
  IS the "absent from all seven" claim D-103-06 asks for. The tree already uses
  this idiom (`plan.test.ts:112`, `:241`, `:268`, `:418`, `:441`, `:495-496`).
  The per-bucket negatives by plugin identifier are kept ALONGSIDE it, exactly
  as `plan.test.ts:498-510` does, so a future change that populated two buckets
  cannot pass by deep-equalling some other empty-ish shape.

- **The three passes are a loop, not three copy-pasted blocks.**
  `sonarjs/cognitive-complexity` and `@stylistic/padding-line-between-statements`
  both apply to test files, and three near-identical blocks would also invite
  `sonarjs/no-identical-functions`. One `for` over the pass numbers, with the
  pass number interpolated into each assertion message, is cheaper on every axis
  and reads as the fixed-point claim it is.

- **No cache-invalidation step is budgeted anywhere in this plan.** The manifest
  cache is content-addressed on `(mtimeMs, size)` (`domain/manifest-cache.ts`),
  and nothing in this plan rewrites a manifest between calls. `dropMarketplaceCache`
  is a DIFFERENT cache (tab completion) and must not appear here.

- **The existing DFEN-04 second-pass block stays.** Its own comment
  (`apply.test.ts:1978-1981`) says it deliberately stops short of the planner
  question and defers it to DFEN-06. This plan answers that question in new
  cases; it does not delete or weaken the block that deferred it.
