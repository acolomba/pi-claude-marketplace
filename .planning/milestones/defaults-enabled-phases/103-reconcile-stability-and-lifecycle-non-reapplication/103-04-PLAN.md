<objective>
Make `enable` and `disable` write where the declaration lives.

Today they pick the physical config file from the user's `--local` flag alone.
For a plugin declared only in `claude-plugins.local.json`, a plain
`/claude:plugin enable foo@mp` therefore writes `enabled: true` into the BASE
file — where CFG-02's wholesale per-key replacement means the merged view never
sees it. The verb reports success, the record flips, and the next unattended
reload reads the local file's `enabled: false`, plans a disable, and undoes the
user's explicit command.

That is the same silent reversal this milestone exists to close, pointed the
other way, and criterion 4 is false for locally-declared plugins until it is
fixed. Phase 102 solved the identical problem for the reconcile-driven install
by threading the planner's `configSource`; a standalone `enable` has no planner
provenance to read, so it must ask the files.

Purpose: the config file is the user's record of their own intent. A verb whose
write lands where nothing reads it makes that record untrustworthy in the worst
way — not by writing something wrong, but by appearing to write something right.
Output: one declaration-aware selector beside the flag-only one, one wiring
change inside the existing lock, and the converse half of criterion 4 proven end
to end on both declaration sites.

This changes a shipped verb for ALL locally-declared plugins, not only the ones
this milestone is about. It is planned as its own reviewable unit for exactly
that reason.
</objective>

## Settled design calls (do NOT re-litigate at execution time)

- **DS-1 — `--local` still wins.** D-103-13's sentence ("select their config
  write target from where the declaration lives, not from the user's `--local`
  flag") describes the defect, which is an `enable` WITHOUT the flag. Dropping
  the flag entirely would make `--local` meaningless for these two verbs and
  break the documented WB-01 / UAT-05 contract that the flag targets the local
  file unconditionally, including creating it fresh on ENOENT. The rule
  implemented here is: an explicit flag targets the local file; absent the flag,
  follow the declaration; absent both a flag and a declaration, the base file,
  which is today's behavior. This is a stated interpretation, not a silent one —
  the SUMMARY must repeat it.

- **DS-2 — a NEW helper beside `selectConfigWriteTarget`, which stays.**
  `install.ts` also calls the flag-only selector (`install.ts:1553`) and this
  plan does not touch the install path. Wrap rather than replace: the new
  helper delegates to the existing one for the flag arm, so the `--local`
  semantics have exactly one definition. `orchestrators/plugin/shared.ts` is not
  a ledger module, so no `import-x/no-cycle` or D-11 directed-edge concern
  arises from the new call — `enable-disable.ts` already imports from it.

- **DS-3 — the selection moves INSIDE the lock.** It now READS a config file,
  and the file's whole WB-01 discipline is that sibling reads happen fresh
  inside the lock the write also holds. `configBasename` is the only value that
  escapes the closure (it feeds the CFG-03 abort row's basename, T-53-02-02), so
  declare it as a `let` initialized to the base file's basename and reassign it
  as the closure's first act. `targetConfigPath` and `siblingConfigPath` are
  used only inside the closure and stay `const` there.

- **DS-4 — the local file is inspected for KEY MEMBERSHIP, never for its
  value.** The question is "where does this declaration live", not "what does it
  say". A local entry replaces the base entry wholesale (CFG-02), so a local key
  that exists — even as a bare `{}` — is the effective declaration and is the
  file to write. Reading `enabled` here would reintroduce the precedence
  question this verb already answered upstream at `enable-disable.ts:552-595`.

- **DS-5 — an absent or invalid local file means "not declared locally".**
  Mirrors the D-18 merge fallback and the `absent` / `invalid` handling in
  `install.ts`'s cross-file declaration read. It must not throw and must not
  create the file.
