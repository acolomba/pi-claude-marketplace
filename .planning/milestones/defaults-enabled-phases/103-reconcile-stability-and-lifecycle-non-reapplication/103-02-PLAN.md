<objective>
Pin DFEN-07 for `update` twice over: once at the source, where a future edit
would introduce the read, and once at the behavior, where a user would feel it.

Both files are clean today — a grep for either token over `update.ts` and
`reinstall.ts` returns nothing. That is the point. This is a characterization
phase, and the two halves fail at different times: the gate fails at the moment
someone types the identifier, the behavioral test fails at the moment that
identifier changes an outcome.

Purpose: `defaultEnabled` is third-party content. A plugin author who could flip
it in a release and thereby flip every existing user's enablement would make the
field a remote switch over code that is already installed. The guarantee that
stops that is negative — these verbs never look — and a negative guarantee needs
a gate, because there is no behavior to observe until it is already broken.
Output: one new architecture gate built on the shared scanning helper, and one
`update` case driven by a mid-flight manifest flip with a version-bump control.

Neither task touches a production file.
</objective>

## Flagged assumptions

- **The version bump is a sufficient control.** It was observed working (the
  research's probe B returned the moved version alongside the unmoved
  enablement), and the cache mechanism that makes it work is documented in
  `manifest-cache.ts`. If a future fixture makes a version bump inconvenient, a
  direct `loadMarketplaceManifest(manifestPath)` read asserting the flipped
  entry is the cheaper second control. Not used here, because the version
  movement is already a record-level fact this case asserts anyway.

- **The gate's mutation check is manual and uncommitted.** There is no way to
  assert "this gate would fail" from inside the gate without a fixture file that
  deliberately contains the forbidden token, which would then need its own
  exclusion from every other scanning gate. The manual check plus the SUMMARY
  record is the honest cost.
