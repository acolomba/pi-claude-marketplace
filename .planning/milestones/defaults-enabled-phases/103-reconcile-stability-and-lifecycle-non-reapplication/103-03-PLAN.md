<objective>
Close the one live hole in the phase's goal sentence. Today a `reinstall` of an
install-disabled plugin re-materializes its artifacts, flips its record to
enabled, renders `(reinstalled)` over a config that still says `enabled: false`,
and lets the next reload quietly put it back. Nothing there reads
`defaultEnabled`, so criterion 3 is untouched — but "nothing re-enables it
behind the user's back, not a `reinstall`" is false until this lands.

`update` already has the branch. `reinstall` never grew one:
`updateStateRecord` writes `enabled: true` unconditionally and the file has no
disabled-record arm at all. This plan gives `reinstall` the counterpart branch,
sited at the same predicate, and then pins DFEN-07 for the verb over a record it
no longer disturbs.

Purpose: a repair verb that changes enablement is a repair verb the user cannot
run safely. The divergence it opens is transient — one reload converges it —
but the row is untruthful while it lasts, and a user who reinstalls a disabled
plugin to fix a broken skill has no reason to expect their disable to be spent.
Output: one short-circuit, one closed-set narrowing arm, one amended comment at
the caller that works around the defect today, and three test cases.

This is a bug fix to a shipped verb. It is planned as its own reviewable unit so
it can be reverted on its own.
</objective>

## Settled design calls (do NOT re-litigate at execution time)

- **DS-1 — the arm returns BEFORE the resolve, and refreshes nothing.**
  D-103-12 says mirror `update.ts:1860-1872`, and the mirror is the GUARD, not
  the body. `update`'s disabled arm exists to re-pin (ENBL-09: version,
  `resolvedSource`, `resolvedSha`, `compatibility`) because moving the pin is
  what `update` is for. `reinstall` preserves the recorded version by contract
  (D-68-02) and carries the recorded `resolvedSha` forward (PURL-07), so there
  is no pin for it to move and nothing a re-resolve could truthfully write. The
  arm therefore sits immediately after the existing `oldRecord === undefined`
  guard in `runLockedReinstall`, before `loadCachedEntry` and
  `resolveInstallable`, and returns a `skipped` outcome. Consequences worth
  stating: no clone materialization on a cache miss, no `tx.save()`, no config
  write-back, no `updatedAt` bump, and therefore no `state.json` mtime churn.

- **DS-2 — the skip note reaches the row through the existing narrowing, not
  through a new outcome field.** `ReinstallSkippedOutcome` carries `notes`, not
  `reasons` (`orchestrators/types.ts:76-79`), and both reinstall surfaces map
  `notes` to the closed set through `narrowReason` (standalone at `:311`, bulk
  at `:959`). Adding an exact-match arm there — beside the existing `up-to-date`
  and `already installed` arms — covers both surfaces with one edit. Widening
  the outcome type to carry `reasons` on the skipped partition is a bigger,
  unnecessary change.

- **DS-3 — no new closed-set member and no catalog amendment in this plan.**
  `already disabled` is an existing `REASONS` member and an existing
  `IDEMPOTENT_REASONS` member, so `skipSeverity` already routes it to `info` and
  no `notify.ts` / `notify-reasons.ts` / `compat-01` / `notify-closed-set-locks`
  edit is implied. `docs/output-catalog.md` gains no block here: the catalog is
  a curated set with a byte-equality runner over what it documents, not a
  totality gate over every producible row, and the milestone's catalog work is
  owned by DOC-01 in a later phase. Record the new reinstall row in the SUMMARY
  as a catalog candidate so that phase inherits it rather than rediscovering it.

- **DS-4 — the caller-side filter STAYS.** `orchestrators/reconcile/apply.ts:1158`
  already refuses to backfill a disabled record, and its comment (`:1150-1157`)
  says why: reinstall's "record write sets `enabled: true` unconditionally". The
  filter is correct on its own terms (a disabled plugin should not be promoted)
  and remains the right behavior, so it is not removed. But its stated
  justification becomes false with this change, and a comment asserting a
  falsehood is worse than no comment. Amend the rationale; keep the guard. This
  is also the fact that bounds the blast radius: the only other in-tree caller
  of `reinstallPlugin` already never passes it a disabled record, so the change
  is visible on the user-invoked verb and nowhere else.
