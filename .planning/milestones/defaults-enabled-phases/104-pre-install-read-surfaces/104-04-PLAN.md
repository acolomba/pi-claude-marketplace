<objective>
Prove the two claims the rendered rows cannot prove about themselves: that
nothing was fetched to produce them, and that nothing was read that should not
have been.

Both are negative guarantees, and negative guarantees fail quietly. A row that
says `{installs disabled}` looks identical whether it came from the marketplace
entry the cached manifest already held or from a plugin manifest inside a clone
someone quietly materialized to read it. The difference is invisible in the
bytes and decisive for the requirement.

Purpose: the surfaces' offline promise is the reason the entry-only rule exists.
If a later change reads a plugin's own manifest on a warm clone — which is
tempting, because it would make these surfaces agree with what `install` reads —
the same plugin starts rendering differently depending on whether a clone happens
to be warm, and closing THAT gap the other way needs a fetch. The warm-clone case
in this plan is the tripwire on that whole path, and it is the highest-value test
of the phase.

Output: two corrected offline guards, two warm-clone declining cases, one
render-map live-field guard file, and — deliberately — no repair of the hollow
guard sitting next to one of them.
</objective>

## Settled design calls (do NOT re-litigate at execution time)

- **The pre-existing offline guard in the list suite is defective, and it stays.**
  It probes for a directory by attempting a file-content read of it, which throws
  for an existing directory just as it does for a missing one, so its boolean is
  false unconditionally; and it runs BEFORE the orchestrator call it means to
  constrain, so even a working check would describe the pre-state. Both faults
  were reproduced during research. It is pre-existing and out of this phase's
  scope under the surgical-changes rule, and it is captured in the backlog. Do
  NOT repair it, do NOT delete it, and do NOT copy its shape.

- **The corrected shape.** Probe path existence with a metadata call, place the
  probe AFTER the orchestrator's await, and assert that the not-found branch is
  the one taken — so a passing test is evidence about what the render did rather
  than about what the fixture started as.

- **Criterion 4 is a DECLINING case, not a gap.** The expected outcome is a bare
  row. Write the test so its title and comment both say that this is the correct
  answer and why: the entry is readable for every plugin regardless of clone
  state, so sourcing from it alone is what makes a plugin render identically warm
  and cold. Reading the warm clone would buy agreement with the install path at
  the cost of that uniformity, and the only way to restore uniformity after that
  would be a fetch the requirement forbids.

- **The list-side warm-mirror helper gets a ONE-ARGUMENT widening, not a second
  helper.** It currently hard-codes the plugin manifest object it writes. Make
  that an optional parameter defaulted to today's value so every existing caller
  is unmoved. A near-identical second helper would be flagged by the
  duplicate-function lint rule anyway. The info-side helper already takes the
  object and needs no change.

- **The render-map guard is a NEW file, modeled on the existing live-field guard
  for the sibling shape.** That file exists precisely because an optional field on
  a shared shape type-checks when an arm passes nothing in its place, renders
  identical bytes for every producer that stamps nothing, and silently drops the
  brace for any producer that does. This phase adds two more optional fields to
  two more shared shapes, so it inherits the same regression class and gets the
  same kind of guard.
