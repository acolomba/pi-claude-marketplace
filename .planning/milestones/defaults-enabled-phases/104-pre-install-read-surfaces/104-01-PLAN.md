## Settled design calls (do NOT re-litigate at execution time)

These are locked by the phase CONTEXT or resolved by the orchestrator before
planning. They are inputs, not open questions.

- **D-104-01 — the marketplace entry is the ONLY source these two read surfaces
  consult.** They never read a plugin's own manifest, not even where a warm clone
  makes it readable with no network at all. The entry is the one source readable
  for EVERY plugin regardless of clone state, which is what lets an unfetched
  `(remote)` row carry the claim, and it makes the same plugin render identically
  warm and cold. Where the entry is silent, the surfaces DECLINE to claim. That
  declining is the correct answer, not a gap; the deliberate divergence from what
  `install` reads is recorded as a contract divergence by the following phase.

- **D-104-01 (silence rule) — only a literal `false` claims.** `true`, absent, an
  explicitly-`undefined` property and a non-boolean all count as silent. This
  mirrors the value-test discipline of the module-private precedence function the
  new predicate sits above, so the read surfaces and the install path agree on
  what counts as a declaration. No malformed-manifest reason is introduced.

- **D-104-02 — reuse the EXISTING `installs disabled` reason token.** No new token
  is minted. The rejected alternative was a future-tense token following the
  deferred-action precedent; it costs a no-expansion-gate amendment, a catalog
  row and a fixture to restate a fact the existing token already states, and it
  would make the read surface and the install surface speak two vocabularies for
  one fact.

- **D-104-03 — the token rides `(available)`, `(remote)` and
  `(partially-available)` rows only.** `(unavailable)` is excluded: nothing will
  install at all there, so the claim would be about an install that cannot
  happen, and that row's brace already carries why. Every installed-record row —
  `installed`, `disabled`, `partially-installed`, `partially-installed-upgradable`,
  `upgradable`, `partially-upgradable`, `failed` — is untouched, which is how
  the "an installed plugin's row never acquires the token" criterion is satisfied:
  by not editing those arms, not by adding a guard.

- **The barrel is NOT touched.** `domain/index.ts` deliberately omits the sibling
  leaf predicates from `version.ts`, and both consumers already import from the
  module path directly. Add the new symbol to the two existing import statements.

- **The predicate is named `entryDeclaresInstallDisabled`.** The conventions doc
  lists `is*` / `classify*` / `looksLike*` as illustrative predicate prefixes, not
  as a gate. This name reads correctly at both call sites, and its first token
  names the SOURCE, which is the load-bearing fact of D-104-01. Record that
  reasoning in its doc comment so a reviewer does not re-open it.

- **Amending the two charter comments is REQUIRED work, not tidying.** Both
  currently assert what this change falsifies. A comment that contradicts the code
  is how a settled decision gets re-litigated two phases later.
