<objective>
Author the single COMPAT-01 no-expansion contract gate: one architecture test file holding every
structural clause of the milestone's promise that it introduced no manifest snapshot, orphan
field, state-schema migration, status token, reason token, glyph, or new network path.

D-98-08 fixes the pin shape: ENUMERATION EQUALITY against hand-written literal member lists, not
count-only pins and not a snapshot file. The existing closed-set gate already pins counts; this
gate pins membership and must not duplicate the counts.

D-98-09 fixes the home: one new file in `tests/architecture/` that DELEGATES the network clause
to the existing orchestrator-network gate rather than duplicating it. Delegation is real, not
narrative — the shared scanning code moves into a non-test helper module both gates import. A
test module must never be imported by another test module: the built-in runner re-registers the
imported file's top-level cases, doubling the run and misreporting the count.

D-98-10 fixes the mechanic: any source-scanning assertion reads files through the Node filesystem
API. Two premises resolved at research time and recorded here so nobody re-litigates them at
execution: (1) the requirement's justification for that rule is historical — the hook-dedup
separator in the plugin info orchestrator is written as an escape sequence with an inline comment
explaining why, so that file is ordinary text today; the RULE stands, the workaround does not, and
no task should be written to handle an unreadable source file. (2) The typebox runtime shape the
schema clauses need was confirmed against the working tree: the state schema's version property
exposes an `anyOf` array of literal-carrying members, so reading their literal values works
directly and the fallback of asserting validator behavior is not needed.

Purpose: this gate is the single audit surface for the milestone's no-expansion promise, and it
must pin the POST-carrier sets (D-98-05), which is why it lands after the four carriers.
Output: one helper module, one gate file, one refactored existing gate, one test-only schema export.

Tracer exemption: this plan produces a verification gate, not product behavior. A tracer slice
would be one clause of the gate, which is exactly what Task 2 already is — a vertical slice
through the gate would restate it with no new information.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-98-10 | Tampering | source scanning inside the gate | medium | mitigate | Every read goes through the Node filesystem promises API in the shared helper; the acceptance criteria negative-grep for subprocess APIs, because a line-tool subprocess can classify a file unreadable and skip it silently, greening the gate on an unchecked file (D-98-10) |
| T-98-11 | Repudiation | enumeration pins | high | mitigate | Hand-written literal member lists, never derived from the constant under test, plus a mandatory mutation check that proves the gate goes red when a member is added — a gate that cannot fail is false assurance, which is worse than no gate |
| T-98-12 | Tampering | exporting the install-record schema | low | accept | A test-only widening of an existing module-private constant; no new write path, no runtime behavior change, and the schema remains the single validation boundary |
| T-98-13 | Denial of service | gate execution under concurrent test runs | low | mitigate | The gate writes nothing, spawns nothing, and changes no process-global state; the acceptance criteria assert this by negative-grep |
| T-98-SC | Tampering | npm/pip/cargo installs | low | accept | This phase runs no package-manager install task; RESEARCH.md records the Package Legitimacy Audit as "Not applicable" |
