<objective>
Finish INFO-11 by reconstructing the hook inventory from the materialized hooks
config, and make every failure shape of that read visible without letting any of
them take the block down.

Purpose: four of the five component kinds are already in the installation
record. Hooks are not — the record holds only a slug, and the entries live in a
file the extension itself wrote. Reading it is the one disk access the state-only
arm makes, so it carries the one containment obligation and the one degradation
story. D-96-03 splits that story honestly: no recorded hooks means no line, while
recorded hooks that cannot be listed means no line PLUS a marker, so silence
never masquerades as a verified absence.

Output: two file-private functions' worth of change in `info.ts` (one new reader,
one wiring line in the existing composer), the degradation matrix in the
orchestrator suite, and two more byte-gated catalog states.

Requirement mapping: INFO-11 hooks reconstruction and containment (Task 1),
INFO-11 degradation matrix and traversal refusal (Task 2), the user contract for
both (Task 3).

Design decision recorded here, per the discretion D-96-03 grants: the degradation
marker is an EXISTING closed-set reason stamped at row level — `narrowProbeError(err)`
for a throw, the literal `"unparseable"` for a parse failure — with the hooks line
omitted. Two alternatives were considered and rejected: (i) a synthetic lenient
hook entry rendering `      (unreadable)` under a `hooks:` header, which abuses
the `event` field to carry a status; (ii) a new `malformed hooks` token, which is
a four-place closed-set amendment (`REASONS` in `notify.ts`, a topic group in
`notify-reasons.ts`, the `REASONS.length === 38` assertion, the catalog reference
table) plus a DOC-08 ripple, for no gain in truthfulness. Attribution is
unambiguous because the hooks config is the arm's only disk read, and the catalog
prose says so.
</objective>

<assumption_delta_decision>
## Assumption delta: add-alongside

The assumption detector fired on "fallback". Decision: **add-alongside**. The
hooks reconstruction here reads the materialized configuration the install ledger
wrote; it does not replace, unify with, or fall back to the manifest-backed arm's
resolver-driven hooks read (`readHookSummaryEntries` / `readLenientHookSummary`),
which stays exactly as it is. The two readers coexist and are documented as
distinct fidelity levels. "Installation record" stays the identity anchor.

What would force a later promote: a milestone that makes `info` derive hooks
record-first on every arm, which would collapse the three readers into one.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `state.json` → path composition | `resources.hooks[i]` is a state-supplied slug used as a path component. A corrupted or tampered record can carry a traversal slug. |
