## Planner decisions (Claude's Discretion, recorded for review)

These fill the per-field gaps D-04 leaves, by the rule "emit what the text
form shows, no more" (CONTEXT, orchestrator follow-ups):

1. Cascade rows carry no `dependencies`. The text form never shows a row's
   soft-dependency list; it shows only the composed `{requires ...}` markers,
   which are already in `reasons`. `ResolvedRow` therefore keeps omitting
   `dependencies`. Plugin-info rows (04-03) do emit their `dependencies`,
   because that text line shows them.
2. Install-scoped means every status whose model row declares `scope`: the 15
   statuses other than available, remote, unavailable, and
   partially-available. Those four catalogue rows carry no scope (research
   FEATURES TS-10); the block carries it.
3. Failure detail mirrors the model's `SerializedCauseChain`: a row carries
   `cause: { causeChain, truncated }` when resolve serialized one, and
   `leaks` and `rollbackPartial` arrays whenever resolve set a failure.
   Rollback entries carry `{ phase, cause? }`.
4. `tally` mirrors the resolved model: `{ label, failures, warnings,
   success?: { count, verb? } }`, all counts integers. The label is what the
   text tally shows.
5. The plugin tool's `details` key becomes `marketplaces` (wire blocks holding
   wire rows) instead of a flat `plugins` list. Flattening would lose the
   block scope that tells two same-named marketplaces in different scopes
   apart for catalogue rows, which carry no scope of their own.
