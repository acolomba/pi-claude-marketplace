<objective>
Give the two reachable, uncontrolled direct-coverage verdicts the planting controls D-117-21 names.

Purpose: the direct-coverage assertion has four distinguishable outcomes and exactly ONE of them has
a control today — the zero-record arm. The other two that a real run can produce have none:

- the shortfall verdict, which is the verdict the whole unreachable-branch pin regime rests on. Every
  pinned shortfall in the broken-windows ledger is a match against a message no control has ever
  proven the assertion emits;
- the ambiguity verdict, which fires when two coverage records claim the same source. That is the
  concrete ambiguity COV-02 names, and research measured it reachable and already guarded but
  uncontrolled.

Research also measured why the existing control can only reach the zero-record arm: the assertion's
injectable root threads to the type-only escape alone, while coverage-record path resolution goes
through the module-level root. Pointing the synthetic record at a real in-repo path sidesteps that
entirely, so no gate script changes — which matters, because a gate edited by the same run that
controls it is not controlled.

Output: a control that plants four states where it planted one.
</objective>

Read the gate script in full first, especially the assertion's four outcome paths and where its
injectable root is and is not threaded. That asymmetry is the whole mechanic of this task.

Extend `scripts/test-coverage-direct.negative.mjs`, keeping its existing two plants exactly as they
are, and following its own shape: build a state, assert the outcome, move on. Add ONE small helper
that builds a synthetic coverage text for a chosen source path and chosen per-counter found and hit
numbers, and drive four states through it.

Build the coverage text so its source field names a REAL in-repo production module by absolute path,
and call the assertion WITHOUT a fixture root. That is the measured workaround: the injectable root
reaches only the type-only escape, so a record pointed at a fixture tree is rejected as outside the
project before any verdict can be reached. Choose a source that is not one of the type-only modules,
so no state can slip into the type-only escape and pass unconditionally.

The four states, in this order:

1. **Complete.** One record, hit equal to found on all three counters. Assert the assertion RETURNS
   a summary string rather than throwing, and assert the string's content. This state is not
   decoration: without it a malformed synthetic text would parse to zero records, both throwing states
   would fire on the wrong arm, and the control would pass having measured nothing. This is the same
   family as the rule that a brute-force zero means nothing until the detector is shown to fire.
2. **Shortfall.** The same record with one counter's hit below its found. Assert the throw and match
   the verdict on the phrase that names an incomplete direct-coverage result for a source, together
   with the deficient counter's numbers. Match loosely on the numbers — never pin an absolute branch
   pair — but pin the SHAPE: the verdict names the source path and reports the deficient counter as
   hit over found.
3. **Ambiguity.** The same complete record emitted twice for the same source. Assert the throw and
   match the verdict on the phrase that names more than one coverage record for a source, together
   with the count.
4. **Mapping refusals, through the command itself.** Spawn the gate script as a subprocess twice:
   once with a path outside the repository, once with a path under the test root that is not a
   corresponding test file — the relocated boundary helper is exactly such a path and is a better
   choice than an invented one, because it is a file that really exists and really cannot be mapped.
   Assert a non-zero exit and the refusal text in each case. Neither needs a script change and neither
   is reachable through the exported assertion, which is why they are driven through the command.

Do not add a fifth state for path-level ambiguity. It is unreachable under the current one-to-one name
mapping; inventing a check for it would be a gate that cannot fire, which is a defect this repository
has already shipped once. The invariant that answers COV-02's remaining half — that the mapping is
injective over the whole inventory — belongs to 117-11 and is not written here.

Name in the summary the fail-closed arms this plan does NOT control, and why: D-117-09 bars a
repo-wide audit of pre-existing controls, so the remaining arms are reported rather than swept. List
them explicitly so the omission is a decision on the record rather than an oversight.

Run the extended control. Then plant the control itself: temporarily relax one verdict in the gate
script so a planted state would pass, confirm the control turns RED, and restore the gate byte for
byte from a copy taken beforehand. That is what separates a control from a fixture that happens to
agree. Record verbatim what each plant printed — write no predicted message anywhere. A plant that
stays GREEN is a finding: narrow or strengthen the claim and report it.

Note that `scripts/` is covered by neither the ESLint target nor the prettier glob nor the fallow file
pattern, so nothing formats or lints this file for you. Match the surrounding style by hand.

Change no production file, no test file, and no gate script — the gate plant is reverted before the
commit and the verify block proves it.
