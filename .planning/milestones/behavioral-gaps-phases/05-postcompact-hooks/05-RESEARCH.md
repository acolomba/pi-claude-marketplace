#### Upstream evidence (claude-code-compat-research)

The phase touches the upstream contract (hook translation), so each material question has an evidence record. Binary: Claude Code 2.1.319 at `/home/linuxbrew/.linuxbrew/Caskroom/claude-code@latest/2.1.319/claude`, read on 2026-11-08 with a Node byte search (the grepped functions are named by their minified names, which change per release). Docs: `https://code.claude.com/docs/en/hooks`, read on 2026-11-08.

1. **Payload.** Claude Code sends the common fields plus `hook_event_name: "PostCompact"`, `trigger` (`"manual"` or `"auto"`), and `compact_summary`, "the conversation summary generated by the compact operation" (binary schema `hook_event_name:T("PostCompact"),trigger:B(["manual","auto"]),compact_summary:o()`; docs "PostCompact input" with the example JSON). The product's `translatePostCompact` already sends exactly these. High confidence.
2. **Trigger.** A `/compact` runs PostCompact with `manual` (binary: `P8t(r.session,{trigger:"manual",...})` on the manual and partial paths). The proactive auto-compaction runs it with `S?"auto":"manual"` where `S` is the auto flag, and the reactive compaction after a prompt-too-long error runs it with `trigger:"auto"` (binary: `qZo({trigger:"auto",...})` feeding `wno`). So Pi's `threshold` and `overflow` both map to `auto`, as `compact-trigger.ts` does (D-CF5-04). High confidence.
3. **Matcher.** The match query of a PostCompact hook is the trigger (binary `matchQuery:n.trigger`; the docs' matcher table lists `manual` and `auto`). High confidence.
4. **Order.** On the full, reactive, and replacement paths, SessionStart(`compact`) hooks (`lPe(...)`, `hookResults`) run before PostCompact (`P8t`), except the precomputed replacement path `hrs`, which runs PostCompact first and passes an empty `compact_summary`. Pi has no such path. D-CF5-04/D-CF5-05 stand. Medium-high confidence.
5. **Output and exit codes (the contract this phase pins).** PostCompact has no decision control ("PostCompact hooks have no decision control. They can't affect the compaction result"; "Claude Code discards a PostCompact hook's `systemMessage` and `continue` fields"; exit 2 "Shows stderr to user only"). The binary shows what "shown to the user" means. The PostCompact runner (`gKr`) turns each hook's result into one line, in hook order, and returns them joined by `\n` as `userDisplayMessage`:
   - a hook that succeeded (exit 0) with output: `PostCompact [<command>] completed successfully: <output>`;
   - one that succeeded with no output: `PostCompact [<command>] completed successfully`;
   - one that failed (any other end) with output: `PostCompact [<command>] failed: <output>`;
   - one that failed with no output: `PostCompact [<command>] failed`;
   - a cancelled hook adds no line.

   `<output>` is trimmed. For a command hook (`AF`'s command branch) it is the stdout on exit 0 and the stderr on any other exit, except that a JSON `decision: "block"` gives its `reason` (or the stderr). Stdout on exit 0 is shown raw, a JSON object included, so `{"systemMessage":"x"}` shows as text and no `says:` notice. A hook that cannot start fails with the error message as output; a hook that its timeout stops fails with the output `Hook cancelled`. With `onFailure: "block"` (`$Vt`), a failed hook that did not exit 2 fails with the output `failed; blocking because onFailure is "block"` (`timed out; ...` after a timeout), then a line break and its stderr when it printed any. `<command>` is the hook's command text, with the `args` of an exec-form hook joined after it by spaces (`AO`: `e.args?[e.command,...e.args].join(" "):e.command`).

   Where the user sees the lines: the `/compact` command result shows `Compacted (ctrl+o to see full summary)` followed by the PreCompact lines and then the PostCompact lines (`[m,_.userDisplayMessage].filter(Boolean).join("\n")` and `I(verbose, w)`). An automatic compaction computes the same text but nothing reads it: no consumer of the auto path's `userDisplayMessage` exists in 2.1.319 (every occurrence of the property name was checked). The model never gets PostCompact output: PostCompact is not among the events whose stdout reaches Claude (docs "Exit code 0"). A PostCompact failure never fails the compaction (`P8t` catches and logs). High confidence for the manual path; medium-high for "nothing on the auto path" (absence of a consumer).

   The product today shows nothing for exit 0 (with or without stdout) and for an exit other than 0 and 2, and shows `PostCompact:<trigger> hook error: [<command>]: <stderr>` for an exit 2, on both triggers (D-CF5-24). That clause of D-CF5-24 rested on the belief that PostCompact used Claude Code's hook error render; the 2.1.319 binary shows it does not. Earlier records never looked at PostCompact's display lines (no `completed successfully` text appears in `.planning/` or `docs/`).
6. **Overflow in Pi 1.5.0.** `AgentSession._checkCompaction` compacts with reason `overflow` in two cases: an error turn whose message reads as a context overflow (such as `prompt is too long`), which Pi compacts and then retries once; and a successful reply whose reported input exceeds the context window, which Pi compacts without a retry. Both fire `session_compact` with reason `overflow` (`dist/core/agent-session.js`). The scripted model reaches both: an `error` step whose message starts `prompt is too long`, and a reply whose `context tokens` exceed 128000 (`features/lib/scripted-model/extension.ts`). Pi reports only `manual`, `threshold`, and `overflow` (`SessionCompactEvent.reason`). High confidence.

#### Output parity (D-BG-501 to D-BG-504)

- **D-BG-501 — after a manual compaction, PostCompact shows each hook's end as Claude Code does.** When a compaction with trigger `manual` (Pi's `/compact`, the RPC `compact`) runs at least one PostCompact hook that ends (any outcome but cancelled), the bridge shows the user ONE hook notice whose text is the hooks' lines joined by `\n`, in routing order, each worded exactly as evidence record 5 gives: `PostCompact [<command>] completed successfully[: <output>]` or `PostCompact [<command>] failed[: <output>]`, with that record's output rule (stdout on exit 0, stderr otherwise, a JSON `decision: "block"` reason first, `Hook cancelled` after a timeout, the start error for a hook that cannot start, and the `onFailure: "block"` text for a failed hook that sets it). The notice is the existing `hook-notice` kind at `info` severity (D-CF5-24's one kind), shown through the existing notification run. This amends D-CF5-24: a PostCompact block no longer shows as `<label> hook error: <message>`. `systemMessage` and `continue` stay dropped (D-CF5-14), and nothing reaches the model. Rationale: parity (evidence record 5); the roadmap's criterion 3 asks for it. Alternatives rejected: keep D-CF5-24's `hook error` notice and add nothing (fails criterion 3 for exit 0 and exit 1, and keeps a render upstream does not use); one notice per hook (upstream shows one block; the PreCompact block notice already joins its messages, D-CF5-18).
- **D-BG-502 — after an automatic compaction, PostCompact shows nothing.** A compaction with trigger `auto` (`threshold` or `overflow`) still runs the matching PostCompact hooks with their payload, but shows no notice for any outcome, exit 2 included, and writes a debug line instead. Rationale: Claude Code 2.1.319 computes the text on its auto paths and never shows it (evidence record 5). Rejected: show the lines on both triggers (diverges from upstream with no license).
- **D-BG-503 — where the run travels: one PostCompact-only optional field on the hook outcome, set where the process ends.** `HookExecResult` (`bridges/hooks/exec-result.ts`) gains one optional, readonly field on its arms for a PostCompact hook's run (whether it succeeded, and its output as evidence record 5 defines it). Only the PostCompact path sets it, at the points where `dispatch-exec.ts` knows how the process ended (the facts it already hands `onFailureBlock`: start failure, timeout, exit code, stdout, stderr) and after the `onFailure` rewrite, so a PostCompact `onFailure` block keeps its run. No other event's results change shape, so no other event's tests change. The wording of a line lives with the other upstream wording in `bridges/hooks/hook-labels.ts` as one new function. The PostCompact composite in `dispatch.ts` builds the notice in a case or function of its own, from `folded.outcomes` in routing order and the trigger, and its old PostCompact block-notice case goes; the SessionStart and SessionEnd paths keep their shape. The field's and the function's names are the planner's. Rationale: an outcome type with event-specific fields already exists (`updatedInput`, `updatedToolOutput`), so the run is data the fold keeps beside each hook. Note: `exec-result.ts` and `hook-labels.ts` are hook modules that the roadmap's enumerated shared list does not name; the change there is additive and PostCompact-only, and it is logged as a dubious choice for the parent. Rejected: a structural property that the declared union does not name, read back through an `in` check (hides data from the type); a buffer on the hooks runtime filled by the executor (a side channel that orders lines by completion, not routing).
- **D-BG-504 — the command in a line is upstream's display command.** `<command>` is the declared `command` text with placeholders kept, followed by the exec-form `args` joined by single spaces when the hook declares `args` (evidence record 5, `AO`). This differs from the `[<command>]` that D-CF5-11's block texts use, which omit `args`; those texts stay as they are.

## Summary

The product change is small and fully contained in five hook files. `HookExecResult` gains one optional field carrying a PostCompact hook's run (`succeeded`, `output`); `dispatch-exec.ts` sets it at the three places a sync hook ends (outer `catch`, child `error`, child `close`), only when `entry.claudeEvent === "PostCompact"`, computed from the `HookExitFacts` it already builds plus the wire answer and whether `onFailureBlock` fired; a new wording function in `hook-labels.ts` writes one line; and the PostCompact composite in `dispatch.ts` joins the lines in routing order into one `hook-notice` when the trigger is `manual`, and writes a debug line when it is `auto`. The old PostCompact `hook error` notice (the `"PostCompact"` label in `blockNotices`'s session group, `dispatch.ts:507-512`) goes.

Probe scenarios run on this worktree (scratch feature files outside the repo, adapter profile, 2026-11-08) settled every scenario mechanic: the overflow compact-and-retry path needs 5 scripted steps with a prior turn (or 3 without one; the CONTEXT premise that a prior turn is required is false, but it works and is locked), records a PostCompact run with trigger `auto` and `compact_summary` `Summary A.\n\n---\n\n**Turn Context (split turn):**\n\nSummary B.`; the auto matcher records only the `auto` hook; today's manual compaction shows only the exit-2 and `onFailure` hooks as `PostCompact:manual hook error: ...` (red for scenario 4); today's automatic compaction shows `PostCompact:auto hook error: [${CLAUDE_PLUGIN_ROOT}/hooks/refused.sh]: not now` (red for scenario 5); and the prompt after a manual compaction sends exactly three messages (the summary message, the kept `Hello.`, the prompt). No new step is needed.

Two existing unit test loops change because they include a PostCompact row that dispatches through the real `dispatchHookExec` and expects `{ kind: "noop" }` (`test/bridges/hooks/dispatch-exec.test.ts:831` and `:904-907`); D-BG-503's "no other event's tests change" holds for other events, but these two shared loops need a per-case expected outcome. One notice case in `dispatch.test.ts:3797-3803` changes. No feature row in `hook/session.feature` changes, and no integration test pins PostCompact.

**Primary recommendation:** Two sequential plans. Plan 01: write scenarios 4 and 5, run them red, then make the five-file product change with its unit cases, and turn them green. Plan 02: scenarios 2, 3, and 6 (keep the seed), each with a recorded red proof by a one-run breakage of `compact-trigger.ts` or the PostCompact branch, plus the PostCompact docs rows and the parent lines.

```ts
// Claude Code's output for a hook its timeout stopped.
const CANCELLED_OUTPUT = "Hook cancelled";

// The run before any onFailure rewrite: a timeout, a start failure (facts.stderr
// carries the start error), else the exit code decides, and a JSON block's
// reason (a block that does not come from stderr) wins over the streams.
function exitRun(facts: HookExitFacts, answer: HookExecResult): PostCompactRun {
  if (facts.timedOut) {
    return { succeeded: false, output: CANCELLED_OUTPUT };
  }

  if (facts.startFailed) {
    return { succeeded: false, output: facts.stderr };
  }

  const succeeded = facts.exitCode === 0;
  if (answer.kind === "block" && answer.fromStderr !== true) {
    return { succeeded, output: answer.reason ?? facts.stderr };
  }

  return { succeeded, output: succeeded ? facts.stdout : facts.stderr };
}

/**
 * D-BG-501 / D-BG-503: how a PostCompact hook ended, as Claude Code 2.1.319
 * reads a command hook, after the onFailure rewrite when `blockedOnFailure`.
 */
export function postCompactRun(
  facts: HookExitFacts,
  answer: HookExecResult,
  blockedOnFailure: boolean,
): PostCompactRun {
  const run = exitRun(facts, answer);
  if (!blockedOnFailure) {
    return run;
  }

  const head = `${facts.timedOut ? "timed out" : "failed"}; blocking because onFailure is "block"`;
  const detail = facts.timedOut ? "" : run.output.trim();
  return { succeeded: false, output: detail === "" ? head : `${head}\n${detail}` };
}
```

### Anti-Patterns to Avoid

- **Reusing `onFailureBlock`'s reason as the run output:** it carries `[<command>]: ` and appends stderr after a timeout; upstream's PostCompact output does neither.
- **Reading the run off the folded result:** `foldOutcomes` keeps only the decisive arm (`dispatch.ts:403-417`); read `folded.outcomes` (routing order, `runHooks` maps hooks in order, `dispatch.ts:245-255`).
- **A runtime buffer filled by the executor:** orders lines by completion (rejected by D-BG-503).
- **Changing `onFailureBlock`'s child-error stderr to the error message:** changes other events' block reasons.
- **An unconditional auto debug line:** breaks the existing PostCompact system-message drop test.

### Pitfall 1: The two PostCompact translator loops in dispatch-exec.test.ts
