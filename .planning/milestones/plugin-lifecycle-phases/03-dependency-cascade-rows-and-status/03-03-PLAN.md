<objective>
Give every closure member that a failed install would have newly materialized,
and did not, its own `(failed) {dependency failed}` row (CAS-01 /
CLOSUREROW-01, D-PL3-01, D-PL3-02, D-PL3-03, D-PL3-15). The list is computed in
`install-cascade.ts` on each failure arm, carried to
`composeCascadeFailureMessage`, and rendered with the root row's own token, so
no closed set grows.

Purpose: a failed install names every member it attempted, as Claude Code names
every member on success (E1), instead of hiding the dependencies it rolled back.
Output: the `unmaterialized` lists on the three failure routes, the member rows,
two edited and two new scenarios, and catalog examples that stay true.
</objective>

Three failure routes reach `composeCascadeFailureMessage` (RESEARCH Pattern 1,
verified):

- Walk failure: `resolveCascade` returns `{ kind: "closure-failed", failure }`;
  `install-flow.ts::unwrapCascade` and `dependency-plan.ts::walkRefusal` forward
  `cascade.failure` verbatim into the subject, so a list INSIDE `failure` reaches
  the renderer with no edit in either file.
- Constraint failure: `{ kind: "constraint-failed", failure }`, forwarded the
  same way.
- Member ledger failure: `failedCascade` returns `member-failed`; `unwrapCascade`
  builds the member subject field by field (one forced line), only when the key
  is not the root.

Subjects built without a list (they stay valid, so the subject side is
OPTIONAL): the three MISS-01 closure literals in `install-flow.ts`,
`dependency-plan.ts::unmovable`, `previewFresh`'s member subject, and
`install-flow.ts::catalogLookup`'s member subject (a lookup that throws mid-walk;
RESEARCH A3, a recorded gap). `dependency-bindings.ts::dependencyRefusal` keeps
only failed rows that carry a cause, so update's settle refusal never shows the
new cause-less rows.

`walkDependencyGraph` already wraps `options.lookup` to fill a `DeclaredEdges`
map (around line 1796). Hoist that wrapper: one recorder serves this plan and
plan 03-04, and a second copy would fail `fallow dupes`.

`handleCascadeThrow` appends `movedRows(args.moved)` after the composed rows. A
disabled dependency whose pin a plan step refreshed and whose re-enable the final
cascade rolled back is in the list AND has a moved row (RESEARCH Pitfall 4).
</context>
