Upstream (Claude Code 2.1.310 install routine, read from the binary): the
cascade installs `sn.closure` from its last element to its first; after each
member installs it appends itself to `dr.get(dep)` for every dependency it
constrains with a version. A refused member's requirers are therefore the
range-declaring members in reverse closure order, after the outside-closure
installed ones from `_Co` (which D-PL3-13 leaves out). The message is
`"${Mt(entry.name,120)}" from the ${dir} is pinned to its listed commit
(${manifestVersion ? "version " + Mt(manifestVersion,120) : "no version"}),
which does not satisfy ${Mt(rs.join(", "),120)} required by
${requirers.map((r) => "\"" + Mt(On(r).name,120) + "\"").join(", ")}.`

Current code: `rangeRequirers` (`install-cascade.ts`, around line 929) returns
`options.rootRequiredBy` for the root, else `[member.requiredBy]` (the first
declarer only). `resolveOneMember`'s directory-pin arm sets
`declared: renderDeclaredRanges(ranges)` (the 200-cap form). After plan 03-03,
`resolveCascade` records every found lookup's declarations in a `declared`
`DeclaredEdges` map through `recordingLookup`, and `requestersOf(declared, key)`
lists each declarer of a key with its ranges, in walk order.
`assertDirectoryPinSatisfied` (`install-outcome.ts`, around line 820) reads the
listed `plugin.json` version and throws `DirectoryPinUnsatisfiedError`, whose
message `shared/errors.ts` builds from the constructor fields; `shared/` may not
import `domain/`, so the cuts happen in the caller. No consumer reads the error's
fields beyond `instanceof` (RESEARCH Pattern 3).

`ClosureMember.requiredBy` (the first declarer, used by the walk's not-found
message) keeps its shape (D-PL3-08).
</context>
