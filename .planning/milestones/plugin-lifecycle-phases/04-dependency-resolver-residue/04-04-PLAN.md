<objective>
RSV-01 (UPDDEP-01 b1), first half, per D-PL4-01: the commit an install preview
resolves travels with the plan to the member it schedules.

- `previewInstall` (`install-outcome.ts`, preview hand-off only) answers its
  preflight's `resolvedSha`.
- The plan's `preview` port answers that commit. `dependency-plan.ts` keeps one
  commit per fresh key and sets it as `previewedCommit` on the member it schedules,
  in the materialize step that installs it and in `final`. The plugin being installed
  takes the commit the caller passes as `DependencyPlanOptions.rootCommit`.
- `ResolvedCascadeMember` (`install-cascade.ts`) gains the optional
  `previewedCommit`.

Purpose: plan 04-05 then pins each member's install to its previewed commit, so a
fresh unpinned git dependency resolves once over the network and installs exactly
what the plan previewed.

Why one commit for four modules: the port type and previewInstall's return type
meet in install-flow.ts's `planningPorts.preview` binding. `Promise<void>` and
`Promise<string | undefined>` are not assignable in either direction (checked with
tsc), so they change together. The binding itself needs no edit.

Output: two commits (the fresh members, then the root).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| git host -> preview clone | The preview resolves a ref-less git source to whatever commit the host's HEAD names at that moment. |
| plan -> install | The plan's members carry what the later install materializes. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-09 | Tampering | a commit the host moved to between the preview and the install | high | mitigate | The plan carries the exact sha the preview resolved on the member (`previewedCommit`); plan 04-05 pins the install to it, and the per-commit copy is keyed by `pluginCloneKey(canonicalCloneUrl, sha)` and immutable (clone-cache.ts). The D-PL4-01 cases pin which member carries which commit. |
| T-04-10 | Spoofing | a commit applied to the wrong member | medium | mitigate | Commits are keyed by member key and set only on the member of that key (`withPreviewedCommit`), never by position; the D-PL4-01 case gives each fresh member a distinct commit and asserts the whole plan. |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed by this plan. |
</threat_model>
