## Summary

The review covered the diff `a8b1e1d0..HEAD`. That is the FIX-02 migration exclusion, the pending mirror, the FIX-03 refusals in install, enable/disable, named update, and named reinstall, the hermetic write-back (`selectLayerWriteBack`), the new reason, and the tests, scenarios, and docs.

What holds:

- The refusal predicate, `selectLayerWriteBack`, and `writeBackRefusal` agree on one decision.
- Every refusal runs before any state or config write. For install, it runs before the promotion and the cascade. For enable and disable, it runs before the cascade resolution and EDEP-02. For reinstall, it runs inside the lock before `loadCachedEntry`.
- Orchestrated calls, the autoupdate cascade, the backfill, and the nameless forms are never refused.
- Every new config-map lookup uses `ownValue`. The tests include prototype-named keys that catch an `in`/`[]` regression.
- Pending and the load agree, because both call `buildConfigFromState(state, local)` with the same `local`.

The main defect is the exclusion rule itself. The projection drops every plugin recorded under a marketplace that the local file declares. When `claude-plugins.json` is absent, the next reload therefore uninstalls those plugins and deletes their data directories. D-02 accepted this edge case on the premise that only data written before the fix can reach it. That premise is false: a marketplace declared in both files (legitimate per D-03) admits flagless installs after the fix too. Several smaller defects follow. The reinstall S5 change is unreachable in production. The named update refusal runs after a networked preflight. Enable and disable refuse idempotent no-ops. One JSDoc contradicts the emit order its own test pins.

## Critical Issues

### CR-01: Migration exclusion uninstalls shared plugins (and deletes their data) under a marketplace that the local file also declares

**File:** `extensions/pi-claude-marketplace/persistence/migrate-config.ts:141-143` (rationale comment at `:106-110`; pinned by `tests/orchestrators/reconcile/pending.test.ts:453-473`)

**Issue:** `buildConfigFromState` skips a recorded marketplace that `local.marketplaces` declares, together with **every plugin recorded under it**, whether or not the local file declares those plugin keys. The comment justifies this with: "The migration runs only while claude-plugins.json is absent, so a marketplace the local file declares is declared only there." That is true of the *current* moment. It says nothing about where the *plugins* under it were declared. The reconcile planner (`plan.ts::buildUninstallBucket`) then sees a retained marketplace and a recorded `provenance: "explicit"` plugin that no file declares, so it plans an uninstall. `apply.ts::applyOnePluginUninstall` calls `uninstallPlugin` without `keepData`, and `uninstall.ts:1140` defaults `keepData` to false, so the plugin's data directory is deleted as well. No command and no prompt is involved.

Two reachable paths. Neither depends on data written before the fix:

1. **A marketplace declared in both files (legitimate per D-03).** `marketplace add mp` writes the base file. The user also declares `mp` in `claude-plugins.local.json`, for example as a personal `autoupdate` override. Then `install p@mp`, flagless, is *not* refused, because `localOnlyMarketplaceRefusal` sees `current.marketplaces.mp`, and it writes `p@mp` into the base file. Later `claude-plugins.json` disappears: the user deletes it, or a project checkout of a revision that predates the file removes it while the gitignored `state.json` and local file stay. On `/reload`, the migration leaves out `mp` and `p@mp`. The merged view declares `mp` (from local) but not `p`, so `p` is uninstalled and its data is removed. Before the fix, the migration restored `p@mp` and nothing was lost.
2. **Every existing user who ran `marketplace add --local` and then a flagless install.** UAT-05 admitted that combination before this phase, so this is the normal state of affected users, not a corner case. If such a user deletes a base file that holds only leaked entries, instead of editing it as the CHANGELOG says, the same uninstall follows.

The new pending test asserts exactly this outcome (`○ p1 (will uninstall)` for a plugin whose key no file declares), so the suite pins the data-loss behavior as intended.

**Fix:** The projection cannot tell a personal plugin from a shared one under a local-declared marketplace, so it must not resolve that doubt by deleting. Possible fixes, each a user decision because they touch D-01/D-02:

```ts
// Option A (non-destructive, minimal): leave out only the marketplace entry and
// the plugin keys the local file declares; keep the other plugin keys of a
// local-declared marketplace. The merged view still resolves them, because the
// local file declares the marketplace, so the planner keeps the plugins.
for (const [mpName, mp] of Object.entries(state.marketplaces)) {
  const marketplaceIsLocal = ownValue(local.marketplaces, mpName) !== undefined;
  if (!marketplaceIsLocal) {
    marketplaceEntries.push([mpName, entryFor(mp)]);
  }
  pluginEntries.push(...sharedPluginEntries(mpName, Object.keys(mp.plugins), local));
}
```

Option A writes plugin keys under a marketplace that the base file does not declare, which is the FIX-03 resolvability concern. The alternative is to write those keys into `claude-plugins.local.json` (add-only, never modifying an entry), which keeps them personal. A third option is to exempt such records from the uninstall bucket on the migration pass. In every option, fix the comment at `:106-110` and change the pending test to expect no uninstall.

## Warnings

### WR-01: The reinstall S5 row is unreachable in production, so a flagless reinstall with an unreadable local file silently skips the declaration

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/reinstall-flow.ts:358-374, 423-449, 865`

**Issue:** Plan 04 changed the reinstall S5 row to name `locked.invalidConfigFile`, and the new `selectLayerWriteBack` adds an `unreadable` arm for the local file on flagless calls. The S5 row, however, is rendered only on the `render !== "none"` arm. The module's own header (`:28-40`) says no production caller reaches that arm: `reinstallPluginsWith` (`:590`) and `reconcile/backfill.ts:425` both pass `render: "none"`. The `render === "none"` return (`:358-374`) does not carry `invalidConfigFile` onward, and `ReinstallPluginOutcome` has no field for it.

Failure scenario: `claude-plugins.local.json` has a syntax error and the user runs `/claude:plugin reinstall p@mp`. `writeBackRefusal` treats the unreadable file as "not a refusal", the reinstall succeeds, and the write-back returns `{ invalidConfig: true, filePath: <local> }`. The value is dropped, and the user sees only `(reinstalled)`. The plugin's base declaration is never written, and nothing says so. Before this phase, the same command wrote the base key. The new test `S5: a flagless reinstall whose local file cannot be read names claude-plugins.local.json` calls `reinstallPlugin` directly in default render mode, so it covers only the dead arm.

**Fix:** Carry the file onto the outcome on the `render: "none"` arm (for example `invalidConfigFile?: string` on `ReinstallReinstalledOutcome`). Render the S5 row from `reinstallPlugins` after the cascade row, as update does from its direct path. Then point the S5 test at `createNodeReinstallPlugins`/`reinstallPlugins` so it exercises the production path.

### WR-02: The named update refusal runs after the networked preflight, so a refusal that needs only the two local config files can trigger clones, auth prompts, and a stray plugin clone

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/update-flow.ts:1107-1117`

**Issue:** `refuseLocalOnlyMarketplaceUpdate` runs after `preparePluginUpdate`. For a git-source plugin, the preflight builds auth (`buildUpdateAuth`), evaluates the constraint gate (a tag listing over the network), and materializes or refreshes the plugin clone (`makeUpdateCloneProbe` → `materializePluginClone`). The refusal then throws, after the user may have gone through a Device Flow prompt. The new clone under `plugin-clones/` stays unreferenced until a later GC. The refusal itself reads only `claude-plugins.json` and `claude-plugins.local.json`, which needs no network. The plan and SUMMARY call this "refused before staging", which holds only for the swap's staging.

**Fix:** Evaluate `writeBackRefusal` before `preparePluginUpdate`. To keep "an up-to-date named update is not refused", carry the refusal through the preflight and raise it only when the preflight returns a candidate:

```ts
const refusal = await localOnlyMarketplaceUpdateRefusal(args); // reads config only
const preflight = await preparePluginUpdate(/* ... */);
if (isUpdatePreflightOutcome(preflight)) return preflight;
if (refusal !== undefined) throw refusal;
```

That still pays the network cost for the up-to-date check. If that cost matters, refuse up front and accept refusing an up-to-date plugin. In either case, document the choice.

### WR-03: Enable and disable refuse idempotent calls that write nothing, unlike update and contrary to D-06's "would write"

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/enable-disable.ts:2357` (vs. the idempotent arm at `:2391` and `resolveIdempotentOutcome` at `:1958-1960`)

**Issue:** `refuseLocalOnlyMarketplace` runs before the ENBL-05 idempotency check. Take `enable foo@mp` on a plugin that is already enabled, where the base file has no `foo@mp` entry and `mp` is declared only locally. `resolveIdempotentOutcome` would return `{ kind: "idempotent" }` and write nothing (`configEnabled === undefined`). It never gets there: the user sees `⊘ foo (failed) {marketplace declared locally}` at error severity instead of `(skipped) {already enabled}`. D-06 scopes the refusal to "a verb that would write a plugin declaration". The named update path deliberately does not refuse an up-to-date plugin (`FIX-03: an up-to-date named update ... is not refused`), so the two verbs now disagree. No test covers the idempotent enable or disable case under a local-only marketplace.

**Fix:** Move the refusal into the arms that write: before `writeEnabledFlagBack` in `resolveIdempotentOutcome` and on the fresh and dispatch arms. Alternatively, decide the idempotency first and skip the refusal when the outcome writes no config. If refusing a no-op is intended, record it in CONTEXT/catalog and add a test that pins it.

### WR-04: `notifyInvalidConfigWriteBack` JSDoc says the S5 row comes after the success row, but it is emitted first

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/update-swap.ts:1283-1291`

**Issue:** The JSDoc says "Direct-path callers surface the abort as a separate warning AFTER the success row". `swapPluginUpdate` calls it at `:1488-1490`, before returning the `updated` outcome. The success row is rendered later by `composeCascade` in `updatePluginsWith`. The new test `S5: a flagless update whose local file cannot be read names claude-plugins.local.json` (`tests/orchestrators/plugin/update-flow.test.ts`) pins the S5 row as notification 0 and the `(updated)` row as notification 1. The phase edited this JSDoc and kept the false claim (WINDOWS #95). The row is also an `error`-severity `(failed)` row, not a "warning".

**Fix:** Correct the comment ("emitted before the cascade's success row, at error severity"), or move the emit after `composeCascade` if the documented order is the intended one, and update the test.

### WR-05: The FIX-03 scenario does not show that the refused install left nothing installed

**File:** `features/plugin/install.feature:69-85`

**Issue:** The scenario checks the failed row and that neither config file declares a plugin. A plausible wrong implementation passes it: one that runs the refusal after the cascade (artifacts and `state.json` record written), renders the failed row, and skips only the config write-back. Under the cucumber skill's review rule, a scenario that a plausible wrong implementation passes is the highest-value finding. The 03.1-05 review recorded this and deferred it to the unit test. The only thing standing in for the real-Pi claim "fails" is a unit test that drives the module, not the extension.

**Fix:** Add a read-only observable that does not need a second `When`. For example, a step that asserts the scope's `state.json` records no plugin `pp` of `tools`, or that the project scope has no skills from `pp`, in the style of the existing read-only config steps.

## Info

### IN-01: `writeBackRefusal` JSDoc overstates "cannot disagree"

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/shared.ts:1432-1437`

**Issue:** For update, the check runs outside any lock, before the preflight. The write-back re-reads both files later, under `withStateGuard`, in `finalizeUpdateRecord`. They share the decision function but not the bytes. A concurrent hand edit between them makes them disagree. The result is a safe silent no-write, but the comment's guarantee does not hold.
**Fix:** Say "reads the same decision rule" and name the TOCTOU window and its safe direction.

### IN-02: A populated state that is entirely local reports `reason: "empty-state"`

**File:** `extensions/pi-claude-marketplace/persistence/migrate-config.ts:58-59, 247`

**Issue:** The `"empty-state"` arm is documented as "an empty-but-present state.json". It is now also returned when the state is populated but the local file declares every record (`FIX-02: writes no base file when the local file declares every record` asserts it).
**Fix:** Extend the arm's JSDoc ("or every record is declared locally"), or add a distinct reason.

### IN-03: The `local-invalid` arm names the base file, not the unreadable local file

**File:** `extensions/pi-claude-marketplace/persistence/migrate-config.ts:236`

**Issue:** `filePath: loc.configJsonPath` points at the file that was *not* written. The file that could not be read is `configLocalJsonPath`, and unlike `existing-invalid` the arm forwards no `error`. The phase fixed this naming problem for the S5 rows.
**Fix:** Add `localFilePath` (and `error`) to the arm, or document that `filePath` is always the base target.

### IN-04: The install refusal precedes the marketplace-absent check and can suggest a remedy that then fails differently

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/install-flow.ts:1657-1663` (vs. `:1796`)

**Issue:** Suppose the local file declares `mp` but the scope has no recorded `mp` yet (hand-edited, not yet reloaded). A flagless `install p@mp` answers "Run the command again with --local", and the `--local` rerun then fails with `marketplace not added`.
**Fix:** Check the refusal only once the marketplace record resolves, or accept and document the ordering.
