### Locked Decisions

#### Fix mechanism
- **D-01:** When the first-run migration builds the base file from `state.json`, it leaves out everything the scope's local file declares. The local file stays the only record of what is personal, and the `state.json` schema does not change.
  - If nothing non-local is left, no base file is written, which is the existing UAT-01 rule against empty files.
  - The read-only planning mirror in `orchestrators/reconcile/pending.ts` (`mergedViewForPlanning`) must apply the same exclusion, so `pending` and the load agree.
  - `state.json` provenance was considered and not chosen.
- **D-02 (user note):** base and local entries are merged per entry; a local entry replaces the base entry with the same key (`persistence/config-merge.ts::mergeScopeConfigs`, CFG-02). There are also rules that refuse to put a plugin in the shared file when its marketplace is declared only in the local file. The fix must respect that model:
  - the migration leaves out the marketplaces the local file declares;
  - it leaves out the plugin keys `plugin@marketplace` the local file declares;
  - it also leaves out the plugins of a marketplace that only the local file declares, since the shared file may not hold a plugin whose marketplace it does not declare.

  Research locates the existing refusal rule and confirms the migration matches it.

#### Coverage
- **D-04:** the whole leak class is fixed, marketplaces and plugins installed with `--local` alike. The marketplace path gets cucumber scenarios. The plugin path is proven by unit tests, because the milestone keeps plugin flows out of `features/`.

#### Existing leaks
- **D-03:** no automatic repair and no warning. A marketplace or plugin can legitimately be declared in both files: shared for the team and local for oneself. A leaked entry therefore cannot be told apart from a deliberate one, so any repair or warning would hit legitimate setups (the user's ruling). The CHANGELOG bullet tells affected users to remove the leaked entry from `claude-plugins.json` and reload. No README entry.

## Summary

The leak has exactly one source: `migrateFirstRunConfig` (`persistence/migrate-config.ts`) writes `buildConfigFromState(state)` into `claude-plugins.json` whenever that file is absent, and it never opens `claude-plugins.local.json`. It runs on every load from `apply.ts::readPassForScope`, before the merged view is read. A real-Pi probe (hermetic sandbox) reproduced it for a marketplace (`add --local`, then a new session) and for a plugin (`install --local`, then a new session).

The fix fits inside `migrate-config.ts`. `migrateFirstRunConfig(loc, state)` already receives `loc`, which carries `configLocalJsonPath`. So the migration can load the local file itself, and the signature that `apply.ts` calls stays the same. The pure projection `buildConfigFromState` takes the local config as a second, required argument and skips: (1) every recorded marketplace the local file declares, together with all its recorded plugins, and (2) every plugin key the local file declares. `pending.ts::mergedViewForPlanning` already holds the parsed local config, so it passes it to the same function. A local file that is `invalid` makes the migration decline to write (a new result arm). It is not treated as empty, because that would leak.

Two findings contradict the CONTEXT and the planner must account for them. **(a)** No rule refuses a shared plugin whose marketplace only the local file declares. The probe shows the opposite: a flagless `install pp@tools` on a `--local` marketplace writes `"pp@tools": {}` into `claude-plugins.json` with no marketplace entry. The D-02 third exclusion is therefore a new, migration-only rule, not a match to an existing one. Its one destructive edge case is listed under Open Questions. **(b)** On today's code, `remove --local` after the leak already stays removed across a new session, because `remove` sweeps both files. The remove scenario fails before the fix only on the observable "`claude-plugins.json` does not exist". The leak left that file behind, holding empty maps.

**Primary recommendation:** Change `buildConfigFromState(state, local)` and have `migrateFirstRunConfig` load the local file after the base-file check, with a new `"local-invalid"` decline arm. Leave `apply.ts` untouched, pass `outcome.local`'s config in `pending.ts`, and add two read-only config steps (`does not exist`, `declares no marketplaces`) for one scenario in `add.feature` and one in `remove.feature`.

## Q2. D-02: the "refusal rule" and the exclusion set

**Finding: the refusal rule does not exist.** The rules that do exist in `orchestrators/plugin/shared.ts`:

1. **CR-02 adoption** (`synthesizeUndeclaredMarketplaceSource`, `shared.ts:582-594`): a plugin write also declares its marketplace in the same file **only when neither file declares it**: `if (scopeConfigs.some((c) => ownValue(c.marketplaces, marketplace) !== undefined)) { return undefined; }`. [VERIFIED: shared.ts:582-594]
2. **UAT-05 membership gate** (`writeAdoptingConfigEntries`, `shared.ts:843-866`): the membership test reads both files, so a `--local` write never re-declares a base-declared marketplace. An unreadable sibling skips adoption. [VERIFIED: shared.ts:784-866]
3. **D-103-13 target selection** (`selectDeclaringConfigWriteTarget`, `shared.ts:709-746`): `--local` targets the local file. Without the flag, the write goes to the file that already declares the plugin key, else the base file. An `invalid` local file returns `{ kind: "unreadable" }` instead of guessing. [VERIFIED: shared.ts:709-776]
4. **D-16 dangling references are valid** (`config-merge.ts:28-30`): "a dangling plugin reference (a plugin entry whose marketplace name does NOT appear in either marketplaces map) is a VALID merged result." [VERIFIED: persistence/config-merge.ts:28-30]

So a flagless install on a local-only marketplace writes the plugin key into the **base** file with no marketplace entry there. Real-Pi probe (hermetic sandbox, deleted afterwards):

```
> marketplace add {home}/marketplaces/tools --scope project --local      -> added
> install pp@tools --scope project                                     -> installed
  claude-plugins.json:       { "schemaVersion": 1, "marketplaces": {}, "plugins": { "pp@tools": {} } }
  claude-plugins.local.json: { "schemaVersion": 1, "marketplaces": { "tools": { "source": "{home}/marketplaces/tools" } } }
```

**Exclusion set (matches D-02 as written; implement it inside the migration only):**

| Recorded item | Excluded when | Why |
|---------------|---------------|-----|
| marketplace `mp` | `ownValue(local.marketplaces, mp) !== undefined` | D-02 rule 1 |
| plugin `p@mp` | the marketplace `mp` is excluded (rule 1) | D-02 rule 3. When the migration runs, the base file is absent, so "declared only in the local file" is the same as "declared in the local file". |
| plugin `p@mp` | `ownValue(local.plugins, "p@mp") !== undefined` | D-02 rule 2 (covers `install --local` of a plugin whose marketplace is shared) |

Use `ownValue` (`shared/own-key.ts:9-14`: `return map !== undefined && Object.hasOwn(map, key) ? map[key] : undefined;`). A bare index lookup reads inherited members: with `local.marketplaces = {}`, `{}["constructor"]` is truthy and would wrongly exclude a state marketplace named `constructor`. The existing test `projects JSON-derived prototype-named marketplaces as own config entries` (`migrate-config.test.ts:195`) seeds `__proto__`, `constructor`, and `toString`. [VERIFIED: shared/own-key.ts:9-14; tests/persistence/migrate-config.test.ts:195-220]

**Effect on the planner, measured against `plan.ts`:**
- Rules 1 and 2 never change the merged view, because `mergeScopeConfigs` lets the local entry win per key (`config-merge.ts:87-115`). They only stop the copy into the shared file. [VERIFIED: persistence/config-merge.ts:87-115]
- Rule 3 changes the merged view only for a recorded plugin under a local-declared marketplace that the local file does **not** declare:
  - `provenance: "dependency"` (the cascade dependencies of a `--local` install, which are declared nowhere, D-04-02): `buildUninstallBucket` skips them (`plan.ts:588`: `if (record.provenance === "dependency") { continue; }`), and `holdsDependencyRecord` keeps their marketplace (`plan.ts:261-263`). Excluding them is safe, and it is what stops `dep@mp` leaking into the shared file. [VERIFIED: orchestrators/reconcile/plan.ts:255-604]
  - `provenance: "explicit"`: the plugin becomes undeclared, so `buildUninstallBucket` plans its **uninstall** (`plan.ts:597-599`). This state, with the base file absent, arises only when the user deletes `claude-plugins.json` after a flagless install on a local-only marketplace, because that install writes the base file (probe above). See Open Question 1.

**Invalid local file at migration time.** `loadConfig` never throws. It returns `{ status: "invalid"; filePath; error }` (`config-io.ts:112-115`). Treating `invalid` as empty would write every local declaration into the shared file, which is the leak. The migration must **decline**: return a new arm `{ migrated: false; reason: "local-invalid"; filePath: loc.configJsonPath }`, and write nothing. This is safe:
- The same read pass aborts the plan for that scope on the local `invalid` arm (`apply.ts:223-235`), so nothing destructive runs.
- The base file stays absent, so the next load after the user repairs the local file migrates with the exclusion.
- `selectDeclaringConfigWriteTarget` already refuses flagless writes while the local file is invalid (`shared.ts:719-721`), and `pending.ts` skips the scope (`:193-196`). So no other path observes the missing base file in that window.

[VERIFIED: persistence/config-io.ts:112-115; apply.ts:223-235; pending.ts:185-196; shared.ts:709-776]

## FIX-03 Refusal

**The seam.** Put one exported predicate in `orchestrators/plugin/shared.ts`, next to `selectDeclaringConfigWriteTarget`. It reads only the selection that each authoring path already makes inside its lock, so the rule has one definition and one cause text:

```ts
// FIX-03 / D-MF-02: a shared declaration may not name a marketplace that only
// the local file declares; a teammate reading the shared file cannot resolve it.
export function localOnlyMarketplaceRefusal(
  selection: Extract<DeclaringConfigWriteTarget, { kind: "selected" }>,
  marketplace: string,
): string | undefined {
  if (
    selection.targetIsLocal ||
    ownValue(selection.current.marketplaces, marketplace) !== undefined ||
    ownValue(selection.sibling?.marketplaces, marketplace) === undefined
  ) {
    return undefined;
  }

  return `The marketplace ${marketplace} is declared only in claude-plugins.local.json. Run the command again with --local.`;
}
```

(Sketch, not compiled.) The four conditions: the target is the base file (no `--local`, and the local file does not declare the key), the base file does not declare the marketplace, and the local file does. When the target is the base file, `sibling` is always the readable local file, because a flagless selection with an invalid local file already returns `{ kind: "unreadable" }` (`shared.ts:719-721`, `localFileLeavesTargetUnknowable`). Whether the `?.` needs a test of its own for branch coverage is for direct coverage to decide. [VERIFIED: shared.ts:709-776]

Why a predicate and not a third arm on `DeclaringConfigWriteTarget`: both dual-mode callers, install (`install-flow.ts:1607`) and enable/disable (`enable-disable.ts:2300`), still need `current`, `sibling`, and `targetConfigPath` in orchestrated mode, where the refusal must not fire. An arm that replaced `selected` would force orchestrated code to handle a case it can never reach. That code would be dead, and the 100% direct-coverage gate would reject it.

**Call sites, one per authoring verb, all standalone-only:**
1. `install-flow.ts`, right after the `selection.kind === "unreadable"` return (`:1622-1625`), before the D-04-07 promotion and the cascade. Gate it on `!orchestrated`. It covers the fresh root, the promotion, and therefore `browse`.
2. `enable-disable.ts`, right after the unreadable return (`:2313-2316`), before `resolveEnableCascadeStep`. Gate it on `!orchestrated`. Throw the existing refusal carrier `EnableRefusedError(reason, cause)` (`:550-557`), as EDEP-02's `dependents remain` does (`:1569`). The standalone catch (`:2453-2478`) already renders `[cause.reason]` with `cause` as the row's cause line.
3. `update` and `reinstall`: replace the flag-only target of `maybeWritePluginConfigBack` with `selectDeclaringConfigWriteTarget({ locations, local, key })`. Make the selection at the top of the locked body, before staging or replacement, and apply the predicate only where the write would add a key: the key appears in neither file. Reuse the same selection for the post-success write-back. This also stops the leak in the probe, because a plugin the local file declares gets no write at all. An `unreadable` selection keeps today's S5 behavior: the write-back is skipped and the existing `{invalid manifest}` warning row is shown.

**Scoping (confirmed by reading the code).** The selector reads only the target scope's own `locations` (`configJsonPath` and `configLocalJsonPath`), so the check is per scope. In the CMP-3 case (a marketplace added in the user scope, a plugin installed into the project scope), neither project file declares the marketplace. The predicate returns `undefined`, and CR-02 adoption declares the marketplace in the project base file as it does today. A user-scope local declaration never affects a project install. [VERIFIED: shared.ts:582-594, 709-746]

**Note on cascade members.** `overwriteDisabledMemberEntries` re-selects each member by declaration alone and only rewrites an `enabled: false` entry that already exists (`shared.ts:883-913`). It never creates a declaration. I recommend leaving it unchanged and documenting that FIX-03 governs the key the command names. If the planner wants members covered too, the same predicate applies in its loop. On a refusal the member is skipped, as an unselected one is today.

### F2. Order relative to materialization, and the row

**Order.** Every check runs inside the scope lock, right after the selection and before any `runPhases` ledger, staging, replacement, or `tx.save()`. A refusal therefore leaves `state.json` (bytes and mtime), both config files, and the staged artifacts untouched. This is fail-clean under NFR-3, and the EDEP-02 refusal already follows the same pattern ("nothing is unstaged, `tx.save` is never called", `docs/output-catalog.md:4075`). For `reinstall`, the check must come before `replacement`, because the existing write-back sits inside a `try` whose `catch` rolls the replacement back (`reinstall-flow.ts:849-859`). Refusing there would not be clean. [VERIFIED: reinstall-flow.ts:830-860; update-swap.ts:895-925]

**Row shape (recommended):** `⊘ pp (failed) {marketplace declared locally}`, severity `error`, `needsReload: false`. The cause line is the hint: `The marketplace tools is declared only in claude-plugins.local.json. Run the command again with --local.` This follows the existing `failed` refusal-row precedents (EDEP-02 `dependents remain`, `UninstallRefusedError`): the token is a closed-set reason, the remedy rides the cause line, there is no absolute path, and marketplace names pass `assertSafeName`.

**Token.** I propose the new token `marketplace declared locally` (three lowercase words, the size every reason uses). It goes into `FailureReason` in `shared/notify-reasons.ts`, the shared failure group that every verb row can carry. Why not reuse a token: `dangling reference` (PURL-06) means "the plugin's `@marketplace` is not declared in the merged config", and here the merged config does declare it, so the attribution would be wrong. The `marketplace not added*` tokens are structural markers whose subject is a marketplace row. If D-06's "within the existing reason vocabulary" means literal reuse, `dangling reference` is the closest member and needs no enrollment (Open Question 3).

### Anti-patterns
- **Loading the local file in `apply.ts` and threading it in:** this touches the composition root and its 7,000-line owner test for no gain. `loc` already carries the path.
- **Treating `invalid` local as `{}`:** this leaks every local declaration (see Q2).
- **Index lookups on config maps:** they read inherited members. Use `ownValue`.
- **Comments that narrate the old leak ("Pre-fix, ...")** are forbidden by typescript-style comments.md. Cite `FIX-02` and `MIG-01` instead.

## Common Pitfalls

### Pitfall: the remove scenario passes on today's code if it only checks `list`
**What goes wrong:** today's code already keeps the marketplace removed, because remove sweeps both files.
**How to avoid:** include `the "claude-plugins.json" file of the project scope does not exist`, and watch the scenario fail before the fix.

### Pitfall: the D-02 rule 3 consequence
**What goes wrong:** a recorded explicit plugin under a local-only marketplace, which the local file does not declare, is uninstalled on the next load when the base file is absent.
**How to avoid:** pin it in the pending owner test and get the user's confirmation (Open Question 1).

### Pitfall: unused step at commit
**What goes wrong:** `check:features` (part of `check:static`, so also of the commit hook) fails on a step that no scenario uses.
**How to avoid:** commit each new step with the scenario that uses it.

### Pitfall: scenario left red in a gate
**What goes wrong:** `check:commit` does not run `test:cucumber`, so a red scenario can be committed. `npm run check` then fails at the wave gate.
**How to avoid:** write the scenario first, run it, record the failure output in the SUMMARY, then land the fix before the gate. Committing the fix in the same commit as the scenario, or right after it, is acceptable.

### Pitfall: hermetic probes only
Any manual real-Pi check runs only through `features/lib/pi-process.ts` with a `mkdtemp` sandbox, or through `npx cucumber-js`. Never against the real `~/.pi/agent`.
