### WR-02: The named update refusal runs after the networked preflight

**Files modified:** `extensions/pi-claude-marketplace/orchestrators/plugin/update-flow.ts`, `tests/orchestrators/plugin/update-flow.test.ts`, `docs/output-catalog.md`
**Commit:** 0bc40818
**Status:** fixed: requires human verification (this changes a behavior the plan required)
**Applied fix:** `refuseLocalOnlyMarketplaceUpdate` now runs before `preparePluginUpdate`, as the orchestrator directed. A refused update builds no credentials, lists no tags, and clones nothing. A new test seeds a git-source plugin whose pinned sha has changed, injects the git-ops fake, and asserts these things: the refused row, unchanged state.json bytes, no new plugin clone directory, and no clone, fetch, or remote-ref calls. Against the code before the fix, that test fails because the new clone directory exists.
**Choice to confirm:** This takes the review's second option, so an up-to-date named update under a local-only marketplace is now refused too. The plan had required that it is not refused (03.1-04-PLAN truth: "an up-to-date named update is not refused"). Knowing that a git-source plugin is up to date can need the network. The test that pinned the old behavior is renamed `...is refused before the version check` and now expects the refusal row. The trade-off is documented in the function's JSDoc and in the `failure-marketplace-declared-locally` section of `docs/output-catalog.md`. If the user wants an up-to-date update not to be refused, the review's first option applies: check before the preflight, but raise the refusal only after the preflight returns a candidate. That option still uses the network.

### WR-03: Enable and disable refuse idempotent calls that write nothing

**Files modified:** `extensions/pi-claude-marketplace/orchestrators/plugin/enable-disable.ts`, `tests/orchestrators/plugin/enable-disable.test.ts`
**Commit:** b7f00f42
**Status:** fixed: requires human verification (logic change)
**Applied fix:** `refuseLocalOnlyMarketplace` now takes the write target and the installed record. It returns without refusing when the call is idempotent and writes no flag. A new helper, `idempotentWritesFlag`, holds the ENBL-05 rule "the targeted config carries the opposite explicit flag". The refusal and `resolveIdempotentOutcome` both use it, so they cannot drift apart. The refusal still runs at the same point in the call, before the cascade resolves and before EDEP-02. Three new tests:
- An idempotent enable renders `(skipped) {already enabled}` and writes nothing.
- An idempotent disable renders `(skipped) {already disabled}` and writes nothing.
- An idempotent enable whose base entry carries the opposite flag is still refused, so a fix that skipped every idempotent call would fail.

The first two fail against the code before the fix.
