### Locked Decisions

#### Named verbs (LAYER-04)
- **D-01 (user, q1):** `uninstall`, `enable`, `disable`, `update`, `reinstall` naming a plugin act on the target layer (shared by default, local with `--local`). When only the other layer declares the plugin they fail, changing nothing, with `plugin declared locally` (hint: run it again with `--local`) or `plugin declared in shared config` (hint: run it again without `--local`). Verbs naming no plugin cover both layers.

#### Both layers (LAYER-05)
- **D-02 (user, q5):** the same plugin may be declared in both layers of a scope; it is installed once per scope (each scope has its own marketplace clone, so the layers cannot drift apart). A declaration in both layers is legitimate (hand edits, a `git pull`).
- **D-03 (user, q5):** `install` into a layer while the other layer declares the plugin adds the declaration to the target layer, installs nothing, and reports `{already installed in [shared|local] layer}`, naming the other layer (a no-op install, not an error).
- **D-04 (user, q3):** `uninstall` from a layer while the other layer declares the plugin drops only the target layer's declaration, uninstalls nothing, and reports `{still installed in [shared|local] layer}` with the hint to repeat [with|without] `--local` to uninstall (a no-op uninstall, not an error).

#### Marketplace in the same layer (LAYER-06)
- **D-05 (user, q4):** a plugin declared in a layer must have its marketplace declared in the same layer. On load a violation is a configuration error for that layer, handled like an invalid layer file (CFG-03: the reload for that scope stops with the error).
- **D-06:** commands keep the rule true: `install --local` under a marketplace only the shared layer declares also declares the marketplace in the local layer (CR-02 synthesis into the target layer); a flagless install under a local-only marketplace stays refused (FIX-03, D-MF-02). Research checks every other writer of a plugin declaration (enable, disable, update/reinstall write-back, import, reconcile) against the rule.

#### Undeclared plugins (LAYER-08)
- **D-07 (user, q2):** an installed plugin that no layer declares is a dependency. A named `uninstall` of it is refused, changing nothing, and lists the plugins in the target layer that need it; when only plugins of the other layer need it, nothing is uninstalled (report why); it is uninstalled only when nothing needs it. Research proposes how the other verbs (enable, disable, update, reinstall) treat an undeclared dependency named directly, consistent with D-01.

#### Merge (LAYER-09)
- **D-08 (user):** plugin entries merge field by field across the layers, local winning on conflicts such as `enabled`. This reverses Phase 3.2's D-10 (plugins wholesale), whose reason (one layer per plugin) no longer holds.

#### Terminology
- **D-09 (user):** every new reason token, message, comment, and test title in this phase uses "scope" and "layer" as defined in PROJECT.md. Existing tokens are renamed in Phase 3.4, not here.

#### Tests
- **D-10 (user rules carried from 3.2 D-12):** real-Pi scenarios for what a real Pi reaches, test-first (C-10); separate `tests/integration/` tests for what a scenario cannot reach; paired unit tests exercise only their module with collaborators mocked per the typescript-unit-tests skill.

- How the configuration error of D-05 is surfaced (reuse the CFG-03 row shape and reason, or a dedicated reason), within "treat it as a configuration file error".

## Summary

Every plugin verb already has the inputs the partition needs, but each one reads the layers by a different rule today. `install`, `enable` and `disable` pick their file through `selectDeclaringConfigWriteTarget` (`orchestrators/plugin/shared.ts:693-730`), which follows the layer that already declares the key when no flag is typed (`resolveTargetIsLocal`, `shared.ts:750-760`). `update` and `reinstall` write back through `selectLayerWriteBack` (`shared.ts:1341-1402`), which writes `{}` for any key the target layer lacks. `uninstall` deletes the key from both layers (`sweepPluginFromConfigLayers`, `uninstall.ts:818-830`). The CR-02 marketplace synthesis treats both layers as one membership set (`synthesizeAdoptedMarketplaceSource`, `shared.ts:817-832`), so `install --local` never declares a shared marketplace in the local layer. The merge replaces a plugin entry whole (`config-merge.ts:104-111`), and the install's DFEN-05 precedence read relies on that (`install-declared-enabled.ts`). [VERIFIED: read this session]

The 3.2 marketplace partition is a direct template. Its pure verdict `marketplaceLayerVerdict` (`orchestrators/marketplace/shared.ts:1006-1061`), its "unreadable other layer refuses" rule (3.2 WR-03), its `{dependents remain}` refusal for a held plugin (`remove.ts:764-782`, 3.2 WR-02), and its transitive dependency walk `pruneOrphansReachableFrom` (`domain/dependency-orphans.ts:142-163`) cover most of what LAYER-04/05/08 need. The resolver already renders a cause line on any `skipped` row that carries `cause` (`shared/notification-resolve.ts:500`), and the wire schema already has an optional `cause` on every row (`notification-wire.ts` `PLUGIN_ROW`), so the D-04 hint needs only a type, not a renderer or wire change.

Three findings change the plan's shape. First, the update/reinstall write-back's "add" arm must go: under D-01 a named update requires the target layer to declare the key (or refuses), and under D-07 an undeclared record is a dependency that must stay undeclared. Today that arm also declares dependency records in `claude-plugins.json` from a bare `update`, from a bare `reinstall`, and from the load-time backfill (`backfill.ts:418-426` calls the reinstall with no flag), and it writes a plugin key without its marketplace, which D-05 would turn into a scope-wide load error. Second, D-08 and DFEN-05 must change together: `resolveInstallDeclaredEnabled` reads the local entry whole, so after a field merge an install under shared `{enabled:true}` plus local `{}` lands disabled while the merged view says enabled. Third, D-05 breaks existing data. Before this phase, `install --local` under a shared-only marketplace wrote exactly the shape D-05 forbids (UAT-05, pinned by `install-flow.test.ts:9611`), so every such scope stops reconciling after an upgrade. This needs a user decision (Open Question Q1).

**Primary recommendation:** Add one flag-only layer selector and one pure `pluginLayerVerdict` (mirroring `marketplaceLayerVerdict`, ideally sharing one generic helper to avoid a fallow clone) in `orchestrators/plugin/shared.ts`. Hook it in standalone mode only, at the points where the FIX-03 refusals sit today. Make the CR-02 gate target-layer-only for the plugin's own marketplace. Retire the update/reinstall "add" write-back. Add a read-pass layer-consistency check that reuses the CFG-03 `invalid-block` row. Switch plugin entries and `resolveInstallDeclaredEnabled` to field semantics in one task. Six new reason tokens; the D-07 refusal reuses `{dependents remain}`; the D-05 error reuses `{invalid manifest}`.

### Pattern 1: Flag-only selector plus pure verdict (replaces "follow the declaring layer")

```ts

type PluginLayerVerdict =
  | { readonly kind: "target-only" }                       // act
  | { readonly kind: "both" }                              // D-02/D-04 territory
```

### Pattern 3: No-op rows

- D-03 install: `(skipped) {already installed in <other> layer}`, `severity: "info"`, `needsReload: false`. `CASCADE_CONTEXT` already declares `skipped: { markers: false, contentReasons: true }` (`install-cascade.messaging.ts:93-99`). Put the two `already installed in ...` tokens in `IDEMPOTENT_REASONS` so `skipSeverity` returns `info` (`notify-reasons.ts:42-69`).
- D-04 uninstall: `(skipped) {still installed in <other> layer}` plus cause `Run the command again with --local to uninstall it.` (or `without --local`). `UNINSTALL_CONTEXT` has only `uninstalled` and `failed` (`uninstall.messaging.ts:32-38`), so add `skipped`. A `skipped` row with `cause` already renders a cause line (`notification-resolve.ts:500-503`), but only `PluginUpdateSkippedMessage` may set `cause` at the type level (`notification-types.ts:553-573`). Add one sibling interface for uninstall and enrol it in `PluginNotificationMessage` (`notification-types.ts:615-635`). Severity: `warning` (not an idempotent reason, so `skipSeverity` gives `warning`) -- see Open Question Q6.

### Anti-Patterns to Avoid
- **Reading the declaring layer when no flag is typed.** That is the D-103-13/16 rule D-01 retires. A flagless named verb always targets the shared layer.
- **Treating an unreadable other layer as "declares nothing".** Refuse with `{invalid manifest}` naming the file (3.2 WR-03, `remove.ts:624-629`).
- **Writing a plugin key without its marketplace** (`writePluginConfigEntry` in `maybeWritePluginConfigBack`, `shared.ts:1457-1466`). Under D-05 that file then stops its scope's reload.
- **A refusal that writes.** Every refusal arm returns before any `saveConfig` and before `tx.save()`.
- **Changing `mergeScopeConfigs` without `resolveInstallDeclaredEnabled`** (Pitfall 2).

## 7. Upstream parity (claude-code-compat-research evidence records)

The phase touches the install lifecycle, the command surface, scope and enablement, so the upstream contract applies. Claude Code has three settings scopes (user, project, local) and a per-scope install record; this project maps Claude Code's `local` settings file to a scope's local layer (SC-1 declines a third scope).

**Record 1: one plugin declared in project and local settings.**
- Claude Code: "These sources merge key by key. For each plugin id, the value that applies is the one from the highest-precedence source that mentions the id. A source that doesn't mention the id leaves the value from the lower-precedence source in effect." Order lowest to highest: `--add-dir`, `user`, `project`, `local`, `flag`, `managed`. "To opt out of a project-enabled plugin on your machine, set the id to `false` in `.claude/settings.local.json`".
- Evidence: https://code.claude.com/docs/en/plugins/loading (read 2026-10-17). Confidence high.
- Verdict: D-08 matches upstream (local wins per key; a local entry without `enabled` "doesn't mention" the value, so shared applies). D-02 (both layers legitimate) matches.

**Record 2: enable/disable with a scope that does not declare the plugin.**
- Claude Code: "Without `--scope`, the command checks your settings files in the order local, project, user, and uses the first scope that mentions the plugin. If you pass a `--scope` where the plugin isn't declared ... A scope that takes precedence over the declaring one: Claude Code writes an override at the scope you passed. For example, `claude plugin disable formatter --scope local` turns off a project-enabled plugin for you alone. Any other scope: the command fails with `Plugin "formatter" is installed at project scope, not user. ## Common Pitfalls

### Pitfall 1: Legacy local layers stop the scope's reload
**What goes wrong:** existing users with a pre-3.3 `install --local` hit a CFG-03-style stop on every reload. **Why:** D-05 turns a shape the old code wrote by default into an error. **Avoid:** settle Q1 before planning; at minimum the cause names the fix (`marketplace add <source> --local` re-declares without a clone, LAYER-01). **Warning sign:** an integration case seeded with the old shape renders `(failed) {invalid manifest}`.

### Pitfall 2: D-08 without DFEN-05
**What goes wrong:** shared `{enabled:true}` + local `{}` installs disabled and stamps `enabled:false` into local. **Why:** `resolveInstallDeclaredEnabled` reads the local entry whole. **Avoid:** change both in one task; add a case for exactly that pair.

### Pitfall 3: Flagless enable/disable shadowed by a local `enabled`
**What goes wrong:** the command flips state and writes the shared layer; the next reload flips it back. **Avoid:** Q3.

### Pitfall 4: A refusal hook after a write or a network call
**What goes wrong:** update refusals after the preflight touch the network (3.1 WR-02); uninstall refusals after `sweepConfigLayers` leave a layer edited. **Avoid:** verdict first; assert config and state bytes unchanged.

### Pitfall 5: The write-back removal hides an S5 surface
**What goes wrong:** catalog states, `ReinstallReinstalledOutcome.invalidConfigFile`, `surfaceReinstallInvalidConfigFiles` and update's S5 rows become dead; fallow dead-code fails if any export is left. **Avoid:** remove them in the same task and drop their catalog states and pins.

### Pitfall 6: Two cognitive-complexity gates
ESLint `sonarjs/cognitive-complexity` 15 and fallow `maxCognitive` 15 disagree; the uninstall and enable-disable closures are already near the ceiling. Extract the verdict handling into helpers (`uninstall.ts` already extracts `emitCascadeFailure`, `emitConfigInvalid`).

### Pitfall 7: fallow dupes between the plugin and marketplace verdicts
A near-copy of `marketplaceLayerVerdict` forms a clone group (threshold 3). Share one helper.

### Pitfall 8: `the user has run {string}` requires severity `info`
A D-04 no-op (warning) cannot be a `Given`; use the D-03 no-op (info) as setup.

### Pitfall 9: Existing unit tests pin the old semantics
§1 lists them per verb. Rewrite them in the task that changes the behavior, with the old assertion inverted where the behavior flips, so the RED run is visible.

## Open Questions (for the user; the locked decisions do not settle these)

1. **Q1 (legacy layers).** Pre-3.3 `install --local` under a shared-only marketplace left `claude-plugins.local.json` declaring `p@mp` without `mp`. Recommendation: (a), with the cause naming `marketplace add <source> --local`.
2. **Q2 (`dangling reference`).** A plugin key whose marketplace neither layer declares is a per-entry `{dangling reference}` row today (D-16). Recommendation: only the cross-layer case, keeping D-16.
3. **Q3 (shadowed flagless enable/disable).** Flagless `enable p` when the local layer says `enabled: false` writes the shared layer and enables the plugin, and the next reload disables it again (local wins, D-08). Refuse it? Recommendation: refuse, changing nothing, reusing `plugin declared locally` with the cause `The plugin p@mp is disabled in the local layer (claude-plugins.local.json), which overrides the shared layer. Run the command again with --local.` (upstream `governed_elsewhere` analog).
4. **Q4 (D-07 details).** (a) When only other-layer plugins need the dependency: a failed `{dependents remain}` row (error), or a `(skipped)` no-op row like D-04 (warning)? Recommendation: failed `{dependents remain}` with a cause naming the plugins and their layer. (b) For enable/disable/update/reinstall of a dependency: act (enable/disable declare it in the target layer; update/reinstall write nothing), or refuse? Recommendation: act (§4); it keeps the EDEP-02 remedy "Disable A first, then B" usable.
5. **Q5 (`--local` on nameless update/reinstall).** With the write-back gone it changes nothing. Options: (a) restrict to plugins the local layer declares (3.2 D-09 autoupdate precedent), (b) ignore the flag, (c) reject it as a usage error. Recommendation: (a).
6. **Q6 (D-04 severity).** `(skipped) {still installed in <other> layer}`: `warning` (the plugin the user asked to uninstall is still installed) or `info` (the target layer's declaration is gone)? Recommendation: `warning`.
