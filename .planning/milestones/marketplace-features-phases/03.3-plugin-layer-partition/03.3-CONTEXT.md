# Phase 3.3: Plugin Layer Partition - Context

**Gathered:** 2026-10-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Partition the plugin verbs by layer and settle how the two layers of a scope relate for plugins (LAYER-04, -05, -06, -08, -09; D-MF-03 as revised 2026-10-17). Use the terms of PROJECT.md "Terminology: Scope and Layer": a **scope** (user or project) owns state, marketplace clones, and installations; a **layer** (shared `claude-plugins.json`, local `claude-plugins.local.json`) only declares intent; the **effective configuration** is the two layers merged field by field, local winning.

In scope: `plugin install`, `uninstall`, `enable`, `disable`, `update`, `reinstall` (named and nameless forms), the load-time check that a plugin's marketplace is declared in the same layer, the plugin-entry field merge, scenarios, integration tests, unit tests, catalog, docs, CHANGELOG.
Out of scope: renaming existing reason tokens, docs, and identifiers to the new terms (Phase 3.4); the latent problem of Pi loading the same plugin installed in both scopes (deferred by the user).

**Today's behavior (scouted 2026-10-17):**
- `install`, `enable`, `disable` pick the layer through `selectDeclaringConfigWriteTarget` (`orchestrators/plugin/shared.ts:~693`): `--local`, or the layer that already declares the key, else shared. `install --local` of a plugin only the shared layer declares writes a second, local entry.
- `update`/`reinstall` write back through `selectLayerWriteBack` (flag only; flagless never writes the shared layer for a locally declared key or a local-only marketplace).
- `uninstall` deletes the key from both layers regardless of `--local` (`uninstall.ts:~818`, `sweepPluginFromConfigLayers`); `--local` only picks the file checked for CFG-03.
- The merge replaces a plugin entry wholesale (DFEN-05); marketplace entries merge field by field since Phase 3.2.
- On load, a plugin declared in one layer whose marketplace only the other layer declares is planned as a normal install (`reconcile/plan.ts ~450-475` checks the merged marketplaces).
- FIX-03 refusals (Phase 3.1) cover install/enable/disable/update/reinstall under a local-only marketplace for the shared layer.

</domain>

<decisions>
## Implementation Decisions

### Named verbs (LAYER-04)
- **D-01 (user, q1):** `uninstall`, `enable`, `disable`, `update`, `reinstall` naming a plugin act on the target layer (shared by default, local with `--local`). When only the other layer declares the plugin they fail, changing nothing, with `plugin declared locally` (hint: run it again with `--local`) or `plugin declared in shared config` (hint: run it again without `--local`). Verbs naming no plugin cover both layers.

### Both layers (LAYER-05)
- **D-02 (user, q5):** the same plugin may be declared in both layers of a scope; it is installed once per scope (each scope has its own marketplace clone, so the layers cannot drift apart). A declaration in both layers is legitimate (hand edits, a `git pull`).
- **D-03 (user, q5):** `install` into a layer while the other layer declares the plugin adds the declaration to the target layer, installs nothing, and reports `{already installed in [shared|local] layer}`, naming the other layer (a no-op install, not an error).
- **D-04 (user, q3):** `uninstall` from a layer while the other layer declares the plugin drops only the target layer's declaration, uninstalls nothing, and reports `{still installed in [shared|local] layer}` with the hint to repeat [with|without] `--local` to uninstall (a no-op uninstall, not an error).

### Marketplace in the same layer (LAYER-06)
- **D-05 (user, q4):** a plugin declared in a layer must have its marketplace declared in the same layer. On load a violation is a configuration error for that layer, handled like an invalid layer file (CFG-03: the reload for that scope stops with the error).
- **D-06:** commands keep the rule true: `install --local` under a marketplace only the shared layer declares also declares the marketplace in the local layer (CR-02 synthesis into the target layer); a flagless install under a local-only marketplace stays refused (FIX-03, D-MF-02). Research checks every other writer of a plugin declaration (enable, disable, update/reinstall write-back, import, reconcile) against the rule.

### Undeclared plugins (LAYER-08)
- **D-07 (user, q2):** an installed plugin that no layer declares is a dependency. A named `uninstall` of it is refused, changing nothing, and lists the plugins in the target layer that need it; when only plugins of the other layer need it, nothing is uninstalled (report why); it is uninstalled only when nothing needs it. Research proposes how the other verbs (enable, disable, update, reinstall) treat an undeclared dependency named directly, consistent with D-01.

### Merge (LAYER-09)
- **D-08 (user):** plugin entries merge field by field across the layers, local winning on conflicts such as `enabled`. This reverses Phase 3.2's D-10 (plugins wholesale), whose reason (one layer per plugin) no longer holds.

### Terminology
- **D-09 (user):** every new reason token, message, comment, and test title in this phase uses "scope" and "layer" as defined in PROJECT.md. Existing tokens are renamed in Phase 3.4, not here.

### Tests
- **D-10 (user rules carried from 3.2 D-12):** real-Pi scenarios for what a real Pi reaches, test-first (C-10); separate `tests/integration/` tests for what a scenario cannot reach; paired unit tests exercise only their module with collaborators mocked per the typescript-unit-tests skill.

### Research answers (user, 2026-10-17; see 03.3-RESEARCH.md open questions)
- **D-11 (Q1):** no automatic repair of local layers written before this phase that declare a plugin without its marketplace; the load error's cause tells the user to run `marketplace add <source> --local`.
- **D-12 (Q2):** a plugin whose marketplace no layer declares keeps today's per-entry `{dangling reference}` row; the whole-layer configuration error (D-05) applies only when the other layer declares the marketplace.
- **D-13 (Q3):** a flagless `enable` (or `disable`) that the local layer's opposite `enabled` overrides is refused, changing nothing, with `{disabled in local layer}` (or `{enabled in local layer}`) and the hint "repeat with --local to enable" (or disable), worded to match `{still installed in [shared|local] layer}`.
- **D-14 (Q4):** a named uninstall of a dependency that only plugins of the other layer need is a skipped no-op row; `enable`, `disable`, `update`, `reinstall` naming a dependency act on it.
- **D-15 (Q5):** `update`/`reinstall` naming no plugin with `--local` cover only the plugins the local layer declares; without the flag, both layers. **Amended (user, 2026-10-17, review IN-05):** with `--local` they also cover the dependencies those local-layer plugins need, walked transitively through installed plugins that no layer declares (the LAYER-08 needer walk read forwards). A dependency that only shared-layer plugins need is not covered, and a plugin the shared layer declares ends the walk. Without the flag, the nameless forms still cover every installed plugin. **Amended again (user, 2026-10-17, verification):** when the walk cannot read the dependencies of a plugin it visits, the whole `--local` form refuses with `{unreadable}` and changes nothing; the cause names that plugin, path-redacted, as `uninstall` and `marketplace remove` refuse (D-05-07: corrupt data is not papered over). An unreadable `claude-plugins.json` also stops the nameless `--local` form (CFG-03), because it decides where the walk ends (user confirmed).
- **D-16 (Q6):** the no-op uninstall row (`still installed in ... layer`) has warning severity.
- **D-17 (Q7):** use "layer" in every new token and message; keep D-01's two approved spellings for now and rename both families (marketplace and plugin) together in Phase 3.4.
- **D-18 (Q8, user):** a scenario may construct a layer file outside of commands to model a hand edit or a version-control update (for the shared layer), with one setup step built from its elements, for example:
  `Given a plugin configuration file in scope <scope> and layer <layer>, with these plugins:` and a table `| marketplace | plugin | enabled |`. It is the only config step that writes; every other config step stays read-only. Record the exception in `.agents/skills/cucumber/rules/steps.md`. The D-05 configuration error gets a real-Pi scenario through it.
- **D-19 (Q9):** `install` into a layer while the other layer declares the plugin but it is not installed installs it normally and declares it in the target layer.
- **D-20 (Q10):** the D-07 refusal diverges from Claude Code (which uninstalls a needed plugin and reports its dependents); record the divergence in D-MF-03 in PROJECT.md.
