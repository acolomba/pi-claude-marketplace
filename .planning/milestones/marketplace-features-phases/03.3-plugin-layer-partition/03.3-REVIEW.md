# Phase 3.3: Code Review Report

**Reviewed:** 2026-10-17T20:11:57Z

## Summary

I reviewed the production diff `f4f38b82..HEAD`, the new scenarios, the writing config step, the two integration files, and the docs. I traced the layer rules against CONTEXT D-01..D-20 for each verb, and checked them against the Phase 3.2 marketplace `remove` and `autoupdate` code.

These parts hold:

- A refusal leaves before any write in every named verb (uninstall, enable, disable, update, reinstall). Update refuses before the preflight, so a refused update touches no network.
- Orchestrated paths never meet a layer rule. Uninstall reads no other layer when orchestrated, enable and disable return early, install skips the no-op, and update and reinstall gate on `cascade`, `cardinality`, or `named`.
- The field merge and `resolveInstallDeclaredEnabled` agree.
- A layer `marketplace remove` drops both the target layer's marketplace entry and its `*@<marketplace>` keys. A full remove sweeps both layers. So neither remove leaves an orphaned plugin key that would trip the new load error. A plugin that both layers declare stays installed through a layer remove.
- The load error can be repaired by command: through `marketplace add <source> --local` (LAYER-01 redeclare), through `uninstall --local`, or as a side effect of `enable --local`.

I found no BLOCKER. These five warnings need a fix:

1. The repair command printed by the new load error is wrong for the project scope.
2. The new target-only marketplace gate widens the known S4 dangling-key arm into a whole-scope load stop.
3. The reinstall layer-refusal classifier also matches every corrupt-manifest error.
4. In the MIG-01 window, the pending check and the load check disagree (WINDOWS #99, confirmed real).
5. The uninstall catalog intro now contradicts the new dependency rule next to it.

## Warnings

### WR-01: The repair command in the load-time layer error omits `--scope`, so following it in a project scope changes the user scope

**File:** `extensions/pi-claude-marketplace/orchestrators/reconcile/reconcile.messaging.ts:133-143` (also `CHANGELOG.md:15`, `README.md:188`, `README.es.md:186`, catalog states `reload-layer-marketplace-undeclared` / `pending-layer-marketplace-undeclared`)

**Issue:** `composeLayerMarketplaceCause` tells the user to run `/claude:plugin marketplace add <source> --local`. It never names a scope. `marketplace add` defaults to the **user** scope (`edge/handlers/marketplace/add.ts:43`, `scope: opened.scope ?? "user"`).

Failure scenario:

1. A project's `claude-plugins.local.json` declares `demo@fixtures` (the shape every pre-phase `install --local` left).
2. The next reload stops the project scope with `⊘ claude-plugins.local.json [project] (failed) {invalid manifest}`.
3. The user types the printed command. It runs at user scope. It either redeclares a user-scope record in `~/.pi/agent/claude-plugins.local.json`, or clones the source into the user scope (network for a git source) and records a new user-scope marketplace.
4. The project error stays. The user now has an unrequested user-scope marketplace that a later reload will reconcile.

D-11 promises the user a manual repair through this cause, and it is the only repair path, so the printed command must be right.

**Fix:** Pass the scope into the cause and print it:

```ts
export function composeLayerMarketplaceCause(gap: LayerMarketplaceGap, scope: Scope): string {
  const other = gap.layer === "local" ? "shared" : "local";
  const one = gap.keys.length === 1;
  const flags = `${gap.layer === "local" ? " --local" : ""} --scope ${scope}`;
  return (
    `The ${gap.layer} layer (${LAYER_FILES[gap.layer]}) declares ${renderDependentKeys(gap.keys)}, ` +
    `but only the ${other} layer declares ${one ? "its marketplace" : "their marketplaces"}. ` +
    `Run /claude:plugin marketplace add <source>${flags} with the source the ${other} layer declares, ` +
    `or remove ${one ? "the plugin" : "the plugins"} from the ${gap.layer} layer.`
  );
}
```

Thread `scope` from `apply.ts:layerMarketplaceGapOutcomes` and `pending.ts:invalidConfigBlocks`, which both have it. Update the catalog bytes, the scenarios, and the CHANGELOG and README sentences to name `--scope`.

### WR-02: The target-only marketplace gate turns the S4 "no string `source.raw`" arm into a scope-wide load stop

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/shared.ts:877-891` (with `synthesizeUndeclaredMarketplaceSource`, `:568-580`)

**Issue:** The plugin's own marketplace is now gated on `[opts.current]` alone (LAYER-06). Before this phase, the gate read both layers. When the target layer lacks the marketplace and the state record has no string `source.raw`, the helper returns `undefined`. This is the S4 "dangerous" arm (forward-compat `unknown`-kind sources admitted by ST-6 / NFR-12). The write then declares the plugin key alone.

Before this phase that arm was reachable only when **no** layer declared the marketplace, and the result was a per-entry dangling row. Now it also fires when the **other** layer declares the marketplace. It writes exactly the shape D-05 forbids, so the scope's next reload stops with `{invalid manifest}`.

Three callers reach it:

- `install --local` under a shared-only marketplace
- the D-03 install no-op (`declareInstalledPlugin`)
- `enable --local` / `disable --local` (`writeEnabledFlagBack`)

The command itself reports success.

**Fix:** When the record has no string `raw`, fall back to the source string the other layer already declares. That string is what the merged view, and therefore `samePlannedSource`, already uses:

```ts
function synthesizeUndeclaredMarketplaceSource(
  scopeConfigs: readonly ScopeConfig[],
  state: ExtensionState,
  marketplace: string,
  fallback?: ScopeConfig,
): string | undefined {
  if (scopeConfigs.some((c) => ownValue(c.marketplaces, marketplace) !== undefined)) {
    return undefined;
  }
  const raw = (ownValue(state.marketplaces, marketplace)?.source as { raw?: unknown } | undefined)?.raw;
  if (typeof raw === "string") {
    return raw;
  }
  const declared = ownValue(fallback?.marketplaces, marketplace)?.source;
  return typeof declared === "string" ? declared : undefined;
}
```

Pass `opts.sibling` as `fallback` for the plugin's own marketplace. Alternatively, refuse the write with a failed row. That is the discriminated return the S4 comment already asks for.

### WR-03: `isLayerRefusal` matches every `InvalidMarketplaceManifestError`, so bulk reinstall rows now render manifest-parser text as a cause line

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/reinstall-record.ts:128-139,174`; contract at `extensions/pi-claude-marketplace/orchestrators/types.ts:158-164`

**Issue:** The new classifier treats any `InvalidMarketplaceManifestError` as "a named reinstall's layer refusal" and attaches it as `cause`. That class is also thrown by `domain/manifest.ts:116,131`: `marketplace.json is not valid JSON: ${String(err)}` and `marketplace.json schema invalid: ...`. `loadCachedEntry` (`reinstall-flow.ts:918-930`) reaches it on every reinstall.

In the plural path, `reinstall.messaging.ts:292` renders `outcome.cause` only when it is set. Before this phase it was set only for the FIX-03 refusal. The bare and `@<marketplace>` forms never pass `named`, so they can never produce a layer refusal. On those forms the only way `cause` is set now is this unintended match.

Failure scenario: `reinstall @mp` runs with a corrupt cached `marketplace.json`. Each row now carries `cause: marketplace.json is not valid JSON: SyntaxError: Unexpected token ..., "<file content snippet>" is not valid JSON`. That text comes from a cloned, possibly third-party repository. This breaks the documented rule that only text built from fixed strings, safe names, or a basename reaches a cause line. The row's reason may also move from its old narrowed token to `invalid manifest`.

**Fix:** Give the layer-file refusal its own class, the way `marketplace/add.ts:463` does with `ConfigInvalidError`. Then test for that class only:

```ts
// shared/errors.ts
export class LayerFileUnreadableError extends InvalidMarketplaceManifestError {
  constructor(basename: string) {
    super(`Config file "${basename}" failed schema validation.`);
    this.name = "LayerFileUnreadableError";
  }
}
// shared.ts unreadableLayerError -> new LayerFileUnreadableError(path.basename(filePath))
// reinstall-record.ts isLayerRefusal -> ... || error instanceof LayerFileUnreadableError
```

Add a reinstall-record case: a plain `InvalidMarketplaceManifestError` gets no `cause`.

### WR-04: In the MIG-01 window, `pending` checks the layer gap on the files on disk while the load checks it after migration (WINDOWS #99, confirmed)

**File:** `extensions/pi-claude-marketplace/orchestrators/reconcile/pending.ts:135-152,241-245` versus `apply.ts:213-266`

**Issue:** `apply.ts` runs `migrateFirstRunConfig` first. That writes `claude-plugins.json` from state, including every marketplace the local layer does not declare (`buildConfigFromState`). It then runs `findLayerMarketplaceGaps`.

`pending.ts` runs `invalidConfigBlocks` on the raw outcome before it loads state. So while `claude-plugins.json` is absent, the shared side reads as `{}` and no local gap is ever found.

Failure scenario:

1. `claude-plugins.json` is absent, `state.json` records `mp`, and the local layer declares `X@mp` without `mp`.
2. `pending` shows a normal plan (it plans against `mergedViewForPlanning`, which does model the migration).
3. The next reload stops the scope with `{invalid manifest}`.

This breaks the DIFF-01 rule that pending shows what the next load sees. Only a hand edit reaches the window, because a pre-phase `install --local` with no shared file synthesized `mp` locally. So it is narrow but real, and the recorded `[marketplace-features]` deviation should stay open until it is fixed.

**Fix:** Run the gap check after `loadState`, against the same view the planner uses:

```ts
const sharedForGap =
  outcome.base.status === "absent" && state !== undefined
    ? buildConfigFromState(state, localConfig)
    : outcome.base.status === "valid" ? outcome.base.config : {};
const gaps = findLayerMarketplaceGaps(sharedForGap, localConfig);
```

Keep the CFG-03 invalid-file blocks where they are, because they must not need a readable state. Add a pending case for the window and close WINDOWS #99.

### WR-05: The uninstall catalog intro, which this phase edited, still says an uninstall is refused while a dependent exists, which contradicts LOAD-03 and the new LAYER-08 prose

**File:** `docs/output-catalog.md:1124` (contradicts `:1254` and `:1328`)

**Issue:** The paragraph gained this phase's layer sentence. It still states: "An uninstall is refused while another installed plugin in the same scope still declares the target as a dependency (PRUNE-05 / D-05-14): nothing is removed and the row names the dependents."

The code refuses only on an unreadable declarer (D-05-07). A declared plugin is removed with `{dependents unsatisfied}` (LOAD-03 state at `:1254`). The new LAYER-08 prose at `:1328` says "a plugin that a layer declares is uninstalled even when other plugins need it".

A reader of the section now gets two opposite rules in the very area this phase changed. The undeclared-dependency refusal is the new, narrower rule.

**Fix:** Replace the PRUNE-05 sentence with the rule as it now stands, for example: "A plugin a layer declares is uninstalled even while another installed plugin still declares it (the row names the dependents, LOAD-03). A plugin no layer declares is refused while a plugin of the target layer needs it, and skipped while only plugins of the other layer do (LAYER-08)."
