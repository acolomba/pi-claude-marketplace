# Phase 3.4 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

---

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| extension -> JSON consumers | Scripts read the closed reason tokens from `json` and `rpc` output and the published schema | Reason tokens, schema enums |
| orchestrator -> rendered row | Plugin and marketplace names and the two config basenames reach the user's screen | Names, config basenames |
| layer files -> uninstall decision and layer verdicts | Which layer declares the plugin picks refusals, no-ops, writes, the kept-installed token, and the needed-elsewhere cause | Per-scope layer config |
| layer files -> load-time and pending error | Plugin keys from a hand-edited user file are interpolated into the cause line | Plugin keys |
| cloned repository -> cached manifest -> cause line | A `marketplace.json` or plugin manifest from a remote repository is parsed offline; the declaration read's failure message is the cause line and the JSON cause chain | Manifest bytes, parser errors, cause text |
| architecture gates -> production source | Gates match identifiers in source text, so a rename can silently disarm one | Identifiers |
| scope root -> config paths | Both layer configs are written only through `saveConfig` inside the scope root (NFR-10) | Config paths |
| comments, tests, scenario titles -> maintainers and readers | They state the layer rules that the code enforces and the tests prove; a bulk edit can weaken a proof | Comments, test titles, steps |
| test step -> sandbox | The one writing config step writes a layer config inside the scenario sandbox | Layer configs |
| docs and gate record -> users and verifier | The READMEs, guides, catalog, and CHANGELOG describe the configs and tokens; the SUMMARY is the gate evidence | Docs, rows |
