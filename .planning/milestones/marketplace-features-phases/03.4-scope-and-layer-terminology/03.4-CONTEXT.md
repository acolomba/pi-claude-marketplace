# Phase 3.4: Scope and Layer Terminology - Context

**Gathered:** 2026-10-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Apply the PROJECT.md "Terminology: Scope and Layer" consistently across reason tokens, messages, catalog, docs, README, CHANGELOG, and code identifiers (TERM-01; ROADMAP Phase 3.4 SC1-SC4). No behavior change except the renamed tokens and message wording, and the parser-detail drop (SC4).

Terms (user, 2026-10-17):
- **scope:** user or project.
- **layer:** base or local; a level, like a scope, not a file.
- **config:** the file holding a layer's declarations: base config `claude-plugins.json`, local config `claude-plugins.local.json`.
- Code says `base` and `local`, never `shared`.

</domain>

<decisions>
## Implementation Decisions

- **D-01 (user):** tokens: `marketplace declared locally` → `marketplace in local layer only`; `marketplace declared in shared config` → `marketplace in base layer only`; `plugin declared locally` → `plugin in local layer only`; `plugin declared in shared config` → `plugin in base layer only`; every token saying "shared layer" (for example `already installed in shared layer`, `still installed in shared layer`) says "base layer". The JSON contract change is recorded in the CHANGELOG with the old and new token. **Amended (user, 2026-10-17):** no old-to-new rename list in the CHANGELOG, because none of the old tokens shipped in a release; the existing Unreleased entries just use the new tokens.
- **D-02 (user):** code standardizes on `base` and `local`: `configJsonPath` → `baseConfigJsonPath`, `configLocalJsonPath` → `localConfigJsonPath`; error classes, functions, variables, test helpers, and comments follow (for example `PluginDeclaredInSharedConfigError` → a base-layer name); IN-02 renames (`selectDeclaringConfigWriteTarget`, `DeclaringConfigWriteTarget`, `UninstallTransaction.loadTargetConfig`) to names that say what they do. No behavior change.
- **D-03 (user):** prose: "the base layer"/"the local layer" for the level; "the base config"/"the local config" (or "the local layer config") for the file, naming the file on first mention, for example "the local config (`claude-plugins.local.json`)". Make it read naturally.
- **D-04 (user):** the `{unreadable}` cause for unreadable dependency declarations drops the parser's detail: it names the record only (for example "cannot read the dependencies of lib@tools"), for `uninstall`, `marketplace remove`, and the nameless `update --local`/`reinstall --local`. **Amended (user, 2026-10-17):** drop only the parser's text, the detail that comes from repository content, in the shared cause builder, everywhere the `{unreadable}` dependency-declarations cause appears; keep the fixed reasons written by this extension (for example "not declared by its marketplace"). So a manifest that fails to load gives "cannot read the dependencies of lib@tools", while "cannot read the dependencies of other@official: not declared by its marketplace" stays as it is.
- **D-04 follow-up (review IN-10, 2026-10-18):** a manifest that fails to load now gives a fixed reason chosen by error class or errno, never by message text: "its marketplace manifest is invalid", "... is missing", or "... cannot be read" (for example "cannot read the dependencies of lib@tools: its marketplace manifest is missing"). Repository text still never reaches the cause line; the leftover gate G4 allows these three fixed reasons.
- **D-05:** user-facing CLI flags (`--local`, `--scope`) do not change.

### Claude's Discretion
