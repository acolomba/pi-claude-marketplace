## Warnings

### WR-01: The D-04 CHANGELOG entry names 4 commands, but the change reaches at least 8

**File:** `CHANGELOG.md:5`

**Issue:** The bullet says that only `uninstall`, `marketplace remove`, `update --local`, and `reinstall --local` stopped showing the parser error. The change lives in the shared builder (`dependency-index.ts:196-198`), so every command that renders that cause changed too:

- `enable` (the cascade walk, `enable-disable.ts:652`)
- `disable` (the EDEP-02 dependents refusal, `enable-disable.ts:1554`)
- `prune` / `prune --dry-run` (`prune.ts:233,344`)
- named `update <plugin>@<marketplace>` (the `held` skip cause, `update-constraint-gate.ts:458`)

Concrete scenario: a user runs `prune` over a scope whose marketplace manifest is malformed. They used to see `cause: cannot read the dependencies of x@mp: marketplace.json schema invalid: ...`. Now they see `cause: cannot read the dependencies of x@mp`, and the CHANGELOG does not mention `prune` at all. D-04 as amended says "everywhere the `{unreadable}` dependency-declarations cause appears". The changelog entry does not match.

**Fix:** Describe the change without a command list. For example:

```markdown
- When a command cannot read a plugin's dependencies, its `{unreadable}` cause now names only the plugin and no longer shows the manifest's parser error.
```

### WR-02: `writeAdoptingConfigEntries` now takes the target layer twice

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/shared.ts:955-972`

**Issue:** The function used to derive the config name for `MarketplaceSourceUndeclarableError` from `path.basename(opts.targetConfigPath)`, so the name could not disagree with the file being written. The rename added a separate required `targetIsLocal` next to `targetConfigPath`. These are two encodings of one fact, and nothing checks that they agree. Every current caller passes both from one `TargetLayers` selection, so nothing is wrong today. But the seam is injectable (`EnableDisableTransaction.writeConfigEntries`), and `PromotionArgs.config` (`install-flow.ts:1308-1313`) now carries both fields by hand. A future caller that pairs `localConfigJsonPath` with `targetIsLocal: false` would refuse with "Declare the marketplace in the base config" while the write targets the local config. That is a wrong remedy on a user-facing cause line.

**Fix:** Keep one source of truth. Either pass the loaded selection:

```ts
export async function writeAdoptingConfigEntries(opts: {
  readonly selection: Pick<LoadedTargetLayers, "current" | "other" | "targetConfigPath" | "targetIsLocal">;
  ...
})
```

or derive the layer inside the function from the path the scope's locations name:

```ts
const layer = opts.targetConfigPath === locationsForRoot.localConfigJsonPath ? "local" : "base";
```

### IN-10: The load-failure arm now discards the error with no trace

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/dependency-index.ts:196-198`

**Issue:** `catch { return unreadableDeclarer(key); }` makes these failures look the same: ENOENT (a deleted clone), EACCES (permissions, which is OS text, not repository text), and a schema-invalid manifest. Nothing is logged, so an operator who sees `{unreadable}` has no way to find which one happened, other than re-running `marketplace update`. This follows the D-04 decision, so it is not a defect. It is a diagnosability cost worth a note in the catalog's remedy text.

**Fix (optional):** Classify errno failures to their existing closed-set reasons (`permission denied`, `source missing`) through the fixed-reason argument, for example `unreadableDeclarer(key, "its marketplace manifest is missing")`. Keep every parser or schema text out.
