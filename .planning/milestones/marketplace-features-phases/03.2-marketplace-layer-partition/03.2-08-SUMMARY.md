# Phase 3.2 Plan 08: A project keeps the marketplace its install added Summary

**An integration test drives the real add, install, remove, list, info, and update code against a local checkout and a git double. It shows that a project install from a user-scope git marketplace makes the project its own clone and record, and that a user-scope remove leaves the project working. A standalone install now also declares, in the same write as the root's key, every marketplace it added for a dependency. Real-Pi scenarios pin both, with url and github rows that turn on with the stand-ins.**

## Accomplishments

- `tests/integration/project-install-adds-user-marketplace.test.ts` (new, 5 cases). The install's `marketplaceAdd` seam is bound to `addMarketplaceToState` and `settleAddedMarketplace` with the git double spread in. The double's `localRefs` carry `refs/remotes/origin/HEAD`, and every case runs in a hermetic environment under a strict notification boundary.
  - `LAYER-07: a project keeps the marketplace its install added after a user-scope remove`: after `marketplace remove mp --scope user`, the project's `p-greet` skill stays. The six notifications are compared whole: the user add, the install, the user remove, `Plugin list: 1 success`, the info row with `skills: greet`, and `● mp [project] (skipped) {up-to-date}`. The update fetches only the project clone and creates nothing under the user extension root. The clone calls are `[REPO_URL, user]` and `[REPO_URL, project]`. The project clone holds `.git/pi-claude-marketplace.json` and the origin `REPO_URL`. The project record's roots are `sources/mp` inside the project extension root, and its source equals the user record's. The project `claude-plugins.json` bytes are compared.
  - `LAYER-07 / WR-07: an install of a plugin the manifest does not list leaves the project without the marketplace`: two clones were made, and the project has no record, no `sources/`, no `sources-staging/` entry, and no config file.
  - `MA-12: a project install replaces the extension's own leftover clone of the marketplace`: a leftover with the marker and a matching origin is replaced, and the install succeeds.
  - `MA-13: a project install refuses a foreign tree where the marketplace clone goes and keeps it`: the install fails with the stale-clone cause, and the tree's bytes and the empty project footprint stay.
  - `LAYER-07: a project install adds the user-scope git marketplace of its dependency to the project`: `app@upstream` (a user-scope path marketplace) pulls `lib@tools` (a user-scope url marketplace). The project gets its own `sources/tools/` with the marker, both records, and (after Task 2) a config that declares `upstream` and `tools` and only `app@upstream`.
- `orchestrators/plugin/shared.ts`: `writeAdoptingConfigEntries` takes `addedMarketplaces?: readonly string[]`. It runs the root's marketplace and each further name through `synthesizeAdoptedMarketplaceSource` and declares every name that returns a source in the one batched patch. The JSDoc keeps D-04-02 for plugin keys and adds the LAYER-07 / D-MF-04 rule.
- `orchestrators/plugin/install-flow.ts`: the standalone write-back passes the names on the transaction's list of added marketplaces, other than the root's. The two D-04-02 comments now say that no dependency plugin gets a key. The orchestrated arm is unchanged.

## Decisions Made

- **One patch, always.** `writeAdoptingConfigEntries` builds its marketplace entries with `flatMap` and `Object.fromEntries`, and it always passes them. An empty patch writes the same bytes as an absent one, so the conditional spread was dropped rather than duplicated.
- **The integration double.** One git double per case covers the user add, the install's add, and the update. It counts the clones across both scopes, and its seeded `origin/HEAD` lets the update finish.
- **Assertion order in the remove case.** The post-remove notifications come first, so the planted RED shows the behavior SC4 names (the failing list, info, and update) rather than the clone count.
