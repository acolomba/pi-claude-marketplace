# Phase 3.2 Plan 05: Dependency retention on marketplace remove Summary

**A marketplace remove now takes the dependency records under the marketplace that only its removed plugins pulled in, keeps the ones a staying plugin still declares (across layers and across marketplaces), and refuses with `{unreadable}`, changing nothing, when the scope's dependency declarations cannot be read.**

## Accomplishments

- `domain/dependency-orphans.ts`: `pruneOrphansReachableFrom(records, index, removed)` walks the index from the removed keys, keeps the candidates it reaches, and hands them to `pruneOrphans`. So the order still puts dependents before dependencies. An orphan no removed plugin reaches stays for `prune` to report.
- `orchestrators/marketplace/remove.ts`:
  - New option `declarationIndex?: typeof buildScopeDeclarationIndex` (a seam; production uses the offline reader).
  - `readRetentionIndex` builds the scope index inside the lock, after the layer gate and before any cascade, but only when the marketplace record holds a `provenance: "dependency"` record. A failure throws `DeclarationIndexStop`, which leaves the lock without `tx.save()`. Outside the lock, `surfaceMarketplaceFailure` renders `marketplaceFailureRows(name, scope, "unreadable", cause)` (standalone) or returns the failed outcome (orchestrated). `surfaceLayerGateStop` now uses the same helper.
  - `fullRemovePlan` lists explicit records only. `cascadeDependencies` orders the dependency records under the marketplace: `pruneOrphansReachableFrom` for a layer remove and `pruneOrphans` for the full remove, both over the removal keys. Before each unstage it re-checks `isHeldBy(index, gone, key)`, where `gone` holds only the keys that actually unstaged (PRUNE-03). A held member is kept and gets no row.
  - `commitRemove` deletes the state record only when no plugin record remains under it. A kept dependency keeps the record, so the data directory and the clone stay (the plan 04 record-deleted key gates them), while the full remove still sweeps both config files.
- Fixture: `OfferedPlugin.dependencies` goes into the plugin's own `plugin.json`. `readOfferedPluginsWithDependencies` reads `name, version, dependencies`, and both parsers share a module-private `requireColumns`. `writeDependencyAllowance` extends the manifest's `allowCrossMarketplaceDependenciesOn`, and `allowDependenciesOn` dispatches it by kind (url and github throw the no-stand-in error).
- Two new Givens in `publishing.steps.ts`. Both offer steps share a module-private `offer` helper.
- Five new scenarios in `features/marketplace/remove.feature`.
- Four new integration cases (the file now has seven `test(` cases).

## Decisions Made

- **Explicit-only full plan.** `fullRemovePlan` now lists explicit records only. With no dependency record under the marketplace, this is the same set as before. With one, the dependency records go through the retention order. A dependency nothing holds is still unstaged, after the explicit records.
- **Candidates from the record.** The dependency candidates are read from the marketplace record, not from the index's `candidates`. So the seam stub only has to supply an index, and every holder outside the removal set (another marketplace's plugin, or a plugin the other layer keeps) is present by construction.
- **Orchestrated mode.** Retention and the refusal also run in orchestrated mode. The refusal returns `{ status: "failed", reason: "unreadable" }`. The reconcile planner keeps any recorded marketplace that holds a dependency record (`holdsDependencyRecord`), so reconcile does not reach this today.
- **Measured cause line.** The scenario and the integration case name `lib@tools` (`lib@mp`) as the declarer, not `alpha`. The dependency was recorded first, and the index walks the records in state order and stops at the first one it cannot read.
- **Fixture plugin.json.** The integration fixture writes `dependencies: []` for plugins without dependencies. An empty list declares nothing, so the existing cases are unchanged.
