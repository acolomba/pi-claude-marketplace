# Phase 3.2 Plan 07: Install adds a user-scope marketplace through the add code Summary

**`marketplace add` now runs as three functions: `parseAddableSource` (the S5a/S5b refusals), the lock-free `addMarketplaceToState`, and the post-commit `settleAddedMarketplace`. A project-scope install that needs a marketplace only the user scope records runs the same body inside its own lock, from the user record's raw source, so the project gets its own record and, for a git source, its own clone. When that install does not save, its lock owner removes every clone the adds created before the lock is released. When it saves, each added marketplace is settled as an explicit add settles it.**

## Decisions Made

- **Settle signature.** `settleAddedMarketplace` reads the scope from `locations.scope` instead of taking a separate `scope`. `runAddOutcome` built `locations` from `opts.scope`, so the value is the same.
- **Credential ops.** The ledger passes `opts.credentialOps` through unchanged. The add body defaults it, so a second `?? DEFAULT_CREDENTIAL_OPS` in `install-outcome.ts` would add an untested duplicate branch.
- **List entry shape.** `{ marketplace, cloneDir: string | undefined }`. The ledger pushes the add's result as is, so it has no conditional spread.
- **Observing the save.** The lock owner wraps `withLockedStateTransaction` and gives the body a transaction whose `save` moves the adds to a committed list. A throw after a successful save therefore removes nothing, and the closure bodies are unchanged except for the lock owner's name.
- **Name in the list.** The list holds the name the add recorded, so a mismatched add's clone (`sources/renamed/`) is the one removed.
