# Phase 3.2: Marketplace Layer Partition - Research

**Researched:** 2026-10-16
**Domain:** Pi extension orchestrators (`marketplace add/remove/autoupdate/noautoupdate`), per-scope config layers, the dependency-retention rule, closed-set notification reasons, real-Pi cucumber scenarios
**Confidence:** HIGH for the code facts (every one read this session); MEDIUM for the recommendations on the open design points listed under Open Questions

## Summary

All four verbs already have the inputs they need for the partition, but each one reads the layers wrongly today. `add` checks only `state.json` and, for git kinds, clones before that check (`add.ts:336-353`, `add.ts:894-931`). `remove` resolves the scope from state, loads the target layer only to run the CFG-03 check, uninstalls every plugin in the state record, and sweeps both layers (`remove.ts:514-586`, `remove.ts:475-505`). `autoupdate` synthesizes a missing entry from `source.raw` (`autoupdate.ts:319-337`). The merge replaces whole entries (`config-merge.ts:87-115`). None of this needs a new dependency, schema change, or state field.

D-01 can match the typed source before any clone through `domain/source.ts::samePlannedSource` (`source.ts:712-745`). The reconcile planner already uses that function as the identity rule between a declared source and a recorded one (`plan.ts:134-151`, `plan.ts:299-333`). The planner is the binding constraint: a re-declaration whose source the planner reads as `different` turns into a `source mismatch` at the next reload. So the match must use `samePlannedSource` and nothing looser.

For D-04-dep, `state.json` records only `provenance: "explicit" | "dependency"` and deliberately no declarer list. Its comment says prune re-derives the answer from the installed declarations (`state-io.ts:151-154`). The existing pure machinery answers the question: `buildScopeDeclarationIndex` (`dependency-index.ts:231-255`), `isHeldBy`, and `pruneOrphans` (`dependency-orphans.ts:74-131`). The dependency index walks one state document only (D-05-05, `dependency-index.ts:7-8`). Every install, CMP-3 dependencies included, lands in the target scope's own state (`plugin/shared.ts:502-535`). So a record can never be held by a plugin of another scope. "A plugin of a marketplace in a higher scope" therefore means a project-scope plugin record under a CMP-3-adopted user-scope marketplace, and the scope-wide index already covers it.

**Primary recommendation:** Put one layer gate in `orchestrators/marketplace/shared.ts`. It reads both layer files inside the lock and returns `declared-in-target | declared-only-in-other | declared-in-neither | unreadable`. Call it from `add` (before the clone, after a `samePlannedSource` lookup), `remove`, and the named `autoupdate`/`noautoupdate`, in standalone mode only. Reuse `isHeldBy`/`pruneOrphans` over `buildScopeDeclarationIndex` for retention, change `mergeScopeConfigs` to a field merge for marketplace entries only, and render both refusals as a `(failed)` marketplace header with one synthetic failed child row that carries the reason and the cause. This is the precedent in `autoupdate.ts:229-259` and `add.ts:577-586`.

### Pattern 3: Retention via the existing prune fixpoint (no new graph code)

```ts
// Sketch [ASSUMED names]; the calls are existing exports.
// removed = target-layer keys `*@mp` that are installed under mp (and not declared by the other layer, Q3)
const snapshot = await buildScopeDeclarationIndex({ state: tx.state, locations });   // dependency-index.ts:231
if (!snapshot.ok) { /* fail closed: refuse before any mutation (Q4) */ }

  (c) => c.marketplace.name === mp && c.provenance === "dependency");

// partial (layer) remove: keep only keys reachable from `removed` through snapshot.index (Q2)
// cascade `removed` first, then `order`, re-checking isHeldBy(index, actuallyGone, key) before each (PRUNE-03)
```

`pruneOrphans` treats every holder outside `gone` as present. Those holders are explicit plugins under `<mp>` that the other layer keeps, records under any other marketplace in the scope, and CMP-3-adopted (user-scope-sourced) records. So one call covers both retention clauses of D-04-dep. Skip the whole index build when `<mp>` holds no `provenance: "dependency"` record. Without a dependency record, retention has nothing to decide. Skipping also keeps today's behavior for a marketplace whose manifest is broken, the common reason to remove one.

### Anti-Patterns to Avoid

- **Matching D-01 sources more loosely than the planner:** for example, tilde-expanding or `path.resolve`-ing both path forms. The planner compares `PathSource.logical` verbatim (`source.ts:734-735`). A "matched" re-declaration whose spelling the planner reads as `different` reports `source mismatch` on every reload (`plan.ts:308-333`).
- **Importing `uninstall.ts` (a plugin ledger) from `marketplace/remove.ts`:** ESLint BLOCK C rejects it (`eslint.config.js:490-494`). Compose `dependency-orphans.ts` + `dependency-index.ts` + `cascadeUnstagePlugin` instead.
- **Importing `MarketplaceDeclaredLocallyError` into `marketplace/shared.ts` from `plugin/shared.ts`:** this creates an import cycle (see Pattern 1). Move the class to `shared/errors.ts`.
- **Running layer logic in orchestrated mode:** reconcile (`apply.ts:285-295`, `apply.ts:403-412`) and import (`import/execute.ts:967-976`) derive desired state from the merged view and never write config. Gate every layer rule on `!orchestrated`, as WR-09 already gates write-back (`add.ts:503-513`, `remove.ts:493-495`, `autoupdate.ts:454-465`).
- **Field-merging with assignment into a plain object:** keep `Map` + `Object.fromEntries` for the outer map (`config-merge.ts:93-114`). A `merged[key] = ...` assignment with a JSON key `__proto__` sets the prototype. `config-merge.test.ts:471` pins own-key behavior.

## Findings by Question

### 1. D-01: matching the typed source before any clone

**Today's order:** `runAddInGuard` loads the target layer for CFG-03 (`add.ts:434-447`), then dispatches by kind (`add.ts:449-485`). A git kind clones into staging (`add.ts:907-919`) before `newMarketplaceName` reads the manifest and throws `MarketplaceDuplicateNameError` (`add.ts:336-353`, called at `add.ts:931`). The path kind stats and reads the manifest, then throws the same error (`add.ts:1101-1125`). The header comment records the "one wasted clone per duplicate" trade-off (`add.ts:42-49`). Every recorded name is a duplicate today, whichever layer declares it.

**Recommended match:** after the CFG-03 check and before the kind dispatch, in standalone mode only:

1. Parse once (already done: `source = parsePluginSource(opts.rawSource)`, `add.ts:713`).
2. Collect `state.marketplaces` records with `samePlannedSource(record.source, opts.rawSource) === "same"`. [VERIFIED: `source.ts:712-745`: the github arm compares `owner`/`repo`/`ref`; the path arm compares `planned.logical === current.logical`, where `logical` equals `raw` (`source.ts:24-28`, `pathSource` at `source.ts:661-667`); the url arm compares `sourceLogical`, which is `.git`- and slash-canonical (`source.ts:740-743`).] Exactly one hit gives the recorded name. Zero or several hits fall through to today's flow.
3. Load the other layer. Apply the layer gate:
   - The target layer declares the name: throw `MarketplaceDuplicateNameError(name, scope)`. That gives today's `(failed) {duplicate name}` row on the marketplace subject (`add.ts:288-290`, `add.ts:364-368`).
   - Only the other layer declares it: `writeMarketplaceConfigEntry(current, targetConfigPath, scopeRoot, name, { source: opts.rawSource })` (`add.ts:506-512`). There is no state mutation, no clone, and no `gitOps` call. The success row is `(added)`.
   - Neither layer declares it (a recorded but undeclared marketplace, see Q1): today this is `duplicate name`. Keep it unless the user rules otherwise.
4. Fall-through (no source hit): today's path. A different source whose manifest yields the same name still reaches `newMarketplaceName` and fails `duplicate name` (D-01).

**Spelling consequences (pin them in scenarios, they are user-visible):**

| Recorded | Typed | `samePlannedSource` | D-01 outcome |
|---|---|---|---|
| `{home}/marketplaces/tools` | `{home}/marketplaces/tools` | same | re-declare |
| `~/marketplaces/tools` | `{home}/marketplaces/tools` | different (raw compare) | `duplicate name` |
| `./tools` (project cwd) | `./tools` | same | re-declare |
| `acme/tools` | `https://github.com/acme/tools` | same (both `github` kind, `source.ts:727-733`) | re-declare |
| `https://h/acme/tools.git` | `https://h/acme/tools` | same (`.git` canonical) | re-declare |
| `acme/tools` | `acme/tools#main` | different (`ref` differs) | `duplicate name` |

Do not relax the path rule. The planner's own match is `samePlannedSource` (`plan.ts:145`, `plan.ts:308`). Writing a spelling the planner reads as `different` makes every reload report a `source mismatch` (`plan.ts:322-332`).

**Orchestrated callers:** reconcile never plans an add for a recorded name (`plan.ts:299-317`). Import adds orchestrated with no config write (`import/execute.ts:967-976`). Bootstrap adds standalone with `rethrowPreconditionErrors` and swallows only `MarketplaceDuplicateNameError` (`bootstrap.ts:105-128`). The D-01 rule changes nothing for bootstrap when the shared layer already declares the official marketplace. When only the user's local layer declares it, bootstrap now declares it in the shared layer too, then enables autoupdate there. That is acceptable, but note it in the bootstrap unit test.

**Post-success tail:** cache invalidation and `seedSameRepoPluginMirrors` (`add.ts:752-781`) are harmless on the re-declare path, because seeding is network-free (NFR-5). Calling `tx.save()` on an unchanged state rewrites `state.json` with the same content. The planner may skip it on the re-declare arm, but that is not required.

### 2. D-02 / D-03 / D-04-dep: layer-scoped remove

**Which plugins a layer "declares from" `<mp>`:** the target layer's own `plugins` keys ending in `@<mp>`. This is the same suffix test `cascadeRemoveFromLayer` uses (`remove.ts:459-463`). Intersect that set with the plugin records under `<mp>` in state to get what to unstage. Keys the layer declares but state does not hold are only dropped from the file.

**Dependency provenance:** it is NOT stored. The record carries `provenance: "explicit" | "dependency"` only. [VERIFIED: `state-io.ts:151-154`: `// D-04-01: the mode only. A declarer list would be a cache of another` / `// plugin's manifest that nothing keeps honest; prune re-derives "does` / `// anything still need this?" from the installed declarations instead.` / `provenance: Type.Union([Type.Literal("explicit"), Type.Literal("dependency")]),`] It must be derived. Use the scope declaration index (`dependency-index.ts:231-255`). It reads each record's declarations offline, in the D-05-06 order: the plugin's own manifest first, then the marketplace entry (`dependency-declaration-read.ts:5-10`). It fails closed on the first unreadable record (`dependency-index.ts:22-27`).

**Cross-scope dependency:** a record is never held from another scope. [VERIFIED: `dependency-index.ts:7-8`: `// D-05-05: one state document. The records walked are the target scope's own,` / `// and a plugin installed in the other scope never holds a record here.`] A project-scope install may READ user-scope marketplaces (`collectInstallReachableMarketplaces`, `plugin/shared.ts:502-518`). It copies such a marketplace record into the project state with `scope: targetScope, plugins: {}` (`cloneMarketplaceRecordForTargetScope`, `plugin/shared.ts:526-535`). The closure walk's `installedKeys`/`knownMarketplaces` are target-scope sets (`dependency-closure.ts:129-138`). Consequences:

- When removing in **project** scope, "a plugin of a marketplace in a higher scope" is a project-state record under a CMP-3-adopted marketplace record. It is in the project index, so `isHeldBy` already sees it. No user-state read is needed.
- When removing in **user** scope, no project record can hold a user record. There is a related hazard OUTSIDE this phase's decisions: the adopted project record keeps the user record's `marketplaceRoot`/`manifestPath` (`plugin/shared.ts:530-534`). A full user-scope remove of a git-source marketplace therefore deletes the clone that project records still point at (`remove.ts:719-721`). This is pre-existing behavior. Flag it to the user (Open Question Q7). Do not fix it silently.

**Retention rule (recommended):** see Pattern 3.
- Candidates: `provenance: "dependency"` records under `<mp>` only. CONTEXT's parenthetical says "installed under the marketplace" (Open Question Q2 covers cross-marketplace dependencies).
- A candidate stays if any holder outside the removal set declares it (`isHeldBy`, `dependency-orphans.ts:74-82`). That covers "the other layer declares a plugin that needs it" and "a plugin of a higher-scope (CMP-3-adopted) marketplace needs it". It also covers a plugin of any other same-scope marketplace, which goes beyond the user's literal rule (Assumption A3).
- Fixpoint over chains (`pruneOrphans`, `dependency-orphans.ts:108-131`), then a per-member `isHeldBy` re-check with only the keys that actually left. That is the PRUNE-03/D-05-13 discipline from `uninstall.ts:684-711`, so a failed cascade keeps what it held.
- Partial remove: restrict the pruned order to keys reachable from the removed keys through `snapshot.index`. Then a pre-existing orphan dependency under `<mp>` is not swept by a layer remove (Q2). The full remove sweeps every unheld dependency record under `<mp>`, because today's full remove removes everything.

**"Still declared by the other layer" → keep record and clone:** the full-remove branch is `commitFullRemove` (`remove.ts:475-505`) plus the clone/data-dir cleanup in `runPostRemoveCleanup` (`remove.ts:713-721`). Today both are keyed on `failedPlugins.length === 0`. The partition needs a second key, "no layer declares `<mp>` after this write" (or, in the full remove, "no retained record is left under `<mp>`"). The partial arm deletes only the unstaged plugin records from `record.plugins` and calls `cascadeRemoveFromLayer` on the target layer only. It skips `delete tx.state.marketplaces[mp]` and skips `removePath(marketplaceDataDir|sourceCloneDir)`. It still removes the per-plugin data dirs (`remove.ts:708-711`) and still runs `garbageCollectPluginClones` (`remove.ts:723-728`), which is safe because it derives live keys from the committed state.

**Last layer goes (full remove) with retention:** if a dependency record under `<mp>` is held from outside, `<mp>`'s state record cannot be deleted. The planner already keeps such a recorded-but-undeclared marketplace. [VERIFIED: `plan.ts:261-263`: `function holdsDependencyRecord(mpRecord: ExtensionState["marketplaces"][string]): boolean {` / `return Object.values(mpRecord.plugins).some((record) => record.provenance === "dependency");`] It never uninstalls dependency records (`plan.ts:584-590`). So the state converges on reload. The user-visible side effect: `marketplace list` lists state records (`list.ts:86-112`), so the marketplace still appears after a `(removed)` row (Open Question Q6).

**Undeclared plugins when the last layer goes:** explicit records under `<mp>` that neither layer declares are uninstalled by the full remove (today's behavior). If the remove left them, the next reload's uninstall bucket would sweep them anyway (`plan.ts:556-602`). Dependency records follow the retention rule above.

**Refusal hook:** inside the lock, right after the CFG-03 target load (`remove.ts:542-546`) and before the record lookup and cascade (`remove.ts:548-573`). Nothing is mutated before the gate. For a refusal, do NOT call `tx.save()`. Use a sentinel throw, as `cfgInvalidSentinel` does (`remove.ts:814-853`), so the closure leaves without saving. The scope resolution (`resolveRemoveTargetOrSurface`, `remove.ts:605-621`) stays state-based (CMP-5 project-then-user) and still yields `marketplace not added` when no state holds the name.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |

**Key insight:** the planner (`plan.ts`) is the oracle for "what converges on `/reload`". Every new command-side rule must leave the files and state in a shape the planner reads as steady. Check each new arm against `planReconcile` in a unit test or the convergence integration test (`tests/integration/reconcile-plan-convergence.test.ts`).

## Common Pitfalls

### Pitfall 1: Planner disagreement after a D-01 re-declaration
**What goes wrong:** the add writes `source: rawSource` into the target layer. With the field merge, local's `source` wins. If the planner reads that string as `different` from the recorded source, every reload reports a `source mismatch`.
**How to avoid:** match only on `samePlannedSource(...) === "same"`, and add one convergence test: re-declare, then plan, then expect the empty plan.

### Pitfall 2: The dependency index fails closed on an unrelated broken marketplace
**What goes wrong:** `buildScopeDeclarationIndex` stops at the FIRST unreadable record in the whole scope (`dependency-index.ts:231-255`). A broken manifest anywhere then blocks removing `<mp>`, including a broken `<mp>` itself, the commonest reason to remove one.
**How to avoid:** build the index only when `<mp>` holds ≥1 `provenance: "dependency"` record. On failure, follow Q4.

### Pitfall 3: Plugin-fixture dependencies ignored
**What goes wrong:** a fixture puts `dependencies` in the marketplace entry, but the plugin's own `plugin.json` (which the fixture always writes) is authoritative and declares none (`dependency-declaration-read.ts:5-10`).
**How to avoid:** write `dependencies` into `plugins/<name>/.claude-plugin/plugin.json`.

### Pitfall 4: Refusal that mutates
**What goes wrong:** the gate runs after the cascade or after `tx.save()`, so a refused remove has already uninstalled something.
**How to avoid:** gate right after the CFG-03 load and leave the lock through a sentinel throw (`remove.ts:814-853` pattern). The unit test asserts byte-identical `state.json` and both config files.

### Pitfall 5: Bare-scope named autoupdate aborts on the first scope's refusal
**What goes wrong:** `setMarketplaceAutoupdate` returns after the first non-collected scope failure (`autoupdate.ts:530-535`). A refusal in project scope hides a valid user-scope flip.
**How to avoid:** collect per-scope refusals as not-founds are collected today, and decide after both scopes (Q8).

### Pitfall 6: Two cognitive-complexity gates
**What goes wrong:** `runRemoveLockBody`/`runRemoveOutcome`/`flipOneScope` grow past ESLint `sonarjs/cognitive-complexity` 15 or fallow `maxCognitive` 15 (which disagree), and no `thresholdOverrides` exists.
**How to avoid:** extract each new arm as a module-private helper called as one statement (the 3.1 pattern, `03.1-04-SUMMARY.md` patterns).

### Pitfall 7: fallow dupes between remove and autoupdate refusal code
**What goes wrong:** two near-identical "failed header + child" builders form a clone group (threshold 3).
**How to avoid:** one builder in `marketplace/shared.ts` used by both.

### Pitfall 8: Existing unit tests pin the old semantics

## Open Questions (the orchestrator should put these to the user)

1. **Q1. A marketplace recorded in state but declared in neither layer** (CMP-3-adopted, or retained for a dependency). D-04 says "neither layer keeps today's `marketplace not added` rows", but today's `not added` is keyed on state, and this record IS in state. Literal reading: named `remove`/`autoupdate` refuse with `marketplace not added`, and `add` stays `duplicate name`. Then the user can never remove it by command, and the planner never removes it while it holds a dependency (`plan.ts:261-279`). **Recommendation:** `remove` performs the full remove (zero layers declare it, so "the last layer" is already gone); `autoupdate` refuses `marketplace not added`; `add` re-declares it into the target layer when the source matches (D-01 extended to the neither-layer case).
2. **Q2. Retention candidates and reachability.** (a) Should only dependency records under `<mp>` be candidates, or also cross-marketplace dependencies of the removed plugins (e.g. `a@tools` → `lib@other`)? 3. **Q3. 4. **Q4. The dependency index cannot be read** (D-05-07). Refuse the whole remove before any change (precedent: `uninstall.ts:299-300`, `UninstallRefusedError("unreadable", ...)`), or remove the explicit plugins and conservatively keep every dependency candidate? **Recommendation:** refuse with `{unreadable}` and the cause naming the declarer (index cause text is path-redacted, `dependency-index.ts:34-39`); only reached when `<mp>` holds a dependency record.

6. **Q6. The full remove with a retained dependency:** the `<mp>` state record survives, so `marketplace list` still shows it after a `(removed)` row. 7. **Q7. 10. **Q10. Nameless autoupdate with `--local`:** cover only the local layer, or every layer (ignoring the flag), or a usage error? **Recommendation:** only the local layer, so the flag keeps one meaning. D-06's "every layer" then applies to the flagless nameless form.

## Q7 Follow-up Research: Each Scope Owns Its Marketplace

**Phase touches the upstream contract?** Yes: install scope and marketplace registration.

### Evidence record (claude-code-compat-research)

- **Question:** where does Claude Code register and clone marketplaces, and what does a project-scope install of a plugin write when only the user level knows its marketplace?
- **Claude Code's behavior:**
  1. A marketplace has two layers. Its **declaration** lives in `extraKnownMarketplaces` of a settings file: user, project, or local. Its **fetched state** is machine-global: one `~/.claude/plugins/known_marketplaces.json` per user, plus one clone under `~/.claude/plugins/marketplaces/<name>/`. [CITED: https://code.claude.com/docs/en/plugins/loading, "Check which stage a plugin reached" and "Find plugins on disk", retrieved 2026-10-16: "There is one `known_marketplaces.json` per user, so a marketplace you add in one project is available in every project"; "`marketplaces/<name>/` The clone or download of a marketplace added from GitHub, another Git host, or a URL. A marketplace added from a local `file` or `directory` source has no copy here"]
  2. `claude plugin marketplace add --scope <user|project|local>` chooses **where the marketplace is declared** (default user). `claude plugin marketplace remove --scope <scope>` "Remove[s] the marketplace declaration from a specific settings scope ... Omit to remove it from every scope." [VERIFIED: `claude plugin marketplace add --help` and `claude plugin marketplace remove --help` on 2.1.296, run 2026-10-16, read-only] When another scope still declares the marketplace, upstream keeps the shared state and the installed plugins. [VERIFIED: binary grep, 2.1.296 (`/home/linuxbrew/.linuxbrew/Caskroom/claude-code@latest/2.1.296/claude`): `Removed marketplace '${H}' declaration from ${n}; still declared in another scope, keeping state layer and installed plugins`] This is the same model D-03 adopts for layers.
  3. A project-scope install writes only `enabledPlugins` into `.claude/settings.json`. It writes **no** `extraKnownMarketplaces` declaration there. [VERIFIED: binary grep, 2.1.296: the settings writer of a marketplace declaration is `function j2e(e,n,r="userSettings",s){return ta(r,(h)=>({extraKnownMarketplaces:{...h?.extraKnownMarketplaces,[e]:n}}),void 0,s)}`. Its only callers are `marketplace add` (CLI, scope from `--scope`), the `/plugin` UI add (`"userSettings"`), `install --marketplace` (`"userSettings"`, printing `Successfully added marketplace: ${m} (declared in user settings)`), and the autoupdate toggle, which writes to the settings source that already declares the entry. No install-path caller exists.] [CITED: https://code.claude.com/docs/en/discover-plugins: with `--marketplace`, a new marketplace "is declared in your user settings even when you pass `--scope project`"; "Committing that entry turns the plugin on for your collaborators but doesn't download it to their machines"]
  4. Removing a marketplace from every scope uninstalls every plugin installed from it and removes their `enabledPlugins` entries. [CITED: discover-plugins, "Manage marketplaces"]
- **Confidence:** high for 1, 2, and 4 (docs + help text + binary string). Medium-high for 3: the conclusion rests on a regex search for `j2e(` callers in minified code, and an aliased call would escape it. The docs passage agrees for the `--marketplace` path.
- **Conflicting or unresolved:** none. Upstream has no per-scope clone, so no upstream scenario of the form "a user remove breaks a project plugin" exists. A project plugin whose marketplace is removed everywhere is uninstalled upstream.
- **Pi constraints:** pi already keeps marketplace RECORDS per scope (D-29 / CMP-1..8, recorded decisions), and pi has no machine-global registry.
- **Proposed divergence and license:**
  - The project scope gets its own clone of a git-source marketplace adopted from user scope. License: a recorded project decision. This extends D-29 (per-scope records), and the user's answer to Q7 is the decision. Record it as **D-MF-04** in PROJECT.md.
  - Declaring the marketplace in the project config on install also diverges from upstream (point 3). But pi already does it (CR-02, below), and the user's proposal keeps it.

### Our code today

- **CMP-3 adoption.** A project-target install resolves the marketplace in project state first, then falls back to user state (`resolveInstallMarketplaceSource`, `plugin/shared.ts:462-481`). When it falls back, `install-outcome.ts:479-482` creates the project container with `cloneMarketplaceRecordForTargetScope(source.sourceRecord, scope)`. [VERIFIED: `plugin/shared.ts:526-535`: `return { ...sourceRecord, scope: targetScope, plugins: {} };`] The spread copies `source`, `manifestPath`, and `marketplaceRoot` **unchanged**. A git-source user record has `marketplaceRoot = <user extensionRoot>/sources/<name>` (`add.ts:940`, `add.ts:963-972`). So the project record points into the **user** clone. Dependency members of a cascade go through the same `runInstallLedgerBody` site, so their marketplaces are adopted the same way.
- **CR-02 already declares the marketplace in the project config.** `writeAdoptingConfigEntries` (`plugin/shared.ts:894`) writes the plugin key and, when neither project layer declares the marketplace, writes `{ source: <user record's source.raw> }` into the **same target file** in one batched patch (`synthesizeAdoptedMarketplaceSource` / `synthesizeUndeclaredMarketplaceSource`, `plugin/shared.ts:582-593, 836-876`). The target file comes from `selectDeclaringConfigWriteTarget`: `--local` gives the local file; otherwise the file that already declares the key, otherwise `claude-plugins.json` (`plugin/shared.ts:709-746`). This already matches FIX-03: the marketplace is declared in no project layer, so no refusal applies, and it lands in the plugin's own target layer. The user's "declare it in the project's claude-plugins.json" therefore **already happens**, in the plugin's target layer. Exception: per D-04-02, dependency marketplaces are not declared, and the planner keeps them through `holdsDependencyRecord` (`plan.ts:250-263`).
- **Reload with that declaration plus a CMP-3 copy.** The planner finds a recorded name with `samePlannedSource(record.source, declared.source) === "same"`, because CR-02 wrote the same `raw`, so the state is steady (`plan.ts:299-313`). Reload therefore **never** gives the project its own clone, and the project record keeps pointing into the user clone indefinitely.
- **What breaks today:**
  - `marketplace remove <mp> --scope user` deletes `<user extensionRoot>/sources/<mp>` for github/url sources (`remove.ts:717-721`).
  - After that, every project read of the copied record fails: the manifest at `record.manifestPath` is gone. That breaks project `plugin list/info`, `update`, `reinstall`, a dependency-index build, and an MCP/hooks restage that resolves `${CLAUDE_PLUGIN_ROOT}` under the marketplace root.
  - Project `marketplace update <mp>` is broken **even before** a user remove. It fetches into the **project** `sourceCloneDir(name)` (`update.ts:392-417`), which a CMP-3 copy never created, so `gitOps.fetch` runs on a directory that does not exist (`marketplace/shared.ts:252-263`).
  - Path sources are unaffected: they have no clone, and both records point at the user's own directory.

### Minimal design (recommended): copy the user clone at adoption time

| Option | Network | Verdict |
|---|---|---|
| A. Real project-scope `marketplace add` (clone) during install | **Clones on install**. NFR-5 allows network on `install` only for git-source *plugins* on a cache miss, so this needs an NFR-5 amendment | Reject: changes the network contract |
| B. **Filesystem copy of the user clone** (working tree + `.git`) into project staging, then an atomic rename to the project `sources/<name>` | None (offline) | **Recommend** |
| C. Keep the pointer and re-clone lazily on a cache miss | Network on a later read, which is not an allowed seam | Reject |

**Option B details:**
1. **Where:** at the CMP-3 adoption point (`install-outcome.ts:479-482`), only when `source.sourceScope !== scope` and the source kind is `github` or `url`. A path source keeps today's record copy, because it has no clone.
2. **How:** reuse the `seedOnePluginMirror` construction (`clone-cache.ts:414-466`).
   - `cp(userRecord.marketplaceRoot, locations.sourcesStagingDir(uuid), { recursive: true })`, then `rename` to `await locations.sourceCloneDir(name)`. The staging and `sources/` directories are siblings under the project extension root (D-09), so the rename stays on one filesystem. The `cp` crosses filesystems safely.
   - The copy includes `.git`, so the `origin` remote and the Q-01 ownership marker (`.git/pi-claude-marketplace.json`, `add.ts:809-825`) come along. Later project `marketplace update` fetches therefore work, and `recognizeLeftover` (`add.ts:843-878`) recognizes the directory as the extension's own.
   - The adopted record then sets `marketplaceRoot = projectCloneDir` and `manifestPath = <projectCloneDir>/.claude-plugin/marketplace.json`. Validate with `loadMarketplaceManifest` after the copy.
   - No `gitOps` is needed. The new helper names no git surface, so it stays outside `NETWORK_SEAMS` (BLOCK F). Put it in a new module with its own pair test, for example `orchestrators/plugin/marketplace-adoption.ts`, rather than in `clone-cache.ts` (a network seam).
3. **Atomicity (NFR-1/NFR-3):** the copy runs before the 7-phase ledger. The array of that ledger is a fixed contract, so the copy cannot become an eighth phase. If the ledger or `tx.save()` fails, remove the project clone, as add's MA-9/WR-07 path does (`add.ts:516-531`). A leftover after a crash still carries the marker and a matching origin, so a later adoption or `marketplace add --scope project` recognizes and replaces it (MA-12/13).
4. **Containment (NFR-10):** the destination comes only from `locations.sourcesStagingDir`/`sourceCloneDir`, which refuse a symlinked destination (PS-1). Reads from the user root are allowed.
5. **Concurrency (assumption):** the copy holds only the project lock. A concurrent user-scope `marketplace update` could tear the copy. Mitigation: validate the manifest after the copy, and a later project `marketplace update` repairs the git state. The alternative, also holding the user lock, adds a two-lock ordering that nothing else uses today. Recommend no user lock.
6. **Existing CMP-3 records:** none are repaired (the user ruled to assume state written by new code). Optionally, a CHANGELOG sub-bullet says to reinstall a project plugin that came from a user-scope git marketplace.
7. **Cost:** one extra clone copy per project per adopted git marketplace (disk only).
8. **Declaration:** unchanged. CR-02 already writes it into the plugin's target layer, so "everything flows naturally from there" holds: project `remove` deletes the project clone (`remove.ts:719-721` now has something to delete), project `update` fetches into its own clone, and a user `remove` touches only the user clone.
