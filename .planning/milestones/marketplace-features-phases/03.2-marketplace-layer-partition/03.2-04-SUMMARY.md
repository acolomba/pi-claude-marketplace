# Phase 3.2 Plan 04: Marketplace remove layer partition Summary

**A named `marketplace remove` now changes only its target config layer. It is refused, changing nothing, when only the other layer declares the marketplace. While the other layer still declares it (or cannot be read), the remove drops only the target layer's declarations and the plugins only that layer declares, and keeps the state record, data directory, and clone.**

## Accomplishments

- `orchestrators/marketplace/shared.ts`:
  - `marketplaceFailureRows(name, scope, reason, cause)` returns the one `(failed)` header with one failed child. The child carries the reason and the cause, because a marketplace header carries no cause (SNM-10).
  - `marketplaceLayerVerdict({ target, other, targetIsLocal, marketplace })` is the pure gate. It returns `declared` (with `other: "declares" | "silent" | "unreadable"`), `refused` (with the D-04 reason and error), `undeclared`, or `other-unreadable` (with the basename only). Membership reads go through `ownValue`.
- `autoupdate.ts`: `autoupdateFailedRow` and the block literal are gone. `notifyAutoupdateScopeFailure` calls the builder with `autoupdateFailedReason(err)`. The bytes are unchanged, as the existing autoupdate cases show.
- `shared/errors.ts`: `MarketplaceDeclaredInSharedConfigError` sits after `MarketplaceDeclaredLocallyError`. It has the same shape, and its message is `The marketplace <name> is declared only in claude-plugins.json. Run the command again without --local.`
- `remove.ts`:
  - Standalone only: inside the lock, after the CFG-03 load and the record lookup, `planStandaloneRemove` loads the other layer and calls the gate.
  - `refused` and `other-unreadable` throw `LayerGateStop`, which leaves the lock with no `tx.save()`. Outside the lock, `surfaceLayerGateStop` renders the refusal through `REMOVE_CONTEXT` (cardinality `single`), or reuses `surfaceCfgInvalid` with the other file's basename.
  - A `declared` verdict whose other layer declares the marketplace or cannot be read makes a layer remove. `layerRemovalEntries` picks the record plugins whose key the target layer declares and the other layer does not. On success, `cascadeRemoveFromLayer` runs on the target file only.
  - Every other verdict, and orchestrated mode, makes today's full remove (`commitFullRemove`, both-layer sweep).
  - `runPostRemoveCleanup` removes the data dir and the clone (`removeMarketplaceFootprint`) only when the record was deleted.
- `features/marketplace/remove.feature`: five new scenarios (two refusals, three layer removes). The description now says that a remove works on one configuration file.
- `features/step_definitions/config.steps.ts`: `declares these plugins:` (`id` column plus flattened entry fields; an empty entry gives the `id` column only). It shares `compareDeclarations` with `declares these marketplaces:`, so no clone group forms.
- `tests/integration/marketplace-layer-remove.test.ts`: three cases across add, install, remove, both config files, the state file, the staged skills, and the url clone.

## Decisions Made

- **Unreadable other layer on a layer remove.** It keeps every plugin installed. It may declare any plugin key, so `layerRemovalEntries` returns an empty set, and the target file still drops its entry and keys. This applies A-07 (an unreadable sibling is never read as declaring nothing) to plugin keys. The plan's text names only the marketplace in that case. The rewritten invalid-sibling case pins this.
- **Post-remove cleanup.** `runPostRemoveCleanup` keeps `allPluginsUnstaged` as the MR-7 early return and adds `recordDeleted`. The data dir and the clone go only when the record was deleted. Plugin-clone GC still runs whenever no plugin failed, so a layer remove also reclaims the clones of the plugins it uninstalled. The plan said to replace the key; keeping both keeps GC "as today".
- **Refusal row summary.** Plan 03 measured `Some operations have failed.` for this row. The scenarios state the measured value, not the plan's `A marketplace operation has failed.`
- **Refusal child id.** The child is named after the marketplace, so its `id` reads `tools@tools` in the JSON payload. The scenarios state it as measured.
- **CFG-03 outcome cause.** The outcome's cause naming the other file (Task 2 behavior) cannot be seen from outside. The gate runs in standalone mode only, and that entry point returns `undefined`. The cases pin the rendered header-only row and the unchanged bytes instead.
