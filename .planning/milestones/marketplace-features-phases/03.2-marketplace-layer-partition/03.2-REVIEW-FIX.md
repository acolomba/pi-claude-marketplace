### CR-01: The project-scope install picks dependencies from the user clone but installs from a fresh project clone

**Status:** fixed: requires human verification

**Applied fix:** The user's model: the install acts as if the marketplace had been added to the project first. `resolveTargetScopeMarketplace` (install-outcome.ts) returns the target scope's own record, and when only the user scope records the marketplace it runs the add body first (the plan 07 `addTargetScopeMarketplace`, unchanged in lock, list, and settle semantics). install-flow's `installCatalog` routes every catalog read of one transaction through it: the root allowlist load (the first read, before the walk), the walk's `lookup`, and the pin probe's `marketplaceRecordFor`. So the closure, the cross-marketplace allowlist, the declared dependencies, and the pin probe read the clone each member installs from. A dependency marketplace that only the user scope records is added when the walk first reads it, which is after the walk's trust guards. A dependency whose marketplace add throws is still attributed to that dependency (RESV-06 block), as when its own ledger ran the add. Adds join the transaction's list, so `discardingUnsavedAdds` still removes the clones of an unsaved install, and settles still run after the save.
**RED:** new integration case `LAYER-07 / D-MF-04: a project install reads the dependencies of the plugin from the clone it installs from` (two git doubles with different fixtures: the user clone has `app` with no dependencies, the project clone has `app` declaring `lib`). **Regression guard:** `RESV-06 / LAYER-07: a dependency whose marketplace add fails is named as the failing member` passes on `HEAD` and after the fix (same RESV-06 block).
**Reworked pins:** the dependency integration case now lists the project marketplaces as `upstream` then `tools` (the root marketplace is added first); `XMKT-01 missing install reports a source removed after authorization` now removes both the added project record and the user record before the member ledger (the race window moved before the add); the install-outcome read-count pin moved from 5 to 4 (one fewer read of the record).
**Human verification:** confirm the per-read add order is the intended model, in particular that a dependency marketplace is added on the walk's first read of it (after the trust guards), not before the walk.
