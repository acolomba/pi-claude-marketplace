# Phase 3.2: Marketplace Layer Partition - Context

**Gathered:** 2026-10-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Partition every marketplace mutation that names a marketplace between a scope's two config layers: shared `claude-plugins.json` and local `claude-plugins.local.json` (LAYER-01..03, D-MF-03). The same marketplace may be declared in both layers. A named command without `--local` changes only the shared layer, and with `--local` only the local layer; it fails when that layer does not declare the marketplace.

In scope: `marketplace add`, `remove`, `autoupdate`, `noautoupdate`; the field-level merge of marketplace entries; real-Pi scenarios; unit tests per module.
Out of scope: the plugin verbs' layer partition (LAYER-04..06, Phase 3.3). `marketplace update` (refresh) writes no config file and is unchanged.

**Today's behavior (scouted 2026-10-16):**
- `add` checks only `state.json` (one record per name per scope, no layer field, `persistence/state-io.ts:296-320`), so adding to one layer while the other declares the name fails as `duplicate name` (`orchestrators/marketplace/add.ts:337-350`). A github/url add clones before that check.
- `remove` ignores `--local` except for the CFG-03 check: it sweeps both layers (`remove.ts:446-447`), deletes the state record and the clone, and uninstalls every plugin in the state record (`remove.ts:411-450`).
- `autoupdate`/`noautoupdate` write the flag into the target layer and synthesize an entry when that layer lacks it (`autoupdate.ts:319-337`). Their idempotency reads only the target layer.
- The merge replaces a base entry with the local entry wholesale (`persistence/config-merge.ts:87-115`).

**Upstream parity:** Claude Code has no layered marketplace records; this partition is a project decision (D-MF-03, recorded in PROJECT.md). No divergence from an upstream contract.

</domain>

<decisions>
## Implementation Decisions

### Add (LAYER-01)
- **D-01:** Adding a marketplace to one layer while the other declares it succeeds when the typed source matches the source already recorded for that name in the scope: the verb only writes the declaration into the target layer, reusing the state record and clone, with no second clone and no network. A different source whose manifest yields the same name still fails as `duplicate name`. Adding to a layer that already declares it stays `duplicate name`.

### Remove (LAYER-02, LAYER-03)
- **D-02:** A named `remove` acts only on the target layer and fails, changing nothing, when that layer does not declare the marketplace (D-04 reason).
- **D-03:** When the other layer still declares the marketplace after a remove, the state record and clone stay. The remove uninstalls the plugins the target layer declares from that marketplace, and drops their declarations from that layer only.
- **D-04-dep (user, Q2):** dependency plugins (installed under the marketplace but declared in neither layer) follow the plugins that pulled them in. A dependency installed for a plugin being removed is uninstalled with it, unless it is still needed by a plugin that stays: one the other layer declares, or a plugin of a marketplace in a higher scope (user scope is higher than project scope). A dependency installed for a plugin of a higher-scope marketplace is left alone. When the last layer removes the marketplace, the existing full remove applies under the same retention rule.

### Reasons (LAYER-02)
- **D-04 (user, Q3):** a named command whose target layer does not declare the marketplace fails with a reason that says which layer has it and how to target it, in the user's words "marketplace is local only, use --local". Without `--local` on a local-only marketplace, reuse Phase 3.1's `marketplace declared locally` token and its cause ("The marketplace X is declared only in claude-plugins.local.json. Run the command again with --local."). With `--local` on a shared-only marketplace, add the mirror token (wording at Claude's discretion, e.g. `marketplace declared in shared config`) with a cause that says to run the command again without `--local`. A marketplace in neither layer keeps today's `marketplace not added` rows.

### Autoupdate (LAYER-02)
- **D-05:** named `autoupdate`/`noautoupdate` change only the target layer and fail when it does not declare the marketplace; the entry synthesis is removed for named forms.
- **D-06 (user, Q4):** the nameless form covers every layer: for each marketplace, the flag is set in every layer that declares it. The user confirmed keeping the optional name.
- **D-07 (user, Q5):** marketplace entries merge field by field, local fields winning (`mergeScopeConfigs`), so a local entry without `autoupdate` inherits the shared value and `noautoupdate --local` is a per-machine override. Idempotency (`already autoupdate`/`already no autoupdate`) is judged against the target layer's own value; research must decide how the effective (merged) value is reported when they differ.

### Tests
- **D-08 (user, Q6):** real-Pi cucumber scenarios cover almost every behavior, each failing on today's code first (test-first, C-10). Unit tests keep covering individual modules at 100% direct coverage. If a behavior cannot be reached by a scenario, the planner flags it and the orchestrator asks the user before relying on a unit test alone. LAYER-03 scenarios install plugins into each layer as setup, reusing the plugin steps Phase 3.1 added.

### Research follow-up answers (user, 2026-10-16)
- **D-09 (Q1-Q6, Q8-Q10):** the researcher's recommendations in 03.2-RESEARCH.md "User Answers (2026-10-16)" are locked: a marketplace recorded but declared in neither layer is fully removed by a named `remove`, refused `marketplace not added` by `autoupdate`, and re-declared by a same-source `add`; a layer remove takes only dependency records under the marketplace that the removed plugins pulled in, and the full remove sweeps every unheld dependency under it; a plugin key declared in both layers stays installed and only the target layer's key is dropped; an unreadable dependency index refuses the remove with `{unreadable}` before any change; the full remove also drops the other layer's dangling `*@mp` plugin keys (never a marketplace entry); a full remove that retains a dependency keeps the state record and is documented in the catalog; named autoupdate without `--scope` refuses only when no scope's target layer declares the name; nameless autoupdate omits undeclared marketplaces; nameless autoupdate with `--local` covers only the local layer (flagless covers every layer).
- **D-10 (Q11, Claude decides):** the field merge applies to marketplace entries only; plugin entries keep the wholesale merge (LAYER-05 in Phase 3.3 keeps a plugin in one layer). The behavior change (a local entry without `autoupdate` now inherits the shared value) gets a CHANGELOG line.
- **D-11 (Q7, D-MF-04):** each scope owns its marketplace records and clones. A project-scope install that uses a user-scope marketplace makes the marketplace a project-scope marketplace exactly as if it had been added there: the marketplace is declared in the project config (the plugin's target layer; the config is desired state) and the project record is a real project-scope record with its own clone, never a copy pointing into the user clone. **Revised (user, 2026-10-16):** no adoption-only path. The install adds the marketplace to the project through the same code as `marketplace add --scope project` (a lock-free add body split out of `add.ts`), so leftover directories, cleanup, and the record shape are exactly those of an explicit add; a failed install discards the add like a failed add. A git source is therefore cloned once from the network on that install; NFR-5 is amended (D-MF-04). Accepted consequences: a relative user-scope source resolves from the cwd as an explicit add would; no separate `(added)` row; the marketplace lists under the project header; reload/import adds write no config (WR-09). This also applies to marketplaces adopted only for dependencies: they get a project clone and a project config declaration (reverses D-04-02). Afterwards every marketplace verb behaves per scope: named forms act on the resolved scope, nameless forms on all. Records written by older code are not repaired (CR-01 ruling). Proof: an integration test that fails first on today's code (user-scope git marketplace, project-scope install, user-scope remove, then project list/info/`marketplace update` still work), plus scenarios with `@url`/`@github` rows that turn on with Phases 9/10.
- **D-12 (Q12, test placement):** a paired unit test calls only its module's functions (more than one only when they produce state consumed by each other); dependencies in other modules are always mocked. Module boundaries follow conceptual integrity, never test convenience. Behavior a real-Pi scenario cannot reach gets a separate integration test under `tests/integration/`. The researcher's classification of the seven unreachable items stands.

### Claude's Discretion
- The mirror reason token's exact wording and its catalog/JSON doc rows.
- How `add` matches the typed source against the recorded one (raw string vs parsed logical source) before any clone.
- Whether dependency provenance already exists in `state.json` or must be derived from the dependency closure; research decides.

</decisions>
