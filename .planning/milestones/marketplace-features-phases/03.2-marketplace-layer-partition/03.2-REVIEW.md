## Summary

Scope: `git diff 208bbedb HEAD` over the phase's production files, features, owner and integration tests, and the docs, CHANGELOG, and README files. I read the full production diffs and the surrounding code they call: `withLockedStateTransaction`, `buildScopeDeclarationIndex`, `pruneOrphans`, the reconcile planner's marketplace diff, the cascade walk, and the add clone body.

Several parts are sound:

- **Lock and rollback.** The layer gate and the declaration-index refusal both leave the lock without a save. The install's add body takes no lock of its own. `discardingUnsavedAdds` removes unsaved clones inside the lock, and the settle runs only for adds that were saved.
- **Field merge.** It keeps own-key safety through `Map` and spread.
- **Orphan check.** The PRUNE-03 re-check is correct.

The main defect is in the D-MF-04 install path. The dependency closure, the cross-marketplace allowance, and the dependency declarations are all read from the **user scope's clone**. The plugin is then installed from the **project's fresh clone**, which is at upstream HEAD. When the user clone is behind upstream, the install can succeed while a dependency is missing.

Other findings:

- Remove retention has gaps: an unremovable broken marketplace, and a layer remove that uninstalls a plugin another plugin still needs, with no warning.
- When the add fails inside an install, its reason token is lost and the row shows an absolute path.
- The docs say a command "changes only the file you target", but full remove and nameless autoupdate also write the other file.
- Both WINDOWS items are real. #96: a scenario pins the wrong JSON id `lib@tools@upstream`. #97: the README command reference is stale.

## Critical Issues

### CR-01: The project-scope install picks dependencies from the user clone but installs from a fresh project clone

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/install-outcome.ts:565-608` (with `install-flow.ts:739-765`, `install-flow.ts:636-654`)

**Issue:** `runInstallCascade` resolves the dependency closure before any member's ledger runs. It reads each subject through `lookupCascadeDependencies`, which calls `resolveInstallMarketplaceSource(... targetState: state)`. At walk time the project state does not record the marketplace yet, so the call falls back to the user record. The walk therefore reads the user clone's `marketplace.json` and the user clone's `plugin.json` (`marketplaceRoot`). `loadInstallRootAllowlist` reads the user clone as well.

Only after that does the root member's ledger call `addTargetScopeMarketplace`. That function clones the source again into `sources/<name>/` at the current upstream HEAD. `preflightInstallResolve` then reads the entry and resolves the plugin from `targetMp`, the new clone (lines 588, 608, 643).

The two clones differ whenever the user marketplace has not been updated recently, which is common because autoupdate is off by default.

Failure scenario:

1. The user scope added `acme/tools` at commit A, where `app` declares no dependencies.
2. Upstream moves to B, where `app` declares `lib`.
3. The user runs `install app@tools --scope project`.
4. The walk sees no dependencies, so the closure is `{app}`.
5. The add clones B, and `app` installs from B without `lib`.
6. The install reports `(installed)` with an unsatisfied dependency. The load-time check flags or disables `app` on the next reload.

The reverse case also happens. A dependency `lib@tools` that the walk resolved from the stale user clone may be missing from the fresh clone, so the member fails `{not in manifest}` after the walk accepted it. Version constraints and the `allowCrossMarketplaceDependenciesOn` policy are decided on the wrong tree in the same way.

The tests do not catch this. The only git-kind proofs are the `@url`/`@github` rows, which are disabled, and the integration test uses one fixture for both clones.

**Fix:** Pick one tree for both the walk and the install. Option 1: run the target-scope add for the root marketplace, and for every user-only marketplace the walk can reach, before `runInstallCascade` and inside the same lock. Then the walk, the pin probe, and the allowlist all resolve through the new project records. Option 2: give the project clone the user record's commit. Check out the user clone's HEAD oid, or clone from the user clone. That keeps the walk's view and the installed tree identical. Sketch of option 1:

```ts
// inside the lock, before runInstallCascade
const rootRecord =
  ownValue(state.marketplaces, marketplace) ??
  (await addTargetScopeMarketplace(state, locations, ledgerOpts, userRecord, add.record));
// the cascade's lookup/marketplaceRecordFor/allowlist now see the project record
```

## Warnings

### WR-01: A broken manifest can make a marketplace impossible to remove, even though every record that cannot be read is one the remove takes away

**File:** `extensions/pi-claude-marketplace/orchestrators/marketplace/remove.ts:704-719`

**Issue:** `readRetentionIndex` calls `buildScopeDeclarationIndex({ state, locations })` with no `exclude`, so it also indexes the records under the marketplace being removed. Feature `remove.feature:189` proves the result. The marketplace's own manifest is broken, so `lib@tools` cannot be read, and the remove is refused.

For a full remove, every explicit holder under the marketplace leaves anyway. Their declarations matter only when one of them fails to unstage, and then MR-7 keeps the record. So the refusal protects nothing.

This combines with the uninstall guard into a dead end. `uninstall alpha` reads `lib`, which cannot be read, so it is refused. `uninstall lib` reads `alpha`, which cannot be read, so it is refused. `docs/dependency-resolution.md` used to name `marketplace remove` as the way out of this mutual refusal. It now says to "repair or update the marketplace manifest first". For a git marketplace whose upstream is still broken, the user has no exit inside the extension except editing files by hand. That conflicts with NFR-2, which says `/reload` must be enough to recover.

**Fix:** Keep D-09's refusal for holders outside the removal set, but do not index the records the remove takes away. Add a set-valued exclude:

```ts
const exclude = new Set(Object.keys(record.plugins).map((p) => `${p}@${marketplace}`));
const result = await args.read({ state, locations, exclude }); // widen exclude to a Set
```

If an explicit member then fails to unstage, keep every dependency under the marketplace. That is the PRUNE-03 conservative arm.

### WR-02: A layer remove uninstalls a plugin that a staying plugin still needs, with no warning, and a declared dependency record skips retention

**File:** `extensions/pi-claude-marketplace/orchestrators/marketplace/remove.ts:577-583, 635-654`

**Issue:** Retention applies only to `provenance: "dependency"` records. `layerRemovalEntries` returns every record whose key the target file declares and the other file does not, and it does not filter on provenance. `fullRemovePlan` does filter out dependency records. The two plans therefore disagree.

Failure scenarios:

1. `alpha@tools` is declared in `claude-plugins.json`, and `beta@tools` in `claude-plugins.local.json` declares `alpha@tools` as a dependency. A shared-file remove unstages `alpha`. `beta` stays installed with an unsatisfied dependency, and the row shows a plain `(uninstalled)` with `info` severity. `plugin uninstall` would mark the same removal `{dependents unsatisfied}`.
2. A dependency record `lib@tools` that the target file also declares, through a hand edit or an entry the config already held (`dependency-resolution.md:127`), goes through the explicit cascade. It is unstaged even when a plugin in the other file holds it. The full remove would keep it.

**Fix:** In `layerRemovalEntries`, filter out dependency records and leave them to `cascadeDependencies`, the same as `fullRemovePlan`. For explicit entries that a staying holder declares (use `findDependents(key, index)` minus `removed`), either stamp `dependents unsatisfied` on the `(uninstalled)` row as `uninstall` does, or refuse. Always read the index on a layer remove, not only when a dependency record exists.

### WR-03: When the other file cannot be read, a layer remove drops the target file's plugin keys but leaves the plugins installed and says nothing

**File:** `extensions/pi-claude-marketplace/orchestrators/marketplace/remove.ts:619-627, 641-643, 663-675`

**Issue:** When the target file declares the marketplace and the other file is `invalid`, `marketplaceLayerVerdict` returns `{ kind: "declared", other: "unreadable" }`. `planStandaloneRemove` then builds a layer plan, and `layerRemovalEntries` returns `[]`. `commitRemove` still calls `cascadeRemoveFromLayer(targetConfigPath, …)`. That drops the marketplace entry and **every** `*@<mp>` key from the target file.

The user sees `● tools [project] (removed)` with no plugin rows and `needs reload: false`. The plugins declared only in the target file are still recorded and on disk, but nothing declares them now. The real uninstall happens later, on the first reload after the other file is repaired, under a reload row the user did not ask for. A record can also stay as a recorded but undeclared explicit plugin.

The catalog documents no row for this path.

**Fix:** Refuse here the same way the target-undeclared arm does. Throw `LayerGateStop` with `{ kind: "other-unreadable", otherBasename }` when `verdict.other === "unreadable"`. The CFG-03 row then names the file to repair, and nothing changes.

### WR-04: Add failures inside an install lose their reason token and show an absolute path

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/install-outcome.ts:487-515`; pinned by `tests/integration/project-install-adds-user-marketplace.test.ts:403-408`

**Issue:** `addMarketplaceToState` throws the add's typed errors: `StaleSourceCloneError`, `UnremovableLeftoverCloneError`, `MarketplaceDuplicateNameError`, `UnreadableSourceCloneError`, and the clone transport errors. `marketplace add` classifies these into `{stale clone}`, `{duplicate name}`, and so on, and it reduces paths to their last segment (NFR-9).

The install goes through `handleInstallThrow` instead, which has no add classifier. The integration test pins this output:

```text
⊘ p (failed)
  cause: stale source clone at /abs/…/.pi/pi-claude-marketplace/sources/mp
```

The row has no reason brace, and the cause carries the full absolute path. D-11 says the install add should behave "exactly as an explicit add", but its failure rows differ, and the output catalog does not document this row.

**Fix:** Wrap the add call in `addTargetScopeMarketplace` with the add's classifier. Export `classifyAddError` (or the reason mapping) from `add.ts`, and reduce paths with `redactAbsolutePaths`. Then the install row carries `{stale clone}`, `{duplicate name}`, `{authentication required}`, or `{network unreachable}` with a path-free cause. Add catalog rows for it.

### WR-05: A mistyped or unavailable plugin name triggers a network clone and possibly a Device Flow prompt before any offline check

**File:** `extensions/pi-claude-marketplace/orchestrators/plugin/install-outcome.ts:565-596`

**Issue:** `preflightInstallResolve` adds the marketplace, which means a network clone and possibly an auth prompt for a private repository, **before** it checks that the manifest lists the plugin and before `requireInstallable`. The test at `project-install-adds-user-marketplace.test.ts:329` proves this: `install ghost@mp --scope project` clones `REPO_URL` into the project and then fails `{not in manifest}`.

Before this phase, that failure needed no network and wrote nothing. The user record's cached manifest already answers the question offline.

**Fix:** Before the add, read the user record's manifest offline. The walk already does this read. Fail `{not in manifest}` there, so the add only runs for a plugin that can be installed.

### WR-06: Path-source re-declaration compares the typed path as a literal string, so a different directory can match and the same directory can fail

**File:** `extensions/pi-claude-marketplace/orchestrators/marketplace/add.ts:396-425`; pinned by `features/marketplace/add.feature` ("another spelling ... fails as a duplicate name")

**Issue:** `samePlannedSource` compares path sources by `logical`, the verbatim string the user typed. The redeclare path then writes the config entry without reading the path.

- **Wrong match:** In user scope, the user adds `./mp` from directory A. Later, from directory B, they run `marketplace add ./mp --local --scope user`. The strings match, so the local file is declared and the row says `(added)`. B/mp is never read: it may not exist, or it may be a different marketplace.
- **Wrong refusal:** `~/marketplaces/tools` and `{home}/marketplaces/tools` name the same directory but fail as `duplicate name`. The new scenario pins this as intended behavior.

Neither case is what the user meant.

**Fix:** For path sources, compare resolved real paths, using the add's tilde expansion plus `path.resolve(cwd, …)` and `realpath`, against the record's `marketplaceRoot`/`manifestPath`. Write the user's spelling only after that check. If the planner must keep string identity, at least `stat` the typed path and require it to resolve to the record's root before re-declaring.

### WR-07: (WINDOWS #96) A scenario pins the wrong JSON id `lib@tools@upstream`

**File:** `features/plugin/cross-scope-install.feature:28`; source `extensions/pi-claude-marketplace/shared/notification-json.ts:410`

**Issue:** `wireRow` builds `id` as `${row.name}@${mp.name}`. A cascade row for a cross-marketplace dependency already carries its marketplace in the name (`lib@tools`), so the wire id becomes `lib@tools@upstream`. That is not a valid `<plugin>@<marketplace>` id. A JSON consumer that splits on `@` reads the marketplace as `tools@upstream`, or `upstream`, instead of `tools`.

The new scenario asserts this wrong value. A fix would therefore make the suite fail, and the scenario cannot detect a regression in the opposite direction.

**Fix:** In `wireRow`, emit `row.name` unchanged when it already contains `@`, or carry the dependency's marketplace on the resolved row and build `id` from it. Update the scenario row to `lib@tools`, then close #96.

### WR-08: (WINDOWS #97) The README command reference still says remove takes "all plugins"

**File:** `README.md:303`, `README.es.md:292`

**Issue:** "Remove a marketplace and all plugins installed from it." / "Elimina un mercado y todos los complementos instalados desde él." Both lines are now false in three ways:

- A remove from one file uninstalls only the plugins that file declares.
- A dependency that another plugin still needs stays, and the marketplace stays listed.
- The remove can be refused (layer gate, `{unreadable}`).

The section at `README.md:179` was updated, but this reference line was not.

**Fix:** Rewrite both lines, for example: "Remove a marketplace from one configuration file and uninstall the plugins that file declares from it. A dependency another plugin still needs stays." Then close #97.

### WR-09: README and CHANGELOG say a command changes "only the file you target", but full remove and nameless autoupdate write both files

**File:** `README.md:179`, `README.es.md:177`, `CHANGELOG.md:5`

**Issue:** README: "A command that writes configuration changes only `claude-plugins.json`, or only `claude-plugins.local.json` with `--local`." CHANGELOG: "`marketplace remove`, `autoupdate`, and `noautoupdate` change only the file you target."

Both are contradicted by the code:

- A named full remove sweeps the other file's `*@<mp>` keys through `commitFullRemove` (`remove.ts` ~531-541, D-09).
- A nameless `marketplace autoupdate` without `--local` writes every file that declares each marketplace (`autoupdate.ts:385-402`, D-06).

The CHANGELOG also leaves out two user-visible changes:

- A full remove now **keeps** dependencies that other plugins need. The marketplace stays listed even though no file declares it.
- `marketplace remove` can now be refused with `{unreadable}`.

**Fix:** Limit the claim to the named forms. Say that the nameless flip covers every declaring file and that a full remove clears the marketplace's plugin keys from both files. Add a CHANGELOG sub-bullet for dependency retention and the `{unreadable}` refusal.

### WR-10: A nameless flip that fails in a later scope or file hides what it already wrote

**File:** `extensions/pi-claude-marketplace/orchestrators/marketplace/autoupdate.ts:308-315, 458-476`

**Issue:** `flipScopes` writes the project scope first. If the user scope then fails, `notifyFlipFailure` reports only that failure and returns `undefined`, so the project rows that already reached disk are never reported. The failure could be the new two-file load hitting an invalid `claude-plugins.local.json` (CFG-03), or a held lock.

This phase makes the trigger more likely. The flagless nameless form now loads and validates **both** files, so a broken local file that used to be irrelevant now aborts the flip.

Inside one scope, `writeFlipPlan` writes the shared file and then the local file. If the second write fails, the first stays written. `autoupdateFailedReason` maps the write error to `{not found}`, which is false.

**Fix:** Keep the rows already collected, and show them together with the failure row (one plural emission). Load every file before any write. Classify config write failures as `permission denied` / `unreadable`, not `not found`.

### WR-11: A scenario title still describes the pre-D-MF-04 model, and the higher-scope retention path is never tested

**File:** `features/marketplace/remove.feature:219`

**Issue:** The title is "Removing a marketplace keeps a dependency that a plugin installed from a user-scope marketplace still needs". Under D-MF-04, `install app@upstream --scope project` adds `upstream` to the project, and the scenario's own line 242 shows the project declaring it. So `app` is a plugin of a **project** marketplace. The behavior tested is retention by a plugin of another project marketplace.

The D-04-dep clause "a plugin of a marketplace in a higher scope" is not exercised anywhere. It cannot happen under D-03-05, which installs a dependency into its dependent's scope. The title misleads the reader, against the cucumber rule that a reader must understand the scenario without opening its steps.

**Fix:** Rename the scenario to "Removing a marketplace keeps a dependency that a plugin of another marketplace still needs". Record in the plan or CONTEXT that the higher-scope clause is unreachable by construction (D-05-05, D-03-05).
