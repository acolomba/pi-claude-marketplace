<objective>
Each scope owns its marketplace records and clones (D-11, D-MF-04), through the code that already
creates them. A project-scope install that needs a marketplace only the user scope records makes it
a project-scope marketplace by running what `marketplace add --scope project` runs: same record
shape, same clone handling, same leftover-directory behavior, same cleanup, same post-commit
settle. The install declares the marketplace in the project config (the desired state), so later
commands and reloads treat it as if it had been added explicitly (user decision, 2026-10-16: no
adoption-only path, no corner case).

Purpose: today the project record adopted from the user scope points into the user's clone, so a
user-scope remove of a git marketplace breaks every project read of it, and a project
`marketplace update` already fails.
Output: three functions in `orchestrators/marketplace/add.ts` shared with the install; the CMP-3
fallback in `orchestrators/plugin/install-outcome.ts` rewired to them; the record-copy helper
removed; per-transaction clone removal and settle in both install lock owners. The integration
proof and the scenarios are plan 08's.

Answers to the coordinator's three questions:
(a) No existing add entry point can run inside the install's lock: `addMarketplace` reaches
`runAddInGuard`, which takes the scope lock itself, and `proper-lockfile` (`retries: 0`) is not
re-entrant; the reconcile add calls `addMarketplace` too. Task 1 splits the add so its body runs
without the lock, as `runInstallLedger` runs the install body for the enable branch (CR-01).
`install-outcome.ts`, the install's lock-free ledger body and not a ledger, may import
`marketplace/add.ts` (ESLint BLOCK C forbids only the plugin ledgers, such as `install-flow.ts`;
`bootstrap.ts` already imports the add); it names no git operation, because the add functions
default their git operations, so BLOCK F holds.
(b) The add body runs inside the install's own transaction, on the same state snapshot, before the
seven-phase ledger. When the install then does not save (a throw or a failure arm), the snapshot
holding the new record is discarded, and the lock owner removes every clone the transaction's adds
created before the lock is released, which is what `runAddInGuard` does when its own write-back or
save fails (WR-07). A failure inside the add body cleans its own staging (MA-9), as in an explicit
add.
(c) Network: yes, once. For a github or url marketplace the first project install that needs it
clones it from its source into the project, exactly as `marketplace add --scope project` does; later
installs find the project record. NFR-5 as written does not allow this: an install may use the
network only for git-source plugins on a cache miss and for a constrained dependency's tag list
(D-03-03), and this is a marketplace clone. It needs a recorded amendment, and PROJECT.md D-MF-04
("a filesystem copy of the user clone, no network") must change with it. The add cannot reuse the
user's local clone without new code: its git arm always clones from the source URL into fresh
staging, its leftover handling only replaces an existing tree, and `isomorphic-git` has no local
file transport. A network-free variant would need a new clone source (for example a transport that
copies the user clone). The user chose the amendment: PROJECT.md now records it in NFR-5 and
D-MF-04, and Task 2's precondition checks that record before any change.
</objective>
