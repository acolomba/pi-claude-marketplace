  3. `rules/features.md`:
     - Scenarios: the three-variant rule for a Scenario Outline counts the rows of every Examples block,
       tagged or not.
     - New section "Source kinds": a behavior that several marketplace source kinds share is one Scenario
       Outline. An untagged Examples block holds the local kinds (`dir` and `file`), an `@url` block holds
       the url kind, and an `@github` block holds the github kind. The kind reaches the steps through a
       `<source kind>` column, and the typed source through a `<source>` column. Tags appear only on
       Examples blocks, and only `@url` and `@github`: a tag on a feature or scenario would also drop its
       local rows. `cucumber.json` runs `not @url and not @github` until each kind has its stand-in: the
       work that adds the url source kind removes `@url`, and the work that adds the github source kind
       removes `@github`. Removing a tag turns on every row of that kind with no feature-file edit.
       A behavior only one kind has lives in a feature file of its own. Add a short Gherkin example
       copied from the ADD-01 Outline in `features/marketplace/add.feature`.
     - New section "Run tokens": a run-specific value is written as a brace token. `{home}` is the sandbox
       home directory: a command expands it, and a result shows it wherever the real path appears.
       `{scenario time}` in a `last updated at` cell matches any exact ISO timestamp between the start of
       the scenario and the check; any other value stays as written and fails (D-05). Tokens never use
       `<...>` (Outline placeholders) or `~` (the product prints `~` itself). Examples cells may carry
       tokens. A stand-in that shows up in output gets its own token the same way (D-03).
     - Data tables: a result with no rows has its own step (`the result lists no marketplaces`), because a
       table with only a header cannot be compared.
  4. `rules/layout.md`, Vertical functions (D-08): when several verbs of one function share steps, a
     topic module under `step_definitions/<function>/` holds the shared ones (for marketplaces,
     `marketplace/publishing.steps.ts`), and each verb has its own `<verb>.steps.ts` beside it. A shared
     topic module never takes a verb's name. A verb module's step text names its verb, so two verb
     modules never define the same text. When a second verb needs a verb module's step, the work that
     finds the second use moves it to the shared topic module, in a commit of its own. Add one sentence
     that `npm run check:features` checks the file families and names this file describes.
  5. `rules/world-and-stand-ins.md`, Fakes and drivers: the driver returns every payload a command emits,
     in emission order, each validated against the published schema. A step that expects one result
     asserts there is exactly one, and never picks one out of several. A command with several payloads
     is compared in two steps: one row per payload, then the rows across the payloads (D-02); when no
     payload carries rows (an info fan-out whose payloads are a marketplace-info and a plugin-info), the
     one-row-per-payload table alone is the whole value. Local
     marketplace fixtures live under the sandbox home directory. The world records each published
     marketplace's source kind and the library dispatches on it, so a new source kind changes library
     code only.
  6. Run `SKIP=npm-check pre-commit run --files <the five files>` and restage until clean.
